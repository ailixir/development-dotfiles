# **Architecture Document: Project "Checks"**

## **1. Overview**

This document outlines the technical architecture and implementation plan for **Project "Checks"**, a centralized orchestration and standardization layer for operational health monitoring at Citibank. The primary goal is to provide a scalable, secure, and maintainable platform that fulfills the requirements detailed in the "Checks" PRD v2.2.

### **1.1. Architectural Principles**

- **Orchestration, Not Replacement:** The system is designed as an orchestration layer that integrates with existing monitoring tools like ITRS, Splunk, Grafana, and AppDynamics, not replace them.
    
- **Decoupled Frontend & Backend:** The React-based single-page application (SPA) will be developed independently from the Python backend services, enabled by a well-defined API contract.
    
- **Scalability by Design:** The architecture must handle a high volume of checks, including resource-intensive UI tests. For the initial build, this will be managed via in-process background tasks, with a design that allows for future migration to a more robust task queue system.
    
- **CSI as the Cornerstone:** The Citi System Inventory (CSI) is the primary organizing principle for all checks, dashboards, and reports.
    
- **Security First:** The design incorporates enterprise security standards from the ground up, including SSO, Role-Based Access Control (RBAC), and integration with a secrets vault.
    

---

## **2. High-Level System Architecture (Simplified)**

For the initial implementation, the architecture is simplified to accelerate development and reduce infrastructure overhead. It consists of four primary logical blocks.

1. **Frontend (Web App):** A React SPA that provides the complete user experience, including the Check Builder, "Checks Studio," dashboards, and reporting.
    
2. **Backend Platform:** A containerized application built with Python (FastAPI). It serves a dual role of providing the API for the frontend and handling the execution of checks.
    
3. **Data & Persistence:**
    
    - **Primary Database (PostgreSQL):** Stores all core data, including check definitions, schedules, historical results, users, and report configurations.
        
    - **Object Storage (S3/Equivalent):** A dedicated store for large binary objects, specifically the video recordings generated by the "Checks Studio" feature.
        
4. **External & Supporting Services:** Critical dependencies the "Checks" platform relies upon.
    
    - **Monitored Systems:** ITRS, Splunk, Grafana, and AppDynamics.
        
    - **Enterprise Services:** The **CSI API**, **SSO (OIDC)**, the **Secrets Vault**, and an **SMTP Relay** for email reports.
        
    - **"Checks Studio" Services:** A **Browser Automation Grid** (e.g., Selenium Grid) and a **Video Processing Service** are required dependencies for the UI testing feature.
        

---

## **3. Frontend Architecture**

The frontend is a modern web application built with React, designed to be intuitive and aligned with the Citi Design System.

### **3.1. Technology Stack**

The UI will be built using the mandatory dependency set provided.

- **Framework:** React 18+ with TypeScript.
    
- **Build Tool:** Vite.
    
- **UI Components:** Material-UI (MUI) v7 and Emotion for styling.
    
- **Routing:** React Router v7.
    
- **Authentication:** `oidc-react` for managing the OIDC authentication flow and `jwt-decode`.
    

### **3.2. Mock Service Strategy**

To enable independent frontend development and facilitate the prototype-first approach, a mock service layer is a mandatory first step.

- **Implementation:** We will use **Mock Service Worker (MSW)**. MSW intercepts outgoing requests from the browser, allowing the UI to be fully developed without any dependency on a live backend.
    
- **Benefit:** This allows the UI team to build and test the entire application, including complex flows like the "Checks Studio," against a predictable mock backend, paving the way for stakeholder demos and approval.
    

---

## **4. Backend Architecture (Simplified)**

The backend is a Python application using the FastAPI framework, designed for simplicity and performance.

### **4.1. Technology Stack**

- **Framework:** Python 3.11+ with FastAPI.
    
- **Asynchronous Tasks:** For the initial implementation, long-running operations (e.g., running a UI test) will be handled by **FastAPI's `BackgroundTasks`**. This avoids the complexity of a separate message broker system like Redis. The API will immediately acknowledge the request while processing the check in a background thread.
    
- **Persistence:** PostgreSQL with SQLAlchemy as the ORM.
    

### **4.2. Key Responsibilities**

- **API Provision:** Exposes a secure RESTful API for the frontend to manage and view all checks, results, and reports.
    
- **Check Orchestration:** Contains the logic to execute checks. This involves making API calls to external systems like Splunk or interfacing with the Browser Automation Grid for UI tests.
    
- **Authentication & Authorization:** Integrates with the enterprise SSO provider to secure all endpoints. It enforces RBAC based on user roles and application ownership.
    

---

## **5. Data and Persistence**

- **Primary Database (PostgreSQL):** Will house structured data for check definitions (e.g., HTTP, Splunk Query, UI Test Steps), schedules, historical results, and report configurations. The CSI will be the primary key for organizing most data.
    
- **Object Storage (S3/Equivalent):** Will be used exclusively for storing video files generated by the "Checks Studio" feature. The database will only store a URL pointer to the video file, which is a scalable approach for handling large binary files.
    

---

## **6. Security**

- **Authentication:** User authentication is handled via the enterprise SSO platform using the OIDC protocol. The frontend will use `oidc-react` to manage the token flow, and the backend API will validate the JWT on every request.
    
- **Authorization (RBAC):** Access control will be managed by the backend, using claims within the JWT to determine which actions a user can perform based on their role and CSI ownership.
    
- **Secrets Management:** All credentials for connecting to databases and external tools will be stored in and retrieved from the enterprise secrets vault.
    

---

## **7. Phased Implementation Plan**

This plan is designed to deliver a functional UI prototype for stakeholder validation and approval before committing to the full backend build.

### **Phase 1: UI Functional Prototype (Stakeholder Approval Gate)**

The goal of this phase is to create a high-fidelity, interactive web application that looks and feels like the final product. The UI will be fully functional but powered by a mock backend service.

**Key Activities:**

1. **Define the API Contract:** Frontend and backend leads will create a strict OpenAPI (Swagger) specification. This contract is the single source of truth for all communication.
    
2. **Setup Frontend Environment:** The UI team will set up the React project using Vite, TypeScript, and all mandatory dependencies.
    
3. **Implement Mock Service (MSW):** The UI team will build a mock API that lives entirely within the frontend codebase, returning realistic, pre-defined data for all user flows. This includes simulating the complete "Checks Studio" flow, which will return a pre-canned video and log output to populate the UI upon clicking "Run Test".
    
4. **Build All UI Components:** The team will develop the complete user interface as specified in the PRD, including the check builder, CSI-centric dashboards, the three-panel "Checks Studio," and the "Live Preview" reporting editor.
    

**Phase 1 Deliverable (Approval Gate):** A deployed, clickable web application demonstrating the complete user journey for all key personas, ready for formal stakeholder approval.

### **Phase 2: Backend Development & Integration (Post-Approval)**

This phase commences only after the UI prototype is formally approved by stakeholders.

**Key Activities:**

1. **Build Core Backend APIs:** The backend team will develop the FastAPI application, implementing every API endpoint exactly as defined in the Phase 1 API contract.
    
2. **Implement Check Execution Logic:** The backend will be built to handle check executions. Simple checks will run synchronously, while complex or long-running checks (Splunk queries, UI tests) will use FastAPI's `BackgroundTasks`. The UI will poll a status endpoint to get the result.
    
3. **Develop Integration Connectors:** The team will build the secure clients needed to communicate with ITRS, Grafana, Splunk, AppDynamics, and the CSI API.
    
4. **Build "Checks Studio" Backend:** This involves creating the service that parses UI test steps and orchestrates the browser automation and video recording services.
    
5. **Switch to Live API:** In the frontend application, the Mock Service Worker will be disabled, and the API client will be reconfigured to point to the live backend endpoints.
    
6. **End-to-End Testing:** A full regression and integration testing cycle will be performed to ensure the live system behaves exactly as the approved prototype did.
