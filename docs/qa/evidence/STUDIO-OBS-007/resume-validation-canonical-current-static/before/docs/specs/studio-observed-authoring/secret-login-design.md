Design only: no code, schema, migration, OpenAPI, test or story file is changed by this document. Every `path:line` below was read on this working tree on 2026-10-09 (HEAD `d954a21c5`); line numbers drift. R3 removes every legacy-compile-path variant (the compile path is retired by STUDIO-OBS-012A): the password-only rule has one adapter and no opt-out; `LOGIN_REQUIRED` is computed from the observation signature on both guided learn and observed replay; migrations follow the ADR-SC-005 D-B re-baseline (V34 absorbed); the backend→runner hop is one TLS/client-certificate hop to one runner process; §10 maps items onto the ADR-SC-005 story set. Incremental re-learn (ADR-SC-005 D-D) does not change this design: a `secretRef` fill in a reused prefix step is replayed by the observed adapter under the same rules.

## 2. Target flow (one page)

```
author: "Enter <var USER> as username" / "Enter <secret PASS> as password" / "Click Sign in" / "Open reports" / …
  classify  → sourceReference{kind:secretRef, intendedSlot:fill.value, referenceName:PASS}; preflight(mayUse + exists), no read
  plan      → model sees step text with the token span masked, the reference (ID), never a value
  materialize → authoredInputs += {kind:secretRef, secretId:PASS}  (no value; hashed into authoredInputsHash)
  propose   → fill.value = {kind:secretRef, sourceInputId}, target = {kind:passwordControl, documentId, generation}  (node-free: the collector never exports a password node)
  prepare   → mayUse recheck (names only); trusted runner proves exactly one visible enabled input[type=password] in the current top-level document
  dispatch  → backend resolve() from Vault (CSI/env/testId/principal scope), RELEASE audit row, send BridgeDispatch.secret on mTLS bridge, erase
  act       → trusted runner re-resolves that unique password input at fill time (0 or >1 ⇒ POLICY_DENIED), origin ∈ allowedOrigins ∩ approvedOrigins, withhold(value) BEFORE fill, fill via the pinned handle
  observe   → next observation is the reached document; knownSecrets scrubs any echo
  publish   → artifact fill value {kind:secretRef, sourceInputId}; inputRecipes {kind:secretRef, referenceName:PASS}; no value anywhere
  replay    → job.secrets/secretOrigins resolved per run by the ordinary dispatch pass, same origin + password rule in the observed adapter, model-free
  stop      → knownSecrets = [], inventory disposed, dispatch frame not retained
```

**4.1 Audit (SEC-9).** New append-only table `studio_secret_use_audit(id, occurred_at, path ∈ {GUIDED,OBSERVED_REPLAY}, execution_id?, session_id?, admission_id?, principal_id, csi_id, environment, test_id, secret_id, vault_version?, outcome ∈ {RESOLVED,NOT_AUTHORIZED,REVOKED,UNAVAILABLE,VAULT_UNAVAILABLE,REVOKED_MID_RUN})`, UPDATE/DELETE refused by trigger, written in the same transaction as the dispatch state change (replay: beside `recordDispatchPolicy`, `StudioDispatcher.java:322`). Never a value. Retention: existing retention pruner window unless Security asks otherwise (§8 Q3). T2 acceptance boundary: One immutable USAGE summary per declared secret under actual owner/attempt/declaration identity is required even for uncertain termination. Known USED may be committed early from verified PROGRESS; unknown and negative usage settle at terminal. Terminal reconciliation recognizes an already committed USED and never creates a second summary. Release/retry/live-recheck events do not create a second usage summary. Guided uses authentic ledger/admission evidence; replay uses authentic sparse `RunnerReport.secretUse`. Wire status remains exactly `USED|NOT_USED|REFUSED`: USED requires positive completed-use evidence, NOT_USED positive no-invocation/unreached evidence, REFUSED positive pre-effect refusal evidence. Missing child result, interrupted effect, mid-step kill or absent entry cannot synthesize NOT_USED or REFUSED. Resolved-but-proven-never-typed remains linked NOT_USED. Actual RELEASE and linked USAGE retain a nonnull resolution `outcome` from exactly `RESOLVED|NOT_AUTHORIZED|REVOKED|UNAVAILABLE|VAULT_UNAVAILABLE|REVOKED_MID_RUN`; RELEASE forbids usage_outcome and USAGE requires it. Audit-only uncertainty for released replay is one USAGE linked to its actual scoped RELEASE with `usage_outcome=UNKNOWN_OUTCOME`, or ACK_LOST only when acknowledgement loss is actually evidenced; neither is a wire status, a resolution outcome, a claimed usage fact or replay authority. Preserve positively committed usage facts. For observed replay, an authenticated PROGRESS report may carry only positively evidenced USED entries in the existing sparse secretUse map. Persist them only in the winning exact execution/accepted-history/attempt/admission/runnerInstance/sequence CAS transaction, after joining the frozen accepted artifact recipe and an actual completed secret-fill PASS receipt in the report. STARTED carries no usage facts; NOT_USED/REFUSED remain terminal-only. Arbitrary runner text, missing keys, failed/started steps, wrong recipes/attempts and payload reduction without supporting receipts cannot establish use. Later FINAL loss, cancel/reaper/unknown or sparse omission cannot overwrite already committed USED. No new wire field or status is introduced. Guided completion retains conservative OK→USED and every non-success→UNKNOWN_OUTCOME for each actual linked consumed secret admission; trusted backend no-send and authentic unreached facts retain their separately proven REFUSED/NOT_USED paths. A generic ledger ACK_LOST label alone never establishes actual acknowledgement loss. **4.2 Password-only fill (SEC-6) — ruling, restated after security review F-1.** The collector never exports a password control (§1), so the model cannot name one and the earlier "`controlType:'password'` at observation" rule was unimplementable. Rule: the model emits `fill(secretRef)` with the node-free target `{kind:"passwordControl", documentId, generation}`; **trusted runner code** resolves the target at `prepare` and again at the moment of the fill — exactly one visible, enabled `input[type=password]` in the current top-level document (frames excluded), pinned as an element handle, origin-checked (§4.3), filled through that handle so a type-flip after resolution fails on the handle. 0 or >1 candidates ⇒ `POLICY_DENIED` with reason `PASSWORD_TARGET_ABSENT` / `PASSWORD_TARGET_AMBIGUOUS`; nothing typed. **Identity continuity (R1-1):** `generation` advances only per observation and `navigation` only on `framenavigated`, so a same-document DOM swap would otherwise let "re-resolve at fill" pick a different element. Resolution therefore runs **inside the collector's isolated world** under the existing `acquire`-style guard — cited `documentId`, `generation`, `observedNavigation === navigation` before and after the in-world call (`browser.ts:304-320`; `invoke` guard `:374`). The element pinned at `prepare` is retained in that world; the fill requires that **the same element** is still attached, still `type=password`, still the unique visible candidate, and that `location.origin` read **in that world** (not `page.url()`) is in `allowedOrigins ∩ approvedOrigins`; any deviation ⇒ `TARGET_CHANGED`, nothing typed; `navigation` is re-checked after the fill. **One function (R1-3):** "visible, enabled password input" is defined once in the isolated-world collector — computed-style visibility plus non-zero box (not viewport), traversal including open shadow roots (`observationCollector.ts:134-137,259-260,418-431`) — and that same function produces `coverage.passwordControls`, the `prepare` resolution and the fill-time check; a `querySelectorAll` resolver is forbidden. Consequences stated: an off-screen but rendered decoy counts ⇒ ambiguous ⇒ refuse; frames and closed shadow roots are excluded ⇒ absent ⇒ refuse. **Form action (R1-2):** the fill is refused with `PASSWORD_FORM_ACTION_NOT_ALLOWED` when the pinned input's owning `form.action` (resolved URL) has an origin outside `allowedOrigins`, or when the input has no owning form and the document origin differs from the observed login document's origin. `GuidedProposalValidator` accepts `passwordControl` only with a `secretRef` value, only for an input whose `sourceStepId` is the fill's step, and only when the cited observation reports `coverage.passwordControls === 1`; the proposal's `executionEvidence` still binds document/generation, so staleness checks are unchanged (I-A1 holds). **Limit (stated; accepted at GA — user default 2026-10-09, ADR-SC-005):** pages with two or more visible password fields (change-password, registration with confirm) are not supported for `secretRef` fills — the author gets `PASSWORD_TARGET_AMBIGUOUS`, nothing is typed, and there is no fallback adapter; a model-supplied ordinal/form narrowing is a reserved extension requiring its own Security review. Likewise a secret into a non-password control (TOTP, API token into a text field) is unsupported: the rule has **no opt-out** on the single path (§8 Q1, decided). Accepted because Vault is `none` in every value set today (GA plan C-3) and no shared environment has ever been deployed (panel 2026-10-09, devops), so no production secret-filling test exists.

## 5. "Blocked by login" — detection and outcome code

**Code:** `LOGIN_REQUIRED` on both paths of the single generation — guided learn and observed replay. **Nature:** an *annotation of a failure that already happened*; it never turns a passing step into a failure or a failing step into a pass. **Detail:** `{stepId|stepIndex, loginStepsPresent}` so the UI can say either "This page asks you to sign in. Add login steps before step N using your secrets" (`false`) or "Your login steps did not sign you in; check the secret and the steps before step N" (`true`).

**Signature S(observation)**, trusted code only, no value reads, top-level document only (frames not inspected), one function for both paths: `observation.coverage.passwordControls ≥ 1` (the structural count the collector exports, §3 — password nodes themselves are never exported, `observationCollector.ts:395-396`) **and** ∃ exported visible+actionable node with `elementType ∈ {button, input}` or `role === 'button'`. The count is document-wide; no same-form correlation is available (R3: the legacy same-form probe is gone with `playwrightAdapter.ts`).

| Path | Where | Fire condition |
|---|---|---|
| Guided | Backend `GuidedTranslationService`, after the observation the current step's proposal attempt was grounded on; uses `coverage.passwordControls` (pin `observation: 3`) plus exported button nodes | The step's attempt ended in a validator rejection, `INSUFFICIENT_EVIDENCE`/`MISSING_SOURCE`, or a `passwordControl` fill proposed without a `secretRef` input **and** S(current observation). `loginStepsPresent` = a `secretRef` fill was dispatched earlier in this session. Session → `FAILED`, result `failure.code=LOGIN_REQUIRED`. |
| Replay | `executor/observedReplay.ts` via the observed adapter, on the action that ends the run with `TARGET_DRIFT` or `POLICY_REFUSED` | The adapter already collected an observation for that action (`observedReplayAdapter.ts`); S(that observation) holds **and** the failing action is not itself a `secretRef` fill. `loginStepsPresent` = an earlier `secretRef` fill was performed in this run. Reported as the replay failure's annotation: `errorCode LOGIN_REQUIRED` with `detail:{stepId, loginStepsPresent}` added to `x-runner-error-codes`; the run stays `FAILED` and the drift step is still named for "Learn again" (incremental re-learn from that step, ADR-SC-005 D-D). |

**False-positive limits (stated).** Registration, change-password and card-CVV pages can match S; the hint then accompanies a run that was already failing, so the cost is a misleading sentence, bounded on guided by the fill-without-`secretRef` trigger and on replay by the drift/refusal trigger. S cannot correlate the button with the password field's form (the count is document-wide), so any page with an unrelated password widget plus any button matches once the step has already failed. Custom/obfuscated login forms without `type=password` are not detected (plain timeout). SSO pages on non-approved origins are blocked earlier by origin confinement and never reach S. Localized button text is deliberately **not** used.

## Optional success-only publication lowering preparation

The unchanged finalize prefix retains the existing document-read transaction and the
abstract user authorization outside it. After successful authorization, an optional
separate owner-to-source capture transaction repeats the original pre-lowering guards,
current source/evidence/basis construction and checked pin selection. It writes no attempt,
progress, receipt or accounting state. The publisher-owned pure lowerer then runs off-lock
on separate owned copies of the captured basis and profile. The retained match cut owns
closed standard-Jackson whole basis/profile/build inputs and their representations; it
contains no cached session, owner, authorization, deadline, key or digest authority.

Actual preparation repeats every original fresh guard/read/strict basis/pin check in order.
Only the original lowerer point may reuse the private successful candidate when the same
publisher and complete fresh JSON, recursive node-kind/shape and serialized representation
match. Otherwise the original locked lowerer runs. Fresh identity, lease/expiry/deadline,
reservation, attempt budget and progress persistence remain unchanged, as do validation,
Core authorization, commit and lifecycle. Legitimate lease renewal is not compared as a
whole mutable owner or cached deadline.

All speculative nonfatal capture/copy/lower/match failures mean unavailable; actual original
preparation establishes the refusal at its original point. No throwable, failure enum or
failure replay is retained. Fatal `Error` can be observed earlier during optional work and
propagates without raw error persistence. The extra transaction/reads, strict basis checks,
pin/resource observations, copies and matching cannot be undone by fallback; stateful getter
or arbitrary override equivalence is not claimed. The same configured contracts instance
and its existing no-eviction compiled schemas are used; no new cache/reload/epoch API exists.
This may add cost or worsen timing. There is no exclusive-cost, latency or C5 PASS guarantee.
No new model, Vault/native call, value read or output sink is added; all existing full TRACE,
privacy, authority and real 1000ms secret renewal requirements remain unchanged.

### Ambient transaction fallback

Optional detached lowering is unavailable when the current thread already has an actual
Spring transaction. The private preparation entry returns null before its extra capture;
default REQUIRED participation cannot be assumed to release existing owner/source locks.
The original prefix, authorization, guarded preparation and downstream validator no-TX
rule remain unchanged. This fallback adds no speculative reads under an ambient transaction.

The optional capture also repeats production current-policy/current-manifest checks and
Core `secretUse.mayUse` permission reads through the original access guard; this is
additional authorized read work, not merely SQL or pure computation. No permission is
cached and no resolved Vault value read is added by lowering preparation.
