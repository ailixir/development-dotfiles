# OBS-007 — observed retry persistence refinement

Owner: Dara, with Aria's completed contract context. Root approved the refinement on 2026-10-10; Lane B owns dispatcher/CAS/grant integration. No SQL oracle is claimed by this design record. Prior V34 migration proof becomes historical until the refined migration and tests run.

AC-13 requires a retryable definite refusal to return to the ordinary dispatch pass, obtain a fresh attempt, and resolve Vault again. The current V34 execution trigger freezes `binding.attemptId`; observed dispatch therefore cannot use the ordinary retry path. The change preserves the accepted revision, source/configuration, scope, profile/build, artifact, learned plan, reference policy and publication provenance identities. It changes no publication or artifact contract and introduces no compatibility.

Root's initial QUEUED assumption is explicitly refined to the stronger existing **owned CLAIMED** seam. A pending observed retry has a live lease owned by the calling dispatcher, no current attempt, admission or persisted admission receipt, and a durable refusal token equal to its previous accepted binding attempt. Merely being queued is insufficient authority to rewrite a binding.

`studio_dispatch_ledger.definite_refusal_attempt_id` records the previous attempt only in the authoritative retryable definite-refusal compare-and-set: DISPATCHING with that attempt, no admission/receipt → QUEUED with `attempt_id=NULL`. Lane B sets this column only after a definite refusal; ambiguous sends, admitted/in-flight attempts, expired/cancelled work and nonretryable refusals do not receive this authority. SQL constrains token minting/consumption to these state transitions.

On the next ordinary pass, under the caller's transaction and live CLAIMED lease, the execution-binding trigger admits exactly one fresh attempt/grant refresh. The binding may change only `attemptId` and `replayGrant`; the grant may change only `grantId`, `attemptId`, `issuedAt`, `expiresAt`. Both attempt and grant nonce must be fresh; all authority/hash fields remain byte-identical, and the new grant expires within 30 seconds. The trigger checks the old attempt against the durable refusal token and checks the calling lease-owner proof. Lane B also conditions its update on the expected lease owner and token.

The refreshed binding is still checked against the immutable published revision and the full closed v3 shape. The existing ordinary pass rechecks current policy/secret authorization and resolves fresh values. `beginObservedDispatch` atomically enters DISPATCHING with the refreshed attempt and clears the token; token reuse, another refresh before send, foreign-owner refresh, stale lease, admitted/receipted or ambiguous refresh all refuse. Values never enter the binding, token, audit or retry state.

Execution and ledger locks must follow the existing dispatcher/admission order (ledger before execution in application transactions). SQL trigger checks supplement the caller CAS; they do not substitute for classification of the runner's actual transport result. The application-level C-4 test must exercise the real observed send/refusal/requeue/fresh-resolution flow, not only a manufactured database transition.

Required actual PostgreSQL oracles: a fully published v3 revision/binding allows a definite-refusal → queued → owned-claim → fresh-attempt refresh; unchanged accepted identities and two different attempts are observed; another refresh/token reuse, wrong owner, stale lease, changed scope/hash/profile, nonfresh attempt/nonce, overlong grant, admission/receipt or ambiguous state refuse; racing refreshers have one winner. V1–V33 and staged V19 remain byte-identical. The migration suite, recorder transaction/idempotency tests and actual Java partition rollover/pruning/least-writer privilege tests must run under root's sole Gradle/PostgreSQL lane.

## Distinct pre-send outage authority (root-approved refinement)

A real Vault outage before any send still has a truthful RELEASE/VAULT_UNAVAILABLE decision. Reusing the accepted binding attempt would collide with the audit's one-decision-per-attempt invariant. Root therefore approved a separate `zero_send_decision_attempt_id`, not a fabricated runner-refusal token. It is minted/replaced only in the same transaction as that actual audit row and a CLAIMED/live-owner/no-attempt/no-admission/no-receipt → QUEUED claim release. SQL joins its attempt to the immutable outage audit decision. On the next owned claim, either refusal or no-send authority must exactly match the current old binding attempt; a stale token cannot grant a second refresh. Both authority columns clear atomically on the new begin-dispatch transition. Repeated outages may replace the no-send token only after the current binding has genuinely advanced and a new outage decision exists. Ambiguous/dispatched/admitted cases cannot mint this token.

The exact lease-owner proof is transaction-local `studio.observed_retry_owner`, compared to the live ledger owner by the execution trigger, alongside Lane B's update CAS owner/token predicates. This records a dispatcher identity, never a value, and expires with the transaction. Caller/ledger lock order stays ledger before execution. Negative tests must include absent/wrong proof and stale lease.

Root approved replacing the active error-code CHECK in V34 with every previous value plus SECRET_TOO_LONG; V20 remains byte-identical. Actual inserts for all existing values/new code and refusal of an undeclared code are required. Root owns the matching Java/OpenAPI/codegen/pin changes.
