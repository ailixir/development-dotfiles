## Teardown design

Keep the production executor at 2 threads / queue 64 / 30-second idle timeout, native daemon threads, and unchanged 15-minute durable redrive window. Add a static queued reservation set alongside TEARDOWNS_IN_FLIGHT; hold that reservation from submission through completion, releasing it on rejection or completion. Both after-commit initial stops and redrive submit through the same helper. Thus no queued-not-started interval can acquire a second slot. Keep the existing in-flight guard and teardownAttempt's bounded resend, acknowledgement validation and durable confirmation untouched.

Replace DiscardPolicy with a value-free rejection handler that increments a pending shed count and rate-limits WARN on the injected service clock, once per 15-minute interval (same default as abandoned WARN, without changing that setting). The handler throws a RejectedExecutionException after recording the shed; the submission helper absorbs it and removes only the in-memory reservation. It never touches the durable teardownRequest. Each emitted WARN reports the accumulated count since the prior emitted WARN, no ids, targets, reason, exception or request data.

Package-private test seam: installTeardownExecutor(ThreadPoolExecutor). It replaces only an idle service executor and requires the injected executor to use the same queue/worker type; tests can saturate a small executor without changing production capacity. The final installer installs the same rejection handler. Red staging first adds only a behavior-neutral installer retaining DiscardPolicy, then adds the test. That staging must compile and fail assertions on old behavior. No red has been executed or is claimed.

Unit tests use unique session ids, a mocked durable repository with mutable row snapshots, a real injected executor blocked by latches (no sleeps), the injected clock, and a logger appender. They prove exactly one WARN in the first interval, no WARN before the boundary, a second accumulated-count WARN at the boundary, intact durable request after shed, one next-tick submission after capacity frees, no duplicate queued or in-flight submission, and confirmation only after the sender acknowledges. Tests own and terminate all their executors.

## Result design (submitted for architect review)

Use one GuidedSessionService.projectResult builder for common v3 result fields. GuidedPublicationResultProjector calls it before overlaying only receipt/publication/currentReadiness. Keep existing receipt-first authority checks and current-head readiness evaluation exactly where they are. Keep the independent evidence installers by passing the caller's evidence projector. Keep the existing presentation instance on each path by passing that projector too if necessary.

Two legacy edge defaults differ today: fallback uses stepIndex.asInt(0) and any present errorCode; receipt path uses stepIndex.asInt(-1) and textual errorCode only. A boolean publicationBase argument retains these exact defaults rather than silently changing behavior. The flag does not grant authority. Direct service reads keep their old default behavior outside the explicit disabled-publication exception.

Exact configuration finding: GuidedPublicationConfiguration installs PublicationLifecycle even when studio.guided.publication.enabled=false; only its started callback suppresses base capture. publication != null is NOT an enabled signal. Proposed package-private @Autowired(required=false) installer receives the existing GuidedPublicationProperties bean, retaining enabled=true for hand-built compositions. No new property key, constructor change or configuration-file edit. The projection reports SUCCEEDED / REFUSED / receipt null only when publication is disabled and there is no publication base; all existing receipt/base paths keep their old publication status rules. This injection choice remains design-only pending Aria/root ruling.

Delete the fallback non-terminal PublicSession shortcut. Architect refinement: the publication-backed controller path keeps its existing publication.status rule (PENDING→202; otherwise 200). The fallback path uses the service's one existing TERMINAL set via package-private terminalOutcome, giving 202 for a live outcome and 200 for terminal. Thus enabled/manual fallback SUCCEEDED/PENDING stays HTTP 200. A regression case pins that edge. The no-publication test is real HTTP via MockMvc, real service and contracts, property explicitly false, and must verify both PREPARING/FINALIZING→202 v3 result and terminal SUCCEEDED→200 REFUSED, null receipt and NOT_PUBLISHED, plus P2/P3 fields. The fixture must demonstrate a session started with publication disabled has no publication base. No provider/model calls.
