## GSMB-DRIVER-02

The pure ownership census, JAVA/UNKNOWN classification, pending and drain decisions derive
from accepted fullcheck resume3 harness a1e7d05ff…9e8aae. Their executable AST bodies match
that exact reference (docstrings excluded). The narrow GSMb adapter applies them separately

proven descendants. Every census-owned key is retained before per-process observations.
Same-start keys survive reparenting; a previously proven Java process cannot become non-Java
by exec or missing observations. UNKNOWN stays pending until reliable current classification
or actual absence/different start. Missing census/identity/poll/receipt observation cannot
supply terminal proof. Unrelated/inherited processes never enter the owned closure.

run_owned never returns/unwinds until the actual Popen child and every observed same-start
owned Java/UNKNOWN identity resolve. An initially unproven child start remains a holding
condition rather than a guessed terminal result. Immediate-child exit alone does not resolve
reparented JVMs. Parent lock is reverified during each drain iteration. Deferred INT/TERM/HUP
record failure and disable keep; they do not kill children, restore under live native work or
release the wrapper. IO, observer and wait exceptions are caught within the drain. Native
log closure occurs after that same drain. A source boundary drains again and verifies exact
lock/helpers before any staging, restoration or next compile. No native phase is restarted
or retried. No inherited/global process is signaled.

A lost/unprovable parent lock causes observation/held failure with no source mutation. A
restoration or original-compile failure remains in the wrapper-held failure disposition and
requires root's separately evidenced recovery. It neither claims restoration nor returns
normally to release the wrapper. The code sends no signal and does not perform an automatic
repair/retry/restart. Arbitrary process kill, machine loss, interpreter crash and storage
failure are not claimed to be recoverable by Python control flow.

## GSMB-DRIVER-03

finalizedSuccess starts false and is assigned only from the complete three ordered b01/b02/
b03 validated receipts plus final original-proof hashes, no sticky error/interruption and
explicit keep. Exceptions always clear it. The final finally decision rereads original proof
bytes/modes and all final seven candidate bytes/modes. No stale earlier true can keep an
unverified unit. A late terminal persistence failure also disables keep, restores/recompiles,
and records incomplete evidence; it does not preserve a now-unproved successful unit.

The collector assessor independently checks actual task/native exits, explicit/fresh task
scope, source/dist/test-input/task collection completeness, exact fresh case/status multisets
against XML, case totals, archive hash/size/mode/original mtime equality, fresh nonempty exec
for each task, native log hash and executed task markers. b03 additionally requires complete
cohort flags and exact invocation/status/afterEach correspondence across both partitions.
These checks do not classify arbitrary nonzero exits as accepted-red or mutation kills.

Journal saves all original bytes/modes and owned new-file state before source writes. It
writes complete same-directory no-follow exclusive temp files, journals their device/inode,
checks content/mode, records rename intent and atomically replaces only the still-bound
original. A partial temp write leaves the original target untouched and removes only its
owned temp inode. A post-rename fault retains the journaled candidate inode for restoration.
Never-staged originals are recognized as original, not mislabeled concurrent edits.

Each restoration path is attempted independently despite another source or receipt IO error.
An existing target must be the exact journal-owned candidate inode/bytes/mode (or an already
verified original/restored state); unexpected user edits are preserved. Owned new files are
deleted only with their exact inode/bytes/mode. Restores use the same atomic journaled method.
Verification checks bytes AND modes and actual absence for previously absent files. Original
compilation is then Popen-owned/drained under the same lock, followed by a second original
bytes/modes check. Failed/incomplete restore or compilation enters held-lock failure, never
ordinary success/unwind. Receipt IO alone cannot abort remaining restoration attempts.
