# Direct Awaitility mapping — authored, not runtime-equivalent proof

The74 POLL rows occupy73 original loops (ids1/2 share one). Each site has a direct Awaitility4.2.2 chain: remaining time from its original absolute monotonic deadline, the original interval, same-thread evaluation, zero Awaitility initial delay, dontCatchUncaughtExceptions and ignoreNoExceptions. No awaitLast/Await.java/shared wait wrapper or dependency/build edit. Installed classfile descriptors and bytecode are inspected only with Python ZIP parsing, not JVM execution.

The original first step runs exactly once outside Awaitility. A do-loop always performs that original body once, including when its caller deadline is already elapsed; a while-loop preserves its original precondition ordering. The first Awaitility callback is a deliberate no-op, so pollDelay(0) does not repeat that first observation/effect. Subsequent callbacks perform one original step after the original interval. PrefixSync's request/lease read therefore does not run twice immediately. For leading-sleep report rows83/86, the caller/initial report remains first and the first actual fresh read remains delayed by the original interval. Original independent post-loop final fresh reads/assertions stay outside the wait unchanged. Local state is copied back in finally so last-value and exceptional exit data remains available as before.

Every original successful stop/return is latched. Original unhandled Exception/Error is stored as the first exact object and immediately rethrown; a later elapsed-time timeout cannot replace it. The direct condition refuses to execute its body again after terminal success/failure. The timeout catcher first rethrows that stored failure, then skips timeout fallback if original success/termination was already observed, even if Awaitility reports elapsed timeout after a late true. Existing independent final reads are preserved; they are not the same as repeating a terminal predicate.

Only H8 row84 has an original timeout-final observation/evidence branch. It runs once from the timeout catcher only if the original body has not already terminally run. A confirmed result or original error, including a private-evidence write followed by assertion failure, prevents a duplicate read/write. If that final call unexpectedly remains nonterminal, the original library timeout is rethrown rather than silently succeeding. This rare library-boundary path remains a named runtime review point, not a fabricated H8 proof.

Interrupt handling is tied to old sleep boundaries. If the original first condition/body succeeds without sleeping, an already-set interrupt flag remains intact. After an unsuccessful original step, Thread.interrupted clears status and throws checked InterruptedException, matching Thread.sleep's old failure/flag contract. Check again before a post-sleep condition, after every false step and in a still-nonterminal timeout catch: Awaitility's sleepUninterruptibly cannot restore a flag and permit silent success/fallthrough. An interrupt set during a genuinely successful original body remains untouched, as the original break/return occurred before its sleep. First failure wins over a later interruption. Original caller catch/restore-interrupt logic remains unchanged. No claim is made to recreate VM-specific native interruption messages/stacks.

The local4.2.2 metadata shows uninterruptible sleep catches InterruptedException and restores status; ConditionAwaiter uses the checked-throwable rethrower, whose safeRethrow0 bytecode is aload_0/athrow. This supports the mapping of the exact checked exception object. It is source evidence, not an executed test of interruption, late success, exception priority or timing. Every95-row entry retains its old timeout classification; `interruption-crosscheck.json` makes per-site first/final/catch behavior explicit.

An absolute deadline is never reset/increased. Every configured interval and deliberate-window value is unchanged. Setup/condition scheduling can still move an evaluation/timeout by up to one old poll turn; exact instruction-level scheduling equivalence is not asserted. Late successful/failed steps are retained rather than replayed. Real runtime boundary proof and independent review remain mandatory before keeping a batch.
