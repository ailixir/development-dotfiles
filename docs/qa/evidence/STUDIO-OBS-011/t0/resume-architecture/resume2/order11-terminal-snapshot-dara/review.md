## Database enforcement and its limits

`V14__guided_sessions.sql:58–80` installs `tr_guided_identity` on every session UPDATE. It freezes session/test/scope identity, limits, versions, source steps, authorization, createdAt and expiresAt, including the scalar test_id and expires_at columns. Once OLD.state is FAILED (or another listed terminal enum), NEW.state must be identical. The CHECK at lines18–21 also requires the document state and scalar state to agree. `V21__guided_session_replaying_prefix.sql:644–708` adds incremental identity/mode/counter guards, without replacing the V14 terminal guard or freezing general progress. The audit searched all22 migration files for replacements/bypasses; all22 are hash-bound unchanged inputs.

These are conditional statements about normal guarded UPDATEs on the same surviving row, with triggers enabled. They do not prove runtime trigger installation, exclude privileged bypass, prove row identity from a filename, or establish that a statement committed. There is no blanket session DELETE trigger or universal append-only history of session progress. Existing FK references can constrain deletion; the audited production paths contain no session DELETE. None of that licenses an unqualified claim that a row could never be deleted/recreated or administratively altered.

`GuidedSessionRepository.save:70–78` validates the document and replaces state/document/progress by session ID; its SQL has no terminal predicate and the repository supplies no immutable-error check. The SQL trigger protects only the listed fields. A direct JSON progress update preserving those fields can pass those guards; no claim that errorCode is database-immutable is valid. The existing source counterexample to **whole terminal-record immutability** is stronger than a hypothetical SQL statement: `teardownAttempt:2771–2780` locks a terminal PENDING row, writes teardownStatus=CONFIRMED, removes teardownRequest, and calls save without changing FAILED. It is reachable after the same stop that persisted FAILED. Late model reconciliation can also change counters/reconciledLateUsage on terminal rows (`:197–239`). Neither path writes errorCode.

## Conditional interpretation without a stop timestamp

The narrow useful conditions are: exact original-source/installed-schema binding; exact same invocation and fourth session/test identity; a genuine snapshot produced by this capture method; no captureFailure/partial file; triggers enabled and no delete/recreate/admin/test bypass for this row; only the audited reachable writer paths between the FAILED assertion and snapshot; no speculative merging with another session. These conditions must be established by the separately scoped evidence review. Merely naming a file “initial” or seeing a matching state does not establish them.

Under those conditions:

* FAILED remains FAILED, so a later cancellation cannot explain away the observed assertion or manufacture its terminal enum.
* Every audited ordinary nonempty errorCode writer that can cause FAILED writes that code in the same transaction as stop(FAILED). Earlier code setters also stop immediately; normal active guards prevent a later unrelated terminal error overwrite. The terminal action sweep excludes the apparently unguarded late-secret helpers. Cleanup confirmation and late usage do not change errorCode. Thus a genuine, preserved, specifically recognized snapshot errorCode can identify a stopping **writer family** without a stop timestamp. RUNTIME_INCOMPATIBLE narrows to failTranslation in this source; it does not choose bootstrap exhaustion, a definite context refusal, other validation, or the underlying runner reason. BUDGET_EXCEEDED has multiple budget writers; INVALID_CONTRACT has multiple translation origins; LOGIN_REQUIRED and the secret-resolution codes narrow different paths. This is conditional call-graph preservation, not an error-code database invariant.
* A preserved bootstrapPhase=CONTEXT_PENDING means the guarded bootstrap writer had reached that committed phase; READY additionally corresponds to finishBootstrap's context/evidence/metadata acknowledgement checks. Neither proves native success at assertion time or a particular runner startup phase. A terminal lifecycle can stop at the same bootstrap phase as failTranslation. Retention can remove the marker, so its absence is weaker evidence.
* The current snapshot does **not** export assignment intent/receipt/live, materialization context identity/live, bootstrap delivery IDs/outcomes/acknowledgements, teardownStatus/request, createdAt/expiresAt/pruned_at, a stop timestamp, owner identity, detail, or a first-writer sequence. It exports materializationPresent, closed bootstrap phase, counters/coordinates, closed continuation, declared obligations, action outcomes and model attempts. Those are useful progress constraints, not substitutes for absent identity/delivery chronology. The source has no generic session stoppedAt/updated_at field to recover from this file.
* The source-defined `closedDiagnostic` maps missing/unrecognized values to OTHER (`:4683–4685`); specifically missing errorCode and an unrecognized code both become OTHER. OTHER must not be treated as proof of no error, a particular error, or a lifecycle writer. Missing numeric fields are omitted, not zero. Snapshot model result status/kind is a later read of attempt rows; late settlement/retention can affect that evidence.

Therefore timestamps are not intrinsically required to distinguish a preserved stop-code writer family, but stronger first-stop or native cause claims still require exact session/context joins and bounded existing diagnostic chronology. The existing snapshot alone cannot supply the original first transport/runner event. A source-only audit cannot establish its actual errorCode/phase, file existence/completeness, or identity joins; none was read here.

This slightly narrows the earlier conservative interpretation: **cleanup ordering does not automatically invalidate a later errorCode/phase as evidence**. The exact improvement is the terminal-state guard plus absence of those field writes on the actual FAILED cleanup path, conditional on identity/provenance/no-bypass. It does not retract the earlier statement that the snapshot is after cleanup, call the entire record immutable, infer the first native cause, or authorize private access.
