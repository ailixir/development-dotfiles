## Story

As a Studio product owner, I want to validate with real nontechnical users that they can author, log in with their secrets, resolve a clarification and re-learn a changed step without learning technical syntax, and to consolidate every gate — including the external compliance, Vault, authorization and deployment-history confirmations — into one honest release-readiness record with an operable runbook, so that the single observed path is released only when the evidence actually supports it.

## Acceptance Criteria

1. **AC-1 — Pilot preparation (gated on D-C).** A consented formative pilot with at least five nontechnical users is prepared on the **login workflow**: a checklist that reaches a login-protected page using `<var USER>`/`<secret PASS>` steps inserted through the OBS-008 reference picker, a grounded ambiguity to resolve, and one edit of a middle step followed by a Run that re-learns only from that step (OBS-015). The pilot script uses the OBS-008 state copy verbatim *(2026-10-16, PO delta D-7: "verbatim" means STUDIO-OBS-008's **shipped** copy, frozen after 008 Done, not the pre-T0 AC text. Since the 008 T0 close-out, the secret-fill `POLICY_DENIED` sentence is struck (A2). "None of these" and a declined side-effect confirmation cancel and focus step N (A3). Replay login and drift copy are keyed on `replayFailure` (A1), and there is no drift copy for a pre-Ready drift (KL-A1-1).)*. The pilot does not start until OBS-009 AC-7 reports the D-C gate passed (≥ 90 %, zero false-pass, zero leak). No external person is contacted or recruited without explicit user authorization; participant access, test secrets and approved origins are identified as prerequisites, not assumed. [ADR-SC-005 D-C "Before any human pilot"; placement map row OBS-010; consensus plan §11]

   **AC-1 obligation: FOCUS-MUTATION-01, the pre-pilot focus-compatibility check.** Inherited from the STUDIO-OBS-015 known limitation FOCUS-MUTATION-01. Sources: Quinn `docs/qa/evidence/STUDIO-OBS-015/execution-20261015/backend/w3-qa-ack02/review.md` §9 and Dex-D5 `backend/w3-d5-diagnosis01/review.md`. Placed by @po (Pax) on 2026-10-16; record `execution-20261015/po-focus-r1-placement/`.

   The problem: before every fill, the runner focuses the field. If anything else on the page changes during that focus, other than a `class` or `style` attribute, the runner refuses the fill as `POST_FOCUS_CHANGED`, and the whole session ends `UNKNOWN_OUTCOME`. Examples of such changes are helper text, an autocomplete list, `aria-expanded` or `data-focus*`. An application whose fields do that cannot be piloted. The pilot participants would never get past such a fill.

   This obligation does not change AC-1's D-C gate or the meaning of any other AC.

   a. **The check, at T0, for every pilot application.**
      - Pilot applications are the approved staging application with real login, plus any other application a participant will use.
      - Run a real-Chromium probe for every fill target that the pilot script authors. Follow the D5 `probe/probe.mjs` pattern:
        - use the pinned Playwright of the runner;
        - use the collector from the **runner `dist` the pilot will run**, recorded by digest (OBS-009 AC-12 i);
        - install the collector in the isolated world, as `browser.ts` does;
        - perform the fill on the real page.
      - A target **passes** when the fill returns without `POST_FOCUS_CHANGED`.
      - Record the following per application and target:
        - the outcome;
        - the mutation record types and attribute names seen during `focus()`, value-free;
        - the `dist` digest.
      - No secret value is typed into a real application for this check. Password fields are probed with a non-secret placeholder on the approved test account only, or are recorded as "not probed, reason".
   b. **The gate.**
      - Any failing target blocks the pilot **for that application**.
      - The block lifts only when the check passes on a runner `dist` that contains the STUDIO-OBS-009 AC-7 FOCUS-MUTATION-01 change. The check is then re-run, and the new digest is recorded.
      - If a target still fails after that change, the application stays blocked, and the evidence goes to @architect.
      - The block is never lifted by editing the application, adding a tolerance setting or skipping the target. Removing the field from the pilot script is not allowed unless @pm records that the script still covers AC-1's workflow.
   c. **Re-run trigger.** Re-run the check whenever the pilot application's release changes, or the runner `dist` changes, before the next pilot session.
   d. **Release-readiness row (AC-4).** One row named "FOCUS-MUTATION-01" records:
      - the per-application check result and its evidence path;
      - whether the OBS-009 AC-7 change has landed, with its evidence path.

      While any pilot application is blocked or unchecked, the row is pending. It is never passed by omission.
