# ARCH015-05 addendum01: repeated replay versus crossed run authority

Aria. This is an authoritative wording clarification to ARCH015-05, subject to Quinn's independent design readiness review. The original manifest and its seven bound files remain byte-exact. No implementation release, application validation, story QA or lifecycle completion is claimed.

The original ruling's phrase “reuse a previous run's proof” means **reuse the previous run's accepted Launch/admission authority or cross that context with a different Execute**. It does not forbid carrying identical `retainedArtifact` bytes from the same immutable published revision under a separately admitted run. If read as prohibiting those bytes, that phrase conflicts with P04; this addendum resolves that wording edge. There is no additional wire, hashing or algorithm contradiction requiring correction.

`Artifact3` is revision content and contains no ordinary replay run/attempt nonce. Its learned admissions and incremental provenance refer to publication history; they must remain unchanged across ordinary replay. Each newly authorized replay may carry the very same artifact bytes, with the same canonical artifact hash. Do not insert a run nonce, mint another revision, rehash publication history, or require the proof bytes to differ just to run the same revision again.

**P04:** two separate authorized runs R1 and R2 of the same immutable revision may both succeed with byte-identical retainedArtifact A. Each has its own fresh backend admission and accepted immutable Launch context. Execute2 must match Launch2's current run/attempt, profile/configuration/build/scope/policy context and admitted artifact commitment; it must satisfy all original exact projection, input metadata, local retained producer, live safety and resource checks. Current released inputs/secrets use their existing per-run resolution rules; retained reads execute once at their original coordinates per run and recapture fresh values. Model calls remain zero. Reusing A as immutable metadata never means reusing cached captured values or old authorization.

**N05:** reject a prior/crossed Launch or admission offered as R2 authority, Execute1 sent in R2's accepted Launch2 context, mismatched run/attempt/configuration/profile/build/scope/policy identities, or a witness B whose canonical hash differs from Launch2's admitted artifactHash. Changing or supplying an expected hash in Execute cannot replace Launch2's pin. A proof serialized during R1 is **not** rejected merely because it was serialized before R2: if it is exactly A, Launch2 independently admits A, Execute2 matches Launch2 and the complete current projection/checks pass, it is valid P04 reuse. Even if R1 and R2 admit identical A, swapping their run contexts remains invalid. Current one-Execute and terminal-state protections remain per child run.

Required focused cases (all planned, not executed):

1. Positive: two separately admitted executions of one revision, distinct run/attempt/admission IDs, identical retainedArtifact bytes/hash, valid current Execute projections, fresh read results, model0.
2. Positive: reconstruct or reuse the prior serialized A under the fresh R2 admission of A; both forms have the same result. Serialization age is not authority.
3. Negative: Launch2 admits A, but Execute1's run/attempt or previous accepted Launch/admission context is crossed into R2; reject even though artifact bytes/hash equal.
4. Negative: Execute2 identity matches Launch2, but another or modified artifact B hashes differently; reject. The same failure holds for a forged expected hash inside Execute or for metadata/operations differing from the admitted A projection.
5. Negative: changing current configuration/profile/build/scope/policy identities, expired/revoked admission at its existing authorization check, second Execute, terminal-context reuse, or a missing fresh accepted Launch cannot be repaired by identical A. Preserve the original distinction between start-deadline acceptance and the live run deadline after Ready; this addendum adds no deadline rule.

Actual inspected source supports this interpretation: launcher builds runId/attemptId from the current job binding while copying artifact operations; childRuntime checks Execute against its accepted Launch run/attempt/configuration/profile and retains one run state; ObservedReplayAuthorizer mints executionId/attemptId per authorization while referencing the verified immutable revision. No source/schema/test change is made by this addendum.
