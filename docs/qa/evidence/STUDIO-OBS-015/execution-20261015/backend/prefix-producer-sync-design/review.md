## Concrete state split and ordinary precedent

`GuidedRuntime.dispatch` resolves arguments at runtime.ts:336 before adding the admission to the dispatch inventory, before its durable journal consumption and before the native fence. On a successful read, lines 421–424 construct a current-session producer and put `{value,producer}` in the private volatile `values` map, then withhold the fresh value. They do not add it to `this.context.producers`.

The authenticated successful-read callback reaches `GuidedSessionService.outcomeV2`; `GuidedBindingStore.successfulRead` derives the same producer from the actual proposal, successful admission and availability receipt, inserts it in PostgreSQL and bumps materialization metadata revision. No captured runtime value is exported. The subsequent `GuidedMaterializationService.context` assembles that producer in the backend context.

`advancePrefix` reads this fresh context at TranslationService:368 and issues a durable request, but calls `dispatch.preparePrefix` directly at line395. Preparation verifies the prefix identity, evidence, original operation and retained target; it does not resolve the binding argument. Dispatch later requires both the fresh local value **and** a canonically identical producer in `this.context.producers`, plus a current allocation and the admission-qualified supplied edge. The bootstrap context's producer array is still empty. Merely persisting the read or sending the later consumer edge cannot satisfy that producer join.

The ordinary `GuidedDispatchService.prepareAndAdmit` already sends the authoritative context and waits for its accepted response before prepare. For a new prefix coordinate the same synchronization is required. `GuidedRuntime.update` on an existing owned runtime accepts only matching fixed identity/input/policy/program, monotonic metadata, preserved allocations/producers/exercised edges and producers backed by exact live local values. It clones the accepted metadata on the same runtime/handle. It neither invents a local value nor replays the read. Existing qualified-edge and canonical-producer checks should remain unchanged.

This follows bridge-design.md's context-handshake, successful-producer, local-value and qualified-consumer protocol, plus final015 ruling §§3–5. It implements existing semantics; no product decision, wire field, schema, new authority, migration or TS runtime relaxation is needed.

## Exact placement and bounded control flow

The only proposed production file is `backend/src/main/java/com/citi/put/checks/studio/guided/translation/GuidedTranslationService.java`, inside `advancePrefix`, immediately after the complete `captured.has("existing")` branch returns and immediately before the current `dispatch.preparePrefix(captured.path("request"))` call.

Keep all earlier branches and their order:

- `done`: return the current result or committed boundary switch; no new context or preparation RPC.
- confirmation `refresh`: use the existing observation-refresh path and return; do not add a context update or substitute an old preparation.
- existing DISPATCHING: reconcile lost acknowledgement; never send context/prepare/dispatch to retry that uncertain consumed work.
- existing ADMITTED: preserve the existing direct dispatch path and stored proof; consume still supplies only one winning authority. Do not reprepare or attach the new update to this recovery branch.
- any other existing action: retain the current return behavior. No state is reclassified by this repair.

On the remaining new-coordinate path:

1. Call and await the existing `dispatch.pushContext(controller,id,fence)` outside SQL. Its noTransaction guard, fresh session/source/owner checks, authenticated transport, schema validation and reply checks stay in force. Proceed only on its successful return; a sent request or generic HTTP success is insufficient.
2. Catch only to classify `GuidedRunnerClient.definiteContextRefusal(failure)`. On that exact classification, invoke the existing `sessions.failTranslation(...,"RUNTIME_INCOMPATIBLE")` and propagate the refusal. This is the already approved ar-2-r14-stops ruling2: context-only409 plus closed IDENTITY_MISMATCH/SCHEMA, public retryable:false, terminal on first receipt. Keep prior successful prefix actions intact; create no new candidate preparation, admission, ledger or consumer edge. Do not catch-and-continue. Other errors retain their original classification and propagation, with no prepare and no effect retransmission. Do not create a new retry loop or apply bootstrap's three-delivery counter to this phase.
3. After the successful push, take one short `sessions.translationTransaction` before prepare. This rechecks current access, owner/fence/live lease, active session and current source after I/O. Require the pending prefix and READY bootstrap still hold, the session is still in its runnable prefix state, the same immutable program's next coordinate equals the captured coordinate, and no action for that coordinate has appeared. Compare the captured PrefixRequestIdentity's fixed fields/input hash/program hash and evidence hash to the current context/progress. A changed coordinate, evidence, identity, pause or newly stored action refuses as stale through existing closed errors; do not dispatch a newly discovered existing action from this check or mutate its uncertainty. Existing recovery may handle that row on its normal continuation. No network call runs inside this transaction.
4. Send prepare with the **unchanged captured request/digest** after the gate commits. Retain the existing post-prepare translation transaction, response/request/operation/evidence checks, guard/confirmation, storePreparation, admit and consume checks. Those remain necessary for races after the new gate. No lock can be held across remote preparation, and a late source/fence/evidence change still must prevent admission/consumption.

The post-push gate is a revalidation, not a new durable command or authorization token. It can remain local in the same production file. Avoid a common authority refactor, a new helper route or moving context delivery into prepare/consume internals.

## Issued request, context acknowledgement and recapture

`GuidedIncrementalStore.issue` commits PrefixRequestIdentity before this new push. Its digest contains schema/session/worker/fence/scope/context/contextRevision/authoredInputsHash/source/configuration/program/coordinate/evidenceHash. It contains **neither materializationRevision nor leaseExpiresAt**. A successful read changes producer metadata/materializationRevision, not that fixed input identity. A normal metadata context update does not collect an observation, advance generation, change source steps, mutate the prefix program or reset ordinals. Input appends are forbidden while prefix is pending. Thus a legal producer update or newer acknowledged lease does not invalidate the already issued request and is no reason to mint another digest or rewrite its evidence.

The existing helper re-reads its context before sending. It may send newer monotonic metadata or a newer informational lease than the earlier request capture. That is intentional. `GuidedRunnerClient` validates a normal context reply as the existing BridgeIdentity equal to the exact identity it sent; the trusted runtime returns it only after `update` applies the supplied full context. The ordinary same-version acknowledgement does **not** carry materializationRevision, authoredInputsHash or contextHash. Do not describe it as a new cryptographic full-metadata receipt or require append-only acknowledgement fields on version1.

When an actual append delivery exists, the existing delivery ID/contextHash acknowledgement and durable `acknowledgeContext` path remain unchanged. Pending-prefix execution should not create an append delivery. Do not use this fix to acknowledge a different pending payload, extend an issued delivery's lease timestamp or restamp historical bootstrap/proof bytes.

The TS ownership layer retains its real acknowledged claim lease separately; `update`'s context timestamp cannot extend local authority. A legal renewal can advance `liveLease` without changing the prefix request. Preparation deadlines remain derived from the still-live acknowledged authority and session deadline, and stored proofs retain their actual expiry/captured metadata revision. No expiry is copied from the old request, invented from the head, or silently enlarged.

**No request recapture is required for the proven metadata gap.** The post-I/O check must fail on real evidence/input/coordinate changes rather than silently recapturing them. A later normal continuation may obtain a fresh legitimate request for genuinely new evidence, preserving the old immutable issued row and existing per-evidence/budget rules. This keeps observation provenance and idempotency explicit.
