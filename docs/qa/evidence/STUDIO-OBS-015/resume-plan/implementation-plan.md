## Actual stop conditions and narrow decisions

The source anchors and exact counterexamples are in [readiness-findings.json](readiness-findings.json). The following must be resolved before C3b/V21 are installed; no worker may silently solve them by weakening existing invariants.

1. **Base-side authored declarations are not universally recoverable (the explicit T0 STOP fires).** Token `<secret ID>` is recoverable: `GuidedSourceClassifier` treats the token's ID as the declaration ID, its configuration reference uses that ID as `referenceName`, and publication writes it to `ui_test_revisions.references.secrets`. This array contains secret IDs, not display aliases. However accepted step context `{kind:"secretRef",referenceId:"credential-alias"}` carries no secretId; the classifier does not materialize it, and the revision stores neither the variables declarations nor that alias-to-ID mapping. `AuthoringV2Request` contains only globalContext/steps; `AuthoringRevisionInputs` has no secret declarations; `GuidedPublicationRepository` persists only selected/materialized reference names. No query of those four frozen fields can reconstruct the missing mapping. Do not consult current draft variables for the base and do not invent a new column. Recommended narrow option: rule one canonical context reference meaning and persist the complete referenced declaration identity in the existing revision `references` JSON at publication, retaining the `variables`/`secrets` arrays needed by V17. Existing insufficient rows must remain explicitly unreconstructable; D-B recreation or a ruled full learn is needed, never fabricated historical hashes. Alternative: reject context-only secret references; that loses an accepted authoring capability and needs explicit PO/user approval. Token-only success does not clear the general STOP.

2. **Plain text-token values are absent from the base identity.** `AuthoringRevisionIdentity.referencedIds` visits contexts only. For a step using `<var ACCOUNT>` with empty context, `nonsecretReferencedValues` omits ACCOUNT. The publication `references.variables` array preserves its name, not its old valueHash; replay input recipes also preserve the name. A later ACCOUNT value edit cannot be compared using the ruled base-only function. Recommended: extend the existing identity builder to union text-token and context references, preserve its stable ordering, and capture hashes for every referenced plain declaration before new publications. This is an AC-1 correctness fix, not another authoring generation. Add a negative fixture for insufficient old identity; do not hash missing values as `null` or classify the test READY.

3. **Prefix bootstrap and suffix inputs contradict the current materialization invariant.** `GuidedMaterializationService.freeze` requires zero actions and zero existing materializations. V14's materialization trigger permits only `live`/`materialization_revision` changes. Runner `GuidedRuntime.update` requires byte-identical authoredInputs/authoredInputsHash. Yet SOURCE_PLAN after the prefix may select new source spans in the edited tail, unknown at bootstrap. Enumerating every possible substring cannot fit the 200-input bound. Calling SOURCE_PLAN before prefix violates AC-3 and the fresh-binding requirement. Recommended option for architect/PO/Dara review: bounded append-only input materialization within the same session/context/recorded browser, preserving every prior inputId and value/provenance, with a new materialization version and per-preparation immutable input identity. It requires a forward V21 extension, current/previous materialization verification, runner append validation and pure publication validation over the correct version for each admission. Alternative deterministic pre-materialization is viable only with a demonstrated complete source-span representation preserving all current capabilities and bounds; none exists in current code. A second session/browser is rejected by AC-3/6. The existing state-only V21 cannot implement this recommendation.

4. **Produced binding hashes commit future consumers.** T0's learnedStepHash includes the produced binding definition minus session-bound fields. `binding.schema.json` includes `consumers`; consumer coordinates/slots are semantic, so the closed deny-list cannot remove them. Editing/deleting a tail consumer can change a prefix producer's hash despite unchanged prefix authoring. Reusing a removed consumer also fails exact-plan verification. Recommended narrowly amend the hash projection: commit producer-local definition at its producer step and commit each semantic consumer edge at its consumer step, preserving all graph semantics under learnedPlanHash/admissionProvenanceHash. This amends the T0 implementation detail while preserving the existing user ACs; proposed ruling A4 specifies the exact producer/consumer projection for PO validation. It is not a new user-visible scope choice. Moving k earlier to the producer contradicts the specified first-authored-change boundary; omitting consumer commitments everywhere weakens verification. The included counterexample makes this choice reviewable.

5. **Post-consumption drift has no resumable receipt today.** `GuidedRuntime.dispatch` consumes its durable journal entry before its last target check; TARGET_CHANGED emits FAILED and closes the browser. Backend `outcomeV2` makes every non-success terminal. Publication requires one successful action per obligation, ordinal contiguity and exact action/association counts. It cannot just filter out a failed consumed action, reset ordinals or replay already dispatched actions. Pre-admission drift can transition safely today with new orchestration: retain all successful prior ordinals and plan only the remaining actions. For a race discovered after consume but before native invocation, proposed ruling A5 specifies an immutable no-invocation drift receipt and a distinct attempt ordinal. The spent admission is never resent; a newly learned admission performs the still-unperformed semantic operation once. Keep the same browser and retain successful earlier operations. Exact receipt, uniqueness and publication checks are defined in A5 for Dara/PO validation. This preserves the existing behavior without asking the user to choose an internal representation. After native invocation began, an ambiguous effect or lost acknowledgement remains UNKNOWN_OUTCOME with no automatic retry.

The continuation ruling itself is ready to pass to Dara. Import only reused prefix obligations/producers, not the old full-plan suffix: `GuidedTranslationStore.acceptPlan:729-740`, `GuidedBindingStore:60-67` and V14 allocation guards forbid removing old consumers later. Keep prior consumers empty or limited to actually exercised prefix use, then append current-draft suffix consumers. V19 retention at `:274-275` drops new progress keys unless V21 retains a safe bounded summary or the summary is in immutable session/publication identity. V21's V17:515 note must name terminal unlinked USAGE/no-decision, not ordinary RELEASE. The five issues above prevent representing this as a fully implementation-ready state-only contract change. They do not reopen ordinary replay authorization, change the governed-policy ruling, expand into F02, add an authoring compatibility path, or authorize changing V12–V20.
