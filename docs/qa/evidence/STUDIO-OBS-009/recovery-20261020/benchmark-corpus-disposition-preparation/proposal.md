## Exact proposed rule

**EP B2.** Count every frozen workflow, including F/N, toward the corpus minimum and require all three real-model repetitions for every required case on the deployed, pinned stack. For the ≥90% completion metric use the frozen, unambiguous workflows whose authored outcome is expected successful completion (class P). A completion requires clarification-free success, publication and a correct independent outcome oracle. F is an intended assertion failure; N is a predeclared unsupported/ambiguous request. Neither earns a positive completion. Publish F/N outcomes separately; the zero-false-pass and zero-secret/PII-leak obligations apply across the entire corpus and observed attempts. Never move a P run to F/N because it failed, clarified, exhausted a session envelope, or encountered an RS-1 read gap.

This is faithful to ADR D-C/009 AC-7 when recorded prospectively: the required 13 ports already include genuine intended-failure/refusal cases, while the completion metric explicitly addresses unambiguous completion. It does not make refusal an end-to-end success. Source support: 009:152–167; T0 questions §B2; QA composition §§1–3; QA T0 §3.4; EP review §§1.2, 4.2. The recommendations are still unadopted; MODEL-SIZING's use of class-P arithmetic did not itself adopt B2.

**EP B3.** Retain `E3-iframe` as N: this exercises the unsupported iframe boundary, with no publication or forbidden action inside the frame. It does **not** demonstrate successful iframe automation. Current collector source marks iframe as an unsupported/hard surface (`observationCollector.ts:351–353,449–454,569`); T0 §B3 explicitly recommends this classification and identifies cross-frame support as a separate capability/privacy change. The current frozen E3 outcome permits FAILED, AWAITING_CLARIFICATION, CANCELLED or EXPIRED. Therefore report its exact terminal and observations, and describe a clean N result as **no false pass observed**, never “correct refusal” or “iframe supported”; expiry/stall alone cannot establish refusal quality. C12 separately requires an observed clarification. There is no proposed cross-frame implementation or privacy waiver. Architect concurrence must confirm the negative-boundary interpretation fulfils the enterprise-pattern slot; any requirement for successful iframe support is a scope decision, not something this proposal silently supplies.

**RS-1/B5.** Choose the explicit disclosure route permitted by EP review §2.1/§4.4; do not add the optional N-RS1 case. Keep D3 and both existing incremental cases in the explicitly declared `mixedVisible` mode and consume the OBS-015 case files unchanged. This mode is a declared configuration supported by T0 §B5 and QA T0 §3.3, not a page rewrite. It does not test exact-mode non-scalar reads.

Proposed report/readiness wording:

> The local corpus contains zero declared RS-1 workflows by corpus design: D3 and the two incremental cases use mixedVisible, and exact-mode non-scalar reads are not exercised. This is not evidence that non-scalar read gaps do not exist. D2 staging login and E1 approved-origin SSO remain UNKNOWN until their actual pages, authored steps and independent oracles are reviewed. Any required value reachable only through an ungranted non-scalar element is marked as RS-1 without moving the value or changing the page; its failed or clarified runs remain in the class-P completion denominator and in rs1NonScalarReadGaps.

The current manifest correctly gives D3/incremental values explicit reachable `<output>` locations; EP review's historical “every valueLocations is []” is not an exact description of current bytes. Its corpus-design concern remains valid. D2/E1's `isRs1Case:false` plus `UNKNOWN_UNTIL_STAGING_PAGES_ARE_READ` must not be aggregated into a confirmed global zero. Reports need known-local counts and unknown case IDs separately, and explicit run-level zeros only for actually observed runs. No runs means unrun, not a measured zero.

009 RS-1(c) permits PM to close F03 on **zero actual RS-1 cases and zero observed gaps**, citing the completed report. This proposal does not close F03: staging is unknown, T4 unrun, and corpus-design limitations must accompany any later PM disposition. Such a closure would be scoped to the reviewed corpus, not a product-wide capability finding. The exact-mode N-RS1 recommendation outside the P denominator conflicts with AC-7 RS-1(b)'s explicit inclusion rule for unambiguous required reads; it is not adopted. If an actual unambiguous RS-1 workflow is found or later added, keep it P and count its three runs. The harness's blanket `EXACT_MODE_CASE_IN_CLASS_P` prohibition (`evaluate.mjs:151–155`) would then need a narrow correction before that case is admitted; inability to read is not ambiguity. No optional synthetic case is necessary merely to approve the disclosure route.
