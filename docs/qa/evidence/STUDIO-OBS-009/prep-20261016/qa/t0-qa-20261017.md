## 1. A18: does a local Testcontainers Vault count as "a dev Vault" for AC-4?

### Classification

**`REHEARSAL_ONLY_NON_CREDITING`.** A Vault container that our own test starts is **not** "a dev Vault" for AC-4, GO condition 3, the OBS-010 release row, or any Done claim. It is allowed as a named, labelled rehearsal. [I: classification is QA's judgment; each anchor below is [V]]

### Reasons tied to the story text

1. [V] AC-4 says the test proves "the **backend token** reads `studio/{csiId}/{environment}/{testId}/secret/*` only and that write/list outside are denied". The design (I-C9, `secret-login-design.md:144`) makes the policy "Required (deployment)": read granted "to the backend identity only", and calls the Vault side "outside this repository". The thing under test is the deployed backend identity's policy binding. A container whose policy and token we author proves only our own policy text (circular). [I: that circularity is the QA reading]
2. [V] The 009 dependency notes list "dev Vault" among the external prerequisites that are "named at T0 and never faked". The register (U5, `prerequisite-register.json`) names the owner as PUT Core / BFF (ED-02). [V] A prerequisite we provision ourselves is the fake the sentence forbids.
3. [V] GO condition 3: "Done is unreachable while … AC-4's Vault policy test is unrun". The AC preamble: an absent external prerequisite makes the AC "unrun, owner X", "never a pass and never a silent skip". A rehearsal does not turn "unrun against the dev Vault" into "run".

### What the rehearsal can prove

| # | Can prove | Basis |
|---|---|---|
| P1 | Our policy document allows the in-scope read and denies a sibling test, another env, another CSI, list outside scope, write outside scope, and (if intended) update/delete inside scope | [I] standard policy evaluation; limited to the Vault version we pull |
| P2 | `HashicorpStudioVaultProvider` works against real KV v2: bounded read, `cas=0` create, metadata list. This would turn the adapter's own Javadoc inference ("a create-only policy answers a duplicate with 403 is an inference from HashiCorp's documentation, not a verified behaviour") into an observation, for our Vault version only | [V] Javadoc text in `HashicorpStudioVaultProvider.java`; [I] the rest |
| P3 | The capability set the adapter really needs. The design says the policy "grants read" [V], but the adapter does a create (`POST data`, `cas=0`) and a metadata list [V Javadoc: "a bounded read, a create-only write and a metadata list"]. A read-only policy would break save, so the policy text in the OBS-010 runbook must say create + list-on-metadata too | [I] |
| P4 | The path template renders to the same prefix the policy globs. KV v2 policies address `<mount>/data/…` and `<mount>/metadata/…`, not the logical path, so a policy written as `studio/…/secret/*` alone would not match [I: general Vault KV v2 knowledge, not verified in this repo] | [I] |

### What it cannot prove

| # | Cannot prove | Why |
|---|---|---|
| X1 | The deployed mount name, KV version and config (cas required, max versions), namespace, Vault version | a dev-mode container has its own defaults [I] |
| X2 | The auth method and role-to-policy binding of the backend identity; that the backend's real token carries only this policy (no identity-group or `default` leakage); TTL and renewal; that `STUDIO_VAULT_TOKEN_FILE` is mounted from the chart | dev mode uses a root token [I]; design names the token file [V `:144`] |
| X3 | That the runner pod has no network path to Vault | the config refusal (`STUDIO_RUNNER_VAULT_ADDRESS`) and chart/NetworkPolicy render are local; reachability on a real cluster is not [I] |
| X4 | Audit device, retention, and the stated KV v2 version-history residual | Vault-side, outside the repo [V design] |
| X5 | That the Vault under test is the one each environment's backend talks to | environment wiring, ED-02 [I] |

### What *would* count as "a dev Vault" (credit rule)

All of these, recorded in `vault-policy.json` with `mode: "dev-vault"`: [I]

1. The instance is operated by the ED-02 owner (PUT Core / BFF), named with Vault version.
2. The policy under test is read from that Vault (or supplied by the owner) and its sha256 recorded. It is not authored by the test.
3. The token comes through the same auth method and role the deployed backend uses (or is the backend's actual token). The pod need not be deployed.
4. The denial matrix is executed: in-scope read allowed; in-scope create/list as the adapter needs; other CSI, other env, other test, and list/write outside scope denied.
5. The record carries timestamp, tester, and the `dist`/backend build identity.

Only the user can broaden this definition (a new GO-3 decision). QA's classification stands until then.

**Stop rule (kept):** stop issuing sessions when cumulative cost ≥ **80 % of the allocation**, or at the **first hard-gate hit** (false pass, or secret/PII leak).
