# Studio inference architecture integration review

**Date:** 2026-09-16 · **Reviewer:** Aria · **Scope:** integrated stories 10.20–10.26 in `wt/epic`, including the existing dirty integration baseline. This is an independent engineering review, not a formal story QA gate or production approval.

The implemented architecture retains the intended boundary: inference proposes a complete FULL envelope or a scoped PATCH; the backend determines identity/order/source, merges exact retained code, validates the complete artifact, publishes an immutable candidate, and requires confirmation. Execution uses the confirmed positional artifact and contains no inference call. This is an appropriate foundation. The findings below were corrected during integration; the re-review distinguishes verified fixes from pending aggregate test evidence. Live production quality/performance remains gated on external evidence.

### Bounded fix re-review

- **A1 — corrected and focused regression verified.** Publication now refreshes the remaining statement bound before acquiring the guard, before insertion, and after insertion; its final draft UPDATE also compares the immutable request deadline with `clock_timestamp()`. Failed final guards throw and roll back insertion. The real-database regression combines an 800 ms held draft lock and a 1.4-second insert trigger with a two-second request budget, and asserts no candidate row or pointer survives. The earlier expired-capture test also passes.
- **A2 — corrected and focused regressions verified.** Refused work writes a terminal FAILED outcome with positively known zero work. Missing-outcome reads first recover a committed request-linked candidate, otherwise derive failure for expired captures, including swept requests; unknown counts/elapsed usage stay null. The candidate-before-outcome crash case remains CANDIDATE even after the deadline. These projections use durable facts without overwriting a late worker's append-only telemetry. OpenAPI usage fields and frontend types now accept nullable unknown counters.
- **A3 — corrected by inspection; aggregate regression result pending.** Both runner-verdict and assembler mappers now enable `FAIL_ON_TRAILING_TOKENS` alongside duplicate-key rejection. Validator malformed-input cases include a valid verdict followed by an object and by a boolean. The coordinator was asked to add the same two cases to the existing assembler invalid-envelope list before its final aggregate run.
- **A4 — corrected by inspection; aggregate regression result pending.** `/api/v2/studio/**` is included in the idempotency filter. `StudioV2IdempotencyFilterTest` exercises create and compile paths through the actual filter twice with the same key and asserts the downstream mutation chain executes once. This tests the filter mechanism, not cross-replica durable idempotency.

Owner-run evidence inspected directly: `/tmp/studio-inference-aria-fixes.log` reports **BUILD SUCCESSFUL**, 45 tests passed with no skips, including the four added refusal/deadline/recovery regressions. The coordinator owns the final broader aggregate and A3/A4 run results. No further critical defect was found in this bounded re-review; this is not production approval.

### A5 — after-commit capture transaction correction

The coordinator's broader `CompilePipelineIT` run exposed a separate integration defect: the save's `afterCommit` callback still has Spring transaction resources bound, so a `REQUIRED` capture could join completed resources without independently committing the newly captured request before the worker used it. `CompileStateService.capture` now uses `REQUIRES_NEW` through the injected state-service proxy. This is the appropriate boundary: draft locking, refreshed source/configuration, immutable request insertion and compile identity remain atomic inside the new transaction, which completes before worker submission. [Spring's transaction-synchronization documentation](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html#afterCommit()) explicitly calls for a separate new transaction for transactional work in this callback.

All production callers were inspected: v1 explicit compilation uses `NOT_SUPPORTED`, v2 compile is nontransactional, and create/update enqueue only after their save commit. There is no current path where capture suspends an uncommitted transaction holding the same draft lock. Internal self-invocation of `beginCompile` intentionally participates in capture's new transaction. Future callers must preserve this precondition rather than invoking capture while holding an uncommitted same-draft lock.

The correction is accepted by architecture inspection; the coordinator's targeted real save-route `CompilePipelineIT` and nine capture regressions are pending at this amendment. No Gradle task was run by the reviewer. Load validation should include connection-pool headroom: after-commit callers can retain the completed save's connection while the new capture obtains another. This is a capacity concern to measure, not a reason to restore the broken transaction boundary.

## Invariants verified by source inspection

- **Atomic source capture:** `CompileStateService.capture` acquires the draft lock and refreshes the entity before snapshotting source/configuration. Expected source/configuration revisions and authoring hash are checked there. Network calls occur after that transaction returns. This removes the original old-input/new-revision race.
- **Source/scope concurrency:** identity, order, source and scope changes are revision-bearing. V18's authoring trigger prevents metadata/reviewer changes without a newer source revision. V2 no-op updates preserve scope review stamps. Legacy changes invalidate unverifiable authoring identity.
- **Identity and confirmation:** post-cutover revisions are unique by compile request, not artifact bytes. V2 confirmation compares request, candidate, source/configuration and authoring hash; existing confirmation binds artifact hash and performs write-once confirmation under the draft-first lock. V18's old content uniqueness is an explicitly retained compatibility phase; V19 is a separately staged incompatible-publisher cutover, not an automatically applied migration.
- **Baseline ownership/evidence:** `InferenceCaptureStore` scopes candidates and executions to test/CSI, requires confirmed compatible revisions and matching references, and checks retained PASSED/FULL execution identity, configuration fields and actual runtime pins. It normalizes the differing configuration shapes through field comparisons. Config-only reuse has a deliberately narrower no-prior-pass exception; it does not fabricate historical success.
- **Conservative scope:** the planner requires reliable step identity, compatible fingerprint and reviewed scope before generating an affected suffix. Structural edits/unknown scope use FULL; exact source reuse avoids inference. Reviewed scope remains an author assumption, not a claim of mechanically proven English independence.
- **Deterministic assembly:** retained steps require exact ID/text equality with the baseline; retained code is copied directly. Model output cannot provide executable position/source fields. Duplicate/out-of-scope/missing identities and mixed unsupported/code shapes fail. Any unsupported/clarification entry prevents the whole candidate.
- **Complete validation:** generated and reused code traverse the same runner endpoint. The backend checks closed response shape, expected version, source-aligned step count/indexes and aggregate/per-step consistency; no configured-version substitution remains. A rejected retained prefix yields explicit full-rebuild-required diagnostics rather than scope expansion.
- **Immutable lineage:** V18 protects new snapshot/provenance columns by default, enforces capture-to-revision equality, and keeps requests/outcomes/step ownership append-only. Mixed provenance preserves immediate baseline and original generating request/revision instead of relabeling retained code as newly generated.
- **Bounded inference:** compile/gateway concurrency is bounded; one request budget is passed through gateway and validator. The maintained Google Gen AI adapter supplies schema and output-token bounds, disables SDK retries, counts attempts, supports cancellation, and keeps secrets out of prompt inputs. No model-selected dependency/write authority or runtime AI is introduced.
- **Authorization boundary:** v2 authoring explicitly requires an authenticated BFF token and CSI read/write permission before accessing authoring state. IDs cannot cross test ownership; CSI is immutable. `/api/**` authentication and generic rate limiting cover v2. This does not replace the platform's still-external authoritative revocation/identity contract.
- **Execution coherence:** acceptance now holds the draft lock while checking readiness and capturing confirmed revision/configuration, marks new executions FULL, and resolves references through the existing permission path. It does not compile on Run.
- **Feature gates:** v2 routes and incremental compilation default off; v2 writes additionally require the request-identity schema cutover. Gateway enablement remains independent and gated by SPK-01. Local filesystem and remote S3 evidence choices are retained.
