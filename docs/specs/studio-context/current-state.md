# Studio context: architecture assessment

Assessed 2026-09-18 by @architect against this working tree. This is a static source review, not a live LLM/browser evaluation. Existing uncommitted product changes were inspected and preserved. Proposed changes below are design recommendations for this spec pipeline, not implemented functionality. The user's scope response selected both supplied context and live page inspection; both paths are therefore included in the requested specification.

## Finding

The mechanism does not yet satisfy context-aware, page-specific English-to-Playwright execution. A gateway can propose TypeScript, but the visible Run path executes a separate hardcoded English interpreter. Neither path carries global context, per-step context, or page evidence. Increasing prompt detail alone cannot close this execution mismatch.

## Existing architecture is a baseline, not runtime proof

`docs/architecture/studio-execution.md:3` labels itself a design baseline with staging outstanding. Its boundaries are useful and should remain:

- Lines 64 and 74: compilation launches no browser; execution does not compile.
- Line 76: V1 explicitly excludes application DOM as a compiler input. Page evidence is therefore a scope amendment, not an undocumented existing capability.
- Lines 82-88 and 130-134: immutable candidates, stale-result rejection, exact confirmation, and execution from a matching confirmed revision.
- Lines 92-96: bounded inputs, opaque references, pinned runtime/prompt policy, bounded repairs; compile cache remains deferred elsewhere in this design.
- Lines 110-126: one artifact entry per source step, bounded sequences of approved awaited operations, default-deny AST validation, trusted invocation rather than arbitrary code evaluation. A fill-plus-submit search fits this existing sequence rule; the current one-statement prompt is unnecessarily restrictive.
- Lines 138-140: readable interpretation and actionable ambiguity diagnostics.

The Epic 10 manifest (`docs/epics/EPIC-10-EXECUTION.yaml:67-173`) plans the foundational contracts, trusted executor, immutable revisions, compiler, confirmation, browser execution and Run gate. Do not mark those stories complete because classes/comments refer to them. This review found no `studio-runner/` source directory in the working tree.

## Recommended bounded design

1. **One authoritative path.** Persist the current draft with optimistic revision checks before compiling. Compile to validated Playwright source, review and confirm the precise source/context/configuration revision, then execute that immutable artifact. Retire the independent Python/regex interpretation as authoritative behavior when the new path becomes runnable.
2. **Versioned context contract (recommended decision).** Use `authoringSchemaVersion: 2` with typed `steps[{id,text,context}]` and typed test-level `globalContext`; freeze the discriminated request/response shapes in OpenAPI. Adapt legacy string arrays and legacy IR to this authoring shape, assigning step IDs once on persisted migration/save, never per render. Reject mixed or invalid v2 input. This avoids parallel ID/text arrays losing alignment. The existing source artifact remains version 1: the compiler derives ordered original source strings and stores stable-ID mapping/context in the immutable revision metadata; authoring and artifact schema versions are separate. Deletion drops that step's metadata; reorder preserves identity; copying creates a fresh ID. Hash all ordered source, relevant context, page-profile revisions, configuration and compiler/runtime versions into compilation provenance. Metadata changes invalidate confirmation even if English text is unchanged.
3. **Deterministic resolution.** Server policy is never overridable. Explicit current-step action/value wins over defaults; applicable step context overrides global defaults for the same field. Page evidence establishes what is observed, not instructions to obey. Conflicting explicit values or contradictory evidence yield a field-specific diagnostic. Unrelated future steps and other pages' hints do not silently influence the current step.
4. **Grounding inputs.** Support explicit versioned page profiles and live learned observations tied to CSI, environment, origin/route and page state. Include only required accessible names/roles/labels, stable test IDs, field/control relationships, supported submission behavior and selected ready/postcondition cues. Record author/capture source, observation time, profile revision and applicability. Supplied profiles always retain supplied provenance; a user-entered claim of observation cannot become trusted live-observed evidence. Only the trusted capture protocol can mint that provenance. Enforce freshness policy and state applicability before a candidate is ready. This cannot guarantee the live DOM has not changed; execution still enforces locator strictness/actionability and reports drift without secretly rewriting code.
5. **Required Learn-page authoring stage.** The user selected live inspection as part of this specification. An explicit bounded authoring session collects current page evidence at each deliberately reached state. This amends the no-DOM V1 scope through a separate contract with destination/CSI/secret controls, bounded collection and intentional authorization for navigation or state-changing actions. Ordinary Compile remains browser-free and Run remains LLM-free. The detailed orchestration below validates each proposed step before advancing and never automatically replays a potentially side-effecting step. Unknown later page states remain ungrounded until supplied or deliberately reached and observed.
6. **Literal versus target semantics.** Parse/resolve a typed intent record for review containing operation, exact literal or reference, target and explicit submission intent. Validate actual permitted AST arguments against it before a candidate can be confirmed. Quoted search text preserves Unicode, case, internal/leading/trailing spaces, quotes and newlines; do not lowercase, trim, rewrite or interpolate it. `exact: true` controls locator text matching, not `fill()` value preservation. A request to enter text alone must not gain an unsolicited Enter/click; a request to submit a search needs the evidenced submission action. Ambiguity cannot be fixed by guessing a value.
7. **Generated source constraints.** Prefer a unique grounded semantic locator; scope using permitted locator chains where necessary. Do not resolve ambiguity with `.first()`, positional choices, force actions or fixed sleeps. Use Playwright actionability/retrying assertions and page-specific ready/result signals inside the approved grammar. Allow bounded multi-operation code within one source-step artifact entry so search can fill, submit and verify its explicitly requested outcome. Use no extra statements merely to claim optimization.
8. **Context/cost minimization.** Select relevant page facts deterministically, deduplicate shared context, account for all serialized bytes/tokens, and reject oversize essential facts instead of silently dropping them. Bound proposals, transport retries and total elapsed compile work together. Keep cache disabled until keys include CSI, identity/configuration policy, all context revisions and runtime compatibility.
9. **Review and evidence.** Show effective global/step context and provenance, value, target and action sequence alongside generated source. Measure translation on fixed multi-page fixtures, including duplicate search fields, non-`q` names, enter-vs-button submission, dynamic result states, exact Unicode literals, stale profiles, context conflicts and injected page instructions. Structural/schema tests and mocked responses remain distinct from real-model fixture results.

## Live-learning orchestration decision

This is required specification scope following the user's response, not a deployed capability. It extends the existing architecture explicitly without granting the model browser capabilities.

1. **Start an explicit learning session.** The server accepts CSI/test/draft revision, selected environment, an approved initial destination and authorized account references. It owns session identity, principal, deadline, action/observation/LLM budgets and a monotonically increasing state generation. The runner owns an isolated Chromium page under restricted service identity; no model receives its handle or a general browser tool. The initial navigation is part of the user-visible start action, not a hidden side effect of Compile.
2. **Observe before proposing.** Capture a bounded sanitized view of the current live page through trusted runner code. Evidence records session/state generation, URL/route, actual observation time, selected page facts, redaction/completeness and hash. A predicted postcondition is never recorded as observed evidence. Evidence for a later step is not inferred solely from the landing page.
3. **Resolve and propose for one stable step.** Assemble global context, that step's local context, exact value/reference intent, authorized predecessor facts and the selected actual observation. A browser-free proposal/validation capability may use the LLM here because this is authoring, not execution. Preserve the ordinary Compile endpoint's property of never launching/advancing a browser.
4. **Validate before any action.** Validate schema, source correspondence, exact literals/references, AST/operation policy, destination and secret-use policy. The trusted runner checks target identity/uniqueness and compatibility with the current observed state. Unresolved ambiguity, stale state generation or unsupported behavior pauses learning with a diagnostic. It must not let the LLM choose a new target after action failure.
5. **Scope-authorized advance.** One explicit Start learning authorizes the displayed test/draft, intended action/value sequence and allowed action scope for that session. Automatically advance routine validated steps whose resolved meaning stays within that unchanged authorization; repeated clicks are not required. Pause for unresolved/changed intent, actions outside scope, replay or unknown prior outcomes; an optional per-step review mode may add deliberate checkpoints. Bind each internally approved advance to the authorizing principal/session/scope digest, stable step ID, source/context/evidence revisions, artifact hash and expected state generation. Server and runner admit one advance for that identity; duplicate requests return its existing outcome. A context edit or newer observation invalidates an earlier proposal. Recheck current policy before dispatch; browser actionability and strict locator matching remain final checks rather than a claim that a prior snapshot freezes the DOM.
6. **Capture actual outcome and new state.** Record whether the step was attempted, completed, failed or has unknown outcome; collect actual post-action evidence and apply only verified predecessor facts to the next step. A failed or ambiguous action is not automatically retried or replayed on reconnect, timeout or process loss. A new session cannot silently replay earlier actions to recreate state. The author must deliberately restore/reach the needed state or supply appropriate context.
7. **Finalize through the normal revision boundary.** Successful learning provides versioned evidence and proposed source, not a runnable approval. Keep observations in the session-local draft; atomically publish selected sanitized evidence/new context revision only when the test still matches its start source/context/configuration revisions. Partial/cancelled/expired or stale sessions cannot publish readiness through late callbacks. Final ordinary compilation/validation binds all ordered steps and chosen observations into one immutable candidate; review and exact confirmation are still required. Behavioral verification binds to the action/code hash actually exercised and its pre/post state generations; regenerated or dependency-changed code loses that verification until deliberately learned again. Normal execution consumes only the confirmed artifact and calls no LLM or learning orchestration.
8. **Bound and terminate.** Separate authoring session quotas from normal run capacity. Enforce configured total session/idle deadlines, observation size, proposal/transport attempts and action count; require configuration before enabling live learning. The authorized backend/worker resolves vault references ephemerally and transfers only required scoped values over encrypted internal transport; the runner has no vault, CSI-store or LLM credentials. Cancel/expiry/crash paths close the page, kill remaining child processes and clear ephemeral credentials. Persist only scoped sanitized evidence and nonsecret outcomes under the approved retention policy. Authentication storage, cookies, resolved credentials and hidden field values never become model inputs. Environment-specific retention/authentication policy remains a delivery gate, not an unresolved choice about whether live learning is in scope.

Proposed contracts should expose session creation, observe/propose, reviewed advance, status/recovery and termination as separate operations with idempotency and optimistic state-generation checks. Their route names and DTOs are frozen by the spec; this decision defines behavior rather than adding runtime endpoints during review. Validate capture API support against the pinned runner version; advanced snapshot capabilities unavailable in the current frontend Playwright 1.57.0 must not be assumed.
