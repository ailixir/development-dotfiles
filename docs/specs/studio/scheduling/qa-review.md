# Studio scheduling — QA planning review and test strategy

Date: 2026-10-05. Reviewer: Quinn, AIOX test architect. Scope: the brownfield-fullstack **planning package**, including discovery, requirements, architecture, UX, implementation plan and Dara's database review. This is an independent planning assessment, not a completed-story gate, Ready/Done transition, implementation verification or release approval.

**Planning verdict: CONCERNS.** The proposed reuse of Studio acceptance, immutable revisions and dispatch ledger is appropriate and the package is sufficient to refine dependency-ordered stories. The remaining concerns have concrete owners and gates below. Product policies require adoption; database/transaction details require architect/data-engineer closure before their stories are Ready. Real unattended identity and existing on-demand production evidence remain release gates. Those external dependencies do not prevent completion of this planning deliverable.

No application test suite, browser run, live platform authorization check, database migration or load experiment was executed by this QA review. Every scenario below is a **future implementation evidence target**. Source inspection does not establish that scheduling exists or works.

Severity denotes consequence if the design obligation is missed during implementation. These findings concern proposed integration, not reported production incidents.

| QA-01 / High | Outcome handling and atomicity are correctness prerequisites. Real PostgreSQL rollback/race evidence closes implementation verification. DB-07. |
| QA-02 / High | The handoff must preserve the full lock order and callback compatibility, not only quota ordering. | E-02/WP5: test → schedule → occurrence → global quota → CSI quota; one candidate per transaction. | QA-03 / High | Version-scoped UTC occurrence keys and string-prefixed manual keys do not provide independent scheduled identity or once-only local slots. | E-02/WP2: nullable UNIQUE ledger occurrence FK, scheduled manual key/digest-null CHECK, typed trusted identities; version-independent `(schedule_id, zone, local wall slot)` uniqueness, earlier-offset resolver and stable anchor through removal/recreation. | QA-04 / High | Redundant occurrence/run links, copied CSI and activation revision ownership need an exact constraint contract. **Final cross-document consistency check: resolved.** WP2 now explicitly carries cross-version local-slot uniqueness, stable recreation anchors and ledger/soft-history linkage; WP5 carries the full lock order and nonlocking overlap/callback requirement. Requirements/architecture/E-02 identify ownership enforcement, deferred polling and retention/linkage choices. UX uses server readiness rather than compile status, default paused creation with explicit Resume and truthful partial success, and durable uncertainty blocking. Schedule-versus-test deletion wording agrees across FR-09, D-09, WP3/WP6 and architecture/UX. These corrected planning discrepancies are closed; adopted policy, exact DDL/linkage choices and future implementation evidence remain legitimate entry/release gates.

## Exact entry, implementation and release gates

1. **Planning handoff complete:** all six inputs present, proposals identified, QA/DB findings trace to owners/work packages, incompatible wording reconciled, no fabricated pass/approval. This review may complete with recorded open policies and external release gates.
2. **Story readiness (E-01–04):** PM/product adopt scope and D-01–14 decisions relevant to each slice; Aria/Dara close its schema/linkage/lock/outcome/retention contracts; Security agrees fail-closed seam; River/Pax create and validate stories with AC and the mapped future evidence. No implementation code before a valid associated story.
3. **Transactional evidence:** all applicable P0 PostgreSQL/concurrency/crash scenarios pass on real PostgreSQL/Testcontainers with deterministic barriers and recorded injected failure boundaries. Assert durable row/identity counts and zero runner sends for refusal; do not accept mock-repository concurrency as a substitute.
4. **Operator/API evidence:** terminal-operable schedule administration and due acceptance precede UI delivery; API/OpenAPI/MSW agree, protected pagination and immutable origin remain compatible, critical accessibility and E2E flows pass. Unit recurrence checks assert exact instants/offsets, not merely chronological increase.
5. **Repository implementation gate:** from `frontend/`, `npm run type-check`, `npm run lint`, `npm run test -- --run`, targeted `npm run test:e2e`, `npm run build`, and `npm run build:standalone` when that path changes. From `backend/`, `./gradlew test` and `./gradlew check` with required JDK/Testcontainers prerequisites. Preserve existing generic scheduling/manual Studio regressions and report baseline failures separately. CodeRabbit has no CRITICAL findings and independent Quinn story verdicts apply the declared lifecycle workflow; this planning review does not substitute for them.
6. **Production enablement (R-01–04):** current real on-demand trust evidence; real live unattended grants/vault policy and revocation; adopted cadence/grace/batch/retention/load budgets and measured isolation; all writer/consumer versions compatible; independent QA and Gage release decision with named pilot CSI/environment/operators. Scheduling capability remains default off until these close.
7. **Operational reversal:** rehearse producer disable and pause while ledger/recovery/cancel remain operable; inspect accepted work and drain compatible consumers before downlevel rollback; retain additive schema/audit and use forward repair. Resume starts future slots with verified revision/grants and investigated uncertainty. No destructive drop, implicit legacy import or automatic browser replay.

Gage/operations must capture due/decision lag, accepted/refused/skipped/deferred/expired/blocked counts, active quotas, transaction/lock duration, network budgets and ordinary API/check performance. An unresolved high-risk invariant or failed P0 test blocks unattended production enablement; product policy adoption and external integration evidence are recorded explicitly rather than concealed by a passing local suite.
