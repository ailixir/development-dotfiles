# Studio scheduling — database design review

Date: 2026-10-05. Reviewer: Dara, AIOX data engineer. Scope: source inspection and proposed database design for the brownfield-fullstack planning workflow. **Planning review: corrections required before implementation readiness.** This is a specialist review, not a QA lifecycle verdict or deployment approval. No database connection, SQL execution, migration, production change or test run occurred.

The review supports Aria's typed `studio_schedules` + `studio_schedule_occurrences` direction in [architecture.md](architecture.md), subject to the corrections below. One schedule per individual test, explicit Resume after executable changes, skip-overlap and one local DST slot are proposed product policies. They are not newly discovered approved requirements. The current working tree, including existing uncommitted changes, is the evidence baseline.

## Findings and concrete corrections

| ID / severity | Finding | Required planning correction |
| --- | --- | --- |
| DB-01 / High | Schedule-first due locking followed by existing acceptance's test lock can deadlock with test-first edit/invalidation. Aria now specifies test-first, but the order must cover every write and bounded polling transaction. | Fix order as **test → schedule → occurrence → global quota → CSI quota → newly inserted execution/ledger**. Handle one test/occurrence per transaction. Schedule CRUD, delete, save invalidation, activation and retention touching live rows must comply. Do not lock many tests then take global quota locks. |
| DB-02 / High | New overlap code could take test then `FOR UPDATE` on an existing ledger; final callback already takes ledger/history then test. | Use a **nonlocking `EXISTS`** on `studio_dispatch_ledger(test_id) WHERE state <> 'DONE'`, under the test lock. All new accepts use the same test lock. A concurrently completing run may conservatively cause a skipped occurrence; it cannot cause a duplicate scheduled acceptance. Do not synchronously mutate/cancel an existing execution while holding a schedule transaction. |
| DB-03 / High | A deterministic internal string prefix alone does not isolate schedule keys from public manual idempotency keys. Manual clients can submit the same prefix. | Add a typed nullable `scheduled_occurrence_id UUID UNIQUE` to the ledger, FK to the occurrence. Scheduled acceptance uses the occurrence UUID and **null manual idempotency key/digest**; add `CHECK (scheduled_occurrence_id IS NULL OR (idempotency_key IS NULL AND request_digest IS NULL))`. Keep existing manual unique constraint and digest resolution unchanged. Core input is `ManualIdentity` or `ScheduledOccurrenceIdentity`, never a client-selected trigger. |
| DB-04 / High | The proposed UTC key `(schedule_id, schedule_version, scheduled_at)` does not suppress the second UTC instant of a repeated local DST slot. Version changes can also bypass version-scoped suppression. | Persist local wall timestamp without timezone, zone and chosen offset. Enforce additional unique `(schedule_id, time_zone, local_scheduled_at)` across schedule versions; use one stable schedule ID per test. The resolver must select the earlier offset and skip the later offset. Resume starts at a future slot; it cannot rerun a terminal local slot. Product/architect must explicitly adopt this cross-version suppression behavior. |
| DB-05 / High | Single-column revision/test FKs do not enforce copied CSI or ensure an activation revision belongs to the scheduled test. | Use composite ownership FKs described below, or an explicitly documented constraint-trigger alternative. Continue authoritative readiness and confirmed-status checks in the service. A FK proves ownership, not runtime readiness or confirmation. |
| DB-06 / High | A composite FK directly from occurrences into partitioned history would be structurally possible but conflict with existing partition detach/drop retention. UUID-only history FK is invalid against the current PK. | Point execution identity/locator integrity to **unpartitioned ledger**, not history. Retain immutable history locator for a bounded lookup; pruned history returns an explicit expired/unavailable representation. Do not add a history FK merely to make an occurrence link look stronger. |
| DB-07 / High | Existing `@Transactional accept()` exceptions can mark an outer occurrence transaction rollback-only even if a caller catches them. | Shared core returns expected accepted/refused/deferred outcomes before execution writes. Manual adapter translates refusal after transaction completion. Occurrence decision + accepted history + ledger + cursor advance commit together; any SQL failure rolls back the entire unit. Never read a poisoned transaction or persist refusal after an unexpected SQL exception. |
| DB-08 / High | Mixed-version APIs may edit, reconfirm or delete a draft without invalidating scheduling, and old dispatch authorization may not enforce a background grant. | Keep producer/activation feature disabled until all writers and Studio dispatcher/authorization consumers are compatible. Retain per-tick current readiness + activated revision equality as defense in depth. Executable invalidation, explicit Resume and dispatch-time grant recheck are rollout gates, not merely UI behavior. |
| DB-09 / Medium | `requested_enabled`, effective state, `blocked_code` and cursor can diverge; a deferred occurrence can create a hot due row. | Use explicit state invariants and a separate eligible-poll timestamp; keep nominal `next_due_at` unchanged during deferral. Bound retry count/backoff/grace and iteration, with no browser acceptance replacement. |
| DB-10 / Medium | New occurrence FKs and retained ledger can prevent occurrence cleanup indefinitely; twelve-month history retention is not a duplicate-protection horizon. | Agree audit, deduplication and replay horizons. Preserve minimal occurrence identity/linkage for as long as ledger references it. Bound redacted detail retention separately. No delete of accepted identity merely because a video/history partition expired. |

DB-01 and DB-07 are already recognized in Aria's draft; this review specifies the obligations needed to implement them. All other items describe proposed-design risks, not verified incidents or existing scheduling defects.

## Recommended schema contract

This is conceptual design, not executable DDL or an allocated Flyway version.

### `studio_schedules`

- UUID PK; `test_id NOT NULL UNIQUE REFERENCES ui_tests(id)` with restrictive deletion; immutable registered `csi_id`; normalized cron; explicit IANA zone; `created_at`, `updated_at`; creator/updater identity reference and activation audit.
- Keep one stable row/ID for a test, including a removal tombstone. Recreating a removed schedule reuses that anchor through an explicit versioned operation, or introduces an independent immutable deduplication anchor; do not silently generate a new ID and reset duplicate protection.
- Add `UNIQUE (id, test_id, csi_id)` for occurrence ownership. To enforce copied CSI, add supporting `UNIQUE (id, csi_id)` on `ui_tests` and reference `(test_id, csi_id)`. Existing quarantined rows remain unchanged; new schedule creation rejects absent/unregistered CSI. Add FK `csi_id → csi_systems(id)` only on the new table.
- `version BIGINT NOT NULL CHECK (version > 0)`. Increment for every user-visible schedule mutation/invalidation/activation. Use expected-version compare-and-update; zero updated rows means stale version, after normal authorization.
- `activated_revision_id` references `ui_test_revisions` through `(activated_revision_id, test_id, csi_id)` with supporting unique `(id, test_id, csi_id)` on revisions. Preserve old activation audit after invalidation; explicit Resume sets the new confirmed ID after locking and current readiness validation. Background execution never substitutes a newer confirmed revision automatically.
- Approved execution-principal/grant reference, bounded length; never bearer credentials. Existing `users(email)` models human users, so do not force service identities into that FK without an approved identity model. Grant verification is an application/platform policy, not a guessed database lookup.
- Use `requested_enabled` as intent and effective `ENABLED | PAUSED | BLOCKED` state; add `deleted_at` for tombstone. Enforce: `ENABLED ⇒ requested_enabled AND deleted_at IS NULL AND blocked_code IS NULL AND activated_revision_id IS NOT NULL AND principal/grant reference IS NOT NULL AND next_due_at IS NOT NULL AND poll_after_at IS NOT NULL`; `PAUSED ⇒ NOT requested_enabled AND blocked_code IS NULL`; `BLOCKED ⇒ requested_enabled AND blocked_code IS NOT NULL`. Removed rows must be paused. Preserve last cursor/activation when paused/blocked for audit; preview computes fresh future slots, not an implied eligible run.
- `next_due_at TIMESTAMPTZ` is the nominal UTC occurrence cursor. `poll_after_at TIMESTAMPTZ` is the next eligible poll instant; normally nominal due, advanced by bounded backoff during deferral. No worker overwrites nominal due with wall-clock now to evade deduplication.
- Cron/zone validity requires the shared application resolver; plain text CHECK constraints cannot establish the agreed Spring cron/DST semantics. Store normalized values returned by that resolver.

### `studio_schedule_occurrences`

- UUID PK and baseline `created_at`, `updated_at`; restrictive composite FK `(schedule_id, test_id, csi_id)` to the stable schedule row. Store immutable schedule version, test, CSI, approved principal/grant reference and activated revision snapshot. Do not FK an old occurrence's version to the mutable current schedule version.
- UTC `scheduled_at`, local `local_scheduled_at TIMESTAMP WITHOUT TIME ZONE`, explicit `time_zone`, chosen `offset_seconds`; positive `schedule_version`. Unique `(schedule_id, schedule_version, scheduled_at)` and unique `(schedule_id, time_zone, local_scheduled_at)`; do not include offset in the local-slot key because that would allow both overlap offsets.
- Decision enum `ACCEPTED | REFUSED | SKIPPED | DEFERRED`, stable bounded decision code, decision timestamp, bounded redacted detail. `DEFERRED` alone may transition to `ACCEPTED`, `REFUSED` or `SKIPPED`; terminal decisions, identity and execution link are write-once. Use a dedicated trigger/conditional SQL transition enforcement following the existing revision immutability approach, rather than copying its function verbatim.
- `ACCEPTED ⇔ execution_id IS NOT NULL AND execution_accepted_at IS NOT NULL`; nonaccepted decisions have neither field. Deferred fields include `retry_at`, positive bounded attempt count and immutable `grace_expires_at`; only `DEFERRED` has retry fields. Enforce `retry_at <= grace_expires_at` and refusal/skipped code presence. No plaintext secret or raw unbounded exception body.
- If duplicating execution linkage on occurrences, use `UNIQUE(execution_id)` plus composite FK `(execution_id, execution_accepted_at)` to a supporting unique pair on ledger. The ledger's reverse `scheduled_occurrence_id` FK creates an insertion cycle: make the occurrence→ledger FK **DEFERRABLE INITIALLY DEFERRED**, preallocate both IDs, insert occurrence then history/ledger, and validate the completed linkage at commit. Alternatively expose execution linkage by joining the ledger's unique occurrence FK and avoid duplicate stored fields. Pick and document one option before DDL; do not introduce an accidental mandatory circular insert.
- The database does not automatically prove UTC/local/zone consistency from these columns. Resolver consistency and immutable writes need exact tests. An optional trigger can validate cross-record immutable provenance if redundant snapshots are retained; specify its lock/order cost explicitly.

### Existing ledger and execution history

The independent nullable unique scheduled occurrence column described in DB-03 is the authoritative scheduled idempotency mapping. Existing rows and old manual inserts have NULL there, and preserve the original `(principal, idempotency_key)` behavior. Reject input that attempts to populate both identities. This is namespace separation by columns and constraints, not a reserved string convention.

Add nullable immutable trigger attribution to history. Legacy rows remain NULL/unknown; updated manual acceptance writes `MANUAL`; scheduled acceptance writes `SCHEDULED` with schedule/version/occurrence/due data. Constraint: scheduled attribution requires complete schedule fields; manual/unknown rows have no scheduled fields. Any FKs into unpartitioned schedule/occurrence/revision anchors are restrictive and need coordinated retention. Snapshot revision increments and result/evidence writes must not change accepted attribution. These additions should not modify the existing runner attempt/admission/recovery semantics.

## Locking, queries and operational bounds

1. Candidate discovery performs a bounded indexed read and CSI rotation; it is not the decision. Acquire only the candidate test row using native `FOR UPDATE OF test SKIP LOCKED`, then the schedule and existing occurrence row. A lifecycle-aware native lookup must handle deleted/quarantined tests without Hibernate's visible-row filtering hiding the reason.
2. Refresh/re-read current managed test and schedule state after locking, following existing save refresh evidence. Validate enabled/version/cursor/current readiness/activation pin. Save/delete/authoring paths perform test lock before schedule invalidation, explicitly including both current soft-delete overloads. Confirmation never clears a blocked schedule.
3. Run a plain indexed active-ledger `EXISTS` while holding the test; do not acquire ledger row locks. Inspect an existing occurrence before any new acceptance. One accepted occurrence resolves to its original run even after draft/schedule edits.
4. For eligible acceptance take existing global then CSI transaction advisory locks. The shared core must not acquire other test/schedule locks while holding global quota locks. All code creating runs must use the test lock; callback and reaper paths retain existing ledger ownership and must not join new schedule writes while holding ledger locks.
5. Persist one decision and, if accepted, one history/ledger mapping; advance nominal cursor only in that transaction. Deferred decisions retain original identity and cursor, advancing only `poll_after_at`. Network timeouts/budget must be explicit because current reference preflight runs before quota locking while the test remains locked. Unexpected SQL failure means rollback/retry the same identity, not a terminal refusal guessed from a database error.

Proposed query-driven indexes:

| Query | Proposed index / bound |
| --- | --- |
| Due candidates | `(poll_after_at, id) WHERE state = 'ENABLED' AND deleted_at IS NULL`, plus `(csi_id, poll_after_at, id)` with the same predicate if CSI rotation needs it. Fixed batch/pass/time budget; no unbounded load-all query. |
| Scheduled overlap | Ledger `(test_id) WHERE state <> 'DONE'`; use `EXISTS` with early exit. Existing per-test historical index is not proof that the active-ledger query is efficient at retained-history scale. |
| Occurrence history | `(csi_id, test_id, scheduled_at DESC, id DESC)` and, when needed, `(schedule_id, scheduled_at DESC, id DESC)`. Apply authorized CSI before ordering/pagination; use a stable cursor, fixed page cap and bounded date filters. |
| Occurrence/retry resolution | Unique UTC identity + local-slot identity + unique ledger occurrence mapping. Deferrals reached through eligible schedule index; avoid a redundant unbounded deferred sweep. |
| Run detail | Execution UUID → ledger locator → history `(id, started_at)`, preserving partition pruning and expired-history semantics. |
| Cleanup | Terminal decision/creation-time batch index only after a retained-identity policy is agreed. Always capped deletes/compaction and predictable order; do not introduce global-lock cleanup transactions. |

Explain plans, row-lock traces and fairness/load evidence are implementation checks, not performed review evidence. Bound cron traversal during long downtime; a missed range cannot be represented by millions of minute rows. If exact skipped-count computation cannot be bounded, the product contract must allow an explicit bounded/unknown count or constrain supported cron shapes. Preview and producer use the same canonical resolver and budgets.

## Retention and mixed-version rollout

**Retention:** existing twelve-month partition pruning only manages history partitions. Ledger and revisions retain identity independently. With a restrictive ledger→occurrence FK, occurrences must remain as long as linked ledger rows remain. Retain compact schedule/occurrence anchors and accepted identities; separately expire redacted detail and presentation payloads. The minimum duplicate horizon must cover grace, maximum worker interruption/replay, administrative resume and restore behavior; no concrete horizon is approved by current requirements. Resume cannot move a cursor backwards. Paused/removed schedules retain IDs and monotonically increasing versions. A restore older than an executed cursor requires reconciliation or continued suspension before activation; fresh random IDs are not reconciliation.

Do not cascade schedule deletion into occurrence, ledger, revision or history. The current historical `ui_test_executions.ui_test_id` FK has CASCADE in V7, but ledger/revision test FKs restrict physical draft deletion. New design must preserve soft deletion and not broaden physical purge as an incidental scheduling feature. History may expire while occurrence attribution remains; UI must then distinguish a recorded accepted run from available retained execution/video details.

**Proposed rollout sequence:**

1. Reserve next unused Flyway version at implementation time; V25 exists in the present tree. Never rewrite deployed V1/V5/V12/V13. Add new tables/indexes and nullable attribution/occurrence fields. Leave new schedule tables empty: do not translate legacy JSON/status into enabled work.
2. Inventory real table/partition sizes and lock budget before choosing supporting unique-index creation/constraint validation. Large existing-table indexes may need a separately configured nontransactional migration; use controlled lock timeout and retryable deployment procedures. This review does not claim zero downtime from untested DDL.
3. Deploy all compatible API/background/dispatcher/recovery code with schedule producer and activation disabled. Exercise old manual writes against the expanded schema; defaults must not fabricate legacy provenance or require new fields from old code. Keep existing manual unique index.
4. Verify no old writers remain, every executable-change path invalidates schedules atomically, every accepted background execution gets current grant/secret policy at dispatch, and normal checks/retries stay separate. Activation remains disabled until these capabilities and existing Studio production prerequisites have evidence.
5. Enable a bounded CSI pilot, observe due latency, deferred/refused/skipped decisions, transaction/lock time, active quotas, DB load and partition health, then expand by explicit release decision. Source configuration defaults are not capacity evidence.
6. Operational rollback disables producer/new activations and pauses schedules; accepted runs remain owned by existing dispatcher/recovery. Rolling back binaries while scheduled runs are active is unsafe if old authorization cannot validate their grants. Drain compatible consumers first. Schema rollback is forward-only, retaining audit/anchors; do not drop new tables to stop scheduling.

Required implementation evidence includes multi-worker identical-slot races, rollback at each write boundary, final-callback versus overlap interleaving, edit/delete/confirm/resume races, version changes across DST overlap, deferred expiry with one identity, old/new manual code compatibility, partition pruning with retained links and bounded long-downtime traversal. This document requests that evidence and does not imply the tests exist or pass.
