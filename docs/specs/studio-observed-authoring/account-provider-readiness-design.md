## 1. Decisions we can define, and facts we cannot supply

Keep the existing Java 21/Spring backend, Chromium/typed runner and React/MUI/central API/MSW boundaries. Account control belongs in the existing Studio bounded context; there is no new broker service, vendor, transport identity, infrastructure or dependency. Define a small capability/authorization adapter around the existing account ports, and add runner connectivity only to a compiled, reviewed registry after provider documentation and security review establish it. An opaque port is an integration boundary, not evidence that its implementation/provider exists. Existing `HashicorpStudioVaultProvider.read(ReferenceKind, VaultScope, String)` reads scoped KVv2 entries; it does not authorize or create a browser session. Never turn that resolver into an assumed session broker.

The product modes are already approved, not new alternatives needing product permission:

| Mode | Availability conditions | Tradeoffs and failure behavior |
|---|---|---|
| Configured approved account | Provider authorizes the selected account for the exact principal/CSI/environment/application/origins and documents its runner initialization mechanism. For the current `initialBlank` profile, it must advertise and prove **non-navigating initialization** of a newly created context. | Fits existing bootstrap and recorded replay with the least change when supported. Default is unavailable. No mode is silently substituted for another, and provider failover never reuses an issued handle or live context.
