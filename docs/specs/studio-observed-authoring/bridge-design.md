## Honest bootstrap and hashes

Replace the unconditional observation prerequisite with a closed execution-evidence union:

- `observedDocument`: sanitized observation hash, current document/generation and actual approved HTTP(S) origin.
- `initialBlank`: worker-attested original isolated browser-context identity, document identity, actual URL `about:blank`, JSON `origin: null`, creation identity and one-use bootstrap evidence ID. This is not an observation and grants no DOM access. Reject arbitrary blank-looking pages, `data:` URLs, application pages with unapproved origins and contexts with any prior application action.

Claim must no longer unconditionally enter OBSERVING. After the approved account connection and exact runtime compatibility are established, remain PREPARING until either real initial-blank evidence or a real approved account-setup page exists. Committing initial-blank evidence permits only the first authored navigation at the first source step, ordinal 0; all other operations require ordinary current observation. Keep this distinction in persisted progress and admission guards rather than pretending PROPOSING always means a page observation exists. No synthetic HTTP origin or observation hash is allowed.

For initial blank, the backend resolves a destination input from immutable authored/configuration provenance, verifies source-step association and destination policy, then admits the typed navigate operation through the same ledger and action budget. The worker rechecks original page identity and blankness during prepare and immediately before dispatch. Success leads to OBSERVING, where the existing approved-origin collector produces the first actual page observation. Redirects remain subject to destination/network policy. Failure or uncertainty never repeats the navigation.

Account setup is explicitly separate from authored work. Its allowed authentication operations and setup receipt identify how the exact isolated browser became connected. Setup cannot secretly perform or satisfy an authored checklist navigation. If supported same-session authentication necessarily establishes an approved application page, use ordinary observation of that page and execute any authored navigation as an independently admitted action. Blank bootstrap is unavailable in that branch. OBS-007 owns production setup; tests may provide a controlled real connection, not a forged connected flag.

Hash semantics are explicit:

1. Replace overloaded `observationHash` in v2 admission/ledger with tagged `executionEvidence` and its `evidenceHash`. For observedDocument, bind the full sanitized observation hash; for initialBlank, hash the canonical complete blank-attestation document. The evidence kind is part of the hashed material; an initialBlank digest is never labelled an observation hash.
2. `operationHash = SHA256(canonical-v1({coordinate, origin, locator, operation}))`. Here `origin` is the actual pre-action document origin: JSON null for initialBlank and canonical HTTP(S) otherwise. Initial navigation has `locator: null`; its destination remains an immutable destination input ID in `operation`. Never substitute destination origin for the nonexistent source origin.
3. The v2 learned-plan action preserves this exact null origin. Only the first navigate action of an explicitly blank-start plan may have it. The plan declares `initialContext: {kind: "initialBlank"}` as a replay precondition; normal plans declare an approved observed-page initial context. No transient browser/document/node/admission IDs enter that durable precondition. The complete learned-plan hash includes initialContext, actions, versions, dependencies and `authoredInputsHash`, alongside existing source/configuration identity.
4. Admission binds `authoredInputsHash` and context revision as well as evidence, operation, scope and fence. Immutable source/configuration resolution supplies destination bytes. A changed input table cannot retain an admission by reusing its opaque ID. Provenance hashes retain ordered exact ledger identities and operation hashes. OBS-006 must preserve these semantics in deterministic lowering and publication, including refusal when replay cannot establish the declared initial context.

There is one ledgered authored navigation and one destination receipt in the blank-start success test. Neither setup nor an artificial fixture pre-navigation may hide a second authored request.

## Prepare, transaction-winner dispatch and local consumption

1. Backend sends `/context` with the frozen input table/hash and a cumulative, monotonic materialization revision. The runner validates the complete table, origins, allocations and scope before acknowledging. Credentials use the separate account channel.
2. Backend sends `/prepare` with the schema-valid full proposal, canonical request digest, execution-evidence identity, scope, context revision, fence and deadline. For node actions the worker uniquely resolves the durable locator to the retained observed DOM element, checks real classification/type/actionability and retains a pinned target. For page/blank actions it pins the actual page/context identity.
3. Worker returns a bounded value-free attestation and opaque preparation ID. The backend stores the authenticated attestation with proposal digest, evidence, worker/fence, expiry and context identity. `authorizeAction` validates this stored proof plus current grants/source/policy and computes the canonical policy decision hash. A model field or caller boolean cannot substitute for this proof. Avoid network calls while holding the session transaction lock: persist proof before admission, then check its identity/freshness in the transaction and revalidate live state at the worker.
4. Admission stores the exact proposal and immutable ledger. The backend dispatch service invokes a v2 consume operation whose in-process result is a discriminated union: `WonConsumption(storedProposal, storedLedger, preparationId)` or `AlreadyConsumed(storedLedger)`/refusal. Only the transaction that changes ADMITTED/count=0 to DISPATCHING/count=1 returns WonConsumption after successful commit.
5. The winning result is ephemeral controller authority, not a durable replayable command response. Do not store/replay it through the generic idempotency response table. Durable route duplicates and new-key attempts return AlreadyConsumed, even when their historical ledger is identical. An HTTP advance response, if retained for orchestration/status, exposes consumed state only; it is not a dispatch permit. Only the backend dispatch service holding the post-commit winning result sends `/dispatch`. No recovery outbox resends a consumed action.
6. Send the stored proposal and ledger, preparation ID and all materialization identities. Worker recomputes request/operation hashes and validates the current lease/fence/scope/tuple and exact prepared target. It atomically records local consumption before the browser call. Use a durable journal outside disposable browser scratch with exclusive creation, fsync of file and directory and restrictive permissions; journal keys bind session/admission/fence/context. Store identities and outcomes, never business values. A missing/corrupt journal makes recovery unsafe, not an empty fresh journal.
7. Revalidate the pinned element/page and appropriate actionability immediately before invoking the trusted browser adapter. Retain the exact target through the operation; do not resolve a replacement, use `.first()` or reinterpret locator roles. A detected mismatch before browser invocation produces a definite refused/failed report under the consumed admission. Transport uncertainty remains UNKNOWN_OUTCOME.
8. `/outcomes` is owner-authenticated and compared to immutable stored admission. Duplicate dispatch messages return journal status and never call the browser twice. Duplicate outcomes are identical-only. Lost winning response, dispatch acknowledgement or callback does not cause automatic navigation/click/read repetition. Conservatively stop UNKNOWN_OUTCOME when consumption happened but completion is not known.

Both concurrency and request-idempotency tests must demonstrate exactly one WonConsumption result. A count=1 ledger, alone, must fail a dispatch-authority test. Crash injection covers backend commit before send, local journal before invocation, effect before acknowledgement and callback loss.

## Lifecycle, cancellation and uncertainty

Worker `/lifecycle` carries bounded reason and identity metadata for lost acknowledgement, lost context and teardown; the backend validates current owner/fence and invokes existing trusted lostAcknowledgment handling. Backend cancellation/expiry commits revocation of future unconsumed work, then sends idempotent `/stop`. Worker serializes stop with its local dispatch gate, rejects new work, closes the browser and destroys the value map. Independently enforced local lease and immutable session deadline stop the worker if notifications cannot arrive. Lease renewal never extends expiresAt; renewal carries current control state and cannot revive terminal work.

Cancellation linearizes durably at the backend against new admission/consume, and locally against future browser invocation when the runner processes stop. Public backend acknowledgement does not promise that an already consumed/in-flight effect was prevented. Preserve its unknown outcome unless a trusted definite outcome was already committed. Lost stop acknowledgements mean teardown is pending/unknown, not proved complete. Late callbacks cannot revive a session, authorize another action or publish; bounded diagnostic handling must preserve terminal ledger uncertainty. Tests place cancellation before consume, after consume/before call, and after the actual application effect.
