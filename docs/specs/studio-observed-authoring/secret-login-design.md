## 2. Target flow (one page)

```
author: "Enter <var USER> as username" / "Enter <secret PASS> as password" / "Click Sign in" / "Open reports" / …
  classify  → sourceReference{kind:secretRef, intendedSlot:fill.value, referenceName:PASS}; preflight(mayUse + exists), no read
  plan      → model sees step text with the token span masked, the reference (ID), never a value
  materialize → authoredInputs += {kind:secretRef, secretId:PASS}  (no value; hashed into authoredInputsHash)
  propose   → fill.value = {kind:secretRef, sourceInputId}, target = {kind:passwordControl, documentId, generation}  (node-free: the collector never exports a password node)
  prepare   → mayUse recheck (names only); trusted runner proves exactly one visible enabled input[type=password] in the current top-level document
  dispatch  → backend resolve() from Vault (CSI/env/testId/principal scope), RELEASE audit row, send BridgeDispatch.secret on mTLS bridge, erase
  act       → trusted runner re-resolves that unique password input at fill time (0 or >1 ⇒ POLICY_DENIED), origin ∈ allowedOrigins ∩ approvedOrigins, withhold(value) BEFORE fill, fill via the pinned handle
  observe   → next observation is the reached document; knownSecrets scrubs any echo
  publish   → artifact fill value {kind:secretRef, sourceInputId}; inputRecipes {kind:secretRef, referenceName:PASS}; no value anywhere
  replay    → job.secrets/secretOrigins resolved per run (legacy resolver), same origin + password rule, model-free
  stop      → knownSecrets = [], inventory disposed, dispatch frame not retained
```

## 4. Trust boundaries, value lifetime, password-only ruling

| Boundary | Rule |
|---|---|
| Gateway (model) | Receives step text with the `<secret ID>` span masked plus the reference `{kind:secretRef, referenceName:ID}`. The ID is permitted (GA plan §7 AC-1); the value is structurally impossible (no `value` field on the kind). Outgoing-bytes canary test. |
| Backend DB | Stores only IDs, vault **version identifiers** and audit rows (§4.1). The dispatch frame is assembled after `GuidedSessionService.consume()` commits (`GuidedDispatchService.java:80-100`) and is never journaled; `Resolved` is try-with-resources (`StudioReferenceResolver.Resolved.close()`). |
| Controller → runner bridge | The only channel carrying a value: `BridgeDispatch.secret` (guided) and `Launch3/Execute3.secrets` (replay), both on the existing mTLS + RS256 JWT chain (`GuidedInternalSecurity.java`, `guided/transport.ts:59-61`). Closed key sets; schema-validated before send and on receipt. |
| Runner memory | Value lives in the dispatch frame until `withhold([value])` copies it into the collector's private inventory (`browser.ts:335`), then the frame reference is dropped. Inventory wiped at `dispose()` (`browser.ts:452`) and on `stop`. The runner itself writes no scratch file, argv or env with a value (legacy rule, `protocol.ts:106`); the browser profile is a separate sink, next row. |
| Browser profile (disk, F-3) | Chromium's password manager, autofill and form history can persist a typed password (`Login Data`, `Web Data`, `Preferences`). Legacy/replay launch a persistent context whose profile lives in run scratch (`browser.ts:90-91`); guided uses `chromium.launch` with a Playwright temp user-data dir under `TMPDIR` (`browser.ts:466`); nothing disables these features today. **Required:** both modes launch a persistent context in a per-run/per-session scratch directory containing a pre-written `Preferences` file (`credentials_enable_service=false`, `profile.password_manager_enabled=false`, `autofill.profile_enabled=false`, `autofill.credit_card_enabled=false`, `session.restore_on_startup=5`) — a file, not `args`, which the sandbox gate forbids (`browser.ts:94-97`); the launcher refuses to start without it; the profile tree is canary-scanned **before** `runScratch.clear()`/context close. **Residual:** Chromium may still write transient files (cache, session storage) during the run; the scan measures, the clear removes. |
| Runner outputs | Ledger/outcome/observation/journal/callback bodies carry codes and IDs only. A redactor built from the resolved values runs over the worker's free-text sinks (stderr line, journal diagnostic text, callback `errorMessage`) — SEC-7 — with a canary test. |
| Video | Masked dots only, because of the password-only rule below. Disclosed as a separate channel; a secret filled into a page that later echoes it in plain text is **not** protected by video and is recorded as a known residual. |

**4.1 Audit (SEC-9).** New append-only table `studio_secret_use_audit(id, occurred_at, path ∈ {LEGACY,GUIDED,OBSERVED_REPLAY}, execution_id?, session_id?, admission_id?, principal_id, csi_id, environment, test_id, secret_id, vault_version?, outcome ∈ {RESOLVED,NOT_AUTHORIZED,REVOKED,UNAVAILABLE,VAULT_UNAVAILABLE})`, UPDATE/DELETE refused by trigger, written in the same transaction as the dispatch state change (legacy: beside `recordDispatchPolicy`, `StudioDispatcher.java:322`). Never a value. Retention: existing retention pruner window unless Security asks otherwise (§8 Q3).

**4.2 Password-only fill (SEC-6) — ruling, restated after security review F-1.** The collector never exports a password control (§1), so the model cannot name one and the earlier "`controlType:'password'` at observation" rule was unimplementable. Rule: the model emits `fill(secretRef)` with the node-free target `{kind:"passwordControl", documentId, generation}`; **trusted runner code** resolves the target at `prepare` and again at the moment of the fill — exactly one visible, enabled `input[type=password]` in the current top-level document (frames excluded), pinned as an element handle, origin-checked (§4.3), filled through that handle so a type-flip after resolution fails on the handle. 0 or >1 candidates ⇒ `POLICY_DENIED` with reason `PASSWORD_TARGET_ABSENT` / `PASSWORD_TARGET_AMBIGUOUS`; nothing typed. **Identity continuity (R1-1):** `generation` advances only per observation and `navigation` only on `framenavigated`, so a same-document DOM swap would otherwise let "re-resolve at fill" pick a different element. Resolution therefore runs **inside the collector's isolated world** under the existing `acquire`-style guard — cited `documentId`, `generation`, `observedNavigation === navigation` before and after the in-world call (`browser.ts:304-320`; `invoke` guard `:374`). The element pinned at `prepare` is retained in that world; the fill requires that **the same element** is still attached, still `type=password`, still the unique visible candidate, and that `location.origin` read **in that world** (not `page.url()`) is in `allowedOrigins ∩ approvedOrigins`; any deviation ⇒ `TARGET_CHANGED`, nothing typed; `navigation` is re-checked after the fill. **One function (R1-3):** "visible, enabled password input" is defined once in the isolated-world collector — computed-style visibility plus non-zero box (not viewport), traversal including open shadow roots (`observationCollector.ts:134-137,259-260,418-431`) — and that same function produces `coverage.passwordControls`, the `prepare` resolution and the fill-time check; a `querySelectorAll` resolver is forbidden. Consequences stated: an off-screen but rendered decoy counts ⇒ ambiguous ⇒ refuse; frames and closed shadow roots are excluded ⇒ absent ⇒ refuse. **Form action (R1-2):** the fill is refused with `PASSWORD_FORM_ACTION_NOT_ALLOWED` when the pinned input's owning `form.action` (resolved URL) has an origin outside `allowedOrigins`, or when the input has no owning form and the document origin differs from the observed login document's origin. `GuidedProposalValidator` accepts `passwordControl` only with a `secretRef` value, only for an input whose `sourceStepId` is the fill's step, and only when the cited observation reports `coverage.passwordControls === 1`; the proposal's `executionEvidence` still binds document/generation, so staleness checks are unchanged (I-A1 holds). **Limit (stated):** pages with two or more visible password fields (change-password, registration with confirm) are not supported for guided `secretRef` fills in this wave — the author gets `PASSWORD_TARGET_AMBIGUOUS` and must use legacy authoring, where the step names the field; a model-supplied ordinal/form narrowing is a reserved extension requiring its own Security review. Applied to the **legacy path too**: `playwrightAdapter.ts` fill of a `vars.secret` pins the element handle (already done for origin, `:504-535`) and refuses when `type!=='password'` with new refusal `SECRET_TARGET_NOT_MASKED` (added to `errors.ts` exhaustively and to `openapi.yaml x-runner-error-codes`); legacy keeps author-named targets, so multi-password forms work there. Trade-off: this breaks TOTP/API-token-into-text-field tests. Accepted because Vault is `none` in every value set today (GA plan C-3), so no production secret-filling test exists; a per-secret opt-out (a Vault-entry key beside `allowedOrigins`) is deferred and needs Security sign-off (§8 Q1).

**4.3 Origin binding (SEC-5).** Guided fill is permitted iff `executionEvidence.origin ∈ secret.allowedOrigins ∩ context.approvedOrigins`; the in-world resolution re-checks `location.origin` (§4.2, R1-1). Failure is `POLICY_DENIED` with nothing typed. **What an `allowedOrigins` entry asserts (R1-2):** the origin's **whole content is trusted** — the route allowlist is origin-granular (`browser.ts:119-123`) and the model, though it cannot `navigate` to arbitrary URLs (`runtime.ts:144-146`), can be steered by page text to **click** a same-origin link to attacker-authored content (user-generated content, stored XSS) presenting a single password field. Origin binding is therefore the trust boundary; the OBS-010 provisioning runbook must say so and secret owners must not list an origin that serves untrusted content. The `form.action` refusal (§4.2) is a cheap structural control on top. **Residual (stated):** same-origin script exfiltration of a typed value is not controllable by the runner. Replay reuses the legacy check verbatim (`secretOrigins` per ID; absent → bound to no origin).

**4.4 Authorization scope (SEC-2).** Resolve through `VaultStudioReferenceResolver` with `VaultScope.of(scope.csiId, scope.environmentId, session.testId)` and `principal = scope.principalId` (the Run principal). `mayUse` at **start** (preflight, names only → `SECRET_USE_NOT_AUTHORIZED` before any browser), at **prepare** (`GuidedDispatchService.prepareAndAdmit`, names only), and at **dispatch** (`resolve`, read + erase). Production `StudioSecretUseAuthorization` source remains GA item C-2 (not this wave). Cross-CSI: the KV path template includes `{csiId}/{environment}/{testId}` so a same-named secret under another CSI is `UnknownReference` → `SECRET_UNAVAILABLE`, never the other value.

**4.5 Cookie import (SEC-10).** Delete `observedAccountContext` (`browser.ts:181-193`), `RecordedContextCapability.installCookies/enter`, and the `context.addCookies` call. No gate, no flag: nothing in the decided flow needs it.

### 4.6 Secret-handling invariants (compliance)

Binding user requirement (2026-10-09): secrets must stay safe for compliance, be used **only at the right moment**, and **never be logged**. Every invariant below is testable (oracle `C-n` in §7), cites the code it relies on (read 2026-10-09), names its story (§10), and states residuals plainly. "Verified" means read in code; "required" means not yet true.

**A. Right moment**

| Inv. | Statement, evidence, story |
|---|---|
| **I-A1 Step binding** | A secret is filled only (a) at a step whose authored source declares `<secret ID>`, (b) in slot `fill.value`, (c) into the unique visible password control resolved by trusted runner code in the collector's isolated world, pinned at `prepare` and proven to be the same attached element at fill (§4.2, R1-1/R1-3; the model never sees a password node), (d) with an owning `form.action` origin inside `allowedOrigins` (R1-2) and on an origin in `allowedOrigins ∩ approvedOrigins`. *Guided proposal:* `GuidedProposalValidator.java:323-339` joins obligation → source reference → authored input, whose `sourceStepId` is the declaring step (classifier `:152-171`); runner `guided/runtime.ts:143` insists `input.sourceStepId === p.coordinate.stepId && intendedSlot === slot`; (c)/(d) per §4.2/§4.3. *Artifact/replay:* `inputRecipes[].stepId` is the declaring step; `validator/observedReplay.ts:261` already demands `input.stepId === ob.stepId && intendedSlot === slotOf(kind)` for `authoredLiteral` — extend identically for `secretRef`, and the executor re-checks at `perform`. *Legacy (verified, already bound):* `validator/references.ts:101-106` accepts a secret only as the `fill()` value argument; `:115-170` cross-checks each step's references against the source line's tokens or the ADR-SC-003 structural policy and rejects "an unauthorized secret reference for this step"; `requireSecretOrigin` (`playwrightAdapter.ts:504-520`); (c) is added by §4.2. **Story: OBS-007.** |
| **I-A2 Just-in-time delivery and scoping** | *Guided:* the value travels only in the `BridgeDispatch.secret` of the admitted fill, built after `consume()` commits (`GuidedDispatchService.java:80-100`), withheld before the fill, inventory wiped at `dispose()` (`browser.ts:452`). *Legacy and observed replay — decision: keep run-scoped delivery.* All declared secrets are resolved once at dispatch and shipped in the job body (`StudioDispatcher.java:320-322,501-506`; `protocol.ts:106-113`). Per-step delivery was evaluated and rejected: it would add a second secret-bearing channel (backend → runner per step) and a backend-driven step loop that the autonomous artifact executor does not have, require either holding values in the backend across the run or N Vault reads for one authorization decision, and the value would still sit in child memory from that step to exit. Residency shrinks from minutes to seconds at the cost of a new channel on a hop that is not yet TLS-authenticated (I-C8). Revisit only if Security requires it after I-C8 lands. *Scoping (verified):* never cached across runs — `Resolved` is try-with-resources and erased on every exit path including throw (`StudioReferenceResolver.Resolved.close()`; `VaultStudioReferenceResolver.java:129-135`); the runner parent wipes on success/failure/throw/drain/cancel (`runCoordinator.ts:45,332-357,946`); one forked child per run with an enumerated environment (`launcher.ts:260-264,387-388`) so concurrent runs share no process; the child receives `stop`, then `SIGKILL` of its process tree within `stopTimeoutMs` (default 5 s; `launcher.ts:422,489-494,309-315`). *Guided worker:* `knownSecrets=[]` and inventory dispose on `dispose()`, one browser context per session — but in-process browsers share one heap, so inter-session isolation is by `capacity` (default 1, `ownership.ts:101`); **required (F-10):** the mounted config asserts `capacity === 1` while secret fills are enabled, or the two-session cross-value isolation oracle must pass. **Residual (stated):** JVM `String` copies and JavaScript strings cannot be zeroed (`StudioReferenceResolver.Resolved` javadoc; `runCoordinator.ts:332`); the decidable property is that no live reference survives wipe and the child process exits. On legacy/replay the values are resident in the child from the `execute` message until exit. *Read side (F-4):* the Vault response is parsed into a Jackson tree and the value is a `String` before `toCharArray()` (`HashicorpStudioVaultProvider.java:349-360`). *Write side (F-4):* both writers build a whole-body `String` (`HttpRunnerDispatchClient.java:113-116` `writeValueAsString`→`ofString`; `GuidedRunnerClient.java:87-89` `canonical(body)`→`ofString`). **Required:** parse the read with a streaming `JsonParser` (`getTextCharacters`) straight into `char[]`; publish bodies as `byte[]` (`ofByteArray`) zeroed after send. Even then Jackson, `HttpClient` and TLS internal buffers remain a residual. *Disk:* browser profile (§4 table, F-3). **Story: OBS-007.** |

## 5. "Blocked by login" — detection and outcome code

**Code:** `LOGIN_REQUIRED` on both paths. **Nature:** an *annotation of a failure that already happened*; it never turns a passing step into a failure or a failing step into a pass. **Detail:** `{stepId|stepIndex, loginStepsPresent}` so the UI can say either "This page asks you to sign in. Add login steps before step N using your secrets" (`false`) or "Your login steps did not sign you in; check the secret and the steps before step N" (`true`).

**Signature S(document)**, trusted code only, no value reads, top-level document only (frames not inspected). *Guided:* `observation.coverage.passwordControls ≥ 1` (the structural count the collector exports, §3 — password nodes themselves are never exported, `observationCollector.ts:395-396`) **and** ∃ exported visible+actionable node with `elementType ∈ {button, input}` or `role === 'button'`. *Legacy:* a fixed probe counts visible `input[type=password]` and visible submit-capable controls in the **same form** (no `inputValue()`). Same-form correlation exists only on the legacy probe; the guided count is document-wide.

| Path | Where | Fire condition |
|---|---|---|
| Guided | Backend `GuidedTranslationService`, after the observation the current step's proposal attempt was grounded on; uses `coverage.passwordControls` (pin `observation: 3`) plus exported button nodes | The step's attempt ended in a validator rejection, `INSUFFICIENT_EVIDENCE`/`MISSING_SOURCE`, or a `passwordControl` fill proposed without a `secretRef` input **and** S(current observation). `loginStepsPresent` = a `secretRef` fill was dispatched earlier in this session. Session → `FAILED`, result `failure.code=LOGIN_REQUIRED`. |
| Legacy | `playwrightAdapter.ts`, on a step ending `TIMEOUT`/`STEP_FAILED` (locator not found or assertion failed) | S(page) via a fixed probe (`locator('input[type=password]:visible')` count, form-scoped submit count; no `inputValue()`), **and** the failing step is not itself a fill into a password control. `loginStepsPresent` = any earlier step filled a `vars.secret`. New `RunFailureKind 'login-required'` → result `FAILED`; `errorCode LOGIN_REQUIRED` added to `x-runner-error-codes`. |

**False-positive limits (stated).** Registration, change-password and card-CVV pages can match S; the hint then accompanies a run that was already failing, so the cost is a misleading sentence, bounded on legacy by the same-form submit requirement and on guided by the fill-without-`secretRef` trigger. Guided S cannot correlate the button with the password field's form (the count is document-wide), so any page with an unrelated password widget plus any button matches once the step has already failed. Custom/obfuscated login forms without `type=password` are not detected (plain timeout). SSO pages on non-approved origins are blocked earlier by origin confinement and never reach S. Localized button text is deliberately **not** used.
