# OBS-006 publication persistence contract — revision 2

Status: normative proposed design, pending independent re-review; no SQL or product implementation. This appendix resolves DATA-006-01–04 and the persistence parts of RUNTIME-001/PUB-001–004. [Publication design](publication-design.md) and [closed contracts](publication-contracts.md) form one design. V33 is currently free; implementation must recheck the migration tip. Existing V30–V32, immutable evidence and original review records remain unchanged.

## D1. Types, lock order and immutable pre-effect base

SQL names below are exact proposed names. `H` is `char(64)` with NOT NULL and lowercase-hex CHECK; `ID` is `varchar(256)` with nonempty CHECK; revision/test/execution/attempt/claim/grant IDs are UUID. CSI uses the existing `ui_tests.csi_id` SQL type. Timestamps are `timestamptz`. JSON documents are closed contract types from C1–C11, checked with required-key/type predicates wrapped in `IS TRUE`, byte limits using `octet_length(convert_to(document::text,'UTF8'))`, and trusted semantic verification. Missing JSON keys cannot pass through SQL three-valued logic. Identity and terminal evidence columns are deny-by-default immutable.

Lock order is session → current ui_tests → translation head/revisions → existing bridge children → publication children → revision/receipt. All captures, limits, reservations and result acceptance serialize on the existing session row. Ordinary compiler/source/schedule writers never lock guided sessions while holding ui_tests. No network, browser, Core, account or validator I/O occurs under these locks. Statement/lock timeout is bounded by the remaining authority deadline; final decisions use database `clock_timestamp()`, not transaction start time.

`ui_tests.publication_epoch bigint NOT NULL DEFAULT 0 CHECK(publication_epoch>=0)` is JDBC/trigger owned, not an ORM mutable field. BEFORE UPDATE compares `compile_request_id`, `current_candidate_revision_id`, `confirmed_revision_id` with `IS DISTINCT FROM`; on any change it sets old+1, rejecting overflow. On no head change it requires NEW epoch=OLD epoch. An explicit attempted override on a head change must be old or old+1; any other value refuses. Thus stale full-row ORM writes cannot regress/reset it; initial zero is not fabricated historical activity. Source/config revisions remain independently checked.

`studio_guided_publication_bases` columns, all NOT NULL unless marked nullable:

- session_id ID PRIMARY KEY REFERENCES studio_guided_sessions(session_id); test_id UUID REFERENCES ui_tests(id); csi_id; result_contract_version smallint CHECK=3.
- source_revision bigint, configuration_revision bigint, publication_epoch bigint, all nonnegative; compile_request_id UUID nullable; candidate_revision_id UUID nullable; confirmed_revision_id UUID nullable.
- source_hash H; configuration_hash H; authoring_hash H; scope_hash H; run_authorization_hash H; source_manifest_hash H.
- original_principal_id ID; run_authorization JSONB (the existing closed scoped Run authorization, no credential); initial_context JSONB (C2 InitialContext); replay_requirements JSONB (C2 ReplayRequirements, trusted pre-effect configuration mapping); created_at.
- UNIQUE(session_id,test_id,csi_id); UNIQUE(session_id,scope_hash).

Because V30 session.test_id is varchar while ui_tests.id is UUID, an INSERT trigger compares session.test_id=NEW.test_id::text and the session document's CSI/principal/scope against the typed base. It does not create an invalid UUID→varchar FK. Capture occurs in the original start/source initialization transaction, after the locked current source is identified and before worker assignment, materialization, model attempts or actions. The trigger requires PREPARING, no assigned owner/fence, and no assignment/materialization/action/model-attempt rows. A late base insert is forbidden, even if no effect can be proved. Publication-disabled new sessions receive no base; old sessions cannot be backfilled. Once present, capture obligations continue even if publication is disabled later. Base UPDATE/DELETE is forbidden.

## D2. Capture original facts before effects

Current `progress.observation` is only the latest snapshot; explicit refresh receipts are not complete observation history. OBS-006 adds `GuidedPublicationEvidenceRepository`, called inside **GuidedSessionService.storePreparation** after current source/owner/evidence checks and `GuidedPreparationStore.store`, in that same transaction. For sessions with a publication base it must copy the current sanitized observation and exact preparation facts before returning the preparation. A missing/mismatched observation refuses preparation; there is no catch-up re-observation or reconstruction from the eventual IR.

`studio_guided_publication_observations`:

- session_id ID, observation_hash H, context_id ID, owner_fence bigint CHECK>=1, document_id ID, generation bigint CHECK>=0, observation JSONB (frozen observation2), captured_at; PRIMARY KEY(session_id,observation_hash).
- FK session_id→base; composite (session_id,context_id,owner_fence)→the existing V31 materialization scope key. The document/generation/hash are verified against the full canonical observation and execution evidence, not merely copied.
- Append-only; duplicate hash must have identical bytes/identities. Maximum 400 distinct snapshots/session, each canonical UTF-8 <=32,768 bytes and aggregate <=1,048,576 bytes. Exceeding limits refuses preparation before admission/effects, with retained prior evidence.

`studio_guided_publication_preparations`:

- session_id ID, preparation_id ID, context_id ID, owner_fence bigint, request_digest H, evidence_hash H, inputs_hash H, materialization_revision bigint, source_manifest_hash H; observation_hash H nullable only for initialBlank; execution_evidence JSONB, proposal JSONB, proof JSONB, captured_at.
- PRIMARY KEY(session_id,preparation_id); FK(session_id,preparation_id)→studio_guided_preparations; FK(session_id,observation_hash)→publication_observations; FK session_id→base.
- `execution_evidence`, `proposal`, `proof` use the existing closed v2 bridge/action schemas, preserving their exact integers/identities. Proof/requestDigest/evidenceHash/context/fence/source/input/materialization checks must match the existing preparation and current session. For observed targets, resolve the exact node by document/generation/nodeId in the copied observation, and verify its exact locator/classification/read recipe. Blank is allowed only for genuine first initialBlank navigation: observation_hash is NULL, but the exact original Action2 page target is nonnull `{kind:page,documentId,generation:0}` and must equal the original bootstrap executionEvidence document/generation. Only origin/derived locator and observation follow their existing null branches. A null target, fabricated document or blank evidence after the first action refuses. ObservedDocument requires nonnull observation_hash and its actual matching snapshot; never manufacture a blank observation row. The SQL branch requires `(observation_hash IS NULL) = (execution_evidence->>'kind' = 'initialBlank')` with the complete required-key predicate `IS TRUE`, so missing kind cannot pass. No inferred subtype or historical policy-file digest is stored.
- Maximum 400 distinct preparation facts, each combined canonical tuple <=16,384 bytes and aggregate <=2,097,152 bytes/session; exact duplicate insert is an equality check, not another charge. Immutable, including original observation association.

`studio_guided_publication_admissions`:

- session_id ID, admission_id ID, preparation_id ID, obligation_id ID (canonical UUID text), proposal_hash H, captured_at; PRIMARY KEY(session_id,admission_id); UNIQUE(session_id,preparation_id); UNIQUE(session_id,obligation_id).
- Scoped FKs(session_id,admission_id)→existing actions, (session_id,preparation_id)→publication_preparations; FK(session_id,obligation_id)→studio_guided_obligation_admissions(session_id,obligation_id) uses its existing varchar identity. The association must equal the existing immutable translation admission association, not allocate another obligation/ledger.
- Insert in **GuidedSessionService.admit**, after existing action insertion, translation.attachAdmission and preparations.attach, inside the same transaction. Verify exact selected preparation, original proposal digest, ledger operationHash, scope and obligation. Failure rolls back all admissions/links before dispatch. Maximum 200 rows/session; UPDATE/DELETE forbidden.

Parent-locking INSERT triggers enforce cross-row identities and aggregate count/byte limits for direct SQL as well as repository writes. Count/size checks occur after dedup equality and before insert. Existing prepared proof may carry page-private authority, so stored snapshots remain access-controlled server evidence, never log/model/export fields. Only sanitized observation2 bytes are retained: no raw DOM, captured values, resolved authoredInputs, cookies, secrets, failure details or sample-value hashes. Artifact/IPC stripping is specified in C3/C8.

The original successful bootstrap metadata delivery proof is retained with its **original acknowledged context/input/allocation snapshot**, and compared to that snapshot, not to later materialization revisions from dependency allocation. A preparation is publication-blocking only when it retains a current dispatch right through a pending/nonterminal admitted action or an unresolved accepted obligation. Unassociated stale duplicate preparations cannot authorize effects after FINALIZING and do not indefinitely block finalization. Every included action nevertheless needs its unique successful preparation/admission evidence; there must be no live model/question/action or unresolved exercised obligation.

## D3. Independent validation basis and snapshot

`GuidedPublicationEvidenceRepository.readBasis` assembles C4 ValidationBasis directly from immutable base/source/translation/materialization/preparation/admission/ledger/producer/consumer rows. It does not accept the lowerer's guards, recipes or action list as evidence. It copies value-free input provenance from authoritative materialization plus source manifest: opaque cfg reference→name/step/kind/slot→inputId, source-span→inputId, and binding producer/consumer coordinates. Java privately checks `authoredInputsHash`; Node checks the provenance mapping and never receives resolved saved values. The returned snapshot is bounded before releasing locks. The actual accepted plan includes server-issued obligations[].obligationId and needs[].bindingId. Read/hash the complete immutable allocated plan, and check every need/binding/producer/consumer join bidirectionally; do not project it down to the unallocated model schema.

Snapshot hash binds: base identities and captured heads/epoch, current authoring/source/config/scope, accepted translation revision/hash, owner/fence and captured validationDeadline, original bootstrap acknowledgement identity, basisHash, canonical learnedPlanHash, artifactHash, policyHash, equivalenceHash, publicationEvidenceHash, requiredProfileHash and validationBuildHash=H(requiredBuild). Artifact is built only after the independently assembled basis; both independently produce the same ordered action equivalence. The attempt captures `validationDeadline=min(claim creation time+15 seconds, session expiry, owner lease expiry at claim)` once; snapshot recomputation uses that stored deadline, not the mutable current lease timestamp. Same-owner/fence renewal leaves snapshotHash unchanged and consumes no new claim; current owner/fence/current lease must still be live, and neither renewal nor Core can extend/revive the captured deadline. Snapshot recomputation before commit uses immutable rows plus current authority/head checks; edits/new rows/translation/fence changes refuse. Node receives the independent basis including original historical node facts solely for validation; child receives none of those identities.

## D4. Session-wide validation claim state machine

`studio_guided_publication_attempts` has:

- session_id ID REFERENCES base; attempt_id UUID; attempt_number smallint CHECK BETWEEN 1 AND 3; finalize_key ID; finalize_digest H; snapshot_hash H; basis_hash H; base_epoch bigint; translation_revision bigint; translation_hash H; owner_worker_id ID; owner_fence bigint.
- artifact_hash H; learned_plan_hash H; equivalence_hash H; profile_hash H; validation_build_hash H; publication_evidence_hash H; claim_id UUID; validation_deadline (immutable captured deadline above); status varchar CHECK in RESERVED,VALIDATING,VALIDATED,REJECTED,SUPERSEDED,UNKNOWN; created_at; claimed_at nullable; completed_at nullable; validator_receipt JSONB nullable; failure_code varchar(64) nullable.
- PRIMARY KEY(session_id,attempt_id); UNIQUE(attempt_id); UNIQUE(session_id,attempt_number); UNIQUE(claim_id); UNIQUE(session_id,attempt_id,claim_id,snapshot_hash,basis_hash). All identity/hash/deadline fields immutable. Claim expiry means validation_deadline; current worker lease expiry is a separate live authority check, not a rehashed field.
- Partial UNIQUE(session_id) WHERE status IN ('RESERVED','VALIDATING'); session-wide number=max+1 under session lock, counting all prior keys/restarts/unknown outcomes. No deleted/reused attempts and no fourth call.

RESERVED has no claimed/completed/result/failure. A committed CAS RESERVED→VALIDATING sets claimed_at once and grants exactly one validator send, conditional on session active FINALIZING, matching snapshot/pins and unexpired captured deadline and live same-owner/fence lease. The network happens after commit. VALIDATING→VALIDATED requires matching claim/snapshot/basis/profile, authenticated validator response, current unexpired captured deadline and current same-owner/fence live lease, plus a passing C5 verdict; result and completed_at are mandatory and failure null. REJECTED requires completed_at/failure and no success receipt. SUPERSEDED means current identity changed; UNKNOWN means expired claim or ambiguous transport; each has completed_at/failure and no success receipt. RESERVED may become SUPERSEDED/UNKNOWN without send. Terminal rows never change. No status permits response hashes to rewrite expected identities.

Lost process before/after send consumes its claim. Expired live claims become UNKNOWN under lock; retry is a **new charged attempt**. A validated attempt can be reused before its original captured deadline for exactly its unchanged snapshot and finalize digest without another validator send; recheck fresh Core and all final guards. A different HTTP key with identical normalized body may join/recover the same matching committed receipt; the first key and canonical request digest remain durable. Reuse of any recorded key with a different body is 409. A different expected source/config digest cannot read a mismatching receipt. No new claims/snapshots after terminal session; only authorized receipt reads are allowed. Semantic/pin validation failures are refusals, not invitations to replay browser work.

## D5. Revision origin, reciprocal receipt and exact cutover

Add nullable revision columns `publication_kind varchar(16)`, `guided_session_id ID`, `learned_plan_hash H` (nullable SQL variant), `revision_digest H` (nullable SQL variant). Extend confirmation_source CHECK to RUN/MANUAL/GUIDED_RUN. Exactly these branches are allowed:

1. **Ordinary**: publication_kind IS NULL, all three guided columns IS NULL, confirmation_source IS DISTINCT FROM 'GUIDED_RUN'. Keep existing ordinary checks. Historical null compile_request_id remains valid unless the separately installed V19 insertion capability requires a request; never backfill fabricated guided origin.
2. **Guided**: publication_kind='GUIDED_RUN', every guided column nonnull, compile_request_id IS NULL, artifact_schema_version=2, confirmation_source='GUIDED_RUN', confirmed_by/confirmed_at nonnull and original Run principal. All required hash patterns and JSON identities must satisfy `IS TRUE`.

Revisions add UNIQUE(guided_session_id,id), UNIQUE(id,test_id,csi_id,guided_session_id), partial UNIQUE(guided_session_id) WHERE publication_kind='GUIDED_RUN', and partial UNIQUE(test_id,revision_digest) for guided origin. FK(guided_session_id,test_id,csi_id)→base(session_id,test_id,csi_id). ## D6. Final publication transaction and read-only receipt recovery

Active flow: public cookie/BFF identity → locked snapshot and claim → committed claim → pure validator → current account policy check (no setup) → **uncached fresh Core** → final locked snapshot/CAS. Active grant is in-memory, expires at min(Core response time+5 seconds, captured validationDeadline, session expiry, current worker lease); checked against database wall clock after bounded lock acquisition. Same original Run principal, current write/execute CSI entitlement and exact snapshot are required. Any Core delay can exhaust the session; it never revives work.

Final CAS compares source/config revisions, source/config/authoring/scope hashes, captured publication_epoch and all three null-safe heads, accepted translation and basis, owner/fence/current lease, bootstrap proof, successful obligations, exact profile, grant identity/expiry and active FINALIZING. Insert revision/receipt, set candidate+confirmed heads/READY, clear compile_request_id and diagnostics, and transition session SUCCEEDED atomically. Clearing the old request makes existing ordinary lockCurrentRequest/publish predicates discard a late pre-base compiler result; epoch alone is insufficient. Preserve ordinary request history. No schedule writes and no synthetic ordinary execution.

Expected conflict rolls back the entire candidate transaction. A fresh session→test locked transaction may record PUBLICATION_CONFLICT only if no committed receipt/success/cancel/other terminal winner appeared. Preserve all browser evidence. Unexpected SQL failure remains retryable, not success/conflict fabrication. All faults after revision, receipt, head and session writes must leave no orphan readiness.

Receipt recovery uses **READ_PUBLISHED_RECEIPT**, a separate method: live cookie, uncached Core.getUserMe, returned principal equal authenticated caller and original Run principal, current CSI `canRead`. It grants only retrieval of the matching immutable receipt, even after session/worker expiry or current source/head change. It does not call active grant refresh, validator, account setup or browser and cannot publish again. Current readiness is independently projected; historical PUBLISHED is not an assertion that this revision remains the ready head. Store normalized request digest/key in receipt/attempts to reject changed body without rebuilding a mutable snapshot. Missing/revoked/unavailable Core refuses even historical access; no cookie persistence/cache fallback.

## D7. Actual ordinary execution binding and admission

Add nullable JSONB `observed_revision_binding` and `observed_admission_receipt` to partitioned ui_test_executions; legacy rows both NULL. Binding is C7 ExecutionBinding, set only in acceptance INSERT and thereafter immutable. Preallocate execution UUID and observed attempt UUID before fresh authorization; persist attempt UUID in binding while existing ledger.attempt_id remains NULL until beginDispatch. Observed dispatcher uses that reserved UUID; legacy retains its existing random attempt allocation. No alternate ledger or new dispatch permission.

Admission receipt is C7 AdmissionReceipt, NULL→exactly one document in the **existing AdmissionCasService claim transaction** after tuple/hash/profile/grant/current-cancel checks and existing CAS. It must match execution id, started_at, reserved attempt, revision UUID/digest, principal, CSI/environment/scope, profile and hashes. An identical admission retry is read-only; changed receipt refuses. Terminal projections cannot set/replace it. Existing runtime_versions remains display data only, never the immutable receipt store.

A separate BEFORE INSERT/UPDATE parent trigger checks closed shape/required types/bounds and column joins, leaves existing V26/V28 guards intact, and is inherited by future partitions. Binding INSERT references a real immutable published revision and caller grant; trigger checks relational revision/test/CSI identities. Any helper relation FK must use `(execution_id,started_at)` because the partitioned PK is not id alone. JSON receipt maximum16KiB, binding maximum32KiB. No credential/account handle/captured value appears in either.
