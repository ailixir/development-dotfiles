# Common observed-2 bridge

Implementation wire freeze for OBS-004. This bundle deliberately contains no model-facing source projection or semantic resolver. Historical parent-directory v1 schemas are unchanged.

All bridge identity envelopes are exact and closed: `schemaVersion`, `sessionId`, `workerId`, `ownerFence`, `scopeHash`, `contextId`, `contextRevision`, `sourceRevision`, `configurationRevision`, `versions`. The context identity is allocated by backend for one worker/fence and never reused after teardown. Context revision is frozen input identity (currently 1); materializationRevision starts at 1 and increases on cumulative allocations/producer/consumer metadata. Context updates cannot change inputs or remove exercised metadata. Lease updates never exceed immutable expiresAt.

Backend sends HTTPS with mutual TLS and a short-lived issuer-provided RS256 JWT (`aud=studio-guided-runner`, `role=backend-controller`). Runner sends callbacks using its issuer-provided credential (`aud=studio-guided-controller`, `role=owning-worker`, `sub=workerId`). No automatic POST retries and no worker signing keys. Receivers validate current owner/fence and full identity; public BFF auth cannot confer internal roles.

Runner receivers: `/internal/v2/studio/guided-sessions/{sessionId}/context`, `/prepare`, `/dispatch`, `/stop`. Context responds with the exact identity envelope (acknowledgement only); prepare responds with `bridge#/definitions/preparation`; dispatch responds with `bridge#/definitions/outcome` only when definitely completed, otherwise reports UNKNOWN_OUTCOME; stop responds with identity only after teardown. All failures use bounded data-free error codes. Backend callbacks: `/bootstrap-evidence` accepts bridge bootstrap; `/observations` accepts identity plus `observation` (v2 shape); `/outcomes` accepts bridge outcome; `/lifecycle` accepts bridge lifecycle. Claim is commands claim. Internal requests carry Idempotency-Key and X-Owner-Fence.

Evidence hash is canonical-v1 SHA256 of the complete tagged executionEvidence. Bootstrap is a genuine fresh isolated about:blank page, generation 0 and JSON null origin. It can authorize only sourceStepIds[0], ordinal0, navigate. Proposal target remains the page shape with the actual documentId/generation. `operationHash` hashes `{coordinate,origin:executionEvidence.origin,locator:target.locator ?? null,operation}`. No source origin is fabricated. Request digest hashes full proposal. Prepared proof cannot carry runtime data.

Dispatch includes exact stored proposal/ledger/preparation ID and the consumer edges for that admission. Count=1 alone is not controller authority: only a committed in-process winner sends it once. Local journal consumption precedes retained-target invocation. Journal duplicates never invoke again. Errors and uncertain gaps never retransmit effects. A successful read reports only availability `{bindingId,producerAdmissionId,contextId,workerId,ownerFence}`; runtime bytes and their lengths/digests/samples never leave the worker. Backend derives producer coordinate/origin/recipe from its immutable proposal. Consumer admission needs a successful earlier producer with same-origin transfer, pending allowed slot/step and current local availability; runner also requires its own local write-once value.

The operation variants inherit existing closed typed operations. Positive read classification/type and retained live element identity must be checked again at invocation. Context metadata is not permission to read arbitrary DOM. Source input allocation validates immutable classified sourceSpan/configuration candidates, exact UTF-16 boundaries, slot/type/step/revision and destination. Controlled test sources do not claim automatic English extraction.

Learned-plan null-origin initialContext precondition is required for later OBS-006 lowering. This bridge never enables publication; production account and semantic planning ports remain fail-closed.

Callback ordering is outcome-before-observation: a successful outcome must receive a durable backend acknowledgement before sending a fresh observation; the backend must first transition ACTING to OBSERVING. The dispatch HTTP response can repeat that same outcome. Identical callback/response reports deduplicate producer metadata; a lost final HTTP response must never downgrade an already committed successful outcome. If outcome acknowledgement is uncertain, stop locally and report lifecycle UNKNOWN_OUTCOME without retrying the browser effect. Only unresolved DISPATCHING admissions become unknown; trusted committed successful admissions remain successful. Push cumulative context after allocation/read/consumer changes before the next dependent prepare/admission. Materialization revision increases independently of frozen context revision.

The trusted source boundary supplies classified nonsecret **regions**, not preselected semantic literals or per-control mappings. A candidate span must be wholly contained in such a region, with complete Unicode boundaries; its kind and slot pass independent closed compatibility checks. This proves provenance/classification only; OBS-005 still owns correct English meaning and association. Unclassified regions are never inferred safe. Authored nonsecret configuration strings may intentionally be empty/whitespace; runtime captured read values alone have the separate nonblank policy.

Backend callback202 replies preserve the full session shape. The runner discards bounded response bodies up to 1 MiB; Unicode source-step identifiers can make a valid 100-step session exceed 64 KiB despite all character-count bounds. The 1 MiB limit does not authorize larger action/observation/value limits. Context approvedOrigins uses the same 10-item, 256-character approved-origin ceiling as its frozen scope.

## Actual-worker assignment and renewal amendment

The context-scoped envelopes and receiver descriptions above have the following explicit pre-context exceptions. `assignment.schema.json` is a closed immutable request with exactly `schemaVersion: 2`, `assignmentId`, `sessionId`, `workerId`, `scopeHash`, `sourceRevision`, `configurationRevision`, `versions`, `expectedFence` and `expiresAt`. It contains no context ID, current-owner fence, input table, account material or model data. The backend persists this assignment intent against the current authorized session/source/configuration and expected fence before sending any network request. It does not call claim using a worker identity.

Controller-to-runner `POST /internal/v2/studio/guided-sessions/{sessionId}/assign` requires the existing controller JWT audience `studio-guided-runner`, role `backend-controller`, verified mTLS/certificate identity and `Idempotency-Key`. It has no `X-Owner-Fence`; expectedFence is in its body. The actual addressed worker reserves one capacity slot for the session and fsyncs a separate assignment creation/tombstone record before making its own backend `/claim` request. It uses its mounted issuer-provided owning-worker JWT and client certificate, not credentials carried by assignment. Claim retains its existing closed request, `expectedFence` and exact tuple, no owner-fence header, and typed 202 full-session response.

Unlike the void outcome/observation callback acknowledgements, claim responses must be bounded, parsed and validated as the full v2 session. Require exact session/scope/source/configuration/versions/hard deadline, canonical scope hash and scoped run authorization, actual owning worker, live lease and nonterminal state. Fresh acquisition returns ownerFence equal to assignment.expectedFence + 1; renewal preserves that acquired fence. Reject a terminal session even when its HTTP status is 202. Nothing launches a browser until an acknowledged assignment and its matching materialized context both exist.

`assignment-receipt.schema.json` is exactly `{schemaVersion: 2, assignment, status, ownerFence, leaseExpiresAt}`. Successful `/assign` returns **200 OWNED** only after the worker validates its live claim grant. OWNED requires both grant fields non-null, the acquisition fence increment and a lease no later than immutable assignment.expiresAt. The response reveals only scoped assignment/owner/lease metadata. STOPPED receipts either retain both historical grant fields or have both null when acquisition was not acknowledged; historical fields never authorize more work. Already stopped assignment repeats refuse with bounded 409 rather than returning an old OWNED response.

Assignment-scoped `/stop` and `/lifecycle` are closed `{schemaVersion: 2, kind: "assignment", assignment, reason}` variants. Reason uses the existing CANCELLED/EXPIRED/UNKNOWN_OUTCOME/LEASE_LOST/CONTEXT_LOST enum. Their nested assignment.sessionId must equal the path. They have no `X-Owner-Fence` and never invent a context identity. Existing context variants are preserved in the bridge unions and still require their current-owner fence header. Assignment `/stop` returns **200 STOPPED receipt** only after local cleanup; context stop still returns its identity acknowledgement and also stops the associated renewal driver. Backend assignment `/lifecycle` retains **202 full-session** acknowledgement, authenticates the actual owning-worker service subject and verifies persisted assignment intent plus current actual owner before affecting state. In-flight claim uncertainty before materialization is handled through this variant; knowledge of assignment.expectedFence alone is not ownership.

The worker registry owns one assignment/capacity reservation per session across pending assignment and running context. Identical concurrent assignments join one claim attempt even under different HTTP keys. Reusing an assignment ID/key with changed immutable content conflicts; a new assignment ID cannot reset the same session. Duplicate responses are checked against current local liveness, not blindly replayed from a cached promise. Persist assignment creation and stop tombstones separately from the existing browser-context/action journal in the same configured journal directory. Existing tombstones after restart refuse automatic reassignment, renewal or browser/context reconstruction. Missing/damaged durable state is not proof of an unused assignment. Pending assignment lifetime is bounded by capacity and immutable session expiry; release its slot only after cleanup, with no double charge when context arrives.

Renew from assignment acknowledgement onward, approximately every 10 seconds for the backend's 30-second lease, including while waiting for context, acting or awaiting clarification. Use one outstanding bounded claim request, a fresh key for each renewal, the acquired expectedFence and the same worker credentials; do not automatically retry POSTs. A dedicated local acknowledged-lease update bypasses the runtime's busy/materialization guard. It validates the full grant, keeps worker/fence/scope/source/configuration/tuple/hard expiry unchanged, and applies only while the assignment and its previous acknowledged lease are still live. Only an acknowledged matching grant can extend the local lease, never beyond expiresAt. A failed/lost renewal stops new work and begins cleanup; a response arriving after local stop or previous lease expiry cannot revive authority.

Context delivery and lease acknowledgement are separate ordering domains. A delayed context with an older lease may update otherwise valid cumulative materialization without regressing the current acknowledged lease. A newer timestamp in a context message cannot extend local authority; only the worker's validated claim acknowledgement can do so. Context cannot alter immutable assignment identity, reopen a stopped assignment or substitute for an initial grant. Stop serializes against local lease application and prevents late claim/context replies from launching. Preserve committed successful outcomes, retain uncertainty for unresolved consumed actions and never retry browser effects after renewal/transport loss. Backend terminal responses terminate renewal without changing an already terminal outcome.

The assignment fixtures check shape, immutable identity, grant/receipt relationships and synthetic ordering traces only. They do not prove timers, fsync, capacity, service authentication or an actual worker claim/renew cycle. Joined backend/runner tests must remove fixture-driven direct claims and prove the real worker acquires and renews with its own mounted credentials before/through browser execution. This amendment supplies no model-facing projection, account connection, artifact lowering, publication or replay readiness.

## Explicit observation refresh amendment

`observation-refresh.schema.json` is a closed request containing the exact existing bridge identity plus `expectedGeneration`, an integer from 0 through 2147483646. Controller-to-runner `POST /internal/v2/studio/guided-sessions/{sessionId}/observe` requires the existing controller JWT audience `studio-guided-runner`, role `backend-controller`, verified mTLS/certificate identity, `Idempotency-Key` and `X-Owner-Fence`. Success is **200** with the unchanged `bridge#/definitions/observation` envelope. It is sent only after the actual owning-worker `/observations` callback receives its durable **202** backend acknowledgement. The existing callback body and response body are unchanged; the backend never impersonates that callback.

The shared callback Idempotency-Key is exactly:

```text
oref- + SHA256(canonical-v1({
  identity: <exact bridge identity from refresh request>,
  idempotencyKey: <refresh HTTP Idempotency-Key>,
  requestDigest: <SHA256(canonical-v1(full refresh request))>
}))
```

The fields inside the hash are JSON values, not interpolated strings; no whitespace, normalization or renamed keys are introduced beyond canonical-v1. `identity` contains no expectedGeneration; the full request digest does. `fixtures.json.observationRefreshCorrelationVector` is the common golden vector. For its identity, expectedGeneration 3 and HTTP key `refresh-step-2`, the request digest is `0dfae8d5751ac96b9397f47e6ee3ed03b346f030faf81d648c7d31f1c2022a8a` and the callback key is `oref-85463e3f7f14e85755f2e0acc7ed3f3aed7fc619744d5545ea85eb54af14fd3e`. The worker callback transport accepts this explicitly supplied key rather than generating another random key.

Before network I/O, the backend locks the session, verifies source/configuration, assignment/current owner/fence/lease, exact context and current committed generation, and persists the refresh intent/digest/callback correlation key. It permits OBSERVING, or PROPOSING with no ADMITTED/DISPATCHING action, and commits OBSERVING before RPC. It refuses ACTING, terminal states and unresolved clarification/auth pauses. Real nonfinal `completeStep`, accepted public clarification or supported authentication resume must perform their existing transition first; refresh never answers or silently resumes them. The prior observation stays historical and cannot authorize admission while OBSERVING.

The worker requires a live acknowledged lease and idle matching context. Compare expectedGeneration to current committed execution evidence, clear unconsumed preparations, reserve local observation count, and collect a new strictly greater generation within the remaining node/depth/time/byte limits. This command cannot turn initialBlank into a fake approved-origin observation. Preserve the local value map, producer handles, action count and ordinals. Commit the owning-worker observation callback before exposing the new local evidence or returning its sanitized envelope. Observation-count reservation occurs before collection; actual sanitized bytes are charged once. Accepted backend callbacks consume durable observation/byte budgets once through existing idempotency. Renewal remains independent of the busy collection gate.

Duplicate same-key/same-digest requests join or retrieve the original collection before testing their now-old expectedGeneration. Changed content under the key conflicts. A cached response is usable only while the same owned context remains live and its observation still matches current committed generation/hash with no superseding admission. A later generation, terminal state or local stop makes the old result stale. Backend duplicate recovery can read the matching current committed observation directly without another collection or runner RPC. An in-flight duplicate joins or receives a bounded busy refusal; it never starts a parallel collection. A legitimate unrelated post-action observation can supersede the pending intent; do not reject that observation or roll state backward to preserve the refresh.

After RPC, the backend rechecks the returned complete identity, generation and canonical observation hash against its owner-authenticated committed observation and current PROPOSING state before providing evidence for planning. Losing only the controller's final response is recoverable metadata loss, not an unknown business effect. If the worker loses callback acknowledgement, it cannot claim the new evidence is ready: conservatively stop the context and report lifecycle loss without replay, while preserving already committed successful action outcomes. Cancellation/expiry can leave historical observation evidence but cannot make it usable for more work. Stop blocks late response publication and uses existing value teardown; refresh itself does not reset runtime values or spend an action.

The synthetic fixtures prove DTO/hash/correlation relationships, duplicate/superseding-state rules and counter invariants only. Required OBS-004 joined evidence uses real nonfinal completeStep, then the worker refresh command/callback pair, then an actual next-source-step action retaining the prior local binding, without dummy actions or controller-generated observations. A trusted fixture StepVerifier may recognize known actual first-step receipts. Also require refresh refusal during an unresolved pause and preservation of the existing v1 clarification regression. The v2 answer DTO already exists. OBS-004 exercises the real v2 answer-to-refresh transition using an explicitly labelled trusted question fixture; the missing v2 clarification question schema and production question creation remain OBS-005. A v1 request against a v2 session is a version mismatch, never proof of v2 resume. Arbitrary English completeness and question generation likewise remain OBS-005 responsibilities. Callback/response-loss, busy/stale requests, cancellation, exhausted budgets and retained same-session values require runtime tests. No model privacy decision, publication or replay-readiness claim is added.

## Reviewed QA remediation: raw JSON and UTC timestamp profile

The undeployed v2 bridge uses an explicit supported timestamp profile: four-digit Gregorian year,
valid month/day, uppercase `T`, hours00–23, minutes/seconds00–59, optional1–9 fractional digits,
and terminal uppercase `Z`. Leap seconds, offsets, whitespace/lowercase separators and excess
precision are rejected. Every v2 `format: date-time` field also carries the shared absolute-end
pattern. No timestamp normalization or hash rewrite is permitted. Authority deadlines additionally
must be finite, current and bounded by the acknowledged lease/hard expiry. This is an explicit
coordinator-approved tightening after REL-002; prior source hashes are historical provenance.
Historical v1 schemas and format behavior remain unchanged.

Guided JSON wire readers reject duplicate decoded keys (including escaped and nested aliases),
trailing JSON, malformed UTF-8, noninteger/unsafe numeric lexemes and negative zero before object
validation. Service JWTs have exactly `alg`/`typ` header keys and required `iss`, `sub`, `aud`,
`role`, `iat`, `exp` claims, with only optional `nbf`; no unknown signed claim is ignored. Numeric
claims use canonical-v1 safe integers, with nonnegative times and existing300-second lifetime.
Malformed input is never echoed in a parse/auth failure. The backend applies its raw-body reader
only to guided public/internal controllers and preserves platform BFF authentication.

`wire-parity.fixtures.json` contains exact base64 raw bytes and positive/negative timestamp vectors.
Java, the runner and Ajv verify the same v2 schema instances. The runner audits only its explicitly
supported active schema roots and reachable references; unresolved JSON pointers, unsupported
validation keywords/formats and malformed schema constructs fail closed at load. This does not
claim OBS-006 learned-plan execution support.
