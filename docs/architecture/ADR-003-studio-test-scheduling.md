# ADR-003: Recurring execution of confirmed Studio tests

Date: 2026-10-05. Decision owner: Aria. Status: accepted for the local implementation of STUDIO-SCHED-001; production activation remains gated.

This records the choices adopted in the [approved specification](../stories/STUDIO-SCHED-001/spec/spec.md) and [implementation contract](../stories/STUDIO-SCHED-001/spec/implementation-contract.md), following independent critique and PO readiness. It adds eight public Studio operations and optional execution provenance to [OpenAPI](../specs/studio/openapi.yaml), without changing runner-produced bodies or admitting legacy schedule JSON as operational work.

Studio tests have their own confirmed revisions, readiness and durable admission ledger. Ordinary check schedules require catalog check IDs and use retry semantics that cannot safely replay uncertain browser actions. The feature therefore uses dedicated typed schedules, immutable activation events and occurrence records, with one stable schedule anchor per saved test. It reuses Studio admission, quotas, dispatch, reference authorization, callbacks, recovery and protected evidence.

Creation is paused. Resume acknowledges the exact ready revision and every outstanding uncertain execution, recording the human actor separately from the background principal. Executable edits or replacement confirmation cannot silently resume future work. Pause/removal settles deferred work and stops future acceptance while preserving accepted runs and audit. Production authorization fails closed; explicitly configured local/test grants provide development evidence only, with secret permission still independently required.

Preview and due production share the server recurrence resolver: zero seconds, minute granularity, validated UTC/IANA timezone, earlier offset once per repeated local slot, and skipped nonexistent slots. Grace defaults to five minutes. The producer skips historical catch-up, bounds missed-range reporting, and retains one nominal occurrence through temporary pre-acceptance deferral. Non-DONE work prevents scheduled overlap. DISPATCH_UNKNOWN, START_TIMEOUT and STALE require investigation and explicit acknowledgment before future slots.

Acceptance serializes test, schedule and occurrence work, then uses existing global/CSI quota locks. Occurrence disposition, immutable history/ledger work and cursor changes commit atomically. The ledger owns the unique occurrence-to-execution link; deferred database constraints validate its provenance at acceptance. Existing callbacks avoid additional schedule locks or revalidating pruned historical details. Audit and uncertainty identities survive detail/video retention and schedule recreation.

Worker/local due production has a separate bounded executor and CSI rotation; API-only instances do not poll. Scheduling defaults off independently of existing dispatch/recovery. Rollback disables new production/activation first and retains compatible handling for already accepted work and durable audit. Database restores older than external browser effects require operator reconciliation before scheduling is enabled.

[Operations](../specs/studio/scheduling/operations.md) provides terminal administration and configuration. [Implementation evidence](../stories/STUDIO-SCHED-001/implementation/) records measured checks and limitations. Live production identity/vault revocation, capacity, restore/retention and on-demand Studio trust evidence remain release prerequisites. Local fixtures and mock/browser UI tests do not establish those integrations.
