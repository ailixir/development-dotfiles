# Guided authoring and observed replay operations

OBS-006 adds deterministic publication and ordinary recorded replay. It does not provide author-owned login through `<secret ID>` steps (OBS-007), automatic Run-client finalize/poll/reconnect (OBS-008), the recorded first guided Run (OBS-013: `GET /api/v1/studio/guided-sessions/{id}/video`; playback is OBS-008), live-model benchmark (OBS-009), or human pilot (OBS-010). An unconfigured account provider refuses; it is not a permissive production fixture.

## Deployment prerequisites and privacy

Apply classpath migrations through V33 before deploying the new API. Preserve V30–V32 and all original receipts/history. V33 adds immutable publication base/original preparation evidence, fenced validator attempts, revision origin/receipt constraints and ordinary execution binding. It creates no execution success or schedule activation. Publication-enabled sessions capture a base before worker assignment; older sessions without a base cannot be backfilled or replayed to manufacture proof.

Deploy the matching packaged observed schemas, reference fixtures and execution profile catalog on backend and runner. The trusted catalog associates profile/schema/reference hashes with actual immutable image and Chromium identities; copied version labels are insufficient. Backend `studio.observed-replay.catalog-json` contains trusted `{profile,build}` entries; `policies-json` contains trusted effective policy snapshots. Runner uses `STUDIO_RUNNER_OBSERVED_CATALOG_FILE`, `STUDIO_RUNNER_OBSERVED_IMAGE_DIGEST`, `STUDIO_RUNNER_OBSERVED_POLICY_FILE`, and independent `STUDIO_RUNNER_OBSERVED_VALIDATION_ENABLED` / `STUDIO_RUNNER_OBSERVED_REPLAY_ENABLED`. Paths and registry entries come from deployment, never jobs or artifacts.

Observed-choice proof changes the packaged validation schema and its exact build identity while preserving the executable profile. Deploy the backend, pure validator, packaged schema and trusted catalog as one supported combination. An older build-pinned artifact must use its retained or re-enabled compatible exact build; matching executable profile alone does not permit it on the new schema bundle. There is no automatic build translation or deployment router. If its compatible build is unavailable, refuse before browser admission and restore that supported combination or deliberately relearn. Never rewrite historical schema/build pins or strip a choice witness to obtain acceptance.

The observed replay policy preserves optional field-only rules: applicationPolicy=null maps to omission at the collector. A present application policy has allowStructuralDiscovery=true and at most32 uniquely identified application/region read grants. Structural discovery is not read permission. Optional field overrides retain independent testId/accessibility/classification validation and may reuse policy IDs. Do not widen the original collector or configure per-control mappings as a mandatory happy path.

Use the existing `studio.runner` service URL and restricted service token for pure validation/ordinary run submission. The ordinary backend `/internal/**` callback chain validates its configured static service token; it does **not** verify the guided-only certificate/JWT identity. Protect the service hop with deployment TLS/internal routing. Runners sharing that token form one trusted service boundary. Guided authoring continues its separate verified JWT/mTLS bridge. Do not forward certificate headers as authentication.

Model input policy remains INPUT-POLICY-01 A: deliberate nonsecret authored literals may reach the learning model; resolved saved values, secrets, account material and captured/page values do not. Publication and saved replay call neither model gateway. Full prompts/model-returned versions absent from immutable history remain unknown; outputContractHash is not a substitute full-prompt digest. Runtime values/account handles are ephemeral and excluded from revision/receipt/diagnostics. Authorized ordinary replay video is a separate evidence channel.

The guided runner client reads `studio.guided-authoring.controller-token-file` (environment `STUDIO_GUIDED_RUNNER_CONTROLLER_TOKEN_FILE`) containing a backend-controller token with textual audience `studio-guided-runner`. The translation coordinator separately reads `studio.guided-authoring.translation.controller-token-file` (`STUDIO_GUIDED_CONTROLLER_TOKEN_FILE`) with textual audience `studio-guided-controller`. The old property remains a compatibility fallback, but one token cannot legitimately authenticate to both receivers; enabled production coordination must mount the two audience-specific files. Both transports reload their token file for each send. Refresh credentials before their existing maximum300-second lifetime expires; preserve issuer, subject, role, verified TLS and time checks. Never use audience arrays/common audiences or put tokens in session/model/revision records. Wrong/swapped audience files must refuse before work.

## Independent feature flags and clocks

`studio.guided.publication.enabled` and `studio.observed-replay.enabled` default false. With both off, existing guided starts and compatible legacy replay remain available; authorized historical receipt reads remain available. Publication off/replay on permits already published compatible observed revisions but creates no new publication bases. Publication on/replay off captures original learning evidence but cannot publish ready artifacts until replay is enabled within the original live lifecycle. Both on enables the complete path. Never add a base to an older session or extend an expired session merely to save it.

Hard ceilings: three pure validation claims per session across keys/restarts, validator15 seconds, active publication Core grant5 seconds capped by original claim/session/current worker authority, and fresh explicit replay admission grant30 seconds. Configuration can tighten these limits. New wire/SQL identity timestamps use identical UTC millisecond-normalized instants; deadlines truncate down. Same-owner/fence heartbeat renewal does not alter the captured validation snapshot or extend its deadline. Source/head/fence/cancellation changes still refuse.

Observed artifact/body/frame caps are documented in publication-contracts.md C1. Enforce bounds while receiving, not after unbounded buffering. Legacy64KiB artifacts and existing legacy body/runtime limits remain unchanged. Recording dimensions are trusted configuration and separate from authored viewport; observed configuration is hash-bound and cannot be silently clamped/defaulted. Account application consumes the original recording/run clock; Ready does not reset the clock.

## Publication, reconnect and receipt access

The real BFF endpoint is `POST /api/v1/studio/guided-sessions/{id}/finalize` (operation `finalizeObservedPublication`, served by `GuidedPublicationController`). From the Studio client the path is `/studio/guided-sessions/{encodeURIComponent(sessionId)}/finalize` over the `/api/v1` API client base, so the prefix appears exactly once. It takes the ambient put_session cookie (`withCredentials`), a stable finalize `Idempotency-Key`, and the closed v3 body of `publication.schema.json`: `{schemaVersion:3,expectedSourceRevision,expectedConfigurationRevision}`, the two revisions being the exact decimal strings from the started context. The body never carries `ownerFence`, `sessionId`, a supplied hash or an internal token. This public OpenAPI contract takes precedence over the retired versioned path and the `schemaVersion:2` body this paragraph used to name, and over the internal `commands.finalize` schema. OBS-008 invokes it automatically at FINALIZING as continuation of the original Run, without another confirmation or browser execution, and exactly once per session (one promise latch that survives a StrictMode double mount). A lost response or a reconnect repeats the same key and body. A disconnected client, expired cookie, a `401`, unavailable Core (`503`) or rejected validation must remain pending/not-ready and is never shown as success. After the session has expired, read the receipt only through `GET /api/v1/studio/guided-sessions/{id}/result`; never refresh or reopen a worker. Fresh Core authorization, deterministic pure validation and the immutable publication receipt remain backend authority, and finalize makes no model, browser or Vault call. Never manually invoke internal supplied-hash finalization to bypass the public authority path.

Finalization joins actual successful admissions/assertions/dependencies and original per-preparation observations, validates the immutable artifact independently in pure Node, then refreshes actual uncached Core authorization outside locks. Commit atomically creates revision/receipt/head/session success and clears the old compile-request pointer. A newer publication, source/configuration edit or compile/head ABA loses the CAS. Keep the successful browser evidence on conflict; do not replay it.

Accepted observed choices require prospective original question/attempt/plan evidence plus an immutable acceptance snapshot captured at the actual preparation boundary. Original question nodes and fresh preparation nodes are proved separately using the exact selected durable locator. Missing historical proof, a preparation without its acceptance receipt, or multiple accepted questions for one obligation requires deliberate new learning; these immutable rows cannot be backfilled. The preserved original answer timestamp is audit data, not a newly inferred acceptance actor or authorization grant. Zero-choice and source-only evidence omit the optional witness entirely.

Base-enabled public polling uses session-view3/result3. The receipt's revisionId is a database UUID and revisionDigest is a separate cryptographic identity. PUBLISHED describes immutable history; currentReadiness independently describes whether that exact receipt revision is still ready. Historical receipt access uses fresh current Core canRead and the original principal even after worker/session expiry or source/head changes. It neither requires canExecute nor performs another validation/account setup/browser call. Current Core denial or absent cookie still refuses. First guided video remains unavailable until OBS-008; publication creates no synthetic ordinary PASSED execution.

Each later explicit ordinary Run obtains its own fresh Core execute grant and scoped account authorization. Queue delay/transport/lock wait cannot refresh its30-second window. The documented Core-only revocation lag is bounded by that window, not instantaneous distributed revocation; local cancel/current policy/account revocation also blocks new admission. No provisional authorization or old learning consent grants replay. Observed scheduled runs fail closed without real unattended authority; legacy schedules remain unchanged. Existing activations are never retargeted: old activation/new head produces ACTIVATION_REVISION_MISMATCH.

## Staged V19 compatibility and rollback

V19 is an optional staged cutover at `backend/db/cutover/V19__studio_inference_candidate_identity.sql`, not the classpath migration number. Do not mark it installed merely from Flyway history. V33 detects the enabled `trg_ui_test_revision_require_request` and matching `studio_inference_require_request` function. Partial/inconsistent catalogs refuse migration for operator repair.

If original staged V19 is already installed, V33 upgrades its function to retain ordinary real-request enforcement while allowing only strict guided origin with the deferred matching receipt cycle. If V33 is installed first, use the updated staged V19, which detects V33 capability, preserves guided indexes/constraints and drops only the intended ordinary dedup index. Without staged V19, V33 preserves historical ordinary null-request compatibility and an ordinary-only equivalent V24 index; it does not silently activate cutover. V21 continues copying locked current authoring; V29 remains deny-by-default immutable. Verify both installation orders on a restored deployment-equivalent schema before rollout; never edit a previously applied classpath migration.

Rollback keeps the forward schema and immutable receipts. Disable new publication claims/commits first, and disable new observed acceptance/dispatch/admission while draining or cancelling already admitted ordinary runs under their existing deadlines. An older image lacking the observed profile refuses artifact2 before browser; it must not enter legacy parsing/model repair. Restore a supported compatible catalog/image or deliberately relearn. Benign learning-prompt/provider/API changes alone do not invalidate saved execution compatibility. Do not reset schedules, rewrite historical pins, replay unknown effects, reuse consumed account setup or manufacture a new worker from old admission history.
