## Story

**As a** the Studio compile pipeline that every author's test compiles through today (the live FULL path),
**I want** the model request restructured so static content leads in `systemInstruction`, the global context is sent exactly once, the response schema has a deterministic key order, the thinking level is sent explicitly and pinned into the compilation fingerprint, usage is recorded completely (including thoughts and cached tokens, null not zero when absent), and repair carries the rejected proposal instead of retrying blind,
**so that** the cost paid on every compile today becomes visible and measurable for the first time, without claiming or depending on any caching saving that has not been verified.

## Acceptance Criteria

1. **AC-11.1** (FR-11, spec §2.1 / requirements.json FR-11): Given two compile requests for different tests at the same prompt/policy pins, then the serialized request bytes before the first request-specific field are identical.
2. **AC-11.2** (FR-11): Given the reorder, then the prompt version pin advances (C0 §6 coordinated pins) and the change is covered by the 10.26 harness before enablement. *(The 10.26 harness run itself is a precondition of `GATE-ENABLE` / `GATE-1026-THINKING`, not of this story's own merge — implementation.yaml subtask 1.6 note: "The AC-11.2 harness coverage happens at GATE-ENABLE, not at A's merge".)*
3. **AC-12.1** (FR-12, also NFR-7 "prompt is linear in steps and not multiplied by global context"): Given a test with G bytes of global context and S steps, then the serialized prompt contains the global context exactly once.
4. **AC-13.1 / AC-13.2** (FR-13): Given a gateway response with usageMetadata including thoughts and cached tokens, then both are persisted in attempt telemetry. Given a response without `cachedContentTokenCount`, then the stored value is null, not 0.
5. **Deterministic provider schema** (spec §3.2.6 "Provider schema"; §6.1 unit test row "Provider schema bytes identical across two fresh JVMs / hash seeds"; named as Story A scope in spec §9: "deterministic schema"): `providerSchema()` is built with a deterministic key order (`LinkedHashMap`/sorted, not `Map.of`), so its serialized bytes are identical across JVMs and hash seeds. The FULL schema's content is otherwise unchanged by this story — the kind-dependent `PREFIX_IMPACT` arm for `PATCH` is Story B2 scope (spec §3.2.5), not this story's.
6. **Explicit, pinned thinking config** (spec §3.2.6 "Thinking"; FR-13; named in spec §9 as "fingerprint with thinkingLevel (pinned MEDIUM)"): `thinkingConfig.thinkingLevel` is always sent explicitly, is never combined with `thinkingBudget`, and is never `MINIMAL` for gemini-3.8-flash. The level is included in the compilation fingerprint. The pinned value is `MEDIUM` — **inferred** to match the gemini-3.8-flash default (Gemini API docs), not verified for Vertex/R2D2; verification is SPK-01's job, not this story's.
7. **Degradation switches** (spec §3.2.6 "Degradation", EC-17/CON-8): if the R2D2 proxy rejects `systemInstruction`, the identical static bytes are sent as the leading text of `contents[0]` instead, preserving static-first order. If it rejects `thinkingConfig`, the field is omitted and the fingerprint records `thinkingLevel:"PROVIDER_DEFAULT"`. `MINIMAL` is rejected at property binding.
8. **Repair carries the rejected proposal on the live FULL path** (FR-10, partial — spec §9 names "rejected-proposal repair on the live FULL path" as Story A scope; §3.2.6 "Repair"): the repair request carries explicit correction instructions plus the bounded, redacted rejected proposal and diagnostics, keeps the same `kind`, and never widens the write set. `RepairRedactionTest` is extended to assert no resolved values and no secret material appear in the rejected proposal (NFR-5). The existing 3-proposal / 3-of-9 transport bounds (NFR-4) are unchanged. *(FR-10's own AC-10.1/AC-10.2 describe an INCREMENTAL compile and are Story B2 scope — not literally testable here, since incremental does not exist yet. This criterion is the live-FULL-path subset of FR-10 that implementation.yaml subtask 1.5 assigns to Story A.)*
9. **Size cap unchanged** (FR-5 AC-5.2 / EC-15, touched incidentally by the prompt-assembly restructure per implementation.yaml subtask 1.4): the context size cap is measured after deduplication; an oversized complete context produces `CONTEXT_TOO_LARGE`, and the prompt is never truncated.
10. **No caching benefit is claimed.** (spec §1 Overview: "No net saving is claimed"; NFR-2; §3.2.6 "Caching claim".) The static prefix is ~9.2 KB, roughly 2.3–2.7K tokens (**inferred**, not tokenized — research.json `researchQuestions.Q1_genai_vertex`), which is below Gemini 3.x's 4,096-token implicit-cache minimum, so **no savings are claimed or targeted from implicit caching in this story**. `cachedContentTokenCount` is recorded and reported only — it is never a pass/fail target. The **net** per-Run cost (FULL vs. INCREMENTAL, including the candidate efficiency levers this story ships: suffix-only output, thinking level, global-context dedup) is **unmeasured until SPK-01 confirms what the R2D2 proxy forwards/returns and the live 10.26 evaluation measures it** (NFR-1, CRIT-7, spec §7 risk "Net cost of INCREMENTAL is higher than FULL"). This story performs no live enablement of any flag (CON-3, CON-8).

### Why this story ships alone, and why it is LIVE-AFFECTING

- Story A restructures the **one live model request every compile makes today** — no flag gates it, because none of its scope depends on incremental compilation existing. It is worth shipping even if incremental compilation never ships (implementation.yaml `stories.A.valueStatement`).

### The caching non-claim — restate in PR description and review

Spec §1 Overview, verbatim: *"No net saving is claimed: INCREMENTAL sends the locked baseline code as extra input, and an escalated request is wasted spend, so the net per-Run effect is measured, not assumed."* For Story A specifically: the static prefix is ~9.2 KB / ~2.3–2.7K tokens (**inferred**, not tokenized — research.json `Q1_genai_vertex`), below Gemini 3.x's 4,096-token implicit-cache minimum (research.json, VERIFIED from Gemini API docs). **Do not report or imply a caching saving from this story.** `cachedContentTokenCount` is captured so a *future* benefit can be observed if the prefix grows or request volume increases — it is not evidence of a benefit today (spec §3.2.6 "Caching claim"; NFR-2; research.json `unverifiedClaims` ASM-2, NFR-2, and "systemInstruction is part of the implicit-cache prefix").
