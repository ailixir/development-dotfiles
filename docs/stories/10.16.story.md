## User Story

**As a** CSI-authorized support engineer looking at a Studio run,
**I want** to see the run's evidence state as it arrives, without the page overstating it; to play and seek the recording by clicking the step whose moment I want to see; and to download the recording when I need to keep a copy,
**so that** I can trust what the platform tells me about a recording it may not have yet (or may never have), and reach the moment that matters without scrubbing through the whole video by hand.

## Problem Statement

Verified by reading the merged tree on this branch. **Item 1 was corrected at validation**: the draft said nothing renders video, which is false.

**1. The page renders video today, and does it in three ways the architecture forbids. No criterion in any story owns retiring any of them.** `ChecksStudioPage.tsx` has three problems.
- **The playback source.** The page copies `exec.videoPath ?? (exec as any).videoUrl` into Redux (`setVideoUrlAction`, lines 330–333). The `videoUrl` fallback reads a raw URL that is not part of the contract, and §6.3 exposes *only* the protected API path.
- **The legacy element.** Line 1061 mounts `<video src={videoUrl || '/assets/videos/sample-ui-test.mp4'}>`. The fallback file does not exist in `frontend/public/`. The `src` is `videoPath` used as a **relative** path, which is wrong whenever the MFE and API run on different hosts (Problem 3).
- **The synthetic seek.** `handleStepClick` (lines 461–468) seeks to **`stepIndex * 10` seconds**, under the comment *"Simulate jumping to step timestamp in video"*. Architecture §6.4 ends with: *"No synthetic index-times-ten mapping remains."* It remains.

Meanwhile `ExecutionProgressView.tsx`, the one place the contract's `ExecutionSnapshot` is rendered, never reads `snapshot.video` or `snapshot.videoPath`. The page's only evidence text is *"Visual proof will appear after run"* (line 1071). That text renders for `FAILED`, `UNAVAILABLE` and `EXPIRED` alike, so it collapses exactly the states §6.1 says to keep distinct.

**2. No MSW handler answers `GET /executions/:id/video`.** `frontend/src/services/mocks/studio/handlers.ts` has no video route. 10.15's record states *"This story serves bytes; it renders nothing and adds no MSW handler"* (`10.15.story.md:301`).

**3. No client function or URL builder exists for the video route.** `studioApi.ts` has neither. The one precedent for a native-element URL, `studioSseTransport.ts:63` `studioExecutionEventsUrl`, builds its own path under `APP_CONFIG.apiBaseUrl`. The video case differs: the server publishes `videoPath` **already carrying the `/api/v1` base**, asserted by `studioContract.test.ts:206`'s regex. So neither naive concatenation nor using `videoPath` as a relative `src` is correct. Concatenation doubles the base in every configuration. A relative `src` resolves against the MFE's origin, which is wrong when `apiBaseUrl` is an absolute URL on another host. The architecture and `SPK-02` both allow that deployment: the Helm values put the MFE and API on different hosts.

**4. The route's refusal surface is unruled, and this story is the first frontend consumer that has to decide what a client does about it.** `getExecutionVideo` declares exactly `{200, 206, 404, 410, 416}`: no `401`, no `403` (`ESC-1`, filed by 10.15, left red in `ExecutionVideoContractEscalationTest`). `EPIC-10-RUN-LOG.md` DEF-09(b) found that the two refusals the route actually emits do not share an envelope. The wrong-CSI `403` answers `{"error":"STUDIO_FORBIDDEN",…}`, with `error` as a **string**, which matches `ErrorResponse`. The identityless `401` answers `{"error":{"message":…,"traceId":…,"code":"UNAUTHENTICATED"}}`, with `error` as an **object**. That question is @architect's. What this story must decide is what its own code does meanwhile (AC-11, AC-12).

**5. The seek-measurement flake has no owner until this story, and what is actually known about it is less than the record says.** `studio-runner/test/fixtures-tier/seek-measurement.test.ts` failed once during story 10.17. @qa did not reproduce it. Verified at validation: `MEDIAN_TOLERANCE_MS = 100` (line 84), `OUTLIER_BOUND_MS = 1_500` (line 85), and the only *asserted* use of 500 ms is the `.skip`ped AC-12b `describe` (line 298). **Correction by @po:** the manifest's wave-6 text says that because both reported errors (579.9 ms, 882.6 ms) lie between 100 and 1500, *"the assertion that failed was the MEDIAN tolerance"*. That does not follow. The run has five steps, and the median is `errors[Math.floor(5/2)]`, the **third** smallest. It exceeds 100 only when **three** of the five steps do, and two mis-attributed steps cannot move it. **Which assertion failed is unknown.** The candidates include the median (if a third step was also above 100 ms, which was not reported) and the assertion-step check `seekingToTheEnd > ASSERTION_TIMEOUT_MS * 0.5` (1000 ms). AC-15 exists to find out before anything changes.

### 10.16a — Evidence state: independent of outcome, and never invented

- [ ] **AC-1: All five `VideoStatus` values render a distinct, named state, asserted against the document in both directions.** The lookup follows the totality-checked pattern of `executionErrorNarratives.ts`. It is an **object literal typed `Record<VideoStatus, …>`**, so TypeScript rejects a missing key and an excess key. The lookup function **throws** on anything not in the record, with no `??` fallback. It covers `PROCESSING | AVAILABLE | FAILED | UNAVAILABLE | EXPIRED`. `studioContract.test.ts`'s existing `assertSameSet` (line 242) is **extended, not re-implemented**, to compare the lookup's keys against `components.schemas.VideoStatus.enum` read from `openapi.yaml`. Together the two checks bind the type to the document with no runtime carrier. *[Source: architecture §6.1; `openapi.yaml` `VideoStatus`; ADR-002 §18.3 "assert it against this document … the other should extend it rather than write a second one"]*

  *Anti-vacuous:* a sixth value reaching the lookup throws rather than rendering a generic panel. Two states with the same accessible name fail `new Set(titles).size === titles.length`, the guard `studioContract.test.ts:269` already runs for `compileStatus`. Deleting one key from the record reddens `assertSameSet`.

- [ ] **AC-2: `PROCESSING`, `FAILED` and `UNAVAILABLE` render as three distinct messages, never collapsed into one "no video" state, including when the check outcome is already terminal.** A snapshot with a terminal `status` and `video.status: PROCESSING` (`TERMINAL_EVIDENCE_PROCESSING`, `executionScenarios.ts`) renders the evidence region as **still being produced**, not as absent or failed. `UNAVAILABLE` and `FAILED` each render their own wording. They reuse `video.error` verbatim where the server supplies it, and show a generic statement where it is `null`. *[Source: architecture §6.1 "`UNAVAILABLE` covers runs without a usable recording; `FAILED` covers evidence production/upload failures"; §5.4 row 5; 10.11 AC-13]*

  *Anti-vacuous:* the named hazard is `UNAVAILABLE` and `FAILED` rendering one message, which is what the page's current *"Visual proof will appear after run"* does. The terminal + `PROCESSING` fixture exists because a component that gated the evidence region on the check outcome instead of `video.status` would pass every other case.

- [ ] **AC-3: `video.partial` is rendered as a qualifier on an `AVAILABLE` recording only. It is read from `video.partial` and never derived from anything else.** *(Amended at validation.)* Two fixtures make an outcome-derived implementation fail in each direction, and they are §17.3's own two cases:
  - (i) terminal `PASSED` + `video: { status: 'AVAILABLE', partial: true }`, the recorder that died on a passing run;
  - (ii) terminal `ERROR`/`TIMEOUT` + `video: { status: 'AVAILABLE', partial: false }`, the deadline kill that flushed cleanly.

  Case (i) renders the qualifier and case (ii) does not. For a non-`AVAILABLE` status the qualifier never renders, even if the body says `partial: true`. `executionScenarios.ts`'s `TERMINAL_EVIDENCE_FAILED` carries exactly such a body today (AC-14). *[Source: ADR-002 §17.3 "It is `false` with `FAILED` and `UNAVAILABLE`, because a recording that does not exist is not a partial one" and its two cases; §17.4 "never derived from outcome in either direction, by either component"; architecture §6.1 "whether an **available** recording is partial"]*

  *Anti-vacuous:* the existing `fixtures.ts` partial row (execution `4444…`, a timed-out run with `partial: true`) **cannot** falsify an outcome derivation, because deriving from outcome gives the same answer there. That is why cases (i) and (ii) are required. The two mutations are `partial = status !== 'PASSED'` and `partial = errorCode === 'TIMEOUT'`. The first reddens case (i) and the second reddens case (ii).

- [ ] **AC-6: The playback and download URLs are built from the origin of `APP_CONFIG.apiBaseUrl` followed by the server-published `videoPath`, verbatim.** The URL never re-composes `videoPath`'s segments, never concatenates `apiBaseUrl` in front of a `videoPath` that already carries the base, and never uses `videoPath` as a relative URL. The test covers **two** configured bases, using 10.11a AC-20(a)'s method (`10.11.story.md:494`; mutation M14 at line 1721):

- [ ] **AC-7: No code in this story ever puts a credential in a query parameter. ### 10.16a — Handling a route this story cannot safely parse

- [ ] **AC-11: This story's code never reads, branches on or renders the JSON body of any `getExecutionVideo` response, whatever its status.** Only `video.status`, `video.error` and `video.expiresAt` on `ExecutionSnapshot` feed the evidence narrative. ### The URL hazard, restated

`APP_CONFIG.apiBaseUrl` defaults to `/api/v1` (`appConfig.ts:49-53`), and `studioApi.ts` calls are relative paths under Axios's `baseURL`. `videoPath` is **already** `/api/v1/…`, so every concatenation doubles the base. A relative `src={videoPath}` works only when the MFE and API share an origin. The correct construction is the origin of `new URL(APP_CONFIG.apiBaseUrl, window.location.href)` followed by `videoPath`. `studioSseTransport.ts:63`'s style can be followed (trim trailing slashes, no query credentials), but not its composition.

### Why `<video>` and download bypass `apiClient`

`apiClient.ts`'s interceptor handles a `401` only for requests made through Axios. A `<video src>` request and an anchor navigation are browser-native, so that interceptor never sees them. That is why AC-12 is a separate, deliberately generic media-error handler. Routing the bytes through `fetch` + blob would also defeat §6.3's `206`/Range support, which exists so the browser can issue its own Range requests while seeking.

### A cross-origin attribute to avoid (@po inference, not a criterion)

Do not set `crossOrigin="anonymous"` on the `<video>`. Under the HTML fetch rules that mode omits credentials, which would strip the ambient session §6.3 requires. Whether `use-credentials` is needed in the cross-host deployment is `ED-06`/`SPK-02`'s question (10.11 AC-20(b)), so leave the attribute unset rather than guess.
