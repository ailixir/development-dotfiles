## User Story

**As a** CSI-authorized support engineer looking at a Studio run,
**I want** to see the run's evidence state honestly as it arrives, play and seek the recording by clicking the step whose moment I want to see, and download it when I need to keep a copy,
**so that** I can trust what the platform is telling me about a recording it may not yet have (or may never have), and get to the exact moment that matters without scrubbing through the whole video by hand.

## Problem Statement

Verified by reading the merged tree on this branch.

**1. Nothing renders `video`, `videoPath`, or a step's `offsetMs`/`durationMs` as a seek target.** `ExecutionProgressView.tsx` — the one place `ExecutionSnapshot` is rendered — reads `snapshot.status`, `snapshot.errorCode`, `snapshot.stepResults[].status/offsetMs/durationMs/message` (as text, per AC-19) and `snapshot.logs`. It never reads `snapshot.video` or `snapshot.videoPath`. The five evidence states architecture §6.1 requires kept "independent of the check outcome" are, today, kept independent by not being shown at all.

**2. No MSW handler answers `GET /executions/:id/video`.** `frontend/src/services/mocks/studio/handlers.ts` maps `/tests`, `/tests/:id`, `/tests/:id/compile`, `/tests/:id/confirm-compile`, `/tests/:id/execute`, `/executions`, `/executions/:id` — and stops there. Story 10.15's own record confirms this in words: *"This story serves bytes; it renders nothing and adds no MSW handler."* Verified independently: no `video` string appears anywhere in `handlers.ts`.

**3. No client function or URL builder exists for the video route.** `studioApi.ts` has no `getExecutionVideo`, no download helper, nothing. The one existing precedent for building a full, origin-aware URL for a native browser element that cannot go through `apiClient` — `studioSseTransport.ts`'s `studioExecutionEventsUrl`, built for `EventSource` — hard-codes its own path (`/studio/executions/{id}/events`) rather than reading a server-published path. The video case is different and harder: the server publishes `videoPath` **already carrying the full base** (`/api/v1/studio/executions/{id}/video`, asserted by `studioContract.test.ts`'s own regex), so naively prepending `APP_CONFIG.apiBaseUrl` to it doubles the base whenever `apiBaseUrl` is itself an absolute, cross-host URL rather than a bare path — which architecture and `SPK-02` both say it can be (*"the Helm values deploy the MFE and API on different hosts"*). No existing code in this repository solves this; it is new.

**4. The route's own refusal surface is genuinely unruled, and this story is the first to have to decide what a client does about it.** Verified in three places. `docs/specs/studio/openapi.yaml`'s `getExecutionVideo` declares exactly `{200, 206, 404, 410, 416}` — no `401`, no `403` — while its siblings `getExecution` and `streamExecution` declare both (`ESC-1`, filed by 10.15, left red, awaiting @architect). Separately, `EPIC-10-RUN-LOG.md`'s wave-6 post-merge verification (`DEF-09`) found that the platform's two *existing* refusal shapes do not even share an envelope on the byte level: a `403` on a wrong-CSI principal answers `{"error":"STUDIO_FORBIDDEN","message":"…"}` (`error` a **string**), while a `401` on no identity at all answers `{"error":{"message":"…","traceId":"…","code":"UNAUTHENTICATED"}}` (`error` an **object**) — verified byte-for-byte in the run log. That question — which shape a client should expect — is queued at @architect jointly with ESC-1 and is explicitly **not this story's to resolve**. What this story must do, and what no prior story has had to state, is decide honestly what its own code does in the meantime (AC-11, AC-12).

**5. The seek-measurement flake has no owner until this story.** `studio-runner/test/fixtures-tier/seek-measurement.test.ts` failed once during story 10.17, was not reproduced by @qa "including under heavy Gradle load," and was recorded "taken on trust as pre-existing." @po's wave-6 ruling on 10.15's open question 5 assigns it here, verbatim: *"10.16 … CONSUMES the 500 ms claim, is the next story to touch step seek, and is the only remaining story whose acceptance depends on that number being trustworthy."* Verified independently by reading the file on this branch: `MEDIAN_TOLERANCE_MS = 100` (line 84), `OUTLIER_BOUND_MS = 1_500` (line 85); the only `500` in the file is the `AC-12b` `describe`'s prose (line 291), which is `.skip`ped. The reported 579.9 ms / 882.6 ms errors are above 100 and below 1500, so the assertion that actually failed was the **median** one, not the outlier one — the "500 ms" figure in the original report was wrong, and this story must not re-derive a bound from it.

## Acceptance Criteria

> Every criterion is falsifiable and cites its source. Where a criterion depends on an open external gate (`SPK-06` phase B), it is written **Blocked on `SPK-06` phase B** rather than as something that could pass without staging evidence — the wave-5 standing rule this epic has followed since story 10.3: *a strong assertion never executed is worse than a weak one.*

### Evidence state — independent of outcome, and never invented

- [ ] **AC-1: All five `VideoStatus` values render a distinct, named state, asserted against the document in both directions.** A totality-checked lookup (adapting the pattern `executionErrorNarratives.ts` already established for `ExecutionErrorCode`: a `Record` keyed by every member, a lookup function that **throws** on anything not in it, no `??` fallback) covers `PROCESSING | AVAILABLE | FAILED | UNAVAILABLE | EXPIRED`. `frontend/src/services/mocks/studio/studioContract.test.ts`'s existing `assertSameSet` helper is **extended**, not re-implemented, to compare the new lookup's keys against `components.schemas.VideoStatus.enum` read from `docs/specs/studio/openapi.yaml` — the same document-reading mechanism ADR-002 §18.3 installed for `compileStatus` and O-12 extended for `ExecutionErrorCode`. *[Source: architecture §6.1 "Keep outcome … separate from evidence: PROCESSING | AVAILABLE | FAILED | UNAVAILABLE | EXPIRED"; `openapi.yaml` `VideoStatus` schema; ADR-002 §18.3 "the other should extend it rather than write a second one"]*

  *Anti-vacuous:* a sixth value reaching the lookup throws rather than rendering a generic panel (mirrors `executionErrorNarrative`'s own falsification). Two states rendering the same accessible name is asserted against directly (`new Set(titles).size === titles.length`, the same guard `studioContract.test.ts` already runs for `compileStatus`).

- [ ] **AC-2: `PROCESSING`, `FAILED` and `UNAVAILABLE` are rendered as three distinct messages, never collapsed into one "no video" state — including while the check outcome is already terminal.** A fixture with a terminal `status` (`PASSED`/`FAILED`/`ERROR`) and `video.status: PROCESSING` renders the evidence region as **still working**, not as absent and not as failed; `UNAVAILABLE` and `FAILED` each render their own wording, reusing `video.error` verbatim where the server supplies one and a generic, honest statement where it does not (`video.error` is nullable). *[Source: architecture §6.1 "`UNAVAILABLE` covers runs without a usable recording; `FAILED` covers evidence production/upload failures"; §5.4 row 5 "Preserve check outcome, settle evidence as failed/unavailable"; 10.11 AC-13, whose evidence-arrival lifecycle this story's fixtures reuse]*

  *Anti-vacuous:* collapsing `UNAVAILABLE` and `FAILED` into one rendered `data-testid`/message is the named hazard; the fixture pairs a terminal outcome with `PROCESSING` specifically because a client that gated the evidence region on the check outcome (rather than on `video.status`) would pass every case except this one.

- [ ] **AC-3: `video.partial` is rendered as a qualifier on an `AVAILABLE` state and is never derived from anything else.** A fixture carries `status: 'AVAILABLE'` (terminal `PASSED`) together with `video: { status: 'AVAILABLE', partial: true, … }` — an outcome and a partial recording that agree by coincidence of the fixture, not by any rule — and the rendered text states the recording is partial without implying the run failed. *[Source: ADR-002 §17.3 "a fact about the recording, never about the run"; §17.4 "never derived from outcome in either direction, by either component"; architecture §6.1 "whether an available recording is partial"]*

  *Anti-vacuous:* falsified by computing `partial` from `status !== 'PASSED'` (or any outcome field) instead of reading `video.partial` — red on exactly this fixture, where the two disagree with what such a derivation would produce.

### Playback surface — mounts, and requests, only when the state says so

- [ ] **AC-4: The `<video>` element is attempted only when `video.status === 'AVAILABLE'` and `videoPath !== null`; for every other state, no request to the video route is ever issued and no `<video>` element mounts.** Driven through MSW with request counting at the mock server (the same "counted at the server, never by asserting a cleanup callback" discipline 10.11 AC-13 uses for its subscription-count guard) — for each of the four non-`AVAILABLE` fixtures, the count of requests to `*/api/v1/studio/executions/:id/video` observed at the server is **zero**. *[Source: architecture §6.1, §6.3; the request-counting pattern established in `studioSseStreaming.node.test.ts`/10.11 AC-13]*

  *Anti-vacuous:* falsified by mounting `<video src>` unconditionally and gating only the visible chrome around it — the request count catches a mount that never paints but still fetches, which a DOM-only assertion would miss.

- [ ] **AC-5: The download affordance is a plain navigation carrying `?download=true`, opened so a failed download never navigates the user away from the run they were viewing, and invents no filename.** The link/button targets a new browsing context (`target="_blank"`, with `rel="noopener"`); the filename is whatever the server's `Content-Disposition` supplies — nothing in this story's code constructs or overrides a filename. Enabled only under the same `AVAILABLE` gate as AC-4. *[Source: architecture §6.3 "`?download=true` uses the same authorization with an attachment filename derived by the API"; epic §10.15 "download" scope, consumed here as the client of that behaviour]*

  *Anti-vacuous:* falsified by constructing a client-side filename (e.g., from `testId`/`executionId`) — a test asserting the anchor carries no `download` attribute with an invented value, only the query parameter, catches it.

### URL construction — the double-base hazard, and no credential in the query string

- [ ] **AC-6: The playback/download URL is built from the origin of `APP_CONFIG.apiBaseUrl` plus the server-published `videoPath`, verbatim — never by re-composing `videoPath`'s own segments, and never by concatenating a path-shaped `apiBaseUrl` in front of a `videoPath` that already carries the full base.** Asserted for **two** configured bases, mirroring 10.11a AC-20's method exactly: (i) the default path-only base (`/api/v1`), where the origin is the page's own; (ii) an absolute, cross-host base (`https://api.example.internal/api/v1`), matching architecture's "MFE and API deployed on different hosts." In both cases the constructed URL's path is exactly `videoPath`'s value, with **no doubled `/api/v1` segment**, observed on the constructed string — not on the request that MSW happens to still match. *[Source: architecture §5.5/§6.3 origin discussion; SPK-02 question 1 "the Helm values deploy the MFE and API on different hosts"; `studioContract.test.ts`'s `videoPath` regex `^/api/v1/studio/executions/[0-9a-f-]+/video$`; 10.11a AC-20's method, extended here to a second URL builder]*

  *Anti-vacuous:* falsified by the naive `` `${APP_CONFIG.apiBaseUrl}${videoPath}` `` — passes case (i) (the two segments do not overlap when the base is bare `/api/v1` and gets stripped to nothing meaningful in a path-relative browser context) and fails case (ii) with an observable `/api/v1/api/v1/studio/...` — which is exactly why both cases are required and neither alone would catch it.

- [ ] **AC-7: No credential is ever accepted or added as a query parameter on this route's requests; `download=true` is the only query parameter this component ever appends.** A request carrying `?token=…`/`?access_token=…` in addition to a valid ambient session is served exactly as without it (asserted against the MSW handler's own behaviour, since this route's authorization is out of this story's hands — 10.15 owns it); this story's own code never constructs a URL with any parameter other than `download`. *[Source: SPK-02 *Shapes*, quoted verbatim by 10.15's own File List: "10.15 assumes an ambient session route (§6.3) and must not add token query parameters"; §5.5's analogous SSE rule, extended here]*

### Step seek — reads AC-19's values unaltered, and disables what cannot be sought

- [ ] **AC-8: Clicking an attempted step's offset seeks the video to that step's `offsetMs`, converted to seconds for the `<video>` API and to nothing else — no rounding beyond that unit conversion, no re-basing, no client-side calibration.** `offsetMs` is read from the snapshot exactly as `ExecutionProgressView`'s `StepTimings` already renders it (AC-19, 10.11a) — the same prop, not a second read. A fixture whose first attempted step's `offsetMs` is non-zero (e.g., `120`) proves the seek target is not re-based against "the first step seen." *[Source: architecture §6.4 "persist `offsetMs`… Use a monotonic runner clock and calibrate its origin against the pinned recorder's first frames"; ADR-002 §INT-5 "the API applies no calibration of its own… never re-bases readings against the first one it sees"; 10.11a AC-19, whose values this story reads and must not re-touch]*

  *Anti-vacuous:* falsified by adding any client-side offset/calibration term, or by re-basing against the smallest observed `offsetMs`, on a fixture where step 0's own offset is non-zero — the seek target moves and the assertion catches it.

- [ ] **AC-9: A step with a null `offsetMs` (`SKIPPED`, or never attempted) offers no seek affordance at all — disabled, not merely inert, and exposed to assistive technology as unavailable using the existing `NOT_ATTEMPTED` wording.** Clicking (or activating via keyboard) a disabled step's offset never calls the seek handler and never moves `currentTime`. *[Source: architecture §6.4 "`SKIPPED` steps have null timing and disabled seek"; §8.2 "Skipped/unstarted timings are null"; the existing `NOT_ATTEMPTED`/`timingText` pattern in `ExecutionProgressView.tsx`, reused rather than re-worded]*

  *Anti-vacuous:* falsified by seeking to `0` for a null offset — the exact `?? 0` bug AC-19 forbids one layer below, reintroduced one layer above it in the seek handler. A fixture with a `SKIPPED` step after a `FAIL` proves it: the seek call is asserted **not to have happened** at all, not merely to have happened "somewhere near zero."

- [ ] **AC-10: A wait/assertion step's seek target is its recorded start, never a value computed from its `durationMs` or finish.** A fixture whose assertion step has an `offsetMs` far earlier than `offsetMs + durationMs` (mirroring 10.12's own AC-12a fixture, which held the two instants seconds apart specifically to make this falsifiable) proves the seek lands at the start, not the end. This story does not re-measure §6.4's rule; it consumes the value 10.11a already preserves and 10.12 already proved is taken at the step's start. *[Source: architecture §6.4 "Clicking a wait/assertion seeks its start, not necessarily the later instant its condition becomes true"; 10.12 AC-12a, which asserted this on the runner side; 10.11a AC-19]*

  *Anti-vacuous:* falsified by seeking to `offsetMs + durationMs` (or to `durationMs` alone) — red on the fixture whose two values are seconds apart.

### Honest handling of a route this story cannot safely parse

- [ ] **AC-11: This story's code never reads, branches on, or renders `getExecutionVideo`'s JSON response body, for any status.** `video.status`, `video.error` and `video.expiresAt` — fields already delivered, closed and well-declared on `ExecutionSnapshot` — are the **only** source this story renders an evidence narrative from. Playback is a native `<video src>` request and download is a plain anchor navigation; neither is issued through `apiClient` or `fetch` by this story's own code, so neither ever hands a JSON body to JavaScript for this story to (mis)parse. **This closes the question the mission context raises (ESC-1's undeclared `401`/`403`, and `DEF-09(b)`'s finding that the platform's two existing refusal shapes do not share an `error` envelope shape) without resolving either escalation**: they bind no code this story ships, because there is no code path here that ever receives the body they are about. Recorded as a **design decision, enforced by review** — like 10.11's "no second parser" constraint, this is a **not-a-guard**: nothing in a runtime suite can fail because someone adds a `fetch` call that parses `error` from this route, so a reviewer checks that no such call exists, and that check is named here rather than pretended to be automatic. *[Source: mission context — ESC-1 (10.15, awaiting @architect), `EPIC-10-RUN-LOG.md` DEF-09(b) (byte-verified envelope divergence, "joins ESC-1 in @architect's queue as one question"); the review-enforced-constraint pattern established in 10.11 §"The 'no second parser' constraint is a review constraint, not a guard"]*

- [ ] **AC-12: A native `<video>` element that fails after being assigned an `AVAILABLE` URL renders exactly one honest, generic, non-diagnostic message — distinct from all five `VideoStatus` messages — and that message's wording never varies by the underlying failure.** A `<video>` element's `error` event exposes a `MediaError.code` (a small closed set: aborted / network / decode / src-not-supported), never an HTTP status, so this application does not fabricate a `401`-vs-`403`-vs-infrastructure narrative it structurally cannot observe. Proven two ways: (a) **positive** — simulating the element's `error` event renders the message; with no error, the message never appears; (b) **equivalence** — the exact same rendered text results whether the underlying MSW fixture for that request would have answered `401`, `403`, `404`, `410`, `416`, or aborts the connection outright — i.e., the test proves the UI text does **not** vary by simulated status, which is the falsification for a claim like "we can tell the user *why* the video is unreachable in this case." *[Source: mission context, same as AC-11; HTML native media error semantics (`HTMLMediaElement.error`), which exposes no HTTP status — a platform fact, not an invented constraint]*

  *This criterion was tightened once already, at draft time.* A naive version — "renders a generic message on error" with no positive-trigger test — would be satisfied by a component that never wires the `error` event handler at all and simply never shows an error surface; the positive-trigger half of (a) is what makes that shape fail.

## Weakest criteria

- **AC-18 is the weakest by construction, and cannot be strengthened.** Re-running a probabilistic, once-observed flake five (or five hundred) times and seeing it not fire is evidence of absence, never proof of it. The criterion is written to say exactly that rather than let a clean run count imply more than it can. This is the honest floor, not a gap to close later.
- **AC-12 needed tightening at draft time before it was written down** (recorded in the criterion itself rather than discovered at review): a version asserting only "the same message renders regardless of status" would be satisfied by a component that wires no error handling at all. The positive-trigger half — the message must actually appear when the element's `error` event fires, and must not appear when it does not — is what a reviewer should check was not quietly dropped during implementation.
- **AC-1 is the epic's own, previously-proven pattern (`executionErrorNarratives.ts`), not a new invention**, and is accordingly the strongest criterion in this list rather than a weak one — named here only to contrast with AC-12, which had no precedent to copy.

### The URL-doubling hazard, restated for the implementer

`APP_CONFIG.apiBaseUrl` defaults to the bare path `/api/v1` (`frontend/src/utils/constants/appConfig.ts`), and every existing `studioApi.ts` call is a **relative** path composed under Axios's `baseURL` — so `/studio/executions/${id}` + base `/api/v1` naturally produces `/api/v1/studio/executions/{id}`, matching `videoPath`'s own value. That coincidence is exactly what makes the double-base bug easy to miss in the common (same-origin, path-only base) case and only visible once `apiBaseUrl` is an absolute, cross-host URL — which architecture and `SPK-02` both say production can be. `studioSseTransport.ts`'s `studioExecutionEventsUrl` is the one existing precedent for constructing a full URL for a non-Axios browser API, but it builds its own path rather than reading a server-published one, so it is a precedent for *style* (strip trailing slashes, no query credentials) and not a template to copy verbatim for this case.

### Why `<video>`/download bypass `apiClient` entirely, and why that is correct here

`apiClient.ts`'s response interceptor already handles a `401` globally (dispatches `put:auth:unauthorized`), but that interceptor only ever sees a response if the request went through the Axios instance. A `<video src>` and an anchor navigation both issue their own browser-native requests outside Axios, so that interceptor never fires for them — which is precisely why AC-11/AC-12 do not (and structurally cannot) reuse it, and why the honest answer is a separate, deliberately generic native-media-error handler rather than an attempt to route video traffic through `apiClient` just to get uniform error handling. Routing a `<video>` element's byte stream through a JS `fetch`-and-blob layer to get that uniformity would also defeat the server's own `206`/Range support (§6.3), which exists precisely so the browser can issue its own Range requests during seeking.
