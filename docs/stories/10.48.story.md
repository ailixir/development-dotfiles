## Story

**As a** CSI owner or platform security reviewer,
**I want** `POST /tests/{id}/execute` to start a Studio run only for the owners of that test's CSI and explicitly authorized administrators, as architecture §9.1 requires,
**so that** no other authenticated user can spend the CSI's runner capacity or drive its test accounts, including tests that type that CSI's vault secrets into allowed origins, and so that a user who cannot run a test sees that in the UI before pressing Run.

## Acceptance Criteria

1. **Refusal, non-oracle.** `POST /api/v1/studio/tests/{id}/execute` returns `403` when the authenticated caller fails `CsiOwnershipEvaluator.canExecute` on the test's CSI. Covered callers: a `viewer`, a `contributor`, an identity with no ownership at all, and an `owner` of a *different* CSI. The response body is **byte-identical** to the `403` for a random unknown test id (same assertion style as `StudioAuthorizationIT:179-197`) and names neither the test nor its CSI. A refused request creates no `ui_test_executions` row, no `studio_dispatch_ledger` row, no idempotency record, calls no readiness, quota or vault/secret resolution, and sends nothing to a runner.
2. **Allowed callers.** A caller who is an `owner` of the test's CSI gets `202` (existing behaviour, unchanged). A caller with an admin role (`checks-admin` or `platform-admin`, the evaluator's own set) gets `202` for a test in a CSI they do not own. The existing `409` codes (`COMPILE_REQUIRED`, `RUNTIME_INCOMPATIBLE`, `IDEMPOTENCY_KEY_REUSED`, `TEST_DELETED`, `TEST_QUARANTINED`) and the `429`/`503` answers are unchanged for those callers.
3. **Same decision as everywhere else.** `StudioService.executeTest` decides with `CsiOwnershipEvaluator.canExecute(auth, test.getCsiId())`, the method `CheckExecuteController` uses. No new role set, no new method, no Studio-local copy of the rule. A `null` CSI is refused. A unit test with a stubbed evaluator (`false` then `true`) proves the service delegates, so changing the evaluator changes Studio's answer.
4. **Authorization is decided first.** For a caller without execute rights: a test that is **not `READY`** answers `403`, not `409 COMPILE_REQUIRED`; a CSI whose pending quota is full answers `403`, not `429`; a replayed `Idempotency-Key` that an owner already used on that test answers `403`, never the owner's `executionId` and never `IDEMPOTENCY_KEY_REUSED`. A non-owner learns nothing about readiness, quota or other users' runs.
5. **The idempotency and race path cannot bypass the check.** The check runs once, at the top of `executeTest`, before `acceptanceService.accept` and therefore before the `catch (IdempotencyRaceException)` branch that calls `resolveIdempotencyRace`. Tests: (a) for an unauthorized caller neither `accept` nor `resolveIdempotencyRace` is invoked (spy or mock on `StudioAcceptanceService`); (b) a principal who was an owner, accepted a run with key K, and was then demoted, replays K and gets `403`, not the stored execution; (c) the existing concurrent-execute race test (`StudioIdempotencyIT`, two instances, one key) stays green for an owner. The check is **not** placed inside `StudioAcceptanceService.accept`/`acceptCore`, because `acceptCore` is shared with the scheduled path (AC-7).
6. **Red first, mutation proven.** The new and inverted tests are run against unmodified `HEAD` and shown red (the inverted `StudioAuthorizationIT` test fails with `202` where `403` is asserted), then green after the fix. Then one temporary mutation, removing the `canExecute` guard from `executeTest`, is applied and the named tests of AC-1, 3, 4 and 5 are shown red; the source is restored and proven byte-identical by `shasum -a 256` before and after. Output quoted in the Dev Agent Record. A criterion with no test that goes red under this mutation is not met.
7. **Scheduled runs follow STUDIO-SCHED-001, unchanged and pinned.** Citations (`docs/stories/STUDIO-SCHED-001/spec/spec.md`): FR-02 (schedule create/read/update/pause/resume/remove use "CSI read/write authorization, nondisclosing resource denial"); FR-04 ("reuse Studio readiness … authorization … checks"); FR-11 ("Use an approved CSI/environment background service principal or platform-approved renewable delegation with a separately recorded human activator. Verify current execution/secret grants at activation, acceptance and pre-send; … fails closed"); §"Background authorization" ("Unattended grants are independent of authenticated manual execution and of secret-use grants", also the javadoc of `StudioBackgroundAuthorization`). Decisions for this story, each backed by a test:
   - a. **Schedule create, update, pause, resume and remove still require `canWrite` on the CSI** (`StudioScheduleService.authorized(..., write=true)`). No execute check is added to them, because the spec does not ask for one and `canExecute` is `canWrite` today. A test asserts `canExecute == canWrite` across the evaluator's role matrix (admin, owner, contributor, viewer, none), so a future divergence fails here and forces the question in Open question 2. If `StudioScheduleApiIT` already refuses a viewer and a contributor on create and on enable, cite it; otherwise add those two cases. *(@po, validation: a grep of `StudioScheduleApiIT` for `viewer`, `contributor` and `403` found none, so expect to add them.)*

A test shows a scheduled occurrence for a schedule whose `execution_principal` has the background grant is still `ACCEPTED` with no request `Authentication` present, i.e. the new manual guard is not on the scheduled path.

## Dev Notes

- **Placement is the whole design.** Put the guard in `StudioService.executeTest`, the non-transactional wrapper, as the pre-`554277fcb` code did (right after `findById`). `StudioAcceptanceService.accept` and `acceptScheduled` share `acceptCore`; a guard there would need an `Authentication` the scheduler does not have and would break unattended runs.
- **403 for everything.** `findById(...).orElseThrow(StudioAccessDeniedException::new)` already yields the same exception for unknown, deleted and quarantined drafts. Reuse it; do not add a new exception or a message that includes ids.
- **Why this matters beyond runner capacity.** A confirmed test can type the CSI's vault secrets into origins the Vault entry allows (`SECRET_ORIGIN_NOT_ALLOWED` check, 10.44); secret-use authorization is separate and stays (`openapi.yaml` text), but it does not stop a stranger from triggering the run.
- **Test helpers.** `StudioExecutionFixtures.identity(...)` builds identities; `StudioAuthorizationIT` already has `owner()`, `reader()`, `contributor()`, `stranger()` and HTTP `post(...)`. Admin identity: look at how other ITs build `checks-admin`.
- **Digest discipline.** Same as 10.47: temporary mutation, `shasum -a 256` before and after. Run the runner `confinement.test.ts` with only the document edited first (expect the pin alone red), then re-anchor. Two concurrent Gradle runs in this worktree share `backend/build`.
- **Name collision to avoid confusing readers.** `docs/specs/studio/secrets-disclaimer/spec.md:442` also cites "ADR-002 O-22", for a different question (accepting the previous disclaimer version after a copy bump). This story's O-22 is the one in §35.4 and the §13 row of 2026-10-07. The ADR row should say "execute check" explicitly.

### Findings for @qa / @architect (not fixed: outside AC-12)

1. **`IdempotencyFilter` replays a cached response before the controller.** It caches 2xx/5xx responses in memory keyed on `X-User-Id + Idempotency-Key` for all `/api/v1/studio/**` POSTs. So over HTTP, a demoted owner replaying their own key within the cache window receives the cached `202` and never reaches `requireExecute`. AC-5b is therefore asserted on `StudioService.executeTest` (where the AC places the check), and the test javadoc records why. Different principals never share a cache key, so AC-1/AC-4 hold over HTTP (measured).
2. **`listsAreScopedBeforePaging…` depends on accumulated rows.** It assumes `CSI_ID`'s readable executions fit one page of 20. It passes with the guard; any future test that accepts more runs on `CSI_ID` in this class can tip it.
3. **Frontend test hygiene:** `apiClient` retries failed GETs with backoff, so a 5xx fixture can leak a retried request into the next test's window. The capability-count test uses its own test id for that reason (first full-suite run under Gradle load counted 2 reads).
