# Story 9.5 — Map & Import DC Sample Data (Checks & Reports) for Testing

| Field | Value |
|---|---|
| **Depends on** | **LOB backend story** (first-class LOB model + APIs). Until that lands, this story uses **mocked LOB endpoints**. |

---

## User Story

**As a** Checks developer / QA,
**I want** a small DC sample of Checks and Reports **configuration** mapped and imported into PUT Checks for test purposes,
**so that** we validate the model mapping, exercise import into our schema/APIs, and see how that sample looks and behaves in the UI (including LOB via mocks until the real LOB backend exists).

---

## Problem Statement

We received a **simple sample dataset from DC** (not a production extract). It contains **configuration data only** for Checks and Reports (definitions, schedules, recipients, associations, etc.) — **no history / execution / run results**.

DC and PUT Checks use **different data models**, so the work is to map fields/concepts and import the sample into Checks for testing.

This is **not a real migration**: no production cutover, no DC decommission, no full-fleet import. The sample is for learning the mapping, proving an import path, and checking UI fit with realistic-enough test data.

LOB does not exist yet in Checks. Story **9.1** assumes LOB as a group of CSIs. This story **depends on a LOB backend story** for the real model; until then it provides **mocked LOB endpoints** so the sample can be grouped and the UI exercised.

---

## Goals

| Goal | Outcome |
|---|---|
| **Model mapping** | Documented DC sample → Checks mapping for Checks and Reports (gaps called out). |
| **Import** | Repeatable import of the sample into a non-prod / local Checks environment. |
| **Sample shape** | Brief characterization of the sample (counts, LOB/CSI spread) so UI expectations are clear. |
| **UI check** | Spot-check that imported sample is usable in All Checks / Reports (and LOB+CSI filter when available). |
| **LOB bridge** | Mocked LOB endpoints for the sample until LOB backend story replaces them. |

---

## Dependency — LOB Backend Story

| Phase | LOB capability |
|---|---|
| **This story (interim)** | Mocked LOB list + LOB→CSI membership aligned to the sample, so import and UI can attach LOB. |
| **LOB backend story** | Real LOB APIs; sample import / fixtures switch from mock LOB IDs to real ones when ready. |

No production migration gate — only a clean swap path from mocks → real LOB for ongoing test data.

## Acceptance Criteria

### A — Mapping (different data models)

- [ ] **AC-1:** Inventory of **configuration** entities/fields present in the **DC sample** for Checks and Reports (no history/execution fields expected).
- [ ] **AC-2:** Mapping doc: DC sample field → Checks field/API, with transforms, defaults, and **gap list** (unsupported → skip or stub for the sample).
- [ ] **AC-3:** Mapping reviewed with PO/tech for obvious semantic mismatches in the sample.

### B — Sample shape & UI check

- [ ] **AC-4:** Short note on sample volumetry (e.g. N checks, M reports, CSIs/LOBs represented) — enough to set UI expectations, not a production capacity study.
- [ ] **AC-5:** After import, sample checks and reports are visible and usable in the UI (lists + open detail/builder as applicable).
- [ ] **AC-6:** Any UI friction with this sample size is noted (optional follow-ups); no production-scale performance work required.

### C — Mocked LOB backend (interim)

- [ ] **AC-7:** Mocked backend endpoints for list LOBs and LOB→CSI membership covering the sample.
- [ ] **AC-8:** Mocks are non-production (`local` / test profile or flag) and documented for replacement by LOB backend story.
- [ ] **AC-9:** Imported sample can associate with mock LOB IDs (LOB = group of CSIs per Story 9.1).

### D — Import path (test only)

- [ ] **AC-10:** Import path loads DC sample **Checks** into Checks using the mapping; failures report source id + reason.
- [ ] **AC-11:** Import path loads DC sample **Reports** into Checks (respecting check dependency order where needed).
- [ ] **AC-12:** Re-run strategy documented for local/test (e.g. wipe sample seed ids or upsert by source key).
- [ ] **AC-13:** Post-import smoke: counts match sample expectations; spot-check a few records in UI.

### E — Quality

- [ ] **AC-14:** Brief runbook: where the sample lives, how to map/import, how mocks work.
- [ ] **AC-15:** Tests for mapping transforms and/or mock LOB endpoints; at least one happy-path import (or fixture) test.

---

## Scope

- Map and import the **DC sample configuration** (Checks + Reports definitions) into PUT Checks for **test purposes**.
- Characterize sample size/shape lightly; confirm UI can show the imported data.
- Mocked LOB APIs for the sample until LOB backend story lands.

### Out of scope

- **History / execution / run results** (not in the sample; do not invent or backfill).
- **Real / production migration** from DC to Checks.
- Production cutover or DC decommission.
- Implementing the **real** LOB backend (LOB backend story).
- Production volumetry / capacity planning.
- Perfect parity for every DC concept not present in the sample or in Checks.
