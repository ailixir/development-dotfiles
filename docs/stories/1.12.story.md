## User Story

**As a** put-checks user clicking "Run Now" on a check,
**I want** `POST /checks/{id}/execute` to return `202 Accepted` immediately with an execution ID I can poll,
**so that** the UI stays responsive for slow check types (Splunk queries can take 60s) and the browser isn't blocked on a synchronous request.

---

## Acceptance Criteria

- [ ] **AC-1:** `POST /api/v1/checks/{id}/execute` returns HTTP 202 + `Location: /api/v1/checks/{id}/executions/{execId}` + body `{"executionId":"<uuid>","status":"PENDING"}` within 50ms P95.
- [ ] **AC-2:** The async work runs on the `checkExecutor` bean from story 1.8 (virtual-thread executor, semaphore-bounded). Dispatch via `@Async("checkExecutor")`.
- [ ] **AC-3:** The async flow: dispatcher.dispatch(check) → executor.execute → `ExecutionPersistenceService.persistResult` (story 1.11) → no return to the HTTP thread (already responded 202).
- [ ] **AC-4:** `@PreAuthorize("@csiOwnershipEvaluator.canExecute(authentication, #checkId)")` on the endpoint.
- [ ] **AC-5:** An execution row is created **upfront** with `status=PENDING` + the assigned executionId so clients polling immediately see PENDING rather than 404. Updated to SUCCESS/FAILURE/WARNING/TIMEOUT when the async task completes.
- [ ] **AC-6:** If the semaphore is saturated (all checkExecutor permits in use), the request fails-fast with HTTP 503 + `Retry-After: 2` — does NOT queue unboundedly. AC tested by setting test-scoped multiplier to `1` and submitting N+1 concurrent executes.
- [ ] **AC-7:** Execution metadata logged at dispatch: `traceId`, `userId`, `checkId`, `executionId`, `checkType`. Same fields present in downstream persist log.
- [ ] **AC-8:** Metric `checks_execute_requests_total{outcome=accepted|semaphore_rejected|authz_denied}` (counter).
- [ ] **AC-9:** Integration tests: `ExecuteHappyPathIT` (202 returned fast, row created PENDING, later SUCCESS), `ExecuteSaturatedIT` (semaphore exhaustion → 503), `ExecuteAuthzIT`, `ExecutePollingIT` (client polls /executions/{execId} sees PENDING → SUCCESS).
- [ ] **AC-10:** JaCoCo coverage ≥ 80%.

## Implementation Notes

- **Upfront PENDING row:** generate `executionId = UUID.randomUUID()`, INSERT a row with `status=PENDING, started_at=NOW()` before dispatching @Async. Gives clients a stable URL to poll. On async completion, UPDATE the row rather than INSERT a new one.
- **Semaphore 503:** catch `RejectedExecutionException` at the controller; map to `ResponseStatusException(SERVICE_UNAVAILABLE)`. `Retry-After: 2` is a polite hint — real backpressure comes from KEDA autoscaling (6.4).
- **No bulk execute in this story:** 1.14 is bulk-delete only for M1. Bulk execute can reuse this endpoint via N parallel calls from a bulk op; do NOT add a bulk-execute path here.

## @po Validation — 2026-04-17 · **10/10 GO**

Upfront PENDING row is the right design — avoids the race where a client polls the Location URL before the async task has inserted anything. AC-6 (semaphore saturation → 503) protects the system from unbounded queue growth; tested with a test-scoped config override, which is both realistic and repeatable.
