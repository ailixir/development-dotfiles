## User Story

**As a** developer maintaining the PUT Checks backend,
**I want** four technical debt items resolved — SectionResolver memory bounds, DST-safe scheduling, Spring-managed ObjectMapper injection, and automated materialized view refresh,
**so that** the processing layer is robust under edge cases and consistent in its use of framework facilities.

---

## Acceptance Criteria

### A — SectionResolver pagination (M1)

- [x] **AC-1:** `SectionResolver.resolve(RuleSection)` uses paginated queries instead of fetching up to 2000 checks.
- [x] **AC-2:** Page size configurable via `checks.reports.section-resolver-page-size` (default 200).
- [x] **AC-3:** Results accumulated in streaming fashion; total capped at `RuleConfig.limit` (default 100).
- [x] **AC-4:** `SectionResolverPaginationIT`: create 250 checks matching rule criteria, verify resolver returns exactly `limit` results without loading all 250 into memory.

### B — DST boundary tests (M3)

- [x] **AC-5:** `DstBoundaryTest`: unit test that exercises `CronExpression.next()` across US Eastern DST transition dates (March spring-forward, November fall-back).
- [x] **AC-6:** Verify that spring-forward (2:00 AM → 3:00 AM) doesn't skip a scheduled execution.
- [x] **AC-7:** Verify that fall-back (2:00 AM → 1:00 AM) doesn't produce a duplicate execution.
- [x] **AC-8:** Document any known Spring CronExpression DST limitations as a comment in `CronDispatcher.advanceNextExecution()`.

### C — Spring-managed ObjectMapper (M8)

- [x] **AC-9:** `ReportDeliveryDispatcher` injects Spring's `ObjectMapper` bean instead of using `private static final ObjectMapper MAPPER = new ObjectMapper()`.
- [x] **AC-10:** Verify existing `ReportDeliveryDispatcherIT` still passes (no behavior change).

### D — Automated materialized view refresh (M4)

- [x] **AC-11:** New `@Scheduled` method in an appropriate bean refreshes `csi_metrics_current` materialized view.
- [x] **AC-12:** Schedule: every 5 minutes (`@Scheduled(fixedRate=300000)`).
- [x] **AC-13:** Uses `REFRESH MATERIALIZED VIEW CONCURRENTLY csi_metrics_current` (non-blocking, requires unique index — verify exists).
- [x] **AC-14:** `@SchedulerLock(name="csiMetricsRefresh", lockAtMostFor="2m", lockAtLeastFor="30s")` — only one instance refreshes.
- [x] **AC-15:** `MaterializedViewRefreshIT`: verify view data updates after new execution results inserted.

### E — Coverage

- [x] **AC-16:** JaCoCo coverage >= 80%.

## Implementation Notes

- **SectionResolver pagination:** Replace `checkRepository.findAll()` with `checkRepository.findAll(spec, PageRequest.of(page, pageSize))` in a loop. Accumulate results until `limit` reached or no more pages.
- **DST test dates:**
  - US Eastern spring-forward 2026: March 8, 2026 (2:00 AM → 3:00 AM)
  - US Eastern fall-back 2026: November 1, 2026 (2:00 AM → 1:00 AM)
  - Use `ZoneId.of("America/New_York")` and fixed `ZonedDateTime` for deterministic tests.
- **ObjectMapper fix:** Simply add `ObjectMapper` to the constructor parameters and remove the static field. Spring auto-configures a global `ObjectMapper` with all registered modules.
- **Materialized view refresh:** The `CONCURRENTLY` option requires a UNIQUE index on the view. Check V1__init.sql for `CREATE UNIQUE INDEX ON csi_metrics_current(...)`. If missing, the migration needs one.
