## User Story

**As the** put-checks scheduling pipeline handling 1,500 executions/minute at peak,
**I want** execution concurrency to be configured independently from the database connection pool, with per-source caps that prevent slow integrations from consuming all execution slots,
**so that** the system can run 250 concurrent external I/O calls without requiring 250 database connections, and HTTP/TCP checks are never starved by slow Splunk or Grafana API calls.

---

## Problem Statement

The current `SemaphoreBoundedExecutor` in `AsyncConfig` derives its permit count from `checks.executor.semaphore-multiplier × spring.datasource.hikari.maximum-pool-size`. This couples external I/O concurrency (HTTP calls, TCP probes) with database connection pool sizing. To reach the capacity target of 250 concurrent execution slots, Hikari would need 63 connections — but the actual DB write rate (50 inserts/sec at peak) only needs ~30 connections.

Additionally, there are zero per-source concurrency limits. All 7 check types share the same semaphore pool. A slow integration source (e.g., Splunk API at 30s/call) can consume all permits, blocking fast HTTP checks (200ms/call).

### Current defaults vs. capacity targets

| Metric | Current | Target | Gap |
|---|---|---|---|
| Execution slots | 40 (4 × Hikari 10) | 250 | 6.25× short |
| Per-source isolation | None | HTTP/TCP: 150, integration: 75, reserve: 25 | Missing |
| Hikari pool | 10 (Spring default) | 20-30 | Config change |

## Acceptance Criteria

### Decoupled concurrency
- [ ] **AC-1:** New config property `checks.executor.max-concurrency` (int, default 250) controls the `checkExecutor` semaphore independently from Hikari pool size.
- [ ] **AC-2:** `AsyncConfig.checkExecutor()` uses `max-concurrency` directly instead of `semaphore-multiplier × hikariMax`. The old `semaphore-multiplier` property is removed.
- [ ] **AC-3:** `applicationTaskExecutor` retains its existing Hikari-coupled semaphore (no change — it's for DB-heavy async work).
- [ ] **AC-4:** Default Hikari pool size explicitly set to 30 in `application.yml` (not left to Spring's default of 10).

### Per-source concurrency caps
- [ ] **AC-5:** New configuration record `SourceConcurrencyProperties` with per-`CheckType` permit limits. Default: `HTTP: 150, TCP: 150, SPLUNK: 75, GRAFANA: 75, ITRS: 75, APPDYNAMICS: 75, UI_TEST: 25`.
- [ ] **AC-6:** `CheckExecutorDispatcher` acquires a per-source semaphore permit before delegating to the executor. The permit is released in a `finally` block after `execute()` returns.
- [ ] **AC-7:** If a per-source semaphore has no available permits, the dispatch logs a warning with `source_throttled type={type} available=0` and returns an `ExecutionOutcome.Failure` with message "Execution throttled: {type} concurrency limit reached" — it does NOT block.
- [ ] **AC-8:** Gauge `checks.executor.source_permits_available` (tag: `check_type`) exposes per-source available permits.

### Config validation
- [ ] **AC-9:** `SourceConcurrencyProperties` validates that the sum of per-source limits does not exceed `max-concurrency`. If it does, a `BeanCreationException` is thrown at startup with a clear message.
- [ ] **AC-10:** `max-concurrency` must be >= 1. Validated at startup.

### Existing behavior preserved
- [ ] **AC-11:** `SemaphoreBoundedExecutor.availablePermits()` still works and is used in health/metrics.
- [ ] **AC-12:** MDC propagation via `MdcTaskDecorator` is unchanged.

### Tests
- [ ] **AC-13:** `ExecutorConcurrencyIT`: verify `checkExecutor` semaphore has exactly `max-concurrency` permits (not Hikari-derived).
- [ ] **AC-14:** `SourceConcurrencyCapIT`: submit `max + 1` tasks for a single source → verify the extra dispatch returns throttled failure, not a block.
- [ ] **AC-15:** `SourceConcurrencyConfigValidationTest`: sum > max-concurrency → startup fails with clear error.
- [ ] **AC-16:** `SemaphoreBoundIT` (existing): verify still passes with new config shape.
- [ ] **AC-17:** JaCoCo coverage ≥ 80% for modified classes.

## Implementation Notes

- `SemaphoreBoundedExecutor` itself is unchanged — only how its permit count is derived changes.
- Per-source semaphores live in `CheckExecutorDispatcher`, not in the executor implementations. Executors remain pure (no concurrency awareness).
- `tryAcquire()` (non-blocking) is preferred over `acquire()` (blocking) for per-source caps — a throttled execution should fail fast, not queue.
- The global `checkExecutor` semaphore still exists as a hard ceiling. Per-source semaphores are a secondary gate: a task must pass both the global semaphore (in `SemaphoreBoundedExecutor`) and the per-source semaphore (in `CheckExecutorDispatcher`).
