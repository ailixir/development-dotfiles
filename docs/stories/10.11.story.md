## User Story

**As a** CSI-authorized support engineer who has just confirmed an exact revision and now wants to
watch it run,

**I want** the Run control to be governed by the server's readiness and nothing else, the run's
progress to reach my screen as it happens rather than by my browser asking eleven hundred times,
and every refusal and every terminal error to tell me plainly what happened to the browser and who
can fix it,

**so that** I am never told a test is runnable when the server would refuse it, never shown a
stale picture of a live run, and never left guessing whether a failed dispatch means I can press
Run again.

## Problem Statement

Everything this story consumes is merged. `GET /api/v1/studio/executions/{id}/events` serves
`text/event-stream` from `SseEmitter`, authorized against the execution's immutable CSI, with
per-pod batched reads, heartbeats, a bounded lifetime and `X-Accel-Buffering: no` (10.7c;
`backend/src/main/java/com/citi/put/checks/studio/sse/`). The snapshot DTO is identical on both
transports. `READY` is producible (10.10). **Nothing in the browser uses any of it.**

Five facts verified on this branch at `52af70c93`, each of which is a defect this story owns:

1. **The Run gate is the retired legacy path.** `ChecksStudioPage.tsx:271` refuses to run unless
   `validation.isValid`, and line 788 disables the button on the same predicate. That is
   client-side English-grammar validation — the authority architecture §8.3 retires by name
   (*"Remove client grammar validation and Python generation as authoritative paths"*). Nothing
   anywhere in the page reads `compileStatus`. A draft that the server would refuse with
   `409 COMPILE_REQUIRED` has an enabled Run button today, and a confirmed `READY` draft whose
   English the client dislikes has a disabled one.

2. **The Code view shows the user code the server never produced and never will run.**
   `CodeTab.tsx` is titled *"Generated Python (Playwright)"* and renders the output of
   `@/utils/studio/codegen/pythonGenerator`, regenerated client-side on every step change
   (`ChecksStudioPage.tsx:101,104` and the auto-sync effect at 320-366). PRD §5.3 retires Python
   export from the Studio plan; §4.4 makes the server's artifact the only executable truth. The
   page currently invites a user to review one language and run another.

3. **Progress is a 700 ms `setInterval`** (`ChecksStudioPage.tsx:282-312`), which the SSE
   assessment records as the thing SSE replaces, and which swallows every error into
   `catch { stop }` — a 401 and a dropped Wi-Fi connection are the same event to it.

4. **`errorCode` is rendered nowhere.** It exists in the type, in ten fixtures and in one contract
   assertion; `grep -rn errorCode frontend/src` returns thirteen lines and not one is a render.
   So a terminal `ERROR` currently reaches the user as the word "ERROR". That is also **why**
   ADR-002 §15.5 could record the frontend union's drift as having no runtime effect — and it is
   why this story is O-12's owner: it is the first story to consume the field.

5. **The union is two values short and cannot be asserted as written.**
   `studioTypes.ts:15-21` declares six members; the document declares eight plus null
   (ADR-002 §15). ADR-002 §18.3 is explicit about the remedy and about the wrong one:
   *"Hand-widening it now would be the worst available move: it would spend the edit and leave the
   mechanism that let it drift in place. … it must **generate the union from this document or
   assert it against this document**."* A TypeScript union is erased at run time, which is exactly
   why nothing noticed — so "assert it" requires a runtime carrier to assert *over*. AC-5 is that.

And one fact about the transport that the rest of this story is written to respect. The SSE
viability note is unusually candid and its candour is load-bearing:

> *"Assessment performed: repository inspection and primary documentation verification. **No SSE
> implementation, runtime spike, or staging test was performed during this review.**"*

Production runs **three API replicas scaling to six** (`values-prod.yaml:2,25-26`, verified). The
MFE and the API are on **different hosts** — `checks.citi.com` and `checks-api.citi.com`, verified
in the same file — so "same-origin" is not what the chart does. The ingress is `nginx` class with
rate-limit annotations and **no streaming settings at all**. `getAuthToken()` returns `null`, so
today the only credential the app attaches is the ambient cookie behind `withCredentials: true`.
Native `EventSource` inherits none of Axios's interceptors regardless. **SPK-02 is OPEN and its
`Shapes` line rules this story's response in advance:** *"if the spike is still open when 10.11 is
drafted, 10.11 builds the transport abstraction plus `EventSource` and the GET fallback, and
defers the header client."* That is what the criteria below do, and it is why several of them are
blocked rather than optimistic.

## Size call — the manifest's `L` verified, and what would break it

The manifest records `size: L` with **SIZE-1 / UNVERIFIED**: estimated before ADR-002, not
re-estimated, because @po declined to invent a number for an undrafted story. Six consecutive
stories moved M → L at validation, every one citing a ruling that landed after the estimate. The
instruction was to size honestly against the criteria actually needed and not to compress criteria
to defend the letter. Doing that:

**It is an L, at the top of the band.**

What makes it a full L rather than a comfortable one:

- **Two legacy retirements that delete code the page currently depends on**, one for its Run gate
  and one for its Code tab. Neither is a deletion in isolation: removing the grammar gate without
  the readiness gate ships an ungated Run, and removing the Python generator without a source to
  put in its place makes the Code tab empty rather than honest.
- **A test capability this repository does not have.** jsdom provides no `EventSource`, and a
  component test that hands the renderer a parsed snapshot proves nothing about streaming — the
  viability note says so in as many words. AC-9 requires a real socket, a real chunked
  `text/event-stream`, and a second frame written *after* the first is observed. That is a new
  harness, in a `node`-environment test file, next to a suite that has only ever run in jsdom.
- **O-12 changes how a frozen mirror file declares a type**, not just its contents: a runtime
  constant with the union derived from it, plus a type-level guard so the type cannot drift back.
- **Four externally gated halves** and two rulings in flight, one of which (AC-15) owns the Code
  view this story's own epic line assigns it.

What keeps it inside L: the backend is merged and needs nothing; the snapshot rendering already
exists and the viability note explicitly plans to *"reuse the snapshot rendering logic behind a
transport abstraction"*; and the comparable is 10.10 — frontend-only, 23 criteria, L — plus a
transport layer. It is materially smaller than 10.7 (L, 47 criteria, split mandated).

**What would move it past L, named so it is visible rather than discovered:** if @architect's
**AC-15** ruling lands during this wave, AC-3(b) unblocks and the Code view stops being an honest
unavailable state and becomes a real rendering of a whole artifact and its source — with its own
truncation, accessibility and no-fabrication obligations, which is most of 10.10's half (ii)
arriving inside a transport story. **That is the point at which the split hint stops being a
contingency and becomes the plan**, and 10.11a/10.11b are each an M.

## Acceptance Criteria

Every criterion is falsifiable and cites its source. Criteria split `a`/`b` follow the epic
convention established by 10.3 and reused by 10.6, 10.7, 10.10, 10.13 and 10.17: the `a` part is
verifiable now; the `b` part names its **owner and its gate** and is recorded **skipped, never
passed** — never quietly marked done. Every `b` part below names the artefact whose existence
closes it, so that **a skip cannot turn green without its gate moving**.

### The run gate, and the two authorities it retires

- [ ] **AC-1:** **Run is enabled if and only if the server says the draft is ready, and the mapping
  over the states is total with no fallback branch.** The predicate is `compileStatus === 'READY'`,
  read from a `GET /tests/{id}` body. Epic §10.11: *"Disable Run until READY"*; §4.6 puts readiness
  on the server; 10.8 AC-26 makes the server-side gate unconditional. The test **reads the five
  states from the document** (`openapi.yaml` → `components.schemas.TestDto.properties.compileStatus.enum`)
  through the binding 10.10 already installed, enumerates them, and asserts Run is enabled in
  **exactly one**. No `default:` branch and no `??` fallback: a sixth value must be a loud error,
  not a permissive one. *Anti-vacuous:* falsified by (a) adding a sixth member to an in-test copy
  of the document → the enumeration goes red because the sixth renders nothing; (b) changing the
  predicate to include `AWAITING_CONFIRMATION` → red. Both recorded.

- [ ] **AC-2:** **Client-side English-grammar validation is no longer an execution gate anywhere,
  and this is proven behaviourally, not by grep.** Architecture §8.3: *"Remove client grammar
  validation and Python generation as authoritative paths."* Two tests, both asserting on
  **requests observed at the mock server**, because a source scan for `validation.isValid` is the
  epic's sixth vacuity precedent (a guard that greps source text) and cannot see a gate
  reconstructed through a differently-named local:
  - with the client validator forced to report **invalid** and `compileStatus: READY`, activating
    Run produces **exactly one** `POST /tests/{id}/execute`;
  - with the client validator forced to report **valid** and `compileStatus` anything but `READY`,
    activating Run produces **zero**.
  A source scan may supplement and may not replace. **The two halves are not equally strong and the
  criterion says so:** the first is the discriminating one, because it can only pass if the grammar
  term is genuinely gone; the second would also be satisfied by a control that is merely disabled,
  which AC-1 already proves, so it is the companion and not the guard. *Anti-vacuous:* falsified by
  restoring the `validation.isValid` term to the enablement predicate → the **first** test red.

- [ ] **AC-3(a):** **Client-generated Python is retired as an authoritative path, and the Code view
  says what it does not have rather than showing something else.** PRD §5.3 (*"Python export is
  retired from the Studio plan"*), architecture §8.3, epic §10.11 (*"retire Python generation"*).
  With AC-3(b) blocked, the Code view renders an **explicit unavailable state naming the blocker**
  — the same shape 10.10's AC-16(a) landed for the summary slot, and for the same reason: a
  fabricated rendering of "the code that will run" is worse than an absent one, because it is the
  precise confusion the confirmation step exists to prevent. Assertions: (i) for every fixture the
  Code view renders **no** generator-derived text; (ii) editing a step produces **no** regenerated
  code (the auto-sync effect is gone, observed by rendering, not by reading the effect);
  (iii) no module on the Run or Code-view path imports `@/utils/studio/codegen/pythonGenerator` or
  `@/utils/studio/ir/parseSteps` — a supplement to (i), explicitly named as the weaker half.
  *Anti-vacuous:* falsified by wiring the generator's output back into the Code view → (i) red.
  **The generator module is not deleted by this story** — it still has non-Studio callers until
  someone checks, and a deletion sweep inside a transport story is scope creep; it is retired *as
  an authority*, which is what the epic line says.

- [ ] **AC-3(b):** *(skipped, never passed)* *(**Blocked** on the **AC-15 Class C ruling** — story
  10.10, @architect, in flight. Owner: this story once the document is amended.)* **The Code view
  renders the confirmed revision's source.** Epic §10.11: *"Code view renders the confirmed
  source."* **Verified, not assumed:** `TestDto` declares `confirmedRevisionId` and
  `currentCandidateRevisionId` and carries **no** artifact, **no** source and **no** `artifactHash`;
  nothing in any `tests`-tagged `2xx` response does. 10.10's AC-15 filed two candidate shapes and
  **candidate B's "For" column names this story**: *"10.11's Code view will want the **confirmed**
  revision, not the candidate."* That distinction matters and is recorded here rather than
  assumed: candidate A as filed exposes the **candidate's** hash and source on `TestDto`, which
  satisfies 10.10 and **may not** satisfy this criterion, since a `READY` draft's confirmed
  revision and its current candidate are the same object only until the draft is edited again.
  **This story proposes nothing and amends nothing.** The gate is an ADR-002 amendment with a §13
  log line that makes the confirmed revision's source reachable from a declared `2xx` response;
  a green here without that entry is a defect.

- [ ] **AC-4:** **Every refusal `POST /tests/{id}/execute` declares is handled distinctly, the
  `409` code set is read from the document in both directions, and the branch is driven by the
  code rather than by the message.** The declared set is
  `x-conflict-codes: [COMPILE_REQUIRED, RUNTIME_INCOMPATIBLE, IDEMPOTENCY_KEY_REUSED, TEST_DELETED, TEST_QUARANTINED]`,
  read through the **existing** `assertSameSet` helper in `studioContract.test.ts` (ADR-002 §18.3:
  *"the other should extend it rather than write a second one"*), compared both ways: no declared
  code without wording, no wording without a declared code. Each narrative states **who clears it**,
  from the `tests` tag's own table — `TEST_QUARANTINED` in particular must say the authored test
  *still exists and returns*, never that it was deleted (BRD §9; ADR-002 §14.3).
  **`429` and `503` branch on the status, not on a code**, and the criterion says why: the `429`
  response declares no `x-conflict-codes` and no example, and the `503`'s `DISPATCH_DISABLED`
  reaches the document only as an *example*, which §14.6 establishes is not assertable. Switching
  on an undeclared code would be hand-widening a vocabulary — the exact manoeuvre §18.3 forbids one
  paragraph away. `503` renders as a platform-wide condition (a banner, per ADR-002 §15.3's
  *"blast radius"* reading), `429` as a retry-later quota condition.
  *Anti-vacuous:* falsified by (a) deleting one entry from the UI map → red; (b) adding a sixth
  code to an in-test copy of the document → red; (c) a fixture whose `message` prose contradicts
  its `error` code, asserting the rendering follows the code → red if the branch reads the message.

### The terminal error vocabulary — ADR-002 O-12

- [ ] **AC-5:** **`ExecutionErrorCode` is asserted against the document, in both directions, and
  cannot be hand-widened.** ADR-002 §18.3 assigns O-12 here as *"a requirement rather than a
  note"*: *"generate the union from this document or assert it against this document."* Four
  obligations, and the first exists because the third is impossible without it:
  1. **A runtime carrier.** The union is derived from an exported runtime constant
     (`EXECUTION_ERROR_CODES`), not hand-written. §15.5 records that the drift *"is not a runtime
     failure — the field arrives as a JSON string and the union is erased"*; an erased type is a
     thing no test can read, so a document-reading assertion needs something that exists at run
     time to compare against.
  2. **The type is derived from the carrier**, so a hand-widened or hand-narrowed type is a
     `type-check` failure rather than a silent second copy. This is the mechanism §18.3 says must
     replace the hand-maintained one, not just its current contents.
  3. **The assertion reads `openapi.yaml`** — the non-null members of
     `components.schemas.ExecutionErrorCode.enum` — through the **same single parsed-document
     binding** 10.10 installed, and compares both ways with `assertSameSet`. **The expected value
     is never imported from `studioTypes.ts`**; an expected value imported from the module under
     test is one of the sixteen catalogued shapes, and it is the shape this criterion is most
     naturally written into.
  4. **Every member has a rendered narrative** and every narrative has a declared member (AC-6
     consumes them). A union asserted and unconsumed reproduces §15.5's own diagnosis — the drift
     was invisible *because nothing narrowed on it* — one layer up.
  *Anti-vacuous, and @qa's probe applied literally (the test's name refers to a production symbol,
  so the production symbol is what gets mutated):* falsified by (i) deleting `AUTHORIZATION_REVOKED`
  from `EXECUTION_ERROR_CODES` → the named test red; (ii) adding a ninth value the document does not
  declare → red; (iii) widening the exported **type** by hand while leaving the constant alone →
  `npm run type-check` non-zero; (iv) replacing the document read with an in-test literal of the
  eight values → a separate provenance guard red, because *"a pinned copy whose provenance nothing
  checks"* is a catalogued shape and this assertion is a pinned copy the moment it stops parsing
  the file. All four recorded.
  **Explicitly not this story's:** the three further assertions ADR-002 §15.8 item 2 offers — the
  keys of `x-assigned-by` against the enum, no assigner being the runner, and the
  `x-runner-error-codes ∩ enum = {TIMEOUT}` intersection. Those live beside the Java escalation
  class §15.8 addresses and are named here so this story does not absorb them by proximity.

- [ ] **AC-6:** **A terminal `ERROR` tells the user what happened to the browser and who can clear
  it, and `DISPATCH_UNKNOWN` does not offer a retry.** The document's own `ExecutionErrorCode`
  table fixes both facts per code and nothing here is invented. One test per code, asserting the
  rendered text carries the browser claim and the remedy owner. The load-bearing case:
  `DISPATCH_UNKNOWN` means *"unknown; a caller must assume neither"*, and §5.1 *"forbids resending
  browser work on an ambiguous outcome, so a new run is an explicit human decision"* — so the
  surface offers **no** one-click re-run for it, while `DISPATCH_FAILED`, `START_TIMEOUT` and
  `STALE` (all *"a new execution"*) do. Two further assertions, because §8.2 makes the mistake easy:
  `errorCode: null` on a non-`ERROR` status renders no error region at all, and a **step**
  locator/assertion timeout renders as a step `FAIL` with execution `FAILED` and **no code** —
  never as `TIMEOUT`. *Anti-vacuous:* falsified by offering a retry on `DISPATCH_UNKNOWN` → red;
  and by rendering a code on a `PASSED` snapshot → red.

### The transport

- [ ] **AC-7:** **All execution progress reaches the screen through one named transport
  abstraction owned by the API service layer, and the component opens no connection of its own.**
  SSE assessment: *"Put subscription creation/cleanup and authentication handling in the API
  service layer; the component should not create unmanaged network connections."* Proven
  behaviourally rather than by import scan: with the abstraction substituted at its seam by an
  implementation that **emits nothing**, the surface shows **no** progress for the duration of a
  run and **zero** execution requests are observed at the mock server. If the component held a
  second source — a surviving interval, a direct `fetch`, an `apiClient` call — progress would
  still appear and that test would be green, which is what makes the substitution discriminating
  rather than decorative. *Anti-vacuous:* falsified by restoring any direct execution read inside
  the component → red.

- [ ] **AC-8:** **The 700 ms polling loop is gone as the primary path.** Verified present at
  `ChecksStudioPage.tsx:282-312`. With the streaming transport healthy for a full run,
  **zero** `GET /executions/{id}` requests are observed at the mock server — asserted on observed
  requests, not on the absence of a timer, because a timer can be renamed and a request cannot be
  disguised. *Anti-vacuous:* falsified by leaving the interval in place beside the subscription →
  red.

- [ ] **AC-9:** **Two snapshots reach the rendered surface as two separate updates, from a real
  socket, over a genuinely chunked `text/event-stream`, before the response closes.** This is the
  criterion the SSE assessment wrote in advance: *"two timed snapshots must reach the browser
  separately before response closure"*, and *"**a buffered mock-controller response does not prove
  SSE delivery**"* — the characteristic vacuous shape for this story, named so it cannot be
  reached by accident. The test's construction is normative, not incidental:
  - a real `node:http` server, a `@vitest-environment node` file, and **the production transport
    module** as the client — not a re-implementation of its parser;
  - the server writes frame 1; the test **waits until the client has surfaced frame 1**; only
    **then** writes frame 2; only then ends the response;
  - assertions: frame 1 is surfaced **while the response is still open** (asserted from the server
    side, on the response object's own not-finished state, not inferred from the client); frame 2
    is surfaced as a **second, distinct** update; and a guard asserts frame 2's write happened
    **after** frame 1's observation.
  That last guard is wave 5's standing rule — *make the mutation land inside the measurement
  window* — transposed exactly: a second frame written before the client connects is delivered to a
  fully buffering client too, and would turn the one real bug this criterion exists to catch into a
  silent pass.
  *Anti-vacuous, and this is the single most important falsification in the story:* replace the
  incremental reader with one that awaits the whole body before parsing → **red**. Recorded with
  the sibling green count.

- [ ] **AC-10:** **State is replaced by monotonic snapshot revision; older and duplicate revisions
  are ignored, and the fixture is sized so that failing to ignore them is visible.** §5.5: *"The
  MFE replaces current state, ignores older revisions."* The sequence is rev 5 → rev 7 → rev 6 →
  rev 7-again, and **rev 6 carries visibly different content** — a different current step and a
  different log tail — so that applying it changes the screen. A lower-revision frame identical to
  the current one would keep this test green with no guard present at all, which is the epic's
  *"a canary sized so it never reaches the hazard"*. Assertion: the rendered state after the whole
  sequence equals rev 7's, field by field on the surface, not on the store.
  *Anti-vacuous:* falsified by removing the revision comparison → red; and by flattening rev 6's
  content to match rev 7's → the test goes green with the guard removed, which is recorded as the
  **negative control** proving the fixture is doing the work.

- [ ] **AC-11:** **A reconnect restores current state and is labelled as transport, never as test
  failure; and a disconnect never cancels or re-executes.** Epic §10.11: *"label transport
  reconnecting separately from test failure"*; §5.5: *"V1 promises current-state recovery, not
  lossless event replay"* and *"never re-executes because a connection failed."* Four assertions:
  (i) on a dropped connection the surface shows a reconnecting state whose accessible name is
  distinct from every `ExecutionStatus` narrative; (ii) the rendered execution status is
  **unchanged** across the drop; (iii) on reconnect the full current snapshot replaces state — the
  client asserts nothing about replay and requests none; (iv) across a drop/reconnect cycle,
  **zero** additional `POST /tests/{id}/execute` requests are observed, and **zero** stop/cancel
  requests. *Anti-vacuous:* falsified by mapping the transport error onto the execution status →
  (i) and (ii) red.

- [ ] **AC-12:** **Bounded reconnect, then bounded GET fallback — and never around a `401`/`403`,
  including when the denial arrives mid-fallback.** §5.5 and the SSE assessment: *"bound reconnect
  attempts before falling back to polling. **Never fall back around a 401/403.**"* and *"use the
  normal GET endpoint to distinguish auth failure, terminal completion, and transient
  disconnection."* Four tests, and the fourth exists because of the epic's *"two guards each
  covering half a property"* shape:
  - a transient disconnect produces at most a **named bound** of reconnect attempts, then switches
    to bounded GET polling at a stated cadence with a stated total bound;
  - the probe that distinguishes the three cases is the **ordinary authorized GET client**, not a
    second HTTP path — asserted by the request the mock server observes;
  - a `401` (and separately a `403`) stops everything: the surface reports the access failure and
    **zero** further requests of any kind are observed after it;
  - **the combined case:** a transient failure engages the fallback, and the fallback's own GET
    then answers `401` — polling stops. A guard covering only the pre-fallback denial and a guard
    covering only the transient path leave exactly this branch uncovered, and it is the branch in
    which a client keeps hammering a route it has been told it may not read.
  *Anti-vacuous:* falsified by deleting the `401` branch → the third and fourth tests red, because
  requests continue past the denial. **`ED-02` note:** the client's rule is provable against any
  `401`; that a real `401` arrives from a real identity through a real gateway is `ED-02`/`ED-06`
  and is not claimed here.

- [ ] **AC-13:** **The stream closes on `streamComplete`, on unmount and on scenario switch — and a
  terminal outcome alone does not close it while evidence is still `PROCESSING`.** §5.5:
  *"Close explicitly on `streamComplete=true`, after evidence is settled"*; §6.1 keeps outcome and
  evidence separate; §5.4 row 5 settles evidence as failed/unavailable at the deadline and sets
  `streamComplete`. Assertions:
  - a snapshot with a terminal `status` + `video.status: PROCESSING` + `streamComplete: false`
    leaves the connection **open**; a later snapshot with the evidence settled and
    `streamComplete: true` is rendered **and then** the connection closes;
  - **evidence failure settles too** — a `video.status: FAILED` with `streamComplete: true` closes
    the stream and renders the evidence state honestly, without touching the check outcome;
  - **no subscription accumulates:** across at least three mount/unmount cycles **and** a scenario
    switch performed **while a stream is open**, the connection count observed at the server —
    opened minus closed — returns to zero. Counted at the server, never by asserting a cleanup
    callback was invoked.
  *Anti-vacuous:* falsified by (a) closing on terminal `status` → the first test red; (b) removing
  the unmount cleanup → the count test red; (c) removing the scenario-switch cleanup → the count
  test red **only because the switch happens mid-stream**, which is why that ordering is written
  into the criterion.

- [ ] **AC-14:** **No credential in the URL, and the subscription is not governed by the Axios

## Anti-vacuous test requirements

This section is normative, not advisory. The epic has catalogued **sixteen** shapes of guard that
cannot fail, every one of them green the whole time it was wrong. The shapes this story is most
exposed to, and the rule each produces:

| # | Shape | Why this story is exposed | The rule here |
|---|---|---|---|
| 1 | **A buffered response proving nothing about streaming** | Named by the SSE assessment as the characteristic failure for this work. A component test that hands the renderer a parsed snapshot satisfies every word of "shows progress" | AC-9: a real socket, a real chunked body, frame 2 written **after** frame 1 is observed, and the falsification is a buffering reader going red |
| 2 | **A canary sized so it never reaches the hazard** | The revision-ordering guard (AC-10) is green with no guard at all if the older frame's content matches the current one | AC-10's rev 6 carries visibly different content, and the flattened-content run is recorded as a **negative control** |
| 3 | **A mutation that lands outside the measurement window** | Wave 5's standing rule. A second SSE frame written before the client connects is delivered to a buffering client too | AC-9's ordering guard; AC-13's scenario switch performed **while a stream is open** |
| 4 | **A source-text scan standing alone** | Both retirements (AC-2, AC-3a) are naturally written as greps for `validation.isValid` and `pythonGenerator`, and a gate rebuilt through a differently-named local passes a grep | Both are asserted on **observed requests** or **rendered output**; the scan is named as the weaker supplement |
| 5 | **An expected value imported from the module under test** | AC-5 is the exact shape: the natural test compares `EXECUTION_ERROR_CODES` against a list, and the nearest list is in the same file | The expected set is parsed from `openapi.yaml`, and a separate **provenance** guard goes red if the read is replaced by a literal |
| 6 | **A pinned copy whose provenance nothing checks** | AC-21(b)'s three measured counts (25 / 16 / 12) are a pinned copy the moment they become expectations | They are recorded as **evidence**, never as assertions |
| 7 | **Two guards each covering half a property** | AC-12: a "stops on 401" test and a "falls back on transient" test leave the branch where the denial arrives **during** the fallback uncovered | The combined case is written into the criterion as its fourth test |
| 8 | **A guard whose name states a structural property of a production symbol while its body asserts over a test-local stand-in** | The sixteenth shape, catalogued by 10.17. AC-5 and AC-15(a) are both phrased as "exactly"/"is the only" | @qa's probe adopted literally: for any test named *enumerates*, *is the only*, *carries no* or *exactly one*, the mutation is applied to the **production symbol the name refers to** |
| 9 | **A guard satisfied by a broken implementation** | AC-7's abstraction test is green if the component keeps a second source, unless the substituted transport emits **nothing** | The substitution is an empty implementation, so a surviving second source makes progress appear and the test fail |

Three rules bind every criterion above:

- **Per-guard falsification is a deliverable** (AC-23), with the named red test, the sibling green
  count and a byte-identical restore verified by SHA-256.
- **A guard that cannot be made to fail is recorded as not-a-guard**, removed from the count, and
  named in the Dev Agent Record — not left in the suite as coverage.
- **A deferral is skipped, never passed**, and every deferral names the artefact that closes it.
  A skip that could turn green without its gate moving is itself a defect.

## Implementation Notes

### The transport is a seam, and the renderer must not know which one it has
The viability note's own design is *"Reuse the snapshot rendering logic behind a transport
abstraction."* Everything below the seam takes a snapshot and replaces state; everything above it
produces snapshots. The revision-ordering rule, the terminal/cleanup rule and the "never
re-execute" rule live **above** any single implementation — AC-16 exists to prove that, by running
the same rules against the fallback. An ordering rule implemented inside the `EventSource` handler
is a rule the fallback does not have.

### A clean bounded close is not an error
The server closes deliberately at its bounded lifetime (DA-3), and at the socket that is
indistinguishable from a drop. A client that treats it as an error will burn its reconnect budget
on normal operation and fall back to polling after a minute of healthy streaming. The distinction
the client **can** make is the one §5.5 prescribes: use the ordinary authorized GET to tell
terminal completion, denial and transient disconnection apart — and stop on denial.

### Why the union needs a runtime carrier
This is the whole of O-12 and it is easy to under-read. §18.3 asks for an assertion against the
document; §15.5 explains that the drift had no runtime effect *because the union is erased*. Those
two facts together mean there is nothing for an assertion to read unless the story creates one.
A `const` array with the type derived from it is the smallest change that makes both the assertion
and the type-level guard possible — and it is the change that removes the mechanism, not just the
symptom, which is what §18.3 asks for in the sentence about hand-widening being *"the worst
available move"*.

### The "no second parser" constraint is a review constraint, not a guard
Nothing in the suite can fail because someone added a second `parseYaml` of `openapi.yaml`.
It is recorded here, and in AC-21(a), as **not-a-guard** rather than counted as coverage, because
the alternative is a criterion that reads like an assertion and is not one — which is the shape
this epic has spent four QA rounds removing. The enforcement is review: AC-5 uses the existing
helper and the existing binding, and a reviewer checks that.

### Seams to watch
- **`ChecksStudioPage.tsx` is 1250 lines and is 10.16's next subject.** Keep the transport in the
  service layer and the new surfaces in composed children with narrow prop surfaces, so 10.16's
  playback work is not also a rewrite of this one. 10.10 kept its own footprint in this file to
  eight lines for exactly this reason.
- **`studioContract.test.ts` is a shared harness, not this story's file.** AC-4 and AC-5 add
  assertions beside the existing helpers and use them.
- **The generator and the grammar parser are retired, not deleted.** Check callers before anyone
  proposes the deletion; a sweep inside a transport story is how a wave-6 merge grows a wave-7
  conflict.
- **`executionPoller.ts` is not this story's.** It serves ordinary checks, not Studio. AC-8 removes
  the Studio page's own interval; it does not touch the checks poller.
- **No CodeRabbit section, and none in Epic 10.** Ruled once for the epic by @po on 2026-09-11:
  `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a Darwin host,
  the CLI is absent, and `graceful_degradation.skip_if_not_installed: true` applies.

## Split hint

**The seam is the transport boundary, and it is clean because §5.5 already designates the GET

**Five things must never be cut apart.**

1. **The revision-ordering rule (AC-10) and the transport that produces out-of-order frames
   (AC-9).** A "replace on higher revision" implemented against a source that never delivers a
   lower one is the epic's *canary sized so it never reaches the hazard*, and it is green forever.
2. **The `401`/`403` stop rule (AC-12) and the fallback it constrains.** A bounded GET fallback
   shipped without it is a client that routes around an access control the server just enforced.
   The SSE assessment says *"Never fall back around a 401/403"* in as many words, and the
   architecture repeats it.
3. **`streamComplete` closure and the evidence-still-`PROCESSING` case (AC-13).** Closing on a
   terminal outcome **is** the defect; the two halves are one property, and splitting them ships
   the defect with a green test beside it.
4. **The grammar-gate removal (AC-2) and the readiness gate (AC-1).** Removing the old gate first
   ships an ungated Run. Adding the new gate without removing the old leaves the retired authority
   still deciding — and the epic retires it by name.
5. **The O-12 union (AC-5) and the rendering that consumes it (AC-6).** ADR-002 §15.5's diagnosis
   is that the drift was invisible *because nothing narrowed on the union*. A union asserted and
   unconsumed reproduces that state one layer up, and would be the second time this exact mistake
   is made in this epic.

abstraction 10.11a deliberately does not build. **Each half is an M.** The trigger is named in

transition. **It needs both halves**, and if only 10.11a lands, 10.16's dependency is not
satisfied. Recorded here the way 10.10 recorded *"10.11 needs (ii), not (i)"*.

## Weakest criteria — named here rather than discovered at validation

@po does this at validation; doing it in the draft makes the validation sharper. In descending
order of how easily each could be satisfied without being true:

1. **AC-14(ii) — "the Axios timeout does not govern the stream".** The weakest concrete claim in
   the story. The criterion itself says the 30-second number is not exercised; a scaled idle
   interval proves the transport does not abort on *an* idle gap, and the gap that matters is the
   ingress's, which nobody has measured. It is written down rather than dropped because a
   subscription accidentally created through the shared client is a real and easy defect — but the
   part of it that reads like a guarantee about 30 seconds is not one.
2. **AC-17 — the mocked development scenario.** It is a fixture with a list of required frames, and
   nothing outside AC-22's matrix notices if the list shrinks. Its value is developer-facing and
   its failure mode is silent. AC-22 is the only thing holding it up, which makes AC-22 load-bearing
   for a criterion that looks like plumbing.
3. **AC-3(a) — the Code view's unavailable state.** 10.10's AC-16(a) had the same weakness and
   named it: *"Easy to satisfy vacuously by rendering nothing at all and calling it an unavailable
   state."* Here it is slightly worse, because the thing being removed (generated Python) is
   visible and its replacement is not, so "the tab is empty now" will read as done.
4. **AC-15(a) — "exactly one implementation of the auth seam".** A criterion phrased as a count is
   the sixteenth catalogued shape wearing a different hat. The falsification (add a second
   implementation → red) is what gives it teeth; without it, the export enumeration is blind to a
   module-local branch on an environment flag, which is exactly where a bearer path gets added
   under pressure when staging refuses cookies.
5. **AC-6 — the per-code narratives.** The facts are taken from the document's own table so the
   test can assert them, which keeps it from being "renders something". The residual softness is
   that a substring assertion passes on text that is technically present and practically
   unreadable — 10.10 named the same residue on its AC-2 and it has not moved.
6. **AC-18 — the log truncation statement.** Cheap to satisfy with a hardcoded sentence. The
   `logsTruncated: false` test is what stops that, and it is the first assertion someone will call
   redundant.

**The criteria most likely to be cut under pressure** are different from the weakest:
**AC-9** (a real-socket test is the most expensive single thing here, and "we have a component test
that shows two snapshots" will be offered as equivalent — it is precisely what the viability note
says is not); **AC-12's fourth test** (the mid-fallback denial, which looks like a duplicate of the
third); **AC-23's falsification table** (the first thing to go once the suite is green); and
**AC-21(a)'s byte-identity check on the escalation file** (because a red test in the suite is
uncomfortable and making it green is one line).
