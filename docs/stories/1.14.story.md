## User Story

**As a** put-checks user cleaning up a batch of retired checks,
**I want** `POST /checks/_bulk` to accept up to 100 delete operations with partial-failure semantics (207 Multi-Status),
**so that** I can delete a batch in one round-trip rather than 100 sequential DELETEs, and operations on unowned CSIs fail only those specific ops rather than rejecting the whole batch.

---

## Acceptance Criteria

- [ ] **AC-1:** `POST /api/v1/checks/_bulk` accepts body:
  ```json
  { "operations": [ { "op": "delete", "id": "<uuid>" }, ... ] }
  ```
  Max `operations.length = 100`; request with 101+ returns `400` with clear message (catches accidental mega-batches before allocation).
- [ ] **AC-2:** Only `op=delete` is supported in M1. Any other `op` value in a request returns `400` for the batch as a whole (unknown op is programming error, not data error). Story 3.9 extends to `update` + `tag`.
- [ ] **AC-3:** Each operation is independently authorized: `canWrite(auth, check.csiId)` evaluated per check. An op on an unowned CSI fails THAT op (status `failed`, code `FORBIDDEN`), not the batch.
- [ ] **AC-4:** Response envelope:
  - HTTP **200 OK** if all ops succeeded.
  - HTTP **207 Multi-Status** on any mixed outcome.
  - HTTP **400** if all ops failed validation (including unknown op, missing id).
  - Body:
    ```json
    { "results": [ { "op_index": 0, "status": "success", "id": "<uuid>" },
                   { "op_index": 1, "status": "failed", "id": "<uuid>",
                     "error": { "code": "FORBIDDEN", "message": "..." } }, ... ] }
    ```
- [ ] **AC-5:** If all ops target the same CSI (single `canWrite` call for efficiency), execution runs in a single `@Transactional` unit — all delete rollback on one failure. Otherwise each op runs in its own short transaction. Decision made by bucketing ops by csi_id at request-parse time.
- [ ] **AC-6:** Audit trail: each op emits a structured log line with `bulk_correlation_id` (generated per request), `op_index`, `user_id`, `check_id`, `outcome`.
- [ ] **AC-7:** Idempotency-Key (from 1.13) applies to the whole batch: replaying the same key within 5 minutes returns the cached 207 verbatim — individual ops are NOT re-run.
- [ ] **AC-8:** Rate-limit bulk bucket consumed (1 bulk token from 1.15's bucket) AND per-operation bucket (delete = write bucket, consumed N times, not 1).
- [ ] **AC-9:** Metric `checks_bulk_operations_total{op,outcome}` + `checks_bulk_batch_size` (histogram).
- [ ] **AC-10:** Integration tests:
  - `BulkAllSuccessIT`: 5 ops, all owned → 200 with 5 successes.
  - `BulkMixedIT`: 3 owned + 2 unowned → 207 with per-op statuses.
  - `BulkAllFailIT`: 5 ops all unowned → 400 (OR 207 — spec §6.4 says 207 for mixed; clarify in code; if all-failed, return 400 with "no operations authorized").
  - `BulkOverSizeIT`: 101 ops → 400 with "max 100".
  - `BulkUnknownOpIT`: `op: "tag"` at M1 → 400.
  - `BulkIdempotencyIT`: replay same key → cached 207 returned, no duplicate deletes.
  - `BulkTransactionalIT`: same-CSI batch with one synthetic failure → all ops rolled back.
- [ ] **AC-11:** JaCoCo coverage ≥ 80%.

## Implementation Notes

- **Single-CSI optimization:** before dispatching ops, bucket by `csi_id`. If all ops share one csi_id, single @Transactional. Else one tx per op.
- **HTTP 400 vs 207 on all-failures:** spec §6.4 says 207 for mixed and 200 for all-success; 400 for all-fail **including validation**. AC-10's all-unowned case is a judgment call — treat as 400 ("no operations authorized") rather than 207 to signal "the request itself was wrong" vs "some parts failed".
- **Bulk correlation ID:** `UUID.randomUUID()` per request, injected into MDC for the duration of the batch. Shows up in every op's log line.
