## User Story

**As** the owner of SPK-06 phase B (@qa) and the next reader of a legitimate seek-measurement failure,
**I want** a runner-side, per-image calibration setting that `takeRunOrigin` can apply, and a seek-measurement failure message that reports each step's true signed lead instead of a mis-attribution's misleading positive number,
**so that** staging can *correct* the readiness-to-first-frame gap once it is measured (not just report it), and so that a future reader of a red median assertion is pointed at the real, small, negative lead rather than a fictitious four-hundred-millisecond one.

---

## Problem Statement

Verified by reading the merged tree at `82322e084` (branch `epic/EPIC-10`).

**1. There is nowhere to put a measured calibration value today.** ADR-002 §26.3 item 3 rules that the readiness-to-first-frame gap, once SPK-06 phase B measures it, is corrected by "a runner setting with default `0`" added to the origin inside `takeRunOrigin`. No such setting exists: `takeRunOrigin(source: OriginSource = systemOriginSource): RunOrigin` (`studio-runner/src/run/timeline.ts:86`) takes no second argument, and nothing in `studio-runner/src/server/config.ts`'s `KEY_SPECS` (the runner's sole, enumerated, fail-closed configuration surface) accepts one. Until this setting exists, SPK-06 phase B can only *report* the gap (§26.3 item 6's fallback), never apply it — the manifest's own `spk06_relation` line says exactly this.

**2. The setting cannot land as a two-line change, because the child that takes the origin is not the process that would read the environment.** `takeRunOrigin` is called once, in the child process, at `studio-runner/src/run/childRuntime.ts:285`. The child process's environment is **not** inherited from the parent's `process.env` — it is built key-by-key from an explicit allowlist, `INHERITED_ENV_KEYS` (`launcher.ts:155`, consumed by `childEnvironment` at `launcher.ts:370-387`), specifically so that "the runner's own configuration ... never enters the process that opens untrusted pages" (`launcher.ts:20-25`). A `STUDIO_RUNNER_*` value therefore cannot reach `childRuntime.ts:285` by adding it to the environment the child is forked with; it has to travel as **data**, the way `recording: { width, height }` already does (`protocol.ts:85`, sent in the `LaunchMessage` `child.send({ kind: 'launch', ... })` at `launcher.ts:430-440`, read as `message.recording` at `childRuntime.ts:258`). This is the plumbing the epic manifest's own comment (`EPIC-10-EXECUTION.yaml:663-666`) says is inferred, not traced, and names the size driver. It is traced, file:line, in Dev Notes below.

**3. The 10.16b QA gate found the median-assertion failure message misleading for exactly the failure mode this calibration exists to correct.** F-5 (`docs/qa/gates/10.16b-seek-measurement-frame-finder.yml:306-321`): "A lead past 100 ms also shows up as a +400–650 ms 'mis-attribution' number rather than the true about −110 ms, which misleads diagnosis." ADR-002 §26.4(b) assigns the fix: report each step's signed distance to the nearest **earlier** change alongside the existing message, so a genuine failure (§26.3 item 6 — a real, red assertion on a slower host, never widened) is diagnosed correctly rather than chased in the wrong direction.

**4. The file's own stated cause for the historical mis-attribution is now known to be wrong, and @po has ruled what it should say instead.** `seek-measurement.test.ts:43-48` and `:72-75` blame "a full-viewport repaint [that] does not always land in a single encoded frame" and "the detector missed a repaint". 10.16b's Dev Agent Record (`10.16.story.md:392`) found, across 27 of 27 mis-attributions and two independent observers, that every one was a systematic lead past the old 60 ms slack — the repaint was found every time. ADR-002 §26.5 rules the replacement content; @po's approval (`EPIC-10-EXECUTION.yaml:690-701`) is conditional on four things this story must prove, not merely assert.

### (a) The calibration setting

- [ ] **AC-1: A new runner configuration key, `STUDIO_RUNNER_SEEK_ORIGIN_CALIBRATION_MS`, is added to the loader's enumerated, fail-closed namespace.** It parses as a non-negative integer (`kind: 'integer'`, `min: 0`, `fallback: 0`, `required: false`), following the exact pattern of every other integer key in `KEY_SPECS` (`studio-runner/src/server/config.ts:134-306`). `RunnerConfig` gains `readonly seekOriginCalibrationMs: number`.   *Anti-vacuous:* the production symbol is `KEY_SPECS.SEEK_ORIGIN_CALIBRATION_MS`. Mutation: delete the row → `loadConfig` with the env var set now reports `is not a configuration key this runner accepts` (the existing unknown-key path, `config.ts:357-367`, re-used, not re-implemented — no new fail-closed logic is written for this AC, only a new enumerated entry). The default is the value this story actually commits to, so this is the load-bearing mutation. *(Replaced at @po validation. The draft's mutation, `min: -1`, could not fail: `parseInteger` (`config.ts:329-336`) rejects `"-1"` with its `^\d+$` regex before `min` is ever consulted, so `min: 0` is not independently falsifiable. The test that `"-1"` is rejected stays, but it is recorded as covering the shared parser, not this row.)*

- [ ] **AC-2: `takeRunOrigin` accepts the calibration and applies it to the origin, not to individual readings — proved by an exact, deterministic shift.** New signature: `takeRunOrigin(source: OriginSource = systemOriginSource, calibrationOffsetMs = 0): RunOrigin`. Implementation: `monotonicZero = source.monotonicNow() + calibrationOffsetMs` (the constant is added to the **zero**, per §26.3 item 2, never to a reading taken from it). `RunOrigin` gains `readonly calibrationOffsetMs: number` (an echo of the argument, kept inspectable the same way `monotonicZero` already is, per `timeline.ts:64-65`'s own stated reason). Two properties, both proved in `studio-runner/test/run/timeline.test.ts` using the file's own `countingSource` fixture (no new browser, no new fixture) so the same injected monotonic sequence drives both a calibrated and an uncalibrated run and the two outputs are compared directly:
  1. `takeRunOrigin(source)` (no second argument) and `takeRunOrigin(source, 0)` produce **byte-identical** `RunOrigin` values — same `monotonicZero`, same `startedAtMs`, and the same sequence of `clock.now()` values across N calls, for the same underlying monotonic sequence.
  2. `takeRunOrigin(source, N)` for `N > 0`, driven by the **same** monotonic sequence as an `N = 0` run, produces `clock.now()` readings that are **exactly `N` smaller** than the uncalibrated run's readings, at every call after the first. `startedAtMs` stays `0` under every `N` — this is not a defect and not something this AC claims to shift: `startedAtMs` is defined as the origin's own first reading, computed as the zero minus itself (`timeline.ts:92`), so it reads `0` at whatever real instant the (possibly shifted) zero now denotes, by construction. Only `clock.now()` calls **after** that first sample move. *Worked example, to remove sign ambiguity:* with `monotonicNow()` returning `1_000` then `1_300` on successive calls, `takeRunOrigin(source, 0).clock.now()` (called once, after the zero read) is `300`. The **same two monotonic values**, replayed through `takeRunOrigin(source, 50)`, give `clock.now() = 250` — fifty milliseconds **earlier**, not later, because the constant enlarges the zero being subtracted. A test that got the sign backwards (adding the offset to the reading instead of to the zero) is exactly what property 2 is written to catch. *[Source: ADR-002 §26.3 item 2 "a measured constant is added to the origin inside takeRunOrigin ... so the zero is recording-context readiness plus the gap"; §26.4(a) "a test that a non-zero value shifts every reading by exactly that amount and that 0 produces byte-identical output to today"]*

  *Anti-vacuous:* the production symbol is `takeRunOrigin` in `timeline.ts`. Mutation 1: change `monotonicZero = source.monotonicNow() + calibrationOffsetMs` to `... - calibrationOffsetMs` → property 2's sign check goes red (readings shift the wrong direction). Mutation 2: apply the offset inside `clock.now()`'s closure instead of to `monotonicZero` (`now: () => source.monotonicNow() - monotonicZero + calibrationOffsetMs`). Readings then move `N` **later**, and property 2 (exactly `N` **smaller**) goes red. *(Corrected at @po validation. The draft predicted that `startedAtMs` would stop being `0` and that property 1 would catch it. Neither happens: `startedAtMs` is `monotonicZero - monotonicZero` (`timeline.ts:92`) and never goes through `clock.now()`, and at `N = 0` the mutated closure is identical to the original.)*

  **What this AC does not settle — ESC-3 (raised by @po, open with @architect).** Two behaviours under a **non-zero** value are not ruled by §26, and this AC asserts neither. (1) A reading taken within `N` ms after readiness is **negative**, but `RunnerStepResult` declares `minimum: 0` and says *"nothing the runner observes precedes the origin"*. (2) `browserStartedAt` stays the wall instant at readiness while the zero moves `N` later, so the §11 pairing drifts by `N`. This AC keeps today's behaviour for both: `browserStartedAt` unchanged, and `startedAtMs` still `0`, asserted as current behaviour and labelled as such, **not** as a ruling. If @architect rules otherwise before implementation, @po amends this AC. Neither behaviour can occur at the shipped default of `0`.

## Dev Notes

### The plumbing chain, traced (not inferred)

The manifest's own size-reasoning comment (`EPIC-10-EXECUTION.yaml:663-666`) names the two endpoints — `server/config.ts`'s `KEY_SPECS` and `childRuntime.ts:285` — and says the plumbing between them "is INFERRED from those two locations, not traced." It is traced here:

```
config.ts (KEY_SPECS → RunnerConfig.seekOriginCalibrationMs)
  → main.ts:62-70  (createConfiguredLauncher builds ProductionLauncherOptions)
    → launcher.ts ChildLauncherOptions.seekOriginCalibrationMs (required field, closed over by createChildBrowserLauncher)
      → launcher.ts:430-440  child.send({ kind: 'launch', ..., seekOriginCalibrationMs: options.seekOriginCalibrationMs })
        → protocol.ts LaunchMessage.seekOriginCalibrationMs (validated: ACCEPTED_LAUNCH_KEYS, parseLaunchMessage)
          → childRuntime.ts:285  takeRunOrigin(dependencies.originSource, message.seekOriginCalibrationMs)
            → timeline.ts takeRunOrigin(source, calibrationOffsetMs)  monotonicZero = source.monotonicNow() + calibrationOffsetMs
```

**Why it cannot travel as an environment variable.** The child process's environment is not inherited from the parent — `launcher.ts:370-387`'s `childEnvironment` builds it from `INHERITED_ENV_KEYS` alone (`launcher.ts:155`), and the module's own docstring (`:20-25`) states the reason: "the runner's own configuration ... never enters the process that opens untrusted pages." This is a deliberate isolation boundary (§9.3), not an oversight, and this story does not weaken it. Data that the child needs but that is not per-run job data — `recording: { width, height }` is the existing precedent — travels in the `LaunchMessage`, which is exactly the channel this story reuses.

**Why `ChildLauncherOptions.seekOriginCalibrationMs` is required, not optional (AUTO-DECISION).** `stopTimeoutMs?: number | undefined` on the same interface defaults inside `createChildBrowserLauncher`'s body (`?? 5_000`). `recording` and `stepTimeoutMs` are required, with no such default, because §6.1/§8.5 treat them as "chosen values rather than library defaults" that every caller must state. The calibration is the same kind of value — "THIS STORY SETS NO VALUE" is itself a chosen `0`, not a gap to paper over with `?? 0` at the one production call site. Making it required forces `realRunner.ts` (the fixtures harness, the only other caller) to write `seekOriginCalibrationMs: 0` explicitly, with a comment citing §26.3 item 5 — a compile-time-visible pin, not a silent fallback. **Reason:** [AUTO-DECISION @sm] required field over optional-with-default → clearer AC-4 falsification (a deletion is a type error, not a silently-defaulted pass) and consistent with the interface's existing style for chosen-value fields.

**Why the chart gets a test, not a `runnerEnv` entry (AUTO-DECISION).** `values.yaml:511-525`'s `runnerEnv` map states its own discipline: "Starting values under §8.5, tuned against staging measurements — not commitments," used for `recordingWidth`/`recordingHeight` etc. precisely because an *implicit Playwright default* would be a value "nobody chose." The calibration's default of `0` is different in kind: it is the runner's own already-chosen default (§26.3 item 3), not an implicit library value, and "THIS STORY SETS NO VALUE" three times in the manifest argues against writing even a placeholder `"0"` into a file a future engineer might mistake for a measured one. **Reason:** [AUTO-DECISION @sm] omit from `runnerEnv`, add a rendered-manifest test instead. **OVERRULED by @po at validation.** The chart's `acceptedEnvKeys` list makes an omitted key impossible to set, and ADR-002 §26.4(a) requires the chart edit. The misreading risk is handled by the line's comment instead (AC-5 item 2).

**Why the diagnostic helper lives in `webm.ts`, not inline in `seek-measurement.test.ts` (AUTO-DECISION).** Placing it as an export lets it be unit-tested against `webm.test.ts`'s already-provenance-verified transcribed recordings without duplicating that data inline in the file under the strictest byte-identity constraint in this story (AC-8). **Reason:** [AUTO-DECISION @sm] symmetric export, tested with existing real data → smaller, more auditable diff to the file F-4's conditions constrain.

**Why the §26.3 item 4 application rule is not implemented in code (AUTO-DECISION).** `takeRunOrigin` receives one number; it has no population of staging measurements to test "same sign on every step, median larger than spread" against. That test is run once, by a human (or @qa's tooling, per ADR-002 §28.3's ownership table), against SPK-06 phase B's own measurement table — before anyone writes a non-zero value into the chart. Pretending otherwise by writing an unreachable runtime branch would be inventing a check nobody can exercise. **Reason:** [AUTO-DECISION @sm] document the rule, do not code it → honest about what AC-6 is (see the vacuous-shape check).

### The arithmetic, precisely (do not get the sign backwards)

`monotonicZero = source.monotonicNow() + calibrationOffsetMs`. The constant enlarges the **zero**, so every later `clock.now() = source.monotonicNow() - monotonicZero` reading is **smaller** by exactly `calibrationOffsetMs` than it would have been uncalibrated — it moves *earlier*, not later. `startedAtMs` stays `0` under every calibration value, because it is defined as the origin's own first reading relative to itself (`monotonicZero - monotonicZero`), which is `0` regardless of what real instant `monotonicZero` now denotes. See AC-2's worked example for exact numbers. A implementer who instead adds the constant inside `clock.now()`'s closure (`... - monotonicZero + calibrationOffsetMs`) gets the *reading* to shift the opposite direction and *also* breaks `startedAtMs`'s invariant — AC-2's falsification plan catches both.

### F-4's proposed replacement text

**For `:43-48`** (replacing the "does not always land in a single encoded frame ... the automated frame finder can pick the next scene change instead" hypothesis):

> The *measurement* is the per-step error, and it is reported in full. The *assertion* has to survive a detector that can still mis-attribute a step: story 10.16b found that every mis-attribution happened when a repaint was stamped more than the helper's slack **before** the reported start — a systematic lead, most likely the readiness-to-first-frame gap AC-12c leaves to staging (ADR-002 §26.2) — never because a repaint was split across frames or missed outright. A lead past the slack is matched to the *next* change instead, hundreds of milliseconds later, which is why it shows up here as a large *positive* error rather than the small negative one it actually is. That is a limitation of reading the container rather than decoding it, not a property of the runner, and an assertion that pretended otherwise would be flaky rather than strict. The two-bound design stays for the same reason as before: a median that one mis-attribution cannot move, plus an outlier bound that catches a process-origin reading.

**For `:72-75`** (replacing "the detector missed a repaint and matched the next scene change" as the stated cause):

> **Mis-attributed** — the old 60 ms slack let a repaint stamped before the reported start slip past it, so the detector matched the *next* scene change instead of the one that was actually there: +137.0, +137.5, +374.0, +416.9 and +657.7 here, +376.4 and +650.4 in QA's run. Every one is positive and every one lands on a later change in the ~720 ms cadence — the signature of the slack being too narrow, not of the detector missing a repaint that was never recorded.

Wording may be adjusted at implementation time; the four facts it must state (systematic lead, AC-12c/§26.2 attribution, "not a split/missed repaint", and the outlier bound's reasoning naming the slack) may not be dropped, per §26.5.
