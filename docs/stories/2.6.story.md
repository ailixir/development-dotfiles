## User Story

**As a** platform operator managing storage costs and query performance,
**I want** a monthly retention pruner that detaches and drops partitions older than the configured retention window,
**so that** execution_results doesn't grow unbounded and old data is cleaned up without impacting live queries.

---

## Acceptance Criteria

### Retention pruner
- [ ] **AC-1:** `RetentionPruner` bean with `@Scheduled(cron = "0 15 3 1 * ?")` (03:15 UTC on the 1st of each month). Scans for partitions older than the configured retention period.
- [ ] **AC-2:** `@SchedulerLock(name = "retentionPruner", lockAtMostFor = "30m", lockAtLeastFor = "1m")` prevents multi-pod races.
- [ ] **AC-3:** Retention period configurable via `checks.partitioning.retention-months` property (default: 12, per NFR-RET-01's 1-year cold window).
- [ ] **AC-4:** For each expired partition: (a) `ALTER TABLE execution_results DETACH PARTITION execution_results_{YYYY_MM} CONCURRENTLY`, then (b) `DROP TABLE execution_results_{YYYY_MM}`. Two separate statements — DETACH CONCURRENTLY cannot run inside a transaction block.
- [ ] **AC-5:** `DETACH CONCURRENTLY` requires PostgreSQL 14+. The existing PG 15 constraint (Zonky + RDS) satisfies this. RDS-parity lint does NOT need a new rule for this (it's standard PG syntax).
- [ ] **AC-6:** If `DETACH CONCURRENTLY` fails (e.g., partition already detached, concurrent DDL), log the error and skip to the next partition. Do not abort the entire pruning cycle.
- [ ] **AC-7:** Generalized: the same pruner handles `ui_test_executions` (monthly, same retention) and `report_executions` (quarterly, potentially different retention). Reuse `PartitionManager` from story 2.5 — add a `pruneExpired(int retentionMonths)` method.

### Audit + metrics
- [ ] **AC-8:** Structured log line per detach+drop: `partition_pruned table=execution_results_2025_03 action=detach_drop`.
- [ ] **AC-9:** Structured log line if skip: `partition_prune_skipped table=execution_results_2025_03 reason=already_detached`.
- [ ] **AC-10:** Micrometer counter `checks_partitions_pruned_total{table}` incremented per successful detach+drop.
- [ ] **AC-11:** Micrometer counter `checks_partitions_prune_errors_total{table}` incremented per failure.

### Tests
- [ ] **AC-12:** IT `RetentionPrunerIT`: create a test partition with an old date range (e.g., 2 years ago), run the pruner, verify the partition no longer exists in `pg_catalog.pg_inherits`.
- [ ] **AC-13:** IT `RetentionPrunerSkipCurrentIT`: verify the pruner does NOT touch current month or future partitions.
- [ ] **AC-14:** IT `RetentionPrunerConfigIT`: set `retention-months=0`, verify all past partitions are pruned (edge case test).
- [ ] **AC-15:** JaCoCo coverage ≥ 80%.

## Implementation Notes
- **DETACH CONCURRENTLY outside transaction:** Spring's `@Transactional` would wrap the operation in a transaction, but `DETACH CONCURRENTLY` cannot run inside one. Use `JdbcTemplate.execute()` without `@Transactional`. The `@SchedulerLock` provides the coordination guarantee instead.
- **Partition age detection:** query `pg_catalog.pg_class` + `pg_inherits` to list partitions, parse the `_YYYY_MM` suffix to determine age. Compare against `YearMonth.now().minusMonths(retentionMonths)`.
- **Test partition creation:** in ITs, create a partition with old date range (e.g., `execution_results_2024_01`), insert no data, run pruner, verify gone. No need to insert test data — the DDL test is sufficient.
- **PG 15 DETACH CONCURRENTLY behavior:** if the partition is already being detached by another process, PG throws an error. The error-isolation per partition handles this.
