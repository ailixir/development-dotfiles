## Problem Statement

**Re-verified independently by this drafter, on this story's own base commit `97e25f3ed`, session `2026-09-17`.** Every citation below was read directly, not transcribed from the spawn brief.

### The defect

- `docs/specs/studio/openapi.yaml` declares `security: [serviceIdentity]` on **both** runner-served routes: `runnerValidateArtifact` (`operationId` at `:849`, `security:`/`serviceIdentity: []` at `:861-862`) and `runnerAdmitRun` (`operationId` at `:903`, `security:`/`serviceIdentity: []` at `:927-928`). Confirmed by direct line read, not grep alone.
- `RunnerValidationClient.java:86-92` complies, with a nuance the one-line citation in the brief elides: the `Authorization: Bearer` header is set **conditionally** —
  ```java
  headers -> {
    if (properties.serviceIdentityToken() != null
        && !properties.serviceIdentityToken().isBlank()) {
      headers.setBearerAuth(properties.serviceIdentityToken());
    }
  }
  ```
  — i.e. it presents a credential when one is configured and silently presents none when it is not. This client is not this story's subject, but the nuance matters for AC-5 below: "the pattern already used elsewhere" is a *conditional* header set, not an unconditional one.
- **`HttpRunnerDispatchClient.java` sets no authentication header at all**, on any code path. Confirmed by direct read of the whole file (159 lines) and independently by `grep -n "Bearer\|Authorization\|auth\|\.header(\"auth" backend/src/main/java/com/citi/put/checks/studio/dispatch/HttpRunnerDispatchClient.java`, which returns nothing (exit code 1). The only header this client sets, ever, is `Content-Type: application/json` (`:70`).
- **There is no outbound identity property reachable from this client at all.** Its constructor takes `StudioExecutionProperties` (confirmed by reading `StudioExecutionProperties.java` in full: it declares `enabled`, `pendingSla`, `startDeadline`, `runDeadline`, `admissionTimeout`, `evidenceRetention`, `referenceCanary`, `Quotas`, `Dispatcher`, `Callback`, `Sse` — no service-identity field of any kind) plus a raw `@Value("${studio.execution.runner-base-url:...}")`-bound `String runnerBaseUrl` (`:43-50`). The token that *does* exist, `StudioRunnerProperties.serviceIdentityToken` (`StudioRunnerProperties.java:22-24`), is wired only into `RunnerValidationClient` — a different bean, for a different route.
- **Runtime evidence, from the co-run harness's own recorded run** (`EPIC-10-RUN-LOG.md:2183-2198`, Phase 1, first run of `StudioCoRunIT` against a real `studio-runner`):
  ```
  component : studio-runner (POST /v1/runs), as reached by HttpRunnerDispatchClient
  refused   : never admitted — no admission_id on the ledger; state DONE, execution ERROR/DISPATCH_FAILED
  runner log: {"event":"request.unauthenticated","path":"/v1/runs","code":"IDENTITY_MISSING"}
  ```
  and, in the same session, leg 1 (`POST /v1/validate`, which presents identity) was green. **The proof is structural, not circumstantial: in one run, against one runner, in one service, leg 1 is green and leg 2 is red** (`:2197-2198`, verbatim).

### Why it matters more than the identity gap itself

`DEF-01` was recorded as fixed — the dispatch body now carries all fourteen keys the frozen `RunJob` schema requires (confirmed by reading `HttpRunnerDispatchClient.body(RunJob)`, `:134-157`: fourteen `body.put(...)` calls, matching the Javadoc's own count). **But the identity refusal happens before the body is ever parsed.** `EPIC-10-RUN-LOG.md:2204-2205` records the falsifying mutation: *"Mutation M1a proves it: dropping a required key from the dispatch body produces a response byte-identical to the baseline."* So DEF-01's fix has a defect class — a malformed body on this exact route — that is currently **unobservable**, not merely untested: no assertion the harness could write today would distinguish "the body is wrong" from "identity is wrong," because the runner never reaches the body. It becomes observable, for the first time, the moment identity is fixed. This story's AC-3 exists because of that sentence, not as an independent idea.

`DEF-02`'s path (the runner reporting an admission and a terminal state back to the API) is likewise **unexercised, not merely unproven**: `StudioCoRunIT`'s leg 3 (`Order(3)`) cannot even attempt its assertion while leg 2 never sets `dispatchedExecutionId` (`StudioCoRunIT.java:387-393`, `:469-475`) — confirmed by reading the guard clause at the top of `theRunnerReportsBackAndTheApiAcceptsWhatItSends`, which throws a `CoRunFailure` naming leg 3 as *blocked, not failing on its own account* rather than attempting a real assertion. `EPIC-10-RUN-LOG.md:2253-2255` states this plainly: *"Legs 2 and 3 cannot pass until identity is fixed, so `DEF-02`'s path remains unexercised by running."*

### The harness that gates this story

`tools/corun.sh` + `backend/src/test/java/com/citi/put/checks/corun/StudioCoRunIT.java` (both merged at `97e25f3ed`, `feat/p1-corun`, confirmed present in this worktree). Four ordered legs (`@Order(0)`–`@Order(3)`), read in full by this drafter:

- **Leg 0** (`theRunnerIsUpEnforcesItsIdentityAndAcceptsTheCredentialTheApiWasGiven`) — the attribution baseline: the runner is up, refuses an unauthenticated `POST /v1/runs` with `401 IDENTITY_MISSING`, and accepts the credential the API was configured with. This leg is **already green today** and unaffected by DEF-05, because it probes the runner directly, not through `HttpRunnerDispatchClient`.
- **Leg 1** (`theApiCompilesADraftThroughTheRealRunnerValidateRoute`) — API → runner, `POST /v1/validate`, through `RunnerValidationClient`. **Green today.**
- **Leg 2** (`theApiDispatchesAConfirmedRevisionToTheRealRunner`) — API → runner, `POST /v1/runs`, through `HttpRunnerDispatchClient`. **This is DEF-05's path, and it is red today.** The assertion is `admission_id IS NOT NULL` on `studio_dispatch_ledger` — deliberately not the ledger state `DISPATCHING`, because `EPIC-10-RUN-LOG.md:2220-2223` records that a mutation (`M2`) caught the original, weaker assertion before it ever ran: *"The original leg-2 assertion accepted state `DISPATCHING`, which is written before the send — so it would have gone green against a runner at a completely wrong address. Re-anchored on `admission_id IS NOT NULL`, the one column only the runner's own CAS can write."* `StudioCoRunIT.java:424-436`'s own Javadoc on `awaitAdmission` restates the same reasoning verbatim, independently confirming the run-log account.
- **Leg 3** (`theRunnerReportsBackAndTheApiAcceptsWhatItSends`) — runner → API, admission and terminal report. **Currently unreached**, blocked on leg 2 (see above).

`tools/corun.sh`'s own two harness-integrity guards (its comments, and confirmed by reading the script): **G1** — without `STUDIO_CORUN=1`, Gradle reports `BUILD SUCCESSFUL` with all four tests skipped, and the wrapper's own reporter (`corun-report.mjs`, read from the XML, never the exit code) treats an empty run as a failure, not a pass. **G2** — an unbuilt runner (`studio-runner/dist/main.js` missing) fails loudly rather than skipping.

## Acceptance Criteria

### (a) The gate itself — proof of admission

- [ ] *(Blocked — see Depends on)* **AC-1: Leg 2 passes on the fixed tree.** `StudioCoRunIT#theApiDispatchesAConfirmedRevisionToTheRealRunner` (`@Order(2)`) is green: `dispatched == 1` and `admission_id IS NOT NULL` on `studio_dispatch_ledger` for the dispatched execution, read via the harness's own `admissionId(executionId)` helper. This is the ledger column "only the runner's own compare-and-set can write" (`StudioCoRunIT.java:434-436`) — **the assertion must remain exactly this predicate**, not a reversion to the weaker `DISPATCHING`-state check that mutation `M2` already falsified once (`EPIC-10-RUN-LOG.md:2220-2223`). *Verified by:* `tools/corun.sh` (harness-verifiable).

  *Anti-vacuous:* the falsifying mutation for this AC is the defect itself — reverting `HttpRunnerDispatchClient` to today's no-header state reproduces the exact red this story starts from (`IDENTITY_MISSING`, no `admission_id`, ledger state `DONE`, execution `ERROR/DISPATCH_FAILED`). No new mutation needs inventing; the before/after **is** the falsification.

- [ ] *(Blocked)* **AC-2: Leg 0 stays green, unchanged, on the fixed tree.** `StudioCoRunIT#theRunnerIsUpEnforcesItsIdentityAndAcceptsTheCredentialTheApiWasGiven` (`@Order(0)`) still asserts all four of: unauthenticated `/health` → `401`; authenticated `/health` → `200`; unauthenticated `POST /v1/runs` → `401 IDENTITY_MISSING`; authenticated-but-empty `POST /v1/runs` → `400 JOB_INVALID`. This is the "no weakening" guard on the **runner's own** identity enforcement: nothing in DEF-05's fix touches the runner, so this leg has no legitimate reason to change, and a fix that happened to also loosen the runner's check would show here first. *Verified by:* `tools/corun.sh`, same run as AC-1 (harness-verifiable; this leg already passes today and is a regression check, not a new proof).

### (b) DEF-01's defect class becomes observable again

- [ ] *(Blocked)* **AC-3: A malformed dispatch body, on the fixed tree, produces a refusal distinguishable from both the identity refusal and from silence — not a response byte-identical to the unmutated baseline.** Procedure: with the identity fix landed and AC-1 green, drop exactly one required key from the dispatch body the fixed `HttpRunnerDispatchClient` sends (@dev/@qa's choice of which key; restore by `sha256` of the file before/after), and re-run leg 2. The runner's own account of the window (`StudioCoRunIT`'s `whatTheRunnerSaidAboutTheDispatch`, `:517-543`) must report the **third** of its three named shapes — *"The API was admitted as a caller and the runner objected to WHAT it was sent"* — never the first (*"refused this dispatch on its IDENTITY"*) and never the second (*"recorded NOTHING … suspect the address"*). This is the exact mutation already performed once, manually, as `M1a` (`EPIC-10-RUN-LOG.md:2204-2205`, *"dropping a required key from the dispatch body produces a response byte-identical to the baseline"*); this AC requires that repeating it on the fixed tree produces a **different, distinguishable** result. *Verified by:* `tools/corun.sh`, one mutated re-run (harness-verifiable).

  *Anti-vacuous:* the production symbol is the identity fix itself (there is no separate "distinguishability" code to mutate — distinguishability is an emergent property of identity now working). The falsifying condition is exactly the one already observed: if this AC's re-run still shows a byte-identical response to the unmutated baseline, the fix has not actually restored DEF-01's own defect class to observability, whatever leg 2's plain (unmutated) run shows.

### (c) DEF-02's path is exercised by running

- [ ] *(Blocked, and blocked specifically on AC-1)* **AC-4: Leg 3 passes on the fixed tree.** `StudioCoRunIT#theRunnerReportsBackAndTheApiAcceptsWhatItSends` (`@Order(3)`) is green: the execution snapshot leaves `PENDING`, and its `revisionId` equals the confirmed revision dispatched. **State plainly in the Dev Agent Record whether this leg was reached at all before the fix** — today it is not merely red, it is unreached (`dispatchedExecutionId == null`, `StudioCoRunIT.java:469-475`), and reporting "leg 3 red" as if it had run would misstate what was actually observed. *Verified by:* `tools/corun.sh`, same run as AC-1 (harness-verifiable).

### (d) The pre-flight guard is falsifiable

- [ ] *(Blocked)* **AC-5: An unconfigured runner or a blank service-identity token produces a terminal, named refusal — proven on a unit test, not the co-run harness.** A test directly against `HttpRunnerDispatchClient.send(...)`, constructed with (i) no configured runner base URL and (ii) a configured base URL but a `null`/blank identity token, must in both cases observe: `DispatchOutcome.kind() == DEFINITE_REFUSAL`, `retryable() == false`, and `detail()` naming the cause (the exact string is @dev's choice; this story does not fix it). It must further observe that **no network attempt was made** — construct the client with any base URL pointed at a closed local port and confirm the outcome is still the terminal, named refusal, not `AMBIGUOUS` (which is what a real connection attempt against a closed port produces, per `HttpRunnerDispatchClient.send`'s own `IOException` branch, `:82-83`). *Verified by:* a new unit test (**not** harness-verifiable — see rationale below).

  **Why the co-run harness cannot verify this AC.** `StudioCoRunIT`'s `@DynamicPropertySource` (`:149-160`) always wires a real runner base URL and a real, matching service-identity token, deliberately: leg 0's whole purpose is an attribution baseline that only holds when the runner is genuinely reachable and correctly credentialed (Javadoc, `:270-277`). A harness that could also run with an unconfigured runner would reintroduce exactly the ambiguity leg 0 exists to remove — "the API refused to try" versus "the API tried and failed" would become indistinguishable again, this time inside the harness itself. The falsifiable guard is provable only below the harness, directly against the client.

  *Anti-vacuous:* mutation — remove the pre-flight guard clause from the fixed client (or replace its condition with one that never triggers) → this unit test's refusal assertion goes red, either because a real HTTP attempt is now made (observable as an actual connection attempt / a different exception type) or because the outcome kind is no longer `DEFINITE_REFUSAL`. Restore; re-run.

### (e) No weakening

- [ ] *(Blocked)* **AC-6: The fix's diff is confined to the dispatch client and its wiring — reviewed, not assumed.** The committed diff must not touch `RunnerValidationClient.java` (already compliant), `docs/specs/studio/openapi.yaml`'s `security:` declarations (already correct at `:861-862`/`:927-928`), or the runner's own identity-enforcement code. *Verified by:* reading the committed diff once it exists (**not** harness-verifiable — this is a code-review check on the diff's shape, not a runtime property anything can assert). Named as a criterion, not left to review discretion, because a fix that "solves" DEF-05 by loosening the contract instead of presenting a credential would leave every other criterion in this story green for the wrong reason.

- [ ] *(Blocked)* **AC-7: The two adjacent observability gaps this investigation found are not silently resolved or silently worsened without being noted.** Two pre-existing facts, both confirmed by reading (see *Routed, not this story's scope* in Dev Notes for why neither is a required fix here): (1) `StudioDispatcher.applyOutcome`'s `DEFINITE_REFUSAL` branch discards `DispatchOutcome.detail()` — it calls `close(executionId, ExecutionErrorCode.DISPATCH_FAILED, now)`, and `StudioDispatchLedgerStatements.closeWithError(UUID, String, Instant)` (`:565`) takes no detail parameter, so an operator sees `DISPATCH_FAILED` whether the runner refused the credential or the body; (2) `CompilePipeline.java:268` maps every runner-side validate refusal to the single `CompileErrorCode.VALIDATOR_UNAVAILABLE` (`CompileErrorCode.java:21`), collapsing "runner refused my credential" and "runner refused my body" the same way, on the *validate* route. **This AC requires recording, in the Dev Agent Record, the value of `ui_test_executions.error_code` after AC-3's mutated re-run** (expected, if unfixed: still `DISPATCH_FAILED`, carrying no distinguishing information) — not requiring it be anything else. If the landed diff happens to also touch either code path, say what changed; this story does not require either fixed, but a gate that let a regression here pass unnoted because "the identity dispatch went green" would be exactly the kind of weakening this AC exists to catch. *Verified by:* querying `ui_test_executions.error_code` after the AC-3 mutation, via the same JDBC access pattern the harness already uses (harness-verifiable for the recording; not harness-verifiable for "is this acceptable," which is a judgment call left to Dev Notes).

## Vacuous-shape self-check

- **Avoids "a guard proved only by reading the code."** AC-1–AC-4 require an actual co-run against a real `studio-runner` process, reading persisted ledger/execution state — not a description of what the fixed code is expected to do.
- **Avoids "the obvious predicate that passes against a wrong address."** AC-1 names the exact ledger column (`admission_id`) that mutation `M2` already showed was necessary, and forbids reverting to the weaker `DISPATCHING`-state check.
- **Avoids "a source-text scan standing in for a runtime assertion."** AC-6 is the one criterion in this story that *is* a text-shaped check (a diff review) — and it is named as such, not disguised as a runtime proof, per this drafter's own standing rule against exactly that substitution.
- **Avoids "a fix that hides its own side effects."** AC-7 requires recording, not assuming, that the two adjacent observability gaps are unchanged.

## Weakest criterion

**AC-6 (diff confinement)** is the weakest criterion in this story, and for a reason distinct from the epic's usual "per-component test" weakness: it is not a runtime property at all. Nothing this repository can run distinguishes "a fix that presents identity" from "a fix that presents identity and also, incidentally, loosens something else three files away" — that can only be caught by a human or an agent actually reading the diff at gate time. This story names the check so it is not skipped, but it cannot make the check automatic. **The named gap:** if the committed diff is large (touching many files, as `wt/epic`'s general uncommitted state — 241 dirty paths at last count — suggests it plausibly could, depending what else has landed by the time this gate runs), AC-6 depends entirely on whoever runs the gate actually reading the whole diff, not sampling it.

## Scope

### In scope

- **This story's own deliverables** (all Blocked until the dependency lands): a new unit test exercising `HttpRunnerDispatchClient`'s pre-flight guard directly, with no live runner (AC-5); the documented mutation-and-rerun procedure against `StudioCoRunIT` for AC-1–AC-4 and AC-7 (whether @dev/@qa choose to make the AC-3/AC-7 mutation a permanent parameterized test or a documented manual procedure is left to them — this story specifies the required observation, not the test's mechanics).

## Dev Notes

### Routed, not this story's scope: OBS-1 and OBS-2

**Ruling, made by this drafter, per the mission's explicit instruction to decide and justify:** both of AC-7's named observability gaps are **routed elsewhere**, not folded into this story's required fixes.

- **OBS-1 — `DispatchOutcome.detail()` is discarded on a terminal `DEFINITE_REFUSAL`.** `StudioDispatcher.applyOutcome`'s `DEFINITE_REFUSAL` branch, when not retryable within the pending deadline, calls `close(executionId, ExecutionErrorCode.DISPATCH_FAILED, now)` with no `LOGGER.warn` and no detail passed through; `closeWithError(UUID, String, Instant)` takes exactly three arguments, none of which is `detail()`. Confirmed by reading both methods directly.
- **OBS-2 — `compile_error` collapses two distinct runner refusals into one code.** `CompilePipeline.java:268` maps a runner-side validate failure to `CompileErrorCode.VALIDATOR_UNAVAILABLE` regardless of whether the runner refused the credential or the body — confirmed by `StudioCoRunIT`'s own leg-1 comment (`:338-342`): *"validator calls = 1 with the runner recording an identity refusal means the credential is wrong. validator calls = 1 with the runner recording nothing means the runner was reached and objected to the body: the API's `compile_error` collapses both of the latter into `VALIDATOR_UNAVAILABLE`."*

**Why routed and not fixed here:** (1) the studio-inference program's diff touches only `HttpRunnerDispatchClient.java` — confirmed by reading the full, current diff — so neither gap is anywhere near the code this story gates, and nothing in that fix could make either better or worse; (2) both are pre-existing production-code changes in files this story's charter (*"specifies nothing to build on this line"*) does not extend to; fixing either would mean this drafter proposing implementation work, which the mission explicitly forbids; (3) this epic's own established practice is to name and route findings like this rather than absorb them into the story that discovered them — e.g. `SEC-2` → 10.18, `O-9` → "the next story touching the internal callbacks" (`EPIC-10-RUN-LOG.md`'s open-escalations notes). AC-7 therefore requires **recording** the current (unfixed) state as a non-regression check, not requiring either gap closed.

### Why AC-5 needs a unit test and cannot be proven by the harness

Restated from the AC itself because it is easy to miss: `StudioCoRunIT`'s wiring (`@DynamicPropertySource`, `:149-160`) always supplies a real, matching runner base URL and identity token. That is not an oversight — it is what makes leg 0's attribution baseline sound (a red leg 2 can only mean one thing, because the alternatives are ruled out by construction). A harness built to also exercise "no runner configured" would need a second wiring mode, and at that point it stops being one attribution-clean harness and starts being two, with twice the surface for exactly the kind of vacuous-guard mistake this epic has repeatedly found (six catalogued shapes and counting, per this drafter's own memory of the epic's history). A plain unit test, constructing the client directly with no Spring context and no live socket, is the narrower and more falsifiable choice.

### On the wording "acceptance spec only — it specifies nothing to build on this line"

This story's Tasks section still lists concrete work items (a unit test, a documented mutation procedure). That is not a contradiction: the "nothing to build" boundary is about the **dispatch-identity fix itself** — the header, the property injection, the guard clause — not about the verification apparatus needed to gate someone else's fix. The precedent (10.19 AC-19(c), 10.34's whole existence) draws this same line: a story can require running things and recording results while proposing zero lines of the fix it verifies.
