## User Story

**As the** put-checks platform running a partitioned `execution_results` table,
**I want** an automated scheduler that creates future monthly partitions ahead of time, a startup bootstrap that ensures partitions exist on fresh deploys, and a health indicator that alerts 3 days before partition exhaustion,
**so that** INSERTs never fail due to a missing partition and ops gets early warning if the scheduler misfires.

---

## Acceptance Criteria

### Partition scheduler
- [ ] **AC-1:** `ExecutionResultsPartitionScheduler` bean with `@Scheduled(cron = "0 0 3 25 * ?")` (03:00 UTC on the 25th of each month). Creates partitions for the next 2 months using idempotent `CREATE TABLE IF NOT EXISTS ... PARTITION OF execution_results FOR VALUES FROM (...) TO (...)`.
- [ ] **AC-2:** `@SchedulerLock(name = "partitionCreator", lockAtMostFor = "10m", lockAtLeastFor = "30s")` prevents multi-pod races.
- [ ] **AC-3:** Partition naming convention: `execution_results_YYYY_MM` (e.g., `execution_results_2026_06`).
- [ ] **AC-4:** DDL executed via `JdbcTemplate.execute()` — not via JPA (DDL is not entity-managed).

### Startup bootstrap
- [ ] **AC-5:** `@EventListener(ApplicationReadyEvent.class)` runs the same partition-creation logic at boot. Ensures every freshly deployed environment has current + next 2 months of partitions.
- [ ] **AC-6:** Bootstrap is idempotent — running on an existing environment with all partitions already created produces no errors and no DDL.

### Health indicator
- [ ] **AC-7:** `/actuator/health/partitions` custom `HealthIndicator` returns `UP` if the partition covering `NOW() + 3 days` exists, `DOWN` otherwise. DOWN includes detail: `"missing_partition": "execution_results_2026_05"`.
- [ ] **AC-8:** Health check queries `pg_catalog.pg_class` + `pg_inherits` to verify partition existence — does not attempt DDL.

### Generalization
- [ ] **AC-9:** The same partition pattern is applied to `ui_test_executions` (monthly) and `report_executions` (quarterly). Use a generalized `PartitionManager` that accepts table name + partition interval. The scheduler calls `partitionManager.ensurePartitions("execution_results", MONTHLY)`, etc.
- [ ] **AC-10:** If `ui_test_executions` or `report_executions` tables don't exist yet (they're M4/M5), the partition manager skips them gracefully with a debug log. No error.

### Metrics + logging
- [ ] **AC-11:** Gauge `partition_future_months_available` — number of future monthly partitions that exist for `execution_results`.
- [ ] **AC-12:** Structured log line per partition created: `partition_created table=execution_results_2026_06 range=[2026-06-01, 2026-07-01)`.

### Tests
- [ ] **AC-13:** IT `PartitionSchedulerIT`: trigger scheduler → verify partitions for next 2 months exist in `pg_catalog`.
- [ ] **AC-14:** IT `PartitionBootstrapIT`: start app → verify current + next 2 months exist.
- [ ] **AC-15:** IT `PartitionHealthIT`: (a) with all partitions → UP, (b) drop the +3-day partition → DOWN with detail.
- [ ] **AC-16:** IT `PartitionIdempotencyIT`: run scheduler twice → no errors, same partitions.
- [ ] **AC-17:** JaCoCo coverage ≥ 80%.

## Implementation Notes
- **Partition DDL format:** `CREATE TABLE IF NOT EXISTS execution_results_2026_06 PARTITION OF execution_results FOR VALUES FROM ('2026-06-01') TO ('2026-07-01')`. The `IF NOT EXISTS` makes it idempotent.
- **Date math:** `YearMonth.now(ZoneOffset.UTC).plusMonths(offset)` for month calculation.
- **Health check query:** `SELECT c.relname FROM pg_class c JOIN pg_inherits i ON c.oid = i.inhrelid WHERE i.inhparent = 'execution_results'::regclass` lists all child partitions. Parse month from name and check coverage.
- **Generalized PartitionManager:** constructor takes `(JdbcTemplate, String tableName, PartitionInterval)`. `ensurePartitions(int lookaheadMonths)` creates missing partitions. `checkHealth(int lookaheadDays)` returns health status.
