## User Story

**As the** Checks squad running a browser runner that touches untrusted web pages and holds no database, vault, CSI or LLM credential,
**I want** a small internal HTTP service that validates artifacts without a browser, takes exclusive admission from the API before it launches anything, and reports cumulative progress and a retried terminal result,
**so that** a refused or ambiguous admission can never produce a browser side effect, a duplicate or lost delivery can never cause a step to run twice, and the component with the largest attack surface can never reach the database.

---

## Problem Statement

`studio-runner/` ships the validator, the trusted executor and the `BrowserAdapter`/`StepReporter` seams (10.2, 10.3), but has no process. `src/index.ts` states it plainly — "the HTTP server (10.6) … [is] added behind the same seams" — and the `Dockerfile` carries the matching note at line 51: the image has no entry point until this story. `StepReporter` exists as an interface with no implementation and a comment naming 10.6 as its supplier. ADR-001 §3 reserves `src/server/` and `src/reporting/` for exactly this work.

Architecture §5 makes four runner-side rules non-negotiable, and none of them exists yet:

| Required | Where |
|---|---|
| The runner reserves capacity and performs an authenticated admission CAS **through the API before launching Chromium**. A failed admission handshake never starts a browser. | §5.1.4 |
| Runner `429` means definite nonacceptance: no durable admission, no browser started. Timeouts, connection loss and 5xx are **ambiguous**: they are not permission to replay. Automatic POST retries are disabled in clients and proxies. | §5.1 closing paragraph |
| Reports carry execution/attempt/admission identities and an increasing `runnerSequence`; progress is a cumulative, bounded, redacted snapshot so a later update repairs a delivery gap. Terminal delivery is retried until acknowledged within a bounded window. | §5.3, §8.4 |
| `health` is liveness; `ready` is the ability to admit safely. Capacity saturation alone keeps readiness **true** and returns `429`; draining sets readiness false. | §8.4 |

And one rule defines the component's blast radius: **"The runner … has no platform user session or DB/vault/CSI/LLM credentials"** (§9.2). It receives per-run values, writes object-store objects and reports to the API. That is the whole list. A runner with a database connection would not be a layering smell; it would be a browser that renders untrusted pages holding a credential to the execution history.

This story is the runner's half of the §8.4 internal contract, against fake browser and storage adapters. Every persistence decision on the other side of those HTTP calls — the admission compare-and-set itself, progress and terminal persistence, snapshot-revision assignment, restart recovery, reapers and ambiguity resolution — is story 10.7.

## Acceptance Criteria

### Contract, service identity and destinations

- [x] **AC-1:** The runner's four internal routes — `POST /v1/validate`, `POST /v1/runs`, `GET /health`, `GET /ready` — and the request bodies it sends to the API's admission and progress routes conform to the `internal`-tagged section of `docs/specs/studio/openapi.yaml`. A contract test asserts conformance. That file is story 10.1's deliverable and is not a dependency of this story: if it has not merged, the test is recorded as **skipped, never passed**, naming 10.1 — the pattern 10.3 used for its `ED-05`-gated stage.
- [x] **AC-2a:** All four runner routes require a restricted service identity supplied as a configured credential. A request with a missing, blank, malformed or wrong credential is rejected `401`/`403` before any handler work, before any validation and before any slot reservation; the body carries a code and no job detail. Comparison is constant-time. Verified here against a configured stub credential.
- [ ] **AC-2b:** *(Deferred — `ED-02`)* The same routes verified against real platform-issued service identity through the real ingress. Verified in **story 10.18** (hardened staging deployment), which `ED-02` gates. No part of this story depends on the backend's current `BffSessionAuthenticationFilter` bypass.
- [x] **AC-3:** The callback destination is deployment configuration only. A callback URL, host or port present in a job body is ignored and the job is rejected with a code; a test submits a job carrying an attacker-controlled callback URL and asserts no request leaves for it. No credential appears in any URL or query string. The runner's only configured outbound destinations are the callback API, the object store (faked here) and the target page through Playwright.

### `POST /v1/validate`

- [x] **AC-4:** `POST /v1/validate` is a browser-free wrapper around `validateArtifact` from 10.2 with bounded work: bounded request body, artifact and step counts taken from the existing `DEFAULT_BOUNDS`, and a wall-clock bound on the call. It returns per-step diagnostics that are bounded and redacted, launches nothing, creates no scratch state, and **cannot reserve a capacity slot** — a test asserts that a validate call during a fully saturated pool still answers successfully and within its bound.
- [x] **AC-5:** An oversized, malformed or non-JSON validate body returns `413`/`400` with a code and no stack trace, no file path and no artifact echo.

### `POST /v1/runs` — order of operations and admission

- [x] **AC-6:** `POST /v1/runs` executes in this order and no other: validate the job envelope (immutable identity fields, artifact, configuration, deadlines) → reserve a capacity slot → complete the API admission CAS → return `202`. **No browser, no child process, no scratch directory and no evidence key exists before the CAS returns success.** A test using the fake browser and storage adapters asserts zero adapter calls for every non-success admission outcome (`409`, `401`, `403`, timeout, transport loss, 5xx).
- [x] **AC-7:** Admission identity belongs to this runner instance and this run: `runnerInstanceId` is stable for the process, `admissionId` is generated fresh per run, and the pair is never reused across runs. The runner never retries an admission with a **new** `admissionId` for the same `attemptId` — doing so is the one way a single runner could compete with itself for an attempt it may already own.
- [x] **AC-7b:** **Competing runner instances cannot both own an attempt** (Epic 10 §10.6 acceptance bullet 2). Two runner service instances are started in one test process with distinct `runnerInstanceId`s against a single fake admission endpoint that implements a single-winner compare-and-set, and both submit the **same** `attemptId` concurrently, with their requests interleaved rather than sequenced. Exactly one receives success and launches the fake browser; the loser receives `409`, launches nothing, creates no scratch and no evidence key, releases its slot, and does **not** re-attempt admission under any identity. The runner-side property under test is that the runner *obeys* the CAS verdict and never acts on a non-success — the CAS itself is 10.7's; the fake endpoint stands in for it here, exactly as the fake browser and storage adapters do.
- [x] **AC-8:** A definite admission refusal — `409` (competing or expired admission), `401` or `403` — stops the run immediately: no browser, slot released, scratch cleared, and a `503`/`409` response to the caller that is explicit about non-acceptance. The runner does not re-attempt admission under any of these.
- [x] **AC-9:** An **ambiguous** admission outcome — HTTP timeout (10 s starting value, §8.5), connection loss, or any 5xx — is not permission to replay. The runner does not resend the admission, does not launch a browser, releases the slot, clears scratch, and records the ambiguity in a structured audit log line plus a counter metric. Automatic POST retry is disabled in whatever HTTP client is used, and a test asserts exactly one admission request was issued for each of the three ambiguous cases. A **`307`/`308` redirect response is a fourth case**: the runner must not re-issue the POST to the redirect target — a followed redirect is a second admission request wearing a different name, and the same "exactly one request issued" assertion covers it.
- [x] **AC-10:** Capacity saturation (initial `POOL_SIZE=1`, §5.2) returns `429` with `Retry-After` and is a **definite non-acceptance**: no slot held, no admission request issued, no scratch created, no browser started, nothing durable anywhere. A test asserts the admission client was never called on this path — 429 must be decidable before the runner talks to the API at all. The capacity decision and the reservation are **one atomic acquire**, not a read followed by a write: the guard is intrinsic to the operation (story 10.4's QA lesson) and there is no `await` — no body parse, no validation, no clock read — between observing free capacity and holding the slot, because every `await` in a single-threaded server is a window in which a second request can observe the same free slot.

### `GET /health`, `GET /ready` and drain

- [x] **AC-11:** `GET /health` reports liveness only and stays `200` while the pool is saturated and while draining. `GET /ready` reports the ability to admit safely: saturated capacity alone keeps readiness **true** (and `/v1/runs` answers `429`); draining sets readiness **false**. Asserted as four distinct states, not as one combined endpoint.
- [x] **AC-12:** `SIGTERM` enters draining: readiness goes false, new `/v1/runs` is rejected `503`, and an already-admitted run **finishes and reports**. `src/main.ts` wires configuration, server start and the drain path, and the process exits only after the in-flight run has delivered its terminal report or its deadline has passed — never by abandoning an admitted attempt silently. Scratch is cleared on the drain path and at startup.

### Reporting — what the runner sends

- [x] **AC-13:** Every report carries `executionId`, `attemptId`, `admissionId`, report kind (`STARTED | PROGRESS | FINAL`), timestamps, `runnerSequence`, the **cumulative** step list and bounded logs, the actual runtime versions read from `runtime-versions.json`, and on `FINAL` the outcome/error and the evidence state. `runnerSequence` is strictly increasing within an attempt, starts fresh for a new attempt, and is never reused or decremented. Progress is a full current-state snapshot, not a delta, so a later report repairs a delivery gap without replaying anything.
- [x] **AC-14a:** `STARTED` is sent only once the browser has actually started — not when admission succeeds and not when an HTTP call begins. Verified against the fake browser adapter from 10.2: a run whose adapter never reports a launch sends no `STARTED`, and the `STARTED` sequence number is always lower than any step's.
- [ ] **AC-14b:** *(Deferred to **story 10.12**, Chromium execution and native video)* The same admission → real browser launch → `STARTED` sequence driven by real Chromium. 10.12 owns the real Playwright adapter and `depends_on: ["10.6"]`, so this is a scope deferral, not an external block: per the manifest's `ED-05` `gate_note`, 10.12 may run on a developer machine. `ED-05` (internal Playwright image) gates only the *in-image* form of this verification, which lands with 10.18/10.19 — the same division 10.3 recorded for its own `ED-05` stage. This story installs and launches no browser.
- [x] **AC-15:** The `StepReporter` implementation that 10.2 left as a seam feeds the report client: `stepStarted`/`stepFinished` update the cumulative snapshot, and the executor's existing per-step outcomes (`PASSED | FAILED | SKIPPED`, null timings for skipped steps) reach the wire unchanged. Reporting is asynchronous to execution — a slow or failing callback must not block, delay or alter a step.
- [x] **AC-16:** Progress delivery is best-effort and never re-runs work: a failed `STARTED`/`PROGRESS` POST is dropped, the next cumulative snapshot carries the missed state, and a test asserts that a run whose first two progress deliveries fail still reports every step correctly in the third, with no step executed twice.
- [x] **AC-17:** Terminal delivery is retried idempotently within a bounded delivery window: the retried `FINAL` is byte-identical — same `attemptId`, same `admissionId`, same `runnerSequence`, same body — so the API can recognise it as a duplicate. **"Byte-identical" is literal and is asserted on the serialized request body, not on the object that produced it:** the `FINAL` body is serialized once before the first send and the exact same bytes are re-sent on every attempt. **No field is recomputed per attempt — including any timestamp.** The AC-13 timestamps in a `FINAL` describe the run, not the delivery; if a per-delivery timestamp or attempt counter is needed it travels as a header, never in the body. A test captures the raw bytes of every delivery attempt and asserts they are equal. Retries are bounded in count and total time, use jitter, and stop on acknowledgement or at the deadline. The runner **never** increments the sequence or mutates the body on a retry.
- [x] **AC-18:** A `409` from the API on any report — ownership lost, superseded attempt, or the execution already finalized — stops reporting for that run immediately, releases the slot and scratch, and never escalates to a retry, a new admission or a relaunch. The outcome is recorded in the runner's structured audit log plus a counter metric and nowhere else; there is no durable runner-side store, and the durable result manifest follows in **10.14**.

### Bounds, redaction and logging

- [x] **AC-19:** The runner bounds every outbound payload before sending it: maximum step count, maximum log entries, maximum log-entry length and maximum body size, all from one configuration source (§8.5). When the retained-log cap is reached the snapshot sets `logsTruncated = true` and the drop policy — oldest entries dropped, newest retained — is asserted by a test, not left implicit. The runner never emits a body that the API would have to reject for size.
- [x] **AC-20:** Secret canary: a job carrying a known canary through `resolvedVars`/`resolvedSecrets` produces reports, structured log lines, diagnostics and error messages in which the canary appears in **no** form — plain, URL-encoded, double-encoded and base64 variants — using `createRedactor` from 10.2, whose variant set already covers exactly these shapes (plain, `encodeURIComponent`, `encodeURI`, double-encoded, and four base64 forms). Request logging never records job values, resolved values or artifact source text; it records only the identity fields from AC-13. The redactor is applied on the outbound path, so a value cannot escape by way of an unanticipated message field. **The assertion is made on the bytes that leave** — the serialized request body handed to the HTTP client and the string handed to the log sink — not on the in-memory objects before serialization, because a field added later is only caught by inspecting the finished payload.
- [x] **AC-21:** Ephemeral values never persist: `resolvedVars`/`resolvedSecrets` are held in memory for the run, are not written to scratch, are not placed in any retry buffer or queued report body, and are cleared on every exit path including the drain and error paths. A test inspects the scratch directory and the pending-report buffer after a failed run and finds no job value.

### Isolation

- [x] **AC-22:** **No DB, no vault, no CSI, no LLM.** The runner has no database driver, no vault client, no platform identity client and no LLM gateway client anywhere in its dependency tree, and holds no credential for any of them. The gate is **fail-closed, not a denylist** — a denylist only fails for a driver somebody predicted, and the whole point is the one nobody predicted. Three build-gated parts, all of which must fail if such a dependency is introduced:
  - **(a) Allowlist over the resolved runtime dependency closure.** `test/isolation.test.ts` reads `package.json` `dependencies` plus the lockfile's transitive production closure and asserts it equals an explicit, enumerated allowlist held in the test. Today that closure is `playwright` and `typescript`; the HTTP server choice, if any, is added to the allowlist in the same commit with its justification. **Any** package not on the list fails the test, whatever it is. This is the part that actually catches the unanticipated case.
  - **(b) Named-module lint rules,** added to `eslint.boundary-rules.js` — the single source of truth that `eslint.config.js` consumes and `test/lint-boundary.test.ts` asserts against deliberate fixtures under `fixtures/lint/**`; the existing `vm`/`worker_threads`/`child_process` entries are the pattern to follow. Extend `FORBIDDEN_MODULES` with the database, vault and gateway client names, and add a fixture per entry so the rules are proven to fire rather than assumed to. This part is a fast, readable denylist layered on top of (a), not a substitute for it. *(The drafted text located these rules in `eslint.config.js`; they live in `eslint.boundary-rules.js`.)*
  - **(c) Configuration surface.** The config loader enumerates the keys it accepts and rejects anything else at startup; there is no database URL, vault address, CSI endpoint or LLM gateway key among them, and a test asserts a config carrying one fails to start rather than being silently ignored. A credential the process never reads cannot leak.

  Note the boundary of what (a)–(c) can prove: they prevent the runner from *linking* a client, not from reaching a database over plain HTTP through a dependency it already has. **AC-3 is the complement** — outbound destinations are a configured allowlist (callback API, object store, target page) and nothing else — and the two criteria must be read together. Runtime dependencies stay minimal and exact-pinned per ADR-001 §5; the HTTP server choice is the only addition this story may make, and `npm run check:pins` covers the pinning.

### Tests

- [x] **AC-23:** Concurrency is proven by holding real state open and by **interleaving**, not by sequential happy-path calls — the rigour story 10.4's QA round established, translated to a component with no database. Where 10.4 held a row lock open, this story holds the capacity slot and the in-flight admission open. Sequential calls that merely *happen* to arrive one after another prove nothing here and do not satisfy this criterion. At minimum:
  - With the single slot held by an in-flight run, a second `/v1/runs` returns `429` without issuing an admission.
  - **Interleaved acquire:** *N* concurrent `/v1/runs` requests whose bodies arrive interleaved — the requests are in flight simultaneously and the test controls the interleaving rather than hoping for it — yield exactly one admission request issued and exactly one `202`; every other request gets `429` and reaches no adapter. This is the falsification test for AC-10's atomic acquire: a read-then-write implementation must fail it.
  - **Two instances, one attempt:** the AC-7b race — two runner instances, one fake single-winner CAS, the same `attemptId`, concurrent — exactly one browser launch.
  - `/v1/validate` stays responsive while the slot is held (AC-4).
  - `SIGTERM` during the in-flight run drains without abandoning it.
  - A `FINAL` retry racing the drain deadline resolves once, and the bytes of each delivery attempt are compared (AC-17).
  - An ambiguous admission racing `SIGTERM` still starts no browser and still issues exactly one admission request.
- [x] **AC-24:** Gates green: `npm run type-check`, `npm run lint`, `npm test` and `npm run check:pins` exit 0 from a clean `npm ci`, with coverage on `src/server/**` and `src/reporting/**` at the thresholds already enforced for `src/validator/**` and `src/executor/**`. `npm run test:fixtures` is unaffected. No new runtime dependency beyond the exact-pinned HTTP server choice, justified in the Dev Agent Record.

## Implementation Notes

- **Nothing here reaches a database.** AC-22 is the story's defining constraint, not a nice-to-have: this is the process that renders untrusted pages. Every criterion above was rechecked against "no DB, no vault, no CSI, no LLM"; any criterion that implied persistence on the runner's side of the wire was moved to 10.7.
- **The contract file is 10.1's.** The runner is coded against the frozen `internal` section of `docs/specs/studio/openapi.yaml`, but the manifest correctly lists `depends_on: ["10.2"]` only — nothing here needs 10.1 to *merge* to be built or tested. AC-1 handles the ordering honestly by recording the contract test as skipped rather than passed if the file is absent.
- **HTTP server library.** ADR-001 §5 leaves the choice to this story and requires it be minimal and pinned. `node:http` covers the four-route surface with no middleware ecosystem, zero new runtime dependency and no supply-chain surface on a security boundary; if a library is chosen instead, exact-pin it and justify it in the Dev Agent Record.
- **Two retry policies, deliberately opposite.** The admission call is never retried (AC-9): an ambiguous outcome may already have granted admission, and a second attempt risks a second browser. The terminal report *is* retried (AC-17), byte-identical, because the API side is idempotent by attempt and sequence. Keep both policies visible in the code and named in the tests so a future change cannot collapse them into one client default. Whatever HTTP client is used must have automatic retries explicitly disabled.
- **`runnerSequence` is per attempt.** It starts fresh for each attempt and is never reused. The runner holds no cross-run state, so this is a per-run counter, not a persisted one.
- **Post-finalization and ambiguity records stay runner-side and non-durable.** A `409` on a report, or an ambiguous admission, is recorded as a structured audit log line plus a counter metric — no table, no column, no local file. The durable record of a terminal result is the object-store manifest, which arrives in 10.14.
- **Starting values (§8.5)** — 10 s admission HTTP timeout, 30 s admitted-start deadline, 30 s default step timeout, 120 s total browser runtime, `POOL_SIZE=1`. These are starting values to be tuned against staging measurements, not commitments. Deadline *enforcement* and process-tree killing are 10.13; this story only honours the deadlines it is given.
- **`Dockerfile` line 51** explicitly defers the entry point to this story; adding it is expected here and is not scope creep.

### HTTP server choice — `node:http`, no new dependency

ADR-001 §5 allows this story one HTTP server library and requires it to be minimal and pinned. It
took **none**. The route surface is four routes with no middleware, no content negotiation and no
templating; `node:http` covers it with zero production dependencies, which keeps the resolved
closure at `playwright`, `playwright-core` and `typescript` — exactly what AC-22a asserts. A
framework would have put a transitive tree of unaudited packages inside the one process that
renders untrusted web pages, to save writing a `switch` on method and path. The outbound client is
Node's built-in `fetch` for the same reason, with `redirect: 'manual'` and no retry loop.

`playwright-core` was added to the AC-22a allowlist with its justification: it is `playwright`'s own
engine, resolved transitively at the same exact version by the same pin. The story text named the
closure as "`playwright` and `typescript`", which is the *declared* set; the *resolved* closure the
criterion actually gates on has three entries.

### Design decisions

- **Ordering is observable, not merely absent** (@po's AC-6 note). The fake HTTP client, fake
  scratch store and fake browser launcher all write into one shared event log, so the assertions
  compare the exact order in which the boundaries were crossed. A reordering that moved scratch
  creation ahead of the CAS changes the array and fails, even though the same calls happened.
- **The capacity guard is intrinsic.** `tryAcquire` observes and holds in one synchronous
  statement. Everything from `JSON.parse` through envelope validation, artifact validation and the
  acquire runs without a single `await`.
- **Progress deliveries are detached but serialized.** Fanning them out let a second report leave
  after the API had already answered `409` to the first, which made AC-18's "stops reporting
  immediately" only approximately true. Chaining keeps steps unblocked (AC-15) while making the
  stop exact.
- **`STARTED` is driven by the launcher resolving**, not by admission or by a call beginning, so a
  run whose launcher never reports a launch sends no `STARTED` at all.
- **`src/main.ts` ships a launcher that refuses** with `BROWSER_LAUNCH_UNAVAILABLE`. That is the
  honest state of the component: 10.12 owns the real adapter, so an admitted run reports a terminal
  `ERROR` rather than appearing to succeed.

### Falsification — the guards were turned off and the tests failed

AC-23 is only worth its length if the assertions are sensitive to the guards. Two neutralisations,
both through seams that already existed, with no production code made test-aware:

| Guard | Neutralised by | Result with the guard off |
|---|---|---|
| Atomic acquire (AC-10) | A `CapacityPool` that observes, yields, then holds | Eight concurrent submits all get `202`; eight admission requests issued |
| Obeying the CAS verdict (AC-7b) | Wrapping the transport so `409` returns as `200` | Both runner instances launch for one attempt |

The HTTP interleaved case drives eight simultaneous requests with their bodies delivered in
interleaved halves. Because Node spreads eight loopback requests across several event-loop turns,
a second form was added that calls `submit` eight times in **one synchronous burst** — that is the
form which genuinely races two acquires inside a single turn, and it is the one the falsification
above breaks.

### Self-critique caught one functional gap

The retained-log buffer, its cap and its drop policy were implemented and tested, but **nothing
populated it during a run** — so `logsTruncated` was structurally unreachable in a real report and
AC-19's drop-policy assertion only exercised the data structure. The `StepReporter` now appends the
browser start, each step start and outcome (with the executor's already-redacted failure text) and
the run result, so the bound, the truncation flag and the newest-wins drop policy are exercised
end to end by a real run rather than only by a unit test on the ring.

### Two things found while building

- `test/no-dynamic-evaluation.test.ts`'s async-IIFE scan fired on `then(async () => …)` in the
  emitted output. The guard is deliberately blunt — an async IIFE is one shape generated source
  could be evaluated through — so the code was written around it with a named constant rather than
  the scan loosened. It then fired a second time on a doc comment quoting the shape; the comment
  was reworded. Both are correct behaviour from the guard.
- The 401 path answers before reading the body, which is what AC-2a requires, and Node then closes
  the connection under a caller that is still uploading. Fixed in the test client by sending the
  request in one write rather than by making the server read a body it has already refused.
