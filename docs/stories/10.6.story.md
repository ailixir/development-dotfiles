## User Story

**As the** Checks squad operating Studio across three API replicas and a separate browser runner,
**I want** one internal contract where a runner takes exclusive, durable ownership of an attempt before anything launches, and then reports cumulative progress and a terminal result that the API persists before acknowledging,
**so that** no two runners can ever own the same attempt, a duplicate, late or out-of-order delivery cannot corrupt or resurrect an execution, and a restart anywhere in the chain produces a truthful result rather than a repeated browser side effect.

---

## Problem Statement

Nothing in the repository connects a runner to the API. `studio-runner/` ships the validator, the trusted executor and the `BrowserAdapter`/`StepReporter` seams (10.2, 10.3), and `src/index.ts` states plainly that "the HTTP server (10.6)" is absent; the `Dockerfile` has no entry point for the same reason. On the backend, `StudioController` exposes only public `/api/v1/studio` routes, and `POST /tests/{id}/execute` is a placeholder. There is no internal route, no admission, no callback handler.

Architecture §5 makes the missing piece the safety boundary of the whole epic:

| Required (architecture §5, §8.4) | Today |
|---|---|
| The runner performs an authenticated admission CAS through the API **before launching Chromium**; only one `(runnerInstanceId, admissionId)` can own an attempt; a failed handshake never starts a browser (§5.1.4) | No admission of any kind |
| Reports carry `executionId`, `attemptId`, `admissionId` and an increasing `runnerSequence`; progress is a cumulative, bounded, redacted snapshot; the API verifies ownership and sequence, applies changes **conditionally**, and assigns its own snapshot `revision` (§5.3, §8.4) | No reporting contract; the `StepReporter` interface has no implementation |
| The API acknowledges **only after commit**; terminal delivery is retried until acknowledged within a bounded window; a delayed report cannot overwrite a finalized execution or another admission (§5.3) | — |
| `RUNNING` is written only on an authenticated browser-start report, not when an HTTP call starts (§5.1.5) | — |
| Internal routes require restricted service identity and are not exposed through public ingress (§8.4, §9.1) | `SecurityConfig` authenticates `/api/**` and ends with `anyRequest().permitAll()`, so a new `/internal/**` route would be **publicly reachable by default** |
| Ambiguous attempts are never replayed automatically (epic goal; §5.1 closing paragraph) | — |
| Check outcome stays separate from evidence state (§6.1) | — |

The SSE assessment adds the deployment constraint that makes this a persistence problem rather than a messaging one: production runs three API replicas scaling to six, so a runner callback and a browser subscription reach different pods. An in-memory emitter or admission registry cannot distribute progress correctly; PostgreSQL is the only authority.

Story 10.1 owns `V13` (the dispatch ledger) and `V14` (execution history v2). **This story creates no migration.** It is the code that operates them.

## Acceptance Criteria

### Frozen internal contract and service identity

- [ ] **AC-1:** The two API routes `POST /internal/studio/executions/{id}/admission` and `POST /internal/studio/executions/{id}/progress`, and the two runner routes `POST /v1/validate` and `POST /v1/runs` plus `GET /health` and `GET /ready`, are implemented exactly as the `internal`-tagged section of `docs/specs/studio/openapi.yaml` (10.1, AC-1) describes them. A contract test on each side diffs the implemented shapes against that file and fails on drift. Neither side defines a field the contract does not contain.
- [ ] **AC-2a:** Both API internal routes and both runner internal routes require a restricted service identity supplied as a configured credential (deployment configuration, never a job field). A request with a missing, blank, malformed or wrong credential is rejected `401`/`403` before any handler work, before any ledger read, and before any slot reservation; the rejection body carries a code and no execution detail. Credential comparison is constant-time. Verified in this story against a configured stub credential.
- [ ] **AC-2b:** *(Deferred — `ED-02`)* The same routes verified against real platform-issued service identity through the real ingress, with `BffSessionAuthenticationFilter.isCoreServiceBypassed()` no longer returning a hardcoded `true`. Verified in **story 10.18** (hardened staging deployment), which `ED-02` gates. This story neither removes nor depends on the bypass; it must make the bypass irrelevant to `/internal/**` by construction (AC-3).
- [ ] **AC-3:** `/internal/**` is served by its own Spring Security filter chain with a higher-precedence `securityMatcher`, whose terminal rule is `denyAll()`. `SecurityConfig`'s existing chain ends in `anyRequest().permitAll()`, so an internal route added without this chain would be anonymously reachable; a test asserts that an unauthenticated `POST` to both internal routes is rejected, and a second test asserts that the BFF session filter, the idempotency filter and the rate-limit filter do **not** run for `/internal/**`. The runner's callback base URL is read from deployment configuration only; a URL supplied in a job body is ignored and the attempt is rejected.

### Runner admission, capacity and validation

- [ ] **AC-4:** `POST /v1/runs` executes in this order and no other: validate the job envelope (identity fields, artifact, configuration, deadlines) → reserve a capacity slot → complete the API admission CAS → return `202`. No browser, no child process, no scratch directory and no evidence key is created before the CAS returns success. A test with a fake browser adapter asserts the adapter received zero calls for every non-success admission outcome (`409`, `401`, `403`, timeout, 5xx).
- [ ] **AC-5:** Capacity saturation (initial `POOL_SIZE=1`, per §5.2) returns `429` with `Retry-After` and is a **definite non-acceptance**: no slot is held, no admission was attempted, no durable state exists and no browser started. `POST /v1/validate` continues to answer within its bound while the pool is saturated — a test issues a validate call during a held slot and asserts a successful, timely response.
- [ ] **AC-6:** `GET /health` reports liveness only. `GET /ready` reports the ability to admit safely: saturated capacity alone keeps readiness **true** (and `/v1/runs` answers `429`), while draining — entered on `SIGTERM` — sets readiness **false**, rejects new `/v1/runs` with `503`, and lets an already-admitted run finish and report. `src/main.ts` wires configuration, server start and the drain path, and exits only after the in-flight run has reported or its deadline passed.
- [ ] **AC-7:** `POST /v1/validate` is a browser-free wrapper around `validateArtifact` from 10.2 with bounded work: bounded request body, bounded artifact/step counts taken from the existing `DEFAULT_BOUNDS`, and a wall-clock bound on the call. It returns per-step diagnostics that are bounded and redacted, launches nothing, and cannot be made to reserve a capacity slot. An oversized or malformed body returns `413`/`400` with a code, never a stack trace.

### Admission CAS (API side, on 10.1's `V13` ledger)

- [ ] **AC-8:** Admission is a **single conditional `UPDATE ... WHERE`** on `studio_dispatch_ledger` that claims `admission_id` and `runner_instance_id` for the supplied `attempt_id`, and its affected-row count is the decision. The guard is intrinsic to the statement — no read-then-write, and no companion write by another class is required for correctness (the rule story 10.4's QA round established). This story does **not** add or tighten the ledger `state` CHECK constraint; that is deliberately deferred to 10.7 so the dispatcher can finalize its own state machine.
- [ ] **AC-9:** A duplicate admission carrying the *identical* `(attemptId, admissionId, runnerInstanceId)` is idempotent: the same success response, no ledger mutation, no new snapshot revision, no additional audit row beyond a de-duplication counter. Proven by issuing the same request twice and asserting the persisted row is byte-identical to after the first.
- [ ] **AC-10:** A competing admission — same `attemptId` with a different `admissionId` or `runnerInstanceId`, or an `attemptId` the ledger has superseded — is rejected `409` with a code. The ledger retains the first owner unchanged. Two runner instances cannot both own an attempt.
- [ ] **AC-11:** Admission for an execution that is already terminal, or whose start deadline has passed, is rejected `409` and never resurrects it. The ledger and the history row are unchanged, and the rejecting response tells the runner definitively not to launch.

### Progress and terminal reporting

- [ ] **AC-12:** Every report carries `executionId`, `attemptId`, `admissionId`, report kind (`STARTED | PROGRESS | FINAL`), `runnerSequence`, timestamps, the **cumulative** step list and bounded logs, actual runtime versions from `runtime-versions.json`, and outcome/error plus evidence state on `FINAL`. `runnerSequence` is strictly increasing within an attempt and starts again for a new attempt. Progress is a full current-state snapshot, not a delta, so a later report repairs a delivery gap without replay.
- [ ] **AC-13:** The API persists an accepted report and **then** acknowledges. The handler commits before writing its response; a commit failure returns 5xx and the runner retries. A test injects a failure after commit but before the response is written and asserts the retried delivery is absorbed by AC-14 rather than duplicating state.
- [ ] **AC-14:** A duplicate delivery of the same `(attemptId, runnerSequence)` is applied at most once: logs are not duplicated, step results are not re-appended, the API snapshot revision does not advance, and the response is the same acknowledgement. Asserted on log array length and on `snapshot_revision`, not only on the response code.
- [ ] **AC-15:** A report whose `runnerSequence` is not greater than `last_runner_sequence` for the current attempt, or whose `attemptId`/`admissionId` does not own the execution, is rejected without being applied and recorded for investigation. This explicitly covers **a late report from a superseded attempt**: it must not regress status, step results, logs, evidence state or the last-run projection. A report arriving after the execution is finalized is likewise recorded and changes nothing (§5.3).
- [ ] **AC-16a:** Status becomes `RUNNING` only when an authenticated browser-start report commits — never when an HTTP call begins, and never on admission alone. Verified end to end with the fake browser adapter from 10.2: admission alone leaves the execution `PENDING`; the `STARTED` report moves it to `RUNNING` and sets `browser_started_at` while leaving the partition key `started_at` untouched.
- [ ] **AC-16b:** *(Deferred — `ED-05`)* The same admission → browser-start → `RUNNING` sequence driven by real Chromium in the internal Playwright image. Verified in **story 10.12** (Chromium execution and native video). No browser is installed or launched by this story.

### Bounds, redaction and evidence

- [ ] **AC-17:** Callback bodies are bounded: maximum body size, maximum step count, maximum log entries and maximum log-entry length, all from one configuration source (§8.5). Exceeding a bound returns `413` with a code and persists nothing. Retained logs are capped; when the cap is reached the snapshot carries `logsTruncated = true` and the drop policy (oldest entries dropped, newest retained) is asserted by a test, not left implicit. A hostile or runaway runner cannot bloat a row.
- [ ] **AC-18:** Secret-canary test: a job carrying a known canary value through `resolvedVars`/`resolvedSecrets` produces reports, persisted columns, audit entries and request logs in which the canary appears in **no** form. The runner scrubs via `createRedactor` from 10.2 (plain, URL-encoded, double-encoded and base64 variants) before any outbound write; the API additionally never logs a report body. Request logging never exposes job values.
- [ ] **AC-19:** Check outcome and evidence state stay separate (§6.1). A `FINAL` report with `PASSED` and a failed upload settles the outcome as `PASSED` and evidence as `FAILED`; an evidence failure never overwrites a known assertion outcome. `streamComplete` is set only once outcome **and** evidence disposition are settled, so a terminal outcome alone does not close the stream. A fake storage adapter stands in for Sonic; the durable manifest is 10.14.

### Durability, restart and ambiguity

- [ ] **AC-20:** No in-memory registry participates in correctness. An admission and a progress report committed through API instance A are fully visible to instance B — asserted with two Spring contexts against one database, the pattern 10.1's `StudioIdempotencyIT` establishes. Restarting an instance loses nothing that was acknowledged.
- [ ] **AC-21:** API restart mid-execution: the runner's bounded terminal-delivery retry redelivers after the API returns, and the result lands **exactly once**. A restart between commit and acknowledgement produces no duplicate logs, no second terminal state and no second snapshot revision. A restart before any admission committed leaves an execution the reaper can classify, not a half-admitted one.
- [ ] **AC-22:** Ambiguous attempts are **never replayed automatically**. This story exposes the reconciliation entry point a reaper calls (`10.7` owns scheduling the sweeps and deriving the deadlines): given an attempt with no acknowledged terminal report, it classifies the outcome from persisted admission/progress state and finalizes with an explicit error code (`DISPATCH_UNKNOWN` where the send outcome is ambiguous, `START_TIMEOUT` where admission committed but no browser start arrived, `STALE` beyond the run deadline — the codes 10.1's DTO already carries). It issues no new dispatch, no new admission and no browser work under any input. A test asserts the ambiguous path calls nothing that could produce a second effect.

### Tests

- [ ] **AC-23:** Concurrency is proven by **interleaving** tests that hold a transaction or row lock open, not by sequential happy-path calls — the rigour story 10.4 added in its QA round (five such cases). At minimum: two concurrent admissions for one attempt; an admission racing a finalization; two concurrent reports at the same `runnerSequence`; a superseded-attempt report racing the current attempt's report; a reconciliation racing a late terminal delivery.
- [ ] **AC-24:** Gates green. Backend: JaCoCo ≥ 80% on the classes this story adds or modifies; `./gradlew spotlessCheck checkstyleMain checkstyleTest spotbugsMain` pass and no **new** `./gradlew check` failure appears beyond the 23 pre-existing baseline failures recorded in story 10.4 (`ED-02`). Runner: `npm run type-check`, `npm run lint`, `npm test` and `npm run check:pins` exit 0, with coverage on `src/server/**` and `src/reporting/**` at the thresholds already enforced for `src/validator/**` and `src/executor/**`.

## Implementation Notes

### What this story needs from 10.1 (resolve at validation)

This story consumes, and does not create, 10.1's schema. Specifically it requires:

- **`V13` `studio_dispatch_ledger`:** `execution_id`, `execution_accepted_at` (partition locator), `attempt_id`, `admission_id`, `runner_instance_id`, `state`, `start_deadline_at`, `run_deadline_at`, `last_runner_sequence`, `snapshot_revision`. All present in 10.1 AC-6.
- **`V14` `ui_test_executions`:** status `PENDING|RUNNING`, `browser_started_at`, `error_code`, `step_results`, `logs`, `logs_truncated`, `video_status`/`video_error`/`video_partial`, `runtime_versions`, `snapshot_revision`, and the `(id, started_at)`-aware repository from 10.1 AC-13. All present in 10.1 AC-7.
- **The typed snapshot DTO** (10.1 AC-3) and the `internal`-tagged section of `docs/specs/studio/openapi.yaml` (10.1 AC-1). This story writes no DTO of its own for the public snapshot.

Three gaps are **not** resolved by 10.1 as drafted, and are raised here rather than fixed by an unassigned migration:

1. **Which `snapshot_revision` is authoritative?** 10.1 puts the column on both the ledger (AC-6) and the history row (AC-7). The progress handler must increment exactly one, and the snapshot DTO must read the same one. Needs a one-line decision at validation; no schema change if the answer is "history row, ledger column is the dispatcher's".
2. **Where is a post-finalization report recorded?** §5.3 requires that a late report "is recorded for investigation". This story proposes a structured audit log entry plus a counter metric and **no** new table or column. If the PO wants that record durable and queryable, the column belongs in 10.1's `V13`, not in a migration invented here.
3. **`last_runner_sequence` is per attempt.** The ledger carries one `attempt_id` per row, so the counter resets naturally when a new attempt claims the row — but that reset must be part of the same statement that claims the attempt, or a superseded attempt's high sequence will suppress the new attempt's first report.

### Design constraints carried in

- **Admission CAS is one statement.** `UPDATE studio_dispatch_ledger SET admission_id = ?, runner_instance_id = ?, ... WHERE execution_id = ? AND attempt_id = ? AND (admission_id IS NULL OR (admission_id = ? AND runner_instance_id = ?)) AND start_deadline_at > now()` — affected rows decide. The `IS NULL OR identical` shape gives AC-9 idempotence and AC-10 exclusivity in the same guard. Do not read the row first and branch in Java; 10.4's QA round showed that a guard split across two statements is not a guard.
- **Do not pre-empt 10.7's `state` CHECK.** Write the state values 10.1 lists as provisional; add no constraint.
- **`/internal/**` must be denied by default.** A new chain with `securityMatcher("/internal/**")` and `@Order` above the existing `filterChain` bean. Without it, `anyRequest().permitAll()` applies and the routes are open — this is the single highest-risk line in the story.
- **HTTP server library.** ADR-001 §5 leaves the choice to this story and requires it be minimal and pinned. `node:http` satisfies the routing surface here (six routes, no middleware ecosystem needed) with zero new runtime dependency and no supply-chain surface on a security boundary; if a library is chosen instead, it must be exact-pinned and justified in the Dev Agent Record.
- **Bounded terminal retry, never a blind POST retry.** §5.1: a runner `429` is definite and retryable by the *dispatcher*; a 5xx or transport loss on `POST /v1/runs` is ambiguous and must not be resent. The runner's own terminal *report* delivery is the opposite case and does retry to the API until acknowledged, within the bounded delivery window, because the API side is idempotent by AC-14. Keep these two retry policies visibly distinct in the code and in the tests.
- **Starting values (§8.5):** 10 s admission HTTP timeout, 600 s pending SLA, 30 s admitted-start deadline, 30 s default step timeout and 120 s total browser runtime. These are starting values to be tuned against staging, not measured commitments.
- **Baseline build state.** 23 integration tests fail on this branch before any change (`ED-02`, recorded in 10.4's QA results). AC-24 holds this story to "no new failures", not to a green `./gradlew check` on a repository that does not start green.
