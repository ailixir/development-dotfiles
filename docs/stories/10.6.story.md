## User Story

**As the** Checks squad running a browser runner that touches untrusted web pages and holds no database, vault, CSI or LLM credential,
**I want** a small internal HTTP service that validates artifacts without a browser, takes exclusive admission from the API before it launches anything, and reports cumulative progress and a retried terminal result,
**so that** a refused or ambiguous admission can never produce a browser side effect, a duplicate or lost delivery can never cause a step to run twice, and the component with the largest attack surface can never reach the database.

---

## Problem Statement

`studio-runner/` ships the validator, the trusted executor and the `BrowserAdapter`/`StepReporter` seams (10.2, 10.3), but has no process. `src/index.ts` states it plainly — "the HTTP server (10.6) … [is] added behind the same seams" — and the `Dockerfile` carries the matching note at line 51: the image has no entry point until this story. `StepReporter` exists as an interface with no implementation and a comment naming 10.6 as its supplier. ADR-001 §3 reserves `src/server/` and `src/reporting/` for exactly this work.

Architecture §5 makes four runner-side rules non-negotiable, and none of them exists yet:

| Required | Where |
|---|---|
| The runner reserves capacity and performs an authenticated admission CAS **through the API before launching Chromium**. A failed admission handshake never starts a browser. | §5.1.4 |
| Runner `429` means definite nonacceptance: no durable admission, no browser started. Timeouts, connection loss and 5xx are **ambiguous**: they are not permission to replay. Automatic POST retries are disabled in clients and proxies. | §5.1 closing paragraph |
| Reports carry execution/attempt/admission identities and an increasing `runnerSequence`; progress is a cumulative, bounded, redacted snapshot so a later update repairs a delivery gap. Terminal delivery is retried until acknowledged within a bounded window. | §5.3, §8.4 |
| `health` is liveness; `ready` is the ability to admit safely. Capacity saturation alone keeps readiness **true** and returns `429`; draining sets readiness false. | §8.4 |

And one rule defines the component's blast radius: **"The runner … has no platform user session or DB/vault/CSI/LLM credentials"** (§9.2). It receives per-run values, writes object-store objects and reports to the API. That is the whole list. A runner with a database connection would not be a layering smell; it would be a browser that renders untrusted pages holding a credential to the execution history.

This story is the runner's half of the §8.4 internal contract, against fake browser and storage adapters. Every persistence decision on the other side of those HTTP calls — the admission compare-and-set itself, progress and terminal persistence, snapshot-revision assignment, restart recovery, reapers and ambiguity resolution — is story 10.7.

## Acceptance Criteria

### Contract, service identity and destinations

- [ ] **AC-1:** The runner's four internal routes — `POST /v1/validate`, `POST /v1/runs`, `GET /health`, `GET /ready` — and the request bodies it sends to the API's admission and progress routes conform to the `internal`-tagged section of `docs/specs/studio/openapi.yaml`. A contract test asserts conformance. That file is story 10.1's deliverable and is not a dependency of this story: if it has not merged, the test is recorded as **skipped, never passed**, naming 10.1 — the pattern 10.3 used for its `ED-05`-gated stage.
- [ ] **AC-2a:** All four runner routes require a restricted service identity supplied as a configured credential. A request with a missing, blank, malformed or wrong credential is rejected `401`/`403` before any handler work, before any validation and before any slot reservation; the body carries a code and no job detail. Comparison is constant-time. Verified here against a configured stub credential.
- [ ] **AC-2b:** *(Deferred — `ED-02`)* The same routes verified against real platform-issued service identity through the real ingress. Verified in **story 10.18** (hardened staging deployment), which `ED-02` gates. No part of this story depends on the backend's current `BffSessionAuthenticationFilter` bypass.
- [ ] **AC-3:** The callback destination is deployment configuration only. A callback URL, host or port present in a job body is ignored and the job is rejected with a code; a test submits a job carrying an attacker-controlled callback URL and asserts no request leaves for it. No credential appears in any URL or query string. The runner's only configured outbound destinations are the callback API, the object store (faked here) and the target page through Playwright.

### `POST /v1/validate`

- [ ] **AC-4:** `POST /v1/validate` is a browser-free wrapper around `validateArtifact` from 10.2 with bounded work: bounded request body, artifact and step counts taken from the existing `DEFAULT_BOUNDS`, and a wall-clock bound on the call. It returns per-step diagnostics that are bounded and redacted, launches nothing, creates no scratch state, and **cannot reserve a capacity slot** — a test asserts that a validate call during a fully saturated pool still answers successfully and within its bound.
- [ ] **AC-5:** An oversized, malformed or non-JSON validate body returns `413`/`400` with a code and no stack trace, no file path and no artifact echo.

### `POST /v1/runs` — order of operations and admission

- [ ] **AC-6:** `POST /v1/runs` executes in this order and no other: validate the job envelope (immutable identity fields, artifact, configuration, deadlines) → reserve a capacity slot → complete the API admission CAS → return `202`. **No browser, no child process, no scratch directory and no evidence key exists before the CAS returns success.** A test using the fake browser and storage adapters asserts zero adapter calls for every non-success admission outcome (`409`, `401`, `403`, timeout, transport loss, 5xx).
- [ ] **AC-7:** Admission identity belongs to this runner instance and this run: `runnerInstanceId` is stable for the process, `admissionId` is generated fresh per run, and the pair is never reused across runs. The runner never retries an admission with a **new** `admissionId` for the same `attemptId` — doing so is the one way a single runner could compete with itself for an attempt it may already own.
- [ ] **AC-8:** A definite admission refusal — `409` (competing or expired admission), `401` or `403` — stops the run immediately: no browser, slot released, scratch cleared, and a `503`/`409` response to the caller that is explicit about non-acceptance. The runner does not re-attempt admission under any of these.
- [ ] **AC-9:** An **ambiguous** admission outcome — HTTP timeout (10 s starting value, §8.5), connection loss, or any 5xx — is not permission to replay. The runner does not resend the admission, does not launch a browser, releases the slot, clears scratch, and records the ambiguity in a structured audit log line plus a counter metric. Automatic POST retry is disabled in whatever HTTP client is used, and a test asserts exactly one admission request was issued for each of the three ambiguous cases.
- [ ] **AC-10:** Capacity saturation (initial `POOL_SIZE=1`, §5.2) returns `429` with `Retry-After` and is a **definite non-acceptance**: no slot held, no admission request issued, no scratch created, no browser started, nothing durable anywhere. A test asserts the admission client was never called on this path — 429 must be decidable before the runner talks to the API at all.

### `GET /health`, `GET /ready` and drain

- [ ] **AC-11:** `GET /health` reports liveness only and stays `200` while the pool is saturated and while draining. `GET /ready` reports the ability to admit safely: saturated capacity alone keeps readiness **true** (and `/v1/runs` answers `429`); draining sets readiness **false**. Asserted as four distinct states, not as one combined endpoint.
- [ ] **AC-12:** `SIGTERM` enters draining: readiness goes false, new `/v1/runs` is rejected `503`, and an already-admitted run **finishes and reports**. `src/main.ts` wires configuration, server start and the drain path, and the process exits only after the in-flight run has delivered its terminal report or its deadline has passed — never by abandoning an admitted attempt silently. Scratch is cleared on the drain path and at startup.

### Reporting — what the runner sends

- [ ] **AC-13:** Every report carries `executionId`, `attemptId`, `admissionId`, report kind (`STARTED | PROGRESS | FINAL`), timestamps, `runnerSequence`, the **cumulative** step list and bounded logs, the actual runtime versions read from `runtime-versions.json`, and on `FINAL` the outcome/error and the evidence state. `runnerSequence` is strictly increasing within an attempt, starts fresh for a new attempt, and is never reused or decremented. Progress is a full current-state snapshot, not a delta, so a later report repairs a delivery gap without replaying anything.
- [ ] **AC-14a:** `STARTED` is sent only once the browser has actually started — not when admission succeeds and not when an HTTP call begins. Verified against the fake browser adapter from 10.2: a run whose adapter never reports a launch sends no `STARTED`, and the `STARTED` sequence number is always lower than any step's.
- [ ] **AC-14b:** *(Deferred — `ED-05`)* The same admission → real browser launch → `STARTED` sequence driven by real Chromium in the internal Playwright image. Verified in **story 10.12** (Chromium execution and native video). This story installs and launches no browser.
- [ ] **AC-15:** The `StepReporter` implementation that 10.2 left as a seam feeds the report client: `stepStarted`/`stepFinished` update the cumulative snapshot, and the executor's existing per-step outcomes (`PASSED | FAILED | SKIPPED`, null timings for skipped steps) reach the wire unchanged. Reporting is asynchronous to execution — a slow or failing callback must not block, delay or alter a step.
- [ ] **AC-16:** Progress delivery is best-effort and never re-runs work: a failed `STARTED`/`PROGRESS` POST is dropped, the next cumulative snapshot carries the missed state, and a test asserts that a run whose first two progress deliveries fail still reports every step correctly in the third, with no step executed twice.
- [ ] **AC-17:** Terminal delivery is retried idempotently within a bounded delivery window: the retried `FINAL` is byte-identical — same `attemptId`, same `admissionId`, same `runnerSequence`, same body — so the API can recognise it as a duplicate. Retries are bounded in count and total time, use jitter, and stop on acknowledgement or at the deadline. The runner **never** increments the sequence or mutates the body on a retry.
- [ ] **AC-18:** A `409` from the API on any report — ownership lost, superseded attempt, or the execution already finalized — stops reporting for that run immediately, releases the slot and scratch, and never escalates to a retry, a new admission or a relaunch. The outcome is recorded in the runner's structured audit log plus a counter metric and nowhere else; there is no durable runner-side store, and the durable result manifest follows in **10.14**.

### Bounds, redaction and logging

- [ ] **AC-19:** The runner bounds every outbound payload before sending it: maximum step count, maximum log entries, maximum log-entry length and maximum body size, all from one configuration source (§8.5). When the retained-log cap is reached the snapshot sets `logsTruncated = true` and the drop policy — oldest entries dropped, newest retained — is asserted by a test, not left implicit. The runner never emits a body that the API would have to reject for size.
- [ ] **AC-20:** Secret canary: a job carrying a known canary through `resolvedVars`/`resolvedSecrets` produces reports, structured log lines, diagnostics and error messages in which the canary appears in **no** form — plain, URL-encoded, double-encoded and base64 variants — using `createRedactor` from 10.2. Request logging never records job values, resolved values or artifact source text; it records only the identity fields from AC-13. The redactor is applied on the outbound path, so a value cannot escape by way of an unanticipated message field.
- [ ] **AC-21:** Ephemeral values never persist: `resolvedVars`/`resolvedSecrets` are held in memory for the run, are not written to scratch, are not placed in any retry buffer or queued report body, and are cleared on every exit path including the drain and error paths. A test inspects the scratch directory and the pending-report buffer after a failed run and finds no job value.

### Isolation

- [ ] **AC-22:** **No DB, no vault, no CSI, no LLM.** The runner has no database driver, no vault client, no platform identity client and no LLM gateway client anywhere in its dependency tree, and holds no credential for any of them. A build-gated assertion fails if one appears: `no-restricted-imports` entries alongside the existing `vm`/`worker_threads` rules in `eslint.config.js`, plus a test over the resolved dependency tree. Runtime dependencies stay minimal and exact-pinned per ADR-001 §5; the HTTP server choice is the only addition this story may make.

### Tests

- [ ] **AC-23:** Concurrency is proven by holding real state open, not by sequential happy-path calls — the rigour story 10.4's QA round established, translated to a component with no database. At minimum, with the single slot held by an in-flight run: a second `/v1/runs` returns `429` without issuing an admission; `/v1/validate` stays responsive; `SIGTERM` during the in-flight run drains without abandoning it; a `FINAL` retry racing the drain deadline resolves once; and an ambiguous admission racing `SIGTERM` still starts no browser.
- [ ] **AC-24:** Gates green: `npm run type-check`, `npm run lint`, `npm test` and `npm run check:pins` exit 0 from a clean `npm ci`, with coverage on `src/server/**` and `src/reporting/**` at the thresholds already enforced for `src/validator/**` and `src/executor/**`. `npm run test:fixtures` is unaffected. No new runtime dependency beyond the exact-pinned HTTP server choice, justified in the Dev Agent Record.

## Scope

### In scope
- `studio-runner/src/main.ts` — process entry: configuration, server start, `SIGTERM` drain, scratch clearing at startup and on exit.
- `studio-runner/src/server/` — `POST /v1/validate`, `POST /v1/runs`, `GET /health`, `GET /ready`; capacity reservation; service-identity check; bounded bodies; structured redacted request logging.
- `studio-runner/src/reporting/` — admission CAS **client**, progress/terminal report client with bounded idempotent terminal retry, the `StepReporter` implementation 10.2 left as a seam, outbound redaction and payload bounding.
- Fake browser and storage adapters throughout; contract tests against the frozen internal contract.
- The `Dockerfile` entry point its line-51 note defers to this story, and `package.json` start script.

### Out of scope — API side, story 10.7
- The admission compare-and-set **itself**: the conditional statement, the dispatch ledger, exclusive ownership persistence.
- Persisting progress and terminal reports, de-duplicating by `(attemptId, runnerSequence)`, rejecting out-of-order and superseded-attempt reports, persist-before-acknowledge.
- Snapshot-revision assignment — the runner supplies only its own `runnerSequence`.
- Restart recovery, pending/running reapers, finalization reconciliation and ambiguity classification.
- The `/internal/**` server-side security chain, execute acceptance, dispatcher leases, secret resolution at dispatch, the kill switch and SSE.

### Out of scope — elsewhere
- Any Flyway migration, entity, DTO or repository. This story touches no Java and no database.
- `docs/specs/studio/openapi.yaml` and the typed snapshot DTO (10.1).
- Real Chromium, native video recording, parent-enforced deadline killing and process-tree reaping (10.12, 10.13).
- The durable object-store result manifest and its deterministic key (10.14); a fake store stands in here.
- Compile orchestration and the readiness gate that will call `POST /v1/validate` (10.8).
- Authorized variable/secret plumbing end to end (10.17); this story only proves the canary does not leak.

## Implementation Notes

- **Nothing here reaches a database.** AC-22 is the story's defining constraint, not a nice-to-have: this is the process that renders untrusted pages. Every criterion above was rechecked against "no DB, no vault, no CSI, no LLM"; any criterion that implied persistence on the runner's side of the wire was moved to 10.7.
- **The contract file is 10.1's.** The runner is coded against the frozen `internal` section of `docs/specs/studio/openapi.yaml`, but the manifest correctly lists `depends_on: ["10.2"]` only — nothing here needs 10.1 to *merge* to be built or tested. AC-1 handles the ordering honestly by recording the contract test as skipped rather than passed if the file is absent.
- **HTTP server library.** ADR-001 §5 leaves the choice to this story and requires it be minimal and pinned. `node:http` covers the four-route surface with no middleware ecosystem, zero new runtime dependency and no supply-chain surface on a security boundary; if a library is chosen instead, exact-pin it and justify it in the Dev Agent Record.
- **Two retry policies, deliberately opposite.** The admission call is never retried (AC-9): an ambiguous outcome may already have granted admission, and a second attempt risks a second browser. The terminal report *is* retried (AC-17), byte-identical, because the API side is idempotent by attempt and sequence. Keep both policies visible in the code and named in the tests so a future change cannot collapse them into one client default. Whatever HTTP client is used must have automatic retries explicitly disabled.
- **`runnerSequence` is per attempt.** It starts fresh for each attempt and is never reused. The runner holds no cross-run state, so this is a per-run counter, not a persisted one.
- **Post-finalization and ambiguity records stay runner-side and non-durable.** A `409` on a report, or an ambiguous admission, is recorded as a structured audit log line plus a counter metric — no table, no column, no local file. The durable record of a terminal result is the object-store manifest, which arrives in 10.14.
- **Starting values (§8.5)** — 10 s admission HTTP timeout, 30 s admitted-start deadline, 30 s default step timeout, 120 s total browser runtime, `POOL_SIZE=1`. These are starting values to be tuned against staging measurements, not commitments. Deadline *enforcement* and process-tree killing are 10.13; this story only honours the deadlines it is given.
- **`Dockerfile` line 51** explicitly defers the entry point to this story; adding it is expected here and is not scope creep.
