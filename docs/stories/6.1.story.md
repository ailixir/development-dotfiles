## User Story

**As a** platform operator running scheduled health checks,
**I want** failed check executions and report deliveries to be retried automatically with exponential backoff,
**so that** transient failures (network blips, DB timeouts) don't silently skip a monitoring cycle.

---

## Problem Statement

Currently, both `CronDispatcher` and `ReportDeliveryDispatcher` handle failures by logging the error and moving on. The cron schedule advances to the next slot even when the current execution failed due to a transient error. This means:

1. **Check executions**: A network timeout at 09:00 means the next execution happens at 09:30 (next cron slot). The 09:00 data point is permanently lost.
2. **Report deliveries**: An SMTP timeout advances `nextDeliveryAt` to the next day. Recipients miss the daily report entirely.

There is no retry, no dead-letter queue, and no visibility into persistent failures.

## Implementation Notes

- **Exponential backoff formula:** `baseDelay × 2^retryCount` where `baseDelay = 30s`. Max delay caps at 120s (retry 2). After retry 2 (120s), the record is dead-lettered.
- **Transaction boundary:** The `FailedDispatch` insert in `CronDispatcher.executeAsync()` must use `REQUIRES_NEW` to ensure the record persists even if the outer transaction rolls back.
- **RetryDispatcher vs CronDispatcher coexistence:** RetryDispatcher uses a separate ShedLock name. Both can run on the same worker instance without contention.
- **Report auto-disable:** Track consecutive failures via a counter on the Report entity (new column `consecutive_failures INT DEFAULT 0`). Reset to 0 on successful delivery. Trigger disable at threshold (5).
