## User Story

**As a** CSI-authorized support engineer looking at a finished Studio run,
**I want** to play and download the run's recording through a protected API path that honours seeking, refuses me honestly when the evidence is not there or has expired, and never dresses up an incomplete recording as a complete one,
**so that** the video proof I may have to show somebody is served only to people entitled to see it, is seekable rather than a single all-or-nothing download, and never tells me something the platform does not know.

---

## Problem Statement

Four things are true on `epic/EPIC-10` at `52af70c93`, each verified by reading the file named.

**1. The route does not exist.** `StudioController` maps `/tests`, `/tests/{id}`, `/tests/{id}/compile`, `/tests/{id}/confirm-compile`, `/tests/{id}/execute`, `/executions`, `/executions/{id}`, `/tests/{id}/validate-variables` and `/validate-steps`; `ExecutionEventsController` maps `/executions/{id}/events`. Nothing maps `/executions/{id}/video`. `ExecutionSnapshotMapper` nevertheless publishes `videoPath = /api/v1/studio/executions/{id}/video` on every `AVAILABLE` execution — so the API is already handing browsers a path that 404s at the dispatcher.

**2. It is the last route the contract still declares as unshipped.** `docs/specs/studio/openapi.yaml` carries exactly one `x-not-yet-implemented: true`, at line 704, on `getExecutionVideo`. ADR-002 §13's last row records the same fact from the other side: after story 10.9 removed the confirm route's marker, *"`pendingOperations()` is `GET /executions/{id}/video` alone"*. Two assertions in `StudioContractTest` hardcode that — `theCompileRouteIsShippedAndTheMarkerCameOffForThatOperationOnly` asserts `pendingOperations()` `.containsExactlyInAnyOrder("GET /executions/{id}/video")`, and `theConfirmRouteIsShippedAndTheMarkerCameOffForThatOperationOnly` asserts the marker `isEqualTo(Boolean.TRUE)`. Both are this story's to amend, deliberately, and both are load-bearing: they are the reason nobody can clear a neighbour's marker quietly.

**3. The API has no way to read an object.** The only store type on the API side is `ResultManifestStore`, whose javadoc lists *three things this interface deliberately cannot do* — it cannot list, cannot take a runner-supplied key, cannot follow a durable callback URL — and whose one operation returns a parsed `ResultManifest`, not bytes and not a range. There is no S3/Sonic client and no such dependency in `backend/build.gradle.kts`. The runner's `ObjectStoreClient` is the mirror image: exactly one operation, `put`, and *"no `get`, no `list`, no `head` and no `delete`"*. So the byte-reading seam this route needs does not exist on either side, and building it read-only-by-construction is this story's, while the real Sonic client behind it is `ED-03`'s and 10.18's.

**4. The document is silent about three things this route will do.** `getExecutionVideo` declares `206` as `{ description: Range response }`, `404` as `{ description: No evidence for this execution }` and `416` as `{ description: Unsatisfiable range }` — **three responses with no declared content**, which is verbatim one of the examples ADR-002 §12 gives for a Class A defect. It also declares **no `401` and no `403`**, while `getExecution` and `streamExecution` both declare both, and §9.1 requires CSI enforcement on this route by name. And it declares no status at all for a store that cannot be reached — where answering `404 No evidence for this execution` would be a statement the API has not observed. The first is Class A and lands here; the other two are Class C and are escalated rather than invented (AC-22).

One further fact, which is the reason the third acceptance bullet of this story matters more than it did a week ago: **story 10.14 made partiality real.** `RunnerReportProjection` no longer writes `videoPartial = Boolean.FALSE`; it writes `Boolean.TRUE.equals(report.evidence().partial())`, and `ExecutionSnapshotMapper` publishes it. A partial recording is now a state the platform can actually be in, and this is the route that serves its bytes.

## Acceptance Criteria

> Every criterion is falsifiable and cites its source. Criteria needing a real ingress or a real bucket are split `a`/`b`; the `b` half is **skipped, never passed**, and names its gate.
>
> **Two standing rules from wave 5 apply to every criterion below.** *Size the fixture so the hazard actually occurs*, and *make the mutation land inside the measurement window*. Where they bite, the criterion says how.

### Authorization — the execution's own CSI, and one code path for both verbs

- [ ] **AC-1: The route authorizes against the execution's immutable CSI, by the same decision the snapshot route makes.** For one execution with `AVAILABLE` evidence, driven through the HTTP layer: a **reader** of the execution's CSI is served; an **owner** is served; a principal with a **different** CSI is denied; a request with **no identity** is denied; a row whose `csi_id` is **null** (quarantined legacy history) is denied to everyone, administrators included. Denials answer with **the same status and the same code the `GET /executions/{id}` route answers** for the identical identity and id — asserted by driving both routes in the same test and comparing the two responses' status and body `error`, never by asserting a literal. *[Source: architecture §9.1 "Readers may view tests/history/SSE/**videos/downloads** for their CSI … Historical access uses execution CSI, not a mutable parent lookup"; §6.3 "checks the execution's immutable CSI"; epic §10.15 acceptance 1; the same-status rule `ExecutionEventsController` states for the SSE route]*

  **The two discriminating mutations, because a route that authorized against the *parent test* would pass a naive version of this.** (a) Change the **execution row's** `csi_id` to one the caller cannot read → the answer must flip from served to denied. (b) Change the **parent test's** `csi_id` to one the caller cannot read, leaving the execution's own value alone → the answer must **not** change. A route that resolves CSI through the parent passes (a) and fails (b); a route that ignores CSI passes (b) and fails (a). Both are required.

- [ ] **AC-2: Soft deletion of the parent test does not move historical access.** With the parent test soft-deleted, every identity in AC-1 gets exactly the answer it got before the deletion — served stays served, denied stays denied — and the served bytes are unchanged. *[Source: architecture §6.3 "including for soft-deleted tests"; §8.3 `DELETE /tests/{id}` "retain authorized history"; epic §10.15 acceptance 1 "soft deletion does not change historical CSI"]*

- [ ] **AC-3: `?download=true` is the same authorization decision, not a second one.** AC-1's and AC-2's whole identity matrix is executed **twice — once with `download` absent and once with `download=true` — in one parameterized run**, and every status and error code is identical across the pair. A separate download code path that forgot a check is the failure this shape exists to catch, and running the matrix once per verb in two hand-written tests is how it survives. *[Source: architecture §6.3 "`?download=true` uses the same authorization"; epic §10.15 scope bullet 2]*

- [ ] **AC-4: No credential is accepted in the URL, and none is needed.** The operation declares exactly two parameters — the `{id}` path parameter and the boolean `download` query parameter — asserted by **reading the frozen document**, not the controller. A request carrying `?token=…`, `?access_token=…` or `?Authorization=…` in addition to a valid ambient session is served exactly as the same request without them, and a request carrying only such a parameter and **no** session is denied — so no query parameter is ever a credential. *[Source: SPK-02 *Shapes*: "**10.15 assumes an ambient session route (§6.3) and must not add token query parameters**"; architecture §6.3; `serviceIdentity`'s own rule that "the credential is never carried in a URL or a query string"]*

### The key is derived, never read back from the wire

- [ ] **AC-5: The object key is derived from immutable execution identity, and a persisted runner-supplied key cannot redirect the read.** The fixture is the discriminating part: seed the store with **two** objects — one at the key the API derives from `(csiId, testId, executionId, attemptId)` holding bytes **A**, and one at a *different* key holding bytes **B** — and persist `video_key` on the execution row pointing at the **second**. The route must serve **A**. An implementation that reads the persisted column serves B and goes red. *[Source: architecture §6.2 "The API derives expected keys from immutable execution identity; **client-supplied keys are never trusted**"; §6.3 "Derive object key server-side"; the derivation the merged tree already holds and this story reuses rather than re-derives]*

- [ ] **AC-6: Nothing in any response is an object key, a bucket, a host or a URL.** For every status this route can answer — 200, 206, 404, 410, 416 — the complete response (status line, every header, the whole body) is captured and asserted to contain neither the derived key string, nor its `studio/` prefix, nor the configured bucket or endpoint value, nor any `http://`/`https://` substring. Asserted on the **captured response bytes**, never on the controller's source. *[Source: architecture §6.2 "Store object keys only; expose the protected API path to the browser"; §6.3; epic §10.15 acceptance 3 "No public URL or durable presigned URL is stored or returned as authority"]*

### Evidence state gates the route, and the two surfaces cannot diverge

- [ ] **AC-7: All five evidence states are answered, and the route reads the state the snapshot publishes.** One parameterized case table over `PROCESSING | AVAILABLE | FAILED | UNAVAILABLE | EXPIRED`. `AVAILABLE` → `200`/`206`; `PROCESSING`, `FAILED` and `UNAVAILABLE` → `404` with the `ErrorResponse` body AC-21 declares; `EXPIRED` → `410` with `error` equal to the value the contract's own `expired` example carries, **read from the document at test time and not transcribed**. Each case additionally asserts that `GET /executions/{id}` for the same row publishes the same `video.status` — the two surfaces are compared in the same test, so one cannot drift from the other. *[Source: architecture §6.1 (the five states, kept separate from outcome); §6.3 "Return a clear expired/unavailable response when appropriate"; contract `getExecutionVideo` responses and its `expired` example; ADR-002 §18.3's method — read the code set from the document, never transcribe it]*

- [ ] **AC-8: Logical expiry beats a physically present object.** A row whose persisted status is `AVAILABLE` and whose `videoExpiresAt` is in the past answers `410` **while the object is still in the store and still readable** — the fixture must actually contain the bytes at the derived key, sized as AC-13's fixture is, or the test passes because the object is missing and proves nothing. The falsifying mutation is removing the expiry comparison, and it must go red **with a `200` carrying the object's bytes**, not with a missing-object error; the recorded failure message must show that. *[Source: architecture §6.2 "Enforce logical video expiry in the API at `videoExpiresAt` even if physical lifecycle deletion is asynchronous … do not claim exact-time physical deletion"; epic §10.15 acceptance 2 "expired evidence is denied regardless of delayed physical deletion"; the read-time expiry derivation the merged snapshot mapper already performs]*

- [ ] **AC-9: The clock is the only thing that moves the expiry answer.** The same row, unchanged, answers `200` before `videoExpiresAt` and `410` after it, with only the clock advanced. The control that stops AC-8 being satisfied by "always 410": a row whose expiry is in the future is served. *[Source: as AC-8; the single-source retention value this story reads rather than re-declares]*

### Partiality — an incomplete recording is served, and is not dressed up

- [ ] **AC-10: A partial recording is served exactly as a complete one, and the route neither gates on partiality nor annotates it away.** Two rows identical in every respect except `video_partial` (`false` and `true`), with the **same** object bytes: the two responses are **byte-identical** — same status, same `Content-Type`, same `Content-Length`, same `Accept-Ranges`, same body bytes — and a Range request over each returns identical `Content-Range` and identical bytes. Partiality is a fact about the recording, published on the snapshot, and it is not this route's to repair, to refuse or to advertise. *[Source: ADR-002 §17.3 ("a fact about the **recording**, never about the run"), §17.4 (never derived from outcome in either direction, by either component); architecture §6.1 "whether an available recording is partial"]*

- [ ] **AC-11: Every length this route states is measured from the object, never computed from a run-side fact.** `Content-Length` on a `200` equals the store's reported size for the derived key; the total in `Content-Range` equals the same number. The discriminating fixture: a **truncated** recording — an object strictly shorter than the run's `durationMs` would imply and shorter than the complete recording of the same run — persisted on a row carrying `durationMs`, `endedAt` and `partial: true`. The stated lengths must follow the **object**. Falsifying mutation: source the total from any column of the execution row → red. This is the epic's third acceptance bullet for the story that produces the condition — *"Abrupt loss reports honest unavailable/partial evidence rather than promising a complete video"* — applied to the surface that serves the bytes. *[Source: epic §10.13 acceptance 3; ADR-002 §17.1 ("a field something populates with a constant is a wire statement that is false"), §17.6 (the API "probes the stored object's duration" alternative was **rejected** — so the object's *size* is read and its *duration* is not); architecture §6.1]*

  **This criterion also forbids reading the webm container.** The route serves bytes and states sizes; it does not parse EBML, does not derive a duration, and does not repair a truncated container. Asserted by serving a deliberately malformed/truncated object and observing that the status, headers and bytes are exactly what a well-formed object of the same length would produce.

### Range — the bytes, not the status

- [ ] **AC-12: A full request is a complete, correct `200`.** Status `200`, `Content-Type: video/webm`, `Accept-Ranges: bytes`, `Content-Length` equal to the object size, and **the body compared byte-for-byte with the stored object** — the whole array, not its length and not a prefix. *[Source: architecture §6.3 "Support ordinary 200, single byte Range/206, valid `Content-Range`, and invalid/unsatisfiable range 416"; contract `getExecutionVideo` `200` `video/webm`; epic §10.15 scope bullet 1]*

- [ ] **AC-13: Every `206` is asserted on the returned bytes, and the fixture is larger than every boundary the table uses.** **A 206 status asserted without comparing the returned bytes to the requested slice does not satisfy any criterion in this story**, and neither does a Range case whose fixture is smaller than the boundary it claims to exercise. Both are stated as prohibitions because both are the characteristic vacuous shapes for this endpoint.

  The fixture is a real object of **at least 1 MiB** of non-repeating, position-derivable content, so that an off-by-one or a wrong offset produces different bytes rather than the same byte. **A guard asserts `fixtureSize > max(boundaries)` where `max(boundaries)` is computed from the case table itself**, not transcribed — so shrinking the fixture or adding a larger boundary fails the guard instead of silently making a case unsatisfiable.

  The table, each case asserting status, `Content-Range`, `Content-Length` **and** `body == object[a..b]`:

  | Case | Request | Expected |
  |---|---|---|
  | First byte | `bytes=0-0` | `206`, `Content-Range: bytes 0-0/S`, length 1 |
  | Mid-object slice | `bytes=x-y`, `0 < x < y < S-1` | `206`, `bytes x-y/S`, length `y-x+1` |
  | Open-ended | `bytes=x-` | `206`, `bytes x-(S-1)/S`, length `S-x` |
  | Suffix | `bytes=-n` | `206`, `bytes (S-n)-(S-1)/S`, length `n` |
  | End past EOF | `bytes=x-(S+1000)` | `206` clamped to `bytes x-(S-1)/S` |
  | Whole object as a range | `bytes=0-(S-1)` | `206`, `bytes 0-(S-1)/S`, body equals the whole object |

  *[Source: architecture §6.3; epic §10.15 scope bullet 1 and acceptance 2 "Seeking/download use valid bytes and headers"; the two shapes named in the epic's vacuous-guard catalogue as characteristic of a Range endpoint]*

- [ ] **AC-14: `416` is the unsatisfiable case only, and a malformed header is not it.** A start at or beyond the object size answers `416` with `Content-Range: bytes */S` and **no bytes from the object in the body** (asserted by checking the body contains no byte sequence from the object, not merely that it is short). An inverted range (`bytes=200-100`) answers `416`. **Separately** — and this is the case that stops "everything is 416" from passing — a syntactically malformed `Range` (`bytes=abc`, `items=0-10`, an empty value) is **ignored**, answering a full `200` identical to AC-12's. Every boundary in this criterion is computed from the **measured** object size at test time (`S`, `S+1`, `S+1000`), never from a transcribed constant, so that resizing the fixture cannot silently convert a satisfiable case into an unsatisfiable one. *[Source: architecture §6.3 "invalid/unsatisfiable range 416"; contract `416` "Unsatisfiable range"; epic §10.15 scope bullet 1]*

- [ ] **AC-15: `?download=true` sets an attachment whose filename the API derives, and composes with Range.** With `download=true`: `Content-Disposition: attachment` with a filename derived by the API from immutable execution identity, matching a strict asserted pattern, containing no object key, no `studio/` prefix, no CSI-external value and no CR/LF. Without `download`: **no** `attachment` disposition. `download=true` combined with a `Range` header yields a `206` that carries **both** the correct `Content-Range` and the disposition, with the sliced bytes asserted as in AC-13 — so the two features are proven to compose rather than assumed to. *[Source: architecture §6.3 "`?download=true` uses the same authorization with an **attachment filename derived by the API**"; epic §10.15 scope bullet 2]*

### The store seam, and what it may not do

- [ ] **AC-16: The API-side video store is read-only by construction, and a ranged read reads only the range.** A new seam with exactly the operations this route needs — a ranged read and a size/existence read — and **no put, no delete, no list, no copy**. The structural half is asserted **on the production interface itself** (reflect over its declared methods and assert the set), not over a test double, because a guard that states a structural property of a production symbol while asserting over a test-local stand-in is the epic's sixteenth catalogued vacuous shape.

  The behavioural half is the one that matters and it is instrumented, not scanned: with a fixture of **at least 1 MiB** and a requested range of **at most 64 KiB**, the fake store records how many bytes it was asked to produce, and the assertion is that the count equals the **requested range length**, not the object size. A "read the whole object, then slice" implementation is ≥16× over and goes red. The instrument reads during the response, so the mutation lands inside the measurement window. *[Source: architecture §6.2 "Runner writes only this prefix; API/recovery **read only**. Runner has no Get/List permissions"; §9.2; the same three-things-it-cannot-do discipline the merged manifest store and the runner's write-only client both state; epic §10.15 scope "Sonic proxy"]*

- [ ] **AC-17: An unreachable store is not an absent object.** The fake distinguishes *the store answered and the key is not there* from *the store could not be reached*, and the two produce different observable outcomes at the route — proven behaviourally by driving both and comparing. **Which status the unreachable case answers is escalated in AC-22 and is not invented here**; until it is ruled, the criterion is that the two cases are not collapsed and that the unreachable case does **not** answer `404 No evidence for this execution`, which would be a statement the API has not observed. *[Source: `ResultManifestStore.isAvailable`'s own rule — "an unreachable store must not look like an absent key" — and the runner's `ObjectStoreUnavailableError` stating the mirror of it; architecture §6.1's honesty requirement; ADR-002 §12 "leave it red and escalate"]*

- [ ] **AC-18a: Everything above is proven against a local fake/compatible store.** No real endpoint, no real credential, no network. The fake is the `ED-03` stand-in this story owns; the real client is 10.18's. *[Source: `ED-03` `fallback` "Local fake/compatible store"; manifest `gate_note` for `ED-03`]*

- [ ] **AC-18b:** *(SKIPPED, NEVER PASSED — BLOCKED on `ED-03`, status **open**; spike **SPK-03**; integration owner **10.18**, integrated proof **10.19**.)* **The same reads against real Sonic.** A ranged `GET` transcript against the real bucket; API credentials proven **read-only** by a recorded denial of a `PUT`; the observed lag between lifecycle expiry and physical deletion, with a `GET` on a logically expired object recorded as either failing or still serving — which is the fact §6.2 forbids assuming. *[Source: `ED-03` `gates:` includes 10.15; SPK-03 *Gates* "10.15 streaming from Sonic"; SPK-03 questions 1, 2, 5]*

### Through the real ingress

- [ ] **AC-19a: The ambient-session assumption is honoured on this branch, and nothing here depends on a bearer header.** The route reads identity only from the ambient session the platform filter establishes; it declares no `Authorization`-carrying parameter (AC-4); and the success path does not constrain content negotiation in a way that turns a denial into a different status — the authorization decision is taken **before** any media type is committed, asserted by observing that a denied request returns the same JSON error body the snapshot route returns and not a `406` or a `500`. This is the trap the merged SSE controller records having avoided, in its own words, for the same reason. *[Source: architecture §6.3 "An authenticated ambient session/gateway route is required for `<video>` and download requests; same-origin alone does not supply a JavaScript bearer header"; SPK-02 *Shapes* for 10.15; the content-negotiation note the merged SSE controller carries]*

- [ ] **AC-20: Both blocked halves carry a gate-still-shut assertion that cannot stay green past its gate.** For each of `ED-03` and `ED-06`, a live test reads that dependency's `status` from the epic manifest and asserts it is `open`; when it is closed, the test goes red **in a run** and the skip above it must be reviewed rather than left in place. Additionally, for `ED-03`, the injected store bean is asserted to be the fake and not a real client, so AC-18b cannot be reported as cleared by someone who wired a real endpoint under the fake's name. *[Source: the epic's convention since 10.3 — "a `b` half that turns green without its gate moving is a defect, not a bonus"; the merged `ED-02` gate-still-shut assertion story 10.17 landed, which asserts by **running** the evaluator rather than by reading the filter's source]*

### The contract

- [ ] **AC-21 (Class A, §12): the three content-less responses are declared, and the marker comes off this operation alone.** Four edits to `docs/specs/studio/openapi.yaml`, all on `getExecutionVideo`, each demonstrated by a contract-test failure before and a pass after, each recorded in one ADR-002 §13 row:

  1. `206` gains declared `video/webm` content and its `Content-Range`/`Content-Length` headers.
  2. `404` gains `application/json` `ErrorResponse` content — it has a description and no content today, which is verbatim §12's own example of Class A.
  3. `416` gains `application/json` `ErrorResponse` content and its `Content-Range: bytes */S` header.
  4. `x-not-yet-implemented` is removed, and `x-implemented-by` is corrected from `'10.16'` to `'10.15'`.

  **The fourth edit's second half is a correction of a wrong value, not a routine update, and is reported as a finding rather than laundered**: the manifest assigns *"Authorized Range video/download endpoint"* to 10.15 and *"Evidence state, playback and step seek"* (Frontend) to 10.16; the retired epic's index table lists 10.15 as Backend and 10.16 as Frontend.

  **@po, wave-6 validation — RULED CLASS A, and the contingency is not needed.** Verified independently: `openapi.yaml:705` carries `x-implemented-by: '10.16'` on `getExecutionVideo`, and the manifest and the retired epic's index both place the backend route in **10.15** and frontend playback in **10.16**. `x-implemented-by` is a **vendor extension carrying a planning attribution**. §12 Class C enumerates *"routes, security schemes, tags, `servers`, status-code semantics, anything on the public surface"* — it is none of those, no client behaviour depends on it, and no conforming implementation is affected by its value. Its current value names a story that will never implement that route, which is **a defect nothing could ever have satisfied** — §12's own Class A language. So the correction lands here with the marker removal, in one §13 row, reported as a finding. ## Implementation Notes

- **The content-negotiation trap is real and is already documented on this branch.** The merged SSE controller declares *no* `produces` on its mapping, with the reason stated in a comment: an authorization failure answers with the same JSON error body the snapshot route does, and a handler declaring only one media type would make content negotiation turn that `403` into a `500`. A video handler declaring `produces = "video/webm"` has exactly the same defect, and AC-19a is the assertion that catches it. Set the media type on the success path.
- **Range is a well-specified protocol; do not improvise it.** RFC 9110's rules for `bytes=x-`, `bytes=-n`, an end past EOF (clamp), an inverted range (unsatisfiable), and a syntactically invalid header (ignore, serve `200`) are what AC-13 and AC-14 encode. If the framework's built-in Range support is used, AC-13's byte assertions still apply unchanged — a framework doing it correctly passes them, which is the point of asserting on bytes rather than on which code ran.
- **The fake store is not a `Map<String, byte[]>` that the route reads whole.** AC-16's instrumented count is the criterion; a fake that hands back the whole array and lets the route slice it makes the count unfalsifiable. Give the fake a ranged read and have it record what it was asked for.
- **Write the fixture so wrong offsets produce wrong bytes.** A megabyte of zeros makes every offset look correct. Generate position-derivable content (e.g. a counter or a keyed stream) so that `object[a..b]` is unique to `(a, b)`.
- **Do not read the container.** AC-11 forbids parsing webm. The route knows a key, a size and a byte range; everything else is the snapshot's.
- **Land the escalation tests early.** ESC-1 and ESC-2 exist to be referred *at the start of the story*, not discovered at the gate. Story 10.14 recorded exactly this lesson about O-14: "discovering at the gate that the ruling never came is how it silently becomes the next story's problem."
- **`ED-02` is not this story's gate, but it shapes what AC-1 can claim.** The admin short-circuit is still live, so an absolute claim of the form "this identity cannot read anything" is not provable here. AC-1's claims are relative and comparative — the route answers what the snapshot route answers — which holds regardless of the bypass, and the absolute claim is AC-19b's.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on 2026-09-11 and re-verified here: `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a Darwin host, the CLI is absent, and `graceful_degradation.skip_if_not_installed: true` applies. A draft checklist expecting such a section is satisfied by that ruling; section 6 is **N/A**.

## The ownerless seek flake — reported, not adopted

There is a `seek-measurement` test in the runner's fixtures tier that @qa characterised as a **pre-existing timing flake**: story 10.17 recorded it failing once and passing on every subsequent run, before and after that story's changes; @qa's gate could not reproduce it in any run including one under heavy Gradle load, and recorded it as *"taken on trust as pre-existing"*. It belongs to no story and has no owner.

**Recommendation: this story should not adopt it, and here is why in full.**

- **Step seek is not this story's subject.** The retired epic's §10.15 scope line is *"execution-CSI authorization, Sonic proxy, Range and attachment handling"*. Seeking is §10.16 — *"Controlled fixture seeks within the architecture's 500 ms target"* — and the file's own `.skip` for the end-to-end measurement says it is owned by **SPK-06 phase B** and *"consumed by 10.16 and 10.19"*. Adopting it here would be this epic's most-repeated mistake in the other direction: a story absorbing work whose owner is already named.
- **This story touches no runner source.** Its only reach into that tree is one constant — the contract pin (AC-23). Making a real-Chromium, video-decoding fixtures-tier test a gate for a backend route would give the story a dependency it has no other reason for, and story 10.17's own cut-risk note records what happens next: `test:fixtures` is *"the first thing dropped when the tier is slow"*, and dropping it un-executes whatever else lives there.
- **It must not stay ownerless, and it should go to 10.16.** 10.16 is the story that *consumes* the 500 ms claim, is the next story to touch step seek, and is the only remaining story whose acceptance depends on that number being trustworthy. Failing that, SPK-06's own owners (@architect, with @qa on phase B). @po's assignment either way.
- **One correction the next owner needs, and it is offered as an inference rather than a reading.** The failure was reported as *"`error=579.9ms` and `error=882.6ms` against a 500 ms target"*. The live bounds in that file are a **100 ms median tolerance** and a **1500 ms per-step outlier bound**; the 500 ms figure in the file belongs to the end-to-end `.skip`, which never runs. Both reported values are below the outlier bound and above the median tolerance, so the assertion that failed is almost certainly the **median** one, not a 500 ms one. I did not observe the failure and am reasoning from the file's constants; the next owner should confirm against the real output before re-deriving anything. The distinction matters, because the file's own commentary attributes large positive errors to a **detector** limitation — a full-viewport repaint that does not land in a single encoded frame, so the frame finder matches the next scene change — which would be a fix in the test helper, not in the runner, and is a different piece of work from widening a bound.
- **What this story will do about it:** run `npm run test:fixtures`, report the result including any flake, and absorb nothing. AC-26 makes that tier reported-but-not-a-gate for exactly this reason.
