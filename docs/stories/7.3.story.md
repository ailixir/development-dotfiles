## User Story

**As the** put-checks backend running in a Kubernetes environment with rolling deployments,
**I want** in-flight check executions to drain gracefully on SIGTERM, async execution to be submitted only after the dispatch transaction commits, the CSI metrics refresh to be ShedLock-guarded, and metrics cardinality to be bounded,
**so that** deployments don't lose execution results, dispatch can never advance nextExecutionAt without the execution actually running, multiple replicas don't waste resources on duplicate materialized view refreshes, and Prometheus scrape size stays bounded.

---

## Problem Statement

### P1: No graceful shutdown
When SIGTERM arrives (rolling deploy), the `checkExecutor` virtual-thread pool is shut down immediately. In-flight HTTP/TCP calls are interrupted, and their `ExecutionPersistenceService.persistResult()` calls may never execute. With 100 concurrent executions at peak, a deploy can silently lose ~100 results.

### P2: Transaction-then-async race
In `CronDispatcher.dispatchSingle()`, the async execution is submitted (`checkExecutor.execute(() -> executeAsync(...))`) inside a `TransactionTemplate.execute()` lambda. The async task may start running before the transaction commits. If the transaction rolls back, the `nextExecutionAt` advancement is reverted — but the execution has already started and will persist a result for a schedule that thinks it hasn't run yet.

### P3: CsiMetricsRefreshScheduler not ShedLock-guarded
`scheduledRefresh()` runs `REFRESH MATERIALIZED VIEW CONCURRENTLY` every 5 minutes but has no `@SchedulerLock`. With 3 replicas, all 3 execute the refresh simultaneously — wasting Postgres I/O.

### P4: Metrics cardinality risk
`checks.execution.total` has a `csi_id` tag. With thousands of CSIs, each producing SUCCESS/FAILURE counters, Prometheus cardinality grows linearly. This causes slow scrapes and high memory in Prometheus.

## Acceptance Criteria

### Graceful shutdown
- [ ] **AC-1:** `CronDispatcher` implements `SmartLifecycle`. On `stop()`, it sets a `shuttingDown` flag that prevents new polls, then waits up to `checks.scheduling.shutdown-timeout-sec` (default 30) for in-flight count (from 7.2) to reach 0.
- [ ] **AC-2:** If in-flight count doesn't reach 0 within the timeout, a warning log `shutdown_timeout inFlight={n}` is emitted and shutdown proceeds.
- [ ] **AC-3:** `SmartLifecycle.getPhase()` returns `Integer.MAX_VALUE - 100` (stops early in the Spring shutdown sequence, before DataSource is closed).

### Transaction-then-async ordering
- [ ] **AC-4:** `dispatchSingle()` uses `TransactionSynchronizationManager.registerSynchronization()` with an `afterCommit()` callback to submit the async execution. The execution is only submitted if the transaction commits successfully.
- [ ] **AC-5:** If the transaction rolls back, no async execution is submitted. A debug log `dispatch_rolled_back scheduleId={id}` is emitted.

### ShedLock on CSI metrics refresh
- [ ] **AC-6:** `CsiMetricsRefreshScheduler.scheduledRefresh()` is annotated with `@SchedulerLock(name = "csiMetricsRefresh", lockAtMostFor = "5m", lockAtLeastFor = "4m")`.

### Metrics cardinality fix
- [ ] **AC-7:** `HttpCheckExecutor` and `TcpCheckExecutor` drop the `csi_id` tag from `checks.execution.total` counter.
- [ ] **AC-8:** New gauge `checks.execution.total_by_csi` is registered once per poll cycle in `CronDispatcher` using a snapshot query, NOT per-execution. This provides CSI-level visibility without per-event cardinality explosion.

### Disable unimplemented check sources
- [ ] **AC-9:** Default config in `application.yml` sets `SPLUNK: false`, `GRAFANA: false`, `ITRS: false`, `APPDYNAMICS: false`, `UI_TEST: false`. Only `HTTP` and `TCP` remain enabled.
- [ ] **AC-10:** `GET /api/v1/checks/sources` response reflects the disabled sources so the frontend can hide unavailable types.

### Tests
- [ ] **AC-11:** `GracefulShutdownIT`: start dispatcher, submit long-running execution, trigger `stop()` → verify execution completes and result is persisted before shutdown returns.
- [ ] **AC-12:** `AfterCommitDispatchIT`: dispatch with a transaction that rolls back → verify no async execution is submitted.
- [ ] **AC-13:** `CsiMetricsLockIT`: verify `CsiMetricsRefreshScheduler` acquires ShedLock.
- [ ] **AC-14:** `MetricsCardinalityTest`: verify `checks.execution.total` has no `csi_id` tag.
- [ ] **AC-15:** Existing `SecurityContextPropagationIT`, `MdcPropagationIT` still pass.
- [ ] **AC-16:** JaCoCo coverage ≥ 80% for modified classes.

## Implementation Notes

- **SmartLifecycle vs @PreDestroy:** `SmartLifecycle` is preferred because it integrates with Spring's phased shutdown, letting us control ordering (stop dispatcher before closing DataSource).
- **afterCommit safety:** `TransactionSynchronization.afterCommit()` runs in the same thread that committed, so submitting to `checkExecutor` from there is safe. The only risk is that `afterCommit` itself throws — wrap the submission in a try/catch to avoid losing the committed transaction's side effects.
- **csi_id metric replacement:** The snapshot-based gauge avoids creating a counter per CSI. Query: `SELECT csi_id, status, count(*) FROM checks WHERE deleted_at IS NULL GROUP BY csi_id, status`. Update gauge every poll cycle (every 10s from 7.2).
