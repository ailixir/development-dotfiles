## User Story

**As the** Checks squad that has built, across seventeen stories, an execution path whose security
controls are almost all still **launch options and unit tests** — a sandbox flag nothing has ever
proved starts under the cluster's PodSecurity level, an egress rule that exists only as a sentence
in an architecture document, a browser whose binary nothing verifies, a private object store that
is a directory on a developer's disk, an SSE route that has never crossed a proxy, and an
authentication filter whose bypass returns a hardcoded `true`,

**I want** the deployment itself to become the control: a runner Deployment whose rendered
manifest cannot be pointed at another browser, cannot reach a destination it has no business
reaching, cannot be handed a credential it must not hold, and drains rather than dropping admitted
work; an ingress route through which a real browser really does receive two timed snapshots
separately; and a deployed profile in which the production auth bypass is **absent**,

**so that** the staging pilot of 10.19 is run against controls somebody has watched fail — and so
that the four facts this repository cannot establish locally are recorded as **measured evidence
or as open gates**, never as a paragraph that reads like one.

## Problem Statement

Seven facts define this story. Every one was read on the branch at `52af70c93`, in this worktree,
and each names where.

**1. There is no runner Deployment.** `helm-chart/put-checks/templates/` contains
`deployment.yaml` (api, worker, frontend — three components from one file), `service.yaml`,
`ingress.yaml`, `hpa.yaml`, `pdb.yaml`, `configmap.yaml`, `serviceaccount.yaml`, `NOTES.txt` and
`_helpers.tpl`. There is **no `studio-runner-deployment.yaml`, no `studio-runner-service.yaml` and
no NetworkPolicy template of any kind**, and no `studioRunner` key in any of the four values files.
ADR-001 §3 names all three files and §9 assigns their hardening values to this story by name. Every
runner control the epic has shipped so far — `chromiumSandbox: true`, the environment allowlist,
`execArgv: []`, the fail-closed configuration loader, the drain — is enforced by the runner's own
process against a pod spec that does not exist.

**2. The auth bypass is unconditional, and it is not the only one.**
`BffSessionAuthenticationFilter.isCoreServiceBypassed()` is

```java
private boolean isCoreServiceBypassed() {
  // Temporary hardcoded bypass while the target platform does not provide Core services.
  return true;
}
```

and `CORE_SERVICE_BYPASS_IDENTITY` carries `List.of("checks-admin", "platform-admin")`. Two more
paths sit beside it in the same file and are not named by `ED-02`: `resolveIdentity` trusts an
**`X-User-Id` request header** — with `X-User-Email`, `X-User-Roles` and `X-User-Csi-Ownership`
parsed straight off the request into a `UserIdentity` — **before** it ever reaches the bypass; and
`applyTemporaryCsiReadBypass` appends `checks-admin` to any identity making a `GET` under
`/api/v1/csi`. Architecture §9.1 requires that *"the trusted gateway must strip/replace identity
headers and prevent direct-backend impersonation; absent identity fails closed"* — the header path
is the impersonation §9.1 names, and nothing in this repository strips it. This is the cause of the
epic's **23 known backend test failures** (10.17's gate: `check --continue` → 834 passed / 23
failed / 6 skipped, failing-class diff versus baseline empty, zero in `studio`), and it has been
deliberately out of scope for every story in the epic.

**3. CSRF is disabled outright.** `SecurityConfig.filterChain` opens with `http.csrf(csrf ->
csrf.disable())`, while the browser path is a session **cookie** (`put_session`) and CORS is
configured `setAllowCredentials(true)`. §9.1 requires that *"cookie-authenticated mutations require
a documented CSRF control"*, and SPK-02's question 7 asks whether one is defined. Today the answer
is no, and no story has been asked it.

**4. The SSE route is shipped and has never crossed a proxy.**
`ExecutionEventsController` exists, sets `Cache-Control: no-store` and `X-Accel-Buffering: no`,
sends a full snapshot on every connection, and `SnapshotBroadcaster` heartbeats on the configured
15 s interval with a 60 s bounded lifetime and a 30 s authorization refresh. The ingress it must
pass through is `className: nginx` with `annotations: {}` in `values.yaml` and, in
`values-prod.yaml`, exactly two annotations — `rate-limit` and `rate-limit-window`. **No streaming
settings of any kind.** The chart's single API Ingress maps `path: /` `pathType: Prefix`, so any
buffering annotation added to it applies to every REST call as well. The SSE assessment is explicit
about the state of this: *"No SSE implementation, runtime spike, or staging test was performed
during this review."*

**5. The production API runs three replicas scaling to six.** `values-prod.yaml`:
`backend.replicaCount: 3`, `autoscaling.enabled: true`, `minReplicas: 3`, `maxReplicas: 6`. The SSE
assessment draws the consequence directly — *"A callback and browser subscription can reach
different pods"* — and SPK-02's question 5 is whether reconnect with `Last-Event-ID` **to a
different replica** restores the current snapshot. The design answers it by reading committed state
rather than by affinity, and nothing has ever tested it.

**6. SEC-2 is still open and its control is a deployment control.** @qa built a browser registry
symlinking every real file except `chrome-headless-shell`, replaced that one with a shim exec'ing
the real binary with `--no-sandbox` prepended, and pointed `PLAYWRIGHT_BROWSERS_PATH` and then
`HOME` at it. **Both launched the shim, the run reported ready normally, and no gate noticed** —
thirteen attacks, eleven blocked, these two through. `chromiumBuild` is recorded at *build* time
and `grep -rn '\.version()\|executablePath' src/` returns nothing. @po declined a runtime identity
check on four grounds, the strongest being that **a shim able to re-exec without the sandbox can
also report the correct pinned version**, so the check catches the careless attack and misses the
careful one. ADR-001 §4.2 makes `PLAYWRIGHT_BROWSERS_PATH` unremovable. The control that works is
the one this story ships: an immutable image, `readOnlyRootFilesystem: true`, and **no deployment
mechanism by which either variable can be set at all**.

**7. The API and the runner disagree about the runner's port.** `application.yml` defaults
`studio.execution.runner-base-url` to `http://put-checks-studio-runner:8090`;
`studio-runner/src/server/config.ts` defaults `STUDIO_RUNNER_PORT` to **8080**. Two derivations of
one fact, in two languages, neither of which has ever been deployed — which is the defect class
this epic has found in almost every wave. It is this story's because this story is where the
Service is written.

And one fact that makes this story's *own* configuration suspect. `templates/configmap.yaml`
renders `configOverrides` as ConfigMap **keys** (`{{ $key }}: {{ $val | quote }}`) consumed by the
container through `envFrom: configMapRef`, and the keys in use are dotted —
`spring.datasource.hikari.maximum-pool-size`, `checks.executor.source-limits.HTTP`,
`checks.scheduling.batch-size`. A ConfigMap key is only injected as an environment variable if it
is a valid environment-variable name; a dotted key is not. *(Verified: the template and the four
values files. **Inferred**, from documented Kubernetes behaviour rather than from this repository:
that such keys are skipped.)* If that inference holds, the chart's `configOverrides` mechanism is
inert and always has been — and this story is about to put deployed configuration at the centre of
five security controls. AC-19 makes it a check rather than an assumption.

Nothing here builds the trusted identity gateway or the real vault (`ED-02` — see AC-20/AC-21 and
*Open Questions* 1), integrates real Sonic in the runner's upload path (`ED-03` — *Open Questions*
3), invents a destination-policy field on the job envelope (ADR-002 **O-6**, Class B — AC-9), or
fixes the Testcontainers JDBC liveness bug (**MED-2** — *Related findings*).

## Acceptance Criteria

> **Convention.** Criteria split `a`/`b` are the epic's standard for externally gated work
> (established by 10.3; used by 10.6, 10.7, 10.8, 10.12, 10.13, 10.14, 10.17). The `b` halves are
> **skipped, never passed**, and each names its gate, its spike and its owner. A `b` half that turns
> green without its gate moving is a defect, not a bonus.
>
> **This story has more blocked criteria than any other in the epic — sixteen of twenty-eight.**
> That is the expected shape of the story that sits behind four open spikes, and it is stated here
> rather than disguised by writing weaker criteria that could pass locally. A reviewer should
> expect the blocked count and should be suspicious of any reduction in it that is not accompanied
> by a spike record under `docs/qa/spikes/SPK-0N/`.
>
> **The rendered-manifest rule, which every chart criterion below depends on.** Assertions about
> the deployment are made on the **output of `helm template`** — captured bytes produced by running
> the renderer — parsed as YAML and asserted structurally. An assertion that greps a `values-*.yaml`
> file, or a template file, is a **source-text scan** and does not satisfy any criterion here. Each
> chart criterion additionally names a **render mutation**: a change to the values or the template
> that must turn that criterion's named test red, with the observed red recorded.

- [ ] **AC-4a (SEC-2, the deployment control): the browser path cannot be redirected by anything
  the deployment can do, and the attack that succeeded is re-run against the image.** Three parts,
  each falsifiable:
  1. **The chart's runner environment is enumerated, not an arbitrary map.** Unlike the
     `backend`/`worker`/`frontend` components — which render `{{- range $key, $val := .Values.X.env }}`
     and will therefore emit *any* key an operator writes — the runner's environment renders from a
     **closed list of keys**, and a values file naming a key outside it **fails the render**. The
     rendered runner container carries **no `PLAYWRIGHT_BROWSERS_PATH` and no `HOME`**, and there is
     no values key that would produce either. This is the same shape as the runner's own
     `ACCEPTED_KEYS` loader, which is fail-closed by enumeration — the deployment side has, until
     now, been the open half.
  2. **No writable mount sits on the browser search path or on `$HOME`.** The rendered volume mount
     paths are asserted **disjoint** from the image's browser registry path and from the image's
     `HOME` (`/home/pwuser`, set by `studio-runner/Dockerfile`), by comparison against the values
     read out of the built image rather than against hardcoded strings.
  3. **@qa's attack, re-run, with the control removed and with it in place.** Inside the built
     image running as `pwuser`: attempt to create a shim browser registry (a directory containing
     a `chrome-headless-shell` that execs the real binary with `--no-sandbox`) in the browser path
     and in `$HOME`. With the container run **read-only** (`--read-only` plus the two tmpfs mounts
     that stand in for the `emptyDir`s), both writes must fail. **The falsification is the point:**
     the identical attack run **without** `--read-only` must succeed and must be recorded as
     succeeding, in the Dev Agent Record, with the shim's output. A control whose removal changes
     nothing observable is not a control.
  **Residual, named and not closed:** an adversary who can edit the pod spec still wins, and
  nothing reads the *running* browser's identity. @po's declination of the runtime check stands
  and this criterion does not reopen it.

- [ ] **AC-6: Drain, readiness and the termination grace period are one derivation, not two.** The
  rendered Deployment sets `terminationGracePeriodSeconds` **greater than or equal to** the runner's
  own total browser runtime cap plus its finalization and delivery margins, and a `preStop` that
  flips readiness before the drain; the readiness probe is `GET /ready` and the liveness probe is
  `GET /health`. The assertion compares the rendered grace period **against the rendered
  `STUDIO_RUNNER_*` deadline values in the same manifest** — arithmetic over the values the pod
  actually receives, not against a number written twice. A saturated pod stays **ready** (the runner
  answers `503` with `Retry-After` and keeps readiness true); a draining pod goes **not ready**;
  both facts are properties of the runner that this criterion must not re-implement, so the
  criterion asserts only that the probe paths are the ones the runner serves for them.
  **Render mutation:** lower the grace period below the derived sum → red; point readiness at
  `/health` → red.
  *[Source: architecture §5.2, §5.4, §8.4, §8.5 ("Recovery deadline is the browser runtime cap plus bounded finalization/delivery margins"); ADR-001 §9 Probes and Termination rows; epic §10.18 scope bullet 2 ("`ready` false on drain, true when merely busy; grace period covers admitted work/finalization budget"); `studio-runner/src/server/capacity.ts` ("a saturated pod … returns `429`/`503` and stays ready; a draining pod returns `503` and sets readiness *false*")]*

- [ ] **AC-7: The runner pod cannot be handed a credential §9.2 forbids it, and its service account
  is its own.** The rendered runner pod carries **no** database URL, vault address, CSI endpoint or

  secret whose name matches those classes, over the **rendered** manifest for all four value sets —
  and it carries exactly the two identity secrets it needs (inbound service identity, outbound
  callback identity) plus the object-store credentials of AC-11a. It uses a **dedicated**

  reason is recorded. **Render mutation:** add a `SPRING_DATASOURCE_URL` to the runner's values →

  `STUDIO_RUNNER_*` namespace and would ignore a `SPRING_DATASOURCE_URL` entirely; §9.2's guarantee

  *[Source: architecture §9.2 ("The runner … has no platform user session or DB/vault/CSI/LLM credentials"); §9.3 ("restricted service-account access"); ADR-001 §9 Config/secrets row and its note that the runner "should get its own service account when RBAC differs … decided in 10.18"; `studio-runner/src/server/config.ts` `CONFIG_PREFIX` scope]*

### B. Egress and destinations — `ED-04` / SPK-05, and ADR-002 **O-6**

- [ ] **AC-8a: A NetworkPolicy template exists, renders, and is default-deny with exactly the three
  destination classes the runner declares.** The rendered `NetworkPolicy` selects the runner pods,
  denies egress by default, and permits exactly: the API callback Service, the object store, DNS,

  is permitted **from the worker pods only** (§8.4: the internal routes are not public, and the MFE
  never talks to the runner). The three permitted classes are compared against the runner's own
  `PERMITTED_DESTINATIONS` (`callback-api`, `object-store`, `target-page`) so a fourth class cannot
  appear on one side alone. **Render mutation:** delete the DNS rule → red; add a fourth peer → red.
  *[Source: ADR-001 §3 (`studio-runner-networkpolicy.yaml` "10.18 (after the egress spike)"), §9 Network row, O-5; architecture §9.3 ("Permit runner access to the callback API, Sonic, approved targets, and controlled DNS only"); `studio-runner/src/server/config.ts` `PERMITTED_DESTINATIONS`]*
- [ ] **AC-8b:** *(Deferred — **`ED-04`** / **SPK-05**; **skipped, never passed**.)* **Enforcement,
  proven from a runner pod with the policy applied:** approved host reachable; unapproved host
  blocked; **redirect** to an unapproved host blocked; subresources and authentication-provider hops
  to approved hosts allowed; cloud/cluster metadata and control endpoints, link-local ranges and
  local files unreachable; DNS behaviour for an unapproved name recorded; callback and object store
  reachable. §9.3 states the limit this criterion must not paper over — *"Standard Kubernetes
  NetworkPolicy operates at network layers, not URL paths"* — so if the spike finds only static
  L3/L4 policy exists, **per-run destination checks in the runner become the primary control and
  Security must accept that limitation explicitly**; that acceptance, or its absence, is part of
  this criterion's evidence.
  *[Source: SPK-05 questions 1–6, *Evidence*, *Shapes* and *Fallback if negative*; architecture §9.3; epic §10.18 acceptance bullet 3; `ED-04` `gate_note` ("10.18 egress enforcement … blocked")]*

- [ ] **AC-9a: ADR-002 **O-6** is carried, not absorbed: no field is added to the job envelope, and
  the policy identity that already exists is bound to the audit trail.** This story **does not**
  define an approved-target or secret-use policy field on `RunJob` — that is a field on a closed,
  runner-consumed body, **ADR-002 §12 Class B**, which an architect rules on first and which a story

## Anti-vacuous test requirements

This section is normative, not advisory. Sixteen guard shapes that could not fail have been
catalogued in this epic, and **three of them were secret-redaction guards** — security guards, green
the whole time, each found by a QA round rather than by the story that wrote it.

**For a hardening story the obligation is stronger than per-guard falsification: it is per-attack
falsification.** Each control must be shown to fail when the control is removed, *against the
specific attack it exists to stop*. "I removed the line and a test went red" is not enough if the
test that went red is not the one modelling the attack.

### The sixteen shapes, and the three that this story is most likely to reproduce

| Shape | How it would appear here |
|---|---|
| Source-text greps instead of captured output | Asserting `values-staging.yaml` *contains* `readOnlyRootFilesystem: true` instead of asserting the **rendered** manifest. Forbidden by the rendered-manifest rule above |
| **Canaries never placed in the request** | AC-4a's shim attack written as "the write would fail" rather than executed. The attack must be **run**, and its **successful** form recorded |
| Isolation tests deleting their own coverage | A NetworkPolicy test that asserts the policy exists by rendering only the policy — the peers must be compared against the runner's own `PERMITTED_DESTINATIONS` |
| Pin checks with an uncompared copy | AC-1's port and AC-6's grace period: both are comparisons **between two rendered values**, never each against a literal |
| Contract checks comparing route strings not bodies | AC-13a comparing annotation *names* rather than the timeout **value** against the heartbeat **value** |
| Two guards each covering half a property, neither carrying a canary | AC-19a's three bypass paths: closing `isCoreServiceBypassed` while the header path stays open is exactly this shape, which is why they are one criterion |
| A scan keyed on a receiver's variable name | Any assertion written against a Helm *template* variable rather than the rendered key |
| An assertion whose discriminating mechanism is pre-empted by a different guard | AC-4a part 3's read-only attack, if the image already lacks the write permission for an unrelated reason — record *why* the write failed |
| A guard satisfied by a broken implementation | A drain assertion satisfied by a pod that never becomes ready at all |
| **A canary sized so it never reaches the hazard** | AC-4a's shim must be a **working** shim that actually launches Chromium with `--no-sandbox`, exactly as @qa built it — not a stub file. *Standing rule from wave 5: size the fixture so the hazard actually occurs* |
| Expected value imported from the module under test | AC-6's grace period computed by the same helper the chart uses |
| A pinned copy whose provenance nothing checks | AC-25's `BASE_SHA256` — re-check against the file, do not trust the constant |
| A source scan over an artefact that quotes itself | AC-12's exact-time-deletion check, if run over a document that quotes §6.2's prohibition. Scope it to the **claims** this story makes |
| A test that journals its own ordering and calls it an observation | AC-5a's reaping proven by reading the **process table**, not by asserting an init was configured |
| **A guard whose name states a structural property of a production symbol while its body asserts over a test-local stand-in** | AC-19a's watch: it must drive the **production** `BffSessionAuthenticationFilter` under both property values, not a test double of it. This is the sixteenth shape, found twice in 10.17 |
| An assertion whose expected value is imported from the module under test | AC-13a comparing the annotation against a test constant instead of against the rendered `STUDIO_SSE_HEARTBEAT` |

### Two standing rules from wave 5, restated because this story is where they bite

- **Size the fixture so the hazard actually occurs.** AC-4a's shim registry, AC-5a's orphaned
  grandchild, AC-23a's kill-switch drive — each must be large enough, real enough and slow enough
  that the failure it models can happen.
- **Make the mutation land inside the measurement window.** A render mutation must be applied
  **before** the `helm template` invocation the assertion reads, not to a cached rendering. An
  attack mutation must be applied before the container starts, not after.

**Four things must not be cut apart.**

1. **Never cut the security context from reaping and drain.** A pod that is hardened but cannot reap
   leaves zombie Chromium processes accumulating in a `readOnlyRootFilesystem` container until it is
   evicted, and a pod that is hardened but cannot drain kills admitted work mid-run — which is
   strictly worse than today, where a developer machine at least finishes the run. SPK-04 asks both
   as one question (its question 6 is the kill-tree and slot recovery under the chosen policy), and
   they are one change.
2. **Never cut the NetworkPolicy from the destination configuration it constrains.** An egress
   policy written without the callback and object-store destinations the runner actually uses turns
   the first staging run into a **silent hang** rather than a refusal — the runner's admission
   succeeds, the browser starts, and the terminal report never arrives. The policy's peers and the
   runner's three `PERMITTED_DESTINATIONS` are one fact.
3. **Never cut the bypass closure (AC-19a) from the header-identity path.** Closing
   `isCoreServiceBypassed` while `X-User-Id` is still trusted **moves** the bypass rather than
   removing it, and produces the worst available outcome: a story that reports "production auth
   bypass absent" while any client that can reach the pod supplies its own roles. This is the
   two-guards-each-covering-half shape, applied to authentication.
4. **Never cut AC-27 from either half.** The deferral bookkeeping is what keeps eight other stories'
   blocked criteria attached to an owner. A half that ships without it orphans them silently, which
   is how a `b` half becomes a passed criterion three waves later.

**If it outgrows even the two-way cut**, @po's order is: **AC-32 (O-16) first** — latent, not live, one
compliant caller, *"not urgent"* in §23.1's own words — and **the runbook last, not first**. BRD §8 makes the
runbook a launch exit criterion with a named owner, and *"the only deliverable whose absence is visible"* is
a reason to keep it rather than to cut it. **The security criteria may never be the part that is deferred:
they are the story** — ratified.

## Related findings — referenced, **not** absorbed

**1. MED-2, the Testcontainers JDBC liveness bug — not this story's, and here is why.**
@qa diagnosed it with a thread dump rather than an inference: the `Test worker` thread is **BLOCKED
on an object monitor** inside `ContainerDatabaseDriver.connect`, starting the next context's Flyway
migration and waiting to lock the one process-wide `org.testcontainers.jdbc.ContainerDatabaseDriver`;
the monitor is held by a daemon **`HikariPool-4 connection adder`** belonging to an *already-finished*
context's pool, itself inside `JdbcDatabaseContainer.createConnection`'s retry-sleep loop against a
container that has gone away. It stalls `--tests` slices reproducibly, and **the full suite is not
immune** — one `check --continue` hung with the identical stack after 612 tests. It hides
**liveness, not correctness**, and a CI job that hits it **hangs rather than fails**, which is the
worse failure mode.

**It is not this story's**, for three reasons. The retired epic's §10.18 scope line is *"runner
Deployment, callback network path, Sonic controls, real SSE/media route and operations handover"* —
a Gradle/Testcontainers JDBC configuration is none of those, and taking it would be Article IV.
@qa's own gate assigns it: `suggested_owner: '@devops / epic-level, not this story'`. And its fix
(`minimumIdle`/`idleTimeout`, eager pool warm-up, or a `connectTimeout` on the Testcontainers JDBC
URL) touches the backend's test infrastructure, which this story does not otherwise open.

**What this story does owe it: AC-22's clause that a hung gate is not a pass.** This story runs the
backend suite for a baseline it expects to move, so it is the most likely story in the epic to hit
the hang and the most likely to mis-read it. The hang, its stack and the retry are recorded.
**It still has no owner**, and that is raised as *Open Question* 2.

## Implementation Notes

- **Start with the rendering harness, not with a template.** Every chart criterion asserts on
  `helm template` output. Build the harness that renders all four value sets, parses the YAML and
  exposes the documents by kind and name **first**; every subsequent criterion is then a structural
  assertion plus a render mutation, and the mutations are cheap. Building templates first and the
  harness last produces a story whose guards are all source scans.
- **The comparison, not the constant, is the criterion.** AC-1 (port), AC-2a (scratch path), AC-6
  (grace period), AC-10a (secret names), AC-12 (retention), AC-13a (timeout vs heartbeat) are each
  written as a comparison **between two values in the same rendered manifest**. A value compared
  against a literal written in the test is a second derivation of the fact, which is this epic's
  most-repeated defect and the one that is invisible until staging.
- **AC-4a's attack is a container experiment, not a Kubernetes one.** It needs `docker run` with
  `--read-only` and two tmpfs mounts standing in for the `emptyDir`s — not a cluster. Run the
  *successful* form first, record it, then run the controlled form. If the successful form does not
  succeed, stop: either the image changed or the experiment is wrong, and a control that appears to
  work against an attack that no longer works is worth nothing.
- **The three bypass paths are one change.** `isCoreServiceBypassed`, the `X-User-Id` header path
  and `applyTemporaryCsiReadBypass` all produce an identity the platform did not vouch for. Closing
  them in separate commits is fine; shipping one without the others is the half-property shape.
  Note that the header path is checked **before** the bypass in `resolveIdentity`, so a test that
  closes only the bypass and sends a header observes no change at all.
- **Expect the 23 to move, and say how.** AC-19a changes what every `/api/**` test authenticates as.
  Some of the 23 may go green; some currently-green tests may go red because they relied on the
  admin identity. Both directions are data. Name each class that moves.
- **The dispatcher is off by default.** `studio.execution.dispatcher.enabled` defaults to `false`;
  a staging deployment that forgets it will queue work and dispatch nothing, which looks exactly
  like an egress problem. Wire it deliberately and note it in the runbook's stuck-runs section.
- **Do not fix the port disagreement by changing the runner's default.** Fact 7 is two derivations
  of one value; AC-1 resolves it by making the chart the single source and comparing the rendered
  values to each other. Changing `config.ts`'s fallback to 8090 would create a third copy.
- **If an implementation finds it needs a new `PLAYWRIGHT_*` or `HOME`-shaped environment key, stop
  and say so** rather than adding it. That is the signal AC-4a exists to catch, and 10.13 recorded
  the same rule for its own constructor.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on
  2026-09-11: `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a
  Darwin host, the CLI is absent, and `graceful_degradation.skip_if_not_installed: true` applies. A
  draft checklist expecting such a section is satisfied by that ruling.
- **Starting values, not commitments.** Every §8.5 value this story renders — the SSE heartbeat and
  lifetime, the deadlines, `POOL_SIZE=1`, the replica count — is a starting value to be tuned
  against staging measurements. AC-14's measurement may move the lifetime; that is the mechanism
  working, not a criterion failing.
- **A spike that returns a negative result is closed, not failed.** SPK-05 finding only static L3/L4
  policy, or SPK-02 finding a bearer-only gateway, are valid closures that select documented
  fallbacks. Record the fallback, the limitation, and who accepted it. Silently weakening an
  architecture guarantee to make a criterion green is the one prohibited outcome.
