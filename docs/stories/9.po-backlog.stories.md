# Story 9.1 — Composable Filter by LOB & CSI

| Field | Value |
|---|---|

---

## User Story

**As an** operations analyst,
**I want** to compose filters by Line of Business (LOB) and CSI with multi-selection,
**so that** I can narrow Checks views to the systems I care about without repeatedly rebuilding scope.

---

## Problem Statement

Global scope today is primarily CSI-centric (Scope Bar / Global Search). LOB is not a first-class filter dimension. Users who work across a Line of Business need to select many CSIs one by one instead of starting from the LOB grouping.

---

## Domain Rules

- A **LOB (Line of Business)** is a **group of CSIs**.
- Both **LOB** and **CSI** support **multi-selection**.
- Selecting one or more LOBs defines the candidate CSI set as the **union** of CSIs belonging to those LOBs.
- The user may further multi-select CSIs within that candidate set.
- **Effective scope** = selected CSIs if any are selected; otherwise all CSIs in the selected LOB(s).
- If no LOB is selected, CSI options follow the user’s accessible CSI set (ownership / visibility rules unchanged).

---

## Acceptance Criteria

### A — LOB & CSI filter UI

- [ ] **AC-1:** User can multi-select LOBs from a LOB picker in the global/composable filter UI.
- [ ] **AC-2:** User can multi-select CSIs from a CSI picker.
- [ ] **AC-3:** When one or more LOBs are selected, the CSI picker options are restricted to the union of CSIs in those LOBs.
- [ ] **AC-4:** Active LOB and CSI selections are shown as chips/tokens and can be cleared individually or all at once.

### B — Filter composition & application

- [ ] **AC-5:** Effective CSI set is computed as:
  - LOB(s) selected, no CSI selected → all CSIs in selected LOB(s)
  - LOB(s) + CSI(s) selected → intersection of selected CSIs with the LOB union (selected CSIs only)
  - No LOB selected → selected CSIs only (or unscoped if none selected)
- [ ] **AC-6:** All Checks and Dashboard results respect the effective CSI set.
- [ ] **AC-7:** Empty state is shown when no checks match the composed filter.

### C — Session behavior & quality

- [ ] **AC-8:** Composed filter state is retained while navigating between in-scope pages in the same session.
- [ ] **AC-9:** Unit/integration tests cover: LOB-only, CSI-only, LOB+CSI, clear-all, and LOB narrowing of CSI options.

---

## Scope

- First-class LOB model as a group of CSIs (source of membership TBD with architecture).
- Multi-select composable filter UI for LOB + CSI.
- Apply effective scope to All Checks and Dashboard.

### Out of scope

- Saved named filters (Story 9.2).
- Team-shared / org-wide filter catalogs.
- Changing CSI ownership or authz rules.

---

## Open Questions

- LOB→CSI membership source of truth (Checks DB, CSI/Core API, or config).
- Whether Studio / Reports list honor the same composed filter in v1.
- URL persistence vs session-only (shareable links).

## User Story

**As a** frequent Checks user,
**I want** to save my current filter configuration under a name and reuse it later,
**so that** I don’t rebuild the same LOB/CSI scope every session.

---

## Problem Statement

After Story 9.1, users can compose LOB + CSI filters, but the configuration is session-ephemeral. Power users who repeatedly monitor the same LOB/CSI sets need durable, named presets.

---

## Acceptance Criteria

### A — Save & manage

- [ ] **AC-1:** From the filter UI, user can **Save filter** when at least one filter dimension is active (LOB and/or CSI).
- [ ] **AC-2:** User provides a display name; name must be unique per user — duplicate names are rejected with a clear validation error.
- [ ] **AC-3:** Saved filter stores the full composable state from Story 9.1 (selected LOB IDs and CSI IDs).
- [ ] **AC-4:** User can rename, overwrite (update), and delete a saved filter they own.

### B — Apply & persist

- [ ] **AC-5:** Saved filters appear in a picker/list; applying one restores LOB + CSI selections and recomputes the effective CSI set.
- [ ] **AC-6:** Saved filters are **user-scoped** and persist across sessions (backend API + storage — not browser-local-only).
- [ ] **AC-7:** Unauthorized access to another user’s saved filter returns 401/403.

### C — Quality

- [ ] **AC-8:** Tests cover: save → reload session → apply; update; delete; duplicate-name rejection; apply restores correct LOB/CSI chips and results.

---

## Scope

- CRUD for user-owned saved filters.
- FE wiring: save, list, apply, rename, delete.
- Persistence of LOB + CSI multi-select state from Story 9.1.

### Out of scope

- Sharing saved filters across team / CSI / org.
- Saving unrelated dimensions (status, free-text search) unless already part of the composable model when this story starts.
- “Set as default on login” (follow-up unless PO expands scope).

---

## Open Questions

- Include tags / environment in the saved payload if those filters already exist alongside LOB/CSI?
- Default-on-login preset in this story or later?

## User Story

**As a** report owner,
**I want** the report email subject to support **current date** and **overall status** variables,
**so that** recipients see when the report was sent and the rollup health without a static subject line.

---

## Problem Statement

The report builder exposes a Subject field, but delivery currently uses a hardcoded pattern in `ReportMailSender` (`[PUT Checks] {name} — {date}`). Authors cannot control a dynamic subject that includes overall status. Only two variables are required for v1: **current date** and **overall status**.

---

## Variable Catalog (v1)

| Variable | Resolves to |
|---|---|
| `{{date}}` | Current date at preview/delivery time |
| `{{overallStatus}}` | Report rollup status (e.g. PASSING / WARNING / FAILING) |

No other subject variables are in scope for this story.

---

## Acceptance Criteria

### A — Authoring & preview

- [ ] **AC-1:** Report Subject field accepts a template string that may include `{{date}}` and/or `{{overallStatus}}`.
- [ ] **AC-2:** UI documents the two supported variables (help text and/or insert chips).
- [ ] **AC-3:** Live Preview shows the **resolved** subject using current date and computed overall status.

### B — Delivery

- [ ] **AC-4:** Scheduled delivery and run-now emails use the resolved subject (not only the hardcoded `[PUT Checks] {name} — {date}` pattern).
- [ ] **AC-5:** If subject is empty, fallback remains the existing default subject pattern.
- [ ] **AC-6:** After resolution, subject length is validated/enforced to an SMTP-safe max (e.g. 255 chars).

### C — Edge cases & quality

- [ ] **AC-7:** Unknown tokens are left unresolved as-is (or rejected on save — document chosen behavior in implementation notes).
- [ ] **AC-8:** Tests cover: both variables resolve; one variable only; empty subject fallback; delivery IT asserts custom resolved subject.

---

## Scope

- Subject template support for `{{date}}` and `{{overallStatus}}` only.
- Resolve at preview and at send time.
- Update backend mail sender + FE preview.

### Out of scope

- Additional variables (report name, CSI list, environment, failing count, etc.).
- Email body templating.
- Per-recipient subject customization.

---

## Open Questions

- Date format and timezone (schedule TZ vs fixed EST vs user locale).
- Whether subject remains fully free-form or always prefixed with `[PUT Checks]`.
- Token syntax confirmation (`{{var}}` vs `{var}`).

# Story 9.4 — Remove My CSIs / Pin Capability

## User Story

**As a** Checks user on the Home page,
**I want** the redundant My CSIs / pin feature removed,
**so that** CSI selection is done through Global Search only and the Home experience is simpler and less overlapping.

---

## Problem Statement

Home currently offers two ways to choose/favor a CSI:

1. **Global Search** — search and set search context (primary, layout-level).
2. **My CSIs / Pin** — pin CSIs from Global Search or CSI Overview; pinned cards on Home set the same search context.

These overlap. Pinning adds localStorage-backed “favorites” (`checks.pinnedCsiIds.*`) and a Home section that duplicates Global Search’s job of selecting CSI scope. PO decision: remove My CSIs / pin capability.

---

## Acceptance Criteria

### A — Remove Home “My CSIs”

- [ ] **AC-1:** Home page no longer renders the **My CSIs** section (`PinnedCSIs`).
- [ ] **AC-2:** Home empty/guidance copy no longer references pinning or “My CSIs” (e.g. “set one from My CSIs”).

### B — Remove pin actions from UI

- [ ] **AC-3:** Global Search no longer shows Pin / Pinned actions or “Pinned to My CSIs” toast.
- [ ] **AC-4:** CSI Overview no longer shows Pin / Unpin (push-pin) controls.

### C — Remove state & persistence

- [ ] **AC-5:** Redux pin APIs removed or unused: `pinnedCsiIds`, `pinCsi`, `unpinCsi`, `setPinnedCsiIds` (and related selectors).
- [ ] **AC-6:** localStorage persistence for pinned CSI IDs is removed (read + write of `checks.pinnedCsiIds.*`).
- [ ] **AC-7:** No dead imports/components remain (`PinnedCSIs` deleted or fully unused).

### D — Quality

- [ ] **AC-8:** Type-check / unit tests updated; any tests asserting pin / My CSIs behavior are removed or rewritten around Global Search context only.
- [ ] **AC-9:** Manual smoke: Home + Global Search still set CSI search context; no pin UI or My CSIs section appears.

---

## Scope

- Remove My CSIs section on Home.
- Remove pin/unpin entry points (Global Search, CSI Overview).
- Remove client-side pin state and localStorage persistence.
- Keep Global Search / search context as the single CSI selection path on Home.

### Out of scope

- Changing Global Search behavior beyond removing pin.
- Server-side “favorite CSI” API (none required; pin was client-only).
- LOB/CSI composable filter (Stories 9.1–9.2).
