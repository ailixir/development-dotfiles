## User Story

**As a** CSI-authorized support engineer who has just written an English checklist and has no way to see what the machine decided it meant,
**I want** each of my own lines shown back to me with the action, target and assertion the validator accepted, the executable source one expansion away, and the plain-language reasons when a line could not be made runnable,
**so that** the thing I approve is the thing that will run — and when I approve it, I approve *that* revision, not whatever the compiler produced while I was reading.

---

## Problem Statement

Every backend half of the confirmation mechanism exists or is landing. `ui_test_revisions` is immutable and write-once on confirmation (10.4). The compile pipeline bounds its work, screens credentials and publishes candidates (10.8). Story 10.9 is landing the bounded repair loop, the `confirm-compile` transaction whose four-field body is conditional in SQL, and — under ADR-002 §16 — the typed diagnostics that a failed compile leaves on the draft.

**Nothing renders any of it.** Verified on the branch at `34138201f`: `frontend/src/services/api/studioApi.ts` has no `compileTest` and no `confirmCompile`; `frontend/src/types/studio/studioTypes.ts` declares `TestDto` without `compileError` and `compileDiagnostics`; and the one view that claims to show generated code, `frontend/src/components/studio/CodeTab.tsx`, renders **client-generated Python** from `@/utils/studio/codegen/pythonGenerator` — a language architecture §8.3 retired and a derivation the server never made.

So today the product's whole trust argument — PRD §5.2, *"The user should feel confident that their plain English commands are being understood"* — is unbacked. A user can save a draft, and that is all. There is no path from `AWAITING_CONFIRMATION` to `READY`, which means no path to a run at all, which is why 10.11 blocks on this story rather than on 10.7.

Four properties make this more than "add a panel".

1. **The five states are five different sentences, and a default branch erases four of them.** `STALE`, `COMPILING`, `AWAITING_CONFIRMATION`, `READY` and `NEEDS_REVISION` (§4.2) differ in what is true, in what the user may do, and in *who can clear the condition*. `STALE` is a failure that is not the author's fault and whose whole remedy is an explicit recompile; `NEEDS_REVISION` is the author's to fix and no amount of retrying will move it. Collapsing any pair into "something went wrong" is the failure mode ADR-002 §14.3 settled on the wire and which this surface can undo in one `switch` statement with a `default:`.
2. **A bounded report rendered as a complete one is a lie the user cannot detect.** `DiagnosticsBounder` refuses to be silent about truncation at three levels — a marker inside a clamped `message` or `excerpt`, `truncated` per step, `truncated` plus `truncationReason` on the document. ADR-002 §16.5 says so and then says what follows: *"a client that renders this document without rendering those flags turns a bounded report into a false one — which is a requirement on 10.10, not decoration."* The failure is silent by construction: the surface looks finished, the user reads three problems, fixes three problems, and the fourth was shed to fit a byte cap.
3. **Confirmation is exact or it is nothing — and the client is the one holding the identity.** §4.2 fixes the body as `{revisionId, artifactHash, sourceRevision, configurationRevision}` and the transaction is conditional on all four. The client's obligation is that those four values come from *the response the user was looking at*, and that a `409` returns the user to a fresh, deliberate review rather than re-sending against whatever is current now. The epic's release ordering is blunt about the alternative: *"No temporary gate bypass or production auto-confirmation is allowed."*
4. **And the client cannot currently build that body.** Verified, not inferred: the amended `openapi.yaml` declares `ConfirmCompileRequest.required` as four fields, and `artifactHash` appears on **no** declared `2xx` response of any `tests`-tagged operation. `TestDto` carries `currentCandidateRevisionId` but not the hash, not the artifact and not the source. `UITestDto.java` matches it field for field. The data exists — `UITestRevision` has `source`, `artifact`, `artifactHash` — and travels on the internal `RunJob` envelope, but nothing public returns it. The same gap denies this story the *"trusted action/target/assertion summary"* and the *"expandable executable source"* its own epic scope line requires, because both are derived from validated operations (§4.7) and the validated artifact is not on the wire. That is AC-15, and under ADR-002 §12 it is a Class C change this story may propose and may not land.

## Size call — M in the manifest, L in this draft

The manifest records `size: M`. Three things have landed or been discovered since that estimate, and the honest scope is **L**. This is the same shape of cause that moved 10.9 and 10.13 from M to L at wave-4 validation: a ruling arriving after the number.

**What would make it an M:** if @architect's ruling on AC-15 declines the artifact surface for V1, half (ii) of the split hint disappears — but so does confirmation, and with it the story's reason to exist. The realistic M is the *other* direction: if (i) and (ii) are landed as two stories, each is an M. That is the split hint, and it is the named mitigation.

## Acceptance Criteria

Every criterion below is falsifiable and cites its source. Criteria split `a`/`b` follow the epic convention established by 10.3: the `a` part is verifiable now, the `b` part names its owner and gate and is recorded **skipped, never passed** — never quietly marked done.

### The compile state is legible, and five states are not one state

- [x] **AC-1:** **Every value of `compileStatus` renders a distinct, named state, and the mapping is total with no fallback branch.** §4.2 fixes the five: `STALE | COMPILING | AWAITING_CONFIRMATION | READY | NEEDS_REVISION`. The test **reads the union from the document** — `openapi.yaml` → `components.schemas.TestDto.properties.compileStatus.enum` — and asserts that each member produces a rendered state with a distinct accessible name, and that no two members render the same one. **No `default:` branch and no `??` fallback exists in the mapping**: a sixth value must be a compile error or a red test, not a silent "something went wrong". *Anti-vacuous:* the assertion is falsified by (a) adding a sixth member to an in-test copy of the document → red, and (b) replacing the exhaustive mapping with one carrying a default branch → red. Both recorded in the Dev Agent Record. This is the same mechanism ADR-002 §18.3 requires for the codes (AC-4); it is installed once and used twice.
- [x] **AC-2:** **Each state states what is true, what the user may do next, and what is blocked — and the four facts below are rendered, not implied.** One test per state, asserting on rendered text and control state:
  | State | What must be rendered | Source |
  |---|---|---|
  | `COMPILING` | a compile is in flight for the source shown; nothing is confirmable yet; the draft is saved | §4.2, §8.3 (`PUT` persists the draft and enqueues compile) |
  | `AWAITING_CONFIRMATION` | a candidate exists and is **not** runnable until this user confirms it; confirmation is the only route to `READY` | §4.2 *"It becomes `AWAITING_CONFIRMATION`"*; §10.8 epic *"never READY automatically"* |
  | `READY` | the confirmed revision is runnable; its identity is shown | §4.6 |
  | `NEEDS_REVISION` | the candidate is **not** runnable, the reasons are the author's to act on, and retrying without editing will not help | §4.7, BRD §6 *"blocks only that candidate with a plain-language reason"* |
  | `STALE` | the draft is **saved and unchanged**, any previously confirmed revision **still runs**, this is not the author's fault, and an explicit recompile is the whole remedy | `CompileError` schema description (all four clauses are in the contract text), §4.7, BRD §6 *"drafts still save … unchanged confirmed tests can execute"* |
- [x] **AC-3:** **A confirmed test whose draft has moved is visibly flagged as needing re-confirmation, and the flag is derived from the body rather than from a local edit event.** BRD §6: *"Editing a confirmed test clearly flags it as needing re-confirmation."* The predicate is `confirmedRevisionId !== null && compileStatus !== 'READY'`, read from one `GET /tests/{id}` body — which is exactly the shape of the contract's own `needsRevision` example (`confirmedRevisionId` set, `compileStatus: NEEDS_REVISION`). It is **not** derived from "the user typed something", because a reload, a second tab and a configuration-only change all produce the condition without a local edit (§4.2: configuration-only changes create a new candidate and require reconfirmation). A test drives each of the three origins and asserts the same flag; a fourth asserts a name/description change does **not** raise it (§4.2: *"Name/description changes do not invalidate confirmation"*) — and that fourth test is the one that proves the flag is not simply "dirty".
- [x] **AC-4:** **The `compileError` code set is read from the contract, compared both ways, and is the only copy.** ADR-002 §18.3 assigns this story the mechanism: *"Whichever lands first should install the document-reading assertion once, and the other should extend it rather than write a second one. Two hand-maintained copies of one vocabulary in two languages is the arrangement that produced INT-4."* In `frontend/src/services/mocks/studio/studioContract.test.ts` — which already parses `openapi.yaml` and is named in §18.3 as the natural home — assert that the UI's code→explanation map and `CompileError.x-compile-error-codes` are the **same set, in both directions**: no code in the document without an explanation, no explanation for a code the document does not declare. *Anti-vacuous, and aimed squarely at the epic's fifth precedent (a pin check with an uncompared fifth copy):* the assertion is falsified by (a) adding a twelfth code to an in-test copy of the document → red, and (b) deleting one entry from the UI map → red. A one-directional `every code has an entry` check does not satisfy this criterion and is named here as insufficient. 10.11 **extends this assertion** for `ExecutionErrorCode` (ADR-002 §18.3, O-12); it does not write a second one.
- [x] **AC-5:** **An undeclared `compileError.code` renders honestly rather than blankly.** §14.7 permits the set to grow — *"A story that lands a new compile failure condition may add its code to that list in its own PR"* — and `code` is deliberately a free string, not an enum (§16.4). So an unrecognized code renders the generic `STALE` narrative of AC-2 **plus the code verbatim**, and never an empty string, never `undefined`, and never a silently-omitted panel. A test feeds a code that is not in the eleven and asserts all three.

### The diagnostics document, rendered without turning a bounded report into a false one

- [x] **AC-6:** **One row per original step, index-aligned to the `steps` in the same body, accepted steps included.** `CompileStepDiagnostics`: *"One entry per original source step, index aligned, present even where the validator returned nothing for that step (§4.4) … The entry count equals the length of `steps` on the same `TestDto`."* Artifact-level rejections (`CompileDiagnostics.artifact`, *"belonging to no single step"*) render in their own region, attached to no step. *Anti-vacuous, aimed at the epic's third precedent (an isolation test that deleted its own coverage):* the fixture is **not degenerate** — it carries at least four steps with an **accepted step between two rejected ones**, so an off-by-one join produces a visibly wrong attribution rather than a coincidentally-correct one. The falsification is an index shift of one on the join → the named test red, recorded. A test also asserts the row count equals `steps.length` for every fixture, and that a document whose `steps` array is shorter than `steps` is surfaced as a defect rather than silently padded.
- [x] **AC-7:** **All three truncation levels are rendered, each proven by its own test on a fixture that actually carries it.** ADR-002 §16.5 and the `CompileDiagnostics` description:
  1. a clamped `message` or `excerpt` carries a visible truncation marker → rendered so the marker survives (not trimmed, not ellipsised away);
  2. `CompileStepDiagnostics.truncated: true` → that step says *"there were more problems for this step than we are showing"*, distinguished in words from "there were no more problems";
  3. document-level `truncated: true` with `truncationReason: TOTAL_BYTES` → the surface says whole steps' reasons were shed and which fact that is.

  Three tests, three fixtures, three falsifications: deleting each render in turn must turn exactly the corresponding named test red, recorded in the Dev Agent Record. *This is aimed at the epic's first two precedents — a canary that stayed green with redaction removed, and an assertion green with the redactor deleted.* A single test that renders one fixture and asserts "the flags appear somewhere" does not satisfy this criterion.

  **@po amendment 2026-09-11 (wave-4 lesson: a fixture must be sized so the hazard actually occurs).** For levels 1 and 2 the fixture is **not** a hand-set boolean. A fixture that sets `truncated: true` on a short, uncut `message` proves the renderer reads a flag; it does not prove the renderer survives a real clamp, and the two failures are different — the second is the one where the marker is trimmed away by the layout, ellipsised by CSS, or lost because the renderer re-clamps the already-clamped string. So: the level-1 fixture carries a `message` and an `excerpt` whose bytes **actually exceed** `DiagnosticsBounder`'s declared caps and carry the bounder's real marker at its real position, and the level-2 fixture carries a step whose diagnostic list was **actually shed** to produce `truncated: true`. Level 3 may be hand-set, because `truncationReason: TOTAL_BYTES` is a document-level fact with no clamped string behind it. Where a real bound cannot be produced from a fixture on the client, the fixture is generated from the contract's declared maxima and the derivation is recorded — never a round number typed into the file.
- [x] **AC-8:** **`attempts` and `exhausted` are rendered as what they mean.** ADR-002 §16.2 fixes the two keys precisely so this story is not guessing. `attempts` renders as *how many times the compiler tried*, `exhausted: true` renders as *the bound was reached and the result is still not runnable — the remedy is editing the step, not retrying* (§4.3 bounds repair at two attempts; §4.7 *"Exhausted repair yields NEEDS_REVISION"*). A test asserts that `exhausted: true` does **not** render a retry affordance, and that `exhausted: false` with `attempts: 1` does not imply a repair happened. The document describes the **last attempt only** and the surface never implies it is a history.
- [x] **AC-9:** **Nothing on this surface states or implies that a step the validator accepted does what its author meant.** §4.1: static validation *"cannot prove the locator matches the application or the assertion captures the user's intent"*; §4.5: *"This restriction limits executable capabilities, not semantic mistakes"*; ADR-002 §16.9 item 6, binding on this story by name; BRD §8 names the realized risk — *"Users treat AI-generated code confirmation as a rubber stamp"*. The assertion is made **on the rendered output of every state, for every fixture** — `render()` then read the text — against a checked-in list of forbidden claim patterns (*verified, correct, guaranteed, will pass, confirmed working, tested*). *Anti-vacuous, aimed at the epic's sixth precedent (a log assertion that grepped source text instead of capturing runtime output):* asserting against the component source file, the JSX, or a constants module does **not** satisfy this criterion; the assertion runs against rendered text, and is falsified by planting one forbidden phrase in one state's copy → red.

### Confirmation is exact, or it does not happen

- [x] **AC-10:** **The confirm control is enabled in exactly one state and for exactly the identity on screen.** Enabled only when `compileStatus === 'AWAITING_CONFIRMATION'` **and** `currentCandidateRevisionId !== null` **and** the identity the request would carry is the identity currently rendered. A test enumerates all five states (reading the union per AC-1) and asserts the control is enabled in exactly one of them. Epic release ordering: *"No temporary gate bypass or production auto-confirmation is allowed."* No configuration flag, query parameter, environment variable or developer affordance enables it elsewhere, and a test enumerates the module's exported surface to assert no such escape exists.

  **@po amendment 2026-09-11 — the export enumeration is a floor and is named as one.** Enumerating exports proves no *exported* escape hatch. A module-local `if (import.meta.env.DEV)`, a `process.env` read, or a prop defaulted to a permissive value inside the component is invisible to it — this is the epic's *"a scan keyed on a receiver's variable name"* shape wearing a different hat. The load-bearing assertion is therefore the **behavioural** one, and it is stated first: the five-state enumeration drives the control through every value of the union with the environment, the query string and the props held at their production values, and asserts exactly one enablement. The export enumeration supplements it; it does not stand alone, and the Dev Agent Record says which of the two a given mutation reddened.
- [x] **AC-11(a):** **The request body is exactly the four declared fields, taken from the one response the user is looking at.** `ConfirmCompileRequest` = `{revisionId, artifactHash, sourceRevision, configurationRevision}` (§4.2, §8.3). All four are read from a **single** `GET /tests/{id}` body held as one value — not re-read per field, not recombined from two fetches, not taken from Redux state that another request may have updated in between. *Anti-vacuous, aimed at the epic's fifth precedent (a contract check comparing route strings instead of response bodies):* the assertion is made on the **captured request body** via the MSW handler (`await request.json()`), never on a spy's call arguments, and it compares the four values against the fixture that was rendered. Two falsifications: omit one field from the body → red; source `sourceRevision` from a second, newer fetch → red. Both recorded.
- [ ] **AC-11(b):** *(skipped, never passed — see Dev Agent Record)* *(**Blocked** — see AC-15. Owner: @architect ruling, then this story or its (ii) half.)* `artifactHash` in that body. **No declared `2xx` response of any `tests`-tagged operation carries it** (verified against the amended `openapi.yaml` at `34138201f`). Until the ruling lands, the accessor that supplies it has exactly one implementation, it returns *unavailable*, and the confirm control is disabled with an explicit explanation naming the blocker. **A hash is never fabricated, never recomputed client-side from anything, and never defaulted** — a client-computed `artifactHash` would be the client asserting what the server canonicalized, which is the one thing the conditional transaction exists to check. Recorded **skipped, never passed**. **@po 2026-09-15 (ADR-002 O-17 routing): UNBLOCKED by ADR-002 §21, which rules candidate A and names `currentCandidateArtifactHash` / `currentCandidateArtifact` as normative. This checkbox stays unticked and this criterion stays *skipped, never passed* in this story, because that is what shipped.**
- [x] **AC-12:** **`409` returns the user to a fresh, deliberate review and never silently accepts new code.** The declared code set is exactly `x-conflict-codes: [STALE_CANDIDATE, TEST_DELETED, TEST_QUARANTINED]` (read from the document, as in AC-4 — not transcribed). Behaviour per code, one test each:
  - `STALE_CANDIDATE` — refetch `GET /tests/{id}`, render what changed, and return the confirm control to its **unconfirmed** state. The refreshed identity is **not** auto-confirmed, and **no confirm request is re-sent** without a new, deliberate act by the user. Epic §10.10: *"refresh on 409 without silently accepting new code."*
  - `TEST_DELETED` / `TEST_QUARANTINED` — **not retriable by the caller** (ADR-002 §14.3), so no retry affordance is offered; `TEST_QUARANTINED` says the author's work **survives** and awaits CSI resolution, and is never reported as a deletion (§14.3: *"Reporting a quarantined draft as `TEST_DELETED` would state that an authored test was deleted, which BRD §9 forbids"*). No restore action is offered for a quarantined draft.

  **The branch is taken on `error`, never on `message`.** @po's ruling on 10.9 (2026-09-11) is a forward constraint on this story: *"the message is human-readable prose and is not a branch key."* A test replaces every `message` with an unrelated string and asserts all three branches still resolve correctly. *Anti-vacuous:* falsified by making the `STALE_CANDIDATE` path re-send the confirm request after refetching → the named test red, recorded. That mutation is the shape of the epic's first precedent — a guard that stays green while the thing it guards is gone.
- [x] **AC-13:** **A double submission sends one request.** 10.9's `confirm` is conditional on `confirmed_by IS NULL`, so a second confirmation of the same revision answers `409 STALE_CANDIDATE`; @po ruled on 2026-09-11 that *"A double-click is 10.10's to debounce, not this story's to absorb into a guarantee."* Exactly one request leaves the client per deliberate confirmation; a second activation while one is in flight sends nothing and is not queued. Asserted by counting requests observed by the MSW handler, not by asserting a `disabled` prop — a disabled attribute set after the second click has already fired proves nothing.

  **@po amendment 2026-09-11 (wave-4 lesson: the mutation must land inside the measurement window).** The in-flight window is **constructed, not hoped for**. The MSW handler for `confirm-compile` is held open on a deferred promise; the second activation is dispatched **while that promise is unresolved**; only then is it resolved and the request count read. A test whose second click fires after the first request has already settled is measuring a settled state and would pass with no debounce at all — it is named here as insufficient. *Falsification:* remove the in-flight guard → the named test observes two requests → red, with the handler still held open, recorded in AC-21's table.
- [x] **AC-14:** **An explicit recompile exists for the `STALE` case and speaks the declared contract.** `CompileError`'s own description — *"an explicit recompile is the whole remedy"* — and §4.1 (*"Compile on source changes or explicit recompile"*) put the control here. It calls `POST /tests/{id}/compile`, and handles what the operation declares and nothing else: `202` → `COMPILING`; `400` with the four authoring-bound codes (`SOURCE_TOO_MANY_STEPS`, `SOURCE_LINE_TOO_LONG`, `SOURCE_TOO_LARGE`, `INLINE_CREDENTIAL`), whose messages name a step index and never its text; `409` with `[TEST_DELETED, TEST_QUARANTINED]`, read from the document. The `202` explicitly does **not** mean success — the operation's own description says so — and the surface must not report it as one.

## Implementation Notes

### The one place the identity lives
Everything the confirm body carries comes from a **single** `GET /tests/{id}` response held as one immutable value for the duration of the review. Not four selectors over a Redux slice, not a re-read per field, not a recombination of a list entry with a detail entry. ADR-002 §16.3's argument for why diagnostics need no `sourceRevision` of their own is the same argument: *"a client aligning `steps[i]` to `compileDiagnostics.steps[i]` is aligning two facts that were read together."* That guarantee is the server's, and it survives only if the client does not take it apart. A refetch produces a **new** value and an explicitly unconfirmed control (AC-12), never a partial update of the old one.

### Why the summary must not be derived from the English
`parseSteps` and `pythonGenerator` both exist and both would produce something that looks like an action summary in an afternoon. Using either would present *the client's* reading of the English as *the validator's* reading of the artifact. The user would then confirm a summary the server never produced, against a hash the server computed from something else — and the epic's whole trust argument inverts: the human control point becomes the place where two different interpretations are silently reconciled. AC-16(a)'s import assertion exists to keep that shortcut from being taken under time pressure, because it is the shortcut that makes the story finishable and worthless.

### Why the escalation test is written this way
The property it asserts — *every required field of a request body is obtainable from some declared response* — is true of every other route in the document, which is what makes its failure on `artifactHash` informative rather than arbitrary. It reads the document rather than naming the field, so it also covers a future request body with the same defect. And it goes green on the amendment with no edit to itself, which is the difference between an escalation and a `TODO`. The precedent is `ExecutionErrorCodeContractEscalationTest` (10.7's), which went `1/2 → 2/2` with no change to the test when ADR-002 §15 landed — recorded in §13's log as the measurement that mattered.

### Seams to watch
- **`ChecksStudioPage.tsx` is 1237 lines and is 10.11's next subject.** Keep this story's addition to composed child components with their own files and a narrow prop surface, so 10.11's transport rewrite is not also a rewrite of the review panel. The middle panel is where PRD §5.2 puts this content; adding a fourth right-panel tab would put the review behind the Proof tab, where a user confirms without having looked.
- **`studioContract.test.ts` is a shared harness, not this story's file.** AC-4's assertion is added beside the existing `componentValidator`/`requiredPropertiesOf` helpers and uses them. A second parser of `openapi.yaml` in a second file is how the two copies of one vocabulary get created — which is the thing §18.3 is trying to prevent.
- **`CodeTab.tsx` is left alone.** It is 10.11's to point at the confirmed source. Touching it here produces a wave-6 conflict on a file this story does not need.
- **The `COMPILING` state has no push channel.** SSE is for executions (§5.5); there is no compile-progress transport in any source. See the auto-decision below — the poll must be bounded, must stop, and its cadence is an open question for @po rather than a number this story asserts is right.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on 2026-09-11: `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a Darwin host, the CLI is absent and `graceful_degradation.skip_if_not_installed: true` applies.

## Weakest criteria — named here rather than discovered at validation

@po does this at validation; doing it in the draft makes the validation sharper. In descending order of how easily each could be satisfied without being true:

1. **AC-19(b) — the nontechnical-user trial.** The weakest by a wide margin. It is a user-research result, it has no test, it depends on AC-16(b) which is itself blocked, and there is no mechanism in this repository that would notice if it never happened. It is deferred to 10.19 and recorded skipped-never-passed for exactly that reason. **If it is ever marked done without a named session, a named participant set and a written result, it was not done.**
2. **AC-18(a) — "accessible controls".** Roles, names and keyboard operability are genuinely assertable and are asserted. But "accessible" in the epic's sense is broader than what four testing-library assertions prove, and the gap between the two is comfortable to live in. AC-18(b) exists to keep the claim honest, and it is deferred to a story that does not yet own it — which is itself a weakness, not a resolution.
3. **AC-17 — "explain unsupported workflows".** A standing paragraph satisfies the letter of it in ten minutes. The substance — telling a user *before* confirmation that their particular checklist relies on a popup — is not detectable on this surface at all, and the criterion says so. The risk is that the standing paragraph is read at validation as the detection.
4. **AC-9 — the honesty assertion.** A forbidden-phrase list is a blunt instrument: it catches *"verified"* and misses *"looks right"*. It is asserted on rendered output rather than on source precisely so it is not trivially green, but it cannot prove the absence of an implied claim. It is a floor, not a proof, and should be read as one.
5. **AC-2 — per-state narratives.** The facts are enumerated in a table so the test can assert them, which is what keeps this from being "renders something". The residual softness is that a test asserting on rendered substrings will pass on text that is technically present and practically unreadable.
6. **AC-16(a) — the unavailable state.** Easy to satisfy vacuously by rendering nothing at all and calling it an unavailable state. The import assertion and the falsification (wire the English line into the summary slot → red) are what give it teeth; without them it is a placeholder that passes.

The criteria most likely to be **cut under pressure** are different from the weakest: AC-7's three separate truncation tests (tempting to collapse into one), AC-21's falsification table (the first thing to go when the tests are already green), and AC-15's escalation test (the only test in the story that is *meant* to be red, and therefore the one someone will try to make green).

### @po's naming at validation — 2026-09-11

The draft's own list is accurate and I am not replacing it. I am **reordering the top of it** and adding three the draft did not see. Ordered by how cheaply each could be green while false:

1. **AC-20, the fixture matrix — promoted to the weakest criterion in the story, above AC-19(b).** AC-19(b) is weak but *visible*: it is deferred, unowned by a test, and named as such, so nobody will mistake it for done. AC-20 is the opposite — it is a criterion the suite appears to enforce and mostly does not. AC-1's enumeration is genuinely self-policing because it reads the union from the document. **Nothing else is.** If the level-2 truncation fixture is never written, AC-7 does not go red; the test simply does not exist, and a green suite is indistinguishable from a covered one. AC-20 is the load-bearing input to AC-1, AC-5, AC-6, AC-7 and AC-12, and the story's entire anti-vacuity argument rests on fixtures nobody checks the existence of. Closed by the amendment above (an enumerable required-set with a referenced-by-a-named-test assertion), and named here because that amendment is itself the first thing that will be cut.
2. **AC-7's truncation fixtures — the hazard must occur, not be declared.** The draft names AC-7 as *cut-prone*; I name it as *vacuity-prone* for a different reason. Three tests over three fixtures that each hand-set a boolean satisfy every word of the criterion and prove only that the renderer reads booleans. The failure the criterion exists to prevent — a marker trimmed by the layout, ellipsised by CSS, or lost to a re-clamp — is invisible to a fixture whose string was never clamped. This is wave 4's *"a canary that does not straddle the cut proves nothing"*, transposed. Amended above.
3. **AC-13's debounce — the mutation must land inside the measurement window.** Wave 4's other lesson, and it applies here exactly: a "second click" test whose second click fires after the first request settled measures a settled state and passes with no debounce present at all. The criterion as drafted says *"while one is in flight"* but does not say how the in-flight window is constructed, and the natural implementation — two synchronous `click()` calls against an MSW handler that resolves immediately — is the one that does not test it. Amended above to require a held-open handler.
4. **AC-10's export enumeration — a scan keyed on the wrong surface.** This is the epic's *"a scan keyed on a receiver's variable name"* shape. Enumerating exports is blind to a module-local `import.meta.env.DEV`, which is precisely where a developer affordance gets added under pressure. Demoted to a supplement above; the behavioural five-state enumeration is now the load-bearing half.
5. **AC-19(b)** — the draft's own first pick, and still the weakest thing in the story *by consequence*. It is deferred and unfalsifiable by any mechanism here. It stays where the draft put it; it is simply less dangerous than AC-20 because nobody can mistake it for satisfied.
6. **AC-9's forbidden-phrase list** — a floor, correctly described as one by the draft. The residual worth stating: the list will be written by the same person who wrote the copy, so it will contain the phrases they thought not to use. Consider seeding it from BRD §8's risk language rather than from the component.
7. **AC-16(a)'s unavailable state, AC-17's standing paragraph, AC-18(a)'s four assertions, AC-2's substring tests** — the draft's own 2/3/5/6, accepted as written and not re-argued.

**Cut-risk, amended.** The draft's three stand. AC-2's principal test is `it.each(DECLARED_STATES)('%s renders its three facts and its own name')`,
and its body reads `const narrative = narrativeFor(state)` — from `compileStateNarratives.ts`, the
very module `CompileReviewPanel` renders from — then asserts `toContain(narrative.whatIsTrue)` and the
same for the other two. **That is true for any content the module happens to hold**, including one
character, and `toContain('')` is vacuously true for none at all.

Measured, three ways:

- Replacing `COMPILING`'s `whatIsTrue` / `whatYouCanDo` / `whatIsBlocked` with `'x'` →
  **full suite `Test Files 2 failed | 19 passed (21); Tests 1 failed | 256 passed (257)`** — the
  unchanged counts.
- Replacing `READY`'s three facts and `NEEDS_REVISION`'s `whatIsTrue` with `'x'` → both studio
  directories **`Tests 1 failed | 185 passed (186)`** — unchanged.
- Replacing all four `COMPILING` fields with four *false* statements reddened exactly one test, and
  only because it also changed the **title**, which `recompile.test.tsx` pins literally.

So **eight of the fifteen facts AC-2's table requires are pinned by nothing.** `COMPILING` must say
the draft is saved, that a compile is in flight for the source shown, and that nothing is confirmable
yet; `READY` must say the confirmed revision is runnable. None of those six sentences is asserted to
say anything. The four hand-written literal-regex tests rescue `AWAITING_CONFIRMATION`,
`NEEDS_REVISION` and `STALE`; `COMPILING` and `READY` have no such rescue.

This is precisely the risk @po named for a UI story — a substring assertion passing on text that is
present and unreadable — in its purest form: **the substring is imported from the thing being
checked.** It is not a live defect; the copy is careful, correct and among the best writing in this
epic. But AC-2 is ticked, it has no row among AC-21's twenty-two, and *"an assertion nobody has seen
fail has not been shown to assert anything"* is this story's own standard.

**Remedy (@dev, follow-up, ~20 lines, no production change):** one literal assertion per required
fact, written in the test and not imported, as `STALE` already has — three each for `COMPILING` and
`READY`, two more for `NEEDS_REVISION` — and the corresponding rows added to the falsification table.
