## User Story

**As a** CSI-authorized support engineer who has just written an English checklist and has no way to see what the machine decided it meant,
**I want** each of my own lines shown back to me with the action, target and assertion the validator accepted, the executable source one expansion away, and the plain-language reasons when a line could not be made runnable,
**so that** the thing I approve is the thing that will run — and when I approve it, I approve *that* revision, not whatever the compiler produced while I was reading.

---

## Problem Statement

Every backend half of the confirmation mechanism exists or is landing. `ui_test_revisions` is immutable and write-once on confirmation (10.4). The compile pipeline bounds its work, screens credentials and publishes candidates (10.8). Story 10.9 is landing the bounded repair loop, the `confirm-compile` transaction whose four-field body is conditional in SQL, and — under ADR-002 §16 — the typed diagnostics that a failed compile leaves on the draft.

**Nothing renders any of it.** Verified on the branch at `34138201f`: `frontend/src/services/api/studioApi.ts` has no `compileTest` and no `confirmCompile`; `frontend/src/types/studio/studioTypes.ts` declares `TestDto` without `compileError` and `compileDiagnostics`; and the one view that claims to show generated code, `frontend/src/components/studio/CodeTab.tsx`, renders **client-generated Python** from `@/utils/studio/codegen/pythonGenerator` — a language architecture §8.3 retired and a derivation the server never made.

So today the product's whole trust argument — PRD §5.2, *"The user should feel confident that their plain English commands are being understood"* — is unbacked. A user can save a draft, and that is all. There is no path from `AWAITING_CONFIRMATION` to `READY`, which means no path to a run at all, which is why 10.11 blocks on this story rather than on 10.7.

Four properties make this more than "add a panel".

1. **The five states are five different sentences, and a default branch erases four of them.** `STALE`, `COMPILING`, `AWAITING_CONFIRMATION`, `READY` and `NEEDS_REVISION` (§4.2) differ in what is true, in what the user may do, and in *who can clear the condition*. `STALE` is a failure that is not the author's fault and whose whole remedy is an explicit recompile; `NEEDS_REVISION` is the author's to fix and no amount of retrying will move it. Collapsing any pair into "something went wrong" is the failure mode ADR-002 §14.3 settled on the wire and which this surface can undo in one `switch` statement with a `default:`.
2. **A bounded report rendered as a complete one is a lie the user cannot detect.** `DiagnosticsBounder` refuses to be silent about truncation at three levels — a marker inside a clamped `message` or `excerpt`, `truncated` per step, `truncated` plus `truncationReason` on the document. ADR-002 §16.5 says so and then says what follows: *"a client that renders this document without rendering those flags turns a bounded report into a false one — which is a requirement on 10.10, not decoration."* The failure is silent by construction: the surface looks finished, the user reads three problems, fixes three problems, and the fourth was shed to fit a byte cap.
3. **Confirmation is exact or it is nothing — and the client is the one holding the identity.** §4.2 fixes the body as `{revisionId, artifactHash, sourceRevision, configurationRevision}` and the transaction is conditional on all four. The client's obligation is that those four values come from *the response the user was looking at*, and that a `409` returns the user to a fresh, deliberate review rather than re-sending against whatever is current now. The epic's release ordering is blunt about the alternative: *"No temporary gate bypass or production auto-confirmation is allowed."*
4. **And the client cannot currently build that body.** Verified, not inferred: the amended `openapi.yaml` declares `ConfirmCompileRequest.required` as four fields, and `artifactHash` appears on **no** declared `2xx` response of any `tests`-tagged operation. `TestDto` carries `currentCandidateRevisionId` but not the hash, not the artifact and not the source. `UITestDto.java` matches it field for field. The data exists — `UITestRevision` has `source`, `artifact`, `artifactHash` — and travels on the internal `RunJob` envelope, but nothing public returns it. The same gap denies this story the *"trusted action/target/assertion summary"* and the *"expandable executable source"* its own epic scope line requires, because both are derived from validated operations (§4.7) and the validated artifact is not on the wire. That is AC-15, and under ADR-002 §12 it is a Class C change this story may propose and may not land.

## Size call — M in the manifest, L in this draft

The manifest records `size: M`. Three things have landed or been discovered since that estimate, and the honest scope is **L**. This is the same shape of cause that moved 10.9 and 10.13 from M to L at wave-4 validation: a ruling arriving after the number.

1. **ADR-002 §16 landed on 2026-09-11** and turned "show diagnostics" into four typed component schemas, **three** distinct truncation levels each with its own falsifiable rendering obligation, an eleven-value code set, and the `attempts`/`exhausted` pair. §16.9 spends a paragraph on what this story *may rely on* and what it *may not do* — a level of specificity that exists because the surface is larger than the manifest's line implies.
2. **ADR-002 §18.3 assigned this story a mechanism, not just a render.** *"Story 10.10 is the first frontend story to consume a code set of that kind, a wave earlier than 10.11. Whichever lands first should install the document-reading assertion once."* That is a test-harness obligation on `studioContract.test.ts` that outlives this story, and 10.11 extends it rather than duplicating it.
3. **The confirm-body gap (AC-15) splits the story's headline capability.** An escalation, a self-resolving contract test, a candidate-shape proposal, and an `a`/`b` split across the criteria the epic names first. None of that was visible when the M was set.

**What would make it an M:** if @architect's ruling on AC-15 declines the artifact surface for V1, half (ii) of the split hint disappears — but so does confirmation, and with it the story's reason to exist. The realistic M is the *other* direction: if (i) and (ii) are landed as two stories, each is an M. That is the split hint, and it is the named mitigation.

## Acceptance Criteria

Every criterion below is falsifiable and cites its source. Criteria split `a`/`b` follow the epic convention established by 10.3: the `a` part is verifiable now, the `b` part names its owner and gate and is recorded **skipped, never passed** — never quietly marked done.

### The compile state is legible, and five states are not one state

- [ ] **AC-1:** **Every value of `compileStatus` renders a distinct, named state, and the mapping is total with no fallback branch.** §4.2 fixes the five: `STALE | COMPILING | AWAITING_CONFIRMATION | READY | NEEDS_REVISION`. The test **reads the union from the document** — `openapi.yaml` → `components.schemas.TestDto.properties.compileStatus.enum` — and asserts that each member produces a rendered state with a distinct accessible name, and that no two members render the same one. **No `default:` branch and no `??` fallback exists in the mapping**: a sixth value must be a compile error or a red test, not a silent "something went wrong". *Anti-vacuous:* the assertion is falsified by (a) adding a sixth member to an in-test copy of the document → red, and (b) replacing the exhaustive mapping with one carrying a default branch → red. Both recorded in the Dev Agent Record. This is the same mechanism ADR-002 §18.3 requires for the codes (AC-4); it is installed once and used twice.
- [ ] **AC-2:** **Each state states what is true, what the user may do next, and what is blocked — and the four facts below are rendered, not implied.** One test per state, asserting on rendered text and control state:
  | State | What must be rendered | Source |
  |---|---|---|
  | `COMPILING` | a compile is in flight for the source shown; nothing is confirmable yet; the draft is saved | §4.2, §8.3 (`PUT` persists the draft and enqueues compile) |
  | `AWAITING_CONFIRMATION` | a candidate exists and is **not** runnable until this user confirms it; confirmation is the only route to `READY` | §4.2 *"It becomes `AWAITING_CONFIRMATION`"*; §10.8 epic *"never READY automatically"* |
  | `READY` | the confirmed revision is runnable; its identity is shown | §4.6 |
  | `NEEDS_REVISION` | the candidate is **not** runnable, the reasons are the author's to act on, and retrying without editing will not help | §4.7, BRD §6 *"blocks only that candidate with a plain-language reason"* |
  | `STALE` | the draft is **saved and unchanged**, any previously confirmed revision **still runs**, this is not the author's fault, and an explicit recompile is the whole remedy | `CompileError` schema description (all four clauses are in the contract text), §4.7, BRD §6 *"drafts still save … unchanged confirmed tests can execute"* |
- [ ] **AC-3:** **A confirmed test whose draft has moved is visibly flagged as needing re-confirmation, and the flag is derived from the body rather than from a local edit event.** BRD §6: *"Editing a confirmed test clearly flags it as needing re-confirmation."* The predicate is `confirmedRevisionId !== null && compileStatus !== 'READY'`, read from one `GET /tests/{id}` body — which is exactly the shape of the contract's own `needsRevision` example (`confirmedRevisionId` set, `compileStatus: NEEDS_REVISION`). It is **not** derived from "the user typed something", because a reload, a second tab and a configuration-only change all produce the condition without a local edit (§4.2: configuration-only changes create a new candidate and require reconfirmation). A test drives each of the three origins and asserts the same flag; a fourth asserts a name/description change does **not** raise it (§4.2: *"Name/description changes do not invalidate confirmation"*) — and that fourth test is the one that proves the flag is not simply "dirty".
- [ ] **AC-4:** **The `compileError` code set is read from the contract, compared both ways, and is the only copy.** ADR-002 §18.3 assigns this story the mechanism: *"Whichever lands first should install the document-reading assertion once, and the other should extend it rather than write a second one. Two hand-maintained copies of one vocabulary in two languages is the arrangement that produced INT-4."* In `frontend/src/services/mocks/studio/studioContract.test.ts` — which already parses `openapi.yaml` and is named in §18.3 as the natural home — assert that the UI's code→explanation map and `CompileError.x-compile-error-codes` are the **same set, in both directions**: no code in the document without an explanation, no explanation for a code the document does not declare. *Anti-vacuous, and aimed squarely at the epic's fifth precedent (a pin check with an uncompared fifth copy):* the assertion is falsified by (a) adding a twelfth code to an in-test copy of the document → red, and (b) deleting one entry from the UI map → red. A one-directional `every code has an entry` check does not satisfy this criterion and is named here as insufficient. 10.11 **extends this assertion** for `ExecutionErrorCode` (ADR-002 §18.3, O-12); it does not write a second one.
- [ ] **AC-5:** **An undeclared `compileError.code` renders honestly rather than blankly.** §14.7 permits the set to grow — *"A story that lands a new compile failure condition may add its code to that list in its own PR"* — and `code` is deliberately a free string, not an enum (§16.4). So an unrecognized code renders the generic `STALE` narrative of AC-2 **plus the code verbatim**, and never an empty string, never `undefined`, and never a silently-omitted panel. A test feeds a code that is not in the eleven and asserts all three.

### The diagnostics document, rendered without turning a bounded report into a false one

- [ ] **AC-6:** **One row per original step, index-aligned to the `steps` in the same body, accepted steps included.** `CompileStepDiagnostics`: *"One entry per original source step, index aligned, present even where the validator returned nothing for that step (§4.4) … The entry count equals the length of `steps` on the same `TestDto`."* Artifact-level rejections (`CompileDiagnostics.artifact`, *"belonging to no single step"*) render in their own region, attached to no step. *Anti-vacuous, aimed at the epic's third precedent (an isolation test that deleted its own coverage):* the fixture is **not degenerate** — it carries at least four steps with an **accepted step between two rejected ones**, so an off-by-one join produces a visibly wrong attribution rather than a coincidentally-correct one. The falsification is an index shift of one on the join → the named test red, recorded. A test also asserts the row count equals `steps.length` for every fixture, and that a document whose `steps` array is shorter than `steps` is surfaced as a defect rather than silently padded.
- [ ] **AC-7:** **All three truncation levels are rendered, each proven by its own test on a fixture that actually carries it.** ADR-002 §16.5 and the `CompileDiagnostics` description:
  1. a clamped `message` or `excerpt` carries a visible truncation marker → rendered so the marker survives (not trimmed, not ellipsised away);
  2. `CompileStepDiagnostics.truncated: true` → that step says *"there were more problems for this step than we are showing"*, distinguished in words from "there were no more problems";
  3. document-level `truncated: true` with `truncationReason: TOTAL_BYTES` → the surface says whole steps' reasons were shed and which fact that is.

  Three tests, three fixtures, three falsifications: deleting each render in turn must turn exactly the corresponding named test red, recorded in the Dev Agent Record. *This is aimed at the epic's first two precedents — a canary that stayed green with redaction removed, and an assertion green with the redactor deleted.* A single test that renders one fixture and asserts "the flags appear somewhere" does not satisfy this criterion.
- [ ] **AC-8:** **`attempts` and `exhausted` are rendered as what they mean.** ADR-002 §16.2 fixes the two keys precisely so this story is not guessing. `attempts` renders as *how many times the compiler tried*, `exhausted: true` renders as *the bound was reached and the result is still not runnable — the remedy is editing the step, not retrying* (§4.3 bounds repair at two attempts; §4.7 *"Exhausted repair yields NEEDS_REVISION"*). A test asserts that `exhausted: true` does **not** render a retry affordance, and that `exhausted: false` with `attempts: 1` does not imply a repair happened. The document describes the **last attempt only** and the surface never implies it is a history.
- [ ] **AC-9:** **Nothing on this surface states or implies that a step the validator accepted does what its author meant.** §4.1: static validation *"cannot prove the locator matches the application or the assertion captures the user's intent"*; §4.5: *"This restriction limits executable capabilities, not semantic mistakes"*; ADR-002 §16.9 item 6, binding on this story by name; BRD §8 names the realized risk — *"Users treat AI-generated code confirmation as a rubber stamp"*. The assertion is made **on the rendered output of every state, for every fixture** — `render()` then read the text — against a checked-in list of forbidden claim patterns (*verified, correct, guaranteed, will pass, confirmed working, tested*). *Anti-vacuous, aimed at the epic's sixth precedent (a log assertion that grepped source text instead of capturing runtime output):* asserting against the component source file, the JSX, or a constants module does **not** satisfy this criterion; the assertion runs against rendered text, and is falsified by planting one forbidden phrase in one state's copy → red.

### Confirmation is exact, or it does not happen

- [ ] **AC-10:** **The confirm control is enabled in exactly one state and for exactly the identity on screen.** Enabled only when `compileStatus === 'AWAITING_CONFIRMATION'` **and** `currentCandidateRevisionId !== null` **and** the identity the request would carry is the identity currently rendered. A test enumerates all five states (reading the union per AC-1) and asserts the control is enabled in exactly one of them. Epic release ordering: *"No temporary gate bypass or production auto-confirmation is allowed."* No configuration flag, query parameter, environment variable or developer affordance enables it elsewhere, and a test enumerates the module's exported surface to assert no such escape exists.
- [ ] **AC-11(a):** **The request body is exactly the four declared fields, taken from the one response the user is looking at.** `ConfirmCompileRequest` = `{revisionId, artifactHash, sourceRevision, configurationRevision}` (§4.2, §8.3). All four are read from a **single** `GET /tests/{id}` body held as one value — not re-read per field, not recombined from two fetches, not taken from Redux state that another request may have updated in between. *Anti-vacuous, aimed at the epic's fifth precedent (a contract check comparing route strings instead of response bodies):* the assertion is made on the **captured request body** via the MSW handler (`await request.json()`), never on a spy's call arguments, and it compares the four values against the fixture that was rendered. Two falsifications: omit one field from the body → red; source `sourceRevision` from a second, newer fetch → red. Both recorded.
- [ ] **AC-11(b):** *(**Blocked** — see AC-15. Owner: @architect ruling, then this story or its (ii) half.)* `artifactHash` in that body. **No declared `2xx` response of any `tests`-tagged operation carries it** (verified against the amended `openapi.yaml` at `34138201f`). Until the ruling lands, the accessor that supplies it has exactly one implementation, it returns *unavailable*, and the confirm control is disabled with an explicit explanation naming the blocker. **A hash is never fabricated, never recomputed client-side from anything, and never defaulted** — a client-computed `artifactHash` would be the client asserting what the server canonicalized, which is the one thing the conditional transaction exists to check. Recorded **skipped, never passed**.
- [ ] **AC-12:** **`409` returns the user to a fresh, deliberate review and never silently accepts new code.** The declared code set is exactly `x-conflict-codes: [STALE_CANDIDATE, TEST_DELETED, TEST_QUARANTINED]` (read from the document, as in AC-4 — not transcribed). Behaviour per code, one test each:
  - `STALE_CANDIDATE` — refetch `GET /tests/{id}`, render what changed, and return the confirm control to its **unconfirmed** state. The refreshed identity is **not** auto-confirmed, and **no confirm request is re-sent** without a new, deliberate act by the user. Epic §10.10: *"refresh on 409 without silently accepting new code."*
  - `TEST_DELETED` / `TEST_QUARANTINED` — **not retriable by the caller** (ADR-002 §14.3), so no retry affordance is offered; `TEST_QUARANTINED` says the author's work **survives** and awaits CSI resolution, and is never reported as a deletion (§14.3: *"Reporting a quarantined draft as `TEST_DELETED` would state that an authored test was deleted, which BRD §9 forbids"*). No restore action is offered for a quarantined draft.

  **The branch is taken on `error`, never on `message`.** @po's ruling on 10.9 (2026-09-11) is a forward constraint on this story: *"the message is human-readable prose and is not a branch key."* A test replaces every `message` with an unrelated string and asserts all three branches still resolve correctly. *Anti-vacuous:* falsified by making the `STALE_CANDIDATE` path re-send the confirm request after refetching → the named test red, recorded. That mutation is the shape of the epic's first precedent — a guard that stays green while the thing it guards is gone.
- [ ] **AC-13:** **A double submission sends one request.** 10.9's `confirm` is conditional on `confirmed_by IS NULL`, so a second confirmation of the same revision answers `409 STALE_CANDIDATE`; @po ruled on 2026-09-11 that *"A double-click is 10.10's to debounce, not this story's to absorb into a guarantee."* Exactly one request leaves the client per deliberate confirmation; a second activation while one is in flight sends nothing and is not queued. Asserted by counting requests observed by the MSW handler, not by asserting a `disabled` prop — a disabled attribute set after the second click has already fired proves nothing.
- [ ] **AC-14:** **An explicit recompile exists for the `STALE` case and speaks the declared contract.** `CompileError`'s own description — *"an explicit recompile is the whole remedy"* — and §4.1 (*"Compile on source changes or explicit recompile"*) put the control here. It calls `POST /tests/{id}/compile`, and handles what the operation declares and nothing else: `202` → `COMPILING`; `400` with the four authoring-bound codes (`SOURCE_TOO_MANY_STEPS`, `SOURCE_LINE_TOO_LONG`, `SOURCE_TOO_LARGE`, `INLINE_CREDENTIAL`), whose messages name a step index and never its text; `409` with `[TEST_DELETED, TEST_QUARANTINED]`, read from the document. The `202` explicitly does **not** mean success — the operation's own description says so — and the surface must not report it as one.

### Unsupported workflows, access and the claims this story may not make

- [ ] **AC-17:** **Unsupported workflows are stated before confirmation, and the surface does not imply it detected them.** §2: *"Unsupported workflows must be explained before confirmation where detectable and fail explicitly otherwise"*, with the V1 exclusions named there — one page, no iframe/popup/multi-page workflows, one run at a time, and *"Pilot applications must support the approved single-page login flow; enterprise MFA is not assumed to work."* Two obligations, and the second is the honest one: the surface renders a standing statement of those limits at review time, **and** the only per-step detection it has is what the validator already rejected and returned as diagnostics. A test asserts the standing statement is present in `AWAITING_CONFIRMATION` and `NEEDS_REVISION`, and a second asserts the surface makes **no** per-step claim of the form "this step is supported" beyond what a diagnostic says — nothing here may read as a clearance the validator did not give (AC-9 covers the wording).
- [ ] **AC-18(a):** **The controls are operable and programmatically described — asserted on the rendered accessibility tree, not on props.** Epic acceptance bullet 1: *"Author → save → review → confirm works in one Studio flow with accessible controls."* Every control has a role and an accessible name; the confirm control, the expand control and the recompile control are reachable and operable **by keyboard alone** (`userEvent.tab()` / `{Enter}` / `{Space}`); compile-state changes are announced through a live region; each step's diagnostics are programmatically associated with that step (`aria-describedby` or an equivalent the accessibility tree exposes). *Anti-vacuous:* assertions use `getByRole` / `toHaveAccessibleName` / keyboard events against rendered output; asserting that a prop appears in the JSX does **not** satisfy this criterion. **No new dependency is added** — `axe-core` is not in `frontend/package.json` (verified) and adding it is a tooling decision this story does not take.
- [ ] **AC-18(b):** *(**Deferred** — a WCAG conformance audit and assistive-technology verification. **No Epic 10 story owns this today**; proposed owner **10.19** (staging validation and handover), for @po to confirm or reassign.)* AC-18(a) proves structure and keyboard operability; it is **not** a conformance claim and the story does not make one. ## Implementation Notes

### The one place the identity lives
Everything the confirm body carries comes from a **single** `GET /tests/{id}` response held as one immutable value for the duration of the review. Not four selectors over a Redux slice, not a re-read per field, not a recombination of a list entry with a detail entry. ADR-002 §16.3's argument for why diagnostics need no `sourceRevision` of their own is the same argument: *"a client aligning `steps[i]` to `compileDiagnostics.steps[i]` is aligning two facts that were read together."* That guarantee is the server's, and it survives only if the client does not take it apart. A refetch produces a **new** value and an explicitly unconfirmed control (AC-12), never a partial update of the old one.

### Why the summary must not be derived from the English
`parseSteps` and `pythonGenerator` both exist and both would produce something that looks like an action summary in an afternoon. Using either would present *the client's* reading of the English as *the validator's* reading of the artifact. The user would then confirm a summary the server never produced, against a hash the server computed from something else — and the epic's whole trust argument inverts: the human control point becomes the place where two different interpretations are silently reconciled. AC-16(a)'s import assertion exists to keep that shortcut from being taken under time pressure, because it is the shortcut that makes the story finishable and worthless.

### Why the escalation test is written this way
The property it asserts — *every required field of a request body is obtainable from some declared response* — is true of every other route in the document, which is what makes its failure on `artifactHash` informative rather than arbitrary. It reads the document rather than naming the field, so it also covers a future request body with the same defect. And it goes green on the amendment with no edit to itself, which is the difference between an escalation and a `TODO`. The precedent is `ExecutionErrorCodeContractEscalationTest` (10.7's), which went `1/2 → 2/2` with no change to the test when ADR-002 §15 landed — recorded in §13's log as the measurement that mattered.

### Seams to watch
- **`ChecksStudioPage.tsx` is 1237 lines and is 10.11's next subject.** Keep this story's addition to composed child components with their own files and a narrow prop surface, so 10.11's transport rewrite is not also a rewrite of the review panel. The middle panel is where PRD §5.2 puts this content; adding a fourth right-panel tab would put the review behind the Proof tab, where a user confirms without having looked.
- **`studioContract.test.ts` is a shared harness, not this story's file.** AC-4's assertion is added beside the existing `componentValidator`/`requiredPropertiesOf` helpers and uses them. A second parser of `openapi.yaml` in a second file is how the two copies of one vocabulary get created — which is the thing §18.3 is trying to prevent.
- **`CodeTab.tsx` is left alone.** It is 10.11's to point at the confirmed source. Touching it here produces a wave-6 conflict on a file this story does not need.
- **The `COMPILING` state has no push channel.** SSE is for executions (§5.5); there is no compile-progress transport in any source. See the auto-decision below — the poll must be bounded, must stop, and its cadence is an open question for @po rather than a number this story asserts is right.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on 2026-09-11: `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a Darwin host, the CLI is absent and `graceful_degradation.skip_if_not_installed: true` applies.

## Weakest criteria — named here rather than discovered at validation

@po does this at validation; doing it in the draft makes the validation sharper. In descending order of how easily each could be satisfied without being true:

1. **AC-19(b) — the nontechnical-user trial.** The weakest by a wide margin. It is a user-research result, it has no test, it depends on AC-16(b) which is itself blocked, and there is no mechanism in this repository that would notice if it never happened. It is deferred to 10.19 and recorded skipped-never-passed for exactly that reason. **If it is ever marked done without a named session, a named participant set and a written result, it was not done.**
2. **AC-18(a) — "accessible controls".** Roles, names and keyboard operability are genuinely assertable and are asserted. But "accessible" in the epic's sense is broader than what four testing-library assertions prove, and the gap between the two is comfortable to live in. AC-18(b) exists to keep the claim honest, and it is deferred to a story that does not yet own it — which is itself a weakness, not a resolution.
3. **AC-17 — "explain unsupported workflows".** A standing paragraph satisfies the letter of it in ten minutes. The substance — telling a user *before* confirmation that their particular checklist relies on a popup — is not detectable on this surface at all, and the criterion says so. The risk is that the standing paragraph is read at validation as the detection.
4. **AC-9 — the honesty assertion.** A forbidden-phrase list is a blunt instrument: it catches *"verified"* and misses *"looks right"*. It is asserted on rendered output rather than on source precisely so it is not trivially green, but it cannot prove the absence of an implied claim. It is a floor, not a proof, and should be read as one.
5. **AC-2 — per-state narratives.** The facts are enumerated in a table so the test can assert them, which is what keeps this from being "renders something". The residual softness is that a test asserting on rendered substrings will pass on text that is technically present and practically unreadable.
6. **AC-16(a) — the unavailable state.** Easy to satisfy vacuously by rendering nothing at all and calling it an unavailable state. The import assertion and the falsification (wire the English line into the summary slot → red) are what give it teeth; without them it is a placeholder that passes.

The criteria most likely to be **cut under pressure** are different from the weakest: AC-7's three separate truncation tests (tempting to collapse into one), AC-21's falsification table (the first thing to go when the tests are already green), and AC-15's escalation test (the only test in the story that is *meant* to be red, and therefore the one someone will try to make green).

### Autonomous decisions recorded during drafting

- **[AUTO-DECISION]** *How does the surface learn that a `COMPILING` compile has finished?* → **Bounded polling of `GET /tests/{id}`, stopping on any terminal compile state.** Reason: SSE is scoped to executions (§5.5) and no source declares a compile-progress channel; `GET /tests/{id}` is the only declared read that carries `compileStatus`. The criterion is written about **boundedness and stopping** — a maximum attempt count, backoff, a stop on every terminal state and on unmount — rather than about a cadence being correct, because BRD §6 makes *"Studio must not exhaust capacity reserved for ordinary checks/REST"* a hard requirement and a number this draft invented would be the wrong place to assert one. **Open for @po** (question 4).
- **[AUTO-DECISION]** *Does this story own retiring the Python generator and the client grammar validation?* → **No.** Reason: epic §10.11's scope line names both by hand (*"Remove legacy English grammar as execution gate and retire Python generation; Code view renders the confirmed source"*). This story neither imports nor deletes them; AC-16(a) asserts the non-import, which is the part that protects *this* story's correctness. Story 10.9's out-of-scope line calls the Code view 10.11's, which agrees.
- **[AUTO-DECISION]** *Where does the review surface live — a new right-panel tab or the middle panel?* → **The middle panel.** Reason: PRD §5.2 puts *"readable action/target/assertion summaries, and an expandable Playwright TypeScript view. The user confirms the exact generated revision before Run becomes available"* in the Control Tower, beside the Run button. A fourth right-panel tab would place the confirmation behind the Proof tab, where a user can reach Run without having passed the review — which is the shape of a gate bypass even when the server still refuses.
- **[AUTO-DECISION]** *Does the surface offer "confirm anyway" for a `NEEDS_REVISION` draft?* → **No, and no affordance hints at one.** Reason: §4.2 makes an invalid candidate unrunnable and writes no revision to confirm; the epic's release ordering forbids any temporary gate bypass. The server would refuse regardless, but an affordance that exists to be refused teaches a user the gate is negotiable.
- **[AUTO-DECISION]** *Is the `409` message shown to the user?* → **Yes, as prose, alongside an explanation derived from the code.** Reason: 10.9 AC-7 makes the message name what moved, which is genuinely useful to a reader; @po's ruling makes it not a branch key. Showing it and branching on it are different things, and AC-12 asserts the second is not happening.
