## User Story

**As a** user viewing the Command Center dashboard,
**I want** the Activity feed and Reports Snapshot sections to display real data aligned with the frontend contract,
**so that** I see a diversified activity timeline and upcoming report schedules instead of perpetually empty/mismatched sections.

---

## Acceptance Criteria

### Backend — Reports Snapshot (stub → real)

- [ ] **AC-1:** `GET /api/v1/dashboard/reports/snapshot` is wired to `DashboardService.getReportsSnapshot(identity, csiId, limit)` instead of returning a hardcoded empty list. If the `reports` table does not exist yet, the method gracefully returns an empty list (try/catch on the native query). If it does exist, it queries the most recent reports joined with their latest execution for `lastStatus`.
- [ ] **AC-2:** Response shape matches the frontend `ReportSnapshotItem` type: `{data: [{id, name, nextScheduledAt, lastStatus}]}`. `nextScheduledAt` is the next cron-derived execution or `null`. `lastStatus` is the status of the most recent `report_executions` row or `null`.

### Backend — Activity type alignment

- [ ] **AC-3:** `DashboardService.getActivityItems` maps execution result statuses to the frontend's expected `type` enum: `FAILURE`/`TIMEOUT` → `"EXECUTION"` (not `"FAIL"`), `SUCCESS` → `"EXECUTION"` (not `"RECOVER"`). The `title` field provides the semantic detail: e.g., "Check failed", "Check recovered".
- [ ] **AC-4:** `ActivityItemDto` gains a `path` field (String, nullable). Populated as `/checks/details/{checkId}` to allow frontend navigation to the originating check. The frontend `ActivityItem.path` type is satisfied.

### Frontend — ActivityItem type update

- [ ] **AC-5:** `ActivityItem.type` union in `dashboardTypes.ts` is updated to include the backend's actual values. The new union: `'EXECUTION' | 'EDIT' | 'ASSIGN' | 'COMMENT' | 'REPORT_SENT'`. The `EXECUTION` type covers both failures and recoveries (differentiated by `title`/`description`).
- [ ] **AC-6:** `ActivityFeed.tsx` chip label for type `EXECUTION` uses a contextual color: `error` tone when title contains "failed", `success` tone when title contains "recovered", default `primary` otherwise.

### Verification

- [ ] **AC-7:** `./gradlew check` passes (backend).
- [ ] **AC-8:** `npm run type-check` passes (frontend).
- [ ] **AC-9:** Dashboard page verified in browser with backend running: Activity feed shows execution events with `EXECUTION` chip; Reports Snapshot shows data if reports exist, otherwise "No reports yet" gracefully.

### Key detail — reports table existence
Story 3.10 covers the reports domain. If the `reports` table doesn't exist yet in the current DB schema, the `getReportsSnapshot` method should catch `PersistenceException` and return `List.of()` — same behavior as the current stub but with a real attempt first.

### Activity type mapping — before/after
| Backend status | Current `type` | New `type` | `title` |
|---|---|---|---|
| FAILURE / TIMEOUT | `"FAIL"` | `"EXECUTION"` | "{checkName} failed" |
| SUCCESS (after failure) | `"RECOVER"` | `"EXECUTION"` | "{checkName} recovered" |

The frontend chip will use `title` content to determine color (error vs success), not the `type` field.
