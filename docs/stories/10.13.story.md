## User Story

**As the** Checks squad that now starts a real Chromium per run and has nothing that stops one,
**I want** the parent to enforce a browser-runtime deadline on a budget separate from queue time, to kill the whole process tree and clear every artefact on every exit path, and to prove — on captured output rather than by reading the source — that no resolved value leaves this process,
**so that** a hung run cannot hold a pod, a killed run cannot claim a video it does not have, a timed-out run says `TIMEOUT` rather than "something went wrong", and a secret that survived contact with a real browser does not survive contact with a log line.

---

## Problem Statement

Story 10.12 built the killable child and deliberately did not kill it. The code says so in four places: `src/run/launcher.ts`'s header ("The *total runtime* deadline is enforcement and belongs to **10.13**: `totalRuntimeMs` is passed through to the child … Nothing here kills a hung tree, and nothing here pretends to"); the `launch` message, which forwards `totalRuntimeMs` with the comment "Passed on, never enforced here"; `stop`'s fallback kill ("10.13 owns killing a hung process *tree* under a deadline"); and `README.md` line 25. `src/run/errors.ts` reserves `TIMEOUT` in the same spirit — "**Reserved, not emitted here** … Enforcement — the deadline, the kill and the emission — is story **10.13**."

So today a child that hangs after `ready` is bounded by nothing. The parent awaits its result; no timer exists; the slot is held; the scratch directory stays; `POOL_SIZE=1` means the pod admits nothing else and answers `429` forever while looking perfectly healthy. The API's running reaper (§5.4) would eventually record `ERROR / STALE`, which is the answer for a runner that *vanished* — not for one that is sitting there holding a browser. §5.2 assigns the enforcement here and nowhere else: "the parent enforces total deadline and kills the child process tree on a hang".

Four properties make this more than "add a `setTimeout`":

1. **The two budgets are not one budget.** §8.5 is explicit — "queue time and browser runtime are separate budgets" — and gives three distinct starting values: a 10 s admission HTTP timeout, a 600 s pending SLA and a 30 s admitted-start deadline, with the recovery deadline being *the browser runtime cap plus bounded finalization/delivery margins*. `runCoordinator.ts` already takes `admittedAtMs` at the CAS and measures the start deadline from it. The runtime cap must not be measured from that instant, or a slow queue silently eats the browser's time and a run dies before it has done anything wrong.
2. **A deadline that fires must be distinguishable.** Today a killed child produces the launcher's abandoned-result path, whose `failureKind` is `'run-fault'` → `RUN_ERROR`. That is the code for "the protocol broke". If this story kills a child on a deadline and does nothing else, the report says the runner faulted, when what happened is the one condition §8.2 names by hand: "a parent-enforced total timeout is `ERROR / TIMEOUT`". The `'total-timeout'` kind already exists in `RUN_FAILURE_KINDS` and already maps to `TIMEOUT`; nothing reaches it.
3. **Redaction has repeatedly been tested by a test that could not tell.** `test/redaction.test.ts` builds a redactor and asks it to redact a string — which proves `createRedactor` works, not that the run's output is clean. The interesting canaries are the ones nobody routes through the redactor: a value interpolated into a formatted argument, a value inside an exception message thrown from a library, a value inside a nested object that renders itself. And there is a channel with no redactor in front of it at all: the child is forked with `stdio: ['ignore', 'inherit', 'inherit', 'ipc']`, so everything the browser child or Playwright writes goes straight to the pod log unbounded and unscrubbed.
4. **Cleanup has to be observed, not inspected.** Chromium is a *grandchild*: the fork's pid is Node, and the browser is below it. `child.kill()` sends `SIGKILL` to the fork. A test that asserts `kill` was called passes while a browser keeps running, holding `/dev/shm`, the scratch directory and a video file open. §9.3 asks for "process reaping" and "clear scratch on every path"; the epic asks for "clean process trees". The only assertion that means anything is one that looks for the processes and the files afterwards.

Nothing here uploads a byte to Sonic (10.14), resolves a secret from a vault (10.17), builds an image or a NetworkPolicy (10.18), or touches the API (10.7). This story stops one run, cleans up after it, and reports the truth about what it stopped.

## Acceptance Criteria

### Two budgets, and the clock each is measured on

- [x] **AC-1:** **Queue time and browser runtime are separate budgets, with distinct timestamps, and neither consumes the other.** §8.5: "queue time and browser runtime are separate budgets." The **queue budget** is the admitted-start deadline (`deadlines.admittedStartMs`, §8.5 starting value 30 s), measured from `admittedAtMs` — the instant the admission CAS returned, which `runCoordinator.submit` already takes. The **runtime budget** is `deadlines.totalRuntimeMs` (§8.5 starting value 120 s), measured from the **browser start**, and from nothing else: not from `admittedAtMs`, not from the `POST /v1/runs` arriving, not from the spawn call, not from the scratch directory being created. Two tests drive the seam rather than describe it: **(i)** a run that spends nine-tenths of its queue budget before launching still gets the **whole** runtime budget, asserted by driving a fake clock and observing the instant the kill is ordered; **(ii)** a run that consumes the whole runtime budget is killed by the runtime deadline and the start deadline is shown *not* to have been what fired, by its code. The two instants are separate fields in the run's state and a test asserts they are not the same read.
- [x] **AC-2:** **The parent enforces on its own monotonic clock, and never re-bases a reading onto the child's.** The child owns the run clock whose zero is the recording origin (ADR-002 §11.2); the parent cannot read it, and must not try. The parent arms the runtime timer on its own monotonic source (`options.now`, the one `runCoordinator` already uses for the start deadline) at the instant it **observes the `ready` handshake**. The inequality is stated because it is the story's one deliberate imprecision: the parent's arming instant is at or after the child's origin by the inter-process handshake latency, so the enforced cap is never *shorter* than the configured one — a run is never truncated below its budget, and the surplus is bounded by `launchTimeoutMs`, which is a separate bound (AC-3). The parent does **not** convert its own elapsed time into a reading on the run timeline: the log entry the timeout writes carries `atMs: null`, because `null` is the contract's encoding for "no reading" (ADR-002 §INT-1, §11.2) and a wall-derived number would be the second origin §11.5 forbids. A test asserts that the timeout's log entry is `null` and not `0` and not a computed value.
- [x] **AC-3:** **Every deadline outcome is a distinguishable, truthful code — not a generic failure.** Five conditions, five observable answers on the serialized `FINAL` body, asserted as five separate tests:

  | Condition | `outcome.result` | `outcome.errorCode` | Browser? |
  |---|---|---|---|
  | Admitted-start deadline already elapsed at the launch point | `ERROR` | `START_DEADLINE_EXCEEDED` | none started (10.12 AC-4) |
  | Child never reports `ready` within `launchTimeoutMs` | `ERROR` | `BROWSER_LAUNCH_FAILED` | started, never ready |
  | **Total browser runtime exceeded** | `ERROR` | **`TIMEOUT`** | killed by this story |
  | A step's locator or assertion timed out | `FAILED` | `STEP_FAILED` | ran normally |
  | The child died for any other reason | `ERROR` | `RUN_ERROR` | gone |

  §8.2 fixes the third and the fourth rows by hand: "a step locator/assertion timeout is `FAIL` and execution `FAILED`; a parent-enforced total timeout is `ERROR / TIMEOUT`". The test that matters most is the **negative** one: a child killed on the runtime deadline must not produce `RUN_ERROR`, which is what today's abandoned-result path (`failureKind: 'run-fault'`) would give it. No code is invented — `'total-timeout'` is already in `RUN_FAILURE_KINDS` and `errorCodeFor` already maps it to `TIMEOUT`; this story makes it reachable. `TIMEOUT` remains the single value shared with the API's `ExecutionErrorCode`, and 10.12's disjointness test stays green unchanged.
- [x] **AC-4:** **No heartbeat, message or configuration extends the maximum deadline.** §5.4: "heartbeats never extend the maximum run deadline indefinitely"; the epic: "A hung child cannot … extend the maximum deadline via heartbeat." Nothing the child sends — `step-started`, `step-finished`, a log line, a protocol keepalive — re-arms, resets or lengthens the runtime timer, and there is no configuration key, job field or protocol message that can. A test drives a child that reports progress continuously past the deadline and asserts it is killed on time anyway; a second asserts that a job body carrying a larger `totalRuntimeMs` than the deployment permits does not get it (AC-6).
- [x] **AC-5a:** **The finalization margin is bounded, sits outside both budgets, and buys a flush.** §5.2: "Close context to flush video when possible"; §8.5: "Recovery deadline is the browser runtime cap plus bounded finalization/delivery margins." When the runtime deadline fires the parent asks for the ordered stop first — the child closes and awaits the recording context, which is the only way the webm is finalized — and gives it exactly `browserStopTimeoutMs`, then kills. That grace is configured, bounded, and **not** part of the runtime budget: a run does not get more browser time by being slow to die, because no step may execute during the grace and a test asserts none does. Two tests: a child that honours `stop` flushes and its evidence is `PENDING` (AC-16); a child that ignores `stop` is killed at the end of the grace, within a stated tolerance, and its evidence is `UNAVAILABLE`. Terminal delivery is then the second bounded margin — 10.6's existing window, attempt cap and backoff are used **as they are** — and it retains bounded resources: by the time the first terminal attempt is made the child process is gone, the browser is gone and scratch is cleared, so the only thing held across retries is one bounded report body (epic: "retry delivery must not retain unlimited resources"). A test asserts no process and no directory survives into the retry loop. **No `await` on any of these paths is unbounded**, asserted by driving each with a peer that never answers.
- [ ] **AC-5b:** *(Deferred — staging; owned by **10.19**, gated with **10.18**)* The runner's total — runtime cap plus stop grace plus terminal delivery window — is demonstrated to sit **inside** the API's recovery deadline against the deployed configuration, so a run this story kills is reconciled from its own `FINAL` report rather than racing the §5.4 running reaper into `ERROR / STALE`. Locally this story asserts the arithmetic against its own configured values and nothing more; the deployed values are 10.18's and the integrated proof is 10.19's. Recorded as **skipped, never passed**.
- [x] **AC-6:** **The effective bounds are the server's, and a job may not enlarge them.** §5.2: "Default step timeout is 30 seconds and total browser runtime 120 seconds, **configurable within server limits**"; the epic: "Step timeout defaults to 30 s; total runtime to 120 s **within API bounds**." The effective runtime cap is `min(job.deadlines.totalRuntimeMs, configured maximum)` and the effective step timeout is `min(job.configuration.timeoutSeconds × 1000, configured maximum)`; a job asking for less gets less, a job asking for more gets the server's value, and the clamp is observable — a test submits a job asking for ten minutes of browser time and asserts the kill lands at the configured maximum. The new maxima go through the enumerated `KEY_SPECS` so the config loader stays fail-closed. `job.configuration.timeoutSeconds` is currently accepted by the envelope and ignored by the run; this criterion is where it starts being honoured, clamped.

### Redaction, proven on what left the process

- [x] **AC-7a:** **Redaction is asserted on captured output, with canaries in the three shapes that defeat a source scan, and every assertion is proven red by mutation.** This epic has repeatedly found redaction that worked beside tests that could not tell, so the criterion is stated as an experiment rather than a property. A run carries a known canary through `resolvedVars`/`resolvedSecrets`. Canaries are planted in **three** shapes, each chosen because it reaches output without anyone deliberately routing it there:
  1. a value interpolated into a **formatted argument** — a message built by template literal or `util.format`-style substitution, where the value is an argument and not the format string;
  2. a value inside an **exception message** thrown from below the run path, so the string is produced by code this story does not own;
  3. a value inside a **nested object rendered by its own `toString`** (or inspection hook), so serialization reaches it through a path no field-by-field redaction enumerates.

  Every one of these surfaces is captured and asserted on the **bytes**, in all the variants `createRedactor` produces (plain, URL-encoded, doubly URL-encoded, `encodeURI`, base64 standard/unpadded/URL-safe): the `LogSink`'s written lines; the child's stdout and stderr as captured by AC-8; every serialized report body posted to the API — `STARTED`, every `PROGRESS`, `FINAL`, and **every byte-identical terminal retry**; `outcome.errorMessage`; every step's `failure`; every log entry's `message`; the spawn `args` and `env` handed to the operating system; the process command line; and every scratch file name and file content. **The proof obligation is the mutation:** for each of the three canary shapes the story records which deliberate mutation — removing the sink's redaction, removing the relay's, bypassing `safeMessage` — turned which named test red, and the test is restored. An assertion nobody has seen fail has not been shown to assert anything.
- [ ] **AC-7b:** *(Deferred — **10.19**, with **10.17**)* The same canary proven through the integrated path — that nothing the **API persists** carries it: progress rows, the persisted snapshot, structured log storage, and the terminal result manifest (10.14's object, 10.17's real secret material). The epic's bullet is "Canary values never appear in stdout, progress, final JSON, **manifests or persisted diagnostics**"; the runner can only assert on what leaves it, and this story says so rather than claiming the other half. Recorded as **skipped, never passed**.
- [x] **AC-8:** **The child's stdout and stderr stop being an unredacted, unbounded channel.** Today the fork inherits both, so Playwright's diagnostics, a Chromium warning and any uncaught stack trace in the child reach the pod log with nothing in front of them — §9.2 requires the runner to scrub "every outbound diagnostic before persistence", and a pod log is persistence. The parent captures the child's output and passes it through the **run's** redactor and the same per-message length cap before it reaches the pod log. Four properties, each asserted: the relay is **line-bounded and volume-bounded**, so a chatty browser cannot flood the log or the parent's memory, and the drop is visible rather than silent; the relay **cannot block or delay** the run, the kill or the parent's control endpoints — a slow or throwing sink is contained the way 10.12's step-event forwarding already is; output arriving **after** the child is killed is still redacted or dropped, never flushed raw; and the relay holds **no reference to a resolved value** after the run (AC-9). This changes the `stdio` the spawner requests, which is a production seam 10.12 closed by type — AC-19 keeps it closed. **@po ruling, 2026-09-11: IN SCOPE, and not scope creep.** Three reasons, in order of weight. The epic's own acceptance bullet names the surface by hand — *"Canary values never appear in **stdout**"* — so cutting the relay would not descope a nice-to-have, it would leave a named acceptance bullet unassertable and force AC-7a's stdout surface to be recorded as *skipped, not passed* on the very story the bullet belongs to. §9.2 requires scrubbing *"every outbound diagnostic before persistence"* and a pod log is persistence, so the current `stdio: ['ignore','inherit','inherit','ipc']` — verified on the branch — is a standing violation this story is the first to be able to close. And it is the **only** redaction that covers output the runner did not format: a Playwright exception or a Chromium warning is precisely the canary shape AC-7a item 2 exists to chase, and no amount of `safeMessage` discipline reaches it. This is redaction work this story owns. It is, however, real work and it is part of why the size moved to L; if the story must be cut it is the **second** half of the split hint, and the cut is then explicit with the stdout surface recorded as skipped-not-passed — never quietly dropped.
- [x] **AC-9:** **No resolved value is retained anywhere, on any path, including the kill path.** §9.2: "Never persist them in jobs, retry queues, manifests or diagnostics." `resolver.wipe()` and the redactor's release happen on **every** exit path — success, step failure, launch failure, start-deadline refusal, runtime-deadline kill, run fault, and drain — and the assertion is made **after a kill**, not only after a clean finish, because the kill path is the one that skips the ordinary `finally`-ordering assumptions. Nothing job-shaped is written to scratch, held in the terminal retry buffer between attempts, captured in a closure that outlives the run, or attached to an `Error` that is retained. A test drives a killed run and asserts the process holds no path to the values afterwards.
- [x] **AC-10:** **Message and retained-log caps hold on the deadline path too.** The epic's bullet is "cap messages and retained logs". 10.6 shipped `ReportBounds` — `maxSteps`, `maxLogEntries` (oldest dropped first), `maxLogEntryLength`, `maxBodyBytes` with a reduced-payload fallback — and this story uses them **as they are** rather than adding a second bounding path. What it must prove is that the new output obeys them: the timeout's own log entry and `outcome.errorMessage` are truncated by the same caps, and a run that floods log lines right up to the instant it is killed still produces a `FINAL` body within `maxBodyBytes`, with `logsTruncated` true and `payloadReduced` set if it came to that — never an oversized body, because a report rejected for size is a lost result the runner cannot replay. AC-8's relay is bounded by the same per-message length.

### Cleanup, observed rather than inspected

- [x] **AC-11a:** **The process tree is gone — established by looking for it.** On each of six paths — success, step failure, launch failure, run fault, **runtime-deadline kill**, and drain — no child process and **no browser process descended from it** survives. This is asserted by **observation against real Chromium**: the pids are enumerated after the run and none remains. An assertion that `kill` was called is explicitly **not** sufficient and is named as insufficient, because Chromium is a grandchild of the fork: `SIGKILL` to the fork's pid leaves the browser orphaned and holding `/dev/shm`, the scratch directory and a video file. The child is therefore started so that the whole tree is reachable — its own process group, signalled as a group after the ordered stop — and the mechanism is proven by a test that hangs the child *below* the Node layer (a browser that ignores close) and still observes an empty tree. Verified on a developer machine, which `ED-05`'s `gate_note` permits.
- [ ] **AC-11b:** *(Deferred — `ED-05` / **10.18**)* The same six paths inside the pinned internal image, under the container's PID-1 process reaping (§9.3 "process reaping"), with `readOnlyRootFilesystem: true`, `emptyDir` scratch and `emptyDir{medium: Memory}` `/dev/shm` (ADR-001 §9). Zombie reaping is a property of the image's entry point, not of this package; this story cannot create that condition on a developer machine and does not claim it. Recorded as **skipped, never passed**.
- [x] **AC-12:** **Scratch, temp output and video artefacts are gone on every path — asserted on the filesystem.** After each of the six paths of AC-11a, the per-run directory is absent and `ScratchStore.list()` is empty: the Chromium profile/user-data directory, the `TMPDIR` contents the launcher points into scratch, the video directory, and **a file the recorder was still writing when the tree was killed**. The `clearAll()` at startup stays (a pod killed mid-run must not let the next run inherit a directory). A test inspects the filesystem after each path rather than asserting that `clear()` was called, and a test asserts a partially written video file is deleted rather than left for someone to find. The epic's path list is "success/failure/timeout/**upload**/callback error": the upload path is **10.14**'s and is named as absent here, the callback-error path is proven now by a terminal delivery that never succeeds.
- [x] **AC-13:** **The slot is released and the next run succeeds.** Epic acceptance bullet 1: "Hung child is terminated, **next run succeeds**." After each path capacity returns to its configured size, and a second run admitted immediately after a killed one executes end to end on real Chromium and passes. This is the assertion that catches a leaked slot, a leaked timer, a leaked scratch name and a leaked `/dev/shm` handle in one test, which is why it is stated as "the next run succeeds" rather than as "the counter returned to 1".
- [x] **AC-14:** **The control endpoints stay responsive while a child is hung.** Epic acceptance bullet 1, §4.5 ("control/validation endpoints have separate bounded resources"). **While** a run is hung and before its deadline fires — measured during the hang, not after it — `GET /health` and `GET /ready` answer within a bounded time, `POST /v1/validate` validates an artifact normally, `/ready` stays **true** (saturation is not unreadiness; 10.6's rule is untouched), and a second `POST /v1/runs` receives `429` with `Retry-After` rather than blocking. The hung child must not be able to stall the parent's event loop through the IPC channel or the AC-8 relay.
- [x] **AC-15:** **Drain on `SIGTERM` finishes or ends admitted work; it never orphans it.** §9.3: "drain admitted work on SIGTERM"; §5.4: "Drain before removing a runner Deployment." On `SIGTERM` readiness goes false, no new admission is accepted, admitted runs are allowed to finish within `drainTimeoutMs`, and a run still hung when that expires is **killed and reported** rather than abandoned — a runner that exits holding a browser is the state the §5.4 reaper has to guess at. Nothing is left running when the process exits, asserted by AC-11a's observation on the drain path.

### Evidence stays honest about what was cut short

- [x] **AC-16:** **A truncated run tells the truth about its video, and the outcome is still independent of it.** Epic acceptance bullet 3: "Abrupt loss reports honest unavailable/partial evidence rather than **promising a complete video**." *(Extended by @po on 2026-09-11 to carry ADR-002 §17.7, which assigns this story the `partial` producer. §17 rules inside this criterion's own subject and adds no new one; the three cases below replace the drafted two.)*

  **Three cases on a runtime-deadline kill, not two**, each asserted on the serialized `FINAL` body:
  - **(a)** the bounded stop of AC-5a completed within `browserStopTimeoutMs` **and** left a playable file (size *and* readable header, 10.12's `recording.ts` check) → `state: PENDING`, **`partial: false`**. A timeout is not automatically a truncation; §5.2's ordered close exists precisely so the webm is finalized.
  - **(b)** the stop grace expired, the tree was killed, and **the file left behind is nevertheless playable** → `state: PENDING`, **`partial: true`**. This is the third case the drafted two-way split absorbed, and it is the dangerous one: today it would report `PENDING` with the API publishing `partial: false` — a salvaged prefix presented as a whole video, which is the exact sentence the epic bullet forbids. **The distinguishing fact is not the file; it is whether the ordered stop completed**, which the parent already holds and which must be recorded **before the signal**, for the same reason AC-3 records the timeout kind before killing. A test drives a child that ignores `stop`, leaves a playable prefix, and asserts `partial: true` — and a mutation that reads the flag from the file's playability instead of from the stop observation must turn it red.
  - **(c)** no playable file → `state: UNAVAILABLE`, **`partial: false`** — a recording that does not exist is not a partial one (§17.3). `PENDING` is never reported over an unflushed or unplayable file, and `STORED` is not this story's word any more than it was 10.12's.

  **`partial` is emitted explicitly on every `FINAL`, `false` included**, so "absent" is unreachable from the runner the moment this story lands (§17.5, §17.7 item 2) — asserted on the serialized body, not on the object that produced it.

  **`partial` is never derived from `outcome`, in either direction, and never computed from `outcome.errorCode` inside the runner** (§17.4). Independence is re-asserted **on this path**, in both directions, because 10.12 proved it only for the launch and step paths: a run killed on the deadline is `ERROR`/`TIMEOUT` whether its recording flushed or not; a video that failed to flush never alters `outcome.result`, `outcome.errorCode` or any step status (§6.1, an epic definition-of-done item); and the two cases §17.3 names as the inference's counter-examples are each asserted — **a cleanly flushed timeout carries `partial: false`, and a recorder that died on a passing run carries `partial: true`**. A mutation implementing `partial = (errorCode === TIMEOUT)` must turn both red.

  **What this story does not fix, stated so it is not mistaken for fixed:** the API still publishes `partial: false` on every execution. `RunnerReportProjection` writes `videoPartial = Boolean.FALSE` unconditionally — verified on the branch — and it is a Java file this story's Scope excludes. ADR-002 §17.7 item 4 assigns that half to **story 10.14** as **O-13**. After this story the runner reports the truth and the API discards it, which is bounded, visible and strictly better than asserting a falsehood — but the public snapshot is not honest until O-13 lands. A test records this as a **named live skip citing O-13 and 10.14**, so the half-fix cannot be read as a whole one.
- [x] **AC-17:** **The step that was running when the tree died keeps the state that was observed of it.** On a kill the in-flight step stays `RUNNING` with `finishedAtMs` and `durationMs` `null` and `failure` `null`; steps never reached are **absent** from the report, which is what `RunnerStepState` already specifies ("one entry per step the runner has **touched**"; the API fills the rest from the confirmed revision, §8.2). The runner does not convert it to `FAIL` — that would claim an assertion outcome it never observed and `RunnerStepState.failure` is documented as "null unless the status is `FAIL`" — and does not convert it to `SKIPPED`, which would claim it was never attempted. The contract's `SnapshotTimeout` example carries `message: 'Total browser runtime deadline reached'` on that step in the **public** snapshot; who writes that text is 10.7's projection question and is raised as an Open Question rather than answered by putting a message where the runner's own schema says `null`.

## Implementation Notes

- **SEC-2 is 10.18's, and here is the reasoning rather than a silent absorption.** QA's SEC-2 (10.12 recheck, MEDIUM) is that `PLAYWRIGHT_BROWSERS_PATH` or `HOME` pointed at a shim registry launches a binary that re-execs the real Chromium with `--no-sandbox`, unnoticed. The control is a **deployment** one — immutable image, `readOnlyRootFilesystem: true`, no environment override — which is `ED-05`/SPK-04 work and is already carried by 10.12's open **AC-6b**, which QA required to name browser-path immutability explicitly. **This story does not take it**, for three reasons: the runner's scope line here is deadlines, diagnostics and cleanup, and a browser-identity check is none of the three (Article IV); the variable cannot be dropped, because ADR-001 §4.2 makes it the mechanism by which the pinned image tells the library where its browsers live; and QA's own judgement is that the runner-side check "is only meaningful inside the image, because `chromiumBuild` is null outside it, so it would land with 10.18 anyway". **The residual gap QA named is real and stays named:** nothing reads the *running* browser's identity — the build number is recorded at image build time only. One fact worth recording for whoever implements it: `ReportedRuntimeVersions` is `additionalProperties: true`, so reporting a resolved executable path and a live `browser.version()` would **not** be a contract edit; the obstacle is ownership and meaningfulness, not the schema. What this story does owe SEC-2 is AC-19: it touches the constructor where the environment is built, and it must leave that surface no wider than it found it.
- **The parent cannot read the child's clock, and must not pretend to.** The run clock's zero is taken in the child at recording-context readiness (ADR-002 §11.2) and the parent never sees that monotonic source. Enforcement therefore runs on the parent's own clock, armed at the `ready` handshake, and the honest consequence is stated in AC-2: the enforced cap is longer than the configured one by the handshake latency. The wrong fixes are both tempting and both forbidden — deriving parent-side readings from `browserStartedAt` (a second origin, §11.5) or re-basing the child's readings against the parent's elapsed time (explicitly rejected). The timeout's log entry carries `atMs: null`; `null` is what the contract provides for exactly this.
- **`RUN_ERROR` is what a naive kill produces, which is why AC-3's negative test exists.** The abandoned-result path in `createInbox` synthesizes `failureKind: 'run-fault'` when the child exits without a result, and a deadline kill makes the child exit without a result. Unless the parent records *why* it killed before it kills, the report will honestly describe the symptom and lose the cause. The deadline must set the kind before the signal, not infer it from the exit.
- **Killing the fork is not killing the browser.** The fork's pid is Node; Chromium is below it, and Playwright's own cleanup only runs if the Node layer is alive to run it. Ordered stop first (which flushes the video, AC-5a and §5.2), then the group. The observation in AC-11a is the only thing that can tell these apart, and it is the reason that criterion is phrased as "enumerate the pids" rather than "assert the kill".
- **The step timeout and the run deadline are different mechanisms with different answers.** A step timeout is Playwright's per-operation bound inside the child and produces `FAIL`/`FAILED` (§8.2) — the run survives it and reports it. The runtime deadline is the parent's and produces `ERROR`/`TIMEOUT` — the run does not survive it. An implementation that lets the step timeout escalate into the run deadline, or that kills the tree because one locator was slow, has collapsed two vocabulary entries the architecture keeps apart.
- **`stdio: 'inherit'` was correct for 10.12 and is not correct after this story.** 10.12's comment is accurate as far as it goes — "the contract is not a debugging channel" — but §9.2 requires scrubbing *before persistence*, and the pod log is persistence. Capturing the child's output is what makes AC-7a's canary assertable at all; it is also the only redaction that survives a library the runner does not control writing something the runner did not format. The relay must be bounded and non-blocking: an unbounded pipe on a chatty browser is a memory leak, and a relay that awaits a slow sink is a new way to hang the process this story exists to keep responsive.
- **Do not build a second bounding or redaction path.** 10.6's `ReportBounds`, its newest-wins log buffer and the serialize-then-redact `Logger` are load-bearing and tested; 10.2's `createRedactor`/`safeMessage` are the scrubber. This story's work is to route the new surfaces through them and then prove it on captured bytes, not to write a second implementation that will drift.
- **The `.nvmrc` mismatch is inherited and must not be laundered here either.** `check:pins --require-image` fails by design because the pinned base image ships Node 24 while `.nvmrc` pins 22 (`ci/stages.md` **O-2a**, owned by `ED-05`/@architect). This story runs Chromium on a developer machine, where the in-image rule does not apply. Do not edit `.nvmrc` or `engines` (AC-20).
- **Starting values, not commitments** — 30 s step timeout, 120 s total runtime, 30 s admitted-start deadline, 10 s admission HTTP timeout, 600 s pending SLA, `POOL_SIZE=1`. §8.5 says to tune them against staging measurements, and the pending SLA is the API's number, not the runner's: the runner never sees it.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on 2026-09-11: `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a Darwin host, the CLI is absent and `graceful_degradation.skip_if_not_installed: true` applies. A draft checklist expecting such a section is satisfied by that ruling.

### AC-14 — the derivation of "a bounded time"

AC-14 says "within a bounded time" and gives no number, and @po left it rather than invent one.
Inventing one here would be Article IV. The number is therefore **derived**:

- §4.5 groups the endpoints into one set — *"control/validation endpoints have separate bounded
  resources"* — naming `/health`, `/ready` and `/v1/validate` together.
- The runner holds exactly **one** enumerated configuration bound over any member of that set:
  `STUDIO_RUNNER_VALIDATE_TIMEOUT_MS` (`config.validateTimeoutMs`, default 5 000 ms). It bounds the
  **heaviest** member — a full default-deny artifact revalidation.
- `/health` and `/ready` do strictly less work, on the same event loop, than a validation does. A
  deployment that accepts that bound for the heavy member has already accepted it for the light
  ones, so the derived bound for the whole set is `validateTimeoutMs`.

`test/server/hung-child.test.ts` **reads `runner.config.validateTimeoutMs`** and asserts against it;
it does not restate the number. An assertion and a constant authored in the same breath would only
be checking that one literal equals another, which is the shape the story warned about.

Falsified: mutation **MH-4** (a 6 s busy-wait inside the relay's delivery) turns
*"stays responsive while the hung child floods its captured output"* red at 6 006 ms against the
5 000 ms derived bound. The bound is live, not decorative.

What the bound is **not**: a claim that the event loop was never blocked at all. It is the claim the
criterion makes — the control endpoints answer, `/ready` stays **true** (saturation is not
unreadiness), `/v1/validate` validates normally, and a second `POST /v1/runs` is refused `429` with
`Retry-After` rather than queued — all measured **during** the hang, with the deadline still armed
and `inFlight === 1`.

### Two defects found by the real-browser tier, not by the unit tier

**(a) The kill was killing the child, not the tree — and the test could not tell.**

AC-11a's suggested mechanism is "its own process group, signalled as a group after the ordered
stop". I implemented exactly that: `detached: true` plus `process.kill(-pid, 'SIGKILL')`. Unit tier
green; fixtures tier green. Then the mutations:

- replacing the group signal with a single-pid kill: **still green**;
- removing `detached`: **still green**;
- **replacing the kill with a no-op**: **still green**.

The control proved the observation, not the code, was at fault. A probe of the live process table
then showed why:

```text
fork pid 16341  pgid 16341        node dist/run/child.js
  desc 16343    pgid 16343        chrome-headless-shell   ← its own group
  desc 16367    pgid 16367        ffmpeg-mac              ← its own group
  desc 16364/5/6 pgid 16343       chrome-headless-shell   (renderers, in Chromium's group)
group kill of -16341 → ESRCH for everything below the fork
```

**Playwright starts the browser and the video encoder detached, each in a process group of its
own.** So `kill(-forkPid)` reaches the Node layer and nothing else — the criterion's own suggested
mechanism is the "killed the child, orphaned the browser" failure wearing the clothes of the fix.
The tests stayed green because Chromium normally exits by itself when its parent's pipe closes, so
*any* kill looked correct.

Two changes followed. In the **source**, `signalProcessTree` now enumerates the tree first (a dead
root has no descendants to walk) and signals each member together with the group it leads,
deepest-first, root last. In the **test**, the browser is `SIGSTOP`ped before the kill — a wedged
browser that cannot notice its parent dying, which is AC-11a's "a browser that ignores close" — and
each previously observed pid is rechecked individually rather than the tree re-walked, because an
orphan is re-parented to init and disappears from any walk starting at the dead fork. With that
arrangement both MT-1′ and MT-2′ turn the fixtures tier red at the 30 s patience bound. Suspended
pids are force-cleaned in `afterEach`; `ps` confirmed no strays after the mutation runs.

**(b) A cleanly flushed timeout was reporting `partial: true`.**

`stop()` returned early on a boolean flag, so a second caller did not *await* the first. The child
sends its `result` **before** it exits, so `execute`'s awaited result resolved while `kill` was
still inside `awaitExit` — and `settleRecording` then read `orderedStopCompleted` before the exit
that sets it, concluded the ordered stop had not completed, and marked a cleanly flushed recording
partial. That is ADR-002 §17.3's first named counter-example, produced by the code meant to satisfy
it. Fixed by sharing one promise. Only the real-Chromium tier has both callers genuinely
overlapping; no unit test reached it.
