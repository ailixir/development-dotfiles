## User Story

**As a** put-checks user,
**I want** to create / read / update / soft-delete HTTP checks against my CSI-scoped catalog with polymorphic configuration stored as JSONB,
**so that** the Create Check page + All Checks page work end-to-end for the HTTP type, and the sealed-hierarchy design is validated against the first real check type before stories 2.2, 3.3-3.6, and 5.5 add 6 more permitted types against the same contract.

---

## Acceptance Criteria

- [ ] **AC-1:** `Check` JPA entity maps to the `checks` table (ARCH §7.1) with `configuration` column annotated `@JdbcTypeCode(SqlTypes.JSON)` holding a `CheckConfiguration` sealed-interface value.
- [ ] **AC-2:** `sealed interface CheckConfiguration permits HttpConfiguration` (others forbidden at compile time; added per story 2.2 / 3.3-3.6 / 5.5).
- [ ] **AC-3:** `@JsonTypeInfo(use=NAME, property="type", visible=true)` + `@JsonSubTypes({@Type(value=HttpConfiguration.class, name="HTTP")})` on `CheckConfiguration`. `@JsonTypeInfo(use=CLASS)` must NOT be used anywhere (CVE vector).
- [ ] **AC-4:** `HttpConfiguration` record fields match PRD §5.1 Basic Checks — HTTP(S) API Endpoint: `method` (GET/POST/…), `url`, `headers: Map<String,String>`, `body` (nullable), `expectedStatusCode` (Integer, default 200), `followRedirects` (bool, default true), `timeoutMs` (Integer, default 5000), `verifyTls` (bool, default true).
- [ ] **AC-5:** `CheckType` enum (`HTTP`, `TCP`, `SPLUNK`, `GRAFANA`, `ITRS`, `APPDYNAMICS`, `UI_TEST`) defined up front. An exhaustiveness test asserts `CheckType.values()` ↔ `CheckConfiguration` `getPermittedSubclasses()` ↔ `@JsonSubTypes.Type` registrations are in sync. If any of the three drifts, the test fails with a clear message telling which one is behind.
- [ ] **AC-6:** REST endpoints:
  - `POST /api/v1/checks` — create. Body is a `CheckRequest` DTO. Validates JSON against sealed hierarchy. Returns 201 + Location.
  - `GET /api/v1/checks` — paginated list. Filters: `csi_id`, `type`, `status`, `environment`, `created_by`, `search` (substring on name/description).
  - `GET /api/v1/checks/{id}` — fetch.
  - `PUT /api/v1/checks/{id}` — replace. Configuration discriminator MUST match original (changing `type` requires delete+create).
  - `DELETE /api/v1/checks/{id}` — soft-delete (sets `deleted_at`).
- [ ] **AC-7:** `@PreAuthorize` via `CsiOwnershipEvaluator`:
  - `canWrite` on POST / PUT / DELETE.
  - `canRead` on GET /checks/{id}.
  - GET /checks list is filtered-at-query-time to CSIs the user owns + public CSIs (same convention as story 1.7 note N-1.7-1; admins see all).
- [ ] **AC-8:** `CheckDto` (response shape) + `CheckRequest` (create/update shape) + `CheckMapper` (MapStruct with `@SubclassMapping` per variant; only HTTP registered for now).
- [ ] **AC-9:** Configuration JSONB roundtrip test: create HTTP check → read back → every HttpConfiguration field byte-identical to input.
- [ ] **AC-10:** Discriminator CHECK constraint from story 1.2 (AC-9) is verified by attempting a raw-SQL insert with `{"method":"GET"}` (no `type`); assert it fails. (Redundant with 1.2 but proves the entity layer doesn't bypass the DB constraint via some ORM quirk.)
- [ ] **AC-11:** "Add a hypothetical 8th type" regression test: temporarily register `@JsonSubTypes.Type(value=FakeConfiguration.class, name="FAKE")` in a test-scoped config; insert + read a FAKE row; assert the 7 real types still roundtrip. Proves forward compatibility (MS-06).
- [ ] **AC-12:** Filter + pagination behavior matches spec §6.1: offset-based for `/checks` (list), cursor-based optional via `?cursor=…`.
- [ ] **AC-13:** Sensitive fields in `HttpConfiguration.headers` (e.g., `Authorization`) masked in logs (extends `MaskingPatternLayout` from 1.1).
- [ ] **AC-14:** Integration tests: `CheckCrudIT`, `CheckFilterIT`, `CheckAuthzIT` (canRead/canWrite/admin-bypass), `ConfigurationRoundtripIT`, `ExhaustivenessIT`, `Hypothetical8thTypeIT`, `HeaderMaskingIT`.
- [ ] **AC-15:** JaCoCo coverage for `checks` package ≥ 80%.

## Implementation Notes (for @dev)

- **Sealed interface + JPA:** Hibernate 6.2+ handles sealed-interface JSONB via @JdbcTypeCode + Jackson. Verify by reading the Hibernate user guide section on `basic-jsonb` (cited in research MS-01) before writing custom type handlers.
- **Header masking:** extend the `MaskingPatternLayout` config with a pattern matching `"Authorization":"<value>"` + `"X-API-Key":"<value>"` etc. Keep the list configurable via `checks.log-masking.header-patterns`.
- **Filter at query time for list:** matches the N-1.7-1 decision for /csi. Small abstraction shared with /csi would avoid duplication but is over-engineering for 2 endpoints — re-evaluate when a 3rd list endpoint appears.
- **Configuration CHECK constraint:** already enforced in DB by story 1.2 AC-9. AC-10 here is a safety test that the entity layer doesn't accidentally bypass it.
- **Exhaustiveness test:** crucial. Without it, adding an 8th CheckType but forgetting the `@JsonSubTypes.Type` registration produces a silent deserialization failure at runtime. The test catches this at build time.
