## User Story

**As a** platform operator responsible for system stability,
**I want** the scheduling system to reject cron expressions that fire more frequently than a configurable minimum interval,
**so that** users cannot accidentally or intentionally create sub-minute schedules that overload the executor pool and downstream monitoring systems.

---

## Acceptance Criteria

- [ ] **AC-1:** New config property `checks.scheduling.min-interval-seconds` (default: `60`). Bound via `@ConfigurationProperties` or `@Value` in `ScheduleService`.
- [ ] **AC-2:** `ScheduleService.validateCronExpression()` computes the gap between the first two execution times of the parsed `CronExpression`. If the gap is less than `min-interval-seconds`, throws `ScheduleValidationException` with a clear message including the computed interval and the configured minimum.
- [ ] **AC-3:** The validation applies on both `create()` and `update()` paths.
- [ ] **AC-4:** `application.yml` declares the default: `checks.scheduling.min-interval-seconds: 60`.
- [ ] **AC-5:** Integration test: `POST /api/v1/schedules` with cron `*/5 * * * * *` (every 5 seconds) returns 400 with a message mentioning the minimum interval.
- [ ] **AC-6:** Integration test: `POST /api/v1/schedules` with cron `0 0 * * * *` (every hour) returns 201 (passes validation).
- [ ] **AC-7:** Integration test: `PUT /api/v1/schedules/{id}` updating to a sub-minimum cron returns 400.
- [ ] **AC-8:** Helm `values.yaml` exposes the property under `backend.configOverrides` and `worker.configOverrides` with appropriate per-environment defaults.

## Implementation Notes

- Spring `CronExpression.next(ZonedDateTime)` returns the next fire time. Call it twice to get the gap: `next1 = expr.next(now)`, `next2 = expr.next(next1)`, `gap = Duration.between(next1, next2)`.
- Use a fixed reference time (e.g., `2026-01-01T00:00:00Z`) for deterministic gap computation, avoiding edge cases where `now` lands near a DST boundary.
- The `@Value` injection is simplest here — no need for a full `@ConfigurationProperties` class since it's a single property consumed in one place.

## Dev Notes / QA Gate Notes

### Dev Notes (2026-05-19)

- Used a fixed `REFERENCE_TIME` (`2026-01-01T00:00:00Z`) for deterministic interval computation, avoiding DST edge cases when using `ZonedDateTime.now()`.
- `ScheduleValidationException` was not handled by `ChecksExceptionHandler` — Spring's default `@ResponseStatus` handler stripped the message from the response body. Added explicit `@ExceptionHandler(ScheduleValidationException.class)` to return structured JSON with the validation message.
- Dev environment uses 30s minimum to allow more frequent testing; UAT/prod use 60s.
- The guard validates on both `create()` and `update()` paths since both call `validateCronExpression()`.

### QA Gate Notes (2026-05-19) — PASS

- 62/62 scheduling tests pass. Zero regressions across CronDispatcher, ShedLock, Partition, and all CRUD/authz tests.
- Edge-case review: exact boundary (60s at min=60) accepted correctly via `<` operator; DST avoided by fixed UTC reference time; constructor guard added for invalid config values (0 or negative).
- Known limitation (accepted): only the first two fire times are sampled for gap computation. Non-uniform crons (e.g., weekday-only) could theoretically have a shorter gap between later executions that is not checked. Acceptable for v1 — sub-minute crons are the primary threat vector and are always caught.
