## User Story

**As** any user of a page that reads the sources/features bootstrap state — Checks Studio, All Checks, the check-type wizard, and every route wrapped in `FeatureGate` (Studio, Reports, Schedules) — and as the owner of 10.19 AC-2 (every failure state visible and truthful),
**I want** the `fetchSources`/`fetchFeatures` thunks to refuse a 200 response that is not the JSON shape their own declared types promise,
**so that** a non-conforming body — an HTML page, an empty response, or the wrong JSON shape — ends the same way a network failure already does today (fail-open defaults, `error` set, `fetched` true, `loading` false), instead of leaving an array `undefined` and crashing the first `.find()` or `.length` call any consumer makes against it.

## Problem Statement

**Re-verified by reading, at this story's own base commit `714dc4553`** (the manifest's finding was written against `7357082e3`; both files are unchanged between the two — confirmed by re-reading, not assumed).

**1. Neither fulfilled reducer checks the payload's shape.** `sourcesSlice.ts`:
```
18  export const fetchSources = createAsyncThunk('sources/fetch', async () => {
19    const response = await sourcesApi.getSources();
20    return response.sources;
21  });
...
33      .addCase(fetchSources.fulfilled, (state, action: PayloadAction<CheckSource[]>) => {
34        state.data = action.payload;
```
`featuresSlice.ts`:
```
40  export const fetchFeatures = createAsyncThunk('features/fetch', async () => {
41    const response: FeaturesResponse = await featuresApi.getFeatures();
42    return response;
43  });
...
55      .addCase(fetchFeatures.fulfilled, (state, action: PayloadAction<FeaturesResponse>) => {
56        state.sources = action.payload.sources;
57        state.features = action.payload.features;
```
Both thunks trust `sourcesApi.getSources()`/`featuresApi.getFeatures()` to have returned the declared `CheckSourcesResponse`/`FeaturesResponse` shape and both reducers assign whatever arrived. Neither the TypeScript generic on `apiClient.get<T>()` (`apiClient.ts:116-119`, `return response.data` cast to `T` with no runtime check) nor axios itself enforces that promise at runtime.

**2. MEASURED (by @qa, not this drafter): a non-JSON 200 body takes the `fulfilled` path, not `rejected`.** `docs/qa/gates/carry-forward-2026-09-16.yml`, probe **M2** — "the setup server answers 200 text/html, simulating the clobber in-process: 1 red, isolation, because error is not a 404 string. 0 hits" — and its own ruling: *"the fulfilled path is taken, since error stays null."* Axios's default transformer does not throw on a non-JSON body; it returns the raw text as `response.data`. So for an HTML body, `response` in `fetchSources` is a **string**; `response.sources` on a string is `undefined` (no throw), and `state.data = undefined`. For `fetchFeatures`, `response.sources`/`response.features` are both `undefined` the same way.

**3. The crash this produces was reproduced, but only against a local stand-in server, never against the real deployment.** `docs/qa/carry-forward-2026-09-16.md`'s mutation table, row **E1** (`ENV-2` rows): with the fix that isolates tests from `:3000` disabled, `pageRunGate` failed with `TypeError: Cannot read properties of undefined (reading 'find')` — the same crash class PROD-1 names. **VERIFIED BY READING:** the `.find()` calls live inside the slices' own selectors — `sourcesSlice.ts:63` (`state.sources.data.find(...)`, inside `selectIsSourceEnabled`) and `featuresSlice.ts:84` (`state.features.features.find(...)`, inside `selectIsFeatureEnabled`) — not inside the page component itself. **INFERRED, NOT TESTED:** that an expired production session, redirected to an HTML login page by an SSO/BFF layer, produces this same response shape. No real deployment was exercised for this finding (manifest, verbatim: "INFERRED, NOT TESTED").

**4. VERIFIED BY READING (this drafter, not in the manifest): the crash surface is wider than "the Studio page."** Every non-test consumer of the two slices' data-bearing selectors:

| Consumer | File:line | Selector used | What breaks on `undefined` |

| `CheckTypeSelector` (used by the check-creation wizard) | `components/checks/wizard/CheckTypeSelector.tsx:116,120-121` | `selectSources` | `sources.length` throws (`reading 'length'`) before `.find()` is ever reached |

No other non-test file imports `selectFeatures`, `selectFeatureSources`, `selectIsSourceEnabledFromFeatures`, `selectSourcesFetched` or `selectFeaturesFetched` (verified by grep across `frontend/src`, excluding `.test.` files and the two slice files themselves).

## Acceptance Criteria

### (a) The guards

- [ ] **AC-1: `fetchSources`'s thunk callback refuses a response whose `sources` field is not an array, before returning it, so the reducer never receives it as a `fulfilled` payload.** Location: the async callback passed to `createAsyncThunk('sources/fetch', ...)` in `sourcesSlice.ts` (currently lines 18-21). A response that is `undefined`, `''`, an HTML string, `{}`, `[]`, or `{ sources: 'not-an-array' }` causes the callback to `throw` a descriptive `Error` (message content is @dev's choice; it becomes `state.error` via the existing `action.error.message ?? 'Failed to fetch sources'` fallback at `:40`) instead of returning. A response of `{ sources: [...] }` — any array, including empty — is returned unchanged, exactly as today. **Validation checks only the top-level shape `CheckSourcesResponse` already declares** (`sourcesApi.ts:9-11`: `{ sources: CheckSource[] }`) — it does not additionally check each item's `type`/`enabled`/`label` fields (see Dev Notes, AUTO-DECISION, and Scope). *[Source: manifest `target_behaviour`, "a fulfilled response whose shape is wrong is handled as a FAILURE"; `sourcesApi.ts`'s own declared `CheckSourcesResponse`]*

  *Anti-vacuous:* the production symbol is the new guard clause inside `fetchSources`'s callback. Mutation: delete or comment out the guard → the malformed-body tests (Task 1) go red, observing `fetchSources.fulfilled` dispatched with an `undefined`/non-array payload and `state.sources.data` left `undefined` — PROD-1, reproduced exactly. Restore the guard; `sha256` of `sourcesSlice.ts` before/after.

- [ ] **AC-2: `fetchFeatures`'s thunk callback refuses a response whose `sources` or `features` field is not an array, before returning it.** Location: the async callback passed to `createAsyncThunk('features/fetch', ...)` in `featuresSlice.ts` (currently lines 40-43). Same malformed-input set as AC-1, applied to both fields of `FeaturesResponse` (`featuresApi.ts:10-13`: `{ sources: CheckSource[]; features: FeatureFlag[] }`). A response with both fields present as arrays (any length) is returned unchanged. Top-level shape only, same limit as AC-1. *[Source: same as AC-1, applied to `featuresApi.ts`'s declared `FeaturesResponse`]*

  *Anti-vacuous:* same mechanism as AC-1, on `featuresSlice.ts`'s guard. Mutation: delete the guard → the malformed-body tests on `*/features` (Task 3) go red the same way. Restore; `sha256` of `featuresSlice.ts` before/after.

### (b) The target state, and what does not change

- [ ] **AC-3: A refused response lands the slice on exactly the state its `.rejected` branch already produces for a network failure — zero reducer changes required to satisfy this AC.** For `sources`: `loading: false`, `fetched: true`, `error` set to a non-empty string, `data` the existing 7-item fail-open list (`sourcesSlice.ts:44-53`) if it was previously empty. For `features`: `loading: false`, `fetched: true`, `error` set, `sources`/`features` populated from `DEFAULT_SOURCES`/`DEFAULT_FEATURES` (`featuresSlice.ts:13-30,65-70`) if previously empty. **Regression controls, both must stay green, unchanged:** a well-formed `{ sources: [...] }` / `{ sources: [...], features: [...] }` body (including the empty-array case, `HttpResponse.json({ sources: [] })` — the exact shape `pageRunGate.test.tsx:81-82`'s own `bootstrapHandlers` already mock) is still stored via `fulfilled`, unchanged from today; a `404` still reaches `rejected` and fails open, unchanged from today (`bootstrapIsolation.test.ts:26-36` already asserts this and must stay green with **zero edits**). *[Source: manifest `target_behaviour`, "It ends in the same state the rejected path reaches today... A well-formed 200 is stored as it is today"]*

  *Anti-vacuous:* the production symbol is the existing fail-open backfill inside each `.rejected` case (`sourcesSlice.ts:43-53`; `featuresSlice.ts:65-70`). Mutation: comment out one backfill `if` block → the malformed-body test's fail-open assertion (the 7-length array / the `DEFAULT_SOURCES`/`DEFAULT_FEATURES` membership) reddens, proving the test checks the specific shape and not merely "is an array." Restore; `sha256` verified.

- [ ] **AC-4: No consumer of either slice throws when a slice lands on the AC-3 failure state.** The concrete, reproduced case — `ChecksStudioPage`, mounted with a real `Provider`/`MemoryRouter`/mock-server harness (not a hand-built store), against an HTML body on `*/checks/sources` and, separately, on `*/features` (two states, per the manifest's own "wave-8 rule" split) — renders without throwing, closing PROD-1's exact crash. The other three found consumers (`CheckTypeSelector`, `AllChecksPage`, `FeatureGate` — Problem Statement, point 4) are **not** given dedicated render tests in this story (see *Weakest criterion*); their safety is a structural consequence of AC-1–AC-3, proved by one selector-level assertion: after either malformed fulfillment, `selectSources(state)`, `selectFeatureSources(state)` and `selectFeatures(state)` each still return a non-empty array, never `undefined` — the exact three selectors those three components read through, and the same guarantee `selectIsSourceEnabled`/`selectIsFeatureEnabled`/`selectIsSourceEnabledFromFeatures` depend on internally for their own `.find()` calls. *[Source: this drafter's own consumer survey, Problem Statement point 4; manifest target_behaviour's "must never leave an array undefined" is general, not scoped to one page]*

  *Anti-vacuous:* the production symbol is the same guard as AC-1/AC-2. Mutation: remove it → the new page-level test (Task 5) reddens with the **exact reproduced crash string**, `Cannot read properties of undefined (reading 'find')` — closing the loop on @qa's original finding under the same conditions this story's own passing test exercises. Run `npx vitest run` (whole frontend suite) before and after this story's change; `bootstrapIsolation.test.ts` stays green in both, and no file times out with `"ENV-2: the store's import-time bootstrap did not settle"`.

## Vacuous-shape self-check

- **Avoids "a guard proved only by reading the code."** AC-1/AC-2 are proved by actually dispatching the real thunk against a mocked/intercepted HTTP response and inspecting the resulting action and state — not by reading the guard and asserting it "looks right."
- **Avoids "two guards each covering half a property."** AC-1 (sources) and AC-2 (features) are deliberately separate, per-endpoint guards — the manifest's own "wave-8 rule" ("split into two states") — so a fix that guards only one endpoint cannot satisfy both.
- **Avoids "a documented invariant only prose protects."** AC-5 is proved by an actual full-suite run, not asserted in Dev Notes alone.

## Weakest criterion

**AC-4's protection of `CheckTypeSelector`, `AllChecksPage` and `FeatureGate`** is the weakest part of this story. It rests on a shared-selector-contract argument (all three read exclusively through `selectSources`/`selectIsFeatureEnabled`, which AC-1–AC-3 guarantee never resolve to `undefined`) plus one selector-level unit assertion — not a dedicated mount-and-render test per component, which is what proves the `ChecksStudioPage` case. This keeps the story at S. **The named gap:** a future change to any of those three components that reads the store through a *different* path than the shared selectors (for example, `useAppSelector((s) => s.sources.data)` inline) would not be caught by this story's guards, only by whatever test that future change itself brings.

## Dev Notes

### Where validation belongs: the thunk — not the reducer, not the API client (AUTO-DECISION)

**[AUTO-DECISION @sm] Validate inside the two thunks' async callbacks, throwing on a bad shape so `createAsyncThunk` dispatches `rejected` automatically.**

- **Not `apiClient.ts` (the API client).** It is generic and endpoint-agnostic — every other API module in the app (`checksApi`, `csiApi`, scheduling, etc.) shares it, each with an unrelated response shape. Adding `CheckSourcesResponse`/`FeaturesResponse`-specific knowledge there would mean either threading a generic runtime-schema mechanism through every `apiClient.get<T>()` call app-wide (inventing a schema library — the brief explicitly rules this out), or special-casing two endpoints inside a class that is supposed to know nothing about them — both break single responsibility and both are far larger than an S story. CLAUDE.md's "All HTTP requests through the centralized API client" rule is about routing every call through `apiClient`, which this story does not change; it does not say the client must know each endpoint's shape.
- **Not the reducer (`.fulfilled` branch).** The `.rejected` branch (`sourcesSlice.ts:38-54`; `featuresSlice.ts:61-71`) already implements the exact target state (fail-open defaults, `error` set, `fetched: true`, `loading: false`) — the manifest's own words, "the same state the rejected path reaches today." Putting the check in the reducer would mean either duplicating that fail-open logic inside the `fulfilled` branch, or having `fulfilled` call into `rejected`'s logic across branches — more code than intercepting the bad shape one line before the reducer ever sees it.
- **The thunk callback** is the one place that (a) already knows the specific declared response type (`CheckSourcesResponse`, `FeaturesResponse`), (b) sits directly before the point where `fulfilled` vs `rejected` is decided, and (c) lets a thrown `Error` become the `rejected` action automatically — `createAsyncThunk`'s own designed mechanism, and consistent with how `apiClient.ts`'s own response interceptor already normalizes failures into a thrown `Error` for the same reason (`apiClient.ts:99-105`). Net diff: two small guard clauses, zero reducer edits.
- **Corroboration, not adoption:** `wt/epic`'s independent, uncommitted work reaches the same site (the thunk callback) with the same mechanism (validate, then throw) for the same two thunks — see the header table. This strengthens, but is not the basis for, this decision; the reasoning above stands on its own from this codebase's existing patterns.

### Validation depth: top-level array shape only (AUTO-DECISION)

**[AUTO-DECISION @sm] Check only that `response.sources` (and, for features, `response.features`) is an array — not each item's `type`/`enabled`/`label` fields.** The manifest's `target_behaviour` names three failure shapes: HTML, wrong JSON shape, empty. All three are caught by an array check on the two declared collection fields; none of the three examples describes a well-formed array of malformed items. Per-item field-type validation (matching `CheckSource { type: string; enabled: boolean; label: string }` and `FeatureFlag { key: string; enabled: boolean; label: string }` exactly) is a real, derivable-from-existing-types strengthening — and `wt/epic`'s independent guard already does it — but it is not named by the manifest and is left as Open Question 1 rather than folded into this story's required scope.

### Proposed guards (illustrative; @dev may adjust the exact error message and variable names, not the location or the two checked fields)

```ts
// sourcesSlice.ts
export const fetchSources = createAsyncThunk('sources/fetch', async () => {
  const response = await sourcesApi.getSources();
  if (!response || !Array.isArray(response.sources)) {
    throw new Error('Invalid /checks/sources response shape: expected { sources: CheckSource[] }');
  }
  return response.sources;
});
```
```ts
// featuresSlice.ts
export const fetchFeatures = createAsyncThunk('features/fetch', async () => {
  const response: FeaturesResponse = await featuresApi.getFeatures();
  if (!response || !Array.isArray(response.sources) || !Array.isArray(response.features)) {
    throw new Error('Invalid /features response shape: expected { sources: CheckSource[]; features: FeatureFlag[] }');
  }
  return response;
});
```
`!response` also catches an empty-string body (falsy) and a `null`/`undefined` one. `Array.isArray(x.sources)` on a string, an object without the key, or an array (whose `.sources` is `undefined`) is `false` in every case — no `typeof` pre-check is needed.

### Testing approach: exercise the real thunk, not a hand-built `fulfilled` action

**This matters and is easy to get wrong.** `sourcesSlice.test.ts`'s existing tests (`:18-31`) call `fetchSources.fulfilled(sources, '')` directly — a hand-built action that never runs the thunk's own async callback. A guard placed inside that callback (as this story specifies) is invisible to a test written that way. New tests must instead dispatch the actual thunk — `store.dispatch(fetchSources())` — against a store, with the underlying HTTP call intercepted (MSW) or the `sourcesApi`/`featuresApi` module mocked (`vi.mock`), so the callback itself runs and its guard is exercised. The page-level test (Task 5) follows `pageRunGate.test.tsx:79-136`'s existing pattern exactly: the module-singleton `store`, `studioMockServer`, and `<Provider store={store}><MemoryRouter><ChecksStudioPage /></MemoryRouter></Provider>` (`pageRunGate.test.tsx:128-136`). The well-formed control body should reuse that same file's own mock shape, `HttpResponse.json({ sources: [] })` / `HttpResponse.json({ sources: [], features: [] })` (`pageRunGate.test.tsx:80-83`) — this is "deriving the shape from existing mocks," per the brief.

### Why FOC-08 is not expected to be at risk

Both branches that set `fetched: true` already do so unconditionally: `fulfilled` at `sourcesSlice.ts:36` / `featuresSlice.ts:59`, and `rejected` at `sourcesSlice.ts:41` / `featuresSlice.ts:64`. This story adds a *third route into* `rejected` (a bad shape, alongside a network error) without touching what `rejected` does. `setup.ts`'s wait condition is `fetched && !loading` for both slices (`setup.ts:81-82`) — unaffected either way. This is why AC-5 predicts no `setup.ts` edit is needed; Task 7 is where that prediction is actually tested, not assumed.
