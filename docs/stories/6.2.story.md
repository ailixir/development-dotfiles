## User Story

**As a** platform operator,
**I want** all three execution tables (`execution_results`, `ui_test_executions`, `report_executions`) to be range-partitioned with DEFAULT partitions as safety nets,
**so that** data growth is managed uniformly and INSERT failures are prevented if a monthly partition is ever missed.

---

## Problem Statement

Currently only `execution_results` is partitioned (V1__init.sql). `PartitionManager` lists all 3 tables as managed, but `ui_test_executions` and `report_executions` are plain tables — calling `ensurePartitions()` or `pruneExpired()` on them will either no-op or error.

Additionally, `execution_results` has no DEFAULT partition. If `PartitionScheduler` fails to create the next month's partition (e.g., lock contention, OOM), all INSERTs fail with `ERROR: no partition of relation "execution_results" found for row`.

## Implementation Notes

- **Table conversion strategy:** Since the system is pre-production, the safest approach is:
  1. Rename existing table to `_old`.
  2. Create new partitioned table with same schema.
  3. Create bootstrap partitions + DEFAULT.
  4. `INSERT INTO new_table SELECT * FROM old_table` (if data exists).
  5. Drop `_old` table.
  This must be a single Flyway migration to maintain atomicity.
- **DEFAULT partition monitoring:** Query `pg_class` for the default partition, then `SELECT COUNT(*) FROM default_partition`. If > 0, something is wrong.
- **Partition column selection:**
  - `ui_test_executions`: use `executed_at` (matches execution_results pattern).
  - `report_executions`: use `created_at` (most natural time dimension).
