## User Story

**As a** platform operator responsible for the Studio API's security boundary (and, transitively, every CSI owner whose drafts the API stores),
**I want** `POST /tests`, `PUT /tests/{id}` and `DELETE /tests/{id}` to enforce the same CSI write authorization that `compile`, `confirm-compile` and `execute` already enforce, with an unknown, soft-deleted or quarantined draft answering the identical `403 STUDIO_FORBIDDEN` those routes already give,
**so that** an authenticated caller without write access to a draft's CSI can no longer create, edit or delete it, and no status code on these three routes can be used as an oracle for whether a draft exists.

---

## Problem Statement

ADR-002 §27.1 read the merged code (`epic/EPIC-10` at `f1d7968df`) and found that three of the seven per-id/create Studio routes carry no CSI write check at all, next to four that do:

| Route | Unknown id | Soft-deleted / quarantined | Draft on a CSI the caller may not use | Evidence |
|---|---|---|---|---|
| `GET /tests/{id}` (unaffected by this story) | 403 | 403 | 403 | `findTestById(UUID, Authentication)` reads through the `@SQLRestriction` and calls `requireRead` |
| `PUT /tests/{id}` | **400** `BAD_REQUEST` *"UI Test not found: {id}"* | **400** | **No check — the save goes through** | `updateTest(UUID, UITestRequest, Authentication)` uses `auth` only to attribute an enqueued compile |
| `DELETE /tests/{id}` | **400** | **400** | **No check — soft-deleted, `204`** | `StudioController.deleteTest(@PathVariable UUID id)` takes **no** `Authentication` at all; `softDeleteTest(UUID)` has no check |
| `POST /tests` | — | — | **No check — the draft is created under any registered CSI** | `createTest` calls `extractIdentity` and `requireRegisteredCsi` only |

`SecurityConfig` requires `.authenticated()` on `/api/**`, `@EnableMethodSecurity` is on, `CsiOwnershipEvaluator.canWrite` already exists and is already called from `compileTest`, `confirmCompile` and `executeTest` — **and from nowhere on create, save or delete** (verified by reading `StudioService.java` and `StudioController.java` on this branch; there is no `@PreAuthorize` anywhere in the `studio` package). Story 10.7's AC-4a says *"Every Studio route enforces identity and CSI permission"*, but its own list covered the reads and `execute` only (`docs/stories/10.7.story.md`); 10.7 is merged and is **not** reopened by this story — this story closes the gap that criterion's own list left open.

**This was masked, not absent.** Before story 10.18b closed the `core-service` identity bypass, every unauthenticated caller was silently upgraded to the hardcoded bypass identity, which carries `checks-admin` — so every request that ever reached these three routes in a test or a demo was, in effect, an administrator, and `canWrite` would have returned `true` regardless of whether the check existed. **No request has ever demonstrated this gap.** It is established by reading the merged code (ADR-002 §27.1), not by a failing probe, which is exactly why this story's own first commit must be the demonstration (Acceptance Criteria, Group A) rather than a fix landed on faith.

**The consequence, stated plainly (ADR-002 §27.3, "O-18", severity high, due before the credentialed pilot):** today, any authenticated caller — reader, stranger, or an owner of an unrelated CSI — can edit or soft-delete a Studio draft that belongs to a CSI they do not own, and `PUT`/`DELETE` on an absent, soft-deleted or quarantined draft answer `400`, which is an existence oracle a route that must not disclose existence cannot have.

### Group B — the three missing write checks (ADR-002 §27.2, §27.3)

- [ ] **AC-2:** `PUT /tests/{id}` and `DELETE /tests/{id}`, called by a principal **without write** on the draft's CSI. That means three identities: the class's `reader()` (`viewer` on that CSI); a `contributor` on that CSI, which is the closest role to a writer, because `CsiOwnershipEvaluator.READ_ROLES` is `{owner, contributor, viewer}` and `WRITE_ROLES` is `{owner}`; and `stranger()`, which has no ownership entry at all, both answer `403 STUDIO_FORBIDDEN` — and the draft row is **byte-unchanged**: `source_revision`, `configuration_revision`, `deleted_at`, `compile_status` and `current_candidate_revision_id`, read directly from the database, are identical before and after the refused call. Today this is `200`/`204` and the row visibly changes (the security assertion ADR-002 §27.5 names explicitly).
- [ ] **AC-3:** `POST /tests` with a `csiId` that **is** registered but the caller may **not** write answers `403 STUDIO_FORBIDDEN`, and **no `ui_tests` row is created** (asserted by a row count taken before and after, not by the response alone). The same caller creating on a CSI it **does** own still succeeds `201`, in the same test, so the deny assertion is not satisfied by a route that refuses everyone.
- [ ] **AC-4:** `PUT /tests/{id}` on an **unknown** id, a **soft-deleted** draft and a **quarantined** draft, called **as an administrator** (`checks-admin`), answers `403 STUDIO_FORBIDDEN` in all three cases — never `400`, never `404` — with **byte-identical response bodies** across the three. The same administrator identity is proven to reach the handler on the same draft **before** it is put into each withheld state (a positive control on the same row), so the three `403`s are attributable to the row's state and not to a broken test fixture. Today all three are `400`.
- [ ] **AC-5:** `DELETE /tests/{id}` on the same three states (unknown, soft-deleted, quarantined), as the same administrator identity, answers `403 STUDIO_FORBIDDEN` in all three — never `400`, never `404` — with the same byte-identical-bodies and positive-control shape as AC-4, and **nothing is written** (no second `deleted_at` bump, no other column changed) for the soft-deleted and quarantined cases. Today all three are `400`.
- [ ] **AC-6 (the non-vacuity control, ADR-002 §27.5, same commit as AC-2/AC-3):** an identity that **can** write — the draft's owner — still gets `200` on `PUT /tests/{id}` and `204` on `DELETE /tests/{id}` for the **same draft** the deny cases in AC-2 exercise. This is not a separate feature; it is the proof that AC-2's `403`s are not satisfied by every request failing for an unrelated reason (a wrong path, a wrong id, a broken fixture).
- [ ] **AC-7:** A malformed save — a body missing `sourceRevision`/`configurationRevision` — sent by a caller with **no** write access to the target draft's CSI still answers `400`, not `403`. This proves the refusal order's first rule (AC-9 below): a request-shape check that does not depend on stored state runs, and answers, before authorization, and reveals nothing about a particular draft either way.

### Group C — the refusal order and what it must never leak (ADR-002 §27.2, §14.4)

- [ ] **AC-8:** The order of refusal on `PUT`/`DELETE /tests/{id}` is exactly: (1) request-shape checks that do not depend on stored state (path-UUID syntax, the required-revisions check on `PUT`); (2) the draft is read **through the visibility restriction** (the same `@SQLRestriction`-scoped read `GET /tests/{id}` already uses) — if absent, `403`; (3) `canWrite` on **that draft's** CSI — if it fails, `403`; (4) for `PUT` only, the locked read (`findByIdForUpdate`) — a draft that disappeared between steps 2 and 4 also answers `403`, never `400`; (5) only after all of that, the existing `409 STALE_REVISION` / `409 CSI_IMMUTABLE` conflict checks. **The read in steps 2 and 4 is the visible one and is never `StudioRepository.findCsiIdIncludingWithheld`** — that method stays reserved for `compileTest`/`confirmCompile`, where §14.4 deliberately reads through a withheld draft to produce `409 TEST_QUARANTINED`/`409 TEST_DELETED`. Using it here would let an authorized owner of a withheld draft see it through a status code, which §14.5 already ruled against for save and delete.
- [ ] **AC-9:** `POST /tests` checks the registered-CSI requirement first. That check answers `400`, is unchanged, and does not depend on who is asking. Only then does it check `canWrite` on the request's `csiId` (`403`), never the other way round. **The proof is its own assertion:** a `POST` whose `csiId` is **not registered**, sent by a caller who is **not an administrator** and has no write on that id, answers `400`, not `403`. The caller must not be an administrator, because an administrator passes `canWrite` on any id, so swapping the two checks would change nothing for them. *(Amended at @po validation: the draft named AC-3's positive control and AC-7 as the proof. AC-7 is about `PUT`, and a positive control cannot detect ordering, so neither proves this.)*

### Group G — what HTTP cannot see (added at @po validation)

- [ ] **AC-18:** A new unit test, `StudioServiceWriteAuthorizationTest`, builds `StudioService` from Mockito mocks. All eleven constructor collaborators can be mocked; `StudioKillSwitchWiringTest` already mocks `StudioRepository` the same way. The test asserts three things:
  - **(a)** `updateTest(id, request, auth)` and `softDeleteTest(id, auth)` **never** call `StudioRepository.findCsiIdIncludingWithheld` (`verify(…, never())`). This is AC-8's prohibition.
  - **(b)** With a non-null `auth`, when the visible `findById` returns the draft and `canWrite` passes but `findByIdForUpdate` returns empty, `updateTest` throws `StudioAccessDeniedException`. This is AC-8 step 4: the draft disappeared between the two reads.

  **Why this exists.** Step 4 maps an empty locked read to `403`. Once it does, the forbidden `findCsiIdIncludingWithheld` read and the visible read give the **same HTTP answer** for every identity. For an administrator, the withheld read passes `canWrite` and the empty locked read then answers `403`. For anyone else, `canWrite` fails and the answer is `403`. The draft said AC-4/AC-5 would catch the wrong read. They cannot, so that falsification could never have failed (the wave-4 rule). The step-4 window also cannot be reached deterministically over HTTP. The CSI is immutable (`409 CSI_IMMUTABLE`, V12), so that window can only change a **status code**; it cannot grant access. That is why a unit-level check is proportionate here and an interleaved integration test is not required.

## Falsification (ADR-002 wave-4 standing rule: a mutation proof that cannot fail is not a proof)

*(Rewritten at @po validation, 2026-09-16. The draft said removing a write check would redden AC-4/AC-5, and that the wrong read would be caught at HTTP level. Neither was true. AC-4/AC-5 are guarded by the **visible read**, not by `canWrite`, and the wrong read is invisible over HTTP (AC-18).)*

Each mutation below is applied alone. For each one, @dev records the command, the red output naming the expected case, and a byte-identical restore checked with `git diff`.

| # | Production mutation | Must go red | Must stay green |
|---|---|---|---|
| M1 | Remove `requireWrite` from `createTest` | AC-3 deny half | AC-3's `201` half, AC-9, everything on `PUT`/`DELETE` |
| M2 | Remove `requireWrite` from `updateTest` | AC-2 `PUT` half (all three identities) | AC-4 (still `403`, from the visible read), AC-6, AC-2 `DELETE` half, AC-3 |
| M3 | Remove `requireWrite` from `softDeleteTest(UUID, Authentication)` | AC-2 `DELETE` half | AC-5, AC-6, AC-2 `PUT` half, AC-3 |
| M4 | In `updateTest`, the visible read's "absent" maps to `IllegalArgumentException` instead of `StudioAccessDeniedException` | AC-4 (all three states answer `400`) | AC-2, AC-5, AC-6 |
| M5 | The same for `softDeleteTest(UUID, Authentication)` | AC-5 | AC-2, AC-4, AC-6 |
| M6 | `createTest` checks `canWrite` before `requireRegisteredCsi` | AC-9 (the non-administrator's unregistered-CSI `POST` answers `403`) | AC-3 |
| M7 | `updateTest` reads the CSI through `findCsiIdIncludingWithheld` | AC-18(a) | **every HTTP test**. Record this as the measured reason AC-18 exists. |
| M8 | Step 4's empty locked read (with `auth`) throws `IllegalArgumentException` | AC-18(b) | every HTTP test |
| M9 | Swap the order in `updateTest` so the required-revisions check comes after authorization | AC-7 | AC-2, AC-4 |

**If any row's "must stay green" column goes red, that is a finding too.** It means the tests are not independent in the way this table claims.

**Named up front, not discovered at review: AC-7 is the weakest of these.** It proves an ordering property (shape-check before authorization) but its failure mode if omitted is a `403` instead of a `400` for a caller who was going to be refused either way — a wrong status code, not a security hole. It is kept because ADR-002 §27.2 states the order as a ruling, not a preference, and because a future change that swaps the order silently would go undetected without it; but unlike AC-2 through AC-6, its own falsification (swap the order) reddens a status-code assertion, not an authorization boundary. If a reviewer needs to cut scope under time pressure, this is the criterion to defer, named explicitly rather than dropped silently.

**@po's weakest-criterion call (validation, 2026-09-16): AC-18(a), not AC-7.** AC-7 is weak, but it is honest: it guards a status code, and M9 reddens it. AC-18(a) is weaker in a way a green run hides. A `verify(never())` on one repository method is a guard on the *shape of the source*. A new repository method that runs the same unrestricted native query under another name would pass it. That is the "source-text scan standing alone" shape, one level up. It is kept because nothing at HTTP level can see the substitution (M7), and **@qa's review must read the read path in `updateTest`/`softDeleteTest`, not just count the green test.**

## Implementation Notes

### The shared write-check helper

`StudioService` already has `requireRead`, `requireExecute` and `requireCompile` — three near-identical private methods, each checking a different `CsiOwnershipEvaluator` method against a `null`-safe CSI. `requireCompile`'s body (`canWrite`, throwing `StudioAccessDeniedException` on `null` or `false`) is **exactly** the check `createTest`, `updateTest` and `softDeleteTest` now need — §9.1 draws no distinction between "may compile/confirm" and "may create/edit/delete"; both are the owner-or-explicit-administrator tier.

**[AUTO-DECISION] Reuse `requireCompile` under a new, more general name rather than duplicate its body → extract a private `requireWrite(Authentication auth, String csiId)` with `requireCompile`'s existing implementation and a Javadoc citing §9.1/§27.2 generally, then have `requireCompile` call it (or rename it outright and update its two existing call sites, `compileTest`/`confirmCompile`) (reason: the two checks are the same permission tier under ADR-002 §9.1 — duplicating the body risks the two drifting apart under a future change to `canWrite`, and the existing name `requireCompile` is misleading once it also gates create/save/delete).** Either the rename or the delegation is acceptable; what is normative is that there is exactly one place `canWrite` is called for all five write-gated operations (compile, confirm, create, save, delete), not two copies of the same three lines.

### `updateTest`'s shape, precisely

Today (lines ~243–265):
```java
public UITestDto updateTest(UUID id, UITestRequest request, Authentication auth) {
  if (request.sourceRevision() == null || request.configurationRevision() == null) {
    throw new IllegalArgumentException("sourceRevision and configurationRevision are required on update");
  }
  UITest test = studioRepository.findByIdForUpdate(id)
      .orElseThrow(() -> new IllegalArgumentException("UI Test not found: " + id));
  // ...409 STALE_REVISION / 409 CSI_IMMUTABLE checks, then the write...
}
```

The required shape inserts the visible read and the write check **between** the existing required-revisions check and the existing locked read, and changes the locked read's failure **only when `auth != null`**:

- `auth != null` (every HTTP call, via `StudioController.updateTest`): read `studioRepository.findById(id)` — absent → `StudioAccessDeniedException`; else `requireWrite(auth, visible.getCsiId())`; then `findByIdForUpdate(id)` — if this *also* comes back empty (the row was deleted or quarantined between the two reads — a real but rare race), throw `StudioAccessDeniedException`, **not** `IllegalArgumentException`, per AC-8.
- `auth == null` (the internal two-argument overload, delegating with `auth = null`): skip both new steps entirely; `findByIdForUpdate(id)` keeps throwing `IllegalArgumentException("UI Test not found: " + id)` exactly as it does today, per AC-10.

`softDeleteTest` gets a parallel, simpler shape, because a soft-delete has no revision comparison to hold a lock across: add `softDeleteTest(UUID id, Authentication auth)`, which reads the visible row once (`findById`, absent → `StudioAccessDeniedException`), calls `requireWrite`, and then mutates the **same managed entity** it already holds — no second query is needed. Keep `softDeleteTest(UUID id)` (no `Authentication`) exactly as it is today for AC-10's internal callers, and have `StudioController.deleteTest` call the new two-argument overload with the `Authentication` Spring already injects into every other controller method on this class.

`createTest` gets one line: `requireWrite(auth, request.csiId());` inserted between the existing `requireRegisteredCsi(request.csiId());` and `userProvisioningService.ensureMirrored(identity);` — after the check that doesn't depend on identity (AC-9), before any side effect.
