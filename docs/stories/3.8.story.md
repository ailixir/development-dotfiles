## User Story

**As a** user viewing the dashboard,
**I want** the health summary, attention list, activity timeline, upcoming schedules, reports snapshot, and global search served from the real backend,
**so that** the dashboard reflects real-time system health from PostgreSQL, not static mock data.

---

## Acceptance Criteria

### Backend — New DashboardController

- [ ] **AC-1:** `DashboardController` created at `/api/v1/dashboard` with 8 endpoints.

**Summary**
- [ ] **AC-2:** `GET /api/v1/dashboard/summary?csiId={optional}` — returns aggregated health counts from checks table. Response: `{overallStatus: "HEALTHY"|"WARNING"|"CRITICAL", counts: {passing, failing, warning, muted}, lastUpdated}`. Uses `csi_metrics_current` materialized view when `csiId` provided, or `SELECT status, COUNT(*) FROM checks WHERE deleted_at IS NULL GROUP BY status` for global. `muted` count: checks with tag `muted`.
- [ ] **AC-3:** Authorization: authenticated. If non-admin, summary is scoped to user's owned CSIs only.

**Attention**
- [ ] **AC-4:** `GET /api/v1/dashboard/attention?csiId={optional}&limit={10}` — returns checks with status `FAILING` or `WARNING`, ordered by `lastExecution DESC`. Response: `{data: [{id, name, csiId, csiName, status, since, reason}]}`. `since` = time of the first consecutive failing execution. `reason` = last execution's error message or "Threshold exceeded".
- [ ] **AC-5:** Authorization: scoped to user's owned CSIs (unless admin).

**Activity**
- [ ] **AC-6:** `GET /api/v1/dashboard/activity?csiId={optional}&hours={24}` — returns recent events: check status changes + report deliveries. Response: `{data: [{id, type, title, description, csiName, timestamp}]}`. `type`: `FAIL`, `RECOVER`, `REPORT_SENT`. Source: `execution_results` table for check events (join on check for csiName), `report_executions` for report events. Ordered by timestamp DESC.

**Upcoming**
- [ ] **AC-7:** `GET /api/v1/dashboard/upcoming?csiId={optional}&limit={10}` — returns next scheduled executions. Response: `{data: [{checkId, checkName, nextExecution, csiName}]}`. Source: `schedules` WHERE `enabled=true` JOIN `checks` for name/CSI, ORDER BY `next_execution_at ASC`.

**Reports snapshot**
- [ ] **AC-8:** `GET /api/v1/dashboard/reports/snapshot?csiId={optional}&limit={5}` — returns recent reports. Response: `{data: [{id, name, nextScheduledAt, lastStatus}]}`. Source: `reports` table + latest `report_executions` row per report. NOTE: this depends on the reports table existing (story 3.10). If reports are not yet built, return empty array with a comment in the code.

**Search**
- [ ] **AC-9:** `GET /api/v1/dashboard/search?q={query}&csiId={optional}&environment={optional}&tags[]={optional}&tagMode={AND|OR}` — cross-entity search across CSIs, checks, and reports. Response: `{data: [{id, type, title, subtitle, path}]}`. `type`: `CSI`, `CHECK`, `REPORT`. Searches name + description fields with `ILIKE`. Max 20 results total (balanced across entity types: up to 8 CSIs, 8 checks, 4 reports).

**Acknowledge + Assign**
- [ ] **AC-10:** `POST /api/v1/dashboard/attention/{id}/acknowledge` — marks a check's current failure as acknowledged. Stores acknowledgement in `execution_results` metadata or a new `acknowledgements` column. Response: `{id, acknowledgedAt}`.
- [ ] **AC-11:** `POST /api/v1/dashboard/attention/{id}/assign` — body `{userId}`. Assigns a failing check to a user for investigation. Stores in check metadata or a dedicated column. Response: `{id, userId}`.

**Service layer**
- [ ] **AC-12:** `DashboardService` created with methods for each endpoint. Uses repository queries, not in-memory filtering.
- [ ] **AC-13:** Summary + attention endpoints are performance-critical (dashboard loads them on every visit). Ensure queries use indexes. Consider `@Cacheable` with 30-second TTL for summary.

**Tests**
- [ ] **AC-14:** Integration tests: `DashboardSummaryIT`, `DashboardAttentionIT`, `DashboardActivityIT`, `DashboardUpcomingIT`, `DashboardSearchIT`. Cover: empty state, filtered by CSI, authorization scoping.

## Implementation Notes

### Activity query (check events)
```sql
SELECT er.id, 
       CASE WHEN er.status IN ('FAILURE','TIMEOUT') THEN 'FAIL' ELSE 'RECOVER' END as type,
       CASE WHEN er.status IN ('FAILURE','TIMEOUT') THEN 'Check Failed' ELSE 'Recovered' END as title,
       c.name as description,
       cs.name as csi_name,
       er.started_at as timestamp
FROM execution_results er
JOIN checks c ON er.check_id = c.id
JOIN csi_systems cs ON c.csi_id = cs.id
WHERE er.started_at > NOW() - INTERVAL ':hours hours'
  AND (:csiId IS NULL OR c.csi_id = :csiId)
ORDER BY er.started_at DESC
LIMIT 20
```

### Search balanced results
Execute 3 queries in parallel (virtual threads), limit each, merge and sort by relevance:
```java
var csiFuture = executor.submit(() -> csiRepo.searchByName(query, 8));
var checkFuture = executor.submit(() -> checkRepo.searchByName(query, 8));
var reportFuture = executor.submit(() -> reportRepo.searchByName(query, 4));
```
