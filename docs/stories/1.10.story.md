## User Story

**As a** put-checks developer adding new executor types (TCP in 2.2, Splunk/Grafana/ITRS/AppD in 3.3-3.6, UI_TEST in 5.5),
**I want** a `CheckExecutor` SPI + dispatcher + the first `HttpCheckExecutor` implementation,
**so that** every future executor story plugs in at the SPI without touching dispatcher code, and the HTTP executor validates the SPI contract end-to-end against a real outbound request.

---

## Acceptance Criteria

- [ ] **AC-1:** `CheckExecutor` interface with `CheckType supportedType()` + `ExecutionOutcome execute(Check, ExecutionContext)`. `ExecutionContext` carries resolved secrets (empty for HTTP in M1), `traceId`, execution ID.
- [ ] **AC-2:** `ExecutionOutcome` is a sealed record hierarchy: `Success(duration, output)` | `Failure(duration, errorMessage, deepLinkUrl?)` | `Warning(duration, message)` | `Timeout(duration)`.
- [ ] **AC-3:** `CheckExecutorDispatcher` holds a `Map<CheckType, CheckExecutor>` auto-wired from all SPI implementations in the Spring context. Throws `UnsupportedCheckTypeException` if no executor registers for a Check's type. Startup check logs which types have executors (useful for diagnosing missing registrations).
- [ ] **AC-4:** `HttpCheckExecutor` implements the SPI for `CheckType.HTTP`. Uses Spring 6 `RestClient` (CON-STACK-11) with per-check timeout from `HttpConfiguration.timeoutMs`.
- [ ] **AC-5:** HTTP executor validates the expected status code — returns `Success` if actual matches expected (default 200), `Failure` otherwise. Captures response time as `duration`.
- [ ] **AC-6:** HTTP executor honors `HttpConfiguration.verifyTls`. When `false` (for dev/test of self-signed endpoints), uses a permissive TLS context — logs a `WARN` at execution time with the check ID so this is auditable. Document in config.
- [ ] **AC-7:** HTTP executor honors `HttpConfiguration.followRedirects`.
- [ ] **AC-8:** Resilience4j `@CircuitBreaker(name="http-executor")` on outbound calls, configurable per-check-type. Circuit trip → `Failure` outcome with clear error message (not a thrown exception bubbling out).
- [ ] **AC-9:** TLS cert errors, DNS errors, connect timeouts, read timeouts all map to distinct `Failure` errorMessages so operators can diagnose without reading stack traces.
- [ ] **AC-10:** Metrics (Micrometer): `checks_execution_duration_seconds{check_type="HTTP",status}` (histogram), `checks_execution_total{check_type="HTTP",status,csi_id}` (counter).
- [ ] **AC-11:** Sensitive request/response data not logged. Only: URL (possibly truncated), method, status code, duration, error class name. Response body NEVER logged (may contain secrets from the monitored system).
- [ ] **AC-12:** Integration tests via WireMock: `HttpExecutorSuccessIT`, `HttpExecutorFailIT` (wrong status), `HttpExecutorTimeoutIT`, `HttpExecutorCircuitBreakerIT`, `DispatcherMissingTypeIT`.
- [ ] **AC-13:** JaCoCo coverage for `checks.executors` package ≥ 80%.

## Implementation Notes

- **RestClient vs WebClient:** HTTP check executor is pure blocking I/O — use RestClient (sync). WebClient is needed only for streaming (§4.1).
- **TLS permissive mode:** guard behind `HttpConfiguration.verifyTls=false` only; never a global toggle. Log warning every execution to create an audit trail.
- **Dispatcher bootstrapping:** log the `Map<CheckType, CheckExecutor>` at ApplicationReadyEvent — makes it obvious in prod logs which executors are registered per pod (useful when 5.5 adds UI_TEST only to studio-image variants).

## @po Validation — 2026-04-17 · **10/10 GO**

Clean SPI design with executor isolation. `ExecutionOutcome` as a sealed hierarchy is the right shape — Success/Failure/Warning/Timeout covers every scenario executors will see, and the Java 21 pattern-match exhaustiveness check in the caller (story 1.11) will catch future gaps.

**Watch:** `http-executor` CircuitBreaker config should be per-CSI (not global) to prevent one flaky endpoint from tripping the breaker for unrelated CSIs. Consider at story gate; may push to 6.4 tuning.
