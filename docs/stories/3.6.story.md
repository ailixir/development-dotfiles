## User Story

**As a** user selecting CSIs from autocomplete, browsing by business unit, or viewing a CSI health summary,
**I want** these features backed by real backend endpoints instead of MSW mocks,
**so that** the data reflects the actual CSI inventory and real-time check health from the database.

---

## Acceptance Criteria

### Backend — New endpoints

- [ ] **AC-1:** `GET /api/v1/csi/search?q={query}&limit={N}` added to `CsiController`. Returns `List<CsiSearchResult>` `[{id, name}]`. Query filters by `name ILIKE %query%` OR `id LIKE %query%`. Minimum query length: 2 characters (return empty list if shorter). Max results: `limit` param (default 10, max 50). Authorization: authenticated users only (no CSI ownership check — search is discovery).
- [ ] **AC-2:** `GET /api/v1/csi/business-units` added to `CsiController`. Returns `List<String>` — distinct business unit names from `csi_systems` table, ordered alphabetically. Cached via Spring `@Cacheable("csi-business-units")` with 5-minute TTL (business units change rarely).
- [ ] **AC-3:** `GET /api/v1/csi/{id}/health` added to `CsiController`. Returns CSI health summary aggregated from checks: `{csiId, totalChecks, passingChecks, failingChecks, warningChecks, overallStatus, lastUpdated}`. Uses the `csi_metrics_current` materialized view (already in V1 migration). If no checks exist for the CSI, returns `{totalChecks: 0, overallStatus: "UNKNOWN"}`. Authorization: requires `canRead(auth, csiId)`.
- [ ] **AC-4:** `CsiSearchResult` record: `{id: String, name: String}`.
- [ ] **AC-5:** `CsiHealthSummary` record: `{csiId: String, totalChecks: int, passingChecks: int, failingChecks: int, warningChecks: int, overallStatus: String, lastUpdated: Instant}`.
- [ ] **AC-6:** `CsiService` extended with: `searchByQuery(String query, int limit)`, `getDistinctBusinessUnits()`, `getHealthSummary(String csiId)`.
- [ ] **AC-7:** Integration tests: `CsiSearchIT` (search by name, search by id, short query returns empty, limit respected), `CsiBusinessUnitsIT` (returns distinct sorted list), `CsiHealthIT` (aggregation correct, no-checks case, authz check).

### Frontend — Wire remaining CSI endpoints

- [ ] **AC-8:** `csiApi.searchCsis()` updated to call real `GET /api/v1/csi/search`. Response shape matches existing FE expectation `[{id, name}]` — no mapper needed.
- [ ] **AC-9:** `csiApi.getBusinessUnits()` updated to call real `GET /api/v1/csi/business-units`. Response is `string[]` — matches existing FE expectation.
- [ ] **AC-10:** `csiApi.getCsiHealth()` updated to call real `GET /api/v1/csi/{id}/health`. Response mapped via existing health type.
- [ ] **AC-11:** CSI domain fully disabled from MSW: uncomment `csi` in `VITE_DISABLE_MSW_DOMAINS` (or remove per-endpoint overrides from story 3.3).
- [ ] **AC-12:** `npm run type-check` passes. `./gradlew check` passes.
- [ ] **AC-13:** CSI autocomplete, business unit filter dropdown, and CSI health card verified in browser.

## Implementation Notes

### Materialized view for health
The `csi_metrics_current` materialized view was created in V1 migration. It aggregates check statuses per CSI. The health endpoint can query this view directly for O(1) reads, with periodic refresh via `REFRESH MATERIALIZED VIEW CONCURRENTLY`.

### Search query safety
Use parameterized query — never concatenate user input into SQL:
```sql
SELECT id, name FROM csi_systems
WHERE (LOWER(name) LIKE LOWER(CONCAT('%', :query, '%'))
   OR LOWER(id) LIKE LOWER(CONCAT('%', :query, '%')))
AND deleted_at IS NULL
ORDER BY name
LIMIT :limit
```
