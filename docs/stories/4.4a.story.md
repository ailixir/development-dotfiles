## User Story

**As a** report delivery dispatcher polling for due reports,
**I want** a materialized `next_delivery_at` column on the `reports` table with a B-tree index,
**so that** the dispatcher can efficiently find reports due for delivery using `WHERE next_delivery_at <= NOW()` without parsing JSONB schedule configurations on every poll tick.

---

## Context & Rationale

The Check scheduler uses `schedules.next_execution_at` (materialized `TIMESTAMPTZ`) for O(log n) indexed polling. Reports currently store scheduling intent in a `schedule` JSONB column but have no materialized timestamp. Without it, the report dispatcher would need to scan all active reports and parse their JSONB schedule to determine which are due — O(n) per poll.

## Implementation Notes

- **Index strategy:** Partial index matches the dispatcher query exactly — `status = 'active'` + `deleted_at IS NULL` + `next_delivery_at IS NOT NULL`. This keeps the index small (only active, non-deleted reports with a schedule).
- **Column nullability:** NULL means "no scheduled delivery" (draft/paused reports). The dispatcher query uses `IS NOT NULL` in the index predicate.
