## User Story

**As a** Studio author whose first compile came back with steps the validator refused,
**I want** the system to try a bounded number of repairs, tell me in plain terms what is still wrong, and then make me approve one exact revision — the one I actually looked at — before anything can run,
**so that** a stale browser tab can never approve code I never saw, an edit I made underneath my own review can never be confirmed by accident, and an API restart in the middle of a compile costs me a retry rather than my confirmed test.

---

## Problem Statement

10.8 ended one step short of the thing the epic exists to guarantee. The compile pipeline runs, the readiness gate is live and unconditional, and `CompileStateService.confirm` is written and tested at the service layer — but **no HTTP route calls it**. `POST /tests/{id}/confirm-compile` still carries `x-not-yet-implemented: true` and `x-implemented-by: '10.9'` in the frozen contract, so today a candidate reaches `AWAITING_CONFIRMATION` and stops there forever. Every confirmed revision in the codebase was seeded by a test fixture.

| Available today | From |
|---|---|
| `CompileStateService.confirm(testId, revisionId, artifactHash, sourceRevision, configurationRevision, principal)` — two conditional statements in one transaction, requiring `AWAITING_CONFIRMATION`, the revision still current, all four values matching, and `confirmed_by IS NULL` | 10.4 |
| `ui_test_revisions` immutable under a write-once trigger that permits `confirmed_by`/`confirmed_at` to move from `NULL` to a value **exactly once** and raises on any second write | 10.4, V12 |
| The bounded compile pipeline: one `propose` per attempt, the `SUPPORTED_ARTIFACT_VERSION` pin, one `/v1/validate` call with no retry, `publishCandidate` / `publishInvalid` / `publishError`, a fixed pool with no queue, a per-attempt budget, late-result drop | 10.8 |
| `DiagnosticsBounder` — index-aligned, one entry per original step, 10 per step, 400/120 characters, 64 KiB total, explicit truncation markers | 10.8 |
| The readiness gate, whose seven-term predicate **never reads `compile_status`**, and AC-23's proof that a confirmed unedited draft left `STALE`, `COMPILING` or `NEEDS_REVISION` by a failed *optional* recompile stays runnable | 10.8 |
| `409` conflict semantics for a withheld draft: `TEST_DELETED` and `TEST_QUARANTINED`, kept separate, declared on `confirmCompile` with an exhaustive `x-conflict-codes` list | ADR-002 §14 |

Missing: the route, the repair loop the architecture bounds at two attempts, and the restart recovery §4.7 requires.

### The three things this story settles

**1. Exact confirmation has to be decidable by a test, not described.** The epic's premise is that a user approves *an exact revision* and that artifact replays without a model in the loop. That premise is only as good as the statement that enforces it. `confirm` already conditions on all four fields intrinsically — one `UPDATE ... WHERE` whose affected-row count is asserted, never a read-then-write — so the work here is to expose it over HTTP without loosening it, and to prove each of the four terms is load-bearing by deleting it and watching a test go red. Five guards in this epic have turned out to be green with the behaviour they guarded removed; four more terms are not going to be taken on trust.

**2. Repair is a bound, not a feature.** §4.3 gives "a maximum of two repair attempts" and §4.7 gives "Exhausted repair yields `NEEDS_REVISION`". That is the whole of the source. It means at most three `propose` calls and three `/v1/validate` calls per compile request, and it means 10.8's per-attempt budget — sized for one of each — no longer covers the worst case. The budget is raised and a startup validation makes the arithmetic explicit, in the same shape `StudioCompileConfig` already validates 10.8's bounds against each other.

**3. The carried-forward column, and why it is cheap.** 10.8's Implementation Notes recorded three options for §4.7's *"Recovery of an abandoned compile request marks it retryable without replacing the confirmed history"* across an API restart, and @po chose option 3 for V1 while naming this story as the owner of option 1: a `compile_started_at` column plus a bounded sweep. The reason it is cheap is a consequence of 10.8's central decision rather than a hope — **because readiness never reads `compile_status`, a row stranded in `COMPILING` blocks nothing that matters**; the confirmed revision still executes and `POST /execute` is still accepted. So the sweep buys a truthful authoring display, not a recovered capability, and it must be built in a way that cannot cost more than that. Nothing here may contradict 10.8 AC-23.

### What must not be contradicted

10.4's guards, as 10.8 consumed them: all three publish transitions condition on `configuration_revision` **intrinsically**, carried on `CompileRequest` and never reconstructed; `confirm` requires `compile_status = 'AWAITING_CONFIRMATION'` as an explicit precondition; `publishError` clears `current_candidate_revision_id`. 10.8's AC-3 — every compile-state column written only through `CompileStateService`, asserted by a scan of the package's SQL and JPA surface — applies to the sweep too, which is why the sweep's statement lives in that class and not in a scheduler.

## Acceptance Criteria

### The confirmation route, exactly as frozen

- [x] **AC-1:** `POST /api/v1/studio/tests/{id}/confirm-compile` is implemented exactly as the frozen contract declares it (`docs/specs/studio/openapi.yaml`, `operationId: confirmCompile`): a required `ConfirmCompileRequest` body of exactly `{revisionId, artifactHash, sourceRevision, configurationRevision}`, `200` with `TestDto`, `400`, `401`, `403`, and `409` whose code set is exactly the declared `x-conflict-codes: [STALE_CANDIDATE, TEST_DELETED, TEST_QUARANTINED]`. **No response code and no conflict code the frozen operation does not declare is added.** A contract test asserts the `200` body against the `TestDto` schema and asserts, on the wire, that the set of `409` codes the route can produce **equals** the operation's `x-conflict-codes` read from the document — the mechanism ADR-002 §14.6 introduced precisely so this claim is assertable rather than decorative.
- [x] **AC-2:** **The `x-not-yet-implemented` marker is removed for `confirmCompile` and for nothing else**, and `StudioContractTest` is updated to say so. Its `theCompileRouteIsShippedAndTheMarkerCameOffForThatOperationOnly` currently asserts `pendingOperations()` contains exactly `POST /tests/{id}/confirm-compile` and `GET /executions/{id}/video`; that assertion is now false by design and **this story updates it** to `GET /executions/{id}/video` alone, adding the mirror test for this route (implemented **and** no longer flagged pending). The video route's marker must not move — a story that quietly cleared a neighbour's marker would present an unimplemented route as shipped, which is the whole reason that test exists. This is Class A housekeeping under ADR-002 §12, the precedent §14.8 item 5 set for `compileTest`; **`x-implemented-by: '10.9'` stays**, one line is added to the ADR-002 §13 amendment log, and **no other edit is made to `openapi.yaml`**.
- [x] **AC-3:** **The order of refusal is part of the contract, and the lifecycle `409` never precedes authorization** (ADR-002 §14.4): an identity that may not act on the draft's CSI learns nothing from a status code about whether the draft exists. Asserted with four callers against one seeded draft — no identity (`401`), a wrong-CSI identity (`403`), an authorized owner on a soft-deleted draft (`409 TEST_DELETED`) and on a quarantined draft (`409 TEST_QUARANTINED`). The one documented exception is stated rather than left to be rediscovered: **bean-validation `400` may precede authorization**, because a malformed body is a property of the request and not of the resource — it answers identically for an id that never existed, so it discloses nothing. A test sends a malformed body as an unauthorized caller and asserts `400`, and the same body as an authorized one and asserts `400`. §9.1's owner-level permission applies: a reader of the CSI is `403`.
- [x] **AC-4:** `400` for anything that is not exactly the declared body: a missing field, a `revisionId` that is not a UUID, an `artifactHash` that is not exactly 64 characters, a non-integer revision. **No compile-state column is written and no `ui_test_revisions` row is touched on any of them.** `ConfirmCompileRequest` is not a closed schema — closure under ADR-002 §6.2 is for runner-*produced* bodies — so an undeclared extra key is **ignored**, not rejected; a test asserts it changes no behaviour and no stored value, and the story invents no `400` code for it.

### Exact confirmation — all four fields, or nothing

- [x] **AC-5:** **The confirmation matches the revision on all four fields intrinsically**, in the conditional statement itself, never by reading the revision and then comparing in Java. Four tests perturb exactly one field each — a different `revisionId`, a different `artifactHash`, a `sourceRevision` off by one, a `configurationRevision` off by one — and each asserts `409 STALE_CANDIDATE`, **no** `confirmed_by`/`confirmed_at` write on any revision row, no change to `confirmed_revision_id`, and no change to `compile_status`. **Proof by mutation is required:** with any one of the four terms deleted from the `WHERE` clause, the corresponding test must go red. Recorded in the Dev Agent Record; a guard nobody has falsified is a guard nobody has tested.
- [x] **AC-6:** **A stale tab cannot approve a newer artifact, even when the source text is unchanged** (Epic 10 §10.9 acceptance bullet 2). A draft compiles to candidate `R1`; an explicit recompile of byte-identical source issues a second `propose` call (10.8 AC-20 guarantees the call happens — there is no cache) and lands one of two ways, and **both are asserted, so the second is not later read as a hole**:
  - **(a) the second artifact differs** — `insertOrReuseRevision` writes a new row `R2`, `R2` becomes `current_candidate_revision_id`, and confirming `R1` from the stale tab is `409 STALE_CANDIDATE` with no write. This is the case the epic bullet names.
  - **(b) the second artifact is byte-identical** — `insertOrReuseRevision` resolves `(test_id, source_revision, configuration_revision, artifact_hash)` to the same row `R1`, so confirming `R1` **succeeds**. Nothing unseen is approved: the bytes confirmed are the bytes the tab displayed, and the four-field body still matches exactly. Named here so a reviewer reading "a stale tab cannot approve" does not read this success as a bypass.
- [x] **AC-7:** **Changed configuration or source underneath the tab returns `409` without approving unseen code** (Epic 10 §10.9 acceptance bullet 3). Three cases, each its own test, each `409 STALE_CANDIDATE` with a message naming *what moved*, and each asserting no write on any revision row:
  - the source was edited after the candidate was produced (`sourceRevision` advanced);
  - execution-affecting configuration was edited (`configurationRevision` advanced — the §4.2 list: environment, variable values/references, viewport, timeout, browser, wait strategy). Each of those seven is driven by its own perturbation and each must advance `configurationRevision`. **Target policy selection is ruled NOT REACHABLE in this story and is recorded as such — never as passing** (@po, 2026-09-11; see Rulings). `ConfigurationChangeClassifier`'s own javadoc states the reason and it is verified on the branch: *"no such field exists on the test contract yet; it is introduced with the destination policy work"* — there is no field on `UITestRequest` or `TestConfiguration` to perturb, so no test can drive the case, and adding one would be Article IV invention. A **named disabled test** states the missing field, names **story 10.18 (`ED-04`, ADR-002 O-6, SPK-05)** as the owner that introduces destination policy, and asserts the classifier still carries the javadoc that records the gap — so the gap cannot be closed silently or forgotten quietly;
  - a recompile is in flight (`compile_status = 'COMPILING'`), refused by `confirm`'s explicit `AWAITING_CONFIRMATION` precondition rather than by anything this story adds.

  And the negative case that must keep working: **a name- or description-only edit is none of these** (§4.2), and confirmation still succeeds after one.
- [x] **AC-8:** **Confirmation is write-once**, and the application guard fires before the database guard:
  - **(a) Re-confirming the same revision** with a body that is still exact is `409 STALE_CANDIDATE`. The `confirmed_by IS NULL AND confirmed_at IS NULL` term matches zero rows, so the request **never reaches V12's write-once trigger** — a test asserts the outcome is a `409` and *not* a `500` from a raised exception, and asserts the original `confirmed_by` and `confirmed_at` are byte-unchanged. Removing that term must turn this test red (the second required falsification).
  - **(b) Confirming a second, different revision** after an edit and a successful recompile **succeeds**: `confirmed_revision_id` moves to the new revision, and the first revision's `confirmed_by`/`confirmed_at` are untouched — §4.6's *"Model changes never rewrite existing revisions"* applied to confirmation identity. History gains a row; it never loses one.
  - **(c) Confirming a previously confirmed *older* revision** while a newer candidate awaits is `409 STALE_CANDIDATE`, because the older revision is no longer `current_candidate_revision_id`. This extends 10.8 AC-14 from the service layer to the wire.
- [x] **AC-9:** **A valid candidate confirms to `READY`; mixed invalid steps block confirmation** (Epic 10 §10.9 acceptance bullet 1). Two halves, one test each. A valid candidate confirmed by its authorized owner sets `compile_status = 'READY'`, `confirmed_revision_id`, and `confirmed_by` to **the authenticated principal** with `confirmed_at`, clears `compile_error` and `compile_diagnostics`, and returns the committed state in the `200` body. A validator verdict in which some steps are `ok` and some are not is `ok: false` as a whole, routes to `publishInvalid` → `NEEDS_REVISION` with no revision row written and the candidate cleared, and every subsequent confirmation attempt — including one carrying a revision id from before the recompile — is `409 STALE_CANDIDATE`.

### Repair — at most two attempts

- [x] **AC-10a:** **The repair loop, against the stub gateway.** On an `ok: false` verdict the pipeline issues a repair attempt carrying the bounded, redacted diagnostics of the attempt that just failed. **At most two repair attempts** (§4.3), therefore **at most three `propose` calls and three `/v1/validate` calls per compile request**, with `attempt` on the gateway `CompileRequest` taking the values 1, 2, 3 and never repeating. A counting stub asserts the exact call counts for each of four shapes: valid first time (1 propose / 1 validate, `AWAITING_CONFIRMATION`); valid after the first repair (2/2, `AWAITING_CONFIRMATION`); valid after the second (3/3, `AWAITING_CONFIRMATION`); never valid (3/3, `NEEDS_REVISION`). Fixtures come from the 28-example reference corpus and the 70-case adversarial corpus so the verdicts are ones the validator is already proven to produce.
- [ ] **AC-10b:** *(Deferred — `ED-01`)* The same loop against the **real R2D2 gateway** with `studio.compile.gateway.enabled=true`. `ED-01` is `status: open` — no endpoint, credentials, project or verified model identifiers exist — and its `gate_note` allows fixture-only compile work while blocking any real compile path. Verified in **story 10.19** (integrated staging validation), which `ED-01` also gates. Recorded as **skipped, not passed**; no shared environment sets `enabled=true` in this story.
- [x] **AC-11:** **Exhausted repair yields `NEEDS_REVISION` with readable, bounded reasons** (§4.7). Publication is through `publishInvalid` and carries the **final** attempt's per-step diagnostics, index-aligned, one entry per original step, plus the attempt count and an explicit exhausted marker under **exactly the two keys the contract now fixes: `attempts` (integer, >= 1) and `exhausted` (boolean)** (ADR-002 §16.2, §16.9 item 2 — the spellings are no longer this story's to choose, and 10.10 reads them). Earlier attempts' diagnostics are **not accumulated** — a test asserts the stored document describes one attempt, not three — and the whole document stays inside the caps 10.8 already owns (10 per step, 400/120 characters, 64 KiB total, aligned to the runner's `DEFAULT_BOUNDS`), with the truncation marker set when it does not fit. A test feeds three successive hostile verdicts of thousands of oversized diagnostics and asserts one bounded document within the cap.
- [x] **AC-12:** **A repaired draft goes back through the same gate, never around it.** Every repair attempt's artifact passes the `SUPPORTED_ARTIFACT_VERSION` pin **and** `/v1/validate` before any publication — a schema-valid `version: 2` artifact returned by a repair is rejected exactly as 10.8 AC-10 rejects it on the first attempt, is never written as a revision and is never sent to the validator. A successful repair becomes `AWAITING_CONFIRMATION` through `publishCandidate` and **never `READY`**; a repaired draft is refused `409 COMPILE_REQUIRED` by the readiness gate until this story's route is called. A structural test asserts **no call path from the repair loop to `CompileStateService.confirm`**, failing on the reference rather than on the call.
- [x] **AC-13:** **Repair stays inside the bounds, and every bounded refusal is still `publishError` → `STALE`, retryable.** 10.8's per-attempt wall-clock budget now covers the **whole compile request including repairs**; its starting value is raised accordingly and a **startup validation asserts `budget > (1 + maxRepairAttempts) × (gatewayRequestTimeout + validateTimeout)`** — the shape `StudioCompileConfig` already uses to validate 10.8's bounds against each other — so a healthy loop is never abandoned mid-repair by arithmetic nobody checked. Budget expiry during the loop abandons the attempt with `COMPILE_BUDGET_EXCEEDED`; a `GATEWAY_BUSY`, timeout or transport failure on a **repair** call ends the loop with that code and does not silently consume a further attempt; a late gateway or validator result from an abandoned repair is dropped in-process without calling any publish method. The bounds table under Implementation Notes is normative, and each row is driven past its bound by a test.
- [x] **AC-14:** **The repair prompt reads no resolved value and echoes no secret.** It carries the fenced source, the pinned syntax reference and `promptVersion`, the output contract and the bounded diagnostics — and nothing else; secret and variable references stay opaque as `<secret ID>` and `<var NAME>`. 10.8 AC-5's canary test is extended over all three attempts: a canary planted in a stored secret value appears in no repair payload, no stored diagnostics document and no audit line, in plain, URL-encoded, double-encoded or base64 form, and the secrets service and vault client are never called on the compile path. Gateway audit records `attempt` alongside the metadata §4.7 already lists (test, CSI, user, model/prompt versions, latency, outcome) and never a request body; the assertion is on the **bytes handed to the log sink and the HTTP client**, not on the objects that produced them.
- [x] **AC-15a:** **Syntax validity is not asserted as semantic correctness** (Epic 10 §10.9 scope bullet 3; §4.1 and §4.5 both say so in their own words). No message, field, response description, javadoc or README line on the compile, repair or confirmation surface states or implies that a validated — or repaired — artifact does what the author meant. A test asserts no such claim exists in the module's user-facing strings, in the same shape as 10.8 AC-7's honesty assertion about credential patterns. Repair changes nothing about this: an artifact that took three attempts is neither more nor less trustworthy than one that took one, and the user reviews and confirms it identically.
- [ ] **AC-15b:** *(Deferred — `ED-01`)* Measuring translation quality — §4.1's *"Representative internal workflows and observed runs/video are required to measure translation quality"* — needs a real model and observed runs. Verified in **story 10.19**. Recorded as **skipped, not passed**.

### Restart recovery — the carried-forward column and its sweep

- [x] **AC-16:** **One forward-only migration, version left unassigned in this draft** (assigned at implementation; the latest on this branch is `V15`). It adds `ui_tests.compile_started_at TIMESTAMPTZ NULL` and a **partial** index over it restricted to `compile_status = 'COMPILING'`, following V12's own partial-index style, so the sweep's selection stays cheap on a table where almost no row is compiling. `beginCompile` sets the column in the **same single statement** that already sets `compile_request_id` and `'COMPILING'` — not a companion write — and every terminal transition (`publishCandidate`, `publishInvalid`, `publishError`, the sweep) clears it. The invariant **`compile_started_at IS NOT NULL` ⟺ `compile_status = 'COMPILING'`** holds after each of those paths, asserted once per path.
- [x] **AC-17:** **The migration is proven against a database holding existing rows.** It is applied on Testcontainers PostgreSQL to a database seeded beforehand with rows in all five compile states, a soft-deleted row, a quarantined row, and a legacy row stranded in `COMPILING` from before the column existed. The stranded row is **backfilled to the migration's own clock**, so it ages from deployment rather than from a timestamp nobody recorded — `updated_at` is bumped by any edit and says nothing about when a compile began, which is exactly why this column exists. No other row receives a non-null value; no row's `confirmed_revision_id` or `current_candidate_revision_id` changes; no `ui_test_revisions` row is touched. A wave-1 migration in this repository passed CI and would have aborted on a database with rows in it; this one is run against one.
- [x] **AC-18:** **The sweep marks an abandoned compile retryable without replacing the confirmed history** (§4.7). A bounded, scheduled sweep moves rows whose `compile_status = 'COMPILING'` and whose `compile_started_at` is older than a configured threshold to **exactly the outcome `publishError` produces** — `STALE`, a retryable `compile_error` carrying a bounded code and nothing else, `current_candidate_revision_id` cleared — and additionally clears `compile_request_id` and `compile_started_at`. It writes **no** `ui_test_revisions` row and changes **no** `confirmed_revision_id`. The batch size is bounded, and the threshold is validated at startup to exceed the AC-13 budget, so a healthy in-flight compile can never be swept out from under itself.
- [x] **AC-19:** **The sweep's guard is intrinsic to its own statement, and it needs no new condition anywhere else.** A single conditional `UPDATE` re-states `compile_status = 'COMPILING'` and the age predicate in its own `WHERE`, over a `SELECT ... FOR UPDATE SKIP LOCKED` selection so concurrent API replicas do not contend, and its SQL lives in `CompileStateService` — so **10.8 AC-3's scan test, which fails on any statement touching the compile-state columns outside that class, still passes unchanged**. Two interleaving tests, each holding a transaction open rather than calling sequentially:
  - **(a)** the sweep runs while a `publishCandidate` for the same request is mid-transaction — exactly one wins, the loser is a no-op, and no row is left half-settled;
  - **(b)** a late `publishCandidate` arriving **after** the sweep is discarded as `DISCARDED_OUT_OF_ORDER` **because the sweep cleared the request identity the publish already conditions on** — no publish guard is modified, widened or given a new term by this story.

  **Proof by mutation is required, and the drafted mutation is corrected because it could not have failed** (@po, 2026-09-11). Deleting the status term from the sweep's outer `WHERE` would *not* turn case (a) red: AC-16's invariant — `compile_started_at IS NOT NULL` ⟺ `compile_status = 'COMPILING'` — makes the status term provably redundant against the age predicate, since every terminal transition clears the column and a `NULL` never satisfies an age comparison. A mutation that cannot fail is the exact failure mode AC-5 exists to prevent, and it is not accepted here either. The status term **stays** — it is the statement's own honest guard and it survives anyone later relaxing the clear — but the two falsifications recorded for the sweep are the ones that bite:
  - **removing the age predicate** from the sweep's `WHERE` must turn AC-18's *"a healthy in-flight compile can never be swept out from under itself"* test red (the third required falsification);
  - **removing `compile_request_id = NULL` from the sweep's `SET`** must turn case **(b)** red — the late `publishCandidate` finds its request identity intact and resurrects a swept row (the fourth required falsification). This is the one that proves the guard-reuse argument under Implementation Notes is load-bearing rather than merely elegant.
- [x] **AC-20:** **The sweep changes nothing about readiness** — 10.8 AC-23's property, restated at the one place it could now regress. A confirmed, unedited draft stranded in `COMPILING` and then swept to `STALE` passes the readiness gate and has its `POST /execute` accepted **both before and after the sweep runs**, on the revision originally confirmed. 10.8's three de-ready tests are re-run in this story's build and must stay green. If a change here would require weakening any of them, the change is wrong.

### No bypass, and the reason a user cannot yet read the reasons

- [x] **AC-21:** **No production auto-confirmation and no temporary gate bypass exist** (Epic 10 release ordering: *"No temporary gate bypass or production auto-confirmation is allowed"*; §10.8 acceptance bullet 3: *"no production auto-confirm fallback exists"*). No property, profile, feature flag, bean or scheduled job confirms a candidate without an authenticated principal's explicit call to this route; `confirmed_by` is always that principal and never a service identity, a constant, a placeholder or null. One test enumerates the configuration surface and asserts no key can auto-confirm or skip the route; a second asserts that every seeding helper capable of producing a confirmed revision is test-scoped and drives the **real** transition — which 10.8's `ReadinessFixtures` already does, and which this story must not regress by adding a faster path. Together with 10.8 AC-26, which covered the readiness half, this closes the release-ordering sentence on both halves.
- [x] **AC-22:** *(Escalation **CLOSED** by @architect — ADR-002 §16, ruled 2026-09-11, before wave 4 closed. AC-22's own first branch applies: **the exposure lands in this story's PR.** Rewritten by @po on 2026-09-11 to state the work rather than the escalation; the criterion's subject — the readable reasons this story persists are reachable by the frontend that depends on them — is unchanged.)* **A failed compile leaves a document a caller can read, with its truncation flags intact.** `openapi.yaml` already carries the amendment, so **this story implements against the amended document and makes no further edit to it** beyond AC-2's marker removal. Six obligations, each asserted (ADR-002 §16.9):
  - **(a)** `UITestDto` gains `compileError` and `compileDiagnostics`, deserialized from the two `jsonb` columns into the declared `CompileError` / `CompileDiagnostic` / `CompileStepDiagnostics` / `CompileDiagnostics` shapes. **Additive only:** every existing field keeps its name, its type and its position, and no other response body moves. A test asserts the mutual exclusion the schema declares — at most one of the two is ever non-null, which is what the merged `CompileStateService` already guarantees on all five statements.
  - **(b)** The document `DiagnosticsBounder` builds emits `attempts` and `exhausted` under exactly those names (AC-11).
  - **(c)** `compileDiagnostics` is **null on the `GET /tests` list projection** and `compileError` is not. One test proves both halves against one draft holding a stored document: present on `GET /tests/{id}`, absent from `GET /tests`. A test that only asserted the presence would not have caught the divergence this criterion exists to declare.
  - **(d)** `TestDto` is added to `StudioContractTest.theFrozenSchemasAndTheJavaTypesShareTheSameFieldNames`. Its absence is why two persisted facts went undeclared for four waves (§16.1's last row); it costs one line and it is the only thing that stops the gap reopening.
  - **(e)** `DiagnosticsExposureEscalationTest` stops being a named disabled test and becomes a **live round trip**: a compile that fails leaves a document a caller reads back through the route, with the truncation markers present at **all three levels** — the marker on a clamped `message`/`excerpt`, `truncated` per step, and `truncated` plus `truncationReason` on the document. A test asserts a bounded document that shed steps carries the document-level flag, because a truncated report rendered as a complete one is worse than no report.

Configuration lives under the existing `studio.compile.*` block in `application.yml`, so §8.5's "one configuration source" stays true.

### What raising the budget actually costs

The pool is four threads with no queue, and a worst-case request now occupies a thread for 240 s instead of 180 s. That does not change the refusal behaviour — 10.8 AC-17 already routes pool saturation to `publishError` → `STALE` with `COMPILE_POOL_SATURATED`, retryable — but it does mean the observable saturation rate rises for the same load. It is stated here rather than discovered in staging. If tuning is needed, the pool size is the knob, not the repair count: the repair count is fixed by §4.3 at two and is not a tuning parameter.

### Why the sweep needs no new condition on any publish guard

The publish transitions condition on `compile_request_id` intrinsically. They do **not** condition on `compile_status` — deliberately, because 10.4 made `beginCompile` unconditional on status and 10.8 built AC-23 on that. So a naive sweep that moved `COMPILING → STALE` while leaving the request identity intact would let a late result from the swept compile resurrect it, and the temptation would be to add a status term to all three publish guards. That would be a guard change in service of a sweep, touching code three other criteria depend on.

The sweep instead **clears `compile_request_id`**, which is what "this compile request is abandoned" means. The existing intrinsic guard then does the work unchanged: the late publish finds no matching request and returns `DISCARDED_OUT_OF_ORDER`. AC-19(b) asserts exactly this, and AC-19 states as a scope constraint that no publish guard is modified. The sweep matching `publishError`'s outcome — `STALE`, retryable error, candidate cleared — is deliberate too: an abandoned compile and a failed compile leave the draft in the same place, so the authoring UI has one state to render and not two.

### Why the sweep is worth so little, and why that is the point

@po chose option 3 for V1 on 10.8 and named this story the owner of option 1. The reason the column is cheap is worth restating where it is being built: **because readiness never reads `compile_status`, a row stranded in `COMPILING` blocks nothing that matters.** The confirmed revision still executes; `POST /execute` is still accepted. The sweep buys a truthful authoring display and a `compile_error` the user can see, not a recovered capability. AC-20 exists to keep it that way — if implementing the sweep ever required weakening one of 10.8's de-ready tests, the implementation is wrong, not the test.

### Why no new conflict code is invented for the exactness failures

Every exactness mismatch — wrong revision, wrong hash, moved source, moved configuration, recompile in flight, already confirmed — answers `409 STALE_CANDIDATE`. The codes are not multiplied, for three reasons. The sources ask for one: §4.2 says *"A stale tab gets 409"*, and the epic says *"Changed configuration/source or concurrent recompile returns 409 without approving unseen code"* — neither distinguishes. ADR-002 §14.3's axis for distinguishing codes is **who can clear the condition**, and all six of these are cleared identically by the caller: reload, recompile, reconfirm. And §14.7, while it lets the story that writes a `409`'s producer populate `x-conflict-codes`, keeps *adding a code the PR does not produce* and *choosing the status* firmly Class C.

What distinguishes the cases is the **message**, which names what moved, and AC-7 asserts that per case. If @po or 10.10 finds that the frontend cannot drive its refresh-on-`409` flow from one code plus a message, that is a legitimate Class C escalation to raise then — with the frontend requirement as its evidence — and not a code to invent now.

### Seams to watch

- **`StudioController` and `StudioService` are hot files.** `FOC-03` serialized 10.7 and 10.8 on them in wave 3; both have merged, so there is no wave-4 conflict recorded against them. Rebase on the merged epic branch before touching either, and keep this story's addition to what it is: one controller method and one service method that authorize, then delegate to `CompileStateService.confirm`. The confirmation transaction belongs in the state service, where every other compile-state write already lives (10.8 AC-3).
- **`CompilePipeline.runAttempt` currently hardcodes `attempt` to `1`** and comments that repairs are this story's. Threading the real attempt number is the smallest correct change; resist restructuring the method, because its settlement checks between the gateway and the validator are what AC-13's late-result drop rests on, and they must now run between *every* pair of calls in the loop.
- **`DiagnosticsBounder` is reused, not extended into a second bounder.** The attempt count and exhausted marker are additional keys on the document it already produces; the caps and the truncation behaviour are unchanged. A second bounding path is how the 64 KiB cap stops being true.
- **The sweep's scheduler and the sweep's statement are different things.** The statement lives in `CompileStateService` so 10.8 AC-3's scan stays green; the scheduler is a thin bounded caller elsewhere. Putting SQL in the scheduler would turn that scan red, and the correct response would be to move the SQL, not to relax the scan.
- **Migration version.** Left unassigned in this draft, as it has been all epic. The latest on this branch is `V15`; the version is assigned at implementation, against whatever has landed by then.

### AC-13 — where the 210 seconds comes from

The criterion names the threshold without saying what feeds it. Derived from the architecture and
from the configuration that already exists, not chosen:

```
worst case for one compile request
  = (1 + studio.compile.repair.max-attempts) × (gateway.request-timeout + runner.validate-timeout)
  = (1 + 2)                                  × (60s                     + 10s)
  = 210s
```

- **`repair.max-attempts = 2`** is architecture §4.3 — "a maximum of two repair attempts" — and the
  `1 +` is the first proposal, which is not a repair. It is a bound, not a tuning parameter.
- **`gateway.request-timeout = 60s`** is 10.5's `StudioGatewayProperties` default and the value
  `application.yml` ships (`STUDIO_GATEWAY_REQUEST_TIMEOUT:60s`). It is the per-call deadline
  *excluding* transport retries, which is the right term here because a retry that outlives the
  deadline is already the gateway's own bound firing.
- **`runner.validate-timeout = 10s`** is 10.8's `StudioRunnerProperties` default and the shipped
  value. Exactly one validator call per attempt, no retry.

The budget is raised 180s → **240s**, clearing 210s by 30s.

**The test drives the real clock boundary rather than a constant I also wrote.**

and the deployed configuration fails too.

### AC-10a — what the call-count test does and does not establish

Stated plainly, because @po named this as a weak criterion. `RepairLoopTest` counts calls into
`ScriptedRepairGateway`, a stub this story wrote and controls.

**It establishes** properties of *the pipeline*: that it issues at most `1 + repair.max-attempts`
proposals; that it numbers them 1, 2, 3 and never repeats; that a repair carries the previous
attempt's bounded diagnostics and the first attempt carries none; that only an `ok: false` verdict
spends an attempt while a gateway or validator failure ends the loop; and that the draft settles in
the state the last verdict implies. The `/v1/validate` half of every count is measured **on the
wire** through WireMock, so that number is not a stub's self-report, and the validator script is a
WireMock *scenario* — a fourth call would receive no stubbed answer rather than silently reusing the
third.

**It establishes nothing about a real model.** Not that a repair prompt ever produces a better
artifact; not that R2D2 accepts this request shape or these bytes; not that three attempts converge
more often than one; not that translation quality is measurable. Those are **AC-10b** and
**AC-15b**, both gated on `ED-01` (`status: open` — no endpoint, credentials, project or verified
model identifiers exist), owned by story **10.19**, and recorded here as **skipped, not passed**. No
shared environment sets `studio.compile.gateway.enabled=true` in this story.

### Guards whose falsification is weaker than it looks, stated rather than hidden

- **`exhausted` is structurally always `true` on a document this pipeline writes.** Exhaustion is
  the only route to `publishInvalid`: a gateway or validator failure on any attempt goes to
  `publishError`, and a valid verdict goes to `publishCandidate`. So the pipeline-level assertion
  `exhausted == true` could not have failed for the honest reason. It is computed rather than
  hardcoded (`attempt >= maxAttempts`) so it stays honest if a non-exhaustion path is ever added,
  and it is falsified at the seam that *can* discriminate:
  `RepairExhaustionTest.theAttemptCountIsAMeasurementAndNotAConstant` drives `DiagnosticsBounder`
  directly with `(1,false)`, `(2,false)` and `(3,true)` and asserts all three round-trip. Mutation
  #10 covers the key names.
- **`ConfirmCompileRouteTest.anIdentitylessCallerIsUnauthorized` is `@Disabled` and is recorded as
  NOT REACHABLE, never as passing.** `ED-02`'s unconditional bypass hands an identity-less caller a
  `checks-admin`/`platform-admin` identity, so no route on this branch can answer `401`. Its live
  sibling `theUnauthenticatedCaseIsNotReachableWhileTheCoreServiceBypassIsOn` asserts the current
  behaviour and **goes red the day the bypass is removed**, which is the signal to enable the
  disabled one. Fixing `ED-02` was explicitly out of scope.
- **`TargetPolicyGapTest.achangedTargetPolicyAdvancesTheConfigurationRevision` is `@Disabled` and is
  recorded as NOT REACHABLE, never as passing.** Owner: story 10.18 / `ED-04` / ADR-002 O-6 /

### Three defects the work found

- **The sweep's batch size was not a bound.** The statement was first written as `UPDATE … WHERE id
  IN (SELECT … ORDER BY … LIMIT ? FOR UPDATE SKIP LOCKED)`. Driving it past its bound —
  `theSweepStopsAtItsBatchSizeAndTheNextRunContinues`, five sweepable rows and a batch size of two —
  it updated **five**. Measured, not reasoned: a probe confirmed the subquery selected 2 and the
  `UPDATE` touched 5, because the planner may re-evaluate an uncorrelated `IN` subquery per outer
  row, which makes the `LIMIT` bound each evaluation rather than the statement. Rewritten as a CTE,
  which is evaluated once. This is the whole reason AC-13's "each row is driven past its bound by a
  test" is not decoration.
- **The new startup arithmetic invalidated an existing test context.** `CompileBudgetExpiryTest`
  lowered `gateway.request-timeout` and `attempt-budget` but not `runner.validate-timeout`, which
  the new rule now includes; its context refused to start. Fixed by lowering the third value with
  the other two, with the reason in the source. That is the rule biting where it should.
- **A fixture defect that only the integrated suite could show.** Every repair test passed in
  isolation and twelve of them failed together. `AbstractRepairPipelineTest` declared
  `@AfterAll stopRunner()`, which JUnit inherits and runs once per **subclass**: `RepairBoundsTest`
  finished first, stopped the WireMock server the other two classes were still bound to, and they
  failed with the validator unreachable — a fixture defect wearing the costume of a product bug.
  The shared server is now stopped by a JVM shutdown hook instead, and the reason is recorded in the
  static initializer so the `@AfterAll` is not helpfully reinstated later. **This is why the class
  was run in the full suite and not only on its own.**

### One 10.8 assertion superseded, and why that is not a relaxation

`CompilePipelineTest.aRejectedArtifactBecomesNeedsRevisionWithIndexAlignedDiagnosticsAndNoError`
verified exactly **one** `/v1/validate` call. Its stub rejects every artifact, so with repair the
compile now makes three — the bound `RepairLoopTest` owns. The number is changed to 3 **with the

### Autonomous decisions taken during implementation

- **[AUTO-DECISION]** *Which `compile_error` code does the sweep write?* → **`COMPILE_BUDGET_EXCEEDED`**
  (reason: ADR-002 §16.4 says a twelfth code signals a bound that was not in §4.3, and no twelfth is
  needed here. The sweep threshold is validated at startup to exceed the per-request budget, so by
  the time a row is old enough to sweep its budget has certainly elapsed — the sweep is the durable
  form of a deadline the process was holding in memory when it died, and the code is literally true).
- **[AUTO-DECISION]** *Which profile runs the sweep schedule?* → **All of them, guarded by
  `studio.compile.sweep.enabled` (default true)** (reason: unlike the execution reapers this is not
  worker-only work — AC-19 states the replicas-do-not-contend property, which is what `FOR UPDATE
  SKIP LOCKED` buys, and a sweep that ran on no API pod would leave the authoring display it exists
  to correct uncorrected in an API-only deployment. The two tests that need determinism set the
  property to `false` rather than racing the schedule).
- **[AUTO-DECISION]** *One sweep-interval configuration key or two representations?* → **One**,
  `studio.compile.sweep.interval-ms`, read by both the `@Scheduled` annotation and the properties
  record, which exposes a derived `interval()` (reason: §8.5 asks for one configuration source; the
  SSE block's `read-interval` / `read-interval-ms` pair is the precedent I chose not to repeat).
- **[AUTO-DECISION]** *How does the repair prompt carry the diagnostics?* → **A nullable
  `repairDiagnostics` field on the gateway `CompileRequest`**, with a 10-argument constructor so
  every first-attempt call site is unchanged (reason: AC-14 says the repair carries the bounded
  diagnostics "and nothing else", and a named field is the only shape in which that claim is
  assertable — `GatewayErrorScrubber` also had to learn to redact it, since a gateway that echoes
  the request back can echo those too).
- **[AUTO-DECISION]** *What does the repair prompt receive — the raw `ValidationOutcome` or the
  bounded document?* → **The bounded document `DiagnosticsBounder` already produced** (reason: one
  bounding path keeps the 64 KiB cap true; a hostile validator response must not become an unbounded
  outbound payload by travelling the repair path instead of the storage path).
- **[AUTO-DECISION]** *`ConfirmCompileRequestDto` and unknown keys.* → **`@JsonIgnoreProperties(ignoreUnknown = true)`
  declared explicitly** (reason: AC-4 requires the key to be ignored; Spring Boot's global default
  already does that, and stating it on the type means a future change to that global default cannot
  silently turn an ignored key into an undeclared `400`).
- **[AUTO-DECISION]** *Where does the five-test repair suite's Spring context come from?* → **A
  shared abstract base with `@Import(RepairStubs.class)`**, rather than a nested `@TestConfiguration`
  per class (reason: Spring Boot keys the context cache on the imported class set and on the
  `@DynamicPropertySource` method, so three test classes share one context and one embedded
  PostgreSQL instead of starting three).
- **[AUTO-DECISION]** *An extra test file beyond the drafted File List.* → **`RepairBudgetExpiryTest`
  split out of `RepairBoundsTest`** (reason: observing a mid-loop budget expiry needs a deployment
  configured with a short budget, and the same class cannot both use the shipped bounds and override
  them — 10.8's `CompileBudgetExpiryTest` set the same precedent for the same reason).
