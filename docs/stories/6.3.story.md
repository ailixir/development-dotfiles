## User Story

**As a** platform operator running checks at scale,
**I want** the CronDispatcher to submit batch items in parallel and the application task executor to be bounded,
**so that** large batches complete within the ShedLock window and unbounded thread creation can't exhaust system resources.

---

## Problem Statement

**CronDispatcher sequential dispatch (H2):** `pollAndDispatch()` iterates due schedules in a `for` loop, calling `dispatchSingle()` sequentially. Each call opens a `TransactionTemplate`, fetches the schedule+check, submits async work, and advances `nextExecutionAt`. With 100 due schedules and a slow database, this sequential loop can take minutes — risking the 5-minute ShedLock expiry.

**Unbounded applicationTaskExecutor (H3):** The `applicationTaskExecutor` bean uses `Executors.newVirtualThreadPerTaskExecutor()` with no semaphore wrapper. While `checkExecutor` is properly bounded (40 permits), the general-purpose executor has no backpressure. Under load, unbounded virtual thread creation can exhaust database connections when tasks perform JPA operations.

## Acceptance Criteria

### A — Parallel dispatch in CronDispatcher

- [x] **AC-1:** Replace the sequential `for` loop in `pollAndDispatch()` with parallel submission using `CompletableFuture`.
- [x] **AC-2:** Each `dispatchSingle()` runs as a `CompletableFuture.runAsync()` on the `checkExecutor` pool.
- [x] **AC-3:** `CompletableFuture.allOf(futures).join()` waits for all dispatches to complete before the method returns.
- [x] **AC-4:** Individual dispatch failures don't abort the batch — each future handles its own exception (same error handling as current `dispatchSingle`).
- [x] **AC-5:** MDC context propagated to each parallel future via `MdcTaskDecorator` (already configured on `checkExecutor`).
- [x] **AC-6:** Metrics: `checks.scheduled.batch_dispatch_duration` Timer tracks total batch dispatch time.

### B — Bounded applicationTaskExecutor

- [x] **AC-7:** `applicationTaskExecutor` wrapped with `SemaphoreBoundedExecutor`, permits = `checks.executor.app-semaphore-multiplier` (default 2) × `hikariMax`.
- [x] **AC-8:** Default permits = 2 × 10 = 20 (less aggressive than checkExecutor's 40).
- [x] **AC-9:** Config property `checks.executor.app-semaphore-multiplier` in `AsyncConfig`.

### C — Tests

- [x] **AC-10:** `ParallelDispatchIT`: insert 10 due schedules (8 OK + 2 failing), verify all dispatch, wall-clock < 3s (proving parallelism + fault isolation).
- [x] **AC-11:** (Merged into AC-10) Failure isolation verified: failing checks don't abort the batch.
- [x] **AC-12:** `AppExecutorBoundIT`: submit tasks exceeding permit count, verify semaphore caps max concurrency.
- [x] **AC-13:** JaCoCo coverage >= 80%.

## Implementation Notes

- **CompletableFuture pattern:**
  ```java
  List<CompletableFuture<Void>> futures = dueSchedules.stream()
      .map(s -> CompletableFuture.runAsync(() -> dispatchSingle(s), checkExecutor))
      .toList();
  CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
  ```
  This submits all dispatches to the semaphore-bounded `checkExecutor`. The semaphore naturally throttles parallelism to 40 concurrent tasks.

- **Transaction safety:** Each `dispatchSingle()` already creates its own `TransactionTemplate`. Running in parallel is safe because each future gets its own transaction.

- **MDC in parallel futures:** `MdcTaskDecorator` on `checkExecutor` captures and restores MDC per task. The parent's `schedulerId` MDC key should be set before submitting futures.

- **ShedLock window:** With parallel dispatch, 100 schedules at ~50ms each = ~5s total (vs ~5s × 100 = 500s sequential with slow DB). Well within the 5-minute lock.
