## User Story

**As a** put-checks user who wants a check to run automatically on a cadence,
**I want** dedicated `/api/v1/schedules` CRUD endpoints with cron expression + timezone support,
**so that** I can create, update, enable/disable, and delete schedules independently from checks, while still seeing the schedule embedded in `GET /checks/{id}` for convenience.

---

## Acceptance Criteria

- [ ] **AC-1:** `Schedule` JPA entity mapping to `schedules` table: id (UUID PK), check_id (FK, UNIQUE), frequency (VARCHAR 50), cron_expression (VARCHAR 100), timezone (VARCHAR 50, default UTC), enabled (boolean, default true), days_of_week (int[]), time_of_day (TIME), metadata (JSONB), created_at, updated_at.
- [ ] **AC-2:** `ScheduleRepository` with `findByCheckId(UUID)`, `findAllByEnabled(boolean)`, and filtered list query (check_id, enabled, timezone params).
- [ ] **AC-3:** `ScheduleService` with CRUD + enable/disable. On create: validate cron expression syntax (use `CronExpression.isValidExpression()` from Spring), validate timezone against `ZoneId.getAvailableZoneIds()`, enforce 1:1 with check via DB unique constraint.
- [ ] **AC-4:** `POST /api/v1/schedules` — body `{ check_id, frequency, cron_expression, timezone, enabled }`. Returns 201 + Location header. Validates check exists and user has write access to the check's CSI.
- [ ] **AC-5:** `GET /api/v1/schedules` — paginated list with optional filters: `check_id`, `enabled`, `timezone`. Admin sees all; non-admin sees only schedules for owned CSIs.
- [ ] **AC-6:** `GET /api/v1/schedules/{id}` — single schedule. Requires read access to the check's CSI.
- [ ] **AC-7:** `PUT /api/v1/schedules/{id}` — full replace. Requires write access.
- [ ] **AC-8:** `PATCH /api/v1/schedules/{id}/enabled` — body `{ enabled: true|false }`. Requires write access. Returns updated schedule.
- [ ] **AC-9:** `DELETE /api/v1/schedules/{id}` — hard delete (not soft). Requires write access. Returns 204.
- [ ] **AC-10:** `GET /api/v1/checks/{id}` response embeds the schedule as a read-only nested field: `{ "schedule": { "id": "...", "cron_expression": "*/5 * * * *", "enabled": true, ... } }`. Null if no schedule.
- [ ] **AC-11:** `next_execution_at` field computed on create/update from `cron_expression` + `timezone`. Stored in the `schedules` table (add column via V2 migration if not in V1, or use existing `metadata` JSONB). Used by story 2.3's dispatcher.
- [ ] **AC-12:** Authorization: all mutating endpoints require `canWrite(auth, check.csiId)`. Read endpoints require `canRead(auth, check.csiId)`. Admin bypass applies.
- [ ] **AC-13:** Integration tests: `ScheduleCrudIT` (create → read → update → delete lifecycle), `ScheduleEnable DisableIT` (toggle enabled), `ScheduleValidationIT` (bad cron → 400, bad timezone → 400, duplicate check_id → 409), `ScheduleAuthzIT` (non-owner cannot create/modify), `ScheduleEmbedIT` (GET /checks/{id} includes schedule).
- [ ] **AC-14:** JaCoCo coverage ≥ 80%.

## Implementation Notes

- **Cron validation:** Spring's `CronExpression.parse()` throws `IllegalArgumentException` for invalid cron strings. Catch and return 400.
- **Timezone validation:** `ZoneId.of(timezone)` throws `DateTimeException` for invalid zones. Catch and return 400.
- **1:1 constraint:** The `idx_schedules_check UNIQUE` index on `check_id` enforces this at DB level. Catch `DataIntegrityViolationException` and return 409 Conflict.
- **Embed in GET /checks/{id}:** Modify `CheckDto.from()` to accept an optional `Schedule` parameter. `CheckService.findById()` does a left-join or separate query.
- **next_execution_at:** Compute using `CronExpression.next(ZonedDateTime.now(timezone))`. Store as `TIMESTAMPTZ`. Dispatcher (2.3) polls this field.
