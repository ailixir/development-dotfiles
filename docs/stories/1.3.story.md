## User Story

**As a** put-checks backend developer about to author dozens of Flyway migrations across M1-M6,
**I want** a CI-enforced lint that rejects any migration using PostgreSQL features unavailable on the managed Amazon RDS cluster (SUPERUSER operations, non-allowlisted extensions, `ALTER SYSTEM`, etc.),
**so that** a migration can never pass CI on Zonky/Testcontainers (which grant SUPERUSER by default) yet fail at production deploy with an RDS permission denial — the exact class of bug flagged by research finding ZK-04/ZK-06.

---

## Acceptance Criteria

- [ ] **AC-1:** A Gradle task `./gradlew rdsParityLint` exists. It scans every `.sql` file under `backend/src/main/resources/db/migration/` and reports violations with file + line number + offending statement.
- [ ] **AC-2:** The lint rejects a migration containing any of:
  - `ALTER SYSTEM` (any form)
  - `CREATE EXTENSION <name>` where `<name>` is NOT in the allowlist
  - `DROP EXTENSION <name>` (removal of any extension is blocked)
  - `ALTER USER ... (SUPER)?USER` / `CREATE ROLE ... (SUPER)?USER` / `ALTER ROLE ... (SUPER)?USER`
  - `CREATE FUNCTION ... LANGUAGE C` (RDS blocks C functions)
  - `COPY ... FROM PROGRAM` (server-side program execution)
  - `pg_read_server_files` / `pg_write_server_files` / `pg_execute_server_program` role grants
- [ ] **AC-3:** The allowlist is **explicit** in a versioned config file at `backend/config/rds-parity/allowlist.yml` with initial entries: `pgcrypto`, `uuid-ossp`, `pg_stat_statements`, `hstore`, `btree_gin`, `btree_gist`. Adding an entry requires a code-reviewed PR (no silent config drift).
- [ ] **AC-4:** The lint task is wired into `./gradlew check` so it runs on every local build and every CI pipeline invocation.
- [ ] **AC-5:** Lint passes cleanly against the committed `V1__init.sql` from story 1.2 (no false positives on the real schema).
- [ ] **AC-6:** A negative test suite exercises the lint with **fixture migrations** under `backend/src/test/resources/rds-parity-fixtures/`. Each fixture is a `.sql` file with a known violation; an integration test asserts the lint detects each violation with the correct file + line number. Fixtures cover each rule in AC-2 (at least one fixture per rule).
- [ ] **AC-7:** A positive fixture (a migration using only RDS-legal operations) exists under `backend/src/test/resources/rds-parity-fixtures/ok/`; the lint MUST NOT flag it.
- [ ] **AC-8:** When the lint fails, the error output includes: (a) the full path to the violating file, (b) the line number, (c) the offending statement (single-line truncation at 120 chars for readability), (d) the rule that was violated, (e) a one-line remediation hint (e.g., "Use the extension allowlist at backend/config/rds-parity/allowlist.yml; escalate to the DBA team to expand it").
- [ ] **AC-9:** Exit codes: `0` on clean, `1` on violations, `2` on internal error (malformed SQL, missing allowlist config). CI uses the exit code; humans read the stderr message.
- [ ] **AC-10:** The implementation is pure-JVM (not a shell script), lives under `backend/buildSrc/src/main/kotlin/` or as a small Gradle task class — so it runs identically on macOS/Linux/Windows CI runners.

## Scope

### In scope

- Gradle task implementation (Kotlin, in `buildSrc/` for clean reuse).
- Allowlist config at `backend/config/rds-parity/allowlist.yml`.
- Positive + negative fixture migrations for the test suite.
- Unit test of the lint itself (parses fixture files, asserts violations).
- Hooking into `./gradlew check`.
- A short `backend/config/rds-parity/README.md` explaining the lint's purpose, allowlist policy, and how to handle false positives or request new allowlist entries.

### Out of scope

- **No SQL parser** — a regex-based matcher over statement-normalized text (whitespace-collapsed, lowercased-keywords) is sufficient for M1. A full PG grammar parser is overkill; revisit in M6 only if false positives become common.
- **No coverage of SQL comments containing violating keywords** — we're fine if a `-- some ALTER SYSTEM note` is benign; the lint must be smart enough to skip line comments (`--`) and block comments (`/* */`) via a pre-pass.
- **No runtime DB-side verification** — this is a static lint, not a simulation. Production deploy failure detection is still Flyway's job on the actual RDS instance; this lint is an early-warning system, not a guarantee.
- **No custom DSL / config schema evolution** — allowlist is a flat list; if the requirements grow (e.g., per-env allowlists), that's a separate future story.

## Implementation Notes (for @dev)

- **Why a regex matcher is enough:** the statements we reject are syntactically distinctive (`ALTER SYSTEM`, `CREATE EXTENSION`, `SUPERUSER` as a role attribute, `LANGUAGE C`, `FROM PROGRAM`). A line-oriented scan that first strips comments + normalizes whitespace catches every instance without reaching for a PG grammar. Document the regex-per-rule table in the `README.md` for future auditors.
- **Comment stripping:** implement a small pre-pass that removes:
  1. `--` line comments (from `--` to end of line, but not inside strings — keep it simple by stripping strings first)
  2. `/* ... */` block comments (non-nested is fine for PG)
  Then normalize whitespace.
- **False-positive avoidance:** `ALTER TABLE` must NOT match the `ALTER SYSTEM` rule. Match `\bALTER\s+SYSTEM\b` (whole-word boundaries, case-insensitive after normalization).
- **Allowlist loading:** parse `allowlist.yml` with Jackson YAML or SnakeYAML. Fail the task with exit code `2` if the file is malformed (distinct from violation exit `1`).
- **`buildSrc/` vs. standalone module:** `buildSrc/` is the idiomatic location for reusable Gradle build logic. Lives at `backend/buildSrc/` so it's scoped to the backend project (not the monorepo root).
- **Performance:** no migration file should exceed a few thousand lines; a regex scan over the full `db/migration/` directory takes <50ms. No need for parallelization.
- **Allowlist evolution policy:** document in `README.md` — adding an entry requires (a) confirmation that RDS has the extension enabled in the target cluster's parameter group, (b) a PR review by a teammate, (c) a note in the PR describing why the extension is needed. Do NOT grant PR-author self-merge for allowlist changes.

### Example implementation skeleton (Kotlin, `buildSrc/`):

```kotlin
// backend/buildSrc/src/main/kotlin/RdsParityLintTask.kt
abstract class RdsParityLintTask : DefaultTask() {
    @InputDirectory
    abstract val migrationDir: DirectoryProperty

    @InputFile
    abstract val allowlistFile: RegularFileProperty

    @TaskAction
    fun lint() {
        val allowlist = loadAllowlist(allowlistFile.get().asFile)
        val rules = listOf(
            NoAlterSystemRule,
            ExtensionAllowlistRule(allowlist),
            NoSuperuserRule,
            NoLanguageCFunctionRule,
            NoCopyFromProgramRule
        )
        val violations = migrationDir.get().asFileTree
            .matching { include("**/*.sql") }
            .flatMap { file -> scan(file, rules) }

        if (violations.isNotEmpty()) {
            violations.forEach { v -> logger.error(v.render()) }
            throw GradleException("RDS-parity lint found ${violations.size} violation(s). See stderr.")
        }
    }
}
```

### Risks / watch-items (non-blocking)

- **R-1.3-watch:** The allowlist's initial entries (`pgcrypto`, `uuid-ossp`, `pg_stat_statements`, `hstore`, `btree_gin`, `btree_gist`) include two extensions (`hstore`, `btree_gist`) that `V1__init.sql` does not use. Fine to include preemptively for common future needs, but note in the README: "Listed extensions are *permitted*; they do NOT imply the migration needs them." Prevents a reader assuming every allowlisted extension is in use.
- **R-1.3-watch:** Regex matchers have an uncomfortable history with SQL dialect edge cases (e.g., `ALTER SYSTEM RESET ALL` vs `ALTER SYSTEM SET ...` — both should be caught by `\bALTER\s+SYSTEM\b`, but verify with fixtures). @qa at gate time: confirm fixtures exercise the tail cases of each rule's regex, not just the canonical form.
- **R-1.3-watch:** `COPY ... FROM PROGRAM` is PG-dialect; `COPY ... FROM '/path/file'` (no `PROGRAM`) is RDS-legal via `aws_s3` extension workflows. The rule must match `FROM\s+PROGRAM\b` specifically. Fixture must include a legal `COPY FROM 'path'` as a negative-negative (must NOT be flagged).
