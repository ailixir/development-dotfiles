## User Story

**As a** CSI-authorized support engineer whose run has finished,
**I want** the video to be stored under a key the platform derives, a durable terminal manifest written before the result is delivered, and the snapshot to tell me honestly whether the recording covers the whole session,
**so that** a lost delivery is not a lost result, a truncated recording is not presented to me as a complete one, and evidence I may later have to show someone is not a claim the API made up.

## Problem Statement

Three things are true on branch `epic/EPIC-10` today, each verified by reading the file named:

**1. The API states a falsehood about every recording.** `RunnerReportProjection.java:126-133` sets `videoPartial = Boolean.FALSE` whenever a report carries evidence — unconditionally. `ExecutionSnapshotMapper.java:88-96` then publishes `Boolean.TRUE.equals(getVideoPartial())`, so a null column reads `false` too. Every execution the API has ever published says *this recording is complete*. Story 10.13 is landing the runner-side producer now (ADR-002 §17); it **cannot** fix this, because its Scope excludes Java. @po held the gap with a live skip naming **O-13 / story 10.14** so the half-fix could not read as a whole one. This story removes the constant, carries the runner's reported value through, and **deletes that skip**.

**2. The one worse case: the API will not merely discard the truth, it will refuse it.** `RunnerEvidence.java` is `@JsonIgnoreProperties(ignoreUnknown = false)` over three record components, and `StrictInternalBodyReader` reads internal callbacks through a mapper with `FAIL_ON_UNKNOWN_PROPERTIES` **enabled** — deliberately, so that "a field the contract does not name is then a `400` rather than a silent divergence". The moment 10.13 emits `evidence.partial` on every `FINAL`, that mapper rejects the whole report with `400 INVALID_REPORT`, the terminal delivery retries until abandoned, and the run is reconciled by a reaper instead of by its own result. ADR-002 §17.7 item 4 says *"the runner reports the truth and the API discards it — which is visible, bounded and strictly better than today"*. On the verified code that sentence is **too kind**: nothing is discarded, the report is refused. Raised as **open question 1**.

**3. There is no upload.** `recording.ts` says so in its own words — *"The recording lives and dies in scratch. Until 10.14 uploads it, the file is deleted with the rest of the per-run directory"* — and the runner's evidence type cannot even express `STORED`. `runCoordinator.ts`'s terminal `finally` is `settled → sendFinal → wipe → clear`: no object is written between the run ending and the result being delivered, so a lost delivery today is a lost result. The API side of the recovery is already built and already waiting — `ManifestKeys`, `ResultManifestStore`, `FinalizationReconciler` — against `FakeResultManifestStore`, whose javadoc names this story: *"the `ED-03` fake store story 10.14 replaces"*.

Two more facts the epic has paid for and this story is the next to touch:

- **`ui_test_executions.error_code` has no CHECK constraint** while `video_status`, constrained in the adjacent V14 statement, does. ADR-002 **O-11**, re-pointed by §18.2 to *"the next migration that touches `ui_test_executions`, which on the current plan is story 10.14's evidence work"*.
- **The terminal manifest the API reads is narrower than §5.3 requires.** `ResultManifest` (Java) carries `outcome, errorCode, errorMessage, browserStartedAt, endedAt, videoKey, evidenceState`. §5.3 requires the manifest to contain *"attempt/revision identity, result, timings, runtime versions, and evidence state"*. Identity and runtime versions are absent. This story is the first to have a producer, so it is the first that can make the document true.

## Migration warning this epic has already paid for — read before writing SQL

Story 10.1's `V14__studio_execution_history_v2.sql` **would have aborted on any non-empty database**. Its section 6 rewrote `ui_tests.browser` to `'chromium'` while V1's inline `ui_tests_browser_check` (`chrome|firefox|safari|edge`) was still in force; the `DO` block that dropped that constraint sat further down the file. On a database with one legacy row the whole migration fails with SQLSTATE 23514.

**CI never caught it, and could not have.** As `LegacyDataMigrationIT`'s own javadoc puts it: *"Every other migration test in the repository builds the schema from scratch and inserts afterwards, so V14's data-transformation statements always match zero rows."* It was found when QA stood up a real container holding one pre-existing row, and `LegacyDataMigrationIT` now guards it by migrating in two stages — `flywayTo("12")`, seed, `flywayTo("14")`.

**AC-16 requires the same treatment for this story's migration, and it is not optional.** A constraint proven only against a schema built empty is proven against the one condition that cannot fail.

## Acceptance Criteria

> Every criterion below is falsifiable and cites its source. Criteria that need a real Sonic endpoint are split `a`/`b`; `b` parts are **skipped, never passed**.

### The objects the runner writes

- [x] **AC-1: The keys are the job's, echoed, and the two derivations are read from one place.** The runner writes the video to `job.videoKey` and the manifest to `job.manifestKey` **exactly as received** — it never derives, computes, normalizes or defaults a key, and the store client's type cannot be called with a key the job did not supply. Verified starting point: `envelope.ts:48-49` already carries both as required closed fields and `runCoordinator.ts:288` already binds them into `evidenceKeys`. A test drives a job whose keys deliberately differ from what `ManifestKeys` would derive for the same identity and asserts the runner used the **job's** strings. Separately, a test asserts that `ManifestKeys.videoKey`/`manifestKey` for one identity equal the keys a job built from that same identity carries — the agreement is asserted, not assumed, because two derivations of one string in two languages is the arrangement ADR-002 §15.6 names as the cause of INT-4. *[Source: architecture §6.2 "The API derives expected keys from immutable execution identity; client-supplied keys are never trusted"; §6.2 key shapes `studio/{csiId}/{testId}/{executionId}/{attemptId}.webm` and `.result.json`; contract `RunJob.videoKey` "never invents or accepts an arbitrary key"; epic §10.14 bullet 1; ADR-002 §15.6]*

- [x] **AC-2: The store client is write-only by construction, not by discipline.** The runner's object-store interface exposes **one** operation — put an object at a given key — and has no get, no list, no head and no delete. This mirrors `ResultManifestStore`'s deliberate three-things-it-cannot-do on the API side, and for the same reason: §6.2 gives the runner no Get and no List permission at all. A test asserts the exported client's own runtime surface is exactly the permitted operation set — **not** a source-text scan for forbidden method names, which AC-23 forbids as sole evidence. *[Source: architecture §6.2 "Runner writes only this prefix; API/recovery read only. Runner has no Get/List permissions"; §9.2; epic §10.14 bullet 3 "Runner writes only; API/recovery read only"]*

- [x] **AC-3: The order is upload → settle evidence → write the manifest → *then* deliver the result, and the boundary is `runScratch.clear()`, not `sendFinal`.** All four happen inside the terminal path. A test records the call order against an instrumented fake store and an instrumented report client and asserts the sequence for a successful run. Asserting on the order of statements in the source does not satisfy this criterion.

  **@po amendment 2026-09-11 — assumption A-4 did not survive 10.13's merge, and the criterion as drafted became one that cannot fail.** The draft assumed the terminal `finally` was `settled → sendFinal → wipe → clear`. On the merged runner (`src/server/runCoordinator.ts`, the `finally` block) it is:

  > `deadline?.cancel()` → `await reporter.settled()` → `await runScratch.clear()` → `resolver.wipe()` → `await reporter.sendFinal(outcome, evidence)`

  10.13 moved the scratch clear **before** the delivery window deliberately, and says so in the code: *"Released **before** the delivery window opens, not after it closes … Clearing scratch and wiping the values afterwards would mean a pod holding a browser profile, a video file and a set of resolved secrets for the whole of it."* **The video file lives in scratch.** So "before `sendFinal`" is now satisfied by an implementation that uploads after `runScratch.clear()` — at which point there is no file to upload, every run reports evidence `FAILED`, and AC-3's ordering test is **green**. That is a guard that cannot fail, in the worst available form: it is satisfied by an implementation that can never work.

  **The boundary is therefore restated as normative:** the upload, the evidence settle and the manifest write all complete — **including every retry AC-5 permits** — **before `runScratch.clear()` runs.** The asserted sequence is `put(videoKey) → evidence settled → put(manifestKey) → runScratch.clear() → resolver.wipe() → sendFinal`. **Two falsifications, both required:** (a) move the manifest write after `sendFinal` → the named test red; (b) **move the video upload after `runScratch.clear()` → the named test red**, and it must go red *on the ordering assertion*, not merely on a missing-file error, so the guard discriminates the ordering rather than the symptom. @dev re-reads the merged block before writing and records the real line numbers — the block has moved once already.

  **Two consequences that are not optional.** (1) AC-5's upload budget now sits inside the window between `reporter.settled()` and `runScratch.clear()`, which is *narrower* than "the runner's total" — the arithmetic in AC-5 is against that window and is stated in the Dev Agent Record. (2) `resolver.wipe()` runs before `sendFinal` but **after** the manifest write, so the manifest writer still has the redactor and the resolved values in scope; AC-6's canary experiment is therefore live at the moment the manifest bytes are produced, which is exactly where it needs to be. Do not "fix" this by moving the wipe earlier. *[Source: architecture §5.3 "Before delivery, runner writes a redacted terminal result manifest to a deterministic Sonic key"; epic §10.14 bullet 2; merged `runCoordinator.ts` terminal `finally` and its 10.13 AC-5a/AC-9 comment]*

- [x] **AC-4: Storage failure never costs the result, and never costs the outcome.** Three cases, each a test, each asserting that a `FINAL` is still delivered and that `outcome.result`, `outcome.errorCode` and every step status are **byte-identical** to the same run with a healthy store:
  - **(a)** the video upload fails, the manifest write succeeds → evidence `FAILED` with a redacted `error`, result delivered;
  - **(b)** the whole store is unreachable, neither object is written → evidence `FAILED`, result delivered **directly**;
  - **(c)** the video uploads and the manifest write fails → evidence reflects the stored video; the run is delivered, and the loss of the manifest is a diagnostic, not an outcome.

  **Falsification required:** an implementation that lets a store error propagate out of the terminal path — so the `FINAL` is never built — must turn (b) red. *[Source: architecture §5.3 "If Sonic is unavailable, still deliver the final result directly with evidence failure"; §6.1 "Upload failure never overwrites a known assertion outcome"; epic §10.14 acceptance bullet 2; epic definition-of-done "Infrastructure/evidence failure is reported honestly"]*

- [x] **AC-5: Uploads retry boundedly and idempotently, and hold nothing unbounded.** A retry writes the **same key with the same bytes**; it never produces a second object, a second key or a suffixed key. Retries are bounded by both attempt count and a wall-clock window, and the whole upload budget sits **inside** the runner's total (10.13 AC-5a's arithmetic), so a slow bucket cannot push the run past the API's recovery deadline. Nothing retains an unbounded buffer between attempts: the video is streamed from the scratch file rather than read wholly into memory, and the manifest's bytes are serialized **once** — the same discipline `reportClient.deliverTerminal` already applies to the `FINAL` body, for the same reason. Asserted: attempt count at the bound and one past it; the object count after a mid-sequence failure and recovery is exactly one.

  **@po amendment 2026-09-11 — two clauses as drafted are unfalsifiable and are replaced by ones that are not.** *"Peak retained bytes do not scale with the recording's size"* names no measurement and no mechanism; it is the shape *"an assertion whose stated discriminating mechanism is pre-empted"* taken to its limit — there is no mechanism at all, so any implementation satisfies it and a reviewer has nothing to check. It is replaced by two decidable claims: **(i)** the store client is handed a **stream or a file handle**, never a `Buffer` of the whole file, asserted on the **argument the client actually receives** (its runtime type / the absence of a whole-file read), with the falsification being *pass a fully-read buffer → red*; and **(ii)** a run whose recording is an order of magnitude larger than the baseline fixture completes with the **same number of whole-file reads** — zero — which is the property that actually distinguishes streaming from buffering.

  The budget clause is also re-anchored: *"the whole upload budget sits inside the runner's total"* is replaced by **"inside the window between `reporter.settled()` and `runScratch.clear()`"**, per AC-3's @po amendment, because that is the window the file exists in. The arithmetic against 10.13 AC-5a's totals is recorded in the Dev Agent Record rather than asserted as a literal. *[Source: epic §10.14 bullet 3 "Retries are bounded/idempotent"; epic §10.13 bullet 3 "retry delivery must not retain unlimited resources"; architecture §5.3; §5.4 "Recovery deadline is the browser runtime cap plus bounded finalization/delivery margins"]*

- [x] **AC-6: No resolved value reaches the manifest — proven on the bytes handed to the store, as an experiment.** The canary discipline story 10.13 established, applied to the one surface §9.2 names by hand alongside jobs and retry queues. At least three canary shapes chosen because they defeat a source scan (a value reaching the manifest through an innocently named local; a value carried on a throwable's message that lands in `errorMessage`; a value in a runtime-version string), planted so each is genuinely present in the run, and asserted **absent from the serialized manifest bytes captured at the store boundary** — not from the object the serializer was given. Each shape ships with its own falsifying mutation, recorded per AC-22. A `doesNotContain` whose canary was never in the run is a vacuous pass and does not satisfy this criterion — this exact defect was found in story 10.5 (gate QUAL: *"AC-10's canary assertions cannot fail … the tests are vacuously true"*). *[Source: architecture §5.3 "No resolved variables/secrets enter manifests"; §9.2 "Never persist them in jobs, retry queues, manifests or diagnostics"; epic §10.13 acceptance bullet 2 "Canary values never appear in … manifests"; story 10.5 QA gate QUAL finding]*

- [x] **AC-7a: The manifest carries what §5.3 names, and one committed fixture is read by both trees.** §5.3 requires *"attempt/revision identity, result, timings, runtime versions, and evidence state"*. The Java `ResultManifest` carries neither identity nor runtime versions today; this story widens it and the runner writes all of them. The agreement between producer and reader is proven by **one fixture, generated by the runner's serializer and committed once**: the runner suite asserts its serializer still produces those bytes, and the backend suite deserializes that same file through `ResultManifest` and asserts every field. Two hand-maintained copies in two languages is forbidden here for the reason ADR-002 §15.6 gives. Additionally: `FinalizationReconciler` **refuses** a manifest whose embedded `executionId`/`attemptId` do not match the key it was read from, records it for investigation and applies nothing — the manifest's identity is defence in depth over the derived key, never a substitute for it. *[Source: architecture §5.3 (manifest contents; "A manifest arriving after finalization is recorded for investigation; it cannot silently change history or trigger a new run"); §6.2; epic §10.14 bullet 1 "keys include execution/attempt and immutable CSI identity"; ADR-002 §15.6; verified narrowness of `ResultManifest.java`]*
- [~] *(SKIPPED, NEVER PASSED — @architect ruling requested 2026-09-11, not landed)* **AC-7b:** *(Escalated — @architect; see open question 2. Recorded as **skipped, never passed** until ruled.)* The terminal result manifest is a **runner-produced body the API deserializes**, and it is **not declared in the frozen contract**. Every other such body is declared and closed (ADR-002 §6.2). This story does **not** add a schema to `openapi.yaml` on its own authority. Until ruled, AC-7a's single shared fixture is the mechanism, and its weakness is stated plainly: a fixture is checkable but it is not a contract, and nothing stops a third consumer from guessing.

  **@po ruling 2026-09-11 — the classification is settled here so @architect is asked one question, not two.** It is **Class B**. §12 defines Class B as *"the shape or meaning of a runner-produced body"* and Class C as *"routes, security schemes, tags, `servers`, status-code semantics, and anything on the public surface."* The manifest is produced by the runner, consumed by the API, and touches no route, no status code and no public surface — it is the paradigm case of B, and declaring it for the first time is a decision (so not A). The question put to @architect is therefore the single one that remains: **should the terminal result manifest be declared as a closed schema in `openapi.yaml`, and if so with what shape** — with §5.3's five contents (*attempt/revision identity, result, timings, runtime versions, evidence state*) as the candidate and this story's widened `ResultManifest` as the proposal. The story proposes and does not land, exactly as §12 requires.

  **The widening of the Java `ResultManifest` is *not* gated on that ruling and proceeds under AC-7a.** §5.3 already requires the five contents; the record being narrower than §5.3 is a defect against a landed normative source, not a contract question, and Article IV puts the source first. What is gated is only whether the shape is *declared in the contract*.

### Evidence disposition stays honest

- [x] **AC-8: `STORED` is earned, and it is the only new word.** The runner's evidence state becomes `STORED` **only after the store has acknowledged the object write**, never before, never optimistically, never because a file was playable. `recording.ts`'s `RunnerEvidenceState` — today `'PENDING' | 'FAILED' | 'UNAVAILABLE'`, narrowed on purpose because *"`STORED` is not this story's word"* — is widened here and only here. Asserted: an upload that throws leaves `FAILED` and never `STORED`; a run whose recording was never playable stays `UNAVAILABLE` and is never uploaded at all; a successful upload reports `STORED` and never `PENDING`. On the API side the projection `STORED → AVAILABLE` already exists (verified in `RunnerReportProjection.projectEvidenceState`) and already stamps `videoExpiresAt = now + retention` **only** on `AVAILABLE`; a test asserts an end-to-end `STORED` report produces `AVAILABLE` with a non-null expiry, and that `FAILED`/`UNAVAILABLE` produce none. *[Source: architecture §6.1 evidence states and their independence; §6.2; contract `RunnerEvidence.state` and its documented projection; `recording.ts` as merged]*

- [x] **AC-9: `partial` travels through the upload unchanged.** The value 10.13's stop observation produced is carried onto the `FINAL` verbatim when `state` moves to `STORED`. The upload path never recomputes it, never clears it on success, and never sets it from the uploaded object's size or duration. Asserted: a run whose stop grace expired over a salvageable prefix, uploaded successfully, reports `state: STORED, partial: true` on the **serialized body**. **Falsification required:** an implementation that resets `partial` to `false` when the upload succeeds — the single most likely accident in this story — must turn it red. *[Source: ADR-002 §17.7 item 4 "Story 10.14 carries it through unchanged when it moves `state` to `STORED`"; §17.3; §17.4]*

## Implementation Notes

- **Land AC-10 first, before anything else in this story.** It is one nullable field on one record. Until it lands, a merged 10.13 talking to a merged API produces `400 INVALID_REPORT` on every `FINAL`. See open question 1.

- **Why AC-13 refuses rather than coerces.** The alternative — the API quietly forcing `partial` to `false` whenever evidence is `FAILED`/`UNAVAILABLE` — is cheaper and is rejected. `RunnerReportProjection.validate`'s own javadoc states the principle: *"Everything here is a `400` rather than a silent coercion, because a silent coercion is a divergence nobody ever finds."* A runner sending that combination has a bug in its stop observation, and a coercion would hide it in exactly the component whose whole purpose this story is to make honest. It is also cheap to get right: 10.13 AC-16 case (c) already fixes `partial: false` for the unplayable case.

- **Why no new runner error code for a storage failure.** §6.1 and the epic's definition-of-done make evidence independent of outcome; a failed upload is `FAILED` evidence on an otherwise unchanged result. `RECORDING_FAILED` already exists and is reachable *"only where the recording lifecycle failed before any step ran"* — a storage failure is not that. Adding a code would put an evidence fact into `outcome.errorCode`, which is the derivation §17.4 forbids, one field over.

- **The manifest is a wire body with no schema, and that is the story's sharpest unowned risk.** Every other runner-produced body is closed in the contract. This one is produced by TypeScript, consumed by a Java record, and governed by nothing. AC-7a's shared fixture is the best a story may do on its own authority; AC-7b escalates the real question. Whoever implements should resist the tempting middle path of "just add a schema" — that is precisely the Class B/C edit §12 reserves.

- **Seams to watch.**

  - `RunnerReportProjection` is story 10.7's file and is touched by this story alone in wave 5 — verified: 10.17's subject is dispatch-time resolution and the vault, not the report projection. Flagged for @po as **open question 4** regardless, because `FOC-03` and `FOC-04` were both found by a story checking rather than assuming.

## The weakest criteria — named honestly

Stating which criteria are most likely to be satisfied vacuously or cut under pressure, so a reviewer knows where to look first.

1. **AC-6 (manifest redaction canary) — the weakest.** This epic has now found vacuous redaction guards **twice** (10.5's `doesNotContain` over a canary never placed in the request; 10.8's source scan of log sites). A canary that never actually enters the run makes every assertion green and means nothing. The mitigation is written into the criterion — *asserted on bytes captured at the store boundary, with a per-shape falsifying mutation* — but the mitigation is only as good as the discipline applying it, and nothing in the test's own name will reveal the failure.

2. **AC-11's un-skip.** The deletion of another story's skip is the single most droppable line in this document: it lives in a different tree from the fix, nothing fails if it is forgotten, and a leftover skip citing an owner that has landed reads to the next person as an open item. It is named in AC-11 and again in T-10.14.3 for exactly that reason.

3. **AC-12 and AC-14 — easy to satisfy against a hand-built input.** Both are about what the API does with a report. The vacuity is not in the assertion but in the input: a projection record constructed by hand in a test can be made to demonstrate anything. Both criteria require the input to be a report the runner's own serializer could produce; that clause is the load-bearing half and it is the half most likely to be relaxed for convenience.

4. **AC-17 (the migration/contract agreement).** The obvious implementation is a hardcoded list in the test, which makes it a **third** copy of the vocabulary and defeats the criterion's whole purpose. It will pass. It will also drift the next time §15 widens, silently, which is the exact failure O-11 exists because of.

5. **AC-16 (the container with pre-existing rows).** Expensive, slow, and the one most likely to be replaced by "we ran the migration in the IT suite and it was fine" — which is what the whole of story 10.1's incident was. It cannot be satisfied by a schema built empty, and no green suite will say so.

6. **AC-18b / AC-19b (`ED-03`).** Deferred parts are structurally weak because nothing enforces them. They are recorded **skipped, never passed**, and AC-19b in particular carries a checkable reviewer instruction (grep the delivered artefacts for a claim of exact-time physical deletion) because a *"do not claim X"* criterion is otherwise unfalsifiable.

7. **AC-21 — the risk here is the opposite one: claiming someone else's green.** The reaper behaviour is story 10.7's and already passes. This criterion is only worth its line if it is driven through the **real write path** this story adds; asserted against a hand-populated fake it re-tests 10.7 and proves nothing new.

### The PostgreSQL 15 `NOT VALID` question — settled, empirically

@sm raised it and neither @sm nor @po verified it. Verified here against `postgres:15-alpine` — **PostgreSQL 15.19**, the exact image `application-test.yml`'s `jdbc:tc:postgresql:15-alpine` runs — on a table built to the same shape (`PARTITION BY RANGE (started_at)`, `PRIMARY KEY (id, started_at)`, a named partition and a DEFAULT partition, seeded with a legitimate row and an out-of-vocabulary one):

1. `ALTER TABLE <partitioned parent> ADD CONSTRAINT … CHECK (…) NOT VALID` is **accepted**. It recurses and produces one `pg_constraint` row per relation — parent plus every partition — all with `convalidated = false`.
2. While still `NOT VALID` it is **enforced on every new write**, per partition, with the offending row in the error `DETAIL`.
3. `VALIDATE CONSTRAINT` then fails loudly on dirty data and succeeds once the data is repaired, flipping all rows to `convalidated = true`.

**§18.2's form is therefore correct and no switch was needed.** One correction to the story's expectation, recorded because AC-16 asserts on it: `VALIDATE CONSTRAINT` names the **relation**, not the row — `check constraint "ck_ui_test_executions_error_code" of relation "ui_test_executions_default" is violated by some row`. The migration's own comment therefore carries the query that finds the row, and `ErrorCodeConstraintMigrationIT` asserts that query returns exactly the seeded out-of-vocabulary value.
