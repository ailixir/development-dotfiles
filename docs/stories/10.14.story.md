## User Story

**As a** CSI-authorized support engineer whose run has finished,
**I want** the video to be stored under a key the platform derives, a durable terminal manifest written before the result is delivered, and the snapshot to tell me honestly whether the recording covers the whole session,
**so that** a lost delivery is not a lost result, a truncated recording is not presented to me as a complete one, and evidence I may later have to show someone is not a claim the API made up.

---

## Problem Statement

Three things are true on branch `epic/EPIC-10` today, each verified by reading the file named:

**1. The API states a falsehood about every recording.** `RunnerReportProjection.java:126-133` sets `videoPartial = Boolean.FALSE` whenever a report carries evidence — unconditionally. `ExecutionSnapshotMapper.java:88-96` then publishes `Boolean.TRUE.equals(getVideoPartial())`, so a null column reads `false` too. Every execution the API has ever published says *this recording is complete*. Story 10.13 is landing the runner-side producer now (ADR-002 §17); it **cannot** fix this, because its Scope excludes Java. @po held the gap with a live skip naming **O-13 / story 10.14** so the half-fix could not read as a whole one. This story removes the constant, carries the runner's reported value through, and **deletes that skip**.

**2. The one worse case: the API will not merely discard the truth, it will refuse it.** `RunnerEvidence.java` is `@JsonIgnoreProperties(ignoreUnknown = false)` over three record components, and `StrictInternalBodyReader` reads internal callbacks through a mapper with `FAIL_ON_UNKNOWN_PROPERTIES` **enabled** — deliberately, so that "a field the contract does not name is then a `400` rather than a silent divergence". The moment 10.13 emits `evidence.partial` on every `FINAL`, that mapper rejects the whole report with `400 INVALID_REPORT`, the terminal delivery retries until abandoned, and the run is reconciled by a reaper instead of by its own result. ADR-002 §17.7 item 4 says *"the runner reports the truth and the API discards it — which is visible, bounded and strictly better than today"*. On the verified code that sentence is **too kind**: nothing is discarded, the report is refused. Raised as **open question 1**.

**3. There is no upload.** `recording.ts` says so in its own words — *"The recording lives and dies in scratch. Until 10.14 uploads it, the file is deleted with the rest of the per-run directory"* — and the runner's evidence type cannot even express `STORED`. `runCoordinator.ts`'s terminal `finally` is `settled → sendFinal → wipe → clear`: no object is written between the run ending and the result being delivered, so a lost delivery today is a lost result. The API side of the recovery is already built and already waiting — `ManifestKeys`, `ResultManifestStore`, `FinalizationReconciler` — against `FakeResultManifestStore`, whose javadoc names this story: *"the `ED-03` fake store story 10.14 replaces"*.

Two more facts the epic has paid for and this story is the next to touch:

- **`ui_test_executions.error_code` has no CHECK constraint** while `video_status`, constrained in the adjacent V14 statement, does. ADR-002 **O-11**, re-pointed by §18.2 to *"the next migration that touches `ui_test_executions`, which on the current plan is story 10.14's evidence work"*.
- **The terminal manifest the API reads is narrower than §5.3 requires.** `ResultManifest` (Java) carries `outcome, errorCode, errorMessage, browserStartedAt, endedAt, videoKey, evidenceState`. §5.3 requires the manifest to contain *"attempt/revision identity, result, timings, runtime versions, and evidence state"*. Identity and runtime versions are absent. This story is the first to have a producer, so it is the first that can make the document true.

## Migration warning this epic has already paid for — read before writing SQL

Story 10.1's `V14__studio_execution_history_v2.sql` **would have aborted on any non-empty database**. Its section 6 rewrote `ui_tests.browser` to `'chromium'` while V1's inline `ui_tests_browser_check` (`chrome|firefox|safari|edge`) was still in force; the `DO` block that dropped that constraint sat further down the file. On a database with one legacy row the whole migration fails with SQLSTATE 23514.

**CI never caught it, and could not have.** As `LegacyDataMigrationIT`'s own javadoc puts it: *"Every other migration test in the repository builds the schema from scratch and inserts afterwards, so V14's data-transformation statements always match zero rows."* It was found when QA stood up a real container holding one pre-existing row, and `LegacyDataMigrationIT` now guards it by migrating in two stages — `flywayTo("12")`, seed, `flywayTo("14")`.

**AC-16 requires the same treatment for this story's migration, and it is not optional.** A constraint proven only against a schema built empty is proven against the one condition that cannot fail.

## Acceptance Criteria

> Every criterion below is falsifiable and cites its source. Criteria that need a real Sonic endpoint are split `a`/`b`; `b` parts are **skipped, never passed**.

### The objects the runner writes

- [ ] **AC-1: The keys are the job's, echoed, and the two derivations are read from one place.** The runner writes the video to `job.videoKey` and the manifest to `job.manifestKey` **exactly as received** — it never derives, computes, normalizes or defaults a key, and the store client's type cannot be called with a key the job did not supply. Verified starting point: `envelope.ts:48-49` already carries both as required closed fields and `runCoordinator.ts:288` already binds them into `evidenceKeys`. A test drives a job whose keys deliberately differ from what `ManifestKeys` would derive for the same identity and asserts the runner used the **job's** strings. Separately, a test asserts that `ManifestKeys.videoKey`/`manifestKey` for one identity equal the keys a job built from that same identity carries — the agreement is asserted, not assumed, because two derivations of one string in two languages is the arrangement ADR-002 §15.6 names as the cause of INT-4. *[Source: architecture §6.2 "The API derives expected keys from immutable execution identity; client-supplied keys are never trusted"; §6.2 key shapes `studio/{csiId}/{testId}/{executionId}/{attemptId}.webm` and `.result.json`; contract `RunJob.videoKey` "never invents or accepts an arbitrary key"; epic §10.14 bullet 1; ADR-002 §15.6]*

- [ ] **AC-2: The store client is write-only by construction, not by discipline.** The runner's object-store interface exposes **one** operation — put an object at a given key — and has no get, no list, no head and no delete. This mirrors `ResultManifestStore`'s deliberate three-things-it-cannot-do on the API side, and for the same reason: §6.2 gives the runner no Get and no List permission at all. A test asserts the exported client's own runtime surface is exactly the permitted operation set — **not** a source-text scan for forbidden method names, which AC-23 forbids as sole evidence. *[Source: architecture §6.2 "Runner writes only this prefix; API/recovery read only. Runner has no Get/List permissions"; §9.2; epic §10.14 bullet 3 "Runner writes only; API/recovery read only"]*

- [ ] **AC-3: The order is upload → settle evidence → write the manifest → *then* deliver the result, and the order is asserted on observed calls.** All four happen inside the terminal path, before `reporter.sendFinal`. A test records the call order against an instrumented fake store and an instrumented report client and asserts the sequence for a successful run. **Falsification required:** moving the manifest write to after the `FINAL` delivery must turn this red. Asserting on the order of statements in the source does not satisfy this criterion. *[Source: architecture §5.3 "Before delivery, runner writes a redacted terminal result manifest to a deterministic Sonic key"; epic §10.14 bullet 2 "Upload video, settle evidence disposition, then store a redacted terminal manifest before acknowledgment-sensitive final delivery"]*

- [ ] **AC-4: Storage failure never costs the result, and never costs the outcome.** Three cases, each a test, each asserting that a `FINAL` is still delivered and that `outcome.result`, `outcome.errorCode` and every step status are **byte-identical** to the same run with a healthy store:
  - **(a)** the video upload fails, the manifest write succeeds → evidence `FAILED` with a redacted `error`, result delivered;
  - **(b)** the whole store is unreachable, neither object is written → evidence `FAILED`, result delivered **directly**;
  - **(c)** the video uploads and the manifest write fails → evidence reflects the stored video; the run is delivered, and the loss of the manifest is a diagnostic, not an outcome.

  **Falsification required:** an implementation that lets a store error propagate out of the terminal path — so the `FINAL` is never built — must turn (b) red. *[Source: architecture §5.3 "If Sonic is unavailable, still deliver the final result directly with evidence failure"; §6.1 "Upload failure never overwrites a known assertion outcome"; epic §10.14 acceptance bullet 2; epic definition-of-done "Infrastructure/evidence failure is reported honestly"]*

- [ ] **AC-5: Uploads retry boundedly and idempotently, and hold nothing unbounded.** A retry writes the **same key with the same bytes**; it never produces a second object, a second key or a suffixed key. Retries are bounded by both attempt count and a wall-clock window, and the whole upload budget sits **inside** the runner's total (10.13 AC-5a's arithmetic), so a slow bucket cannot push the run past the API's recovery deadline. Nothing retains an unbounded buffer between attempts: the video is streamed from the scratch file rather than read wholly into memory, and the manifest's bytes are serialized **once** — the same discipline `reportClient.deliverTerminal` already applies to the `FINAL` body, for the same reason. Asserted: attempt count at the bound and one past it; the object count after a mid-sequence failure and recovery is exactly one; peak retained bytes do not scale with the recording's size. *[Source: epic §10.14 bullet 3 "Retries are bounded/idempotent"; epic §10.13 bullet 3 "retry delivery must not retain unlimited resources"; architecture §5.3; §5.4 "Recovery deadline is the browser runtime cap plus bounded finalization/delivery margins"]*

- [ ] **AC-6: No resolved value reaches the manifest — proven on the bytes handed to the store, as an experiment.** The canary discipline story 10.13 established, applied to the one surface §9.2 names by hand alongside jobs and retry queues. At least three canary shapes chosen because they defeat a source scan (a value reaching the manifest through an innocently named local; a value carried on a throwable's message that lands in `errorMessage`; a value in a runtime-version string), planted so each is genuinely present in the run, and asserted **absent from the serialized manifest bytes captured at the store boundary** — not from the object the serializer was given. Each shape ships with its own falsifying mutation, recorded per AC-22. A `doesNotContain` whose canary was never in the run is a vacuous pass and does not satisfy this criterion — this exact defect was found in story 10.5 (gate QUAL: *"AC-10's canary assertions cannot fail … the tests are vacuously true"*). *[Source: architecture §5.3 "No resolved variables/secrets enter manifests"; §9.2 "Never persist them in jobs, retry queues, manifests or diagnostics"; epic §10.13 acceptance bullet 2 "Canary values never appear in … manifests"; story 10.5 QA gate QUAL finding]*

- [ ] **AC-7a: The manifest carries what §5.3 names, and one committed fixture is read by both trees.** §5.3 requires *"attempt/revision identity, result, timings, runtime versions, and evidence state"*. The Java `ResultManifest` carries neither identity nor runtime versions today; this story widens it and the runner writes all of them. The agreement between producer and reader is proven by **one fixture, generated by the runner's serializer and committed once**: the runner suite asserts its serializer still produces those bytes, and the backend suite deserializes that same file through `ResultManifest` and asserts every field. Two hand-maintained copies in two languages is forbidden here for the reason ADR-002 §15.6 gives. Additionally: `FinalizationReconciler` **refuses** a manifest whose embedded `executionId`/`attemptId` do not match the key it was read from, records it for investigation and applies nothing — the manifest's identity is defence in depth over the derived key, never a substitute for it. *[Source: architecture §5.3 (manifest contents; "A manifest arriving after finalization is recorded for investigation; it cannot silently change history or trigger a new run"); §6.2; epic §10.14 bullet 1 "keys include execution/attempt and immutable CSI identity"; ADR-002 §15.6; verified narrowness of `ResultManifest.java`]*
- [ ] **AC-7b:** *(Escalated — @architect; see open question 2. Recorded as **skipped, never passed** until ruled.)* The terminal result manifest is a **runner-produced body the API deserializes**, and it is **not declared in the frozen contract**. Every other such body is declared and closed (ADR-002 §6.2). Whether the manifest joins them — and whether that is Class B or Class C under §12 — is not this story's call, and this story does **not** add a schema to `openapi.yaml` on its own authority. Until ruled, AC-7a's single shared fixture is the mechanism, and its weakness is stated plainly: a fixture is checkable but it is not a contract, and nothing stops a third consumer from guessing.

### Evidence disposition stays honest

- [ ] **AC-8: `STORED` is earned, and it is the only new word.** The runner's evidence state becomes `STORED` **only after the store has acknowledged the object write**, never before, never optimistically, never because a file was playable. `recording.ts`'s `RunnerEvidenceState` — today `'PENDING' | 'FAILED' | 'UNAVAILABLE'`, narrowed on purpose because *"`STORED` is not this story's word"* — is widened here and only here. Asserted: an upload that throws leaves `FAILED` and never `STORED`; a run whose recording was never playable stays `UNAVAILABLE` and is never uploaded at all; a successful upload reports `STORED` and never `PENDING`. On the API side the projection `STORED → AVAILABLE` already exists (verified in `RunnerReportProjection.projectEvidenceState`) and already stamps `videoExpiresAt = now + retention` **only** on `AVAILABLE`; a test asserts an end-to-end `STORED` report produces `AVAILABLE` with a non-null expiry, and that `FAILED`/`UNAVAILABLE` produce none. *[Source: architecture §6.1 evidence states and their independence; §6.2; contract `RunnerEvidence.state` and its documented projection; `recording.ts` as merged]*

- [ ] **AC-9: `partial` travels through the upload unchanged.** The value 10.13's stop observation produced is carried onto the `FINAL` verbatim when `state` moves to `STORED`. The upload path never recomputes it, never clears it on success, and never sets it from the uploaded object's size or duration. Asserted: a run whose stop grace expired over a salvageable prefix, uploaded successfully, reports `state: STORED, partial: true` on the **serialized body**. **Falsification required:** an implementation that resets `partial` to `false` when the upload succeeds — the single most likely accident in this story — must turn it red. *[Source: ADR-002 §17.7 item 4 "Story 10.14 carries it through unchanged when it moves `state` to `STORED`"; §17.3; §17.4]*

### O-13 — the API stops asserting a falsehood

- [ ] **AC-10: `RunnerEvidence` (Java) gains `partial`, and the API stops refusing the report that carries it.** The record grows a nullable `Boolean partial` matching the contract's optional property. A test posts a runner-shaped `FINAL` body containing `evidence.partial` to `POST /internal/studio/executions/{id}/progress` and asserts **`200`**. **This test must be shown red before the record is widened**, with the observed failure recorded in the Dev Agent Record: `StrictInternalBodyReader` enables `FAIL_ON_UNKNOWN_PROPERTIES` and `RunnerEvidence` is `@JsonIgnoreProperties(ignoreUnknown = false)`, so today the body is refused `400 INVALID_REPORT`. A test that is green both before and after has not tested this. *[Source: verified — `RunnerEvidence.java`, `StrictInternalBodyReader.java:29`, `StudioInternalController.java:64-69`; contract `RunnerEvidence.partial`; ADR-002 §17.2, §17.5]*

- [ ] **AC-11: The hardcoded `Boolean.FALSE` is gone, the reported value is projected, persisted and published — and the held skip is deleted.** `RunnerReportProjection` projects `report.evidence().partial()`, with **absent meaning `false`** (§17.5). The value persists to `video_partial` through the statements that already carry it (verified: `ProgressReportService:252` and `:278` already pass `projected.videoPartial()` into both the terminal statement and `settleEvidence`) and `ExecutionSnapshotMapper` keeps publishing the column it already reads. Three cases asserted **end to end through the persisted row and the published snapshot**, not on the projection record alone: reported `true` → published `true`; reported `false` → `false`; absent → `false`.
  **Two obligations, and neither is optional:**
  - **The mutation.** Restore `videoPartial = Boolean.FALSE` and the `true` case must go red. *A test that passes with the hardcoded value still in place is exactly the failure to prove against*, and it is the easiest one to write by accident — because `false` is a valid boolean and the story's happy path produces `false`.
  - **The un-skip.** Story 10.13's live skip citing **O-13 / story 10.14** — landed by its T-10.13.9, anticipated in `studio-runner/test/fixtures-tier/deadline-cleanup.test.ts` — is **located by its O-13 citation, not by a guessed name**, and **deleted**, with the assertion it was standing in for made live. A skip whose named owner has landed is worse than never having had one: it reads as an open item and is not. *[Source: ADR-002 §17.7 item 4; §18.4 O-13; story 10.13 AC-16 final paragraph and T-10.13.9; verified `RunnerReportProjection.java:126-133`, `ExecutionSnapshotMapper.java:88-96`]*

- [ ] **AC-12: `partial` is never derived from the outcome, in either direction, on the API side either.** The two counter-examples §17.3 names are asserted **on the published snapshot**: a run killed on the deadline whose ordered stop flushed cleanly publishes `ERROR`/`TIMEOUT` with `partial: false`; a `PASSED` run whose recorder died publishes `partial: true`. **Falsification required:** an implementation of `videoPartial = "TIMEOUT".equals(errorCode)` must turn **both** red. Symmetrically, no evidence field may influence `status`, `errorCode` or any step status — the independence 10.12 and 10.13 assert runner-side, re-asserted here on the surface the user actually reads. *[Source: ADR-002 §17.4 "It is false in both directions"; architecture §6.1; epic definition-of-done "upload failure never overwrites a known assertion outcome"]*

- [ ] **AC-13: `partial: true` alongside evidence that does not exist is refused, not coerced.** §17.3: partiality is meaningful only where a playable object exists; it is `false` with `FAILED` and `UNAVAILABLE`, *"because a recording that does not exist is not a partial one"*. A report carrying `state: FAILED` or `UNAVAILABLE` with `partial: true` is rejected `400 INVALID_REPORT` in `RunnerReportProjection.validate`, alongside the shape checks already there. This follows that method's own stated principle verbatim — *"Everything here is a `400` rather than a silent coercion, because a silent coercion is a divergence nobody ever finds."* Asserted both ways: the invalid combination is refused; the three valid combinations are accepted. *[Source: ADR-002 §17.3; `RunnerReportProjection.validate` javadoc as merged. The alternative — quietly forcing it to `false` — is rejected in Implementation Notes.]*

- [ ] **AC-14: The timed-out step's message is synthesized where — and only where — a terminal `TIMEOUT` meets a step still `RUNNING`.** `RunnerReportProjection.projectSteps` today copies `failure` verbatim, so the contract's `SnapshotErrorTimeout` example is aspirational and nothing produces it (verified). It produces it now, with the example's own text: `Total browser runtime deadline reached`. Four assertions, three of them negative:
  - a terminal `errorCode: TIMEOUT` with step 1 `RUNNING` → that step carries the message and the `SnapshotErrorTimeout` example is reproduced;
  - a terminal error with **any other code** and a `RUNNING` step → **no** message is invented;
  - `TIMEOUT` with **no** `RUNNING` step → no message anywhere;
  - a step whose runner-supplied `failure` is already non-null is **never overwritten**.

  The input is a report the runner's own serializer could produce, not a hand-built projection record. **Falsification required:** widening the predicate to any terminal error must turn assertion 2 red. *[Source: ADR-002 §18.1 — "may write that message **only** where it can name the cause — a terminal `errorCode` of `TIMEOUT` and a step still `RUNNING` — and must invent nothing for any other code or status"; §18.4 O-13 second half; contract example `SnapshotErrorTimeout`, `stepResults[1].message`]*

### O-11 — the database enforces the vocabulary it publishes

- [ ] **AC-15: One forward-only Flyway migration adds the CHECK `error_code` has never had.** Form as ADR-002 §18.2 fixes it: `error_code IS NULL OR error_code IN (<the declared values>)`, named in `V14`'s own convention (`ck_ui_test_executions_error_code`, beside `ck_ui_test_executions_video_status`). `ui_test_executions` is **range-partitioned by `started_at` with primary key `(id, started_at)`** since V7, and `ALTER TABLE` on the partitioned parent recurses into every partition **including the DEFAULT one** — so §18.2's form is `ADD CONSTRAINT … NOT VALID` followed by `VALIDATE CONSTRAINT`, rather than a blocking scan of every partition. **The version number is deliberately not assigned in this draft**: V12–V15 are merged and story 10.9 adds the next Studio migration in wave 4, so the free version is a merge-time fact. @dev assigns it and records it in the File List — the discipline story 10.7 established. **If PostgreSQL refuses `NOT VALID` on a partitioned parent at the version this project runs (`postgres:15-alpine` in the IT tier), that is a finding to record and escalate, not a licence to silently switch form.** *[Source: ADR-002 §18.2 (form, partitioned-table caveat, named owner "story 10.14's evidence work"); §15.9 O-11; §15.5 "the column has no CHECK — unlike `video_status`, constrained in the adjacent V14 statement"; V14 §1; architecture §8.1 forward-only, §8.2 "The current table has `(id, started_at)` as its primary key"]*

- [ ] **AC-16: The migration is proven against a container that already holds rows — not against a fresh schema.** A `LegacyDataMigrationIT`-shaped integration test: migrate to the version **before** this one, **seed**, then migrate the rest. The seed spans at least two partitions **including the DEFAULT partition**, and contains: rows with `error_code IS NULL`; a row for each declared value; and — the case that matters — **a row holding a value outside the vocabulary**, which is the only way a ninth value can exist (§15.5: a restored dump or a manual repair). The behaviour on that row is **decided and asserted**, not discovered: `VALIDATE CONSTRAINT` fails loudly, naming the row, and the operator remedy is documented in the migration's own comment. Both directions are asserted — clean data validates, dirty data refuses. **A test that builds the schema empty and inserts afterwards does not satisfy this criterion.** *[Source: this story's *Migration warning* section; `LegacyDataMigrationIT` javadoc and its two-stage `flywayTo("12")` → seed → `flywayTo("14")` structure; architecture §8.2 "verify migration behavior on historical, current, future and default history partitions"; ADR-002 §15.5, §18.2]*

- [ ] **AC-17: The constraint's value list is read from the frozen contract, never transcribed.** A test asserts the set of values in the migration equals `components.schemas.ExecutionErrorCode.enum` in `docs/specs/studio/openapi.yaml` — the document `ExecutionErrorCodeContractEscalationTest` already parses — so the next widening of §15's vocabulary is a **red test** rather than a silent drift between SQL and the published enum. Falsification: removing a value from the migration goes red; adding one the enum does not declare goes red. A hardcoded list inside the test is a **third** copy of the vocabulary and does not satisfy this criterion. *[Source: ADR-002 §18.2 "widened in lockstep with the enum whenever §15's vocabulary grows"; §15.6 properties 1–4; §18.3 "install the document-reading assertion once … Two hand-maintained copies of one vocabulary in two languages is the arrangement that produced INT-4"]*

On the API side `FakeResultManifestStore` — *"the `ED-03` fake store story 10.14 replaces"* — is now fed by the runner's real serializer through AC-7a's fixture instead of by hand-built objects. This also un-defers what it can of **story 10.7's AC-28b**, which reads *"(Deferred to story 10.14 / `ED-03`)"*; whatever of AC-28b still cannot pass on a fake is named here and left with `ED-03`. *[Source: manifest `ED-03` `gate_note` and `fallback`; epic §10.14 scope line "local fake/compatible store plus real Sonic integration"; story 10.7 AC-28b; `FakeResultManifestStore` javadoc]*
- [ ] **AC-18b:** *(Deferred — **`ED-03`**; owned by **10.18**, integrated proof **10.19**. Recorded as **skipped, never passed**.)* Real Sonic endpoint/bucket/path-style access; **runner write-only credentials scoped to the `studio/` prefix with no Get and no List**; API/recovery **read-only** credentials; encrypted transport and storage under platform policy. The client-side half is proven now (AC-2: the type cannot express a read); the **credential** half is a deployment fact this story cannot create and does not claim. `ED-03`'s owner is recorded as Platform/SRE and its status is `open`.

- [ ] **AC-19a: Retention is one configuration value, and the API stamps expiry from it.** The 30-day logical expiry lives in one configuration source (§8.5 — *"keep their implementation values in one configuration source"*), and the projection's `videoExpiresAt = now + retention` on `AVAILABLE` reads it from there. Logical expiry is enforced by the API at `videoExpiresAt` **regardless of physical deletion** — verified already true in `ExecutionSnapshotMapper` (`AVAILABLE` + elapsed expiry reads `EXPIRED`); a test keeps it true across this story's changes. *[Source: architecture §6.2 "Enforce logical video expiry in the API at `videoExpiresAt` even if physical lifecycle deletion is asynchronous"; §8.5; epic §10.14 bullet 4]*
- [ ] **AC-19b:** *(Deferred — **`ED-03`**; owned by **10.18** with **10.19**. Recorded as **skipped, never passed**.)* Verified lifecycle configuration on real Sonic: physical deletion, **versioning/noncurrent-object** behaviour and **incomplete-upload cleanup**. Deletion compliance is **tracked**, and **nothing in this story's code, docs or story text claims exact-time physical deletion** — §6.2 forbids that claim before Sonic's behaviour is verified, and the epic bullet says *"Track deletion behaviour rather than assuming exact-time object removal."* A reviewer may check this `b` part by grepping the delivered artefacts for such a claim; finding one is a failure of this criterion.

### Recovery — the point of the manifest

- [ ] **AC-20: A crash after the manifest upload but before the result is acknowledged is recoverable, and no browser runs twice.** The epic's first acceptance bullet for this story. Proven with the manifest the runner **actually writes** rather than a hand-built one: the runner is stopped between the manifest write and the `FINAL` acknowledgement, and the execution finalizes from the manifest at the derived key with the **real** outcome, applied idempotently, with the fake runner client's `POST /v1/runs` count still exactly one. No bucket listing or durable callback URL is required"; story 10.7 AC-28a/AC-31]*

- [ ] **AC-21: When both channels are down, the reaper records infrastructure failure and nothing is invented.** API delivery fails **and** the store is unreachable, then the runner is lost. The execution resolves through the running reaper into a terminal state that says infrastructure failed; **no recovered result appears, no outcome is guessed, no partial manifest is treated as whole**. ## Implementation Notes

- **Land AC-10 first, before anything else in this story.** It is one nullable field on one record. Until it lands, a merged 10.13 talking to a merged API produces `400 INVALID_REPORT` on every `FINAL`. See open question 1.

- **Why AC-13 refuses rather than coerces.** The alternative — the API quietly forcing `partial` to `false` whenever evidence is `FAILED`/`UNAVAILABLE` — is cheaper and is rejected. `RunnerReportProjection.validate`'s own javadoc states the principle: *"Everything here is a `400` rather than a silent coercion, because a silent coercion is a divergence nobody ever finds."* A runner sending that combination has a bug in its stop observation, and a coercion would hide it in exactly the component whose whole purpose this story is to make honest. It is also cheap to get right: 10.13 AC-16 case (c) already fixes `partial: false` for the unplayable case.

- **Why no new runner error code for a storage failure.** §6.1 and the epic's definition-of-done make evidence independent of outcome; a failed upload is `FAILED` evidence on an otherwise unchanged result. `RECORDING_FAILED` already exists and is reachable *"only where the recording lifecycle failed before any step ran"* — a storage failure is not that. Adding a code would put an evidence fact into `outcome.errorCode`, which is the derivation §17.4 forbids, one field over.

- **The manifest is a wire body with no schema, and that is the story's sharpest unowned risk.** Every other runner-produced body is closed in the contract. This one is produced by TypeScript, consumed by a Java record, and governed by nothing. AC-7a's shared fixture is the best a story may do on its own authority; AC-7b escalates the real question. ## The weakest criteria — named honestly

Stating which criteria are most likely to be satisfied vacuously or cut under pressure, so a reviewer knows where to look first.

1. **AC-6 (manifest redaction canary) — the weakest.** This epic has now found vacuous redaction guards **twice** (10.5's `doesNotContain` over a canary never placed in the request; 10.8's source scan of log sites). A canary that never actually enters the run makes every assertion green and means nothing. The mitigation is written into the criterion — *asserted on bytes captured at the store boundary, with a per-shape falsifying mutation* — but the mitigation is only as good as the discipline applying it, and nothing in the test's own name will reveal the failure.

2. **AC-11's un-skip.** The deletion of another story's skip is the single most droppable line in this document: it lives in a different tree from the fix, nothing fails if it is forgotten, and a leftover skip citing an owner that has landed reads to the next person as an open item. It is named in AC-11 and again in T-10.14.3 for exactly that reason.

3. **AC-12 and AC-14 — easy to satisfy against a hand-built input.** Both are about what the API does with a report. The vacuity is not in the assertion but in the input: a projection record constructed by hand in a test can be made to demonstrate anything. Both criteria require the input to be a report the runner's own serializer could produce; that clause is the load-bearing half and it is the half most likely to be relaxed for convenience.

4. **AC-17 (the migration/contract agreement).** The obvious implementation is a hardcoded list in the test, which makes it a **third** copy of the vocabulary and defeats the criterion's whole purpose. It will pass. It will also drift the next time §15 widens, silently, which is the exact failure O-11 exists because of.

5. **AC-16 (the container with pre-existing rows).** Expensive, slow, and the one most likely to be replaced by "we ran the migration in the IT suite and it was fine" — which is what the whole of story 10.1's incident was. It cannot be satisfied by a schema built empty, and no green suite will say so.

6. **AC-18b / AC-19b (`ED-03`).** Deferred parts are structurally weak because nothing enforces them. They are recorded **skipped, never passed**, and AC-19b in particular carries a checkable reviewer instruction (grep the delivered artefacts for a claim of exact-time physical deletion) because a *"do not claim X"* criterion is otherwise unfalsifiable.

7. **AC-21 — the risk here is the opposite one: claiming someone else's green.** The reaper behaviour is story 10.7's and already passes. This criterion is only worth its line if it is driven through the **real write path** this story adds; asserted against a hand-populated fake it re-tests 10.7 and proves nothing new.

## Open questions for @po

1. **ADR-002 §17.7 item 4 understates the consequence, and it changes the ordering.** It says *"the runner reports the truth and the API discards it — which is visible, bounded and strictly better than today."* On the verified merged code the API does not discard it: `StrictInternalBodyReader` enables `FAIL_ON_UNKNOWN_PROPERTIES` and `RunnerEvidence` is `@JsonIgnoreProperties(ignoreUnknown = false)` over three components, so a `FINAL` carrying `evidence.partial` is refused `400 INVALID_REPORT`, the terminal delivery retries until abandoned, and the run is reaped instead of reported. Nothing in CI catches this: the runner suite validates against the document (which permits `partial`), and the backend suites use their own fixtures. **Recommendation:** AC-10 is a single nullable field and is mergeable on its own; land it first, and consider landing it *inside wave 4* so the integrated branch is never in that state. Does this warrant a note in ADR-002 §17.7, or a manifest `FOC` entry for the wave-4 → wave-5 boundary?

2. **The terminal result manifest is an undeclared wire body.** It is produced by the runner, deserialized by the API into `ResultManifest`, and is not in the frozen contract — while every other runner-produced body is closed there (§6.2). The Java record is also **narrower than §5.3 requires** (no attempt/revision identity, no runtime versions). Is declaring it Class B or Class C under §12, and does it need an architect ruling before this story widens the Java record? This story does **not** add a schema on its own authority; AC-7b holds the question with a skip.

3. **`VALIDATE CONSTRAINT` in the same migration, or a follow-up?** §18.2 gives the form (`NOT VALID` then `VALIDATE`) but not the packaging. In the same migration, a restored dump holding an out-of-vocabulary row makes the migration fail at deploy. Split across two, the constraint enforces on writes immediately and the validation is an operator action. **[AUTO-DECISION]** *Drafted as one migration with both statements, and AC-16 asserts the loud failure* — because a migration that half-applies is the state nobody reasons about correctly. @po's call to overrule. Secondary, and genuinely unknown to me: I did not verify that PostgreSQL 15 accepts `ADD CONSTRAINT … NOT VALID` on a **partitioned parent**; AC-15 requires @dev to verify and escalate rather than silently switch form.

4. **Wave-5 file ownership.** 10.14, 10.10 and 10.17 share wave 5. Checked, not assumed: 10.10 is the action-review surface and shares nothing; 10.17's subject is dispatch-time reference/secret resolution and the vault. The two contacts I can see are `studio-runner/src/server/runCoordinator.ts` (this story inserts four steps into the terminal `finally`; 10.17 may touch the resolver's lifecycle) and `docs/specs/studio/openapi.yaml` + the `confinement.test.ts` pin, if AC-26 lands. Is a `FOC-05` warranted, or is the overlap genuinely empty? `FOC-03` and `FOC-04` were both found by a story checking rather than assuming, which is why this is asked rather than dismissed.

5. **O-14: is §17.5 the Class B ruling, or does landing it need a fresh one?** §17.5 states the rationale, the condition and the ordering, and §18.4 names this story as owner — which reads as a pre-ruling. But §12 says an architect rules *first, in this ADR*, and §17.5 explicitly *"recorded as O-14 rather than done now"*. AC-26 is drafted conditionally on @po's answer rather than assuming the permissive reading.

6. **Size.** Drafted as **L** against a manifest **M**, with the reasoning in *Size* above. Both wave-4 stories moved M → L at validation for the same cause — an architect ruling landing after the estimate — and that cause applies here twice (§17's O-13, §18.2's O-11). Requesting the manifest be updated with the reasoning, as it was for 10.9 and 10.13.
