## Story

**As a** Checks user who authors a UI test,
**I want** a step whose click or navigation lands on an HTTP error page (403, 404, 500 ...) to fail,
**so that** a run never shows all steps green while its own recording ends on "Access Denied".

## Context

Live evidence: execution `eaaa887c-44d5-4338-8625-3b3191b930d0` of "kernel-releases". Step 5, `Click the "browse" link in the "linux-next:" row of the releases table`, is PASS. git.kernel.org's bot protection answered 403, and the recording ends on an "Oh noes! Access Denied" page. The run PASSED with every step green.

Why it passes today (verified in the tree 2026-11-01, not run):

- After a step's code, `performStep` waits for the navigation it started (`host.settleNavigation`, only when `tally.fenceCrossed` or `tally.effects.length > 0`) and then `awaitWhitelistedMainFrame` checks the domain. Neither looks at the HTTP status. `studio-runner/src/run/observedReplayAdapter.ts` L136-137.
- `trackNavigation` in `studio-runner/src/run/browser.ts` (L136-166) listens to main-frame `request` and `framenavigated`; it never reads the response. `browser.ts` is the only module that imports Playwright, so the main-frame response status is observed there.
- A step ends with a closed `closedCode`. The list is closed and pinned: `ReplayError` (`studio-runner/src/executor/observedReplay.ts` L8, `replayError`) is the `closedCode` enum of `docs/specs/studio-observed-authoring/contracts/v3/replay-ipc.schema.json`, mirrored in `studio-runner/src/validator/observedSchemas.json` and sealed by `OBSERVED_SCHEMA_BUNDLE_HASH`. Today: INVALID_CONTRACT, PROFILE_MISMATCH, AUTHORIZATION_EXPIRED, POLICY_REFUSED, TARGET_DRIFT, READ_REFUSED, REFERENCE_REFUSED, ASSERTION_FAILED, CANCELLED, TIMEOUT, OUTCOME_UNKNOWN, INTERNAL_ERROR, LOGIN_REQUIRED, PASSWORD_CONTROL_READ_REFUSED, REFERENCE_MISMATCH. None means "the page answered with an error status".

Learning must agree: a test learned while the site answered an error page would record proof on that page and then fail (or worse, pass) every replay.

## Acceptance Criteria

1. **AC-1 — Main-document error fails the step.** When an action step (one that crossed the effect fence, or recorded an effect, as in the FIX-25 condition) lands on a main-frame document whose final HTTP response status (after redirects) is 400 or higher, the step fails with a closed, documented failure code and the run FAILS at that step. Later steps do not run.
2. **AC-2 — Only the main-frame document counts.** A response with status >= 400 for any sub-resource (favicon, scripts, images, fetch/XHR) or for a sub-frame never fails a step. A 3xx hop that ends in a 2xx document passes.
3. **AC-3 — Read and check steps are unaffected.** A step that did not cross the fence and recorded no effects (read, assert, capture) does not evaluate the rule, even when the current page was itself an error page. The rule looks at the document an action step lands on, not at the page the step started on.
4. **AC-4 — Learning and replay agree.** The same rule applies to the learning replay that records proof and to the model-free replay. A step that lands on an error page during learning is not learned as passed; the author sees the same failure sentence as in replay. Both paths use one implementation, not two copies of the check.
5. **AC-5 — Plain sentence everywhere the failure shows.** The step list, the failure overlay over the video and the run's error narrative show one plain sentence for the new failure, with the numeric status in visible text. `VideoFailureOverlay.tsx` (`STEP_FAILURE_SENTENCES`) and `executionErrorNarratives.ts` have an entry; no raw code is the only thing shown. Wording for 401/403 follows the PO ruling (Open question 2); until ruled, one sentence for all statuses.
6. **AC-6 — kernel-releases-style run fails at step 5.** A runner test serves a page whose link navigates to a document answering 403, with sub-resource 404s on the starting page. The run fails at that step, the earlier steps are green and the 404s do not matter. In addition, @qa re-runs the live "kernel-releases" test once the fix is in. Bot protection there is intermittent, so a PASS caused by an unblocked site is recorded as "not reproduced", not as evidence; the local test is the gate.
7. **AC-7 — Failure code and contract impact handled.** @architect rules first: a new closed code (working name `NAVIGATION_HTTP_ERROR`) or reuse of an existing one. The ruling is recorded in ADR-SC-008 (or a short ADR-SC-009 addendum). If a new code is added, in the same change: `replay-ipc.schema.json` and `observedSchemas.json` updated and the bundle hash re-sealed; `publication-fixtures.json` re-sealed; published revisions that fail `PROFILE_MISMATCH` after the hash move are listed with the re-publish path (no compat layer, per the single-path rule); backend `ExecutionErrorCodeContractEscalationTest`, `StudioContractTest` and `docs/specs/studio/openapi.yaml` carry the code; frontend maps it (AC-5). Whatever carries the status in `detail` holds the number only: no URL, no query string, no page body.
8. **AC-8 — Fixtures and tests.** Runner tests cover AC-1 to AC-4 (403, 404, 500 main document; sub-resource 4xx; redirect to 2xx; read step on an error page; learning). Frontend tests cover the sentence in step list and overlay. MSW execution fixtures include one run failed with the new code.

## Open questions

1. **@architect:** new code vs reuse. Reuse candidates are semantically wrong (`ASSERTION_FAILED` is "expected content missing", `TARGET_DRIFT` is "page changed"); a new code costs the full hash/publication ripple in AC-7. Also: do learning and replay need a shared host method on `StepApi` (for example one that returns the landed main-document status after `settleNavigation`) so the check lives once?
2. **@po:** should 401/403 be a clearer, distinct message ("the site blocked the automated browser")? This is the kernel.org case; the author's next action differs from a 404 (a broken link) or a 500.
3. **@po:** no opt-out is planned. A test that deliberately navigates to a 404 page to assert its text would now fail at the navigation step. Confirm that is acceptable for v1.
