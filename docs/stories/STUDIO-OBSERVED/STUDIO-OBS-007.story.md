## Story

As a Studio author, I want to write login steps that reference my saved credentials as `<secret ID>` — exactly as `<var NAME>` works for nonsecret values — and have the guided first Run and later model-free replays fill them only into the one password control at the one moment the step calls for, so that login-protected pages can be tested on the single observed path without any account provider while no credential is ever shown, stored outside Vault, or logged.

## Acceptance Criteria

Binding decisions: login is author-owned through `<secret ID>` steps (design §0); observed/guided is the **only** authoring path and the compile path, artifact 1 and every "legacy" variant are removed by OBS-012A (ADR-SC-005 D-A) — this story therefore has **no legacy half**: one password-only rule, one adapter, one `LOGIN_REQUIRED` signature, two audit paths (`GUIDED`, `OBSERVED_REPLAY`). Binding compliance requirement (design §4.6): secrets stay safe, are used **only at the right moment**, and are **never logged**. Every AC is testable by the oracle it cites (design §7, C-n / SEC-n); security conditions 1–9 (R1-tightened) are carried verbatim.

**Guided `secretRef` pipeline**

3. **AC-3 — `secretRef` end to end.** A declared `<secret ID>` classifies to `sourceReference{kind:secretRef, intendedSlot:fill.value, referenceName:ID}`; an undeclared ID is `FORBIDDEN_SCOPE`. The model receives the step text with the token span masked plus the reference (the ID), never a value: a gateway spy asserts the outbound bytes contain the ID and zero planted-value bytes (SEC-1). Materialization adds `authoredInputs += {kind:secretRef, secretId}` with no value, hashed into `authoredInputsHash`. The learned plan and lowered artifact carry `fill.value={kind:secretRef, sourceInputId}` and `inputRecipes[inputId]={kind:secretRef, referenceName:ID}` — the **only** spelling of a secret use on the single path — and `artifactHash` is identical before and after a Vault rotation (SEC-8). `validator/observedReplay.ts` and `ObservedRevisionVerifier` refuse any artifact whose fill literal equals a declared secret's resolved value and any `authoredLiteral`/`sourceSpan` overlapping a `<secret …>` token. [design §2, §3 "Reference rule"]

4. **AC-4 — Right moment: step binding (I-A1).** A secret is filled only (a) at a step whose authored source declares it, (b) in slot `fill.value`, (c) into the unique password control of AC-5, (d) on an origin in `allowedOrigins ∩ approvedOrigins` whose owning `form.action` origin is inside `allowedOrigins`. `GuidedProposalValidator` accepts a `passwordControl` target only with a `secretRef` value, only for an input whose `sourceStepId` is the fill's step, and only when the cited observation reports `coverage.passwordControls === 1`; `executionEvidence` document/generation staleness checks are unchanged. Runner `guided/runtime.ts` insists `input.sourceStepId === coordinate.stepId && intendedSlot === slot` for `secretRef` as it does for `authoredLiteral`; `validator/observedReplay.ts` and the observed executor re-check `inputRecipes[].stepId` at validation and at `perform` (`REFERENCE_MISMATCH`). The artifact-1 binding in `validator/references.ts` is **not** cited as evidence (it leaves with OBS-012A). [design §4.6 I-A1; §4.2; §4.3; oracle C-1]

5. **AC-5 — Trusted password-control resolution (security condition 1, tightened by R1-1/R1-2/R1-3).** The model never sees a password node (the collector does not export them). "Visible, enabled `input[type=password]`" is defined **once** in the isolated-world collector — computed-style visibility plus non-zero box (not viewport), traversal including open shadow roots, frames and closed shadow roots excluded — and that single function produces `coverage.passwordControls`, the `prepare` resolution and the fill-time check; a `querySelectorAll('input[type=password]')` resolver outside it is forbidden (static test, C-20). Resolution runs inside the collector's isolated world under the existing `acquire`-style guard (cited `documentId`, `generation`, `observedNavigation === navigation` before and after the in-world call); the element pinned at `prepare` is retained in that world and the fill requires the **same element** still attached, still `type=password`, still the unique candidate, with `location.origin` read in-world (not `page.url()`) inside `allowedOrigins ∩ approvedOrigins`; any deviation ⇒ `TARGET_CHANGED`, nothing typed; `navigation` is re-checked after the fill (C-18). 0 or >1 candidates ⇒ `POLICY_DENIED` with reason `PASSWORD_TARGET_ABSENT` / `PASSWORD_TARGET_AMBIGUOUS`, nothing typed; off-screen rendered decoys count (⇒ refuse), iframe/closed-shadow inputs do not (⇒ absent ⇒ refuse). A pinned input whose owning `form.action` resolves to an origin outside `allowedOrigins`, or a form-less input on a document whose origin differs from the observed login document, ⇒ `PASSWORD_FORM_ACTION_NOT_ALLOWED`, nothing typed (C-19). **Limit (ADR-SC-005 default, no opt-out):** multi-password pages and secrets into non-password controls are unsupported for `secretRef` fills at GA — `PASSWORD_TARGET_AMBIGUOUS`/`POLICY_DENIED`, nothing typed, no fallback adapter; stated in the runner README. [design §4.2, §4.3; security review "R1 delta check" R1-1, R1-2, R1-3; oracles SEC-6, C-18, C-19, C-20; ADR-SC-005 defaults "Secrets"]

6. **AC-6 — Just-in-time delivery, scoping, digests (I-A2, I-A3, F-7, F-10).** Backend `mayUse` is checked at session start (names only, before any browser; `SECRET_USE_NOT_AUTHORIZED`, zero Vault reads, no session row), at `prepareAndAdmit` (names only) and at dispatch (`resolve` + erase), through `VaultStudioReferenceResolver` with `VaultScope.of(csiId, environmentId, testId)` and the Run principal; a same-named secret under another CSI is `SECRET_UNAVAILABLE`, never the other value (SEC-2). The value travels only in the `BridgeDispatch.secret` of the admitted fill, built after `consume()` commits inside the resolution scope, never journaled, never in a retry buffer or idempotency store (C-2: exactly one `dispatch` frame carries it; no `context`/`prepare`/`observe`/`stop` frame does). The backend dispatch digest is computed without `secret`; the runner replay map strips `secret` before hashing — byte-identical bodies differing only in `secret.value` yield the same digest, a different `secret.secretId` yields `IDEMPOTENCY_CONFLICT` (C-15). The runner `withhold`s the value before the fill and drops the frame reference; `knownSecrets` scrubs any echo from the next observation (SEC-4 `/echo`); inventory and `knownSecrets` are wiped at `dispose()` and on `stop` (SEC-3). The guided mode asserts `capacity === 1` while secret fills are enabled (`CONFIGURATION_DENIED` otherwise) **or** a two-session cross-value isolation oracle passes — the implemented choice is stated in evidence (C-17). Observed replay keeps run-scoped delivery (all declared secrets resolved once at dispatch; per-step delivery rejected, design I-A2). [design §4.4, §4.6 I-A2/I-A3; F-7; F-10; security conditions 7, 9]

**Observed replay**

7. **AC-7 — Replay secrets through the ordinary dispatch pass.** Observed replay carries `job.secrets`/`job.secretOrigins`, resolved per run inside `ObservedReplayAuthorization.job()` within the ordinary dispatch pass; `Launch3` carries `scope` instead of deriving it from an account handle; the observed adapter performs the same origin check (`secretOrigins` per ID; absent list ⇒ bound to no origin) and the same password-only rule — the published `passwordControl` guard replayed against `/two-passwords` or `/no-password` ⇒ `POLICY_REFUSED`, nothing typed; replay is model-free (both gateways silent). The `requireSecretOrigin` implementation in `playwrightAdapter.ts` is **not** what the test cites (removed by OBS-012A). [design §3 `replay-job`/`replay-ipc` rows, §4.3, §4.6 I-A2/I-A3; oracle SEC-6 replay row, C-1]

8. **AC-8 — No value reads on password controls (F-6).** `hasValue`/`controlValue` reads on `type=password` controls are refused in the observed executor (learn and replay) with `PASSWORD_CONTROL_READ_REFUSED`; assertion failure text never embeds a password-control reading (`observed` omitted); a deliberately failing value assertion on a text control whose page shows the canary produces redacted failure text (C-14). [design §4.6 I-B5; security condition 6]

**Never logged — sink inventory**

9. **AC-9 — Backend sinks (I-B4, F-4).** A final `SecretValue` type wraps `char[]`, prints `<secret>` from `toString()`, has no Jackson-visible getter and is written only by one explicit writer (`JsonGenerator.writeString(char[],int,int)`) used by the two secret-bearing serializers (`HttpRunnerDispatchClient` body, guided `BridgeDispatch` builder) and replay `job()`, erasing after write; `RunJob.resolvedSecrets: Map<String,String>` and `text(resolved.secrets())` are replaced. The Vault read is parsed with a streaming `JsonParser` (`getTextCharacters`) straight into `char[]` — the secret path never calls `ObjectMapper.readTree`; bodies are published as `byte[]` (`ofByteArray`) and zeroed after send (test seams for both). Oracle C-5: with root and `com.citi.put.checks` at TRACE and every appender captured during a two-path controlled run (guided learn, observed replay), zero canary hits in logs, problem+json bodies, SSE frames, `/actuator/prometheus` and the `IdempotencyFilter` cache; `RunJob.toString()`/`SecretValue.toString()` print no value. Residuals (JVM `String` copies, Jackson/`HttpClient`/TLS buffers) are documented in the evidence file, not asserted. [design §4.6 I-B4, I-A2 read/write residuals; security condition 4]

10. **AC-10 — Runner sinks (I-B5, SEC-7, F-10).** A static test asserts `tracing.start`, `recordHar`, `on('console'` and `screenshot` stay absent from `studio-runner/src`. The guided mode runs a redactor built from the resolved values over stderr lines, journal diagnostic text and callback `errorMessage` (a test-only hook embedding the value yields `[REDACTED]`, SEC-7). Oracle C-6: a `/slow` fill timeout leaves zero canary hits in child stdout/stderr, relay output, step `failure`, manifest, callbacks, journal and parent log; `DEBUG=pw:*` set on the parent is absent from the child env and the run proceeds; Playwright's **raw** error text captured before the redactor contains the canary while every sink after it does not. [design §4 "Runner outputs", §4.6 I-B5; security condition 9]

11. **AC-11 — Browser profile disk sink (F-3).** Guided and observed-replay launches both use a persistent context in a per-run/per-session scratch directory containing a pre-written `Preferences` file (`credentials_enable_service=false`, `profile.password_manager_enabled=false`, `autofill.profile_enabled=false`, `autofill.credit_card_enabled=false`, `session.restore_on_startup=5`) — a file, not `args`, which the sandbox gate forbids; the launcher refuses to start without it (negative test). After a login Chromium would offer to save, the profile tree and the guided user-data directory are canary-scanned **before** `runScratch.clear()`/context close ⇒ zero hits (C-3). The residual (transient Chromium cache/session files during the run) is stated; evidence records the Chromium version the preference names were verified against. OBS-013 later makes this same context recorded. [design §4 "Browser profile"; security condition 3]

12. **AC-12 — One value bound; secrets API pin (F-5, I-B6).** `StudioSecretsService.MAX_VALUE_LENGTH` is lowered 8192 → 4096 at create (`INVALID_SECRET_VALUE` for 4097), bridge `secret.value` is 1..4096, the sanitizer bound stays 4096; a longer already-stored Vault entry is refused at dispatch with `SECRET_TOO_LONG`, never truncated (C-13); `allowedOrigins` bounds are unchanged. Contract tests pin the `StudioSecretsController` route set (`GET /tests/{id}/secrets` names only, `POST /tests/{id}/secrets` returning `{name, version, allowedOrigins}`; no read-value route, no PUT) and assert that no response schema in `openapi.yaml` or `openapi-v3.yaml` has a secret value property (C-7 backend half; MSW/UI half is OBS-008). [design §3 `bridge#dispatch` row, §4.6 I-B6; security condition 5 as reworded in the R1 delta]

**Authorization at release, revocation, audit**

13. **AC-13 — No stale frame; bounded post-release window; revocation (I-A3, F-2).** The verified dispatch ordering is preserved: resolve immediately before `send`; `AUTHORIZATION_REVOKED` closes with no send; a Vault outage releases the claim and the next pass re-resolves; a retryable definite refusal re-queues with a fresh `attempt_id` and re-resolves; an ambiguous send is never resent; guided recovery re-enters `admitAndDispatch → consume` and never sends a frame twice (C-4). New: a worker-side revocation sweep rechecks `mayUse` for every in-flight execution/session holding a released secret at the control-poll cadence and writes a write-once `revoked_at`; `ExecutionControl.revoked` is carried on the progress acknowledgement by the same path as `cancelRequested`; guided sessions receive `stop{reason: REVOKED}`; the run cancels within one control poll (bound stated as ≤ 2 s plus one in-flight step, never zero) with nothing typed and an audit row `REVOKED_MID_RUN`. Revocation between prepare and dispatch ⇒ `SECRET_USE_REVOKED`, zero sends. [design §4.6 I-A3; security condition 2 as tightened]

14. **AC-14 — Audit table and rows (SEC-9, I-C10).** `studio_secret_use_audit` is append-only (UPDATE/DELETE refused by trigger) with the §4.1 columns (`path ∈ {GUIDED, OBSERVED_REPLAY}`, `execution_id?`, `session_id?`, `admission_id?`, `principal_id`, `csi_id`, `environment`, `test_id`, `secret_id`, `vault_version?`) plus `row_kind ∈ {RELEASE, USAGE}`, `release_id`, `attempt_id`, `release_seq`, `coordinate_step_id` + `coordinate_ordinal`, and `outcome ∈ {RESOLVED, NOT_AUTHORIZED, REVOKED, UNAVAILABLE, VAULT_UNAVAILABLE, REVOKED_MID_RUN}`; never a value (canary scan of the table). Rows are written in the same transaction as the dispatch state change on both paths: one RELEASE row per release including every retry (two rows, two `attempt_id`s on a forced retry); one USAGE row per declared secret — guided joined from the ledger outcome by `admission_id`, replay from `RunnerReport.secretUse` — so a resolved-but-never-typed secret is `NOT_USED` (C-11). Retention: the existing retention pruner window (design §8 Q3 default). DDL authored by @data-engineer as `V34__studio_guided_secret_login.sql` on the **current** baseline; OBS-012A re-homes it into `V17__secret_use_audit` (ADR-SC-005 D-B). [design §4.1, §4.6 I-C10, §6 "Migration"; security review F-8]

**Login detection**

18. **AC-18 — `LOGIN_REQUIRED` on guided learn and observed replay (design R3 §5).** An annotation of a failure that already happened — it never turns a passing step into a failure or vice versa — with `detail:{stepId, loginStepsPresent}`. Signature S(observation), trusted code only, one function for both paths: `coverage.passwordControls ≥ 1` **and** an exported visible actionable node with `elementType ∈ {button, input}` or `role === 'button'`. Guided: `GuidedTranslationService` fires it when the step's attempt ended in a validator rejection, `INSUFFICIENT_EVIDENCE`/`MISSING_SOURCE`, or a `passwordControl` fill proposed without a `secretRef` input, **and** S holds; `loginStepsPresent` = a `secretRef` fill was dispatched earlier in the session; session → `FAILED`, `failure.code = LOGIN_REQUIRED`. Replay: `executor/observedReplay.ts` via the observed adapter, on the action that ends the run with `TARGET_DRIFT` or `POLICY_REFUSED`, when S(that observation) holds and the failing action is not itself a `secretRef` fill; `loginStepsPresent` = an earlier `secretRef` fill was performed; reported as `errorCode LOGIN_REQUIRED` with `detail:{stepId, loginStepsPresent}` in `x-runner-error-codes`; the run stays `FAILED` and the drift step is still named for "Learn again" (OBS-015). After login steps the next observation is of the reached document; login-page evidence is never reused for protected-page controls. False-positive limits (registration/change-password/CVV pages; custom forms without `type=password`; SSO on non-approved origins blocked earlier) are documented; localized button text is not used. Oracle (§7 "§5" row): `/reports` without login steps ⇒ `{loginStepsPresent:false}`, wrong password ⇒ `{true}`, registration page with passing assert ⇒ no annotation — on guided; the same three on a published plan with the fixture session expired between learn and replay. [design §5; §7 "§5" row]

### What the code does today (design §1, condensed)

Guided input kinds are `nonsecretText | destination` and require a value. `GuidedSourceClassifier` already parses `<secret ID>` and requires it declared but emits configuration references only for `var`; the change is emission, not parsing. Every guided start fails `AUTH_CONNECTION_REQUIRED`. `knownSecrets` is always `[]`; the collector merges/withholds and wipes on dispose; sanitizer bound 64 × 4096. The collector **never exports a password control as a node** — hence the node-free target. The ordinary dispatch pass resolves secrets at dispatch only, erases on every exit path, carries `secretOrigins`; it has no password-only rule and no login detection. The observed replay job carries `accountHandle`; V33 DB functions require account fields; `AWAITING_AUTH` is in the V30 CHECK. `translation.enabled` is dead unless set (two gates). No production guided data exists; publication and observed replay default off; the guided worker has no `CMD`/chart (OBS-009).

### Target flow (design §2)

```
author: "Enter <var USER> as username" / "Enter <secret PASS> as password" / "Click Sign in" / "Open reports"
  classify  → sourceReference{kind:secretRef, intendedSlot:fill.value, referenceName:PASS}; preflight mayUse + exists, no read
  plan      → model sees step text with the token span masked, the reference (ID), never a value
  materialize → authoredInputs += {kind:secretRef, secretId:PASS} (no value; hashed into authoredInputsHash)
  propose   → fill.value={kind:secretRef, sourceInputId}, target={kind:passwordControl, documentId, generation}
  prepare   → mayUse recheck (names only); trusted runner pins exactly one visible enabled input[type=password]
  dispatch  → backend resolve() from Vault (CSI/env/testId/principal), RELEASE audit row, BridgeDispatch.secret on mTLS bridge, erase
  act       → same pinned element re-proven in-world (attached, type=password, unique, origin, form.action), withhold BEFORE fill, fill via handle
  observe   → next observation is the reached document; knownSecrets scrubs any echo
  publish   → artifact fill value {kind:secretRef, sourceInputId}; inputRecipes {kind:secretRef, referenceName:PASS}; no value anywhere
  replay    → job.secrets/secretOrigins resolved per run (ordinary dispatch pass), same origin + password rule in the observed adapter, model-free
  stop      → knownSecrets = [], inventory disposed, dispatch frame not retained
```

### Trust boundaries in one paragraph (design §4)

The gateway sees IDs, never values (structural: the kind has no `value` field). The DB stores IDs, vault version identifiers and audit rows. The only value-bearing channels are `BridgeDispatch.secret` (guided, mTLS + RS256) and `Launch3/Execute3.secrets` (replay, the backend→runner hop that OBS-009 makes TLS with client-certificate authentication). Runner memory holds the value from the dispatch frame until `withhold` copies it into the private inventory; wiped at `dispose`/`stop`; no scratch file, argv or env ever carries it. The browser profile is a separate disk sink neutralised by the pre-written `Preferences` file and canary-scanned. Video shows masked dots only (password-only rule); a page that later echoes a secret in plain text is a stated residual. Runner free-text sinks pass a redactor built from resolved values. Transport gates G-1 (guided mTLS), G-2 (no real credential in Vault until every secret-bearing hop is TLS-authenticated) and G-3 (no scheduled secret-referencing run before production background/secret-use authorization sources exist) are OBS-009/OBS-010 items and are **not** closed by this story.
