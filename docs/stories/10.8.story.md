## User Story

**As a** Studio author whose English checklist is turned into executable Playwright source by a model I do not control,
**I want** compilation to happen once at authoring time, inside hard bounds, and execution to be gated on the exact revision I confirmed rather than on a status column,
**so that** a failed or slow compile can never take away a test I already approved and did not edit, an artifact that failed validation can never be confirmed or dispatched, and no run ever waits on — or pays for — a language model.

---

## Problem Statement

Every piece of the compile path exists except the pipeline that connects them, and the gate that decides whether a test may run.

| Available today | From |
|---|---|
| `CompileStateService` with five conditional transitions — `beginCompile`, `publishCandidate`, `publishInvalid`, `publishError`, `confirm` — each a conditional `UPDATE ... WHERE` whose affected-row count is asserted, over an immutable `ui_test_revisions` guarded by a write-once trigger | 10.4 |
| `LlmGatewayClient.propose(CompileRequest) → CompileResponse`, `studio.compile.gateway.enabled` defaulting to `false`, a resilience4j bulkhead and bounded transport retry, gax retries provably disabled, defensive parsing that pins `SUPPORTED_ARTIFACT_VERSION = 1` | 10.5 |
| Runner `POST /v1/validate` — browser-free schema/AST/policy validation with bounded work and per-step diagnostics; a rejected artifact is still a `200` | 10.6, ADR-002 |
| `SYNTAX_REFERENCE_VERSION`, `runtime-versions.json`, `isCompatible(provenance)`, a 28-example reference corpus and a 70-case adversarial corpus | 10.2, 10.3 |

Missing: `POST /tests/{id}/compile` (the frozen contract marks it `x-implemented-by: '10.8'`), prompt assembly, the asynchronous orchestration between gateway and validator, and the readiness predicate. `StudioService.executeTest` today accepts any execution of any test — its own javadoc says so: *"No live dispatch happens here: story 10.7 replaces this with the full acceptance transaction, quotas, readiness checks and the dispatcher."*

### The constraint this story exists to settle

Story 10.4's QA round left one issue open and pointed it here:

> **ISSUE-003** — `beginCompile` is unconditional on current status, so a failed optional recompile de-readies a previously confirmed, unedited draft (`READY → COMPILING → STALE`). AC-12 mandates the `STALE`, so this is AC-conforming — but **10.8 must settle whether readiness keys on `compile_status = 'READY'` or on `confirmed_revision_id` still matching the draft's revisions.**

It is settled here, and the sources settle it the same way. Architecture §4.6: *"Execute only when the current confirmed revision matches the draft's source/configuration revisions and artifact hash, all steps validated, and current target/runtime policy permits it."* Epic 10 §10.8's first acceptance bullet: *"Gateway outage leaves saved draft retryable and **unchanged confirmed tests runnable**."* Neither names the status column. A readiness predicate that reads `compile_status = 'READY'` would let a gateway outage revoke an approval nobody withdrew — which is precisely the failure the epic's acceptance bullet forbids.

So `compile_status` is the authoring UI's state and never a term of the gate. That is a load-bearing decision, not a detail: it is what makes an optional recompile *optional*.

### What must not be contradicted

10.4's fix round hardened three guards, and nothing here may weaken them: all three publish transitions condition on `configuration_revision` intrinsically (carried on `CompileRequest`), `confirm` requires `compile_status = 'AWAITING_CONFIRMATION'` as an explicit precondition, and `publishError` clears `current_candidate_revision_id`. This story consumes those methods; it writes no compile-state column itself.

## Acceptance Criteria

### Contract, draft-first, and transitions through the service only

- [ ] **AC-1:** `POST /api/v1/studio/tests/{id}/compile` is implemented exactly as the frozen contract declares it (`docs/specs/studio/openapi.yaml`, `operationId: compileTest`): `202` with `CompileAccepted {compileRequestId, compileStatus, sourceRevision, configurationRevision}`, plus `401`/`403`. **No response code the frozen route does not declare is added.** A contract test asserts the response body against the document and asserts the `x-not-yet-implemented` marker is removed for this operation only. **This story makes no edit to `docs/specs/studio/openapi.yaml`** beyond removing that one marker: under ADR-002 §12, a status code on a public operation is **Class C** — architect, always — and loosening is never a story's call.
- [ ] **AC-1b:** *(Escalated to @architect — ADR-002 §12 **Class C**; **not** implemented here.)* **Compiling a soft-deleted or quarantined test needs a `409` the frozen `compileTest` operation does not declare, and this story leaves the contract test red rather than inventing a code.** The divergence is real and verified on the branch: `CompileStateService.requireCompilable` already throws `StudioConflictException("TEST_DELETED", …)` and `("TEST_QUARANTINED", …)`, which surface as `409`, and AC-3 forbids any path that bypasses the service — so **no implementation of this route can both honour 10.4's guard and satisfy the document as written**. That is close to a Class A "nothing could have satisfied it" defect, but it lands as **Class C**: it changes status-code semantics on a public operation, `confirmCompile` and `executeTest` already declare the same `409`, and §12 gives routes and status codes to @architect without exception.
  What this story does, and nothing more: implement the route for every case the document *does* declare; leave the deleted/quarantined case **unimplemented and its contract test failing**, with an `it`/`@Disabled` naming this criterion and the referral; and escalate to @architect with the divergence demonstrated and a candidate shape (add `'409': { $ref: '#/components/responses/Conflict' }` to `compileTest`, with `TEST_DELETED` and `TEST_QUARANTINED` as the codes, matching the two operations that already carry it). **Three non-options, named so they are not quietly taken:** returning `403` — a deleted test is not an authorization failure and saying so would be a lie the frontend then has to un-learn; returning `202` and failing asynchronously — that begins a compile on a draft nobody may compile and spends a gateway call to say so; and widening `requireCompilable` so the case cannot arise — that is loosening a guard to stop a test telling the truth, which §12 names as the one manoeuvre whose only effect is to silence a failure. If @architect rules before wave 3 closes, the story picks the case up in the same PR; if not, the case is carried to 10.9, which owns `POST /tests/{id}/confirm-compile` and will meet the identical question on a route that already declares its `409`.
- [ ] **AC-2:** The draft is committed before any compile work begins. `POST /tests` and `PUT /tests/{id}` persist and commit the draft and return without waiting for the gateway (§8.3: *"persist draft and enqueue compile without waiting for gateway"*); no gateway call, no runner call and no outbound HTTP of any kind occurs inside the request thread or inside a database transaction. A test with a gateway stub that blocks until released asserts the save returns, the row is readable from a second connection, and the compile is still in flight.
- [ ] **AC-3:** Every compile-state transition goes through `CompileStateService`. The pipeline writes **none** of `compile_status`, `compile_request_id`, `compile_error`, `compile_diagnostics`, `current_candidate_revision_id`, `confirmed_revision_id` by any other path — no repository setter, no JPA dirty write, no ad-hoc SQL. A test scans the compile package's SQL and JPA surface and fails on any statement targeting those columns outside `CompileStateService`, and the state-machine tests are re-run to prove the conditional guards still fire.
- [ ] **AC-4:** The pipeline passes back the **exact** `CompileRequest` value returned by `beginCompile` and never a reconstructed one, so the conditional publish compares against the revisions the compile was actually started for. Out-of-order completion, **including two compiles of the same unedited source**, cannot publish an older candidate: a test starts compile A, starts compile B, completes B then A, asserts A returns `DISCARDED_OUT_OF_ORDER`, that B's candidate is current, and that no `ui_test_revisions` row was written for A. *(Epic 10 §10.8 acceptance bullet 2.)*

### Prompt inputs, authoring limits and credential patterns

- [ ] **AC-5:** Prompt assembly builds the gateway `CompileRequest` from exactly the three §4.3 inputs — the ordered draft source **fenced as data**, the versioned Playwright syntax reference, and the output/allowed-language contract — plus the metadata fields 10.5 already declares (`testId`, `csiId`, `principal`, `compileRequestId`, `attempt`, `promptVersion`, `syntaxReferenceVersion`). Secret and variable references stay opaque as `<secret ID>` and `<var NAME>`. **No resolved value is read on the compile path:** a test asserts the secrets service and the vault client are never called during a compile, and a canary planted in a stored secret value appears in no request payload and no audit line, in plain, URL-encoded, double-encoded or base64 form.
- [ ] **AC-6:** Authoring limits are enforced **before** a compile request is begun: maximum step count, maximum characters per source line, and maximum total source bytes (values in the bounds table under Implementation Notes, from one configuration source per §8.5). An over-limit draft is rejected at the API with `400` and a code; `beginCompile` is not called and no compile state changes. A test asserts the backend step cap is **not looser** than the runner's `DEFAULT_BOUNDS.maxSteps` (100), so no draft can be authorable and structurally uncompilable.
- [ ] **AC-7:** Known credential patterns are rejected before gateway submission (§4.3), with `400`, a code, and guidance pointing at vault references. The rejection message names the pattern class and the step index and **never echoes the matched text**. The user-facing copy, the javadoc and the README all state the limitation in the source's own terms — *"Pattern checks cannot detect every pasted secret and must not be described as a proof that arbitrary text is secret-free"* — and a test asserts no message in the module claims detection is complete.
- [ ] **AC-8:** The backend's pinned `syntaxReferenceVersion` equals `studio-runner/src/versions.ts` `SYNTAX_REFERENCE_VERSION`, asserted by a drift test built on the `ArtifactSchemaDriftTest` pattern (one canonical value, a second copy, a test that fails when they disagree). A drift fails the build rather than producing artifacts compiled against a reference the runner no longer implements.

### Gateway call, artifact parsing and version pinning

- [ ] **AC-9:** The pipeline calls `LlmGatewayClient.propose` **once** per compile attempt — repair attempts are 10.9's and this story issues none — and routes every non-`OK` `GatewayOutcome` to `publishError`: the draft stays saved and unchanged, `compile_status` becomes `STALE`, `compile_error` carries the bounded, scrubbed `GatewayErrorCode` and nothing else, and `current_candidate_revision_id` is cleared by the service. Each of `GATEWAY_UNAVAILABLE`, `GATEWAY_BUSY`, `GATEWAY_TIMEOUT`, `GATEWAY_TRANSPORT`, `GATEWAY_PARSE_FAILURE`, `COMPILE_INPUT_TOO_LARGE` and `GATEWAY_OUTPUT_TOO_LARGE` has its own case.
- [ ] **AC-10:** **The consumer pins its own executable artifact version.** `artifact.schema.json` deliberately constrains `version` to `integer, minimum 1`, so a future `version: 2` document is schema-valid; **schema validity is therefore not executability**. This pipeline accepts an artifact only when, after schema validation, `version == SUPPORTED_ARTIFACT_VERSION` (`= 1`, the pin 10.5's `GatewayResponseParser` already holds). A schema-valid `version: 2` artifact is rejected as a parse failure, is **never** written as a candidate revision and is **never** sent to `/v1/validate`; the pin is asserted by a test that constructs exactly that artifact. The candidate's `artifact_schema_version` column records the pinned version, and the readiness gate re-asserts it (AC-25).
- [ ] **AC-11a:** A compile runs end to end against a **stub gateway** returning recorded fixture artifacts: enqueue → `beginCompile` → prompt → stub `propose` → parse → `/v1/validate` (stubbed per AC-12a) → `publishCandidate` → `AWAITING_CONFIRMATION`, with the revision's provenance carrying the model, prompt, language-policy, syntax-reference, validator, executor and runtime-compatibility versions §8.1 requires. Fixtures are drawn from the 28-example reference corpus so the compiled artifacts are ones the validator is already proven to accept.
- [ ] **AC-11b:** *(Deferred — `ED-01`)* The same pipeline against the **real R2D2 gateway** with `studio.compile.gateway.enabled=true`. `ED-01` is `status: open` — no endpoint, credentials, project or verified model identifiers exist, and `docs/qa/spikes/SPK-01/` states plainly that the gateway *"must not be pointed at R2D2 … until every row in Findings is filled in"*. Verified in **story 10.19** (integrated staging validation), which `ED-01` also gates. Recorded as **skipped, not passed**; no shared environment sets `enabled=true` in this story.

### Validation, `NEEDS_REVISION` and what can never be confirmed

- [ ] **AC-12a:** The pipeline calls runner `POST /v1/validate` with a body conforming to the frozen **closed** `ValidateRequest` schema (`artifact`, `source`, `references`; an undeclared key is a `400` at the runner), carrying the restricted service identity §8.4 requires, against a configured runner base URL that is deployment configuration and never job- or user-supplied. **Exactly one call per compile attempt, with no automatic retry** and a bounded wall-clock timeout; a timeout, transport loss or `5xx` is a compile failure routed to `publishError` (`STALE`, retryable), not a reason to guess a verdict. Verified against a stubbed runner endpoint (WireMock) asserting request conformance and the one-call property.
- [ ] **AC-12b:** *(Deferred — deployment form only, `ED-05` / story 10.18)* The same call against a **deployed** `studio-runner` Service. To be explicit about what does and does not gate this story: `/v1/validate` is browser-free, takes no capacity slot and launches nothing, so **`ED-05` (the internal Playwright image) constrains none of this story's validation semantics** — AC-12a through AC-16 are fully verifiable now. What `ED-05` gates is only the existence of a deployable runner image to call in a shared environment, which arrives with **story 10.18** and is exercised in **10.19**. Recorded as **skipped, not passed** — the same division 10.3 recorded for its fixture tier and 10.6 for its real-identity check.
- [ ] **AC-13:** `ok: false` is a **verdict, not a transport failure** — the contract is explicit that a rejected artifact is still a `200`. It routes to `publishInvalid`: `NEEDS_REVISION`, with per-step diagnostics stored index-aligned, one entry per original step, artifact-level diagnostics kept separate from step diagnostics as the `ValidateResponse` separates them. A test asserts a `200 {ok: false}` never produces a `compile_error` and never retries.
- [ ] **AC-14:** **An invalid artifact can never become confirmable.** `publishInvalid` writes no `ui_test_revisions` row and leaves `current_candidate_revision_id` cleared, and `confirm` requires `AWAITING_CONFIRMATION` (10.4's ISSUE-002 fix). A test drives a draft to `NEEDS_REVISION`, then attempts `confirm` with (a) a fabricated revision id, (b) the id of a *previously* confirmed revision of the same test, and (c) the id of a candidate that a later compile superseded — asserting `409 STALE_CANDIDATE` in all three, no `confirmed_by`/`confirmed_at` write, and no change to `confirmed_revision_id`.
- [ ] **AC-15:** Diagnostics are bounded and redacted **before** they are handed to `publishInvalid`: at most N diagnostics per step, a maximum message length, a maximum excerpt length and a maximum total byte size (bounds table below, aligned with the runner's `maxDiagnosticsPerStep`, `maxDiagnosticMessageLength` and `maxExcerptLength`). Truncation is explicit in the stored structure, not silent. This closes the 10.4 LOW finding *"`compile_diagnostics` unbounded until 10.8"*. A test feeds a hostile validator response with thousands of oversized diagnostics and asserts the persisted JSONB is within the cap and the truncation marker is set.
- [ ] **AC-16:** A valid artifact becomes `AWAITING_CONFIRMATION` through `publishCandidate` and **never `READY`**. No path in this story sets `READY`; only `CompileStateService.confirm` does, and its HTTP endpoint is 10.9's. A test asserts that a full successful compile leaves `confirmed_revision_id` unchanged — including the case where the test was already confirmed before the recompile.

### Bounded compile work

- [ ] **AC-17:** Compile concurrency is bounded by a fixed-size executor with **no unbounded queue**, separate from request-serving threads. At saturation the compile is refused rather than queued indefinitely: the refusal routes to `publishError` (`STALE`, retryable, with a code), the request thread never blocks, and the `202` contract of AC-1 still holds because acceptance and execution are separate events. A test saturates the pool with blocked compiles and asserts the next compile lands `STALE` with the code, within a bound, while `POST /tests` and `GET /tests` stay responsive.
- [ ] **AC-18:** Each compile attempt has a **total wall-clock budget** covering prompt assembly, the gateway call, parsing, `/v1/validate` and persistence — distinct from, and larger than, the gateway's own `request-timeout`. On expiry the attempt is abandoned: `publishError` → `STALE` with a code, and **a late gateway or validator result from the abandoned attempt is dropped in-process without calling any publish method.** This is belt-and-braces on top of 10.4's conditional publish, which alone would still allow a late result to publish when nothing had moved on. A test releases a blocked stub *after* the budget expires and asserts no candidate is written and no further state change occurs.
- [ ] **AC-19:** Every bound has a named behaviour at the bound, and all values come from **one configuration source** (§8.5). The bounds table under Implementation Notes is normative for this criterion: for each row, a test drives the input past the bound and asserts the stated outcome. No bound is enforced only by a comment.
- [ ] **AC-20:** **The compile cache stays disabled in V1** (§8.5). No cache, no memoization and no keyed reuse of a gateway response exists: two compiles of byte-identical source issue two `propose` calls, asserted by a counting stub. This is distinguished in code and in the test name from 10.4's `insertOrReuseRevision`, which resolves an identical artifact to the existing revision row *after* the gateway has answered — that is artifact identity, not a cache. §4.3's requirements for a future cache (key over all ordered source/context/version inputs, isolate CSIs) are recorded in the README as not implemented.
- [ ] **AC-21:** **A gateway outage leaves the saved draft retryable and unchanged confirmed tests runnable** (§4.7; Epic 10 §10.8 acceptance bullet 1). One test covers both halves: with the gateway stub failing, a `PUT` saves the draft and the compile lands `STALE` with a `compile_error`; a *separate*, already-confirmed and unedited test still passes the readiness gate and its `POST /execute` is accepted throughout the outage.

### The readiness gate

- [ ] **AC-22:** **The readiness predicate is exactly this, and `compile_status` is not a term of it.** A test may execute if and only if, read consistently from the draft row and its confirmed revision:
  1. `deleted_at IS NULL` and `quarantined_at IS NULL`;
  2. `confirmed_revision_id IS NOT NULL` and resolves to a revision `r` with `r.test_id = test.id` and `r.csi_id = test.csi_id`;
  3. `r.confirmed_by IS NOT NULL` and `r.confirmed_at IS NOT NULL`;
  4. `r.source_revision = test.source_revision` **and** `r.configuration_revision = test.configuration_revision`;
  5. `r.source_hash` equals the canonical hash of the draft's current ordered `originalText`, computed with the single canonicalization helper 10.4 asked to be shared, and `r.artifact_hash` equals the canonical hash of `r.artifact`;
  6. `r.artifact_schema_version = SUPPORTED_ARTIFACT_VERSION`;
  7. the revision's recorded provenance is runtime-compatible under AC-25.

  Term 5 is deliberate belt-and-braces: revision counters are the primary guard, but a counter bug would otherwise let edited text run under an approved hash. A test asserts, by reading the gate's own query and by a mutation experiment, that **no value of `compile_status` changes any verdict** — the predicate is evaluated across all five states with everything else held fixed and returns the same answer each time.
- [ ] **AC-23:** **The de-ready case, stated as its own criterion because it is the story's reason to exist.** A confirmed, unedited draft whose *optional* recompile fails is driven `READY → COMPILING → STALE` by 10.4's deliberately unconditional `beginCompile` (its ISSUE-003; AC-conforming per 10.4 AC-12, and intended behaviour, not a defect). All of the following still pass the gate and are accepted for execution, on the revision originally confirmed:
  - `compile_status = 'STALE'` after a failed recompile of unedited source;
  - `compile_status = 'COMPILING'` with a recompile in flight;
  - `compile_status = 'NEEDS_REVISION'` after a recompile whose proposed artifact failed validation.

  Each is a separate test. A regression that reintroduces a `compile_status = 'READY'` check must fail all three.
- [ ] **AC-24:** Every negative readiness case returns `409 COMPILE_REQUIRED` with a message that says **what needs confirmation**, not merely that something is wrong: never confirmed; source edited since confirmation; configuration edited since confirmation (the §4.2 list: environment, variable values/references, viewport, timeout, browser, wait strategy, target policy selection — noting that 10.4's LOW findings record **target policy selection as still missing from `ConfigurationChangeClassifier`**, so either this story closes that gap or the case is recorded as not yet reachable, never as passing); a candidate awaiting confirmation that nobody confirmed; a name- or description-only edit **not** being a negative case. Soft-deleted and quarantined tests are refused by their own existing codes. One test per case.
- [ ] **AC-25:** Runtime compatibility is checked server-side and maps to `409 RUNTIME_INCOMPATIBLE`, closing the backend half of 10.3 AC-8. The backend gate owns the **exact-match** terms it can hold without duplicating a rule: `artifact_schema_version`, validator schema version and syntax reference version, compared against the configured runtime pin (§8.5). The **ranged** Playwright/executor terms stay with the runner's own `isCompatible` pre-launch revalidation (10.3 AC-7, §4.5) — one rule, one owner, no drift. A test proves a revision recorded under an older validator schema version is refused `409 RUNTIME_INCOMPATIBLE` on execute, naming the differing fields, and is preserved rather than reinterpreted or deleted (§4.6).
- [ ] **AC-26:** **Server enforcement is authoritative and unconditional.** The gate is a service consulted on the execute path before any dispatch effect; there is no auto-confirm fallback, no `permitAll`-style property, no profile and no feature flag that skips it. A test enumerates the configuration surface and asserts no key can disable readiness, and a second test asserts the gate is reached even when the request carries a client-supplied "already confirmed" hint, which is ignored.
- [ ] **AC-27:** **Unconfirmed, stale or incompatible revisions never reach a runner** (Epic 10 §10.8 acceptance bullet 3). For each negative case of AC-24 and AC-25, a test asserts the outcome is a `409` *and* that no admission request, no job body and no runner HTTP call of any kind was issued, using a counting runner stub. The assertion is on the wire, not on the return value.

### No runtime LLM

- [ ] **AC-28:** **No LLM call happens during execution** — an epic definition-of-done item (*"No runtime LLM call during execution"*) and §4.1's *"Compile on source changes or explicit recompile, never on execute."* Two independent parts, both required:
  - **(a) Structural.** A test asserts that no class outside `com.citi.put.checks.studio.compile` references `com.citi.put.checks.studio.compile.gateway`, so the execute, dispatch, readiness and snapshot paths cannot reach the gateway even transitively. It fails on the import, not on the call.
  - **(b) Behavioural.** A counting `LlmGatewayClient` stub records **zero** calls across a full accept → readiness → dispatch cycle for a confirmed revision, including the AC-23 states where the draft's `compile_status` is not `READY`.

### Audit, redaction and gates

- [ ] **AC-29:** Gateway audit records metadata only — test, CSI, user, model/prompt versions, latency, outcome — and never resolved values or full request bodies (§4.3, §4.7). This story adds no log site that carries source text, artifact source, resolved variables or secret values; the assertion is made on the **bytes handed to the log sink and to the HTTP client**, not on the objects that produced them, and covers the compile path's new sites as well as 10.5's existing `GatewayAuditLogger`.
- [ ] **AC-30:** `./gradlew check` is green from clean — spotless, checkstyle, spotbugs, jacoco — with the project's coverage thresholds met on the new compile-pipeline and readiness packages. Testcontainers integration tests cover the state transitions against a real PostgreSQL; the concurrency cases of AC-4, AC-17 and AC-18 are proven by **holding state open and interleaving**, not by sequential happy-path calls (the standard 10.4's QA round set and 10.6 followed). At least one falsification is recorded in the Dev Agent Record: with the readiness predicate changed to read `compile_status = 'READY'`, the three AC-23 tests must go red.

## Scope

### In scope
- `POST /tests/{id}/compile` and its acceptance path; enqueue-on-save wiring in `StudioService` for create and update.
- Asynchronous compile orchestration: bounded executor, per-attempt budget, abandonment, late-result drop.
- Prompt assembly, source fencing, authoring limits, credential-pattern rejection, the backend-held syntax reference and its drift guard.
- Artifact acceptance: schema validation plus the `SUPPORTED_ARTIFACT_VERSION` pin, canonical hashing, candidate construction including §8.1 provenance.
- The backend client for runner `POST /v1/validate`: configured base URL, service identity, bounded timeout, one call, no retry.
- Diagnostics bounding and redaction before `publishInvalid`.
- `ExecutionReadinessService` — the predicate of AC-22, the `409 COMPILE_REQUIRED` / `409 RUNTIME_INCOMPATIBLE` mapping and messages — supplied as the implementation of the `ExecutionReadiness` interface `10.7a` declares, replacing its provisional one, and wired into the execute acceptance path so the gate is live and provable in this story (`FOC-03`).
- Configuration keys for all of the above in one source, and the no-runtime-LLM structural gate.

### Out of scope — 10.9
- Repair attempts (the §4.3 maximum of two) and the repair prompt; this story issues one gateway call per compile and no repair.
- `POST /tests/{id}/confirm-compile` — the HTTP endpoint, its request validation and its `409` surface. This story exercises `CompileStateService.confirm` at the service layer only, to prove what cannot be confirmed.

### Out of scope — 10.7
- The execute acceptance transaction itself, durable idempotency, quotas, the dispatch ledger claim, leases, admission CAS, progress handlers, SSE, reapers and the kill switch. 10.8 supplies the readiness verdict that 10.7's transaction consults; it does not own the transaction.
- Any runner-side behaviour: admission, reporting, capacity, drain.

### Out of scope — elsewhere
- Frontend review, confirmation and run-gate surfaces (10.10, 10.11).
- Variable and secret resolution at dispatch (10.17). Compilation reads no resolved value at all (AC-5).
- Chromium, video, evidence and the durable manifest (10.12–10.16).
- Changes to `docs/specs/studio/openapi.yaml` or `artifact.schema.json`, beyond removing the one `x-not-yet-implemented` marker for `compileTest`. The contract is frozen and ADR-002 is binding; this story implements a route the document already declares, and the one place the document is wrong (AC-1b) is **escalated, not edited** — §12 gives status-code semantics on a public operation to @architect, always.
- Any Flyway migration. See the Implementation Notes entry on the one column this story would otherwise want.

### Why the frozen `202` survives a bounded pipeline

`compileTest` declares only `202`, `401` and `403`. Acceptance and execution are separate events: the `202` says the compile request was *recorded* — its identity is persisted by `beginCompile` and returned in `CompileAccepted` — not that a model was reached. Every bounded refusal downstream (pool saturation, gateway bulkhead, timeout, budget expiry) therefore surfaces asynchronously as `STALE` plus a `compile_error` that the authoring UI reads and the user retries. This is exactly the shape §4.7 already prescribes for a gateway outage, generalised to every bound, and it needs no undeclared response code. 10.5 independently reached the same conclusion for its own bulkhead: `GATEWAY_BUSY` is documented as *"the caller should retry later rather than queue"*.

### The one column this story would otherwise add — and does not

V12 fixed the `ui_tests` compile columns and there is no `compile_started_at` among them. That is enough for the in-process cases: the bounded executor holds each attempt's deadline in memory, so AC-18's abandonment and late-result drop work today. What it is **not** enough for is §4.7's *"Recovery of an abandoned compile request marks it retryable"* **across an API restart** — after a restart, a row left in `COMPILING` cannot be aged, because `updated_at` is bumped by any edit and says nothing about when the compile began.

Per the drafting constraint, **this story writes no migration and assigns no version.** The options, for @po and @architect:

1. A later story adds a `compile_started_at` (or equivalent) column and a bounded sweep that moves aged `COMPILING` rows to `STALE` with a retryable error.
2. Restart recovery is folded into 10.9, which already owns repair and is the natural home for "this compile is retryable".
3. Accept the gap in V1 and document it: a row stranded in `COMPILING` by a restart is cleared by the user's next explicit recompile, because `beginCompile` is unconditional on current status — the same property that causes AC-23's de-ready case also makes the stranded state self-healing on the next user action.

**@po ruling, 2026-09-11 — option 3 for V1, with the column carried forward to 10.9 as a named owner rather than left unassigned.**

Option 3 is chosen, and the reason it is cheap is a consequence of this story's own central decision rather than a hope. Because **readiness never reads `compile_status`** (AC-22), a row stranded in `COMPILING` by a restart **blocks nothing that matters**: the confirmed revision still executes, `POST /execute` is still accepted, and the only cost is an authoring-UI state that looks busier than it is until the user's next explicit recompile clears it — which `beginCompile` does unconditionally, the very property AC-23 exists to defend. A story that keyed readiness on the status column could not have taken this option at all; that it can is evidence the predicate is right.

So: **no migration, no version assigned, AC-18 stays scoped to the in-process case**, and the limitation is documented in the module README in the same honest terms AC-7 uses for credential patterns — a stranded `COMPILING` is a stale display, not a blocked test.

**Carried forward with an owner: option 1's `compile_started_at` column and its bounded sweep belong to 10.9.** 10.9 already owns repair and is the natural home for "this compile is retryable"; it is the next story to touch this surface; and it lands before the authoring UI (10.10) can complain. This is recorded as a carry-forward on 10.9 rather than a wish: if 10.10 or 10.11 finds that a permanently-spinning draft is unacceptable to a reviewer, the requirement is already owned and the migration is one column. It is **not** escalated to @architect — a nullable timestamp on a table V12 already owns is a story-level change, not an architecture one.

### Where the runtime-compatibility rule lives

There is one compatibility rule and it lives in the runner (`isCompatible`, 10.3 AC-7). Re-implementing its ranged Playwright/executor comparison in Java would create exactly the drift `ArtifactSchemaDriftTest` exists to prevent. So the backend gate holds only the **exact-match** terms — artifact schema version, validator schema version, syntax reference version — which are single-value comparisons against a configured pin and cannot drift into a different rule. The ranged terms are enforced by the runner's pre-launch revalidation, which §4.5 already requires and which runs before any browser launch. The division is stated here so that a future reviewer does not read the backend gate as incomplete.

### Two things that look like each other and are not

- **`insertOrReuseRevision` is not a cache.** 10.4 resolves an identical `(test_id, source_revision, configuration_revision, artifact_hash)` to the existing row rather than duplicating it. That happens *after* the gateway answered. A compile cache would avoid the call. AC-20 asserts the call still happens; name the test so the distinction survives.
- **`STALE` is not "not ready".** `STALE` describes the *draft's* relationship to its last compile. Readiness describes the *confirmed revision's* relationship to the draft's revisions. A confirmed, unedited test sits at `STALE` after a failed optional recompile and is fully runnable. If a reviewer finds this surprising, AC-23 is the criterion that exists to defend it and the epic's acceptance bullet is the source that requires it.

### Seams to watch

- **`StudioService` / `StudioController` overlap with 10.7 — now `FOC-03` in the manifest, and the ordering is mandated.** The draft was right to raise it: both stories are wave 3, both rewrite `StudioService` (382 lines) and `StudioController` (150 lines) on the execute path, and the manifest carried only wave-1 conflicts. **@po ruling, 2026-09-11: serialize on the two shared files; `10.7a` lands first; no single-ownership merge of the two stories.** 10.7 *replaces* `executeTest` wholesale, so landing this story's readiness wiring first means 10.7 deletes it and restores it by hand — and AC-26's whole point is that the gate is unconditional and unskippable, which is exactly the property a hand-restored merge loses without anyone noticing. Ordering is `10.7a` (dispatch, which carries the acceptance transaction and the readiness seam) → this story's gate wiring → `10.7b`/`10.7c`, which touch neither file. **Everything else here starts on day one:** the compile package, prompt assembly, authoring limits, the credential screen, the canonicalizer, the diagnostics bounder, the `/v1/validate` client, `ExecutionReadinessService` itself and the no-runtime-LLM gate share no file with 10.7, so only T-10.8.1's controller/service wiring and T-10.8.7's final injection actually wait. The mitigation the draft proposed — the predicate in its own injectable service — is kept and made binding: **10.7 declares the `ExecutionReadiness` interface plus a provisional implementation; this story supplies `ExecutionReadinessService` against that same interface and deletes the provisional one.** Neither story introduces a second type and the acceptance path is wired to the interface. See `FOC-03` in `EPIC-10-EXECUTION.yaml`.
- **Prompt version.** `promptVersion` is a required field on 10.5's `CompileRequest` and no source fixes its value. Introduce it as a pinned constant next to the syntax reference version, bumped deliberately, and record it in revision provenance (§8.1) — the model changing must never rewrite an existing revision (§4.6).
- **`references` on `ValidateRequest`.** The declared variable and secret **names** travel to the validator so it can check that `vars.get`/`vars.secret` calls correspond to the source. Names only; no values (§4.3, §9.2).

## PO rulings on the drafted open questions

1. **Wave-3 file ownership — RULED: serialize, `10.7a` first; recorded as `FOC-03` in `EPIC-10-EXECUTION.yaml`.** Not single ownership: 10.7 is the largest story in the epic and is itself now under a mandated three-way split, so folding this story into it would build one unreviewable merge out of two reviewable ones. Not parallel either — 10.7 *replaces* `executeTest` wholesale, so the reverse order has it delete and hand-restore this story's readiness wiring, and AC-26's unconditional gate is exactly the kind of property a hand-restored merge loses silently. The split is what makes serialization cheap: `FOC-03` names `10.7a` as the landing point, not all 47 of 10.7's criteria, so this story's gate wiring is not queued behind SSE and reapers. Only T-10.8.1 and T-10.8.7's final injection wait; the entire compile package starts on day one. The draft's own mitigation is kept and made binding — the predicate lives in its own injectable service, against an interface 10.7a declares, with no second type. Waves 1 and 2 each carried one such conflict (`FOC-01`, `FOC-02`) and both were real; raising this one before it bit was the right call and it is now recorded where wave planning will actually read it.
2. **`409` on the compile route — RULED: escalate to @architect as ADR-002 §12 **Class C**; scoped out of this story, left red.** Now criterion **AC-1b**. The divergence is verified, not suspected: `CompileStateService.requireCompilable` already throws `StudioConflictException` for `TEST_DELETED` and `TEST_QUARANTINED`, AC-3 forbids bypassing the service, and `compileTest` declares only `202`/`401`/`403` — so no conforming implementation exists. It is close to Class A, but a status code on a public operation is Class C and §12 admits no exception; `confirmCompile` and `executeTest` already declare the same `409`, which makes the amendment small and the precedent clear. The story therefore implements everything the document does declare, leaves this one case unimplemented with its contract test **failing and named**, and refers it — which is precisely the behaviour §12 codified after 10.6 did it and four divergences got ruled on instead of buried. Three non-options are named on the criterion so they are not quietly taken: `403` (a lie about why), `202`-then-fail-async (spends a gateway call to refuse a draft nobody may compile), and widening `requireCompilable` (loosening a guard to silence a test — the one manoeuvre §12 singles out). If no ruling lands before wave 3 closes, the case goes to 10.9, which meets the identical question on a route that already declares its `409`.
3. **Restart recovery of an abandoned compile — RULED: option 3 for V1; option 1 carried forward to 10.9 with a named owner.** Option 3 is cheap for a reason this story earned rather than assumed: because readiness never reads `compile_status` (AC-22), a row stranded in `COMPILING` blocks **nothing** — the confirmed revision still executes and `POST /execute` is still accepted; the only cost is an authoring display that looks busier than it is until the user's next explicit recompile, which `beginCompile` clears unconditionally. A story that keyed readiness on the status column could not have taken this option, so being able to take it is evidence the predicate is right. No migration, no version assigned, AC-18 stays scoped to the in-process case, and the limitation goes in the README in the same plain terms AC-7 uses for credential patterns. The `compile_started_at` column and its bounded sweep are **assigned to 10.9**, which already owns repair and retryability and lands before the authoring UI can complain — recorded as a carry-forward, not a wish. Not escalated to @architect: a nullable timestamp on a table V12 already owns is a story-level change.
