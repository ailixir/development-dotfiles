## User Story

**As a** put-checks backend developer persisting rows that reference a user (`created_by` columns on checks/reports/ui_tests/csi_systems per ARCH §7),
**I want** a `users` context that mirrors identity from Core's `/users/me` into the local `users` table on first-seen-session + updates `last_login` thereafter,
**so that** foreign keys to `users.email` (the platform's stable identifier per the BFF identity contract — story 1.4) resolve without a per-request round-trip to Core, and the `GET /users/me` endpoint on put-checks returns the same identity that's referenced across the domain tables.

---

## Context

The `users` table (ARCH §7.1) is a **local mirror**, not an alternate identity store. The authoritative identity is Core's `/api/v1/users/me`. This story populates the mirror so:
- FK integrity holds on `created_by` columns when rows are inserted.
- The module's `GET /api/v1/users/me` can return a stable shape including module-specific fields (preference cache, last module-interaction time) without calling Core every time.
- `last_login` tracks when a user most recently interacted with put-checks (module-level telemetry).

## Acceptance Criteria

- [ ] **AC-1:** `User` JPA entity at `backend/src/main/java/com/citi/put/checks/users/entity/User.java` maps to the `users` table defined in V1 (story 1.2). Fields: `id` (UUID), `sso_id` (platform user id), `name`, `email`, `department`, `created_at`, `last_login`, `is_active`.
- [ ] **AC-2:** `UserRepository` (Spring Data JPA) with `findBySsoId(String)` + `findByEmail(String)`.
- [ ] **AC-3:** `UserProvisioningService` exposes `provisionOrTouch(UserIdentity identity)`: if no row exists with `sso_id = identity.userId()`, insert a new row with `last_login=NOW()`; else update `last_login=NOW()`, `name`, `email`, `department` (in case any changed upstream). Runs in `@Transactional`.
- [ ] **AC-4:** An `@EventListener` on a platform event `UserAuthenticatedEvent` (emitted by `BffSessionAuthenticationFilter` from story 1.5 on successful identity resolution) invokes `provisionOrTouch` **asynchronously** on the `applicationTaskExecutor` (story 1.8) so the critical request path is not blocked by the write.
- [ ] **AC-5:** A `RateLimitedProvisioningWrapper` deduplicates provisioning calls within a 30-second window (same sso_id in-memory Caffeine gate) — prevents a burst of concurrent requests from each doing a redundant UPDATE.
- [ ] **AC-6:** `GET /api/v1/users/me` endpoint returns the authenticated user's mirror row (not the Core response verbatim) — module-level fields only. Returns `404` only if mirror provisioning has not yet happened (first request within the 30s window before async provisioning lands) — in that case, the response carries a `Retry-After: 2` header.
- [ ] **AC-7:** Sensitive fields (`email`, `name`) are masked in logs via the `MaskingPatternLayout` from story 1.1 — a unit test confirms a log line containing provisioning data does not leak raw email.
- [ ] **AC-8:** Integration test `UserProvisioningIT` (@SpringBootTest + Zonky) asserts: first call with new `UserIdentity` inserts a row; second call within 30s does NOT hit the DB (verified via a repository spy); second call after 30s updates `last_login`.
- [ ] **AC-9:** Integration test `UserMeEndpointIT` asserts `GET /users/me` returns the mirrored shape after provisioning completes.
- [ ] **AC-10:** JaCoCo coverage for the `users` package ≥ 80%.

## Implementation Notes (for @dev)

- **Event-driven vs. filter-embedded:** the provisioning call is triggered by an application event, not inline in the filter. This keeps 1.5's filter pure (identity resolution only) and 1.6's service pure (mirror management only). The event pattern also lets 1.6 be retried independently if provisioning fails (filter keeps serving requests — mirror catches up eventually).
- **30s Caffeine gate:** `expireAfterWrite(30s)`, `maximumSize(10_000)`. Key = `sso_id`. On cache hit, skip the write entirely.
- **Why async:** provisioning is a write; the request path is reads. Even a 5ms write on every request adds up. Keep it off the critical path.
- **Entity-level field masking:** prefer `MaskingPatternLayout` at the Logback level (from 1.1) over custom `@ToString` exclusions — fewer places to maintain.
