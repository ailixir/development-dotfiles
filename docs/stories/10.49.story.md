## Story

**As a** CSI owner and platform security/audit reviewer,
**I want** every V1 Run compile to be recorded as a compile request that the server itself stamps `trigger = RUN`, to be auto-accepted only under that trigger and for the principal who requested it, and to record truthfully on the revision that the confirmation was a Run confirmation rather than a reviewed one,
**so that** the C0-A3 conditions the shipped code does not meet (§35.2 table) are met, the deadline recheck stops passing vacuously, the audit can tell a reviewed confirmation from a Run confirmation, and the staged V19 cutover stops being a trap that would break every Run compile.

## Context (verified by the drafter by reading; nothing was run)

- **The ruling.** ADR-002 §35.2: Run is the confirming act (user decision DEC-OQ3, C0-A3 approved 2026-09-23), but the implementation meets only the principal condition and the identity/prefix condition. The "trigger", "`confirmationSource`" and "deadline recheck" conditions are not met (§35.2 table). §35.3: the v1 `POST /tests/{id}/compile` takes no body, so **the server stamps `trigger = RUN` on every v1 compile request; the route is the trigger**. Auto-accept may occur inside the compile's publication transaction.
- **The hazard.** Decision §2: applying `backend/db/cutover/V19__studio_inference_candidate_identity.sql` at HEAD breaks every V1 Run compile. `CompileStateService.beginCompile` (`:176-198`) writes only `ui_tests`; `publishAcceptedCandidate` (`:268-327`) calls `insertOrReuseRevision` (`INSERT_REVISION`, `:50-65`, no `compile_request_id`); V19's `trg_ui_test_revision_require_request` rejects a revision with `compile_request_id IS NULL`. The decision's own caveat: this is read from code and from `InferenceMigrationLatestIT:695-699`, **not executed**.
- **Vacuous deadline.** Decision §2, last bullet: the `deadline_at` term in `lockCurrentRequest` (`:722-723`) and in `publishCandidate`'s final CAS (`:241-243`) is `NOT EXISTS (… ui_test_compile_requests … deadline_at <= clock_timestamp())`, which is **vacuously true with no request row**. So the missing deadline recheck (§35.1 item 5a) is missing because the request row is missing, not only because a statement is absent.
- **Pre-V19 audit.** Decision §3 item 5b: before V19 the trigger is read "through `ui_tests.compile_request_id` under the publication lock" and `confirmation_source` is written on the revision.
- **Other defects listed by §35.1.** Item 5(b) `publishAcceptedCandidate` never uses `insertCapturedRevision`; item 5(c) its javadoc says "save-triggered" though no save path compiles; item 6 `NoAutoConfirmTest` skips `CompileStateService` (`NoAutoConfirmTest.java:107,252`) and its `contains("SET confirmed_by = ?, confirmed_at = NOW()")` check is satisfied by either statement; item 7 `compile/README.md:3-5,20,30,105` and the `CompilePipeline` class javadoc `:66-69` still say an explicit compile publishes `AWAITING_CONFIRMATION`.
- **Not verified (decision §2, §35.1 item 5b):** that `recordOutcome`'s `revisionId` lookup by `compile_request_id` is null today, and that `queryForObject` finds nothing through the captured branch with no request row. Both are *inferred* in the sources. @dev measures them in Task 1.
- **Latest migration.** `backend/src/main/resources/db/migration` ends at `V28__studio_execution_scope_immutable.sql` (verified); the decision (§4) fixes the next free number at **V29**. V19 is staged outside that directory (`backend/db/cutover/`) and is not part of the ordinary Flyway path.

## Acceptance Criteria

*(Numbering is this story's. Wording of the ruling is quoted from §35.5 and the decision; do not weaken it.)*

**A. Migration V29 (forward-only; DDL detail by @data-engineer)** — §35.5 item 1

1. **`trigger` on compile requests.** `ui_test_compile_requests.trigger` exists, is set by the server, is **immutable** after insert, and holds `RUN` for every V1 compile. The column may not be set from a request body or any client label (§35.3). *(@po, validation)* **Value set: `RUN`, `COMPILE_CHANGES`, `REBUILD_ALL`**, the closed set of C0-A3's approved wording (`c0-amendment-review.md` §4: "a server-captured, immutable `trigger ∈ {RUN, COMPILE_CHANGES, REBUILD_ALL}`"). No other value (in particular no `SCHEDULED` or `MANUAL`) is admitted. V1 code writes only `RUN`; the two v2 values exist so the column's domain is the contract's and AC-12 can seed one. Immutability is already enforced for every column of the table by V18's `trg_ui_test_compile_requests_immutable` (rejects any `UPDATE`/`DELETE`); a migration IT asserts that an `UPDATE` of `trigger` is rejected.
2. **`confirmation_source` on revisions.** `ui_test_revisions.confirmation_source` accepts `RUN` and `MANUAL`, is **write-once**, and is written together with `confirmed_by`. The V12 write-once trigger is amended so that the column is permitted as confirmation bookkeeping and cannot be rewritten afterwards. *(@po, validation)* The function in force is `ui_test_revisions_write_once()` in the deny-by-default form restored by **V27** (not V12's enumerated list). V27's header contract binds: do **not** redefine it with an enumerated column list; add `confirmation_source` to **both** the exclusion array (first `IF`) and the write-once check (second `IF`, alongside `confirmed_by`/`confirmed_at`), and add it to `InferenceMigrationLatestIT`'s mutable-column allow-list **in the same change**. A migration IT shows: first confirmation may set it; a second write, or a change of it on an already-confirmed revision, is rejected `23514`.
3. **No backfill.** Rows auto-accepted before the fix keep `confirmation_source = NULL` ("unknown"). They are never backfilled as `MANUAL` (§35.5 item 1). A migration test asserts a pre-existing confirmed revision reads `NULL` after V29.
4. **Forward-only and V19-compatible.** V29 is a normal Flyway migration; it does not touch, renumber or apply `backend/db/cutover/V19…`. The existing migration ITs (`InferenceMigrationLatestIT` and the head-schema suites) are run before and after and their results quoted; a changed result is explained.

**B. V1 compile-request capture** — decision §3 item 1a, §4 (i)

5. **Request row per compile.** `CompileStateService.beginCompile` writes a `ui_test_compile_requests` row for every V1 compile, **in the same transaction** as its existing `ui_tests` write, using the existing V18 columns (FULL plan, fingerprint, `deadline_at`) and carrying `trigger = RUN`. The compile target is always FULL; this story adds no incremental behaviour.
6. **No prompt change.** The change involves no `PROMPT_VERSION`, fingerprint or prompt-byte change (decision §4). A test (or the existing prompt-golden tests, cited by name) proves the prompt bytes for an unchanged test are identical before and after.
7. **Linkage.** The accepted revision is linked to its compile request through the `insertCapturedRevision` branch when the capability is present (decision 1a: "The revision is linked when the capability is present"). `ui_tests.compile_request_id` is set so the publication lock can read the request. The `recordOutcome` `revisionId` lookup by `compile_request_id` is measured: record in the Dev Agent Record whether it was null before (the §35.1 inference) and non-null after.

**C. Auto-accept conformance** — §35.5 item 2, §35.2 table, decision §4 (ii)

8. **Auto-accept only when conformant.** `publishAcceptedCandidate` auto-accepts **only** when the request's `trigger = RUN` **and** the confirmer equals the request's `created_by` (today `candidate.createdBy()`). Any other case publishes through `publishCandidate`, i.e. `AWAITING_CONFIRMATION`.
9. **Deadline recheck on the accepted path.** The accepted path gains `publishCandidate`'s deadline recheck (`:212`, `:222`, `:228`, `:243`) and its `insertCapturedRevision` branch (`:224-225`). Reusing that path and adding the two confirmation statements is "the expected shape" (§35.5 item 2); another shape is allowed if every criterion here still holds.
10. **Source written.** Run auto-accept writes `confirmation_source = RUN`; the manual `confirm` writes `MANUAL`. Both write it together with `confirmed_by`/`confirmed_at`.
11. **Behavioural: expiry now refuses.** A test that is red on unmodified HEAD for the right reason: a V1 compile whose request is past `deadline_at` at the final CAS is **refused** on the accepted path (no revision published, no `READY`), where HEAD passes it because no request row exists (decision §2). The test inserts a real request row; it does not rely on the vacuous `NOT EXISTS`.
12. **Behavioural: non-RUN publishes `AWAITING_CONFIRMATION`.** A test seeds a request whose `trigger` is `COMPILE_CHANGES` (a value the AC-1 domain admits; no constraint bypass) and shows the candidate is published `AWAITING_CONFIRMATION`, not auto-accepted (§35.5 item 3). *(Open question 1, resolved at validation.)*
13. **Behavioural: confirmer ≠ requester.** A test shows that when the confirmer differs from the request's `created_by`, the compile is not auto-accepted.
14. **Identity binding unchanged.** The request/revision guard (`lockCurrentRequest`) and the reference-policy check (§35.2 table, "Met" rows) still hold; their existing tests stay green.

**D. Guard test rewritten** — §35.5 item 3

15. **`NoAutoConfirmTest` rewritten to the new property:** *exactly two confirmation writers exist — the manual `confirm` and the Run auto-accept.* The scan **includes the SQL inside `CompileStateService`**, which closes the vacuity (§35.1 item 6). The old `contains("SET confirmed_by = ?, confirmed_at = NOW()")` check is replaced by one that distinguishes the two statements.
16. **Mutation proof.** Temporarily adding a third `confirmed_by` writer (or removing the `trigger = RUN` condition from the auto-accept) turns a named test red; source restored and proven byte-identical by `shasum -a 256` before and after, output quoted. A test that stays green under the mutation does not satisfy this criterion.
17. **10.9 AC-21 is superseded** by the ADR-002 §35 ruling. §35.5 item 3 says its owner records that and the ADR does not edit the story: the Change Log of this story records the supersession, and @po records it on 10.9 at validation.
