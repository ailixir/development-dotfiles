## User Story

**As a** user configuring checks that need credentials (API keys, tokens),
**I want** secret management (list, create, resolve) backed by the real backend,
**so that** secrets are stored securely and resolved at execution time without exposing values in the frontend.

---

## Acceptance Criteria

### Backend — New SecretsController

- [ ] **AC-1:** `SecretsController` created at `/api/v1/secrets` with 2 user-facing endpoints.

- [ ] **AC-2:** `GET /api/v1/secrets` — list secret metadata (never returns values). Response: `{data: [{id, label, scope, last4, createdAt, expiresAt}]}`. Authorization: authenticated. Scope filter: `project` (visible to all project users), `org` (visible to org members), `user` (visible only to creator).
- [ ] **AC-3:** `POST /api/v1/secrets` — create secret. Body: `{label, scope, value}`. The `value` is encrypted and stored. Response: `{id, label, scope, last4, createdAt}` — value echoed ONLY on creation response (one-time visibility). Returns 201.
- [ ] **AC-4:** Internal-only endpoint: `POST /api/v1/internal/resolve-secret` — body `{id}`. Returns `{id, value}` (decrypted). This is server-to-server only — not called by the frontend. Protected by a separate authorization check (e.g., only callable from the execution context, not from user requests). For M3, a simple check like `request.getRemoteAddr() == "127.0.0.1"` or a service-to-service token.

**Data model**
- [ ] **AC-5:** `Secret` JPA entity mapping to `secrets` table: id (VARCHAR PK, format `sec_{random}`), label, scope (ENUM: project, org, user), encrypted_value (bytea), last4 (VARCHAR 4), created_by, created_at, expires_at (nullable).
- [ ] **AC-6:** Encryption: AES-256-GCM using a key from environment variable (`CHECKS_SECRET_ENCRYPTION_KEY`) or Vault in production. For local profile, use a hardcoded dev key (clearly marked as dev-only).

**Service + repository**
- [ ] **AC-7:** `SecretsService` with: `list(UserIdentity)`, `create(CreateSecretRequest, UserIdentity)`, `resolve(String secretId)`.
- [ ] **AC-8:** `SecretsRepository` extends JpaRepository with scope-based visibility query.

**Tests**
- [ ] **AC-9:** Integration tests: `SecretsCrudIT` (create returns value once, list never returns value, last4 correct), `SecretsVisibilityIT` (scope-based filtering), `SecretsResolveIT` (internal resolve returns decrypted value).

### Frontend — Wire secrets

- [ ] **AC-10:** New `secretsApi.ts` service created (or update existing) with `listSecrets()` and `createSecret(label, scope, value)`.
- [ ] **AC-11:** Secret-related UI components (if any — check creation form, Studio variable binding) updated to call `secretsApi`.
- [ ] **AC-12:** FE never calls resolve-secret — that's server-side only.
- [ ] **AC-13:** `VITE_DISABLE_MSW_DOMAINS` updated to include `secrets`.
- [ ] **AC-14:** `npm run type-check` passes. `./gradlew check` passes.
- [ ] **AC-15:** Secret creation + list verified in browser.

## Implementation Notes

### Encryption approach (M3 — local dev)
```java
@Service
public class SecretEncryptor {
    private final SecretKey key;
    
    public SecretEncryptor(@Value("${checks.secrets.encryption-key}") String base64Key) {
        byte[] decoded = Base64.getDecoder().decode(base64Key);
        this.key = new SecretKeySpec(decoded, "AES");
    }
    
    public byte[] encrypt(String plaintext) { /* AES-GCM */ }
    public String decrypt(byte[] ciphertext) { /* AES-GCM */ }
}
```

### Scope visibility query
```sql
SELECT id, label, scope, last4, created_at, expires_at
FROM secrets
WHERE (scope = 'project')
   OR (scope = 'org' AND created_by IN (SELECT email FROM users WHERE department = :userDept))
   OR (scope = 'user' AND created_by = :userEmail)
ORDER BY created_at DESC
```
