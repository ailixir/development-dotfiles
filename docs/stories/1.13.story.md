## User Story

**As a** put-checks user whose flaky network might retry a `POST /execute`,
**I want** the backend to honor an `Idempotency-Key` header by deduplicating requests within a 5-minute window,
**so that** a network hiccup doesn't kick off two executions against the same check + an accidental double-send of a scheduled report doesn't spam the recipient list twice.

---

## Acceptance Criteria

- [ ] **AC-1:** `IdempotencyFilter` (OncePerRequestFilter, ordered AFTER `BffSessionAuthenticationFilter` from 1.5, BEFORE `RateLimitFilter` from 1.15) intercepts requests where HTTP method is one of `POST`, `PUT`, `PATCH`, `DELETE` AND path matches `/api/v1/checks/**`, `/api/v1/reports/**`, `/api/v1/studio/**`, `/api/v1/schedules/**`, `/api/v1/checks/_bulk`.
- [ ] **AC-2:** The filter checks for an `Idempotency-Key` header. If absent: pass through without dedup (idempotency is opt-in for clients). If present: normalize to UUID format (enforce format; 400 with clear error if malformed).
- [ ] **AC-3:** Cache key = `(Idempotency-Key, userId)`. Caffeine, TTL 5 minutes, max 50_000 entries.
- [ ] **AC-4:** On cache miss: proceed with the request; on successful completion (2xx OR 5xx — both are cacheable deterministic outcomes), store the serialized response (status + headers + body) in the cache. On cache hit: return the cached response verbatim.
- [ ] **AC-5:** 4xx responses are **NOT cached** — user-correctable errors (400 bad request, 403 auth, 404) might be legitimately different on retry (user fixed input).
- [ ] **AC-6:** Cached responses include an `Idempotent-Replayed: true` response header (so clients can optionally log it). Original response does NOT have the header.
- [ ] **AC-7:** If a request with the same Idempotency-Key arrives while the original is still in-flight (not yet cached), the second request waits up to 30s for the first to complete + serves the cached result. After 30s: return 409 Conflict with error "Idempotent request in progress; try again later".
- [ ] **AC-8:** Headers stripped before caching: `Cookie`, `Authorization`, `Set-Cookie` — prevent leaking sensitive transport-level state across clients (even within the same user's session, which shouldn't happen, but defense in depth).
- [ ] **AC-9:** Metric `checks_idempotency_{hits|misses|in_flight_conflicts}_total` (counter).
- [ ] **AC-10:** Integration tests: `IdempotencyFirstCallIT` (miss path → 200 + cached), `IdempotencyReplayIT` (hit path → 200 + `Idempotent-Replayed: true`), `IdempotencyMalformedKeyIT` (400), `Idempotency4xxNotCachedIT` (retry of a 400 gets re-evaluated), `IdempotencyInFlightConflictIT` (with latch: second request waits then gets result), `IdempotencyExcludedRoutesIT` (GET / read routes pass through regardless of header).
- [ ] **AC-11:** JaCoCo coverage ≥ 80%.

## Implementation Notes

- **Serialization format:** JSON wrapper containing `{status, headers: allowedMap, body: base64}`. Body base64-encoded so cache doesn't need content-type awareness.
- **In-flight conflict logic:** use a `ConcurrentHashMap<String, CompletableFuture<CachedResponse>>` alongside the Caffeine cache. First request puts a future; second request finds the future + awaits.
- **5-minute TTL:** enough for retry scenarios without keeping state forever. Clients that genuinely want idempotency for longer can retry with a new key.
