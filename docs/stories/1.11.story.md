## User Story

**As a** put-checks user inspecting a check's recent runs,
**I want** `GET /checks/{id}/history` to return cursor-paginated execution results + `GET /checks/{id}/executions/{execId}` for a single run, backed by an atomic write path that also cascades the latest status to `checks.status` via the §7.4 trigger,
**so that** the dashboard's recent-activity feed populates with real data and `checks.status` always reflects the most recent execution without requiring a separate UPDATE from the application.

## Acceptance Criteria

- [ ] **AC-1:** `ExecutionResult` JPA entity maps the `execution_results` table (ARCH §7.1). Partitioned table support via Hibernate: standard INSERTs target the parent; PG routes to the current-month child automatically (no app-level routing).
- [ ] **AC-2:** `ExecutionResultRepository` with cursor-friendly query methods: `findRecentByCheckId(UUID checkId, Instant before, int limit)` returning ordered by `started_at DESC`.
- [ ] **AC-3:** `ExecutionPersistenceService.persistResult(Check, ExecutionOutcome, Instant startedAt, Instant endedAt)` runs in `@Transactional(propagation=REQUIRES_NEW)` — isolated from the caller's transaction so a failing persist doesn't abort the calling flow (e.g., async execute in 1.12).
- [ ] **AC-4:** The §7.4 DB trigger (defined in V1 from story 1.2) auto-updates `checks.status` + `checks.last_execution_at` + `checks.last_execution_id` when a row is INSERTed into `execution_results`. Integration test verifies the cascade happens atomically (within the same TX as the INSERT).
- [ ] **AC-5:** `GET /api/v1/checks/{id}/history` — cursor-paginated (per spec §6.1): `?cursor=<opaque>&limit=20`. Response envelope includes `nextCursor`, `hasMore`; `total` intentionally omitted (O(N) scan on 1M+ rows).
- [ ] **AC-6:** The cursor is opaque (base64-encoded `(startedAt, id)` tuple) — does NOT leak primary key sequences + prevents bad clients from writing cursor math.
- [ ] **AC-7:** `GET /api/v1/checks/{id}/executions/{execId}` — single result fetch. `404` if execution doesn't belong to the given check.
- [ ] **AC-8:** `@PreAuthorize("@csiOwnershipEvaluator.canRead(authentication, #checkId)")` on both endpoints.
- [ ] **AC-9:** `ExecutionResultDto` + mapper. `errorMessage` included for failures; `output` optional (may be large).
- [ ] **AC-10:** Integration tests:
  - `PersistenceIT`: persist outcome → verify row inserted → verify trigger cascaded checks.status.
  - `HistoryCursorIT`: insert 50 rows, paginate 5 pages of 10 with cursor; assert ordering + no duplicates.
  - `HistoryPerformanceIT`: insert 10k rows in the current-month partition; page 1 fetch P95 < 100ms (catches regression if someone drops the `(check_id, started_at DESC)` index).
  - `AuthzIT`: unauthorized user gets 403 on history + single fetch.
- [ ] **AC-11:** JaCoCo coverage for `checks.execution` (or wherever this lives) ≥ 80%.

## Implementation Notes

- **Cursor encoding:** `Base64(startedAt.toEpochMilli() + ":" + UUID.toString())`. Small, opaque, tamper-resistant (clients can't manipulate meaningfully without breaking base64).
- **REQUIRES_NEW rationale:** if the caller (1.12's async execute) has an outer transaction for request handling, a rollback of that shouldn't undo the execution history write. Persistence is a fact; request handling is ephemeral.
- **Partition pruning:** cursor queries with `started_at` predicates get partition-pruned by PG 15 at execution time (PG-05). Verified in `HistoryPerformanceIT` — if a reviewer notices the perf test failing, first check EXPLAIN plan for partition pruning.
