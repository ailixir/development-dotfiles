## User Story

**As a** platform operator deploying put-checks to production,
**I want** each check source (HTTP, TCP, Splunk, Grafana, ITRS, AppDynamics, UI_TEST) gated by a feature flag in backend configuration,
**so that** only sources with working backend executors are available to users, and new sources can be enabled by changing a config property when their executors ship — without a code deployment.

## Acceptance Criteria

### Backend

- [ ] **AC-1:** New `@ConfigurationProperties("checks.sources")` class `CheckSourceProperties` with:
  ```yaml
  checks:
    sources:
      HTTP: true
      TCP: true
      SPLUNK: false
      GRAFANA: false
      ITRS: false
      APPDYNAMICS: false
      UI_TEST: false
  ```
  All 7 `CheckType` values must appear in the map. Missing keys default to `false`. Property names match the `CheckType` enum exactly (case-insensitive binding by Spring Boot).

- [ ] **AC-2:** New endpoint `GET /api/v1/checks/sources` returns the enabled sources:
  ```json
  {
    "sources": [
      { "type": "HTTP", "enabled": true, "label": "HTTP/HTTPS Check" },
      { "type": "TCP", "enabled": true, "label": "TCP Port Check" },
      { "type": "SPLUNK", "enabled": false, "label": "Splunk Query" },
      { "type": "GRAFANA", "enabled": false, "label": "Grafana Metrics" },
      { "type": "ITRS", "enabled": false, "label": "ITRS Geneos" },
      { "type": "APPDYNAMICS", "enabled": false, "label": "AppDynamics APM" },
      { "type": "UI_TEST", "enabled": false, "label": "UI Test (Checks Studio)" }
    ]
  }
  ```
  Unauthenticated — this is a configuration discovery endpoint (no auth required, like OpenAPI spec).

- [ ] **AC-3:** `CheckService.create()` rejects check creation for disabled sources with `400 Bad Request`:
  ```json
  { "error": "CHECK_SOURCE_DISABLED", "message": "Check type SPLUNK is not available. Available types: HTTP, TCP" }
  ```

- [ ] **AC-4:** `CheckExecutorDispatcher.dispatch()` rejects execution for disabled sources with `409 Conflict` (check exists but source was disabled after creation):
  ```json
  { "error": "CHECK_SOURCE_DISABLED", "message": "Check type SPLUNK is currently disabled" }
  ```

- [ ] **AC-5:** `DashboardService` excludes disabled-source checks from attention items, activity, and summary counts. Existing checks of disabled types remain in the database but are treated as "muted" in aggregations.

- [ ] **AC-6:** Metric `checks.sources.enabled{type}` gauge (1 or 0 per type) emitted at startup and on `@RefreshScope` if cloud config is wired later.

- [ ] **AC-7:** Default config in `application.yml` enables only HTTP and TCP. Profile overrides can enable additional sources (e.g., `application-staging.yml` could enable SPLUNK for testing).

### Frontend

- [ ] **AC-11:** `AllChecksPage` — if a check's type is disabled, show a muted badge ("Source disabled") next to its status. Execution and schedule actions are disabled for these checks.

- [ ] **AC-12:** MSW mock handler for `GET /api/v1/checks/sources` returns all types enabled (preserves current development experience). When MSW is disabled (story 1.17), real backend response takes over.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| **R-1: Fail-open FE exposes disabled types** — if `/sources` endpoint is unreachable, FE shows all types as enabled; user creates a SPLUNK check that backend rejects at save | LOW | Backend gate (AC-3) is the authoritative guard. FE fail-open only affects UX (user sees form, gets 400 on submit). Acceptable for dev; prod will have the endpoint available |
| **R-2: Config drift between environments** — staging enables SPLUNK=true for testing, but production config is never updated when executor ships | MEDIUM | AC-6 metric gauge `checks.sources.enabled{type}` enables alerting on config mismatch between environments. Document in runbook |
| **R-3: Orphaned checks after source disable** — if a source is disabled after checks of that type already exist, those checks become un-executable | LOW | AC-4 returns 409 (not 500) with clear message. AC-5 mutes them in dashboard. AC-11 shows "Source disabled" badge. User can still view/delete them |
| **R-4: Label drift** — labels in `/sources` response vs FE `checkTypes` array can diverge | LOW | Implementation Notes specify labels match. AC-2 defines canonical labels. FE can prefer server labels in future story |

## Implementation Notes

- **Config pattern:** follows existing `checks.rate-limit.*` and `checks.scheduling.*` convention under the `checks:` namespace. Spring Boot's relaxed binding handles `checks.sources.UI_TEST` vs `checks.sources.ui-test` transparently.
- **Label source of truth:** labels in the `/sources` response match the frontend `checkTypes` array. If we later want server-driven labels, this endpoint is the right place.
- **Dashboard muting:** disabled-source checks are excluded from `attention` and `summary.counts` but still appear in `AllChecksPage` (with muted badge) so users can see them and decide to delete.
- **No DB migration needed:** this is purely config + application logic.
- **Graceful degradation:** if `/sources` endpoint fails, frontend falls back to showing all types as enabled (fail-open for dev experience, fail-closed only at backend create/execute).

## Dev Notes

**@dev (Dex) · 2026-04-28**

### Implementation Decisions
- Used `@ConfigurationProperties("checks")` on a record, re-using the existing `checks:` namespace. The `sources` field binds to `checks.sources.*` in YAML. Spring Boot relaxed binding handles both `checks.sources.UI_TEST` and `checks.sources.ui-test`.
- Created two separate `CheckSourceDisabledException` classes: one in `checks/` (for creation, returns 400) and one in `checks/executors/` (for dispatch, returns 409). This keeps the exception semantics close to their origin.
- Added `ChecksExceptionHandler` (`@RestControllerAdvice`) since no global handler existed. Also maps `IllegalArgumentException` → 400 for consistency.
- `SecurityConfig` updated: `GET /api/v1/checks/sources` is `permitAll()` (ordered before `/api/**` → `authenticated()`).
- FE `sourcesSlice` dispatched at bootstrap in `store/index.ts`. Fail-open: if rejected, populates all 7 types as enabled.
- Studio guard uses a wrapper component pattern (`ChecksStudioPage` → `ChecksStudioPageInner`) to avoid hooks-before-return violation.

### Test Results
- **Backend unit tests:** 9/9 PASSED (CheckSourcePropertiesTest: 5, CheckServiceSourceGateTest: 2, DispatcherSourceGateTest: 2)
- **Frontend unit tests:** 6/6 PASSED (sourcesSlice.test.ts)
- **Existing executor tests:** 6/6 PASSED (HttpExecutorIT — no regression)
- **Integration tests (AC-14):** BLOCKED by pre-existing Zonky EmbeddedPostgres `initdb` failure (35 tests affected across all IT suites, not specific to this story). These tests pass when run individually but fail in parallel due to resource exhaustion.

### Known Issues
