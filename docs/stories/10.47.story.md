## Story

**As a** maintainer who relies on `tools/corun.sh` as the integrated evidence that the API and the studio-runner work together,
**I want** the eleven co-run legs to follow the compile flow the product has today (compile publishes `READY` with the revision already accepted, then the test runs) instead of waiting for an explicit confirm step that compile no longer has,
**so that** the co-run reports 11 of 11 again, its evidence for cancel, recovery and a real passing run is current rather than silently unverified, and a red leg means a product defect rather than a stale harness.

## Context (verified by the drafter unless marked)

- **Observed (10.35 gate, both iterations, `tools/corun.sh`):** `legs executed: 11 · failures: 8 · errors: 0 · skipped: 0`. Green: legs 0, 2, 3. Red: leg 1 and legs 4 to 10, all with `the draft did not become confirmable — compile_status is READY`, `compile_error=null`, gateway calls 1, validator calls 1. The compile succeeds; the harness waits for a state it no longer produces.
- **Cause (read in code):** `CompilePipeline` line ~369 calls `compileStateService.publishAcceptedCandidate(...)` unconditionally on a validated candidate. `publishAcceptedCandidate` inserts the revision, sets `confirmed_by`/`confirmed_at`, and publishes `READY` in one transaction. Introduced by `554277fcb` ([Story 10.44]; `git log -S publishAcceptedCandidate -- backend/src/main` returns only that commit — *path filter added by @po: without it the command also returns four docs/checkpoint commits*). The method javadoc at `CompilePipeline.java:148-149` gives the rationale: *"a second confirmation step would ask the same question twice."*
- **Harness sites (read at drafting, line numbers may drift):** `StudioCoRunIT.java` waits on `Set.of("AWAITING_CONFIRMATION", "NEEDS_REVISION", "STALE")`, throws `CoRunFailure` unless the status is `AWAITING_CONFIRMATION`, and then calls `states.confirm(...)` in exactly three places: leg 1 (`:408-449`), `runATrivialPassingTestToPassed` (`:618-634`, used by legs 4 and 10) and `confirmedStallTest` (`:1048-1064`, used by legs 5 to 9). Leg 2 is green only because `confirmed_revision_id` is already set by the auto-accept.
- **Not verified:** whether legs 4 to 10 pass once past the compile helper. Per the gate (OBS-H1) they are **unverified on this tree, not proven broken**: the PASSED/DONE run (leg 4), the five cancel legs (5 to 9) and the recovery proof (leg 10) have not executed on this tree.
- **Observed, not in scope (the contract is not uniformly documented).** `compile/README.md:20,105` and the class javadoc at `CompilePipeline.java:68` still describe explicit compiles publishing `AWAITING_CONFIRMATION`, and `NoAutoConfirmTest` (Story 10.9 AC-21, "no production auto-confirmation") scans for the opposite property. ## Acceptance Criteria

1. **Each of the eight red legs passes, or is explicitly retired.** In one `tools/corun.sh` run on a committed tree, leg 1 and legs 4, 5, 6, 7, 8, 9, 10 of `StudioCoRunIT` each either pass, or are removed/disabled **only** with a named ruling reference (an ADR section or a @po/@architect ruling recorded in the story's Change Log, by id and date) that says why the leg no longer applies. A leg that is simply skipped, `@Disabled` without that reference, or loosened until green does not count. The report line must be consistent with the outcome: `legs executed: 11 · failures: 0` if none is retired, otherwise the retired legs are named in `tools/corun.sh`'s header and in the Dev Agent Record.
2. **The harness asserts the current flow, not the removed confirm.** After `pipeline.compile(...)`, leg 1 and the two shared helpers (`runATrivialPassingTestToPassed`, `confirmedStallTest`) wait for `READY` (with `NEEDS_REVISION` and `STALE` still accepted as terminal so a bad compile fails fast with its attribution) and fail with the existing `CoRunFailure` attribution unless the status is exactly `READY`. No call to `states.confirm(...)` remains in the co-run package. What the old confirm step used to prove is kept as direct assertions: a candidate/accepted revision exists; `ui_tests.confirmed_revision_id` equals that revision; the confirmed-by principal is the test owner; the validator was consulted exactly once by the real runner (`validationClient.callCount() - callsBefore == 1`, unchanged). The wait set must not still contain `AWAITING_CONFIRMATION` as an accepted outcome.
3. **Legs 0, 2 and 3 stay green, unchanged in meaning.** Leg 0's four assertions (unauthenticated `/health` 401, authenticated 200, unauthenticated `POST /v1/runs` 401, the credential the API was given accepted) are not edited. Leg 2's predicate stays `admission_id IS NOT NULL` on `studio_dispatch_ledger` (10.35 AC-1) and leg 3's assertions stay as they are. If a change to a shared helper requires touching a line inside those three legs, the diff shows it and the Dev Agent Record says why; the default expectation is zero lines changed in them.
4. **The realigned legs can fail.** Red-before-green, once, by one temporary mutation on the realigned leg-1 path: make the stub gateway return an artifact the real runner validator rejects (or otherwise force a non-`READY` terminal compile status), run leg 1, and show it goes red with the `CoRunFailure` naming the observed `compile_status`, not green and not a different error. Restore the source and prove it byte-identical (sha256 before and after, as in the 10.35 gate). Recorded in the Dev Agent Record with the red output quoted.
5. **No production code change; a real defect stops the story.** The diff contains no file under `backend/src/main/`, `studio-runner/`, `frontend/`, `docs/architecture/`, or any `openapi.yaml`. If any leg, once the compile helper is realigned, fails for a reason that is **not** harness staleness (for example a cancel leg exposes a wrong ledger state, a process leak, or a PASSED run that ends otherwise), **@dev stops**: records the leg, the exact failure text and the attribution it printed, and the split story is drafted by @sm. The leg stays red and is not retired, weakened or worked around to reach 11 of 11 (that is AC-1's retirement rule, which requires a ruling, not a defect).
6. **Diff confinement, reviewed not asserted.** `git diff --stat` for this story's commit(s) lists only `tools/corun.sh`, `backend/src/test/java/com/citi/put/checks/corun/StudioCoRunIT.java` and files in the same package (`CoRunEnvironment`, `CoRunFailure`, `RunnerProcess`, `CallbackProxy`, `FixturePage`, `BlackHolePage`), plus this story file. @qa lists the stat in QA Results and states which of those files changed. `tools/corun.sh` changes are comment/text only unless a leg's retirement requires otherwise (the header text "compile, confirm and dispatch" is stale after this story and is updated). `tools/corun-report.mjs` is not in the list and is not edited here.
7. **Committed-tree evidence.** The 11-leg result that closes AC-1 is recorded against a commit SHA, with the output of `git status --short` at the time. Any uncommitted file that the co-run could read (the 10.35 gate recorded OBS-H5: another agent's untracked `V28__...sql` in `build/resources`) is listed with a one-line statement of why it cannot turn a red leg green. A run on an unrecorded or dirty tree does not close AC-1.
8. **The two guards that make a co-run result trustworthy are unchanged.** G1 (without `STUDIO_CORUN=1` all legs are skipped and the wrapper treats that as a failure) and G2 (the wrapper reads the XML, never the exit code) in `tools/corun.sh`/`corun-report.mjs` are not weakened; the final report states the executed/skipped counts from the wrapper, `skipped: 0`.
