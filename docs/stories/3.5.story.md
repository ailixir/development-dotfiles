## User Story

**As a** logged-in user of the PUT platform,
**I want** the Checks module to fetch my identity and permissions from the real backend,
**so that** I see only the CSIs I own and can perform actions based on my actual role, not a hardcoded mock user.

---

## Acceptance Criteria

- [ ] **AC-1:** `apiClient.ts` updated: remove Bearer token injection for user auth. The platform BFF sets an HttpOnly `put_session` cookie — the browser sends it automatically. No explicit `Authorization` header needed for user requests.
- [ ] **AC-2:** `apiClient.ts` `withCredentials: true` set on the axios instance to ensure cookies are sent cross-origin (dev proxy scenario).
- [ ] **AC-3:** New `usersApi.ts` service created in `src/services/api/` with `getMe(): Promise<UserDto>`.
- [ ] **AC-4:** `usersApi.getMe()` calls `GET /api/v1/users/me`. Response: `UserDto` `{id, ssoId, name, email, department, createdAt, lastLogin, active}`. Maps to FE `User` type.
- [ ] **AC-5:** User mapper `mapUserDtoToUser(dto: BackendUserDto): User` created in `src/services/api/mappers/userMapper.ts`. Maps: `department`→ used for display, `ssoId`→ not displayed but stored for correlation.
- [ ] **AC-6:** `csiApi.getUserPermissions()` refactored: instead of calling `GET /csi/user-permissions` (MSW endpoint), it calls `usersApi.getMe()` and derives permissions from the user identity. NOTE: the backend resolves CSI ownership via `CsiOwnershipEvaluator` server-side — the FE doesn't need a separate permissions endpoint. RBAC is enforced backend-side; FE uses role from `/users/me` for UI-level gating (show/hide admin features).
- [ ] **AC-7:** Store: user state populated from `/users/me` on app init. If the endpoint returns 404 with `Retry-After`, the FE retries after the indicated delay (user record being created asynchronously by BE on first login).
- [ ] **AC-8:** FE admin check: `user.roles` or `user.department` + convention determines if admin UI elements are shown. Exact mapping TBD based on BE `UserDto` shape — may need a `roles` field added to `/users/me` response or a separate `/users/me/permissions` call.
- [ ] **AC-9:** `.env.development` updated: for local dev without Core service, document how to bypass auth (e.g., `spring.profiles.active=local` on BE auto-creates a dev user, or a dev-only endpoint).
- [ ] **AC-10:** `npm run type-check` passes.
- [ ] **AC-11:** App boots, user identity displayed correctly in header/profile area (manual verification).

## Implementation Notes

### Backend UserDto shape
```json
{
  "id": "550e8400-...",
  "ssoId": "bb12345",
  "name": "Bruno Buger",
  "email": "bruno.buger@citi.com",
  "department": "Technology Infrastructure",
  "createdAt": "2026-04-17T...",
  "lastLogin": "2026-04-27T...",
  "active": true
}
```

### Cookie-based auth flow
```
Browser → PUT Shell (port 3000) → COIN OIDC → Core service mints put_session cookie
Browser → Checks MFE → API calls include put_session cookie automatically
Backend → BffSessionAuthenticationFilter reads put_session → introspects via Core → UserIdentity
```

### Local dev workaround
When running `./gradlew bootRun --args='--spring.profiles.active=local'`, the `LocalEmbeddedPostgresConfig` likely seeds a dev user. The FE dev proxy at `/api/v1` forwards to `:8080`. The BE's local profile may skip Core introspection and use a hardcoded identity — verify with existing BE config.
