## User Story

**As a** developer deploying the hardened scheduling pipeline to production,
**I want** an end-to-end integration test that exercises the full dispatch→execute→persist→trigger→status-cascade chain, a concurrent ShedLock contention test proving only one scheduler runs, and a capacity smoke test verifying 500 dispatches complete within the ShedLock window,
**so that** we have confidence the pipeline works as a unit under realistic conditions and can handle the documented peak workload.

---

## Problem Statement

The current test suite tests individual components (dispatch, execution, persistence, partitioning) in isolation. No test exercises the full pipeline from schedule poll through to status cascade trigger. Key gaps:

1. **No E2E pipeline test:** We don't know if CronDispatcher → CheckExecutorDispatcher → HttpCheckExecutor → ExecutionPersistenceService → `update_check_status_from_execution()` trigger works as a connected chain.
2. **No concurrent lock contention test:** `ShedLockIT` tests lock acquisition from a single thread, not two dispatchers racing for the same lock on the same datasource.
3. **No capacity smoke test:** We claim 3,000 dispatches/min but have no test proving 500 dispatches (one batch) complete within the lock window.
4. **No report delivery retry lifecycle test:** The interaction between `ReportDeliveryDispatcher` failure → `FailedDispatch` creation → `RetryDispatcher` retry → deletion is untested as a connected flow.

## Acceptance Criteria

### E2E dispatch pipeline test
- [ ] **AC-1:** `DispatchPipelineE2EIT` (`@SpringBootTest`):
  1. Insert a CSI, check (type=HTTP), and schedule (nextExecutionAt = past).
  2. Start WireMock on a dynamic port returning HTTP 200.
  3. Call `cronDispatcher.pollAndDispatch()` directly.
  4. Wait (with timeout) until `execution_results` has a row for this check.
  5. Assert: execution status = SUCCESS, check.status cascaded to PASSING (via DB trigger), schedule.nextExecutionAt advanced to future.
- [ ] **AC-2:** Same test with WireMock returning HTTP 500 → execution status = FAILURE, check.status = FAILING.
- [ ] **AC-3:** Same test with WireMock not started (connection refused) → execution status = FAILURE, check.status = FAILING, error message contains "Connection refused".

### ShedLock contention test
- [ ] **AC-4:** `ShedLockContentionIT`: create two `CronDispatcher` instances sharing the same `DataSource` and `ScheduleRepository`. Insert 10 due schedules. Trigger `pollAndDispatch()` on both instances concurrently (two threads). Assert: exactly 10 dispatches total (not 20), proving only one dispatcher acquired the lock.
- [ ] **AC-5:** After the lock is released, the second dispatcher can acquire it on the next call.

### Capacity smoke test
- [ ] **AC-6:** `CapacitySmokeIT`: insert 500 schedules (all due now) with HTTP checks pointing at WireMock (fast 10ms response). Call `pollAndDispatch()`. Assert: all 500 `nextExecutionAt` values advanced within 30 seconds wall-clock (well within the 2m ShedLock window).
- [ ] **AC-7:** Assert: all 500 execution results eventually persisted (with a polling wait of up to 60s for async completions).
- [ ] **AC-8:** Assert: `checks.scheduled.dispatches_total{outcome=success}` counter >= 500.

### Report delivery retry lifecycle test
- [ ] **AC-9:** `ReportRetryLifecycleIT`:
  1. Insert a report with `nextDeliveryAt` in the past and an intentionally broken recipient.
  2. Call `reportDeliveryDispatcher.pollAndDeliver()`.
  3. Assert: delivery fails, `FailedDispatch` record created with type=REPORT.
  4. Call `retryDispatcher.pollAndRetry()`.
  5. Assert: retry executes (with fixed recipient or mock), `FailedDispatch` is deleted on success.

### Backpressure integration test
- [ ] **AC-10:** `BackpressureIntegrationIT`: insert 500 due schedules. Saturate the executor with long-running tasks (pre-fill all permits). Call `pollAndDispatch()`. Assert: poll is skipped, `checks.dispatch.polls_skipped_total{reason=backpressure}` incremented, no new dispatches submitted.

### Dashboard native SQL soft-delete audit
- [ ] **AC-11:** `DashboardSoftDeleteIT`: insert a check, soft-delete it (set `deleted_at`). Call each `DashboardService` method. Assert: deleted check does NOT appear in summary counts, attention items, activity items, upcoming items, or search results.

### Tests meta
- [ ] **AC-12:** All 106+ existing tests still pass (full regression).
- [ ] **AC-13:** JaCoCo coverage ≥ 70% project-wide (existing gate).

## Implementation Notes

- **WireMock for E2E:** Use `@WireMockTest` with dynamic port. Configure the check's `HttpConfiguration.url` to point at WireMock's `baseUrl()`. This avoids network dependencies.
- **Polling wait pattern:** Use `Awaitility.await().atMost(Duration.ofSeconds(60)).until(() -> resultRepo.findByCheckId(checkId).size() > 0)` for async result assertions.
- **ShedLock contention:** Both dispatchers share the same `DataSource` and `ShedLock` table. Use `CountDownLatch` to synchronize start. Use `ExecutorService.invokeAll()` to run both concurrently.
- **Capacity smoke — data setup:** Use `JdbcTemplate.batchUpdate()` to insert 500 checks + 500 schedules efficiently, not JPA save loops.
- **Dashboard audit:** Use native SQL to insert and soft-delete (to bypass `@SQLRestriction`), then call service methods and verify absence.
