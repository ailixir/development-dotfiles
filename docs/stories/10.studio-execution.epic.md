# 10.1 — Studio execution schema and poll contract

**Component:** Backend, Frontend
**Depends on:** none
**Overview:** Make in-flight executions persistable and return the shape the Studio page already polls for.
**Story points:** 5

### Why this first

Today `ui_test_executions` only allows terminal statuses, so a honest `PENDING`/`RUNNING` row cannot survive `ddl-auto: validate`. The MFE already polls; it needs a stable DTO before anyone wires real dispatch.

### Description / Scope

**Backend — Flyway (partitioned table)**

- Widen status check constraint to `PENDING | RUNNING | PASSED | FAILED | ERROR`.
- Make `ended_at` and `duration_ms` nullable (in-flight rows have no honest value).
- Add `step_results JSONB NOT NULL DEFAULT '[]'` and `video_object_key TEXT`.
- Add partial index on `(status, started_at)` where status is in-flight (needed later by reapers; cheap to add now).
- Verify constraint/column changes on **all** partitions including `DEFAULT`. Partitioned tables are the usual place migrations “look green” and then fail on the next month’s partition.

**`step_results` shape (contract for 10.7 / 10.12 / 10.16)**

```json
[
  {
    "stepIndex": 0,
    "status": "PASS",
    "offsetMs": 840,
    "durationMs": 2100,
    "message": "Go to \"https://www.citi.com\""
  },
  {
    "stepIndex": 2,
    "status": "FAIL",
    "offsetMs": 4120,
    "durationMs": 880,
    "message": "Wait for the text \"User ID\"",
    "error": "Locator not visible within 30000ms"
  }
]
```

Per-step status: `PENDING | RUNNING | PASS | FAIL`.

**Execution status meaning**

| Status | Meaning |
|---|---|
| `PENDING` | Accepted, not yet on a runner |
| `RUNNING` | Runner started (or dry-run accepted) |
| `PASSED` | All steps passed |
| `FAILED` | A step failed; video should exist when recording is live |
| `ERROR` | Infrastructure problem — details in `error_details.code` |

**DTO / API**

- `GET /studio/executions/{id}` returns `stepResults[]`, `logs[]` (array, not a string), video availability flag / `videoObjectKey` presence (do not invent a durable URL).
- Fix `GET /studio/executions` so listing works **without** a required `testId`; keep `?testId=` as an optional filter. Paginate consistently with other Studio list endpoints.

**Frontend**

- Map legacy `COMPLETED` → `PASSED` during cutover.
- Treat timeout as `ERROR` + `error_details.code = TIMEOUT` (not a separate status enum value).
- Poll loop must render PENDING / RUNNING / terminal states from the real API with no client-side shape hacks.

### Out of scope

Compiler columns (`compiled_steps`). Video streaming endpoint. CSI auth (10.7). Reapers. Actually writing step results from a runner (10.7).

### Acceptance criteria

- [ ] A `PENDING` row inserts under `ddl-auto: validate` on every partition including DEFAULT.
- [ ] Poll `GET /studio/executions/{id}` returns `stepResults` and `logs` as arrays.
- [ ] `GET /studio/executions` without `testId` returns 200 (empty or paged), not 400.
- [ ] Existing Studio poll loop renders PENDING / RUNNING / terminal states from the real API with no client-side shape hacks.
- [ ] Integration test covers insert PENDING → update RUNNING → terminal PASSED with sample `step_results`.

# 10.2 — Compiled-step artifact validator

**Component:** Runner
**Depends on:** none (library only; HTTP wrapper is 10.6)
**Overview:** Reject any generated Playwright that is not a single-step, allowlisted snippet.
**Story points:** 5

### Why this exists

The LLM proposes code; this library **disposes**. Nothing runs in Chromium until it passes AST + allowlist. Same library is used at compile time (`POST /v1/validate`) and again at run time (defense in depth).

### Artifact contract

```json
{
  "version": 1,
  "steps": [
    {
      "stepIndex": 0,
      "originalText": "Go to \"https://www.citi.com\"",
      "code": "await page.goto('https://www.citi.com');"
    }
  ]
}
```

### Description / Scope

**Validate (all must pass)**

- TypeScript AST parse of each `code` string.
- Call allowlist only:
  - Navigation: `page.goto`, `page.waitForURL`
  - Locators: `getByRole`, `getByText`, `getByLabel`, `getByPlaceholder`, `getByTestId`, `locator` (CSS)
  - Locator actions: `click`, `fill`, `press`, `check`, `uncheck`, `selectOption`, `hover`
  - Assertions: `expect(locator).toBeVisible` / `toContainText` / `toHaveValue`; `expect(page).toHaveURL` / `toHaveTitle`
- Alignment: one output entry per input line; indexes match; `originalText` equals the source line exactly.
- Secrets/vars in code only as `vars.secret('…')` / `vars.get('…')` (or the agreed `vars.*` surface). A literal that looks like a resolved secret value rejects the artifact.

**Forbid (any occurrence rejects the step)**

- `import` / `require` / `eval` / `new Function`
- `page.evaluate`, `addScriptTag`, `exposeFunction`
- Network, filesystem, process, timer APIs
- Browser/context management (`launch`, `newContext`, `close`, …)
- Loops; variable declarations that leak across steps

**Library shape**

- Pure function: `validate(artifact) → { valid, steps: [{ stepIndex, ok, diagnostics[] }] }`.
- No HTTP, no Chromium, no LLM.
- Fixture corpus checked into the repo: valid snippets, each forbidden construct, injection-style output (`ignore previous instructions…`), misaligned indexes, secret-looking literals.

### Out of scope

HTTP server (10.6). LLM. Chromium. Syntax-reference file (10.3). Widening the allowlist for non-MVP APIs.

### Acceptance criteria

- [ ] Fixture corpus covers valid snippets, each forbidden construct, injection-style output, and misaligned indexes.
- [ ] Validator is a library function the runner can call from `/v1/validate` later.
- [ ] A step that imports a module or calls `page.evaluate` is rejected with a clear diagnostic.
- [ ] `vars.secret('LOGIN_PW')` is accepted; a hardcoded password-like string in `fill(...)` is rejected.

# 10.3 — Pinned Playwright syntax reference

**Component:** Runner (shared file; backend compile pipeline reads it in 10.8)
**Depends on:** none (pair with 10.2 on allowlist content)
**Overview:** Give the compiler a version-matched Playwright excerpt so the model emits current APIs.
**Story points:** 2

### Why this exists

Models invent stale Playwright APIs from training data. The prompt must include a curated excerpt that matches the **exact Playwright version** pinned in the future runner image. The reference and the image version must never drift independently.

### Description / Scope

- Curated markdown/text excerpt covering only: navigation, locators, actions, assertions that appear on the 10.2 allowlist.
- One Playwright version constant (e.g. `PLAYWRIGHT_VERSION=1.x.y`) shared with the future runner Dockerfile / package.json.
- File lives in-repo at a stable path the backend can load as a prompt string in 10.8 (copy into the API image, or shared package — pick one and document it in the story notes).
- Examples in the reference must themselves be allowlist-legal (no `page.evaluate` demos).

### Out of scope

CI that fails on version drift (post-MVP). Full Playwright docs dump. Shipping the reference inside the LLM gateway itself.

### Acceptance criteria

- [ ] Reference file exists, versioned, and only documents allowlisted APIs.
- [ ] Version constant is documented in one place for runner image + reference.
- [ ] Compile pipeline (10.8) can read it as a string without network fetch.

# 10.4 — Compiler columns and STALE transitions

**Component:** Backend
**Depends on:** none (parallel with 10.1)
**Overview:** Persist compile state on `ui_tests` so later stories can freeze and gate runs.
**Story points:** 2

### Description / Scope

**Flyway additions on `ui_tests`**

| Column | Type | Purpose |
|---|---|---|
| `compiled_steps` | JSONB | Frozen artifact: `{ version, steps: [{ stepIndex, originalText, code }] }` |
| `steps_hash` | TEXT | `sha256` of the plain-English steps the artifact was compiled from |
| `compile_status` | VARCHAR | `READY \| NEEDS_REVISION \| STALE` (default `STALE` for new/edited tests) |
| `compile_meta` | JSONB | `modelId`, `promptVersion`, `playwrightRefVersion`, `compiledAt` |

**Behavior**

- On create or update that changes `steps`: set `compile_status = STALE`, clear or leave `compiled_steps` as-is until 10.8 recompiles (do not auto-call LLM here).
- Recompute `steps_hash` from the canonical serialization of the plain-English lines (document the exact hash input: newline-joined trimmed lines, UTF-8, no trailing blank line ambiguity).
- Test DTO exposes `compileStatus`, `stepsHash`, and (when present) compiled step summaries for the FE.

### Out of scope

Calling the LLM. Confirm endpoint. Readiness gate on execute. Clearing `compiled_steps` policy beyond STALE flag.

### Acceptance criteria

- [ ] Editing steps flips `compile_status` to `STALE`.
- [ ] `steps_hash` is deterministic for the same step text (unit test with two identical saves).
- [ ] GET test DTO includes compile status after migration.
- [ ] Existing tests without compile columns migrate cleanly (default STALE).

# 10.5 — R2D2 LLM gateway client

**Component:** Backend
**Depends on:** none (start immediately — longest external lead)
**Overview:** One client to call the Citi LLM with pinned model settings and an audit trail. No prompt assembly yet.
**Story points:** 5

### Why the API owns this (not the runner)

Compile is authoring-time orchestration (user, CSI, DB, audit). The runner must never hold LLM credentials or call the gateway. See architecture trust boundaries.

### Description / Scope

**Client responsibilities**

- Auth to R2D2 / Citi LLM gateway, connect/read timeouts, bounded transport retries (not repair retries — those are 10.9).
- Config (names illustrative):

```yaml
studio:
  compiler:
    gateway-url: ${CITI_LLM_GATEWAY_URL}
    model-id: ${STUDIO_COMPILER_MODEL_ID}   # pinned
    prompt-version: 1                       # pinned
    temperature: 0
```

- Request API: structured JSON output mode; temperature 0.
- Response parsing into a typed candidate list: `[{ stepIndex, originalText, code }]`. Malformed JSON → typed client error (no silent empty list).
- Audit each call: test id, CSI, user, model id, prompt version, latency, success/failure — **never** secret/variable plaintext, never full step text if it could contain secrets (steps should already be tokenized before this client is used in 10.8; still scrub known secret patterns defensively).

**Platform confirmation (blocking knowledge, not blocking code merge)**

- Confirm with the platform team that temp-0 and JSON mode exist. Write the result in the ticket.
- If unavailable: document fallback (validation still guarantees correctness; expect higher repair rates / latency).

### Out of scope

Prompt assembly (fenced steps + syntax reference). Repair loop. Result cache. Compile persistence. Calling `/v1/validate`.

### Acceptance criteria

- [ ] Stub-gateway tests: success, malformed JSON, timeout, outage.
- [ ] Gateway temp-0 / JSON-mode support is confirmed or a fallback is documented on the story.
- [ ] Audit log never contains secret or variable plaintext.
- [ ] Client is injectable / mockable so 10.8 can unit-test the pipeline without a live gateway.

# 10.6 — studio-runner HTTP service and backend contract

**Component:** Runner
**Depends on:** 10.2
**Overview:** Turn the existing Node boilerplate into the internal Studio runner the Spring API calls to validate artifacts and accept (dry-run) jobs.
**Story points:** 8

### How it talks to the backend

The runner is a **cluster-internal HTTP service**. It never calls the API, Postgres, Vault, CSI, or the LLM. The Spring API is the only client.

Two API → runner calls, both with a shared **service token** (not a user session):

| When | Backend calls | Runner does (this story) |
|---|---|---|
| User saves / compiles a test | `POST /v1/validate` with a candidate artifact | Run the 10.2 validator; return ok or per-step diagnostics |
| User clicks Run | After CSI + (later) compile gate: insert `PENDING`, then `POST /v1/runs` and **wait** for the HTTP response | Accept one job, dry-run it, return a full result body |
| User polls | `GET /studio/executions/{id}` on the **API only** | Nothing — the runner has no poll API |

```
MFE                         Spring API                         studio-runner
 |                               |                                    |
 |  PUT /studio/tests/{id}       |                                    |
 |------------------------------>|  POST /v1/validate  + token        |
 |                               |----------------------------------->|
 |                               |  200 { valid } or per-step errors  |
 |                               |<-----------------------------------|
 |                               |                                    |
 |  POST /studio/tests/{id}/execute                                   |
 |------------------------------>|  authorize, INSERT PENDING         |
 |  202 { executionId }          |  POST /v1/runs + token + job       |
 |<------------------------------|----------------------------------->|
 |  GET /studio/executions/{id}  |         (HTTP call stays open)     |
 |------------------------------>|  200 { status, stepResults, ... }  |
 |  PENDING / RUNNING / result   |<-----------------------------------|
 |<------------------------------|  persist row, return to poll       |
```

**Job request** the API will send on `/v1/runs` (same shape 10.7 / 10.12 will use — dry-run ignores browser fields):

```json
{
  "executionId": "uuid",
  "testId": "uuid",
  "csiId": "174523",
  "artifact": { "version": 1, "steps": [{ "stepIndex": 0, "originalText": "…", "code": "…" }] },
  "resolvedVars": {},
  "resolvedSecrets": {},
  "viewport": { "width": 1920, "height": 1080 },
  "stepTimeoutMs": 30000,
  "runTimeoutMs": 120000,
  "sonicKey": "studio/{csiId}/{testId}/{executionId}.webm"
}
```

**Result** the API persists on the execution row:

```json
{
  "executionId": "uuid",
  "status": "PASSED",
  "stepResults": [{ "stepIndex": 0, "status": "PASS", "offsetMs": 0, "durationMs": 10, "message": "…" }],
  "logs": [{ "timestamp": "…", "level": "info", "message": "dry-run" }],
  "videoObjectKey": null,
  "error": null
}
```

**Status codes the API must handle:** `200` finished · `400` bad job · `401/403` bad/missing token · `429` + `Retry-After` at capacity · `500` crash. Ready/live probes are **not** a capacity signal — a busy runner stays ready and answers 429 on `/v1/runs`.

### Description / Scope

Start from the **existing Node service boilerplate** (HTTP server, config, logging, tests). Do not invent a new scaffold and do not add Compose/Helm.

- `GET /health`, `GET /ready` — process up only.
- `POST /v1/validate` — wrap the 10.2 library; return `{ valid, steps: [{ stepIndex, ok, diagnostics[] }] }`.
- `POST /v1/runs` — **dry-run**: require a valid artifact and the required job fields; do not launch Chromium or touch object storage; return a deterministic synthetic `PASSED` (or `ERROR` if the artifact fails re-validation) using the contract above.
- Service-token auth on `/v1/*`. Health/ready stay unauthenticated for probes.
- `POOL_SIZE` semaphore on `/v1/runs` only (default 1). `/v1/validate` is not gated by the run pool.
- Request validation, structured logs (`executionId`, `testId`, `csiId` — never `resolvedSecrets` / var values), config via env (`PORT`, `SERVICE_TOKEN`, `POOL_SIZE`).
- Contract tests (or a checked-in OpenAPI + examples) so 10.7 can implement the Java client against a frozen shape.
- Unit/integration tests for auth, validate success/fail, dry-run success, 400, 429.

### Out of scope

Chromium / Playwright launch (10.12). Sonic / MinIO / upload (10.14). Docker Compose, Dockerfile, Helm, NetworkPolicy (10.18). LLM. Java dispatch client (10.7).

### Acceptance criteria

- [ ] Existing boilerplate is the project root; runner starts with `npm start` (or the boilerplate’s equivalent) and serves the four routes.
- [ ] A documented curl/HTTP example of `POST /v1/validate` and `POST /v1/runs` matches the contract 10.7 will call.
- [ ] Valid artifact → dry-run `200` with `status`, `stepResults[]`, `logs[]`, `videoObjectKey: null`.
- [ ] Invalid artifact on `/v1/runs` → `400` or result `ERROR`; Chromium is never invoked.
- [ ] Missing/wrong service token on `/v1/*` → `401/403`; `/health` and `/ready` still work.
- [ ] `POOL_SIZE=1`: second concurrent `/v1/runs` returns `429` + `Retry-After`; a parallel `/v1/validate` still succeeds.
- [ ] Logs never contain `resolvedSecrets` or variable values from the job body.

# 10.7 — Execute dispatch and CSI on Studio routes

**Component:** Backend
**Depends on:** 10.1, 10.6
**Overview:** Replace the PENDING-only stub with real dispatch, and lock Studio routes to CSI roles before any browser work is reachable.
**Story points:** 5

### Dispatch flow (API side)

```
POST /studio/tests/{id}/execute
  → CSI authorize (owner/execute role)
  → (later 10.8) compile-readiness gate
  → INSERT ui_test_executions (PENDING)
  → 202 { executionId }
  → async: POST {runner}/v1/runs  (HTTP stays open; timeout = runTimeout + margin)
       on 429: keep PENDING, backoff retry (config: retry-429-max, backoff-ms)
       on 200: persist stepResults, logs, videoObjectKey, terminal status; update test last-run fields
       on timeout / connection / 5xx after retries: ERROR + error_details.code; never leave row stuck
```

### Description / Scope

**Dispatch client**

- Config:

```yaml
studio:
  execution:
    enabled: true
  runner:
    base-url: ${STUDIO_RUNNER_URL}
    token: ${STUDIO_RUNNER_TOKEN}
    request-timeout-ms: 150000
    retry-429-max: 20
    retry-429-backoff-ms: 2000
```

- Job body matches the 10.6 contract. For this story, artifact may be a placeholder / last-known steps until 10.8 freezes real compiled artifacts — document that 10.8 will swap the source to DB `compiled_steps` only.
- Transition: PENDING → RUNNING when the runner call starts (or when the runner first acknowledges — pick one and stick to it in the DTO).
- `studio.execution.enabled=false`: still return `202` after insert, **do not** call the runner; leave PENDING or mark ERROR with `DISPATCH_DISABLED` — pick one, document it, test it. Prefer: accept 202, no dispatch, row stays PENDING until an operator/reaper (reaper is post-MVP; for MVP mark ERROR + `DISPATCH_DISABLED` so the poll loop terminates).

**CSI authorization (hard requirement of this story)**

Wire the existing CSI ownership evaluator on **all** Studio routes that exist today:

| Access | Routes |
|---|---|
| Read | GET tests, GET test by id, GET executions, list executions |
| Owner / execute | create, update, delete, execute |

Compile / confirm / video endpoints get the same checks as those endpoints land (10.8, 10.9, 10.15). Do not ship execute without CSI.

### Out of scope

Compile-readiness `409` (10.8). Video endpoint. Secret resolution (10.17). Reapers. Chromium. Calling the LLM.

### Acceptance criteria

- [ ] Against the dry-run runner, poll shows PENDING → RUNNING → PASSED with step results.
- [ ] Dispatch failures leave a terminal `ERROR` row (never stuck PENDING forever in the happy failure paths covered by this story).
- [ ] Kill switch off: 202 returned, no runner call; poll reaches a terminal state.
- [ ] Non-owner execute/create/edit → 403. Non-reader GET → 403.
- [ ] Integration test uses a WireMock / Testcontainers stand-in for the runner contract from 10.6.

# 10.8 — Compile pipeline and readiness gate

**Component:** Backend
**Depends on:** 10.3, 10.4, 10.5, 10.6
**Overview:** Translate saved steps via the Citi LLM, validate them on the runner, freeze the artifact, and refuse runs that are not READY.
**Story points:** 5

### Compile flow

```
PUT /studio/tests/{id}  (or POST /tests/{id}/compile)
  → persist steps, compile_status = STALE
  → build prompt:
       1. fenced steps (data, not instructions) with indexes
       2. pinned Playwright syntax reference (10.3)
       3. output contract + allowlist
  → R2D2 client (10.5) temp 0 + JSON
  → POST {runner}/v1/validate
  → on valid: persist compiled_steps + compile_meta + steps_hash; leave status needing confirm (not READY yet — 10.9) OR set a “compiled but unconfirmed” representation
  → on gateway outage: stay STALE, clear error to client; already-frozen READY tests unchanged
```

Clarification for this story vs 10.9: **this story freezes a validated artifact and implements the execute gate.** Prefer: after successful validate, store artifact and set status to something the FE can show, but `READY` only via confirm in 10.9. If confirm is not yet shipped, gate execute on “artifact present + hash match + not STALE” temporarily — **better:** land confirm endpoint stub that auto-confirms in tests only, or require 10.9 in the same PR train. Default plan: 10.8 sets post-validate status to `NEEDS_REVISION` if any step failed validate, else leaves `STALE` until confirm (10.9) sets `READY`. Execute gate: `READY && hash matches`.

### Description / Scope

- Prompt inputs only: fenced steps, syntax reference, output contract. Secrets/vars stay opaque tokens (`<secret ID>`, `<var NAME>`) → compile to `vars.*` calls.
- Plaintext never goes to the LLM.
- `POST /tests/{id}/compile` re-triggers the same pipeline (gateway recovery / after edits).
- Execute preflight before dispatch:
  - `compile_status = READY` AND `sha256(current steps) = steps_hash` else `409 COMPILE_REQUIRED`
  - Non-Chromium browser value → `400`
- Job payload to the runner uses **only** `compiled_steps` from the DB — never client-supplied code.

### Out of scope

Repair retry loop (10.9). Confirm endpoint (10.9). FE confirmation UI. Result cache keyed by step hash. Audit of every prompt body beyond 10.5’s audit fields.

### Acceptance criteria

- [ ] The four-step demo checklist compiles to a validated artifact stored on the test.
- [ ] Tokens never appear as plaintext in prompts, artifacts, or audit logs.
- [ ] Gateway down → STALE + error; already-READY tests (if any) are unchanged.
- [ ] Execute of a STALE / unconfirmed test returns 409 and does not call the runner.
- [ ] Execute after READY + matching hash dispatches the frozen artifact bytes, not a re-translation.

# 10.9 — Compile repair, diagnostics, and confirm

**Component:** Backend
**Depends on:** 10.8
**Overview:** Retry a bad compile with validator diagnostics, surface per-step reasons, and require user confirm before READY.
**Story points:** 3

### Description / Scope

**Repair (bounded)**

- If `/v1/validate` returns per-step failures: one repair attempt that sends diagnostics back to the model (max attempts configurable; MVP = 1 in this story’s AC, architecture allows 2 — implement `repair-max-attempts: 2` if cheap).
- Still-invalid step → mark that step `NEEDS_REVISION` with a human-readable reason (“couldn’t produce valid code for this step — try rephrasing”). Other steps may remain valid in the stored candidate.
- No silent fallback: never invent code for a failed step.

**Confirm**

- `POST /tests/{id}/confirm-compile`
  - Reject if any step is `NEEDS_REVISION`
  - Reject if `steps_hash` no longer matches current steps (user edited mid-flight)
  - Else set `compile_status = READY` and freeze the artifact as the runnable source of truth

**DTO**

- Expose per-step compile diagnostics on the test GET so 10.10 can render reasons inline.

### Out of scope

Compile result cache. FE layout (10.10). Widening allowlist. Second product language for diagnostics.

### Acceptance criteria

- [ ] An uncompilable step gets a reason and does not block diagnostics on the others.
- [ ] Confirm on a mixed NEEDS_REVISION test is rejected.

# 10.12 — Chromium harness and video recording

**Component:** Runner
**Depends on:** 10.6
**Overview:** Execute the frozen artifact in Chromium and record a webm with per-step timings. Independent of the compiler track.
**Story points:** 5

### Runner-side run flow

```
POST /v1/runs
  → auth + pool semaphore
  → re-validate artifact (10.2); refuse ERROR / 400 if invalid — do not launch Chromium
  → chromium.launch()
  → newContext({ viewport, recordVideo: { dir } })
  → newPage(); t0 = now()
  → for each step:
       offsetMs = now() - t0
       run code in harness scope { page, expect, vars }
       PASS/FAIL + durationMs
       on FAIL: stop; remaining steps stay PENDING
  → close context (flushes .webm)
  → return result + local webm path (upload is 10.14)
  → browser close (launch/close per run; no warm pool)
```

### Description / Scope

- Replace dry-run `/v1/runs` with real execution when a feature flag / env allows; keep dry-run mode for CI without browsers if useful.
- Harness: step code is a function body / async IIFE whose free names are only `page`, `expect`, `vars`. No `require`, no global process.
- Default timeouts: use job `stepTimeoutMs` / `runTimeoutMs` (full enforcement in 10.13; this story must at least apply step timeout or hard-fail obviously hung steps).
- Integration fixture: static HTML page served locally; steps that click / assert against it.
- `offsetMs` stamped at step **start** relative to recording start (`t0`).

### Out of scope

Sonic upload (10.14). Full redaction matrix (10.13). Helm / shm sizing (10.18). Multi-browser.

### Acceptance criteria

- [ ] Integration test against a static HTML fixture: correct PASS/FAIL, `offsetMs`, non-empty local webm.
- [ ] Tampered/invalid artifact does not launch Chromium.
- [ ] First failure stops later steps; those steps remain PENDING (not PASS).
- [ ] Browser process is gone after the request completes (no leaked Chromium in the test process tree).

# 10.13 — Run timeouts, redaction, and cleanup

**Component:** Runner
**Depends on:** 10.12
**Overview:** Bound every run in time and keep resolved values out of logs and result payloads.
**Story points:** 5

### Description / Scope

**Timeouts**

- Per-step timeout from job (`stepTimeoutMs`, default 30s): fail that step as FAIL with timeout message; stop further steps.
- Whole-run timeout from job (`runTimeoutMs`, default 120s): kill context; status `ERROR` with timeout code; keep partial video if Playwright flushed it.
- Ensure pool slot is released on all exit paths (success, fail, timeout, crash).

**Redaction**

- Build a redaction filter from all values in `resolvedVars` and `resolvedSecrets`.
- Scrub before any log line, step `message`, or `error` leaves the runner.
- Structured logs may include `executionId`, `testId`, `csiId` only — never values.

**Cleanup**

- Delete temp video files and scratch dirs after the result is returned (or after successful upload in 10.14).
- On process signals, attempt context close so webm flushes when possible.

### Out of scope

Sonic. API-side reapers. Observability dashboards. Blurring secrets that appear on-screen in the video (documented residual risk).

### Acceptance criteria

- [ ] A hung step fails that step; a hung run ends as ERROR.
- [ ] Injected values never appear in runner stdout, result JSON, or stored logs (fixture injects a unique canary secret string).
- [ ] After a run, temp webm / profile dirs are removed on the success path.
- [ ] Pool semaphore recovers after timeout so a subsequent run is accepted.

# 10.15 — Authorized video streaming endpoint

**Component:** Backend
**Depends on:** 10.1, 10.7 (CSI), 10.14 (real objects in staging/MinIO)
**Overview:** Stream a run’s video through the API after a CSI read check. Same-origin so `<video>` works with platform auth.
**Story points:** 5

### Why proxy instead of direct Sonic

Browser `<video>` cannot attach arbitrary auth headers. Same-origin `GET /api/v1/studio/executions/{id}/video` reuses the platform session cookie. Range requests (`206`) are required for seeking.

### Description / Scope

- `GET /studio/executions/{id}/video`
  - Load execution → resolve test → CSI **read** check → 403 if denied
  - If `video_object_key` null → 404
  - Sonic `GetObject` with `Range` support → stream `206` / `200` with correct `Content-Type` (`video/webm`) and `Accept-Ranges`
- API uses **read-only** Sonic credentials (cannot PutObject).
- DB stores object key only — never a URL, never a presign.
- Do not log the object bytes; log execution id + key name only.

### Out of scope

302 to presigned Sonic URL. Transcoding. Per-test (not per-execution) video route. Caching CDN.

### Acceptance criteria

- [ ] Browser (or curl with Range) can seek via range requests (`206` with partial content).
- [ ] Non-reader → 403. Missing video → 404.
- [ ] No durable video URL is stored in the database.
- [ ] Integration test with MinIO + CSI deny/allow matrix.

# 10.17 — Variable and secret-token plumbing

**Component:** Backend, Runner
**Depends on:** 10.7, 10.8, 10.13
**Overview:** Resolve `<var>` / `<secret>` at dispatch and inject them only in runner memory. Compile stays token-only.
**Story points:** 5

### Lifecycle (must hold)

```
authoring     <secret ID> / <var NAME> in step text
compile       tokens pass through prompt + artifact as vars.* calls — no plaintext
dispatch      API resolves into job.resolvedVars / job.resolvedSecrets (in memory)
run           harness injects; redaction (10.13) scrubs outputs
persistence   never — no DB column, no log, no artifact, no Sonic key metadata
```

### Description / Scope

**Backend**

- At execute (after CSI + compile gate): resolve `<var NAME>` from the test’s variable definitions / request overrides; missing required var → `400` with names listed; **do not** call the runner.

- Artifact and compile prompts remain tokenized.

**Runner**

- `vars.get('NAME')` / `vars.secret('ID')` read from the in-memory maps supplied on the job.
- Missing key at runtime → fail that step clearly (should be rare if API prechecked).

### Out of scope

New Vault client / AES-GCM (existing secrets service may be a stub — real Vault is a prerequisite ticket, not this one). Secret-in-video blur. FE secrets picker redesign.

### Acceptance criteria

- [ ] A variable-driven test runs with the resolved value and the value is absent from DB, API logs, artifact, and step results.
- [ ] A secret-token test compiles without sending plaintext to the LLM (assert on captured gateway request in test).
- [ ] If the secrets interface can resolve a value, it never appears in stored or logged output (canary string test).
- [ ] Missing required variable → 400, no runner call.
