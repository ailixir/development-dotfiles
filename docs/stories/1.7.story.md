## User Story

**As a** frontend user navigating the PUT Checks module,
**I want** a read-only API for the CSI catalog — listing CSIs (paginated + filtered), fetching a single CSI's details, and listing the checks under a CSI —
**so that** the Dashboard, All Checks, and Create Check pages can render real CSI data from the backend and I can drill from CSI list → CSI detail → check list without a page reload.

## Acceptance Criteria

- [ ] **AC-1:** `CsiSystem` JPA entity + `CsiSystemRepository` matching ARCH §7.1 `csi_systems` (id varchar(20), name, description, business_unit, criticality, owner_email, environment, status, metadata JSONB, timestamps, soft-delete).
- [ ] **AC-2:** `GET /api/v1/csi` — paginated list. Query params: `page`, `size` (default 20, max 100), `business_unit`, `criticality`, `environment`, `status`, `owner_email`, `search` (substring match on name + description). Returns response envelope per spec §6.1. Excludes soft-deleted rows.
- [ ] **AC-3:** `GET /api/v1/csi/{id}` — single CSI fetch. Returns `404` for non-existent or soft-deleted.
- [ ] **AC-4:** `GET /api/v1/csi/{id}/checks` — paginated list of checks under the CSI. Same pagination + filter contract. Requires that `Check` entity exists (this story stubs with an empty query until 1.9 lands; no contract leak — returns `200` with empty `data[]`).
- [ ] **AC-5:** `@PreAuthorize("@csiOwnershipEvaluator.canRead(authentication, #id)")` on `GET /csi/{id}` enforces CSI ownership; admins bypass. Unauthenticated → 401; no ownership → 403.
- [ ] **AC-6:** `CsiDto` (response shape) + `CsiMapper` (MapStruct) convert entity ↔ DTO. Metadata JSONB surfaces as `Map<String, Object>` in the DTO.
- [ ] **AC-7:** `CsiService` is the sole business-logic layer; `CsiController` delegates and translates. No direct repo calls from the controller.
- [ ] **AC-8:** Cursor-based pagination option available for `/csi/{id}/checks` per spec §6.1 (since checks history grows unbounded); offset-based for `/csi` (list is bounded at ~5k per NFR-SCALE-03).
- [ ] **AC-9:** Integration tests: `CsiListIT` (filters + pagination + soft-delete), `CsiFetchIT` (200/404/403), `CsiChecksEndpointIT` (empty until 1.9; proper envelope).
- [ ] **AC-10:** Contract diff against committed `openapi.yaml` (story 1.16 adds the diff test; this story appends the three endpoints to the yaml so 1.16 has something to diff against).
- [ ] **AC-11:** JaCoCo coverage for `csi` package ≥ 80%.

- Filter + pagination (offset-based for list, cursor-based for checks sub-collection).

### Out of scope
- POST/PUT/DELETE on CSI — CSIs are provisioned upstream by the CSI API (ASM-05); put-checks consumes only. If future needs surface, a separate story.
- The `csi_metrics_current` materialized view endpoint (`GET /csi/{id}/metrics`) — that's M2 after the scheduler lands (story 2.5 area).

## Implementation Notes
- **Soft-delete handling:** use Hibernate `@Where(clause = "deleted_at IS NULL")` on the entity — no need to sprinkle `.filter(...)` across repo queries. Admin-only "include deleted" query can be added later without changing this story's ACs.
- **Metadata JSONB:** map as `Map<String, Object>` using `@JdbcTypeCode(SqlTypes.JSON)`. This is simpler than a sealed hierarchy (unlike CheckConfiguration) because CSI metadata is genuinely freeform per-CSI-system.
- **Pagination for checks sub-collection:** even though checks under a single CSI are typically < 100, the sub-collection endpoint should still use cursor pagination because a high-volume CSI could accumulate thousands.
- **MapStruct + JSONB Map:** straightforward — no `@SubclassMapping` needed.

## @po Validation — 2026-04-17 · **9/10 GO** (note N-1.7-1)

Good story overall. One authorization ambiguity worth surfacing explicitly before @dev starts.

**N-1.7-1 (non-blocking, resolve with @architect before @dev picks up):** `GET /api/v1/csi` (list) has **no @PreAuthorize** per AC-5 — only single + sub-collection are gated. This means any authenticated user can enumerate the entire CSI catalog, regardless of their own CSI ownership. Is that intentional?
- **Argument for open list:** the CSI catalog is a discoverability tool; a user can't do anything destructive from the list.
- **Argument against:** regulated-domain principle of least privilege — if a user has no business touching CSI X, they shouldn't even see it exists.
- **Recommendation:** default to filter-at-query-time (list returns only CSIs the user owns + CSIs marked `public=true` in metadata), with admin-role seeing all. Defer implementation detail to @dev but lock the policy before implementation.

**Other watch-items:**
- `/csi/{id}/checks` is bounded by `checks` existing — the story stubs it (AC-4) but this means the 1.7-drafted endpoint returns empty until 1.9 lands. FE testing (1.17) must be aware.
- `metadata` JSONB as `Map<String, Object>` is simpler than sealed, but means the frontend must tolerate any shape Core/CSI-API emits. Ensure FE's CSI type is lenient.
