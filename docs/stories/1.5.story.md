## User Story

**As a** put-checks backend engineer wiring the platform-standard BFF auth into every protected endpoint,
**I want** a `BffSessionAuthenticationFilter` that resolves the incoming request's `put_session` cookie via Core service introspection (with Phase-2 `X-User-*` forward-compat), a resilient `CoreServiceClient`, a `CsiOwnershipEvaluator` + `@RequiresPermission` aspect wired into Spring Security, and the CORS config the platform auth doc requires,
**so that** every M1+ story can protect endpoints with `@PreAuthorize` / `@RequiresPermission` against real platform identity, no put-checks code ever validates a COIN JWT directly (DEBT-04 upheld), and a Core outage produces a clear `503 Retry-After` rather than a demo/mock fallback (AUTH_FLOW.md error rule).

## Acceptance Criteria

### Group A — Filter core

- [ ] **AC-1:** `BffSessionAuthenticationFilter extends OncePerRequestFilter` registered via Spring Security's `SecurityFilterChain` at high priority (before `UsernamePasswordAuthenticationFilter`).
- [ ] **AC-2:** OPTIONS (CORS preflight) requests pass through untouched — no auth enforcement, no Core calls, no cookie reads. Verified by `OptionsBypassIT`.
- [ ] **AC-3:** Two-path identity resolution order:
  1. If request carries `X-User-Id` header (non-blank), parse `X-User-Id` + `X-User-Email` + `X-User-Roles` (CSV) + `X-User-Csi-Ownership` (CSV) into a `UserIdentity`. This is the Phase-2 forward-compat path for when an Envoy sidecar injects identity (platform-shell `PHASE_2.md`).
  2. Else extract `put_session` cookie → call `CoreServiceClient.getUserMe(cookieValue)` → receive `UserIdentity`.
- [ ] **AC-4:** On resolved identity, populate `SecurityContextHolder` with a `JwtAuthenticationToken`-compatible wrapper (or custom `BffAuthenticationToken`) carrying `UserIdentity` as the principal. MDC fields `userId` + `traceId` set. A `UserAuthenticatedEvent` is published on the Spring `ApplicationEventPublisher` (consumed by story 1.6 for async provisioning).
- [ ] **AC-5:** On missing/invalid session (no cookie, Core returns 401 from `/users/me`): filter writes HTTP 401 + JSON body `{"error":{"code":"UNAUTHENTICATED","message":"Session required","traceId":"<mdc-trace-id>"}}` + `Content-Type: application/json`. The filter does NOT redirect — that's the frontend's responsibility (dispatches `put:auth:unauthorized` event, shell redirects to `/api/v1/auth/login`).
- [ ] **AC-6:** On Core 5xx or transport failure (connect timeout, read timeout, circuit breaker open): filter writes HTTP 503 + `Retry-After: 5` + JSON body `{"error":{"code":"AUTH_TEMPORARILY_UNAVAILABLE","message":"..."}}`. Never falls back to any demo/mock identity per `put-platform-shell/AUTH_FLOW.md §Error handling rules`.

### Group B — CoreServiceClient

- [ ] **AC-7:** `CoreServiceClient` uses Spring 6 `RestClient` (CON-STACK-11). Three methods:
  - `UserIdentity getUserMe(String cookieValue)` → `GET {core-base}/api/v1/users/me` with `Cookie: put_session=<value>`.
  - `PermissionsPayload getUserPermissions(String cookieValue)` → `GET {core-base}/api/v1/users/me/permissions`.
  - `AuthzCheckResult checkPermission(String cookieValue, String permissionName)` → `POST {core-base}/api/v1/authz/check` with body `{"permission":"<name>"}`.
- [ ] **AC-8:** Timeouts: `2s connect / 3s read` per spec §11.2 integrations table. Configurable via `checks.core-service.timeout.*` properties.
- [ ] **AC-9:** Resilience4j: `@CircuitBreaker(name="core-service")` + `@Retry(name="core-service")` on all three methods. Retry policy: 3 attempts with exponential backoff (100ms, 500ms, 2s) — retryable on 5xx + network errors, NOT on 4xx.
- [ ] **AC-10:** A `CoreServiceUnauthorizedException` (runtime) signals a clear 401 from Core. A `CoreServiceUnavailableException` signals 5xx / transport failure / open circuit. Filter distinguishes these for AC-5 vs AC-6.
- [ ] **AC-11:** `UserIdentity` is a Java `record` with fields matching the BFF contract from story 1.4 (at minimum: `userId`, `email`, `name`, `department`, `roles: List<String>`, `csiOwnership: List<CsiOwnershipEntry>`). If story 1.4 agrees a different shape, `CoreServiceClient` includes an adapter to normalize to this internal record.

### Group C — Identity cache

- [ ] **AC-12:** A Caffeine cache named `identity-cache`, `expireAfterWrite=60s`, `maximumSize=10000`, keyed on the `put_session` cookie value (String). The filter's cookie-introspection path reads through this cache. On cache miss, calls Core. On cache hit, skips Core call entirely. Metric `checks_identity_cache_hits_total` / `_misses_total`.

### Group D — CORS

- [ ] **AC-13:** `CorsConfigurationSource` bean allows: explicit origin allowlist from `checks.cors.allowed-origins` (env var `CHECKS_CORS_ALLOWED_ORIGINS`, comma-separated); NO wildcard; `allowCredentials=true`; methods `GET,POST,PUT,PATCH,DELETE,OPTIONS`; allowed headers `Authorization,Content-Type,Idempotency-Key,X-Requested-With`; exposed headers `Retry-After,X-RateLimit-Remaining,Location`. Applied to `/api/**`.
- [ ] **AC-14:** `CorsAllowedOriginsConfigIT` asserts that a request from an allowlisted origin gets `Access-Control-Allow-Origin: <that-origin>` + `Access-Control-Allow-Credentials: true`; from a non-allowlisted origin, the CORS headers are absent (browser blocks).

### Group E — Authorization

- [ ] **AC-15:** `CsiOwnershipEvaluator` bean exposes:
  - `canRead(Authentication auth, String csiId)`
  - `canWrite(Authentication auth, String csiId)`
  - `canExecute(Authentication auth, String csiId)`
  - `isAdmin(Authentication auth)` → true if roles contain `checks-admin` or `platform-admin`.
- [ ] **AC-16:** Admins bypass all CSI ownership checks. For non-admins, `canWrite/canExecute` require the csi to be in `csiOwnership` with role `owner` (or as agreed in 1.4 contract); `canRead` also permits `contributor` + `viewer`.
- [ ] **AC-17:** `@RequiresPermission("checks.monitors.edit")` custom annotation + `PermissionAspect` (Spring AOP) calls `CoreServiceClient.checkPermission()`. Result cached per (userId, permission) for 60s in a separate Caffeine cache `permission-cache` (same bounds as identity cache). On `allowed=false`, throws `AccessDeniedException` → Spring Security converts to 403.
- [ ] **AC-18:** `@PreAuthorize("@csiOwnershipEvaluator.canWrite(authentication, #csiId)")` works on a sample protected endpoint (unit-style test via `@WebMvcTest` is acceptable).

### Group F — Integration + end-to-end

- [ ] **AC-19:** `BffFilterHappyPathIT` (full Spring Boot + WireMock for Core): authenticated request with valid cookie → Core returns identity → downstream endpoint sees `SecurityContextHolder` populated.
- [ ] **AC-20:** `BffFilterUnauthIT`: missing cookie → 401 with spec-shaped JSON body.
- [ ] **AC-21:** `BffFilter503IT`: Core returns 500 → filter returns 503 + `Retry-After: 5`, body `AUTH_TEMPORARILY_UNAVAILABLE`. Never a demo fallback.
- [ ] **AC-22:** `GatewayHeadersTrustIT`: `X-User-Id` header present → Core is NOT called; identity comes from headers. (Phase-2 forward-compat.)
- [ ] **AC-23:** `IdentityCacheIT`: two back-to-back requests with the same cookie → Core called once; TTL expiry tested via time-forwarding of Caffeine ticker.
- [ ] **AC-24:** `PermissionAspectCacheIT`: `@RequiresPermission` hit twice → Core `/authz/check` called once.
- [ ] **AC-25:** JaCoCo coverage for the security/auth packages ≥ 80%.

### Group G — Explicit non-behaviors (anti-regression)

- [ ] **AC-26:** The application dependency list does NOT include `spring-boot-starter-oauth2-resource-server` (guarded by a Gradle task that fails the build if the dependency shows up — prevents accidental reintroduction of the pre-DEBT-04 pattern).
- [ ] **AC-27:** No Spring bean attempts to fetch JWKS from COIN. A grep-based build check (in `./gradlew check`) fails if any config references `spring.security.oauth2.resourceserver.jwt.issuer-uri` or the old `CHECKS_OIDC_ISSUER` env var.

## Implementation Notes (for @dev)

- **Start with `UserIdentity` + `CoreServiceClient`.** Pin shape to whatever `bff-identity-contract.md` (story 1.4) specifies. If the contract has evolved since this story was drafted, defer to the committed doc.
- **Resilience4j config:**
  ```yaml
  resilience4j:
    circuitbreaker:
      instances:
        core-service:
          slidingWindowSize: 20
          minimumNumberOfCalls: 10
          failureRateThreshold: 50
          waitDurationInOpenState: 30s
    retry:
      instances:
        core-service:
          maxAttempts: 3
          waitDuration: 100ms
          exponentialBackoffMultiplier: 5
          retryExceptions:
            - java.io.IOException
            - org.springframework.web.client.RestClientException
          ignoreExceptions:
            - com.citi.put.checks.secur.CoreServiceUnauthorizedException
  ```
- **Cache invalidation:** on logout (if the module ever adds a logout hook — currently out of scope), invalidate that cookie's identity cache entry. For M1, 60s TTL is the only invalidation mechanism.
- **Filter vs. `AuthenticationProvider`:** using a filter (not an `AuthenticationProvider`) keeps the Core introspection out of Spring Security's standard JWT pipeline. This avoids accidental interactions with `oauth2-resource-server` patterns.
- **Event ordering:** `UserAuthenticatedEvent` is published **after** `SecurityContextHolder` is populated but **before** the chain continues. Story 1.6's listener is `@Async` (applicationTaskExecutor from 1.8) — does NOT block the request.
- **MDC population:** set `traceId` (from `X-B3-TraceId` or `traceparent` if present; else generate UUID) + `userId` (from resolved identity) in the filter. The `MdcTaskDecorator` (1.8) propagates these across `@Async` boundaries. Clear MDC in a `finally` on filter exit.
- **Anti-regression checks (AC-26/27):** implement as Gradle `doLast` on the `check` task — simple text scans of `build/dependencies.txt` + `application*.yml`. Don't over-engineer.
- **Split execution:** implement 1.5a first (filter + client + CORS) and integration-test against WireMock. Once 1.5a is green, add 1.5b (evaluator + aspect). Keeps the review surface manageable.
