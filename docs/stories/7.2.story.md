## User Story

**As the** CronDispatcher polling for due schedules every 10 seconds,
**I want** dispatching to be non-blocking (fire-and-forget) with a dedicated lightweight executor for the dispatch transaction, backpressure that skips polling when in-flight count exceeds the execution capacity, and tuned batch/poll configuration,
**so that** the dispatcher achieves 3,000 dispatches/minute without the `CompletableFuture.allOf().join()` blocking the scheduler thread for the duration of the slowest execution.

---

## Problem Statement

### Problem 1: `join()` blocks the scheduler

`CronDispatcher.pollAndDispatch()` submits all dispatches via `CompletableFuture.runAsync(() -> dispatchSingle(s), checkExecutor)` and then calls `.join()`. This blocks the scheduler thread until every dispatch + execution completes. At p99 (30s), a batch of 500 can block for 30+ seconds, holding the ShedLock lock and preventing the next poll cycle.

**Effective throughput with join:** `500 / (execution_p99 + poll_delay) = 500 / 40s ≈ 750/min` — well below the 3,000/min target.

### Problem 2: Dispatch and execution share the same executor

`dispatchSingle()` runs on `checkExecutor`, which is gated by the execution semaphore. But the dispatch transaction (read schedule, advance nextExecutionAt, save) is a lightweight DB operation (~5ms), while the actual check execution (HTTP call, TCP probe) takes 200ms–60s. Mixing both on the same semaphore means dispatch capacity is throttled by execution capacity.

### Problem 3: No backpressure

If the executor is saturated (all 250 permits in use), the next poll still fetches 500 schedules and submits them. The semaphore's `acquire()` blocks each virtual thread, growing the virtual thread count unboundedly. No mechanism skips the poll when the system is overloaded.

## Acceptance Criteria

### Dedicated dispatch executor
- [ ] **AC-1:** New `dispatchExecutor` bean in `AsyncConfig` — a virtual-thread executor with its own semaphore (permits = batch-size, default 500). This executor runs `dispatchSingle()` (the DB transaction), NOT the check execution.
- [ ] **AC-2:** `CronDispatcher` injects `dispatchExecutor` (for dispatch transactions) and `checkExecutor` (for execution). `dispatchSingle()` runs on `dispatchExecutor`; `executeAsync()` is submitted to `checkExecutor`.

### Fire-and-forget (no join)
- [ ] **AC-3:** `pollAndDispatch()` no longer calls `CompletableFuture.allOf(futures).join()`. Dispatches are fire-and-forget. The method returns as soon as all dispatch transactions are submitted.
- [ ] **AC-4:** The ShedLock `lockAtMostFor` is reduced from `5m` to `2m` since the poll method no longer waits for execution.
- [ ] **AC-5:** `batch_dispatch_duration` timer now measures only the dispatch submission time (not execution time).

### In-flight tracking + backpressure
- [ ] **AC-6:** `CronDispatcher` maintains an `AtomicInteger inFlightCount` that increments when `executeAsync()` is submitted and decrements in the `finally` block of execution.
- [ ] **AC-7:** At the start of `pollAndDispatch()`, if `inFlightCount.get() >= checks.executor.max-concurrency` (from 7.1), the poll is skipped entirely with a debug log: `dispatch_skipped reason=backpressure inFlight={n} maxConcurrency={m}`.
- [ ] **AC-8:** Gauge `checks.dispatch.in_flight_count` exposes the current in-flight value.
- [ ] **AC-9:** Counter `checks.dispatch.polls_skipped_total` (tag: `reason=backpressure`) tracks how often backpressure triggers.

### Config tuning
- [ ] **AC-10:** Default `checks.scheduling.batch-size` changed from 100 to 500.
- [ ] **AC-11:** Default `checks.scheduling.poll-interval-ms` changed from 30000 to 10000.
- [ ] **AC-12:** `ShedLock lockAtLeastFor` remains 10s (ensures minimum gap between polls even if the method returns instantly).

### ReportDeliveryDispatcher parity
- [ ] **AC-13:** `ReportDeliveryDispatcher.pollAndDeliver()` is refactored to use `CompletableFuture` parallel dispatch (matching CronDispatcher pattern) instead of sequential `for` loop.
- [ ] **AC-14:** In-flight tracking and backpressure applied to ReportDeliveryDispatcher with the same pattern.

### Tests
- [ ] **AC-15:** `NonBlockingDispatchIT`: trigger `pollAndDispatch()` with a slow-executing check (5s sleep) → verify the method returns in < 1s (proving it doesn't join).
- [ ] **AC-16:** `BackpressureIT`: saturate executor with `max-concurrency` tasks → trigger `pollAndDispatch()` → verify poll is skipped and counter incremented.
- [ ] **AC-17:** `DispatchThroughputIT`: dispatch 500 schedules → verify all 500 dispatch transactions complete and `nextExecutionAt` is advanced for each.
- [ ] **AC-18:** `ReportDeliveryParallelIT`: verify report delivery uses parallel dispatch.
- [ ] **AC-19:** Existing `CronDispatcherIT`, `CronDispatcherBatchIT`, `ParallelDispatchIT` still pass.
- [ ] **AC-20:** JaCoCo coverage ≥ 80% for modified classes.

## Implementation Notes

- **Fire-and-forget safety:** If the JVM crashes between dispatching and execution, the check misses one cycle but `nextExecutionAt` is already advanced. The next poll picks it up on the following cycle. This is acceptable — the alternative (not advancing until execution completes) risks duplicate dispatches.
- **In-flight counter accuracy:** The counter must decrement in `finally` to handle both success and exception paths. A leaked increment (missing decrement) would eventually trigger permanent backpressure — add a watchdog log if `inFlightCount` exceeds `max-concurrency × 1.5`.
- **Dispatch executor sizing:** Permits = batch-size because all 500 dispatch transactions should run concurrently (they're fast ~5ms DB ops). The limiting factor is Hikari, not the dispatch executor.
- **ReportDeliveryDispatcher:** Simpler than CronDispatcher — no in-flight count needed since report delivery volume is low. Just parallelize the loop.
