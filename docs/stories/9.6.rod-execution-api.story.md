# Story 9.6 — External API for Check Executions (ROD Integration)

| Field | Value |
|---|---|
| **Size** | M (spike + thin API) — may split if Coin decision expands scope |
| **Depends on** | Existing check execute APIs; **Coin capability check** (gate before choosing auth mechanism) |

---

## User Story

**As** ROD (release management tool),
**I want** an external API to manage / trigger Checks executions, authenticated in a machine-friendly way,
**so that** we retain the same capability we have today against DailyChecks (DC), and can call PUT Checks instead of DC during release workflows.

---

## Problem Statement

ROD already integrates with **DailyChecks (DC)** to drive check executions as part of release management. PUT Checks must expose an equivalent **external** capability.

Functional surface is expected to be relatively small (trigger / manage executions for known checks). The main complexity is the **auth layer**:

| Today (DC) | Target (PUT Checks) |
|---|---|
| Basic auth | Prefer **API key** or **M2M** (client credentials) — whichever is easier and supported |

PUT Checks and **EAMP** use **Coin** as the auth solution. We must **not** invent a one-off auth scheme without first validating what Coin supports and what EAMP patterns already exist for service-to-service access.

Interactive user session auth (BFF cookie / Core introspection for the SPA) is the wrong model for ROD.

---

## Goals

| Goal | Outcome |
|---|---|
| **Coin-first decision** | Documented recommendation: API key vs M2M (or Coin-supported equivalent), based on Coin capabilities + EAMP precedent. |
| **External execution API** | ROD-callable endpoints to trigger / manage check executions (parity with DC usage, mapped to Checks model). |
| **Non-interactive auth** | Machine client can authenticate without a human browser session. |
| **Safe rollout** | Scoped credentials, auditability, and clear ops runbook for ROD onboarding. |

---

## Phase 0 — Coin / EAMP discovery (hard gate)

Before implementing auth or exposing production credentials:

- [ ] **AC-1:** Spike / outreach: what Coin supports for **non-interactive** clients (M2M / client credentials, API keys, service accounts, etc.).
- [ ] **AC-2:** Confirm how **EAMP** (or sibling PUT services) authenticates machine callers today — prefer reuse over a Checks-only invent.
- [ ] **AC-3:** Decision record (short ADR or story note): chosen mechanism (**API key** vs **M2M** vs other Coin-supported option), rationale (“easiest that Coin supports”), and rejected options (including “copy DC basic auth” unless Coin/security explicitly allows it).
- [ ] **AC-4:** Implementation of external auth **does not start** until AC-3 is agreed with security / platform (or recorded PO+tech exception).

---

## Acceptance Criteria

### A — External execution API (ROD capability)

- [ ] **AC-5:** Document ROD’s current DC usage (which operations: trigger execute, poll status, cancel?, bulk?) so Checks endpoints cover the needed parity — not a full public platform API.
- [ ] **AC-6:** External API allows ROD to **trigger check execution** for a check it is authorized to run (map to existing `POST /checks/{id}/execute` semantics or a dedicated external route).
- [ ] **AC-7:** External API allows ROD to **read execution status / result** needed for release gating (poll by execution id or equivalent).
- [ ] **AC-8:** Contract (OpenAPI or short integration doc) shared with ROD: auth header shape, request/response, error codes, rate limits.

### B — Auth layer (post–Coin decision)

- [ ] **AC-9:** Implement the **chosen** Coin-aligned auth mechanism from AC-3 (API key **or** M2M — not both unless required).
- [ ] **AC-10:** ROD credentials are distinct from end-user BFF sessions; browser cookie auth is not required for these calls.
- [ ] **AC-11:** Unauthorized / invalid credential → 401; authenticated but not allowed for that check/CSI → 403.
- [ ] **AC-12:** Credential lifecycle documented: issue, rotate, revoke (even if v1 is manual/ops-assisted).

### C — Authorization & safety

- [ ] **AC-13:** Execution calls are constrained (e.g. CSI ownership / allowlisted checks / ROD client scope) — ROD cannot execute arbitrary checks platform-wide without policy.
- [ ] **AC-14:** Audit trail: who/what client triggered the execution (client id or key id in logs/audit), correlatable to execution records.
- [ ] **AC-15:** Rate limiting appropriate for machine callers (reuse or extend existing execute limits).

### D — Quality & handoff

- [ ] **AC-16:** Integration tests: valid credential can execute + poll; invalid credential rejected; over-scoped access denied.
- [ ] **AC-17:** ROD onboarding runbook: how to obtain credentials, base URL, example curl, and difference vs DC basic auth.

---

## Scope

- Discovery of Coin (+ EAMP) support for M2M / API key style auth.
- Decision + implementation of one external auth mechanism.
- Minimal external API surface for ROD to manage check **executions** (trigger + status as needed for parity).
- Docs/contract for ROD.

### Out of scope

- Full CRUD of check **configuration** for ROD (unless DC parity spike proves it is required — default is executions only).
- Replicating DC basic auth “as-is” without Coin/security review.
- Replacing interactive user auth (BFF / Core) for the SPA.
- Broader public developer platform / third-party marketplace APIs.
- ROD UI changes (owned by ROD team).

---

## Suggested approach (non-binding)

1. **Spike Coin** — client credentials / API keys / service principals; talk to EAMP owners.
2. **Pick easiest Coin-supported option** — document in AC-3.
3. **Thin adapter** — external route(s) or gateway that authenticate the machine client, then call existing execute/status services with a service identity.
4. **Hand ROD the contract** — migrate their DC client to Checks.
