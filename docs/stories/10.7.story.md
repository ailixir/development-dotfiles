## User Story

**As the** Checks squad accepting on-demand Studio runs on an API that runs three replicas scaling to six, dispatching them to a runner that holds no database, and showing a support engineer live progress,
**I want** acceptance, dispatch, admission, progress and recovery to be durable compare-and-set operations against PostgreSQL, with progress reaching the browser over SSE snapshots read per pod from committed state,
**so that** a duplicate execute never produces two runs, an ambiguous send is never replayed into a second browser, a restart at any point yields a truthful result rather than a repeated effect, a late report can never rewrite finalized history, and a callback landing on one pod is visible to a subscriber on another without a broker, a sticky session or an in-memory registry.

## Problem Statement

This is where the reliability guarantees of Epic 10 actually live. Everything upstream produces something durable *for this story to protect*: 10.4 the immutable revision, 10.1 the ledger and the snapshot contract, 10.6 a runner that asks permission before it launches a browser and retries its terminal report until acknowledged. None of that is worth anything if the other side of those HTTP calls is not exactly once.

Today the other side barely exists:

| Required | Present on this branch |
|---|---|
| Acceptance transaction with durable principal-scoped idempotency, quotas, readiness and preflight (§5.1.2) | `StudioService.executeTest` writes a `PENDING` row and a ledger row, and its own Javadoc says "story 10.7 replaces this with the full acceptance transaction, quotas, readiness checks and the dispatcher" |
| A dispatcher that claims queued ledger rows with a lease and records an attempt before the send (§5.1.3–5.1.4) | Nothing. `StudioDispatchLedgerRepository` has exactly one finder |
| `POST /internal/studio/executions/{id}/admission` and `.../progress` (§8.4) | Declared in the frozen contract as `x-not-yet-implemented: true`, `x-implemented-by: '10.7'`. No handler, no route |
| A restricted-service-identity chain for `/internal/**` (§8.4, §9.1) | `SecurityConfig` ends `anyRequest().permitAll()`, so an unmatched `/internal/**` path is **open** |
| CSI enforcement on every Studio route (§9.1) | `StudioController` carries no `@RequiresPermission` and no CSI check on any route. `CsiOwnershipEvaluator.canRead/canWrite/canExecute` exist and are called only from `StudioService.listExecutions` |
| Pending and running reapers, finalization reconciliation (§5.4) | Nothing |
| `GET /executions/{id}/events` (§5.5) | `x-not-yet-implemented: true`, `x-implemented-by: '10.7'` |
| The ledger's `state` CHECK constraint | `V13` line comment: *"The CHECK constraint is deliberately NOT added here: story 10.7 owns the final dispatcher state machine and adds it then."* |

**This story absorbed roughly thirteen criteria from story 10.6.** 10.6 was drafted with the API half inside it and redrafted to runner-only on 2026-09-11, because §10.6's scope line ends *"No DB/vault/CSI/LLM access"* and §9.2 states the runner *"has no platform user session or DB/vault/CSI/LLM credentials"*. 10.6's Out-of-scope section names the transfer explicitly and this story owns every item on it: the admission compare-and-set **itself**; persisting progress and terminal reports and de-duplicating them by `(attemptId, runnerSequence)`; rejecting out-of-order and superseded-attempt reports; persist-before-acknowledge; snapshot-revision assignment; restart recovery; the pending and running reapers; finalization reconciliation; ambiguity classification; the `/internal/**` server-side chain; execute acceptance; dispatcher leases; secret resolution at dispatch; the kill switch; and SSE.

Two facts shape the SSE half before any code is written. The production Helm values configure **three API replicas scaling to six**, so a runner callback and a browser subscription reach different pods and an in-memory emitter registry is wrong by construction, not merely inelegant. And `ChecksStudioPage` already polls execution snapshots every 700 ms, so the rendering exists; what is missing is progress reaching persistent state at all, which the SSE assessment names as "the main shared implementation effort".

## Acceptance Criteria

### The frozen contract

- [ ] **AC-1:** The two API-side internal routes — `POST /internal/studio/executions/{id}/admission` and `POST /internal/studio/executions/{id}/progress` — and the public `GET /executions/{id}/events` are implemented and conform to `docs/specs/studio/openapi.yaml`. Each is served at the path the document declares under its **own path-item `servers` entry** (ADR-002 §3.1): the two callbacks at `{apiInternalBaseUrl}` + `/internal/studio/...`, **never** under the document base `/api/v1/studio`, which a generator would otherwise compose into `/api/v1/studio/internal/studio/...` — a path nothing serves. All three `x-not-yet-implemented: true` / `x-implemented-by: '10.7'` markers are removed, which arms `StudioContractTest.declaredOperations` against real routes. **ADR-002 O-4 closes here:** `AdmissionResponse` and both callback response bodies gain `additionalProperties: false` with every field named, now that a producer exists — the ADR left them open only because closing a schema against an imagined producer is how the INT-4 divergence happened. Conformance is asserted on the **serialized bytes** the API receives and serves, in both directions, not on the objects behind them. The runner's own contract test (10.6 AC-1) must stay green against the amended document; the amendment is additive to schemas the runner produces.

### The dispatch ledger's state machine

- [ ] **AC-2:** The `state` CHECK constraint `V13` deferred to this story is added by a **forward-only migration** (see Implementation Notes — this is the one genuinely absent artefact and the story assigns it no version). The enumerated set is exactly `V13`'s provisional list, unchanged: `QUEUED | CLAIMED | DISPATCHING | ADMITTED | RUNNING | FINALIZING | DONE`. It is unchanged deliberately — `V13` already ships three partial indexes built for this vocabulary and for a **single absorbing terminal state** (`state IN ('QUEUED','CLAIMED','DISPATCHING')`, and `state <> 'DONE'` twice), so widening or renaming the set would silently strand the indexes the reapers depend on. The ledger's `state` is a **dispatch** state and never an outcome: `DONE` covers success, error, disablement and reaped work alike, and the outcome plus `error_code` live on the execution history row (§8.2) and are not duplicated here. A second CHECK makes admission identity all-or-nothing — an `admission_id` may not exist without both an `attempt_id` and a `runner_instance_id` — because a half-written identity is a CAS guard with a hole in it. A test asserts each rejected value fails at the database, not in Java.
- [ ] **AC-3:** Every state transition is enforced by the `WHERE` clause of the single `UPDATE` that performs it, and the affected-row count is the verdict: `1` is success, `0` is the conflict, and `0` is **never** treated as success or retried into success. The permitted set, and no other: `QUEUED→CLAIMED→DISPATCHING→ADMITTED→RUNNING→FINALIZING→DONE`; `CLAIMED→QUEUED` (lease expiry with no attempt issued); `DISPATCHING→QUEUED` (a **definite** runner `429` only, and the next send must carry a fresh `attempt_id`); and `*→DONE` from any non-terminal state for the reapers and the kill switch. **Nothing leaves `DONE`.** The guard is **intrinsic to the statement** and may never depend on a companion write by another class, a preceding `SELECT`, or a Java-side check that the statement then trusts — story 10.4's QA round rejected that alternative because any future writer silently reopens the hole. A test enumerates the full transition matrix and asserts every disallowed pair updates zero rows.

### Authorization

- [ ] **AC-4a:** Every Studio route enforces identity and CSI permission **on the server**, before any work. Readers (`CsiOwnershipEvaluator.canRead`) may reach `GET /tests`, `GET /tests/{id}`, `GET /executions`, `GET /executions/{id}` and `GET /executions/{id}/events`; owners and explicitly authorized administrators (`canExecute`) may reach `POST /tests/{id}/execute`. Lists are scoped **before** paging — `listExecutions` already does this and `listTests` and the per-id reads must match it. Historical and media access uses the **execution's own immutable `csi_id`**, never the parent test's current value and never a mutable parent lookup, **including for soft-deleted tests**. Wrong identity, a cross-CSI execution id, a cross-CSI test id and a missing permission each reject with a code and no test or execution detail — a `403` must not disclose existence, and a `404`-shaped answer must not be reachable by probing a CSI the caller cannot read. Verified here against identities the test supplies through the existing header path and `CsiOwnershipEvaluator`.
- [ ] **AC-4b:** *(Deferred — `ED-02`)* Absent identity failing closed, the trusted gateway stripping and replacing identity headers so a forged `X-User-Id` cannot impersonate, and the documented CSRF control for cookie-authenticated mutations — all verified **through the real ingress** in **story 10.18**, which `ED-02` gates. This story adds no route that depends on those being true today.
- [ ] **AC-5:** The epic's release-ordering requirement that **"production auth bypass is absent before pilot" cannot close in this story, and is recorded rather than quietly assumed.** `BffSessionAuthenticationFilter.isCoreServiceBypassed()` returns a hardcoded `true` and `applyTemporaryCsiReadBypass` widens roles on read routes; both are `ED-02` and both are removed in **10.18**. This story **adds no new bypass and removes none**, and asserts the narrower property that is decidable today: its authorization decisions are taken from `CsiOwnershipEvaluator` against the identity in the security context, so a test that supplies a non-bypassed identity with the wrong CSI is rejected. The **23 pre-existing `ED-02` integration failures** measured at story 10.5 are the baseline; this story must not increase that count, and the failing set is compared class by class before and after and recorded in the Dev Agent Record.
- [ ] **AC-6a:** `/internal/**` is served by its **own `SecurityFilterChain`** with higher precedence and `securityMatcher("/internal/**")`. It requires the restricted service identity the contract declares (`serviceIdentity`, HTTP bearer), compared in **constant time**, and rejects a missing, blank, malformed or wrong credential with `401`/`403` **before any handler work and before the request body is read** — the body carries a code and no execution detail. The chain runs **no** `BffSessionAuthenticationFilter`, establishes no user session, performs no CSI evaluation, and does not run the idempotency or rate-limit filters, which wrap user mutations and have no meaning for a service-to-service callback. This is not a hardening nicety: the existing chain ends `anyRequest().permitAll()`, so **`/internal/**` is open today** — a test asserts both callbacks are unreachable without service identity and that the credential never appears in a URL, a query parameter or a log line. A second test asserts the internal operations are absent from the public springdoc surface.
- [ ] **AC-6b:** *(Deferred — `ED-02` / `ED-06`, story 10.18)* Proof that `/internal/**` is not reachable **through public ingress** and that internal transport is encrypted (§8.4). A filter chain cannot prove a network property; 10.18 owns the deployment that can.

### Execute acceptance

- [ ] **AC-7:** `POST /tests/{id}/execute` is one transaction that snapshots the confirmed revision id, the CSI, the environment, the nonsecret configuration, the principal and the declared references onto the history row; inserts the `PENDING` history row **plus** its ledger row; and persists the principal-scoped `(idempotency_key, request_digest)` mapping **in that same transaction**. `202` is returned only after commit. Two concurrent executes with the same principal and key, issued **from two application contexts against one database**, yield exactly **one** execution: the loser observes the `uq_studio_dispatch_ledger_idempotency` unique violation and returns the winner's execution rather than creating a second history row. The guard is the **unique index itself**, not a read-then-insert — the in-memory idempotency filter alone is insufficient across replicas (§5.1.2), and so is a `SELECT` followed by an `INSERT`. Same key with a different digest returns `409` and creates nothing. The digest covers the route and the request-determined inputs only, never server state, because returning the same execution is the whole point of a retry; the current `requestDigest(testId, principal)` is widened accordingly. Proven by an **interleaving** test that holds the first transaction open past the second's insert.
- [ ] **AC-8a:** Acceptance rejects an unready test with `409 COMPILE_REQUIRED` and an incompatible one with `409 RUNTIME_INCOMPATIBLE`, with a body that explains what needs confirmation or compatibility work (§4.6, §8.3). **Readiness must not be expressed as `compile_status = 'READY'`.** Story 10.4's ISSUE-003 records that `beginCompile` is unconditional on current status, so a failed *optional* recompile drives a confirmed, unedited draft `READY → COMPILING → STALE`; a `READY` check would then refuse to run an artifact the user already reviewed and confirmed. The predicate keys on **`confirmed_revision_id` still matching both the draft's `source_revision` and `configuration_revision`** and the revision's `artifact_hash`. That predicate belongs to 10.8, so this story calls a single named seam whose only implementation here is that form — 10.8 replaces one implementation rather than hunting a condition scattered across the acceptance path. **The seam's shape is fixed here by @po so the two stories cannot produce two of it:** this story declares the interface `ExecutionReadiness` with one method returning a verdict type that can already carry `COMPILE_REQUIRED` and `RUNTIME_INCOMPATIBLE`, and supplies a provisional implementation; **10.8 supplies `ExecutionReadinessService` as the full implementation of that same interface and deletes the provisional one.** Neither story introduces a second type, and the acceptance path is wired to the interface, never to a concrete class. The falsifying test is explicit: a confirmed, unedited draft whose `compile_status` was pushed to `STALE` by a failed optional recompile **is accepted**, and an implementation that checks `compile_status` must fail it.
- [ ] **AC-8b:** *(Deferred to **story 10.8**, bounded compile pipeline and readiness gate)* The complete §4.6 predicate, including per-step validation state, current target policy and runtime-compatibility revalidation, and the `409` diagnostics that go with them. 10.8 `depends_on: ["10.6"]` and not on this story, so this is a scope deferral rather than an external block; what this story owes 10.8 is a seam that does not have to be unpicked and a gate that does not contradict the predicate.
- [ ] **AC-9:** Acceptance enforces input limits and **global and per-CSI pending quotas**, returning `429` when full (§5.1.1, §5.4 "bound … pending rows per CSI/globally"). The quota decision and the insert are **one critical section**, so two concurrent accepts at the limit cannot both observe room: a read-then-insert must fail the interleaving test in which both transactions are held open across each other's count. A test asserts the per-CSI quota does not consume the global one twice and that a full CSI does not block a different CSI.
- [ ] **AC-10a:** Variable and secret **references are preflighted without resolving or persisting any value** (§5.1.1): the declared names must be references this CSI is permitted to use, and an unknown or unpermitted reference is `400` with a code naming the reference, never its value. Resolution happens at dispatch (AC-13a) and nowhere else. A secret canary planted in the stub resolver appears in **no** history row, **no** ledger column, no structured log line, no error body and no SSE payload — asserted on the serialized bytes and on the committed rows, in plain, URL-encoded, double-encoded and base64 forms.
- [ ] **AC-10b:** *(Deferred to **story 10.17**, `ED-02`)* Real vault integration and real secret-use authorization. The `SecretsService` stub cannot satisfy staging acceptance; 10.17 `depends_on: ["10.7"]` and owns the credentialed path end to end. This story ships the seam and the canary, not the vault.
- [ ] **AC-11:** The **kill switch** is deployment configuration (§8.5) under the existing `studio:` block. When execution is disabled, all five properties hold in one scenario:
  - new `POST /tests/{id}/execute` returns **`503`** with `DISPATCH_DISABLED` — the code already exists on `ExecutionErrorCode`;
  - **queued undispatched work is closed explicitly**, not left to a deadline: rows in `QUEUED` or `CLAIMED` become history `ERROR` / `DISPATCH_DISABLED` and ledger `DONE`, and the closure is idempotent so a second pass changes nothing and bumps no revision;
  - **admitted work finishes**: `ADMITTED`, `RUNNING` and `FINALIZING` rows are untouched and their reports are still accepted and applied;
  - **reads, callbacks and recovery stay active** — `GET /executions`, `GET /executions/{id}`, `GET /executions/{id}/events`, the video route, both internal callbacks and both reapers;
  - re-enabling does **not** resurrect a closed row.

### Dispatcher

- [ ] **AC-12:** The dispatcher runs on the **worker profile only** (the existing `worker` profile / `checks.worker-mode`), with its own bounded thread and connection budget, and the API profile never claims a row — asserted by starting an API-profile context and observing that a queued row is never claimed. The claim is one conditional `UPDATE` whose `WHERE` carries `state = 'QUEUED'` and an expired-or-absent lease, and whose affected-row count is the verdict. Two dispatcher instances racing for the same queued row: exactly one claims, proven by an interleaving test that holds the first transaction open across the second's attempt.
- [ ] **AC-13a:** **Immediately before the send, and after the claim**, the dispatcher rechecks that execution and CSI authorization still hold and that secret use is still permitted, and resolves reference values then and only then (§5.1.3). This is the first half of the pair the dispatcher must re-verify before the send; AC-13b is the second half and is externally gated. A revoked permission or a vanished reference becomes a **terminal `ERROR` with an explicit code** — never a retry, never a silent skip. §5.1.3 requires the code but no source names it, so the two names added to `ExecutionErrorCode` are a **recorded decision, not an inference**. **Ratified by @po on 2026-09-11: `AUTHORIZATION_REVOKED` and `REFERENCE_UNAVAILABLE`.** Both are dispatcher-assigned at the recheck, both name a condition only the dispatcher can observe, and both are disjoint from the reaper-owned `START_TIMEOUT`/`STALE`/`TIMEOUT` and from every value the runner may emit, so AC-16's disjointness and 10.12's AC-17 intersection test both continue to hold — 10.12's test must read this enumeration rather than a copy of it, and its criterion has been corrected to do so. Resolved values are ephemeral: never written to the ledger, the history row, a log line, a retry buffer, a manifest or an SSE payload, and cleared on every exit path including the error path. Same canary discipline as AC-10a.
- [ ] **AC-13b:** *(Deferred — ADR-002 **O-6** / `ED-04`, story 10.18 SPK-05)* §9.3 requires variable URL destinations to be resolved against the approved-origin policy **at dispatch and again during execution**. ADR-002 O-6 records that whether the approved target and secret-use policy travels **on the job** or is enforced solely at the **egress layer** is unresolved, and that the frozen contract deliberately declares only the reference *names* rather than a field nobody implements. This story therefore neither invents the job field nor claims the enforcement; it records on the execution which policy identity it dispatched under, so 10.18 can bind the decision to an audit trail that already exists. **Deferral confirmed by @po on 2026-09-11; the contract edit is not assigned here.** Adding an approved-target or secret-use-policy field to the job body is a field on a closed runner-consumed body — **ADR-002 §12 Class B**, which an architect must rule on first and which a story may propose but not land. O-6 is still `status: open` and the egress-versus-job question is genuinely unsettled, so assigning the edit to this story would mean inventing a representation for a policy nobody has specified, against Article IV. Recording the dispatched policy identity is the correct minimum: it is decidable today, it costs 10.18 nothing, and it leaves the audit trail in place whichever way SPK-05 rules.
- [ ] **AC-14:** `DISPATCHING` and a **fresh `attempt_id`** are **committed before** the HTTP send (§5.1.4). The ordering is asserted, not assumed: a second connection observes the committed row while the fake runner client is still blocked from returning. An `attempt_id` is never reused across attempts. If the process dies between that commit and the send, §5.1 explicitly permits the outcome to end as **unknown** rather than risk duplicate effects, and AC-29 tests that case.
- [ ] **AC-15:** The runner's response is classified into exactly three outcomes and no fourth:
  - **`202`** — admitted path continues; the API waits for the admission CAS and the `STARTED` report.
  - **`429` is definite non-acceptance** (§5.1 closing paragraph): no durable admission, no browser. It may be retried with `Retry-After` and jitter **within `pending_deadline_at`**, by returning the row to `QUEUED` and issuing a **new `attempt_id`** on the next send. Past the pending deadline it is `ERROR` / `DISPATCH_FAILED`.
  - **Timeout, connection loss, any 5xx, and a `3xx` redirect are ambiguous.** They are **not permission to resend**. No second send, no second attempt; the row stays `DISPATCHING` and recovery resolves it against admission, progress and manifest state (AC-30, AC-32). Automatic HTTP retries are **explicitly disabled** on the dispatcher's client and redirects are **not followed** — a followed redirect is a second dispatch wearing a different name — and a test asserts **exactly one** request left the process for each of the four ambiguous cases.
- [ ] **AC-16:** **The API never copies a runner-supplied `outcome.errorCode` into `ui_test_executions.error_code`.** ADR-002 §6.1 leaves `outcome.errorCode` an open string precisely because every value `ExecutionErrorCode` enumerates is assigned by the **API's dispatcher or reapers**, and the contract's mapping table records the two sets as **disjoint**. The API maps the runner's outcome onto its own vocabulary through an explicit table rather than by string pass-through; the one mapping a source fixes is a parent-enforced total timeout → `ERROR` / `TIMEOUT` (§8.2), and 10.12 owns the rest (ADR-002 O-5). Until then an unmapped runner code persists as `ERROR` with the raw code in the bounded diagnostic text and **never** in `error_code`. The decidable test: plant a runner report carrying `START_TIMEOUT` and assert the persisted `error_code` is not `START_TIMEOUT` — a reaper-owned verdict must not be obtainable by a component that cannot observe the condition.

### Admission CAS

- [ ] **AC-17:** `POST /internal/studio/executions/{id}/admission` is a compare-and-set expressed as **one conditional statement** whose `WHERE` carries every precondition — the execution, the current `attempt_id`, `state = 'DISPATCHING'` and `admission_id IS NULL` — and never as a `SELECT` followed by an `UPDATE`, and never depending on a companion write by another class (AC-3's rule). Verdicts:
  - one row updated → **`200`**, this `(runnerInstanceId, admissionId)` owns the attempt;
  - the **same** `(attemptId, runnerInstanceId, admissionId)` arriving again → **`200` idempotently**, decided by a second conditional statement that matches the identity **exactly**, never by "an admission already exists, close enough";
  - a different `admissionId` or `runnerInstanceId` on an owned attempt, a superseded `attemptId`, a row past `pending_deadline_at`, or a row already `DONE` → **`409`** with a code;
  - an unknown execution → **`409`**: the frozen contract declares `200/400/401/403/409` for this operation and no `404`, so an unknown or expired execution is a definite refusal rather than a status the runner has no rule for.
  No browser may start without a `200`, which is the property 10.6 AC-6 obeys and this criterion supplies.
- [ ] **AC-18:** **Two replicas cannot both grant an attempt, and a lost admission response cannot produce a second one.** Two admissions for the same `attemptId` with different `admissionId`s, issued from two application contexts against one database with their transactions **interleaved** rather than sequenced, yield exactly one `200` and one `409` and exactly one owner. Separately, the **lost-response** case: the API commits the CAS and the runner's read of the response is lost. The runner never re-admits (10.6 AC-9), and this story asserts the complementary property from the API side — a second admission carrying a **new** `admissionId` for the same `attemptId` is refused `409` — so that even a misbehaving or future runner cannot obtain a second owner. A test asserts the fake runner client's `POST /v1/runs` count is exactly one across the whole scenario.
- [ ] **AC-19:** On a successful CAS the API sets `start_deadline_at` (admitted-start; 30 s starting value, §8.5) and `run_deadline_at` (browser runtime cap plus bounded finalization and delivery margins, §5.4), both derived from **persisted timestamps**. **`pending_deadline_at` is a different column with a different origin** and is set at acceptance (600 s pending SLA, §8.5). The separation is tested, not documented: a run that queued for a long time and then started promptly is **not** reaped, and a run that was admitted promptly and then hung **is** — an implementation sharing one timestamp fails one of the two. **Heartbeats never extend `run_deadline_at`** (§5.4), and a test drives repeated progress reports past the deadline and asserts the running reaper still fires.

### Progress and terminal persistence

- [ ] **AC-20:** **The progress handler acknowledges only after commit** (§5.3, §8.4). The ordering is the criterion, not a note: because the runner retries a terminal report byte-identically until acknowledged (10.6 AC-17), an acknowledgement sent before commit loses a terminal result on a crash and the runner has no durable store to replay it from. Asserted two ways — a commit failure injected after the handler's work yields a non-`200`, and the acknowledgement observed by the client is never sent before the row is visible to an independent connection.
- [ ] **AC-21:** Every report is applied by **one conditional statement** whose `WHERE` carries every precondition: `execution_id`, `attempt_id`, `admission_id` and `runner_instance_id` all matching the current owner; `last_runner_sequence < :runnerSequence`; and a current state that permits the transition. Zero rows updated is a `409` with a code and **never** a silent `200`. Specifically:
  - a report from a **superseded attempt** → `409`;
  - a **duplicate delivery of an already-applied `(attemptId, runnerSequence)`** → **`200`, applying nothing**, matching the admission route's duplicate-identity rule and §5.3's "duplicate deliveries must not duplicate logs". Answering `409` here would be a false statement to the runner, which records it as lost ownership. **Confirmed by @po on 2026-09-11 against 10.6's admission semantics:** `409` on the admission route means *competing* admission — a second party is claiming an attempt this one owns — and 10.6 AC-18 makes the runner stop reporting and raise an audit line on any `409`. A re-delivered, already-applied `FINAL` is not a competitor; it is the same owner finishing the job the API told it to retry until acknowledged (10.6 AC-17). The two routes stay symmetric: on **both**, an exactly-matching identity replayed is `200` and applying nothing, and a *differing* identity is `409`. The asymmetry to avoid is answering `409` to a correct actor, which converts a healthy retry into a false ownership-loss record and, worse, teaches operators to ignore the one signal that means a real race. A test delivers the identical `FINAL` bytes three times and asserts one committed state, three `200`s, logs not duplicated, and `snapshot_revision` incremented **exactly once**;
  - a **lower** sequence than the applied one → `409`, applying nothing;
  - **a stale callback cannot regress a final state.** A `PROGRESS` or `FINAL` arriving after the execution is terminal changes nothing and returns `409`. The test drives a **reaper finalization first** and then delivers a late runner report, asserting the persisted history row is unchanged apart from the investigation record §5.3 requires — "recorded for investigation; it cannot silently change history or trigger a new run" — and asserting no new run was dispatched.
- [ ] **AC-22:** `RUNNING` and `browser_started_at` are written **only** by a committed `STARTED` report that carries a non-null `browserStartedAt` and comes from the owning admission — never when the dispatch HTTP call begins, never on a `202`, never by a reaper (§5.1.5, §8.2). And `started_at`, which is the **history partition key** and the public `acceptedAt`, is never changed when the browser begins (§8.2): a test asserts it is identical before and after `STARTED`, because changing it would move the row between partitions.
- [ ] **AC-23:** Every visible state change increments `snapshot_revision` **in the same statement that makes the change**, so a revision can neither be assigned for a change that did not commit nor omitted for one that did. The revision is monotonic per execution, is the SSE event `id`, and is the API's own — `runnerSequence` is never used as the revision (ADR-002 mapping table). §5.3 says *every* visible change, **including reaper and evidence updates**, and those are the two paths a progress-shaped implementation would miss, so each has its own test.
- [ ] **AC-24:** The **`RunnerReport` → `ExecutionSnapshot` projection** is implemented as the mapping table on `RunnerReport` in the frozen contract specifies (ADR-002 §INT-4), with one test per row:
  - `steps[]` → `stepResults[]`, with untouched steps filled **`PENDING`** from the confirmed revision's ordered source (§4.4), so the persisted result carries **one entry per original step** (§8.2). `originalText` comes from the revision and is never echoed by the runner;
  - step status vocabulary is §8.2's `PENDING | RUNNING | PASS | FAIL | SKIPPED`; a report carrying `PASSED`/`FAILED` in a step is a **`400`**, not a silent coercion;
  - `logs[].atMs` → `logs[].at`, **derived by the API as `browserStartedAt + atMs`** and by nothing else (ADR-002 §INT-1, reaffirmed by §11.7). `atMs = 0` is the browser start; `atMs = null` yields `at = null` and is **never** rendered as the epoch and never as the browser start; where `browserStartedAt` is itself null, `at` is null **and so is every reading in that report** — ADR-002 §11.2 makes "a report with `browserStartedAt: null` carries no reading" a contract invariant, and a report that breaks it is a `400`, not a partially-derived snapshot. A test asserts all four cases on the serialized snapshot;
  - `logs[].level` lower-case on the wire, upper-case on the snapshot; `DEBUG` has no runner producer and appears only on API-produced lines;
  - `outcome.result` (`PASSED | FAILED | ERROR`) → `status`; `PENDING` and `RUNNING` stay API-owned;
  - `outcome.errorCode` → **not** copied (AC-16);
  - `evidence.state` (`PENDING | STORED | FAILED | UNAVAILABLE`) → `video.status`; **`AVAILABLE` and `EXPIRED` are decided by the API** against retention, never by a runner that holds no Get or List permission (§6.1, §6.2);
  - `evidence.manifestKey` recorded on the ledger and **not published** on the snapshot;
  - `runtimeVersions` (open) → `runtime` (the §4.6 subset);
  - `runnerSequence` → never `revision`.
  Three rules bind the whole projection, each stated because each is a silent failure otherwise (ADR-002 §11.7, binding):
  - **The API applies no calibration and adds no origin.** Readings arrive already on the recording timeline; `offsetMs = round(startedAtMs)` and nothing more. In particular the API must **never re-base readings against the lowest, first or earliest reading it has seen** — a plausible-looking "fix" that would have concealed the §11.1 defect rather than surfaced it, and which `StepResult.offsetMs` now forbids in the contract. A test plants a report whose first step reading is large and asserts the persisted `offsetMs` is that value, not zero.
  - **`0` is a position, not a missing value.** A null-coalescing or truthiness-based projection that treats `0` as absent loses the one line that anchors the timeline. A test asserts a `0` reading survives the projection distinctly from `null`.
  - **The API rounds once, at persistence.** The wire is fractional by ADR-002 §4.3; `offsetMs` and `durationMs` are `int64` on the public snapshot. No intermediate rounding, and no second rounding on read.
  Two negative tests: a report body carrying a field the closed schemas do not name is a **`400`** (ADR-002 §6.2 — "an open schema over a wire body is not a contract"), and the projection is asserted on the **serialized snapshot bytes**, not on the mapper's return value.
- [ ] **AC-25:** **Evidence never overwrites a known outcome** (§6.1): an upload failure settles `video.status` and leaves `status` alone. `streamComplete` becomes true only once **both** the outcome and the evidence disposition are settled, including evidence failure — an execution reaching a terminal status while video availability may still change does **not** set it. A test asserts `status = FAILED`, `video.status = PROCESSING`, `streamComplete = false`, then settles evidence and asserts `streamComplete` flips **with a new revision**.
- [ ] **AC-26:** The callback is bounded (§5.4): body size, step count, log entries and log-entry length, all from one configuration source. A body over the bound is **`413`** with a code — the status the contract declares — and changes nothing. `logsTruncated` and the contract's `payloadReduced` flag are both **persisted**, not dropped, because they are the API's only record that the runner shed diagnostics to deliver a result it could not replay.
- [ ] **AC-27:** The `ui_tests.last_run_status` projection updates **only** when the finishing execution is newer by `(acceptedAt, executionId)` than the projected one (§8.2). `applyLastRunProjection` exists from 10.1; this story wires the terminal path into it and asserts an **older late completion does not overwrite a newer run**.

### Restart recovery and reapers

- [ ] **AC-28a:** Restart at each of the four points yields a **documented, truthful result without repeating effects**. Each is a test that stops and restarts the dispatcher or API at exactly that point and then asserts the fake runner client's `POST /v1/runs` count is **exactly one**:

  | Restart point | Truthful result | Never |
  |---|---|---|
  | **Before send** — `QUEUED`/`CLAIMED`, lease expired, no attempt issued | Reclaimed and dispatched within `pending_deadline_at` | — |
  | **After admission** — `ADMITTED`, no `STARTED` | Reconciled against admission, progress and manifest state; otherwise `ERROR` / `START_TIMEOUT` at `start_deadline_at` | A second dispatch |
  | **During execution** — `RUNNING`, past `run_deadline_at` | Manifest reconciled; otherwise `ERROR` / `STALE` | A second dispatch; a replay |
  | **After manifest write** — terminal manifest at the deterministic key, delivery lost | The manifest is read at the **known key** and applied idempotently, yielding the **real** result, not `STALE` | Bucket listing; a durable callback URL; a second run |

  And the fifth, ambiguous case §5.1 names explicitly: a crash **between committing the attempt and sending it** ends `ERROR` / `DISPATCH_UNKNOWN` rather than being replayed — *"a dispatcher crash between recording an attempt and sending it may intentionally end as unknown rather than risk duplicate effects."* Ending as unknown is the correct answer here, and a test that "fixes" it into a replay is the failure.
- [ ] **AC-28b:** *(Deferred to **story 10.14** / `ED-03`)* The manifest reconciliation above runs against a **fake store** here, as the manifest recorded under `ED-03`'s fallback requires ("10.7 uses a fake store until 10.14 integration"). Real Sonic keys, write-only runner credentials, read-only API credentials and 30-day lifecycle behaviour are 10.14 and 10.18. The **key derivation itself is not deferred**: the API derives it from immutable execution identity here (AC-31).
- [ ] **AC-29:** The **pending reaper** reclaims only rows for which **no dispatch attempt was issued** — `QUEUED` or `CLAIMED` with an expired lease (§5.4 row 1). Rows in `DISPATCHING` are **never reclaimed**, whatever their lease says, and the test that proves it offers the reaper a `DISPATCHING` row with a long-expired lease and asserts no re-dispatch. Past `pending_deadline_at` without admission the row is closed `ERROR` / `DISPATCH_FAILED`, or `ERROR` / `DISPATCH_UNKNOWN` where the send outcome was ambiguous, and the two are distinguishable from the persisted state rather than from a log line.
- [ ] **AC-30:** The **running reaper** closes the three §5.4 conditions: admitted past `start_deadline_at` → reconcile, else `ERROR` / `START_TIMEOUT`; running past `run_deadline_at` → reconcile the manifest, else `ERROR` / `STALE`; **outcome known but evidence not settled** by its deadline → **preserve the check outcome**, settle evidence `FAILED` or `UNAVAILABLE`, and set `streamComplete`. Both reapers run on the **worker profile**, are bounded in batch size and runtime, and are **idempotent**: a second pass changes nothing and bumps no revision. Every reaper write goes through AC-21's conditional statements, so a reaper can never regress a state a late report already settled — **and symmetrically a late report can never regress the reaper's terminal state**. Both directions are tested as interleaves, in both orders.
- [ ] **AC-31:** Finalization reconciliation reads the terminal manifest at the **deterministic key the API derives from immutable execution identity** (§6.2) — never a runner-supplied key, never a bucket listing, never a durable callback URL. A manifest found before finalization is applied **idempotently** and yields the real outcome in place of an ambiguous timeout. A manifest arriving **after** finalization is recorded for investigation and changes no history and triggers no run (§5.3). A test supplies a manifest whose outcome contradicts the reaper's `STALE` and asserts the manifest wins **before** finalization and loses **after** it.

### SSE

- [ ] **AC-32:** `GET /api/v1/studio/executions/{id}/events` returns `text/event-stream` from Spring MVC `SseEmitter`, authorized against the execution's **immutable** CSI (AC-4a). Event type is `execution.snapshot`; the SSE `id` is the API `snapshot_revision`; `data` is exactly `ExecutionSnapshotDto` — **the same type `GET /executions/{id}` returns**, asserted by serializing both for one execution and comparing the bytes, so the MFE renders one type regardless of transport. Initial delivery and **every reconnect deliver a full current snapshot, never a replay**. Response headers carry `Cache-Control: no-store` and `X-Accel-Buffering: no`. `Last-Event-ID` is accepted and used **only to identify the reconnect**: a value ahead of, behind, equal to, absent from or malformed relative to the current revision all produce the same current snapshot, and a test asserts all five. **No credential appears in the URL or any query parameter.**
- [ ] **AC-33:** **A callback committed on replica A becomes visible to an SSE subscriber on replica B**, and the mechanism is the one the SSE assessment prescribes and no other. Each replica **batches a database read for the execution ids its own subscribers are watching, every 500–1000 ms, and broadcasts only snapshots whose `revision` changed**, with one read shared across local viewers of the same run. There is **no cross-pod messaging, no broker, no sticky session, and no in-memory emitter registry that a callback writes into** — production runs three API replicas scaling to six, so a callback and a subscription reach different pods and an in-memory registry is wrong by construction. The test starts **two application contexts against one database**, posts a runner progress callback to context A, and asserts the subscriber on context B receives a snapshot at the higher revision within a bounded interval. The falsification is required: an implementation that publishes only into an in-memory structure must fail this test. **No transaction and no DB connection is held for a stream's lifetime** — asserted by observing the connection pool's active count while N streams are open and idle.
- [ ] **AC-34:** Streaming is verified over **real HTTP against the running application through the full security and filter chain**, with a client that reads the socket incrementally — **not** a `MockMvc` controller return value, because a buffered mock response does not prove SSE delivery (SSE assessment, *Validation*). Asserted: **two timed snapshots arrive as separate events before the response closes**; an idle interval longer than the heartbeat survives because comment heartbeats arrive every **15 s**; the stream ends at its **bounded lifetime** (60 s starting value) and a client reconnect restores current state; and `streamComplete = true` closes the stream explicitly **after evidence is settled**, while an execution reaching a terminal status with evidence still `PROCESSING` does **not** close it (§5.5, §6.1).
- [ ] **AC-35:** Sends run on a **bounded, dedicated sender executor** — never on the runner-callback thread, never on the batched DB-reader thread, and never on an ordinary check-execution thread, because Servlet writes can block. Per-client pending snapshots are **coalesced**: a reader N revisions behind receives the **current** snapshot, not N of them. Bounds exist and are named for concurrent streams per user and per pod, watched executions per pod, and payload size. **Timeout, client disconnect, error, completion and application shutdown** each release the subscription, drop the execution from the watched set when it was the last viewer, and **return sender capacity** — asserted by counting live subscriptions, watched ids and free sender capacity before and after **each of the five paths**, not by asserting that no exception was thrown. A stalled client is disconnected rather than left holding a sender.
- [ ] **AC-36:** Each connection is authenticated and authorized at open, and **async writers use an explicitly captured subscription identity with refreshed authorization** — never the request thread's `SecurityContextHolder`, which `BffSessionAuthenticationFilter` clears in its `finally` block, so a writer that reads it later reads nothing. A **bounded authorization refresh interval** terminates delivery when CSI access is revoked or the session expires: a test revokes access mid-stream and asserts delivery stops within the interval and the stream closes with an auth-shaped signal rather than silently. Reconnect re-authorizes from scratch.
- [ ] **AC-37a:** The server makes the client's "never fall back around a `401`/`403`" rule **possible**: an unauthorized or forbidden request to the events route answers with the **same status and code the GET snapshot route would**, so a client can distinguish denied access from terminal completion and from a transient disconnect through the ordinary GET. The client-side behaviour — bounded reconnects, GET polling fallback, and never falling back around a `401`/`403` — is **story 10.11**'s; this story owns only the server property and asserts it for both routes.
- [ ] **AC-37b:** *(Deferred — `ED-06`, story 10.18)* Validation through the **real ingress**: the authenticated same-origin cookie route, buffering disabled through the whole proxy chain, idle timeouts above the 15 s heartbeat, and the staging streaming spike (two timed snapshots, heartbeat idle, cross-replica reconnect). A demonstrated gateway incompatibility is **recorded and uses GET fallback without changing this story's execution contract**.

### Bounded resources, tests and gates

- [ ] **AC-38:** **Studio overload does not exhaust ordinary check and REST capacity** (§5.4 — "Test overload while ordinary REST/check traffic continues"). With Studio driven to its bounds in one run — maximum concurrent SSE streams including deliberately **stalled slow consumers**, the pending quota full, the dispatcher saturated and callbacks arriving — ordinary check and REST traffic continues within its normal latency and error budget, measured **in the same test run**, not inferred. Every Studio pool is bounded and **separate**: dispatcher threads and DB connections, the SSE sender executor, the batched-read worker, pending rows per CSI and globally, callback body size, and SSE subscriptions. A test asserts a named bound exists for each and that exceeding it produces a **bounded rejection** rather than unbounded growth.
- [ ] **AC-39:** **Every concurrency property is proven by holding a transaction open and controlling the interleaving**, the rigour story 10.4's QA round established. Sequential calls that merely happen to arrive one after another prove nothing and do not satisfy this criterion. At minimum: duplicate execute across two contexts (AC-7); two dispatchers racing one queued row (AC-12); two admissions racing one attempt (AC-18); a progress report racing a reaper finalization **in both orders** (AC-21, AC-30); the quota at its limit (AC-9); and cross-replica SSE visibility (AC-33). Each of the six ships with a **falsification**: the guard is neutralised through a seam that already exists, the real assertion is shown to go **red**, and the file is restored byte-identically. A guard whose removal leaves the suite green is not a tested guard.
- [ ] **AC-40:** Gates green from a clean build: `./gradlew check` — `spotless`, `checkstyle`, `spotbugs`, `jacoco` — with coverage thresholds **not lowered** and the new packages added to the coverage `include` with their own per-package thresholds so the new surface cannot hide inside the bundle figure. The **23 pre-existing `ED-02` failures measured at story 10.5 are the baseline**: this story adds none, and the failing set is compared class by class before and after and recorded. The runner suite (`studio-runner`, `npm test`) stays green against the amended contract.

## Implementation Notes

- **One migration, and the story does not version it.** Adding a CHECK constraint to a merged table cannot be done by editing `V13`; Flyway is forward-only, so a new migration is **genuinely absent** and this story creates exactly one. Its version number is deliberately left unassigned here: `V12`, `V13` and `V14` are merged and other Epic-10 branches are in flight, so the next free version is a merge-time fact, not a drafting-time one. @dev assigns it at implementation and records it in the File List. **No other migration is expected.** Every column AC-2 through AC-31 needs already exists on `V13` (`attempt_id`, `admission_id`, `runner_instance_id`, `lease_owner`, `lease_expires_at`, `pending_deadline_at`, `start_deadline_at`, `run_deadline_at`, `last_runner_sequence`, `snapshot_revision`, `manifest_key`) or `V14` (`browser_started_at`, `error_code`, `revision_id`, `csi_id`, `principal`, `step_results`, `logs_truncated`, video columns, `runtime_versions`, `snapshot_revision`). If something turns out to be missing, say so in the Dev Agent Record rather than widening the migration silently.
- **The state vocabulary is inherited, not chosen.** `V13`'s three partial indexes are written against `('QUEUED','CLAIMED','DISPATCHING')` and `state <> 'DONE'`. That is evidence of the intended shape — one absorbing terminal state, outcome kept on the history row — and AC-2 adopts it rather than designing a second vocabulary that would strand the indexes the reapers query through.
- **Guards are intrinsic or they are not guards.** Every conditional statement in this story carries its whole precondition in its own `WHERE`, and the affected-row count is the verdict. `CompileStateService` is the in-repo pattern to follow: `UPDATE … WHERE id = ? AND compile_request_id = ? AND source_revision = ? AND configuration_revision = ?`, with `updated != 1` failing loudly. Story 10.4 rejected the alternative for a reason that outlives the class that introduced it — a guard established by a companion write is silently reopened by the next writer who does not know about it.
- **Quotas need a critical section, and the mechanism is @dev's to choose.** AC-9 states the property (two concurrent accepts at the limit yield one accept and one `429`) and not the mechanism. A transaction-scoped advisory lock keyed on the CSI, released by commit, makes the count and the insert one critical section and keeps the guard inside the transaction; a global quota keyed on one constant lock serializes accepts, which is acceptable at Studio volume and should be named as a deliberate cost if chosen. A plain count-then-insert is what the interleaving test exists to fail.
- **Two retry policies, deliberately opposite — the mirror image of 10.6's.** The **dispatch** send is never retried on ambiguity (AC-15), because an ambiguous outcome may already have started a browser. The **terminal report** *is* retried by the runner, byte-identically (10.6 AC-17), which is exactly why the API must be idempotent by `(attemptId, runnerSequence)` and must acknowledge only after commit (AC-20, AC-21). Keep both visible in the code and named in the tests so a future change cannot collapse them into one client default. Automatic retries must be explicitly disabled on the dispatcher's HTTP client and redirects must not be followed.
- **No in-memory registry. This is the one design decision the story fixes outright.** Three replicas scaling to six mean a callback and a subscription land on different pods. The prescribed mechanism is a per-pod set of watched execution ids, a batched read every 500–1000 ms, and broadcast only on a changed `revision`. It is the one design in which the SSE layer reads nothing but committed state — which is also what makes the 10.7c split hold.
- **`SecurityContextHolder` is cleared in a `finally` block.** `BffSessionAuthenticationFilter` clears the context after `chain.doFilter`, so an async SSE writer that reads it later reads nothing. AC-36's "explicitly captured subscription identity" is a consequence of code that already exists, not a precaution.
- **Error-code ownership is a safety property, not bookkeeping.** `ExecutionErrorCode` is dispatcher- and reaper-assigned. A runner string copied into `error_code` would let a component that cannot observe a condition publish the verdict for it — a `START_TIMEOUT` the reaper never decided. AC-16's test is the cheapest guard against it. The two new codes AC-13a needs are a recorded decision (see Open questions), because §5.1.3 requires "an explicit code" and names none.
- **Starting values (§8.5), not commitments.** 10 s admission HTTP timeout, 600 s pending SLA, 30 s admitted-start deadline, recovery deadline = browser runtime cap plus bounded finalization/delivery margins, 15 s SSE heartbeat, 60 s stream lifetime, 500–1000 ms batched read interval. All are tuned against staging measurements (§10). Queue time and browser runtime are separate budgets, and AC-19 makes that testable rather than aspirational.
- **ADR-002's runner items are already closed on this branch.** O-1 (`StepStatus = 'PASS' | 'FAIL' | 'SKIPPED'`) and O-2 (terminal log line `atMs: null`) landed in `86a187267`, and O-3's backend assertion is already rewritten as `internalRoutesStayOffThePublicSurfaceAndNameWhatServesThem`. This story therefore inherits a green contract surface and owes it only O-4 and its own three routes. Do not re-derive these; check them and move on.
- **This story is correct by contract today and correct in fact when 10.12 lands.** ADR-002 §11.7 records the sequencing plainly: the merged runner still injects no run clock, so `executeSteps` falls back to a process-origin `performance.now()` and today's readings are offsets from *process* start while the browser-start line carries a literal `0`. Until 10.12's injected clock lands, this story's derived instants will be absurd on a real runner — an hour-old pod reports a first step at `startedAtMs ≈ 3_600_000`. **Let them be absurd.** The defect is upstream and visible, and compensating for it in API code would put a second, undocumented calibration in the component ADR-002 §11 just ruled must hold none, and it would outlive the cause by years. AC-24's three rules exist to make that non-compensation testable rather than merely intended. Nothing here waits on 10.12: the field 10.12's draft proposed (`recordingOriginMs`) was **rejected** and does not exist, and this story must not be written as though it might.
- **`FOC-03` binds this story's merge order, and the split is how it is paid for.** 10.7 and 10.8 both rewrite `StudioService` (382 lines) and `StudioController` (150 lines) in wave 3. `10.7a` lands on those two files first — it *replaces* `executeTest` wholesale, so the reverse order would have 10.7 delete 10.8's readiness wiring and re-add it by hand, which is exactly how an unconditional gate (10.8 AC-26) goes missing in a merge. 10.8's compile pipeline package, prompt assembly, validate client, diagnostics bounding, `ExecutionReadinessService` and its no-runtime-LLM gate share no file with this story and start in parallel on day one. See the manifest's `FOC-03`.
- **Verify through `GET /executions/{id}` first.** It carries the identical DTO and §5.5 designates it as SSE's recovery and fallback path. Every dispatch, persistence and recovery criterion is decidable through it, which is what lets 10.7c be cut last without leaving 10.7a and 10.7b unverifiable.

## PO rulings on the drafted open questions

1. **Two new `ExecutionErrorCode` values (AC-13a) — RATIFIED as drafted: `AUTHORIZATION_REVOKED` and `REFERENCE_UNAVAILABLE`.** §5.1.3 demands "a terminal `ERROR` with an explicit code" for a revoked permission and a vanished reference at dispatch and names neither, so a name had to be chosen rather than inferred, and choosing it is a product decision. These two are the right ones on the test that matters: each names the **condition the dispatcher actually observed**, not the consequence, so a support engineer reading `error_code` learns why the run stopped rather than merely that it did. `DISPATCH_FAILED` was available and is wrong — it says the send failed when in fact the send never happened. Both are dispatcher-assigned and therefore stay inside the half of the vocabulary ADR-002 §6.1 reserves for the API, keeping AC-16's disjointness intact and keeping 10.12's AC-17 intersection at exactly `{TIMEOUT}`. Two consequences are recorded rather than left to be discovered: 10.12's disjointness test must **read this enumeration rather than a hardcoded copy** (its AC-17 has been corrected), and neither code may ever be produced by a runner.
2. **ADR-002 O-6 (AC-13b) — DEFERRAL CONFIRMED; the contract edit is not assigned here.** Putting the approved-target and secret-use policy on the job is a field on a closed body: **ADR-002 §12 Class B**, architect-first, proposable by a story but not landable. O-6 is still open, SPK-05 has not ruled between the job field and egress-only enforcement, and inventing a representation for an unspecified policy is an Article IV violation wearing a schema's clothes. This story keeps the honest minimum — recording which policy identity it dispatched under — which is decidable today and survives either ruling. If SPK-05 lands early enough for wave 3, the amendment goes to @architect and 10.18 implements it; it does not come back here.
3. **Duplicate already-applied `FINAL` answers `200`, not `409` (AC-21) — CONFIRMED.** Judged against 10.6's admission semantics rather than in the abstract. On the admission route `409` means **competing** admission: someone else is claiming an attempt this runner owns, and 10.6 AC-18 makes the runner stop reporting and write an audit line. A re-delivered, byte-identical `FINAL` is not a competitor — it is the same owner obeying the retry-until-acknowledged rule the API itself imposed (10.6 AC-17), which exists precisely because the runner has no durable store to replay from. Answering `409` would write a false "ownership lost" line for a runner that did exactly as instructed, and the cost compounds: an audit signal that fires on healthy behaviour is an audit signal operators learn to ignore, so the one `409` that means a real race gets lost in the noise. The rule is symmetric across both internal routes and should be named that way in the code: **an exactly-matching identity replayed is `200` applying nothing; a differing identity is `409`.** AC-21's three-identical-`FINAL`s test — one committed state, three `200`s, logs not duplicated, `snapshot_revision` incremented exactly once — is the criterion that keeps it honest.
