## User Story

**As the** Checks squad operating a runner whose accepted language is bound to one exact Playwright version and browser image,
**I want** a versioned reference corpus and CI checks that fail whenever the package, lockfile, image tag, recorded runtime versions or reference examples drift apart,
**so that** a confirmed artifact is only ever executed on the runtime it was validated for, and upgrades are explicit, tested events rather than silent reinterpretation.

---

## Problem Statement

Architecture §4.3 pins model, prompt, language policy, syntax reference, Playwright package/browser image and trusted-executor versions together, with CI validating reference examples against that runtime. §4.6 requires runtime upgrades to revalidate compatibility and run a fixture corpus before release, and to block incompatible/revoked revisions explicitly. Today there is no Playwright pin anywhere in the repository and no CI definition in it (the pipeline is @devops-owned outside the repo). [ADR-001 §4.2](../architecture/ADR-001-studio-runner-scaffolding.md) fixes the mechanism: one declared pin, four asserted copies (package.json, lockfile, Dockerfile `ARG`, `runtime-versions.json`), browsers only from the image.

The internal Playwright image (manifest `ED-05`) does not exist yet: the fixture-execution stage can be proven locally and defined for CI, but cannot be green in the pipeline until the image lands.

## Acceptance Criteria

### Pin consistency
- [ ] **AC-1:** `npm run check:pins` asserts equality of: `package.json` `dependencies.playwright` (exact, no range), the lockfile's resolved `playwright` version, `Dockerfile` `ARG PLAYWRIGHT_VERSION`, and `runtime-versions.json.playwright`; it also asserts `engines.node` major equals `.nvmrc`. Any mismatch exits non-zero with a message naming the disagreeing copies.
- [ ] **AC-2:** A Vitest test mutates each copy in a temp directory and asserts `check:pins` fails for every single-copy drift (four cases) and passes when all agree.
- [ ] **AC-3:** `npm run build` emits `runtime-versions.json` with `{playwright, chromiumBuild, node, validatorSchema, executor, image}`; `chromiumBuild` and `image` are read from the environment inside the pinned image (`PLAYWRIGHT_BROWSERS_PATH` revision directory and an `IMAGE_TAG` build arg) and are `null` on a plain Node build, which `check:pins` treats as "not asserted", never as a pass.

### Reference corpus
- [ ] **AC-4:** `fixtures/reference/` (from 10.2) is versioned by a `SYNTAX_REFERENCE_VERSION` constant and a `fixtures/reference/manifest.json` listing every example with the permitted method it demonstrates; a test fails if a permitted method in the validator's surface schema has no reference example or if an example uses a method outside the surface.
- [ ] **AC-5:** Unit tier: every reference example passes `validateArtifact` on the current validator (browser-free), so a language-policy change that breaks an example fails CI immediately.
- [ ] **AC-6a:** Fixture tier wiring: `npm run test:fixtures` (`vitest.fixtures.config.ts`) runs every reference example end-to-end through the `BrowserAdapter` seam against controlled local HTML fixture pages; in this story the adapter is the fake from 10.2 and the run is proven locally. `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` stays set; the stage is defined for CI inside the pinned image (gated by `ED-05`) and recorded as **skipped**, never passed, until that image exists.
- [ ] **AC-6b (verified in 10.12):** the same corpus executes on the real Playwright adapter and pinned Chromium (locally via `npx playwright install chromium` at the pinned version). 10.12 must cite this AC in its acceptance; 10.3 is Done for wave 1 without it.

### Compatibility and blocking
- [ ] **AC-7:** The runner exposes `isCompatible(provenance) → {ok, reason}` comparing an artifact's recorded `validatorSchema`, `executor`, `playwright` and `syntaxReference` versions with the running `runtime-versions.json` under a documented rule (exact match for validator schema and syntax reference; documented compatible range for Playwright/executor). An incompatible artifact yields the documented error code `RUNTIME_INCOMPATIBLE` with the differing fields, and no adapter call is made.
- [ ] **AC-8:** A test proves an artifact recorded under an older validator schema version is rejected with `RUNTIME_INCOMPATIBLE` rather than silently reinterpreted; the backend maps this to `409 RUNTIME_INCOMPATIBLE` on execute (mapping implemented in 10.8, contract in 10.1).
- [ ] **AC-9:** `studio-runner/README.md` § "Runtime upgrade procedure" documents the upgrade procedure from ADR-001 §4.2: bump all copies in one PR, regenerate `runtime-versions.json`, run reference and adversarial corpora, record compatibility for existing confirmed revisions, never rewrite approved source.

### CI wiring (definition, not pipeline files)
- [ ] **AC-10:** `studio-runner/ci/stages.md` lists the eight ADR-001 §7.2 stages with the exact npm scripts/commands per stage, which stages need the pinned image, and the expected artifacts (`dist/`, `runtime-versions.json`, image tag). This is the hand-off document for @devops (ADR open item O-1).
- [ ] **AC-11:** A deliberate mismatch (e.g. Dockerfile `ARG` bumped alone) demonstrably fails `npm run check:pins` in a recorded local run recorded in the story's Change Log.

### Tests meta
- [ ] **AC-12:** `npm run type-check && npm run lint && npm test && npm run check:pins` green on a plain Node image; coverage for `src/compat/**` and `scripts/**` ≥ 80%.

## Implementation Notes

- **FOC-02 (recorded in the manifest by @po, 2026-09-10):** 10.2 and 10.3 both touch `studio-runner/package.json`, `Dockerfile`, `vitest.fixtures.config.ts` and `fixtures/reference/` in wave 1. Serialize: T-10.2.0 scaffold lands first, then 10.3; or assign one owner. See EPIC-10-EXECUTION.yaml `file_ownership_conflicts`.
- Playwright refuses to launch a browser build that does not match the package version, so the fixture tier doubles as a runtime-drift detector; keep that behavior (never set `PLAYWRIGHT_BROWSERS_PATH` to a mixed-version directory).
- The compatible-range rule for Playwright is a documented decision in this story; start with exact match and relax only with evidence from the fixture tier.
- Do not fetch browsers in CI on the plain Node image; `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` stays set everywhere except the local `playwright install` step.
