## User Story

**As the** Checks squad that has so far executed every artifact against a fake browser adapter,
**I want** the real Chromium adapter behind the same `BrowserAdapter` seam — sandboxed, recording native video, reporting step timings on one calibrated run timeline, and refusing to launch whenever policy, compatibility or the start deadline says no,
**so that** the first real browser this platform starts is one that cannot be talked out of its sandbox, cannot silently trade a correct check outcome for a missing video, and produces timings that a user can actually seek a video by.

---

## Problem Statement

Everything upstream of this story was executed against fakes. `src/main.ts` says so in running code: `UNAVAILABLE_LAUNCHER` refuses every launch with `BROWSER_LAUNCH_UNAVAILABLE`, and the comment above it names this story. `src/server/adapters.ts` says the same about `BrowserLauncher`. `src/executor/adapters/BrowserAdapter.ts` says it in its opening line — "story 10.12 supplies the real implementation; every test here uses a fake". The `fixtures-tier` test says it again, and `test/isolation.test.ts` confirms no module under `src/` imports `playwright` today. The component exists; the browser does not.

Two earlier stories closed with an explicit, recorded skip pointing here:

| Deferral | What it was | Where it was recorded |
|---|---|---|
| **10.3 AC-6b** | "the same corpus executes on the real Playwright adapter and pinned Chromium … 10.12 must cite this AC in its acceptance" | 10.3 line 43; QA verdict "AC-6b — **Deferred to 10.12** … No browser was installed or launched" |
| **10.6 AC-14b** | "the same admission → real browser launch → `STARTED` sequence driven by real Chromium" | 10.6 line 75; @dev's record: "Deferrals recorded as skipped, never passed … **AC-14b** to 10.12" |

Both were described as *skipped, not passed*. This story is where they either close or stay honestly open.

Four properties make this more than "swap in the real adapter":

1. **The sandbox.** §9.3 requires `chromiumSandbox: true` — non-root, compatible seccomp, "prove sandbox startup in staging; **do not disable it silently to make the image run**". Playwright's launch default is `false`, which adds `--no-sandbox`. The default is the wrong way round, which is precisely why the requirement has to be a gate and not a habit.
2. **Evidence is not outcome.** §6.1: "Upload failure never overwrites a known assertion outcome." The epic repeats it in its definition of done. A run whose assertions passed and whose video did not flush is a `PASSED` run with failed evidence, and that has to be true on the wire, not just in prose.
3. **The run timeline has no origin yet.** ADR-002 fixes `atMs = 0` as the browser start, on the same monotonic clock and origin as the step readings, with the API deriving `at = browserStartedAt + atMs`. But `executeSteps` today falls back to `defaultClock = { now: () => performance.now() }`, whose origin is **process start**, and nothing in `runCoordinator.ts` injects a clock. So today's step readings are offsets from process start while the browser-start log line carries a literal `0`. Two origins on one timeline. Under the fake launcher nobody could see it; under a real recorder it is the difference between a working seek and a wrong one.
4. **Calibration is now placed, and the placement is binding.** ADR-002 open item **O-7** was closed on 2026-09-11 by §11: **calibration is applied runner-side, at the clock**, and the `recordingOriginMs` field this story's first draft proposed was **rejected** — the contract gains no field. What survives to this story is **O-8**: the run-scoped clock, the removal of the process-origin default from production, the pairing of the two origin reads, the staging measurement of the readiness-to-first-frame gap, and a scale assertion the schema cannot make. **O-5**, the real `outcome.errorCode` set, remains owned here (today's `STEP_FAILED`/`RUN_ERROR`/`RUN_NOT_STARTED` are placeholders built around a fake launcher).

Nothing here moves a byte to Sonic (10.14), enforces a deadline or kills a process tree (10.13), or touches the API (10.7). This story starts one browser, records one video, and reports what it observed on one clock.

## Acceptance Criteria

### The seam, and keeping Playwright behind it

- [x] **AC-1:** A real Playwright `BrowserAdapter` and a real `BrowserLauncher` replace the fakes behind the **existing** seams; `BrowserAdapter`, `StepReporter`, `BrowserLauncher`, `BrowserSession`, `LaunchOptions` and `ScratchStore` keep their current shapes, and `UNAVAILABLE_LAUNCHER` is removed from `src/main.ts`. **No Playwright type, value or import escapes the adapter:** `playwright` and `playwright-core` are importable only from the designated module(s) under `src/run/**`, enforced the way `child_process` already is — added to `RUN_ONLY_MODULES` (or an equivalent adapter-scoped entry) in `eslint.boundary-rules.js` **with a proving fixture under `fixtures/lint/`**, so the rule is demonstrated to fire rather than assumed to. A test asserts that `src/validator/**`, `src/executor/**`, `src/server/**` and `src/reporting/**` contain no Playwright import, which is the property QA verified holds today and which this story must not spend.
- [x] **AC-2:** **Nothing launches before revalidation.** After admission and before any browser process exists, the run revalidates the artifact under the same default-deny policy (`validateArtifact`) and checks runtime compatibility through the existing `src/compat` module against the recorded `runtime-versions.json`. Either failing means **no Chromium process is created** — asserted by observing the spawn seam, not by observing an absence of output — the slot is released, scratch is cleared, and the run reports a definite code (`RUNTIME_INCOMPATIBLE` already exists in `src/compat`). "Rejects incompatible artifacts before browser launch" (§4.5) and "produces the documented error rather than silent reinterpretation" (10.3 acceptance) are the same sentence read from two sides.
- [x] **AC-3:** **No generated source crosses into the browser process.** The parent→child boundary carries the validated operation list as data only: no artifact source text, no code string, no serialized function. The existing `test/no-dynamic-evaluation.test.ts` scan and the `no-eval`/`no-new-func`/`vm`/`worker_threads` boundary rules are extended to cover `src/run/**`, and a test asserts the child's accepted message schema rejects a message carrying a source field.
- [x] **AC-4:** **The start deadline is a refusal, not a race.** If the job's admitted-start deadline (`deadlines.admittedStartMs`, §8.5 starting value 30 s) has already elapsed when the run reaches the launch point, the runner refuses to launch: no browser, slot released, scratch cleared, definite code, and the terminal report says so. §5.2: "The runner refuses to launch after the server-issued admission/start deadline." Enforcement of the *total* runtime deadline and killing a hung child are **10.13**; this story only honours what it is given and structures the child so 10.13 can kill it.

### Chromium, the child process and the sandbox

- [x] **AC-5:** **One browser, one context, one page, per run, in a killable child process.** The child is spawned per run and exits on every path (success, step failure, launch failure, error); the browser and context are closed before it does; the parent's `/v1/validate`, `/health`, `/ready` and `/v1/runs` endpoints stay responsive throughout, on separate bounded resources (§4.5, §5.2). A test asserts the child process is gone and the slot released after each of the four paths.
- [x] **AC-6a:** **The sandbox is enabled and cannot be turned off.** The launch option is `chromiumSandbox: true`, always, with no configuration key, environment variable, job field or code path that can set it to `false`. `--no-sandbox`, `--disable-setuid-sandbox` and `--disable-gpu-sandbox` appear **nowhere** in `studio-runner/` — a repo-wide gate (test over source plus a proving lint fixture) fails if one is introduced, including inside a string, an args array or the Dockerfile. If Chromium cannot start with the sandbox, the run reports `ERROR` with a launch code and the runner **never** relaunches without it; a test drives that path and asserts no second launch with different arguments. Verified here on a developer machine, which the BRD milestone "Real browser, real video (dev)" and `ED-05`'s `gate_note` explicitly permit.
- [ ] **AC-6b:** *(Deferred — `ED-05` / `SPK-04`)* The same launch proven **in-cluster**: non-root under the cluster's PodSecurity level, with the seccomp profile SPK-04 selects (`RuntimeDefault` vs. an approved `Localhost`), `readOnlyRootFilesystem: true`, `emptyDir` scratch and `emptyDir{medium: Memory}` `/dev/shm`, on the internal Playwright image. Verified in **story 10.18**, evidenced by SPK-04. ADR-001 §9 leaves `seccompProfile` to that spike deliberately; there is no fallback that disables the sandbox.

### Native video

- [x] **AC-7:** **Native webm on the single page's context, with an explicitly configured resolution.** Recording is configured at context creation (never per page, never merged across pages), the resolution is an explicit configured value rather than an implicit default — §6.1 requires the text needed for evidence to stay readable — and the context is **closed and awaited** so the file is flushed (§6.1, Playwright's documented finalization behaviour). The run records the produced file's path inside the per-run scratch directory and its **size in bytes**, and a test asserts a non-trivial size and a readable webm header for a fixture run. The epic's "explicit readable recording size" is a reported number, not an assumption.
- [x] **AC-8:** **The check outcome and the evidence state are independent, in both directions.** Two tests, not one: (i) steps all pass but recording fails or the flush produces no playable file → `outcome.result = PASSED` with a failed evidence state and a populated `videoError`-equivalent diagnostic; (ii) a step fails while the video records perfectly → `outcome.result = FAILED` with healthy evidence. Evidence never alters `outcome.result`, `outcome.errorCode` or any step status. §6.1: "Upload failure never overwrites a known assertion outcome." This is an epic definition-of-done item and is asserted on the serialized `FINAL` body, not on intermediate objects.
- [x] **AC-9:** **Evidence vocabulary and key discipline.** The runner reports `PENDING` when a playable recording exists and has not been stored — storage is **10.14**, so `PENDING` is the honest state and `STORED` is never emitted by this story — `FAILED` when a recording was attempted and could not be produced or flushed, and `UNAVAILABLE` when no usable recording exists at all (§6.1, ADR-002 §6.1's runner vocabulary). `videoKey`/`manifestKey` are echoed from the job's server-derived keys and are never invented, derived or accepted from anywhere else (§6.2). A test submits a job whose keys differ from any pattern the runner could compute and asserts the echo is exact.

### The run timeline, and where calibration goes

- [x] **AC-10:** **`t = 0` is the browser start, on one monotonic clock, for every reading in the report.** A run-scoped monotonic clock is created in the child at the instant the recording context and page are ready, and that instant is *both* the zero of the clock *and* the instant `browserStartedAt` is stamped and `STARTED` is sent. That clock is injected into `executeSteps`, replacing the fallback `defaultClock` whose origin is **process start** — today's `runCoordinator.ts` passes no clock, so step readings are currently offsets from process start while the browser-start log line carries a literal `0`, which ADR-002's ruling makes wrong. Asserted: the `STARTED` log entry's `atMs` is a *reading* that happens to be `0`, not a constant; every step reading and every log `atMs` in the same report lie on that origin, are non-negative and fractional; `null` still means "no reading" (skipped steps, the terminal run line) and is never `0`.
- [x] **AC-11:** **Calibration is applied runner-side, at the clock — ADR-002 open item O-7, ruled by @architect on 2026-09-11 (§11.2) and binding here. The `recordingOriginMs` field this story proposed is REJECTED, and this story adds no field to any contract body.** The reasoning is recorded so it is not relitigated: subtracting two readings of one monotonic clock is exact wherever the subtraction happens, so a wire constant conveys nothing the runner could not have applied itself and only makes correctness depend on every consumer remembering to apply it — story 10.7 is the proof, since it computes `at = browserStartedAt + atMs`, which is right under this ruling and silently wrong under the field. Retry and recovery agree: zeroing at the clock fixes each entry's value at the instant it is observed, so an entry is identical across cumulative reports, across byte-identical terminal retries, and on the Sonic manifest path, whereas nothing in a closed schema would have stopped report *n* and *n+1* disagreeing about a wire origin. The consequences ADR-002 §11.6 assigns to this story — tracked as open item **O-8** — are criteria here, not notes:
  1. **The process-origin default is removed from the production path.** `executeSteps`' optional `clock` defaulting to `performance.now()` is a defect generator: the seam exists so the origin can be chosen, and the default quietly chooses process start whenever a caller forgets. After this story the production path **cannot run without an explicitly supplied run clock** — the default is deleted or confined to test construction — and a test asserts that constructing the production run path without a clock fails rather than silently running on process time.
  2. **The two reads are paired.** The wall-clock `browserStartedAt` and the run clock's zero are one instant observed twice: taken **adjacently at recording-context readiness**, never at launch-call time, never at admission, never re-derived afterwards. A test asserts both come from that one code point and that no other site stamps either.
  3. **The scale is asserted, not just the shape.** ADR-002 §11.6 records that the runner's contract-test validator implements `$ref`/`type`/`required`/`properties`/`additionalProperties`/`enum`/`allOf`/`anyOf`/`oneOf`/`const` and **ignores `minimum`**, so the `minimum: 0` the amendment added is documentary and a schema cannot tell a process-origin reading from a legitimate late one. A run through the fake browser must produce a first step reading **within a small, named bound of `0`**, and the assertion must go red when the run clock is replaced by a process-origin one. `createFakeClock`'s `startMs = 1_000` must not be what makes it pass, which is proven by running the same case at `startMs = 0` and again at a deliberately large offset.
  4. **A report with `browserStartedAt: null` carries no reading.** ADR-002 §11.2 states this as a contract invariant; the runner enforces it as the producer — in such a report every `startedAtMs`, `finishedAtMs`, `durationMs` and `atMs` is `null`. A test drives the launch-failure path and asserts it on the serialized `FINAL` body.

  The runner may keep a separate process-origin clock for its own stdout diagnostics; the contract is not a debugging channel (§9.2). If the readiness-to-first-frame gap proves material against the 500 ms budget, the correction is folded into the origin the runner takes — a runner-side constant beside the other pins — and still needs **no contract change**. Measuring that gap is AC-12c.
- [x] **AC-12a:** **Seek accuracy measured on a developer machine, by the method SPK-06 phase A defines.** Against a local fixture page displaying a monotonic timestamp, with the pinned Playwright version: for every attempted step — including step 0 (navigation) and a deliberately failing assertion step — the **reported `startedAtMs` — which under AC-11 is already an offset on the recording timeline and carries no calibration term** — is compared with the frame at which the step's visible effect appears, and the table (run × step: reported offset, observed frame time, error) is recorded in the story's Dev Agent Record. A wait/assertion step seeks to its **start**, not to the instant its condition became true (§6.4), and this is asserted rather than described. The measured tolerance is reported as a number; the 500 ms figure is not claimed here.
- [ ] **AC-12b:** *(Deferred — `SPK-06` phase B)* The same measurement **through the real pipeline** — dispatch → runner → Sonic → API `/video` → MFE seek — against the 500 ms target, in staging. Owned by **SPK-06 phase B** and consumed by **10.16** ("staging validates the target before release claims") and **10.19**. Recorded as skipped, never passed, until that evidence exists.
- [ ] **AC-12c:** *(Deferred — staging; **owned by this story**, evidenced by `SPK-06` phase B)* **The readiness-to-first-frame gap, measured.** ADR-002 §11.6 item 3 records that recording-context readiness is a *proxy* for the recorder's first frames and not the same instant, and assigns measuring that gap to this story on the controlled fixture **in staging**. If it is a material fraction of the 500 ms budget, a measured constant is folded into the origin the runner takes — runner-side, needing no contract change, which is the second reason the calibration stays in one component. Recorded as **skipped, never passed** until staging evidence exists; consumed by **10.16** and **10.19**. AC-12a's developer-machine measurement does **not** claim it, and this story must not report a number for it from a laptop.
- [x] **AC-13:** **This story makes no contract edit, and that is the criterion.** ADR-002 §11.2 rejected `recordingOriginMs` and amended `docs/specs/studio/openapi.yaml` itself: `RunnerStepState` and `RunnerLogEntry` now state the run clock and its origin instead of deferring placement to "the recording stories"; `startedAtMs`, `finishedAtMs`, `durationMs` and `atMs` gained `minimum: 0`; `browserStartedAt` states its pairing with the clock's zero; and `StepResult.offsetMs` and `ExecutionLogEntry` state that the API applies no calibration of its own. **No field was added, removed or retyped, every runner-produced body stays closed, and this story adds none.** `docs/specs/studio/openapi.yaml` does not appear in this story's File List, and a check asserts the file is byte-unchanged by this story's diff. 10.6's `test/contract.test.ts` stays **14/14 against the document as it already stands**, before and after.

  Under ADR-002 §12 this is **Class B** — the shape or meaning of a runner-produced body — where an architect rules first and the story implements against the amended document. This story is the case that established §12 (it proposed a field with the defect demonstrated, could not land it, and referred the question), and it complies by implementing §11.6 rather than by editing. Nothing in `src/run/**` may reopen a closed body, relax a `required` list or widen an enum to admit what the adapter happens to produce: §12's "loosening is never a story's call" is absolute, and a divergence found here is **left red and escalated**, not fixed locally.

### Executing the artifact for real

- [x] **AC-14:** **First failure stops the run; the rest are `SKIPPED` with null timings; attempted steps have real offsets and durations.** Driven by real Chromium on a fixture page: a failing assertion yields `outcome.result = FAILED`, the failing step `FAIL` with a redacted message, every later step `SKIPPED` with `startedAtMs`/`finishedAtMs`/`durationMs` all `null`, and every attempted step a non-null offset and duration (epic §10.12 acceptance bullet 2; §5.2). The executor's existing per-step outcomes reach the wire unchanged — this story adds no second reporting path.
- [x] **AC-15:** **Single page in V1; an unexpected popup is explicit, never silent.** A fixture page that opens a second page or a popup causes the run to close the popup and report an unsupported-workflow code and message; execution does not continue on the other page, no second recording is created, and no video is merged (§5.2, epic §10.12 bullet 4). The fixture that triggers it is part of the corpus, so the behaviour is proven rather than described.
- [x] **AC-16:** **Reporting stays 10.6's.** Cumulative `STARTED`/`PROGRESS`/`FINAL`, monotonic `runnerSequence`, best-effort progress, byte-identical bounded terminal retry, `409` stop and outbound bounding/redaction are used **as they are**; this story adds no report kind, no second client and no field beyond AC-13's. A test asserts the child's step events reach the existing `RunReporter` seam and that a slow or failing callback still cannot block, delay or alter a step across the process boundary.
- [x] **AC-17:** **The real runner error-code set — ADR-002 open item O-5.** `outcome.errorCode` values the runner may emit are enumerated in one exported constant, each traced to an observable condition: artifact revalidation failure, runtime incompatibility (`RUNTIME_INCOMPATIBLE`, already defined), browser launch failure, sandbox-unavailable launch failure, start-deadline refusal, unsupported multi-page workflow, recording production failure, and step failure. Two properties are asserted, not asserted-by-inspection: **(a)** the set is **disjoint from the API's `ExecutionErrorCode` enumeration except for the single value `TIMEOUT`** — ADR-002 §6.1 rules that every other value there is assigned by the dispatcher or a reaper (§5.4) and a runner must never emit one, while §8.2 fixes exactly one runner-observable code, the parent-enforced total timeout. The test reads both lists and asserts the intersection is exactly `{TIMEOUT}`, and the failure message names the offending values. The test **reads the API's enumeration rather than a hardcoded copy of it**: story 10.7 adds two dispatch-time codes in the same wave (`AUTHORIZATION_REVOKED` and `REFERENCE_UNAVAILABLE`, ratified by @po on 2026-09-11 under its AC-13a), so a frozen list of "the five this component must never produce" would be stale before the wave closed; **(b)** every code the runner *can* produce is in the set, enforced by an exhaustive switch over the run's failure kinds so a new kind fails type-check rather than inventing a string. §8.2 already fixes one runner-observable case — a parent-enforced total timeout is `ERROR`/`TIMEOUT` — and its *enforcement* belongs to **10.13**; this story reserves the code and does not emit it. Today's placeholders `STEP_FAILED`/`RUN_ERROR`/`RUN_NOT_STARTED` are replaced or justified, not left as scaffolding.

### Determinism, egress and the fixture corpus

- [x] **AC-18a:** **The reference corpus executes on real Chromium — this closes 10.3 AC-6b.** All 28 reference examples in `fixtures/reference/` run end to end through the *real* adapter at the pinned Playwright version against the four local pages in `fixtures/pages/`, served at the URLs `fixtures/reference/manifest.json` binds them to. CSS `locator()` selectors — which the fake-adapter tier explicitly cannot verify and which its skipped test names — resolve in the live DOM. Chromium is the build that ships with the pin (`npx playwright install chromium` at the pinned version locally; Playwright refuses a mismatched build, so drift fails loudly). The run is **deterministic**: the same corpus executed twice yields identical per-step statuses and identical step counts. 10.3's `it.skip` naming this story is deleted, not re-skipped.
- [ ] **AC-18b:** *(Deferred — `ED-05`)* The same corpus inside the **pinned internal Playwright image**, as `ci/stages.md` stage 6 defines it. Stays recorded as **skipped, never passed** until the internal image exists; closed by **10.18** and confirmed by **10.19**. This story installs a browser on a developer machine and does not build or publish an image.
- [x] **AC-19:** **No network egress beyond the local fixture pages.** Every request the browser issues during the corpus run is observed, and the run resolves and reaches nothing outside the local fixture host: no external DNS lookup, no request to `example.com` or any other public name despite the manifest's URL bindings, no `file://` access, no link-local or metadata address. A test fails on any request whose destination is not the fixture server. This is the runner-side complement to §9.3's network controls, and it is what makes the corpus safe to run in CI; the enforced-egress form belongs to **SPK-05 / 10.18**.
- [x] **AC-20:** **This closes 10.6 AC-14b.** Admission → **real** browser launch → `STARTED`: `browserStartedAt` is stamped and `STARTED` is sent only once real Chromium has actually started — not on admission success and not when the launch call begins — the `STARTED` sequence number is lower than any step's, and a run whose launch fails sends **no** `STARTED` at all. The **observed start is distinct from the dispatch/admission time** and the test asserts a measurable gap rather than equality (epic §10.12 acceptance bullet 3; §5.1.5 "`RUNNING` is written only on an authenticated browser-start report"). 10.6's `AC-14b` skip is deleted, not re-skipped.

### Secrets, scratch and the gates

- [x] **AC-21:** **The canary survives contact with a real browser.** A job carrying a known canary through `resolvedVars`/`resolvedSecrets` is executed against a fixture form page: the value reaches the intended field in the page, and appears in **no** form — plain, URL-encoded, double-encoded, base64 — in any report body, structured log line, diagnostic, error message, child-process argument list, child environment, spawn command line, scratch file name or scratch file content, using the existing `createRedactor`. Asserted on the bytes that leave and on the spawn arguments actually passed. §9.2's disclosed limitation stands and is restated in the README rather than defended against: **on-screen secrets can appear in the video**, no blurring or transcoding is introduced in V1, and Security acceptance for that is not claimed by this story.
- [x] **AC-22:** **Scratch is the only thing the browser writes to, and it is cleared on every path.** The recording, the browser profile/user-data directory and any Chromium temp output are confined to the per-run scratch directory created after admission; `readOnlyRootFilesystem: true` and a writable `/dev/shm` are honoured (ADR-001 §9); resolved values are never written there; and the directory is cleared on success, step failure, launch failure, error and drain, with a test inspecting the filesystem after each. Until 10.14 uploads it, the recording is deleted with the rest of the scratch and the story says so plainly rather than implying a file survives.
- [x] **AC-23:** **The pins hold and `.nvmrc` is not touched.** `npm run check:pins` still compares its six copies and still fails naming any that disagree; `--require-image` still turns an unasserted image into a failure, with absent, empty and whitespace tags all counting as unasserted. **The open Node mismatch (`ci/stages.md` O-2a) is not resolved by this story and must not be laundered:** the public base image at the pinned Playwright version ships Node v24.20.0 against a `.nvmrc` of 22, stage 6a fails by design, and the fix is a base-image choice under `ED-05` or an ADR-001 §4.2 amendment — never a change to `.nvmrc` or a widening of `engines`. A test asserts `.nvmrc` still reads `22`, so a later convenience edit is a red build. The pinned Playwright version stays **1.63.0** exactly; any bump is the ADR-001 §4.2 upgrade procedure, not this story.

## Implementation Notes

- **The Node mismatch is inherited, not fixed here (O-2a).** `check:pins --require-image` fails today because `mcr.microsoft.com/playwright:v1.63.0-noble` ships Node v24.20.0 while `.nvmrc` pins 22. 10.3 deliberately refused to widen `.nvmrc` — "that would delete the only copy that pins Node" — and handed the requirement to `ED-05` as `ci/stages.md` open item **O-2a**, owned by Platform/SRE with @architect: either the internal image ships the pinned major, or ADR-001 §4.2 is amended. **This story does neither.** It runs Chromium on a developer machine, where the in-image rule does not apply (the rule is read off `chromiumBuild`, which only exists under the image's `PLAYWRIGHT_BROWSERS_PATH`), and the in-image stage stays recorded as skipped, not passed. AC-23 exists to make a convenience edit to `.nvmrc` a red build rather than a quiet one. If this blocks the image-based tier, escalate to `ED-05`; do not resolve it in `studio-runner/`.
- **Serving the fixture pages.** `fixtures/reference/manifest.json` binds the four pages to `https://example.com/...` URLs. The real adapter must reach *those pages* without reaching that host. Two mechanisms are available and either satisfies AC-18a/AC-19: a loopback `node:http` static server with the manifest's URLs rewritten to its base, or Playwright request fulfilment that serves the files without leaving the process. Whichever is chosen must make AC-19's "nothing left the machine" *observable* rather than argued — count and assert the destinations, do not reason about them. Prefer the loopback server: it exercises the real navigation, DNS-free, and keeps the adapter free of a routing behaviour the validated language does not have.
- **Where the origin is taken matters more than what it is called.** AC-10 puts the run-timeline zero at recording-context readiness precisely so the only calibration term left is the recorder's own first-frame delay — a property of the pinned recorder, not of the run, which is what SPK-06 phase A is set up to measure once. Taking the origin at process start, at launch-call start, or at admission would all spend the 500 ms budget on something other than calibration.
- **SPK-06 phase A should precede the build.** The spike register says so explicitly ("Phase A gates nothing but should precede 10.12 drafting") and it shapes both the measurement method and the recording-resolution default. It no longer shapes a wire field: ADR-002 §11 rejected `recordingOriginMs`, so there is no constant to build as `null`-until-measured and nothing to hold open. If phase A is still open when implementation starts, run AC-12a's measurement by its method anyway and **record the tolerance actually measured, never the 500 ms target**. The readiness-to-first-frame gap is a staging number (AC-12c) and must not be guessed from a laptop.
- **Two deadlines, two owners.** The admitted-start deadline is a **refusal** and belongs here (AC-4); the total runtime deadline is **enforcement** and belongs to 10.13. Structure the child so 10.13 can kill its process tree without redesigning the launcher, and keep the deadline values flowing through `LaunchOptions.totalRuntimeMs`, which 10.6 already passes and deliberately does not enforce.
- **The sandbox default is backwards, so treat it as a gate.** Playwright's `chromiumSandbox` defaults to `false`. A reviewer cannot see an option that was never written. AC-6a therefore asserts both the positive (the option is `true`) and the negative (no disabling flag exists anywhere, proven by a fixture that fails lint), because the failure mode this criterion exists for is a future engineer adding `--no-sandbox` at 2 a.m. to make a build pass.
- **The calibration question is closed; do not reopen it in code.** The first draft of this story proposed `recordingOriginMs` and @architect rejected it (ADR-002 §11.2). The failure mode to guard against now is the reverse of the original defect: an implementer who "helpfully" re-bases readings against the lowest one seen, or ships a second origin for diagnostics on the contract body. Both are explicitly rejected in §11.5. One origin, taken once, at recording-context readiness.
- **`PASSED` with no video is a correct result, and must look deliberate.** The easiest wrong implementation is a `try` around the whole run that turns a recording failure into `ERROR`. AC-8 tests both directions for that reason.
- **`STORED` is not this story's word.** Reporting `PENDING` leaves the evidence unsettled until 10.14 ships, which §5.4's finalization reaper already handles ("outcome known but evidence/delivery not settled by deadline → preserve check outcome, settle evidence as failed/unavailable"). That is the honest interim, and it is why AC-9 forbids `STORED` here rather than leaving it to judgement.
- **Nothing in this story reaches a database, a vault, a CSI service or an LLM.** 10.6's AC-22 isolation gate is load-bearing and untouched: the allowlist, the named-module lint rules and the fail-closed config loader all stay as they are, and AC-24 keeps the production closure at three packages. New configuration keys (recording resolution, fixture-server base in tests) go through the enumerated `KEY_SPECS`, which keeps the loader fail-closed.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on 2026-09-11: `core-config.yaml` sets `coderabbit_integration.enabled: true` but `installation_mode: wsl`, and this repository is worked on a Darwin host where `wsl bash -c …` cannot run; the CLI is absent (`~/.local/bin/coderabbit` does not exist) and `graceful_degradation.skip_if_not_installed: true` applies. No story in `docs/stories/` carries such a section and `docs/qa/coderabbit-reports/` does not exist. The house story format is authoritative: **no CodeRabbit heading is added to any Epic 10 story**, and a draft checklist that expects one is satisfied by this ruling. If the CLI is ever installed on a supported host, @devops re-enables it and @po amends the format once, for the whole epic, rather than per story.
- **Starting values, not commitments** — 30 s step timeout, 120 s total runtime, 30 s start deadline, `POOL_SIZE=1`, and whatever recording resolution SPK-06 phase A recommends. §8.5 says to tune them against staging measurements.

## Dev Agent Record

**Agent:** @dev (Dex) · 2026-09-11 · branch `story/10.12`

### The defect this story was really about

`executeSteps` fell back to `defaultClock = { now: () => performance.now() }`, whose origin is
**process start**, and `runCoordinator.ts` injected no clock — so every step reading the runner
produced was an offset from process start, while the browser-start log line carried a literal `0`.
Two origins on a timeline ADR-002 §4.1 requires to have one, and `minimum: 0` was satisfied by both
of them, which is why no schema could see it.

What changed:

- `ExecuteOptions.clock` is **required**, and `executeSteps` refuses at run time as well —
  a type-level guard is not one the emitted JavaScript enforces.
- `takeRunOrigin` reads the monotonic clock **once** and derives both the zero and the first
  reading from that one sample, so "adjacent" is a property of the code rather than a hope. The
  test asserts `monotonicNow` is called exactly once.
- The origin is taken **in the child**, at recording-context readiness, and `browserStartedAt` is
  read there too. A parent that took it when a `ready` message arrived would have folded the
  inter-process latency into the zero.
- `RunSnapshot.build` strips every reading when `browserStartedAt` is `null`. The call sites have
  nothing to report on that path today, which would have made AC-11.4 true by accident; the
  producer enforces it instead.

### AC-12a — the seek measurement

Method: SPK-06 phase A. For each attempted step the reported `startedAtMs` — already an offset on
the recording timeline, carrying no calibration term — is compared with the frame at which the
step's visible effect appears. The frame is found by reading the **WebM container** (cluster
timestamps and `SimpleBlock` lengths) rather than decoding: a decoder means spawning `ffmpeg`, and
`child_process` is confined to `src/run/**`, so a measurement that needed one would have to live
outside the tests that consume it.

`fixtures/pages/timeline.html` repaints the whole viewport with pseudo-random noise on every step
and changes nothing else — no timer, no animation — so a repaint is orders of magnitude larger than
an unchanged frame. Step 0 is the navigation; step 4 clicks (visible, at its start) and then spends
a 2 s timeout failing an assertion, which is how "a wait/assertion step seeks to its **start**" is
made falsifiable.

Table, from the clean gate run (two runs × five attempted steps; all times in ms on the run
timeline):

| Run | Step | Reported `startedAtMs` | Observed frame | Error |
|---|---|---|---|---|
| 1 | 0 (navigation) | 2.1 | 0.0 | **−2.1** |
| 1 | 1 | 756.6 | 720.0 | **−36.6** |
| 1 | 2 | 1487.6 | 1440.0 | **−47.6** |
| 1 | 3 | 2199.8 | 2160.0 | **−39.8** |
| 1 | 4 (failing assertion) | 2917.9 | 3280.0 | **+362.1** |
| 2 | 0 (navigation) | 1.1 | 0.0 | **−1.1** |
| 2 | 1 | 749.0 | 720.0 | **−29.0** |
| 2 | 2 | 1469.9 | 1440.0 | **−29.9** |
| 2 | 3 | 2185.5 | 2160.0 | **−25.5** |
| 2 | 4 (failing assertion) | 2903.0 | 3280.0 | **+377.0** |

**The measured tolerance, reported as a number: median |error| ≈ 30 ms; 8 of 10 steps within
48 ms.** Two of ten steps show ≈ +370 ms, and the honest attribution is the *detector*, not the
runner: a full-viewport repaint does not always land in a single encoded frame, and when it does
not, the container-only frame finder picks the next scene change instead. Decoding pixels would
settle it; this story cannot decode pixels for the reason above. The assertion is therefore stated
as a **median** tolerance (< 100 ms) plus a loose per-step outlier bound (< 2500 ms) that a
process-origin reading — out by the process uptime, seconds to minutes — fails instantly.

**The 500 ms figure is not claimed here**, and neither is the readiness-to-first-frame gap: the
systematic component above (consistently ≈ −30 ms) contains that gap, but a laptop cannot separate
it from its own scheduling noise. AC-12c is a staging number and stays skipped.

### QA fixes — SEC-1 and the two MEDIUMs (post-review)

**SEC-1 is real and I reproduced it before fixing it.** With `NODE_OPTIONS="--import …"` set on the
parent and nothing in the repository changed, the preload ran inside the forked browser child
(`hasIpc=true`), logged `INTERCEPTED chromiumSandbox=true`, rewrote it to `false`, added
`--no-sandbox`, and the launch reported ready. Exactly QA's finding, end to end.

**The fix is an allowlist that no longer contains a loaded gun, plus a guard stated over the class.**
`NODE_OPTIONS` is off `INHERITED_ENV_KEYS`. It is not replaced by a denylist of the variables anyone
happened to think of — that is the shape that just failed, since `NODE_OPTIONS` was *reviewed onto*
the allowlist by people who knew what it did. `assertNoCodeLoadingKeys` re-checks the **constructed**
child environment on every launch against four namespaces: `NODE_*` (the interpreter's own —
`NODE_OPTIONS`, `NODE_PATH`, `NODE_REPL_EXTERNAL_MODULE`), `LD_*` (the glibc loader in the image:
`LD_PRELOAD`, `LD_AUDIT` — this one reaches the *browser* binary, not just Node), `DYLD_*` (the same
on macOS, where the fixtures tier runs) and `OPENSSL_*` (`OPENSSL_CONF` loads providers, which are
shared objects). A future addition to the allowlist fails the launch loudly instead of quietly
widening the browser process's trust boundary.

**I found a second channel in the same class and closed it too.** `fork` defaults `execArgv` to
`process.execArgv`, so a runner started `node --import evil dist/main.js` replays `--import evil`
into the browser child *even with the environment fully enumerated* — the allowlist does not cover
interpreter flags. I proved the channel rather than arguing it: with `execArgv: []` removed the
preload ran in the child and subverted the sandbox again; with it in place the preload ran only in
the parent. The child is compiled ESM and needs no interpreter flags, so it gets none.

**Both attacks re-run after the fix, and the five that already failed re-run too.** QA's
`NODE_OPTIONS` attack: the preload never executes in the child, the launch proceeds sandboxed. The
`execArgv` variant: same. The five in-repo attacks still fail — one Playwright launch site; no
config key names a sandbox; extra fields on the launch request (`chromiumSandbox: false`,
`args: ['--no-sandbox', …]`, `sandbox: false`) are still ignored by an object literal with no
spread, with `DEBUG=pw:browser` showing **zero** occurrences of `sandbox` on the Chromium command
line; library and browser environment variables (`PLAYWRIGHT_CHROMIUM_SANDBOX`, `CHROMIUM_FLAGS`,

`test/run/sandbox.test.ts` assertions red.

**Every new assertion was falsified.** Re-adding `NODE_OPTIONS` to `INHERITED_ENV_KEYS` turns three

**MED-2 is closed at both levels.** The production options literal is typed

**MED-1 is judged, and the bound is lowered rather than defended.** `OUTLIER_BOUND_MS` goes from

### Self-critique — two defects found before review, and fixed

Both were in `src/run/launcher.ts`, both invisible to the happy path, and both found by asking
"what if the child dies at the wrong moment?" rather than by a failing test:

1. **A run that could hang.** The exit handler *delivered* an abandoned-child result to whoever was
   listening, but did not *record* one. A child that died before `execute` was called therefore
   left `awaitResult` with nothing to resolve, and the run would have sat there until the drain
   deadline — a runner that never reports is exactly the state §5.4's reaper exists to clean up,
   and the runner must not create one. `test/run/launcher.test.ts` now drives that ordering.
2. **A callback that could take down the parent.** Step events are forwarded to 10.6's reporter
   inside the IPC `message` handler; a reporter that threw would have surfaced as an uncaught
   exception in the **parent** — the process serving `/health`, `/ready` and `/v1/validate` for
   everything else. AC-16's "a slow or failing callback cannot block, delay or alter a step" has
   to keep holding across the process boundary, and a callback that kills the parent has done
   rather worse than delay a step. The forwarding is now guarded and the test asserts the
   throwing-reporter case does **not** escape.

### Known limitation, stated rather than worked around

The seek measurement's frame finder reads the container, not the pixels, and mis-attributes
roughly one step in ten (see the table above). It is a limitation of the measurement instrument.
Closing it needs a decoder, which needs a child process, which ADR-001 §6 confines to `src/run/**`
— so the right place to settle it is SPK-06 phase B in staging, where AC-12b already lives.
