---

## Context

**PUT Checks** is our app to create operational health checks, run them on demand or on a schedule, and show pass/fail history. The UI is a React micro-frontend; the API is a Spring Boot backend.

**DailyChecks (DC)** is the legacy system that already runs tool checks (including Splunk). For now we **call DC**, not Splunk’s API directly.

We chose **Proposal B**: one shared backend `DailyChecksAdapter` (auth, HTTP, retries, outer mapping, deep links, metrics). Each tool has a thin executor that only shapes its request and parses its reply. Throttling stays in the existing Dispatcher.

This story is the **first full-stack slice — Splunk only**: user can create/edit a Splunk check in the UI, run it, and see the result, with the backend executing via DC.

---

## Scope

**Backend**
- Shared `DailyChecksAdapter` + DC client config (URL, auth, timeouts, retry/circuit breaker)
- Thin `SplunkCheckExecutor` + `SplunkMapping`
- Typed Splunk configuration on create/update/get check APIs
- Map DC response → stored execution outcome (`ExecutionOutcome`)
- Splunk source flag (`checks.sources.SPLUNK`, default **off**)
- Unit + WireMock tests (success, business fail, timeout, auth fail)

**Frontend**
- Create / edit Splunk check in the existing check wizard (config fields aligned with backend contract)
- Run Splunk check on demand and show result / history in the UI
- Respect source enablement (Splunk hidden or disabled in type picker when backend flag is off)
- Fix any FE↔BE field mapping gaps for Splunk (request payload + displayed outcome)
- Basic UI test coverage for Splunk create path (and run/result smoke if practical)

**Both**
- Short runbook: DC URL/auth, enable Splunk flag, how to verify in UI — see [9.7.1.splunk-dc-bridge.runbook.md](./9.7.1.splunk-dc-bridge.runbook.md)

---

## Out of scope

- Grafana, ITRS, AppDynamics, or other DC sources
- Calling Splunk’s own API/SDK directly
- Migrating/importing existing DC check definitions
- Major redesign of the check wizard UX
- Changing Dispatcher throttling design
- ROD / external machine API (separate story)

---

## Acceptance criteria

1. **E2E:** User can create a Splunk check in the UI, save it, run it, and see a success or failure result driven by the backend DC bridge  
2. Backend executes Splunk **only** via `DailyChecksAdapter` (no direct Splunk client); executor stays thin  
3. FE Splunk config fields match the backend API contract (create/edit/load round-trip works)  
4. When Splunk source is disabled, UI does not offer it as a selectable type (or shows it disabled); execute API rejects it  
5. Results cover success, business fail, timeout, and clear auth failure (backend tests required; UI shows a readable failure state)  
6. DC-specific types stay in the backend bridge package (not leaked as public FE contracts beyond our check config/result DTOs)  
7. Runbook exists for env config + how to demo the Splunk path in UI
