## User Story

**As the** put-checks backend team,
**I want** a signed-off, machine-checkable contract document that specifies the exact shape of the identity/permission payloads Core (`put-platform-shell`) emits to module backends,
**so that** story 1.5 can implement `BffSessionAuthenticationFilter` + `CoreServiceClient` against a stable contract, prevent identity-shape drift, and unblock every downstream `@PreAuthorize` / `@RequiresPermission` wiring in EPIC-01/02/03/04/05 without reworking later.

---

## Context (why this is a blocker, not just a nice-to-have)

Spec v3 §7.1/§7.2 describes Core-service introspection as the platform's auth model (superseding the incorrect direct-COIN-OIDC design from spec v1/v2 — see DEBT-04, commit `76d94bafc`). The specific shape of:

- `GET /api/v1/users/me` response body (especially `csi_ownership`)
- `POST /api/v1/authz/check` request/response
- Cookie scope (`put_session` domain/path/SameSite)

is **owned by the Core team in `put-platform-shell`**, not by this repo. Without a committed contract, every story touching `CsiOwnershipEvaluator` or `@RequiresPermission` either (a) hardcodes a guess that later breaks or (b) blocks on external coordination when it's too late. Story 1.4 forces that coordination **first**, not later.

## Open Questions for Core Team

These are the questions that, once answered, fully define the contract. The kickoff message sends this list verbatim.

1. **`csi_ownership` shape.** Is it a flat list of CSI IDs (`["174523","99887"]`), a list of `{csi_id, role}` objects, or a nested org-context tree (cf. `put-platform-shell/RBAC.md §8.2`)? If role-bearing: what is the role vocabulary (`owner`/`contributor`/`viewer`/… anything else)?
2. **Permission-name namespacing.** What's the canonical format for `POST /api/v1/authz/check` permission names? (e.g., `checks.monitors.edit`, `checks:bulk:execute`, `put-checks.bulk.execute`.) Who owns the registry of valid permission names?
3. **Role claim propagation.** Does `/users/me` return a `roles: []` array? If yes, what's the role vocabulary (`checks-admin`, `platform-admin`, `checks-operator`, …)? If no, is role-check only possible via `/authz/check`?
4. **Cookie scope for separate-origin deployment.** If put-checks backend is served from a different origin than the shell (e.g., `put-checks.citigroup.com` vs `put.citigroup.com`), is the `put_session` cookie domain-scoped to cover both, or does the module backend sit behind the shell's nginx (same-origin)? What are the supported deployment topologies?
5. **Core error envelope.** On 401 from `/users/me`, does Core return JSON like `{"detail":"Unauthorized"}` or a richer envelope? What about 5xx? Our filter needs a stable shape to distinguish "session invalid" (→ 401 to client, FE redirects to login) from "Core unavailable" (→ 503 to client, no demo fallback per `AUTH_FLOW.md §Error handling rules`).

## Implementation Notes (for @pm + @dev-sidekick)

- **Who drives this story:** primarily `@pm` (external coordination, contract authoring, sign-off). `@dev` pairs on the FakeCoreServiceClient + CoreContractComplianceTest so they compile against the real backend project structure from story 1.1.
- **Initial payload guess** (to seed the conversation with the Core team, not a unilateral decision):
  ```json
  {
    "user_id": "alice@citi.com",
    "email": "alice@citi.com",
    "name": "Alice Brown",
    "department": "Global Ops",
    "roles": ["checks-operator"],
    "csi_ownership": [
      { "csi_id": "174523", "role": "owner" },
      { "csi_id": "99887",  "role": "contributor" }
    ]
  }
  ```
  We send this as a strawman; Core team amends.
- **JSON Schema library choice:** use `com.networknt:json-schema-validator` in Java — actively maintained, Draft 2020-12 support, Spring-compatible. Pin version in `build.gradle.kts` as a `testImplementation` (contract test is test-scope).
- **Document format:** plain Markdown with fenced `json` blocks for examples and a fenced `json` block per JSON Schema. No generated HTML / PDF.
- **Sign-off mechanism:** pull-request review on the commit that introduces `bff-identity-contract.md` is the sign-off artifact. Core-team lead reviews and approves the PR; the PR description links back to this story.
- **If the Core team is slow to respond:** do NOT invent the contract unilaterally. Escalate to `@pm` → user. The fallback is a `FakeCoreServiceClient` returning the strawman shape, clearly labeled "PROVISIONAL — awaiting Core-team sign-off", and story 1.5 proceeds against it *only* in dev/staging. Production cutover of 1.5 is gated on this story's AC-3 sign-off.
