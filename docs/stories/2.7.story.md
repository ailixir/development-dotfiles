## User Story

**As a** platform operator deploying put-checks to Kubernetes,
**I want** to run the application as two separate deployments — an API deployment serving REST traffic and a Worker deployment running schedulers/dispatchers — using the same Docker image with different Spring profiles,
**so that** check execution workloads don't compete with API request serving for CPU/memory, each tier scales independently, and a pathological check execution cannot take down the API.

---

## Context & Rationale

### Problem

The current architecture couples API serving and scheduler execution in the same JVM:

```
Pod (single deployment)
├── REST API (serving user traffic)
├── CronDispatcher (@Scheduled, 30s poll)
├── PartitionScheduler (@Scheduled, monthly)
└── RetentionPruner (@Scheduled, monthly)
```

ShedLock ensures only one pod dispatches, but all pods pay the cost of running the scheduler infrastructure. More critically, a spike in check executions (heavy Splunk queries, slow HTTP targets consuming all 40 semaphore permits) affects API response times because both share the same JVM heap, CPU, and thread pool.

### Solution: Option C — Dedicated Worker Deployment

Same Spring Boot application, same Docker image, deployed twice with different profiles:

```
Deployment 1: API (replicas: 3)               Deployment 2: Worker (replicas: 2)
┌────────────────────────────┐                ┌────────────────────────────────┐
│ spring.profiles.active=api │                │ spring.profiles.active=worker  │
│                            │                │                                │
│ ✅ REST controllers        │                │ ❌ REST controllers (excluded)  │
│ ✅ Security filters        │                │ ✅ Actuator (health/metrics)    │
│ ✅ Swagger UI              │                │                                │
│ ❌ CronDispatcher          │                │ ✅ CronDispatcher              │
│ ❌ PartitionScheduler      │                │ ✅ PartitionScheduler          │
│ ❌ RetentionPruner         │                │ ✅ RetentionPruner             │
│ ❌ checkExecutor (bounded) │                │ ✅ checkExecutor (bounded)     │
│                            │                │                                │
│ HPA: CPU/request-based     │                │ HPA: queue-depth/permits-based │
└────────────────────────────┘                └────────────────────────────────┘
         │                                              │
         └──────────── shared PostgreSQL ───────────────┘
         └──────────── shared ShedLock table ───────────┘
```

- [x] **AC-1:** New `application-api.yml` profile that sets:
  - `checks.scheduling.dispatcher-enabled: false`

- [x] **AC-2:** New `application-worker.yml` profile that sets:
  - `checks.scheduling.dispatcher-enabled: true`
  - `checks.scheduling.partition-scheduler-enabled: true`
  - `checks.scheduling.retention-pruner-enabled: true`
  - `server.port: 8081` (actuator-only, no API traffic)
  - `management.server.port: 8081`

- [x] **AC-3:** `PartitionScheduler` and `RetentionPruner` annotated with `@ConditionalOnProperty` (matching the CronDispatcher pattern) so they respect profile toggles:
  - `PartitionScheduler`: `@ConditionalOnProperty(name = "checks.scheduling.partition-scheduler-enabled", havingValue = "true", matchIfMissing = true)`
  - `RetentionPruner`: `@ConditionalOnProperty(name = "checks.scheduling.retention-pruner-enabled", havingValue = "true", matchIfMissing = true)`

- [x] **AC-4:** Default behavior preserved — when no profile is specified (current `local` profile), ALL components load (API + schedulers). The separation is opt-in for production.

### Worker-mode controller exclusion

- [x] **AC-5:** Worker profile excludes REST controllers from component scanning OR controllers are annotated with `@ConditionalOnProperty(name = "checks.worker-mode", havingValue = "false", matchIfMissing = true)` to prevent unnecessary bean creation and port binding.

- [x] **AC-6:** Worker profile still loads `SecurityConfig` minimally for actuator endpoint protection (basic auth or permitAll for health/prometheus in internal network).

### Executor tuning per profile

- [x] **AC-7:** Worker profile allows independent tuning of `checkExecutor` semaphore permits via `checks.executor.semaphore-multiplier` — worker can run with higher multiplier (e.g., 8x vs 4x) since it doesn't share resources with API traffic.

- [x] **AC-8:** `AsyncConfig` conditionally creates `checkExecutor` and `uiTestExecutor` beans only when dispatcher is enabled, to avoid unnecessary thread pool allocation in API-only pods.

### Health & observability

- [x] **AC-9:** Worker deployment exposes `/actuator/health` with:
  - `db` (datasource)
  - `partitions` (PartitionHealthIndicator)
  - `shedlock` (lock status — optional, nice-to-have)

- [x] **AC-10:** Worker deployment exposes `/actuator/prometheus` with all Micrometer metrics (dispatch counters, partition gauges, execution timers).

## Implementation Notes

### Profile activation in Kubernetes

```yaml
# API Deployment
spec:
  containers:
    - name: put-checks-api
      image: put-checks:latest
      env:
        - name: SPRING_PROFILES_ACTIVE
          value: "api"
      resources:
        requests: { cpu: "500m", memory: "512Mi" }
        limits: { cpu: "2", memory: "1Gi" }

# Worker Deployment
spec:
  containers:
    - name: put-checks-worker
      image: put-checks:latest
      env:
        - name: SPRING_PROFILES_ACTIVE
          value: "worker"
        - name: CHECKS_EXECUTOR_SEMAPHORE_MULTIPLIER
          value: "8"
      resources:
        requests: { cpu: "1", memory: "1Gi" }
        limits: { cpu: "4", memory: "2Gi" }
```

### Controller exclusion strategy

Prefer `@ConditionalOnProperty` over component-scan exclusion — it's more explicit and testable:

```java
@RestController
@ConditionalOnProperty(name = "checks.worker-mode", havingValue = "false", matchIfMissing = true)
public class ChecksController { ... }
```

Alternative: use `@Profile("!worker")` on controllers. Simpler but less granular.

### ShedLock compatibility

No changes to ShedLock — it already handles multi-deployment safely. Both API and Worker pods share the same `shedlock` table. Only the Worker pod's dispatcher acquires locks. If 2 Worker replicas exist, ShedLock still ensures single execution.

### Backward compatibility

The `local` profile (used for development) does NOT set `checks.worker-mode` — `matchIfMissing = true` ensures all beans load. Zero disruption to existing development workflow.
