## Story

**As a** Studio author compiling context-aware UI steps,
**I want** the runner to prove that generated Playwright means exactly the resolved intent at compile and execution time,
**so that** login, protected navigation and every other step cannot acquire extra or altered browser behavior.

## Acceptance Criteria

1. A closed, independently versioned `expectedIntent` contract represents exactly one stable step
   identity and ordered typed operation list per v2 source step. Missing, duplicate, reordered,
   unknown-version and oversized expectations fail closed.
2. The backend assembles expected intent only from saved, resolved authoring inputs before the LLM
   call. It preserves complete locator chains, literal/reference values, key, assertion kind and
   semantic options; unsupported or underspecified semantics block proposal.
3. Runner validation compares parsed operations with expected operations using exact count, order
   and semantics. It rejects extra/missing/reordered actions, a wrong target/value/key/reference,
   changed locator scope, assertion kind or behavior-changing option.
4. Normalization is limited to documented equivalent defaults. `force`, `trial`, altered button or
   click count, relaxed `exact`, regex broadening and changed assertion options cannot pass unless
   explicitly expected. Runtime timeout ceilings remain policy-owned.
5. Context-selected variable/secret references are authorized per step from expected intent while
   still requiring artifact declarations and allowed argument positions. Cross-step, undeclared,
   unused and wrong-position references fail. Legacy source-token alignment is unchanged.
6. `POST /v1/validate` and `RunJob` accept optional `expectedIntent`; legacy callers may omit it.
   Backend v2 compile and dispatch require it. Validation responses remain diagnostics-only and
   artifact schema v1 is unchanged.
7. The canonical expected-intent JSON that passed validation is persisted on the immutable
   candidate revision. Confirmation and dispatch use that snapshot. A v2 revision with a missing or
   corrupt snapshot requires recompilation and never falls back to legacy behavior.
8. Runner execution repeats semantic validation before capacity, admission, scratch allocation or
   browser launch, then executes only the typed operations returned by that validation.
9. The canonical login/protected flow passes through the actual runner boundary: navigate to login,
   fill contextual username and opaque password reference, submit, verify authenticated state,
   navigate and verify a protected page in the same browser session.
10. Secret values never enter the prompt, artifact, expected-intent snapshot, diagnostics or logs;
    existing CSI/environment/principal/vault authorization remains mandatory.
11. Contract, compatibility and integration tests cover exact Unicode/whitespace/empty/escaped
    literals; extra actions before/between/after; wrong key/target/reference/options/assertions;
    context-only references; immutable snapshot dispatch; zero-browser refusal; and legacy calls.
12. Independent QA reviews 10.41. On PASS, QA separately re-reviews Story 10.39 REQ-005 without
    overwriting its historical FAIL evidence.
