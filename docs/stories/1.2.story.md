## User Story

**As a** put-checks backend developer,
**I want** `V1__init.sql` to materialize the full database schema from ARCH §7 (with the 3 amendments from spec v3) and Flyway + Zonky (local) + Testcontainers (CI) to be fully wired so the application boots against a real PostgreSQL 15 database,
**so that** every subsequent story can add business logic against a stable, production-shape schema, with identical DDL semantics on local dev and CI — and the schema itself becomes committed, forward-only, and checksum-verified by Flyway on every app start.

## Implementation Notes (for @dev)

- **Start with the SQL.** Write V1 against the ARCH §7 text literally, then apply the 3 amendments. Resist refactoring at this stage — verbatim match to ARCH makes future audit simple.
- **Partition naming convention:** `execution_results_YYYY_MM` (e.g., `execution_results_2026_04`). The scheduler in 2.5 will append partitions using the same convention.
- **Don't add a DEFAULT partition.** Spec §8.2 + research PG-09 are explicit: `DETACH CONCURRENTLY` (story 2.6) is incompatible with a default partition. If a row is inserted outside bounds, it MUST fail — that's the signal that the partition scheduler (2.5) is late.
- **JSONB GIN indexes:** ARCH §7.1 specifies `idx_checks_configuration USING GIN (configuration)` — make sure the GIN index is defined on the parent partitioned table (it propagates to children automatically per PG-02).
- **Zonky pinning:** `io.zonky.test.postgres:embedded-postgres-binaries-bom:15.X.Y` — use the PG minor version that matches your target RDS cluster. If unknown at M1 time, document the chosen version in Dev Notes and flag to @pm for confirmation before staging.
- **Testcontainers image:** `postgres:15-alpine` is fine for CI speed. Reuse containers via `@Testcontainers(disabledWithoutDocker = true)` and the `.withReuse(true)` flag (requires `testcontainers.reuse.enable=true` in `~/.testcontainers.properties`).
- **Hibernate `ddl-auto=validate`** is a safety net — if any future story adds a JPA entity whose columns don't exist in Flyway's schema, Hibernate fails at startup with a clear error. This is the desired behavior.
- **Don't attempt a `flyway:migrate` Gradle task coupled to Zonky.** Zonky runs in-process; Flyway auto-runs via Spring Boot on startup. The Gradle `flywayValidate` task validates checksums against a running DB (typically for CI/staging).
- **Smoke entities go in `src/test/`** — they're throwaway. Story 1.7, 1.9 etc. author the real entities under `src/main/` later; delete smoke entities at that point (note in Dev Notes which ones get superseded).

## Dev Notes — 2026-04-17 (@dev)

**Zonky PG minor chosen:** `15.6.0` via `io.zonky.test.postgres:embedded-postgres-binaries-bom:15.6.0`. Matches the targeted RDS PG 15.6 cluster (per ZK-R3). Revisit on staging cutover if RDS minor drifts.

**Partition bootstrap dates:** V1 bootstraps `execution_results_2026_04` (Apr) + `execution_results_2026_05` (May). Current local date is 2026-04-17, so writes today hit the current-month partition cleanly. Story 2.5 (app-managed scheduler) takes over once `next_month` needs to be auto-created; until 2.5 lands, **do not deploy later than 2026-05-15** without manually adding a 2026-06 partition.

**ARCH ↔ V1 deviations / notes:**
- `users` has no `updated_at` column per ARCH §7.1 (only `last_login`). Story 1.2 AC-13 mentions a `users` updated_at trigger — that's inconsistent with ARCH. V1 does NOT add the column and does NOT add the trigger; AC-13 coverage for `users` deferred to a future minor schema story if ever needed.
- `execution_results` PK changed from `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` (ARCH §7.1) to `PRIMARY KEY (id, started_at)` with `id UUID NOT NULL DEFAULT gen_random_uuid()`. PostgreSQL requires the partition key in the PK for partitioned tables — no workaround. Documented as part of Amendment 2.
- Check-status cascade trigger (ARCH §7.4) original maps execution status to check status 1:1 — but ARCH execution_results.status is in `{SUCCESS,FAILURE,WARNING,TIMEOUT}` and checks.status is in `{PASSING,FAILING,WARNING,PENDING,UNKNOWN}`. V1 maps: SUCCESS→PASSING, FAILURE→FAILING, WARNING→WARNING, TIMEOUT→FAILING. Surface at @po / @qa for explicit confirmation at gate.

**Zonky programmatic config vs. @AutoConfigureEmbeddedDatabase:**
- `LocalEmbeddedPostgresConfig` uses `EmbeddedPostgres.builder().start()` directly (on `@Profile("local")`) so `bootRun` gets Zonky without needing test annotations.
- Tests use `@SpringBootTest` with `@ActiveProfiles("local")` which reuses the same `LocalEmbeddedPostgresConfig` — ONE Zonky instance per context. Fast enough (~2s cold start on Apple Silicon).
- If a later story needs @DataJpaTest with isolated Zonky per test, swap to `@AutoConfigureEmbeddedDatabase(provider = ZONKY)` from the `embedded-database-spring-test` testImplementation dep (already on classpath).

**Test suite composition:**
- 7 test files + 13 smoke entities = 20 new compilation units.
- `SchemaSmokeContainerIT` gated on Docker availability (`@Testcontainers(disabledWithoutDocker = true)`); in a no-Docker local run it's skipped cleanly — coordinate Docker availability on CI before merging to `main`.
- JaCoCo scope: smoke entities live under `src/test/` → excluded from production coverage automatically. Tests contribute line coverage against main-source code (LocalEmbeddedPostgresConfig, Flyway callbacks if added later, logging config).

**Open items for @qa gate:**
- Run `./gradlew check` from a JDK 21 install — confirm Flyway applies V1 cleanly to Zonky.
- Confirm Docker availability in CI for Testcontainers ITs.
- Confirm the TIMEOUT → FAILING mapping in the check-status cascade is intentional / aligns with product intent.
- After `./gradlew check` is green, flag for deletion: smoke entities get superseded per-context in stories 1.7 (csi_systems), 1.9 (checks), 1.11 (execution_results), etc. @qa should spot-check at each of those gates.
