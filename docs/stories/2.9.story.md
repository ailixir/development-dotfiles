## User Story

**As a** platform operator running scheduled checks at scale,
**I want** the CronDispatcher to only dispatch checks for which execution capacity exists, and to recover gracefully when a check is throttled due to a race condition,
**so that** no scheduled execution is silently recorded as a failure when the system is at capacity — instead, checks wait in the queue and execute when slots free up.

---

## Context & Rationale

### Problem

When per-type `tryAcquire()` fails in `CheckExecutorDispatcher`, the schedule's `nextExecutionAt` has already been advanced. The check is persisted as a terminal `FAILURE("Execution throttled")` with no recovery. Under burst load (e.g., 5,000 HTTP checks due in the same minute), up to 70% of executions are silently dropped.

### Root Cause

The dispatch pipeline advances the schedule (consumes it from the queue) before confirming the check can actually execute. The per-type semaphore uses non-blocking `tryAcquire()` which fails immediately when capacity is exhausted, and that failure is treated as a terminal execution result.

### Solution: Two-Layer Defense

**Layer 1 — Capacity-gated polling:** Poll per `check_type` with a budget equal to available source permits. Unfetched schedules remain due in the DB — naturally queued.

**Layer 2 — Throttle recovery:** If a race condition causes `tryAcquire()` to fail despite the pre-check, revert `nextExecutionAt` instead of persisting a terminal failure.

## Acceptance Criteria

### Schema — denormalize check_type onto schedules
- [ ] **AC-1:** Flyway migration adds `check_type VARCHAR(20)` to `schedules` table.
- [ ] **AC-2:** Migration backfills `check_type` from `checks.type` via `UPDATE ... FROM`.
- [ ] **AC-3:** Column is `NOT NULL` after backfill (two-step: add nullable → backfill → set NOT NULL).
- [ ] **AC-4:** `Schedule` entity includes `checkType` field.
- [ ] **AC-5:** Schedule creation paths (ScheduleService) populate `checkType` from the associated check.

### Layer 1 — Capacity-gated polling
- [ ] **AC-6:** `CheckExecutorDispatcher.availablePermitsSnapshot()` returns `Map<CheckType, Integer>` of current available permits per type.
- [ ] **AC-7:** `ScheduleRepository.findDueByType(Instant now, String checkType, Pageable)` queries due schedules filtered by `check_type`.
- [ ] **AC-8:** `CronDispatcher.pollAndDispatch()` polls per type: for each enabled `CheckType`, fetches `min(availablePermits, globalBudget)` due schedules. Unfetched schedules remain in DB.
- [ ] **AC-9:** Total dispatched per poll does not exceed `maxConcurrency - inFlightCount`.
- [ ] **AC-10:** Metric `checks.dispatch.deferred_due_count` gauge per `check_type` reports how many due schedules were left in the queue.

### Layer 2 — Throttle recovery
- [ ] **AC-11:** New `ExecutionOutcome.Throttled(CheckType type)` variant added to the sealed interface.
- [ ] **AC-12:** `CheckExecutorDispatcher.dispatch()` returns `Throttled` instead of `Failure` when `tryAcquire()` fails.
- [ ] **AC-13:** `CronDispatcher.executeAsync()` handles `Throttled` by reverting `nextExecutionAt` to `now + 5s` (not advancing to next cron cycle).
- [ ] **AC-14:** No `execution_results` row is persisted for a `Throttled` outcome.
- [ ] **AC-15:** Metric `checks.dispatch.throttle_reverted_total` counter with tag `check_type`.

### Ad-hoc execution path
- [ ] **AC-16:** `CheckExecuteController` (ad-hoc POST) still returns `Throttled` as a `409 Conflict` (or `503 Service Unavailable`) with a descriptive message, NOT a silent failure.

### Tests
- [ ] **AC-17:** Unit test: `CronDispatcher` dispatches only up to available permits per type.
- [ ] **AC-18:** Unit test: `CronDispatcher` leaves unfetched schedules in DB when capacity is exhausted.
- [ ] **AC-19:** Unit test: `Throttled` outcome triggers schedule revert, not failure persistence.
- [ ] **AC-20:** Integration test: with HTTP permits = 2 and 10 due HTTP schedules, all 10 execute successfully across multiple poll cycles (no throttle failures).
- [ ] **AC-21:** Unit test: `CheckExecuteController` returns appropriate HTTP status on `Throttled`.
- [ ] **AC-22:** Migration test: `check_type` column is populated correctly from `checks.type`.

## Implementation Notes

- **Flyway migration ordering:** must run after partition migrations (2.5/2.6). Use timestamp-based naming.
- **`findDueByType` index:** add `CREATE INDEX idx_schedules_type_next ON schedules(check_type, next_execution_at) WHERE enabled = true` for efficient per-type polling.
- **Race window:** between `availablePermitsSnapshot()` and actual `tryAcquire()`, ad-hoc executions can steal permits. Layer 2 handles this — expected to be rare (< 1% of dispatches).
- **Revert delay (5s):** prevents hot-loop where the same schedule is immediately re-fetched. Must be less than `poll-interval-ms` to avoid unnecessary lag.
- **Backward compatibility:** existing `findDueSchedules` method kept for any callers; new `findDueByType` used only by CronDispatcher.
