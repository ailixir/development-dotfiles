## User Story

**As a** platform operator relying on precise check scheduling,
**I want** the CronDispatcher to advance `next_execution_at` from the schedule's own timestamp (not wall-clock `now()`), and to allow configurable batch sizes,
**so that** delayed dispatches don't skip execution windows and batch throughput can be tuned per environment.

---

## Context & Rationale

### Drift Bug

`CronDispatcher.advanceNextExecution()` currently calls:

```java
ZonedDateTime now = ZonedDateTime.now(ZoneId.of(schedule.getTimezone()));
ZonedDateTime next = expr.next(now);
```

If the dispatcher runs late (e.g., ShedLock delay, GC pause, pod restart), `now` is past the intended window. `CronExpression.next(now)` returns the NEXT window after the current wall-clock, silently skipping the original intended slot.

**Correct behavior:** use the schedule's own `nextExecutionAt` as the base:

```java
ZonedDateTime base = schedule.getNextExecutionAt()
    .atZone(ZoneId.of(schedule.getTimezone()));
ZonedDateTime next = expr.next(base);
```

This ensures the schedule advances one tick at a time regardless of dispatcher latency.

### Batch Size

`BATCH_SIZE = 100` is hardcoded. Heavy-check environments (Splunk queries, UI tests) may need smaller batches; lightweight environments (HTTP-only) may benefit from larger ones.

## Implementation Notes

- **Edge case: rapid successive polls.** If the dispatcher polls twice before the schedule's `nextExecutionAt` is committed, the `findDueSchedules()` query could return the same schedule. The existing transactional wrapping + `advanceNextExecution` within the TX prevents this — verify in IT.
- **Null-safe fallback:** `schedule.getNextExecutionAt()` can be null for newly-created schedules that haven't been dispatched yet. The fallback to `now()` is correct for this case only.
