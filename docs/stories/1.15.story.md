## User Story

**As a** security-conscious put-checks operator,
**I want** per-user rate limiting applied to every authenticated endpoint, with distinct token-bucket policies for reads, writes, executes, sends, and bulk operations,
**so that** a single compromised session cannot flood the platform (NFR-THRU-03 target is 500 RPS platform-wide; no single user should reach that), and routine dashboard polling (1/sec reads) proceeds without disruption.

---

## Acceptance Criteria

- [ ] **AC-1:** Bucket4j added as a dependency (`com.bucket4j:bucket4j-core` + Caffeine integration).
- [ ] **AC-2:** `RateLimitFilter` (Spring `OncePerRequestFilter`, ordered AFTER `BffSessionAuthenticationFilter` from 1.5) extracts the authenticated user (`SecurityContextHolder`), classifies the endpoint, consumes a token, and either passes through or short-circuits with `429 Too Many Requests`.
- [ ] **AC-3:** Endpoint classification per spec §6.5:
  - **Read** (`GET /*`) → 600 req/min
  - **Write** (`POST/PUT/PATCH/DELETE /*` except below) → 120 req/min
  - **Execute** (`POST /checks/{id}/execute`, `POST /studio/tests/{id}/run`) → 60 req/min
  - **Send** (`POST /reports/{id}/send`) → 10 req/min
  - **Bulk** (`POST /checks/_bulk`) → 20 req/min AND double-charge the per-operation bucket (bulk counts once as bulk + N times as the op class)
- [ ] **AC-4:** Admin JWT role (`checks-admin` or `platform-admin`) multiplies all buckets by 10×.
- [ ] **AC-5:** On 429, response carries: HTTP 429 status, `Retry-After: <seconds>` header (computed from bucket refill rate), `X-RateLimit-Limit: <capacity>`, `X-RateLimit-Remaining: 0`, `X-RateLimit-Reset: <epoch>`, JSON body `{"error":{"code":"RATE_LIMITED","message":"..."}}`.
- [ ] **AC-6:** Bucket state held in Caffeine (in-memory, per-pod) keyed by `(user_id, bucket_class)` with TTL = 2× refill interval (prevents unbounded memory).
- [ ] **AC-7:** CORS preflight `OPTIONS` requests are exempt from rate limiting (per spec §7.1.1 — no cookies, no identity).
- [ ] **AC-8:** Unauthenticated requests are **not** rate-limited by this filter — they are already rejected by `BffSessionAuthenticationFilter` with 401. Document in code comment.
- [ ] **AC-9:** Config properties expose all bucket capacities + refill rates in `application.yml` under `checks.rate-limit.*` — tunable per environment without code change.
- [ ] **AC-10:** Metrics: `checks_rate_limit_consumed_total{user_hash,class}` (counter) + `checks_rate_limit_rejected_total{user_hash,class}` (counter). `user_hash` is SHA-256 of user_id truncated to 8 chars — prevents high-cardinality explosion while preserving per-user diagnostics.
- [ ] **AC-11:** Integration test `RateLimitReadIT` hits a read endpoint 601 times in 60s with one user → first 600 pass, 601st returns 429 with all required headers.
- [ ] **AC-12:** Integration test `RateLimitExecuteIT` hits `/execute` 60 times fast, 61st returns 429 with `Retry-After` indicating the next available slot.
- [ ] **AC-13:** Integration test `RateLimitAdminMultiplierIT` asserts an admin user can make 6000 read requests (600×10) in 60s without 429.
- [ ] **AC-14:** Integration test `RateLimitPreflightBypassIT` asserts 10000 `OPTIONS` requests in a second all pass through.
- [ ] **AC-15:** Integration test `RateLimitBulkDoubleChargeIT` asserts a bulk call containing 50 ops consumes 1 bulk token AND 50 op tokens.
- [ ] **AC-16:** JaCoCo coverage for the rate-limit package ≥ 80%.

## Implementation Notes
- **Filter order:** place `RateLimitFilter` after `BffSessionAuthenticationFilter` via `@Order` or `FilterRegistrationBean.setOrder()`. Auth must happen first so we have a user id to key on.
- **Classifier** — keep simple: a small routing table (list of `RequestMatcher` + class enum). Use Spring's `AntPathRequestMatcher`. Avoid a custom DSL.
- **Caffeine key design:** `String.format("%s:%s", userId, bucketClass)`. 10k max entries; evict LRU.
- **Admin multiplier:** compute the bucket capacity at classify-time based on the user's roles; don't maintain two separate bucket stores.
- **`user_hash` metric tag** — SHA-256 of user_id, hex-encoded, first 8 chars. Caution: 8 hex chars = 32 bits → collision probability meaningful at 50k+ users (~0.03%). Acceptable for a diagnostic tag; a full hash per metric would blow up Prometheus cardinality.
- **`Retry-After` math:** for a bucket with capacity=60 refilling linearly over 60s, the wait time is `ceil((tokens_needed - tokens_available) × 1000ms)` converted to seconds.

## @po Validation — 2026-04-17 · **10/10 GO**

Thorough coverage. 16 ACs sounds high but each tests a distinct invariant (per-class cap, admin multiplier, OPTIONS bypass, bulk double-charge, error-response shape including all three X-RateLimit-* headers). Strong foundation for NFR-SEC-04.

**Watch-items (non-blocking):**
- The AC-3 limits (60 req/min execute, 10 req/min send) are sensible defaults but have never been validated against actual user workflow. Instrument in staging first and tune before prod. AC-9 exposing these via config properties makes tuning cheap.
- `user_hash` 32-bit truncation (AC-10) is a reasonable cardinality tradeoff; if ever it becomes meaningful, @qa can flag at 6.3's gate (Redis migration is a natural time to revisit the hash width).
- **Per-pod bucketing** means in a 3-pod staging env, a user can burn 1800 read-tokens/min (600 × 3) before the global limit bites. The M6 Redis migration (6.3) fixes this. Until then: accept the looseness in single-replica dev/staging; do NOT cut M1 production release with multi-replica until 6.3 lands.
