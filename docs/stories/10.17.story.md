## User Story

**As the** Checks squad that has built an execution path in which a resolved secret is
resolved at dispatch and then **thrown away** — the dispatcher opens
`StudioReferenceResolver.Resolved`, never reads it, and sends the runner a job body that carries
reference *names* and no values,

**I want** the declared variable/secret references to keep their type from the confirmed revision
to the browser, secret *use* to be authorized as its own decision rather than inherited from
execute permission, the resolved values to travel on the one envelope the contract already
declares for them and to be refused before a browser starts if they do not correspond, and every
one of those values to be driven through story 10.13's captured-output canaries rather than past a
parallel assertion written here,

**so that** a support engineer can run a checklist that logs into a real application, and the only
place that credential ever exists is worker memory, runner memory, browser memory and the target's
own request — and so that the guard which proves it is one somebody has watched go red.

## Problem Statement

This is the epic's secret-handling story, and four facts on the branch define it. All four were
verified by reading the code at `34138201f`, not inferred.

**1. Resolved values are resolved and discarded.** `StudioDispatcher` opens the resolver's
`try (StudioReferenceResolver.Resolved resolved = references.resolve(csiId, referenceNames))`
block, records the dispatch policy, commits the attempt, and then constructs
`new RunJob(executionId, attemptId, testId, csiId, revisionId, environment, referenceNames,
callbackBaseUrl)` — `resolved` is never read. Its `close()` zeroes the `char[]`s. The seam works
exactly as story 10.7 built it, and it feeds nothing. `RunJob.java`'s own javadoc states the
reason: *"It carries declared reference **names** and never resolved values (§9.2): the runner
holds no vault credential and has nothing to do with a value."* The first clause is right and the
second is wrong — §9.2 says the runner *"may receive per-run values"*, and holding no vault
credential is precisely **why** the worker must hand them over. That sentence is the story's
problem in one line.

**2. The job body does not conform to the frozen contract, and nobody has noticed.** The frozen
`RunJob` is `additionalProperties: false` and requires fourteen fields, including `resolvedVars`
and `resolvedSecrets`. `HttpRunnerDispatchClient.body()` writes eight keys, four of which
(`testId`, `csiId`, `environment`, `callbackBaseUrl`) the closed body does not permit, and omits
ten it requires. The runner's `validateEnvelope` is **default-deny on keys** and validates before
capacity, so a real dispatch to a real runner returns `400 JOB_INVALID`, which
`HttpRunnerDispatchClient.classify` maps to `refusedTerminal` — every real run would end
`ERROR / DISPATCH_FAILED` today. No test asserts the dispatch body against the frozen document:
`StudioContractTest` checks that `POST /v1/runs` is *declared*, never that what this API sends
conforms to it, and `HttpRunnerDispatchClientTest` builds a `RunJob` and asserts the classification
table. Story 10.7's QA round attacked sixteen forged requests at the internal chain and did not
look at this. It is not a contract defect — **the contract is right and the producer is wrong** —
so ADR-002 §12 does not apply and no architect ruling is needed; what is needed is a producer.

**3. The type is destroyed one layer below where 10.8 created it.** `CompileInputs.from` already
separates `StudioVariable.KIND_SECRET_REF` from `plain` and `referencesJson()` already writes
`{"variables": [...], "secrets": [...]}` onto the revision — verified on the branch. Then
`ExecutionReferences.declaredNames` walks that document and **flattens it into one
`List<String>`**, and `StudioReferenceResolver.preflight/resolve` take one flat list. So by the
time anything can act on a reference, nothing knows which of them is a secret. The contract's
`ReferenceDeclarations` (`{variables, secrets}`) and its two separate resolved maps cannot be
filled from a flat list. This is the "token correspondence, typed variable adapter" of the epic's
own scope line, and it is one adapter wide.

**4. Nothing authorizes secret *use*.** `StubStudioReferenceResolver.preflight(String csiId,
List<String> referenceNames)` **does not read `csiId` at all** — it checks
`secrets.findByReferenceId(name).isEmpty()` against the global table and nothing else, so any CSI
may name any secret. `resolve` returns a configured canary string for every name. `SecretsService`
stores `request.value().getBytes(UTF_8)` under a `// TODO: Replace with real AES-GCM encryption`
and `resolveSecret` returns the literal `"REDACTED"`. The `secrets` table has `reference_id`,
`label`, `scope`, `owner`, `last_four`, `encrypted_value`, `rotated_at`, `expires_at` — and **no
CSI column**, which is why `preflight` cannot use the parameter it is given. `ED-02` names this
exact pair ("the current `BffSessionAuthenticationFilter` admin bypass and `SecretsService`
REDACTED/plaintext stub cannot satisfy staging acceptance") and the manifest's gate note is
explicit: *"10.17 credentialed staging acceptance cannot pass on stubs."*

And one fact that makes this story's tests uniquely easy to write wrong.
`BffSessionAuthenticationFilter.isCoreServiceBypassed()` returns a hardcoded `true`, so **every
HTTP request on this branch arrives as `CORE_SERVICE_BYPASS_IDENTITY` with roles
`["checks-admin", "platform-admin"]`**, and `CsiOwnershipEvaluator.isAdmin` short-circuits
`canRead`, `canWrite` and `canExecute` to `true` for every CSI. An authorization test for this
story written through the ordinary request path is therefore green **because authentication is
disabled**, in both directions: the refusal case never refuses, and the permit case permits
regardless of what this story implements. For a secrets story that is the worst available outcome,
and AC-17 exists for it alone.

Nothing here removes the bypass (10.18, `ED-02`), integrates the real vault (`ED-02`), enforces
approved destinations (`ED-04` / ADR-002 **O-6** / 10.18 SPK-05), uploads anything (10.14) or
checks the running browser's identity (**SEC-2**, 10.18 — see *Related security context*).

### Typed references, and the envelope that is meant to carry them

- [x] **AC-1: The reference type survives from the revision to the wire; the flat list dies.**
  §4.5's *References* row distinguishes `vars.get('NAME')` from `vars.secret('ID')` and permits
  secret values *"only in approved action argument positions/destinations"*; §8.3 fixes typed
  `variables` as `plain` or `secretRef`; §8.1 records *"declared references"* on the revision; and
  `CompileInputs.referencesJson()` already writes `{"variables": [...], "secrets": [...]}` there.
  `ExecutionReferences.declaredNames` flattens that document and is replaced by a reader that
  returns the two sets **separately and in declaration order**. Every consumer changes with it:
  `StudioReferenceResolver.preflight` and `.resolve` take the typed declaration, not a
  `List<String>`, and the acceptance and dispatch paths pass it through unflattened.
  **Falsifiable:** a revision declaring `vars.get('REGION')` and `vars.secret('LOGIN_PW')` produces
  a job whose `references.variables` is exactly `["REGION"]` and whose `references.secrets` is
  exactly `["LOGIN_PW"]`; a mutation that appends both to one list, or that swaps them, turns a
  named test red. A revision whose stored `references` document is of a shape this reader does not
  recognise is a **terminal refusal**, not an empty declaration (AC-10) — the current reader's
  `orElse(List.of())` fallback is exactly the fail-open this criterion removes.
- [x] **AC-2: The dispatch body conforms to the frozen closed `RunJob`, asserted against the
  document rather than against a Java type.** §8.4 enumerates the job fields; the contract closes
  the body with `additionalProperties: false` and fourteen `required` names; the runner's
  `validateEnvelope` is default-deny on keys. **Verified divergence (see Problem Statement 2): the
  API sends four keys the body forbids and omits ten it requires, so every real dispatch is
  refused `400 JOB_INVALID` before capacity.** This story makes the producer conform. Each missing
  field has a source and none is invented:

  | Field | Where it comes from | Not this story's |
  |---|---|---|
  | `artifact`, `source`, `configuration`, `artifactHash` | the confirmed revision (§8.1) | — |
  | `csi` | the execution's own immutable `csi_id` (§8.1, §9.1) — replacing the forbidden `csiId` | — |
  | `references` | AC-1's typed declaration — replacing the flat array | — |
  | `resolvedVars`, `resolvedSecrets` | AC-3's resolution (§8.4, §9.2) | — |
  | `deadlines` | §8.5's admitted-start and runtime values, which 10.7 already persists as `start_deadline_at` / `run_deadline_at` | the clamp is **10.13** AC-6's |
  | `videoKey`, `manifestKey` | §6.2's two key templates, derived from immutable execution identity | writing the **objects** is **10.14**'s; deriving a key is not uploading one |

  The four forbidden keys go, and `callbackBaseUrl` in particular: §8.4 makes the callback
  destination deployment configuration *"never arbitrary job-supplied URL"*, and the runner's
  `CALLBACK_SHAPED_KEYS` list exists to refuse exactly this class by name. **Falsifiable, and the
  form of the assertion is the criterion:** the test serializes the body the dispatcher actually
  hands the HTTP client and validates those **bytes** against `RunJob` read from
  `docs/specs/studio/openapi.yaml` — not against `RunJob.java`'s field names, which is the
  assertion that would have stayed green through all of this. A second test drives the real
  runner's `validateEnvelope` with that body and asserts `ok: true` with zero problems.

- [x] **AC-3: Resolved values reach the runner, and the runner refuses a job whose values do not
  correspond to its declarations — before capacity, before admission, before a browser.** §9.2:
  *"The runner may receive per-run values"*. The epic's acceptance bullet: *"unauthorized or
  missing reference prevents browser launch."* `validateEnvelope` today checks that
  `resolvedVars`/`resolvedSecrets` are string records and **never compares their keys to
  `references`** — verified — so a job declaring a secret and supplying no value is admitted, takes
  a capacity slot, launches Chromium, and dies mid-step with
  `Secret "LOGIN_PW" was not resolved for this run.` in front of a real application. Correspondence
  becomes part of envelope validation, which runs **first** in `runCoordinator.submit`, before
  `pool.tryAcquire()`:
  - every declared secret id has a key in `resolvedSecrets`; every declared variable name has a key
    in `resolvedVars`;
  - **no resolved key is undeclared, in either map** — a value the artifact cannot name is a value
    that should not be in the process;
  - a secret id appearing among the variables, or the reverse, is a refusal;
  - the refusal is `400` with a code and **names the reference, never the value**, and the
    problem detail passes through the run's redactor before it is logged.

  **Falsifiable:** four separate tests (missing secret, missing variable, undeclared extra,
  crossed type) each assert `400`, `pool.inUse === 0`, that no admission request was issued, and
  that no browser process exists — the last by the observation tier 10.13 builds, because
  "assert launch was not called" is the assertion class this epic has already found worthless.
- [x] **AC-4: Secret use is its own authorization decision, not execute permission reused.**
  §9.2: *"Secret reference names alone grant no permission."* `ED-02`'s own description names
  *"real vault integration **with secret-use authorization**"* as a thing distinct from identity.
  §9.1 gives owners and authorized administrators execute; it does not say that executing a draft
  entitles a principal to every reference the draft names. This story introduces a
  `StudioSecretUseAuthorization` seam consulted **separately** from `CsiOwnershipEvaluator`, and
  the acceptance path consults both. **Falsifiable, and this is the mutation that matters:** a
  principal holding `owner` on the execution's CSI — so `canExecute` is `true` — and **not**
  entitled to `LOGIN_PW` is refused at preflight with `400` naming `LOGIN_PW`; an implementation
  that returns `canExecute(auth, csiId)` from the new seam turns that test red. The reverse
  mutation is also recorded: a seam that returns `true` unconditionally must turn the same test
  red, which is what stops the seam from being a decorative interface.
- [x] **AC-5a: Resolution is confined to the approved revision's declarations, for the execution's
  own CSI and its own environment — the half decidable today.** Epic §10.17 scope bullet 1:
  *"Resolve only references in the approved revision for its CSI/principal/environment."* Three
  properties, three tests: the resolvable set is read from the **confirmed revision the execution
  snapshotted**, never from the draft's current `variables` and never from the request; the CSI is
  the **execution's own immutable `csi_id`** (§8.1, §9.1 — *"Historical access uses execution CSI,
  not a mutable parent lookup"*), so moving or editing the parent test between acceptance and
  dispatch changes nothing; and the environment is the one snapshotted at acceptance, so a
  reference entitled only in `dev` is refused for a `prod` execution. A test edits the draft to
  declare a fourth reference after acceptance and asserts the dispatched set is the revision's
  three.

- [x] **AC-6: A refusal names the reference and never the value, and a name grants nothing.**
  §9.2's closing sentence. Every refusal this story can produce — unknown reference, unentitled

### Revocation, rotation and the terminal vocabulary

- [x] **AC-7a: A revoked entitlement and a vanished reference are each terminal, with the code
  that already exists for them, and no browser starts.** §5.1.3 and ADR-002 §15.2: the vocabulary
  is ratified and declared — `AUTHORIZATION_REVOKED` is *"a fact about the principal"*,
  `REFERENCE_UNAVAILABLE` *"a fact about the draft and its environment"*, both dispatcher-assigned,
  both meaning the send **never happened**. 10.7 wired both to
  `ProvisionalDispatchAuthorization` (which checks only that the draft exists, is not soft-deleted
  or quarantined, and that the CSI is registered) and to the stub resolver. This story supplies
  the real conditions behind them without touching the codes:
  - entitlement withdrawn between acceptance and dispatch → `ERROR` / `AUTHORIZATION_REVOKED`;
  - reference deleted from the vault between acceptance and dispatch → `ERROR` /
    `REFERENCE_UNAVAILABLE`;
  - neither is retried, neither is skipped, and in **both** cases `POST /v1/runs` is never called —
    asserted on the recording dispatch client's request count being exactly zero, not on a log line.

  **`x-assigned-by` stays true:** neither code becomes reachable from a runner, and
  `x-runner-error-codes ∩ ExecutionErrorCode.enum = {TIMEOUT}` is re-asserted from the document
  (ADR-002 §15.6) rather than from a second copy. **No enum is widened** — widening
  `ExecutionErrorCode` is Class C and is not this story's (ADR-002 §12).
- [ ] *(skipped — blocked)* **AC-7b:** *(**Blocked — `ED-02`**; owner **10.18**, proven in **10.19**. **Skipped, never
  passed**.)* The same two conditions driven by a **real** identity revocation through the trusted
  gateway and a **real** vault deletion, against a non-bypassed session. On this branch the
  revocation half is unobservable: every request is `platform-bypass` with `checks-admin`, so a
  "revocation" is a test fixture changing a fake's answer.
- [x] **AC-8: Rotation takes effect at dispatch, exposes nothing, persists nothing, and requires no
  recompile.** §4.2: *"Vault value rotation does not require embedding a value or recompile;
  execution records a nonsecret vault version identifier when available. Artifacts pin references,
  not secret contents."* Epic §10.17 scope bullet 2: *"recheck revoked/rotated values at dispatch.
  Record nonsecret vault version identifier when supported."* One test rotates the value between
  the acceptance transaction and the dispatcher's claim and asserts, on one run: the browser
  receives the **new** value; the **old** value appears nowhere (bytes, every surface of AC-13a);
  `confirmed_revision_id`, `artifact_hash`, `source_revision` and `configuration_revision` are
  **unchanged**, so no reconfirmation is provoked; `compile_status` is untouched; and the
  **nonsecret version identifier** recorded on the execution differs before and after. The
  identifier is a nonsecret opaque string supplied by the provider — never the value, never a hash
  of the value, and a test asserts a rotation of a value to *itself* still changes nothing that
  could be used to compare values. **No migration:** it is recorded the way 10.7 records
  `dispatchPolicyIdentity`, by merging a key into the execution's `configuration_snapshot` jsonb —
  a decision stated so the next reader does not re-open it, and so this story does not queue behind
  10.9's `ui_tests` migration.
- [x] **AC-9: The fake vault cannot be reached from a deployed profile, and the provider choice is
  fail-closed.** `ED-02`'s fallback is *"Development identities confined to local/mock operation"*;
  §8.5 keeps deployment configuration in one source; §9.1 requires absent identity to fail closed.
  The provider is selected by one enumerated configuration key with **no default** — candidate name
  `studio.secrets.vault.provider`, alongside the existing `studio.execution.*` keys; the name is the
  implementer's to settle, the absence of a default is not. **No new environment variable reaches
  the runner** (10.13 AC-19's exact-set assertion on `INHERITED_ENV_KEYS` binds here too): the
  provider lives entirely on the API side, and a resolved value crosses to the runner only on the
  job body. Three
  assertions: the application **refuses to start** when the key is absent or unrecognised, rather
  than falling back to anything; the fake provider is unreachable outside the development/test
  profiles and a test asserts the context fails rather than substituting it; and the fake's name
  appears in a startup log line and on the health/info surface, so a deployment running on the fake
  says so out loud. A silent fallback to a fake vault is the single worst failure mode this story
  can ship and it is cheaper to make impossible than to detect.
- [x] **AC-10: An unreadable, absent or unrecognised reference declaration at dispatch is terminal,
  not an empty set.** `StudioDispatcher.referenceNames` returns `List.of()` when the revision is
  missing — verified — so a dispatch whose revision cannot be read proceeds as a run with no
  references and no secrets, which for a login test means a browser opening a real application with
  an empty password field. The epic's bullet is *"unauthorized or **missing** reference prevents
  browser launch"*. The condition becomes terminal, with no `POST /v1/runs` issued and no attempt
  recorded beyond the closing write.

  **@po ruling 2026-09-11 on Open Question 1 — the code is `REFERENCE_UNAVAILABLE`.** The draft was right to raise it rather than assume it; the recommendation is accepted, and the reasoning is recorded so it is not re-opened. ADR-002 §15.3's axis is *what condition was observed*, not what consequence followed, and an unreadable or absent confirmed revision is *"a fact about the draft and its environment"* on every reading of that axis: the same principal attempting the same draft fails identically, the remedy points at the author or at whoever restores the row, and nothing about the principal's entitlement has changed — which is what would make it `AUTHORIZATION_REVOKED` instead. Both codes are already ratified, both are dispatcher-assigned, and both mean **the send never happened**, which is true here. **No ninth enum value** — that would be Class C and is not proposed, not needed, and would split one condition across two codes for no reader's benefit.

  Two constraints ride with the ruling. **(a)** The refusal message names the **reference declaration** as unreadable and never the revision's contents, per AC-6. **(b)** `x-assigned-by` stays true: this path is dispatcher-side, so the code does not become reachable from a runner, and `x-runner-error-codes ∩ ExecutionErrorCode.enum = {TIMEOUT}` is re-asserted from the document as AC-7a requires. ## Anti-vacuous test requirements

This section is normative, not advisory. It exists because **six guards that could not fail have
already been found in this epic, and three of them were secret-redaction guards.**

| # | The guard that could not fail | Why it could not | What this story must do instead |
|---|---|---|---|
| 1 | A secret canary that stayed green **with redaction removed** | The canary value never reached the surface being asserted, so `doesNotContain` was true for the wrong reason | **Every** leak assertion first **proves the value travelled** — on the wire, in the row, in the captured buffer — and only then asserts it is absent from the guarded surface. 10.8's QA fix is the pattern to copy |
| 2 | A redaction assertion green **with the redactor deleted** | It asserted the redactor's own behaviour (`redact(x)` returns `[REDACTED]`), not the output's | Assertions are made on **captured output bytes** — the appender's buffer, the serialized body, the file on disk — never on the return value of the thing under test. 10.13's AC-7a is this rule for the runner; AC-12 is it for the API |
| 3 | A log assertion that **grepped source text** instead of capturing runtime output, and stayed green against **all three** leak mutants | A source scan models the leak paths it knows about and is blind to a value arriving through an innocently named local, a throwable's cause chain, or a nested record's own `toString` | API-side log assertions attach a live logback appender encoding `%msg` and `%ex{full}` with the relevant loggers at `TRACE`, exactly as `CompilePipelineTest` now does, **and** a fixture-guard test asserts the appender is live before any `doesNotContain` is trusted |

Three further rules bind every criterion above:

- **Per-guard falsification is a deliverable, not a practice.** AC-20. The record names the test.
- **A mutation that reddens the whole suite has proven nothing.** Record how many tests stayed
  green; a discriminating guard is one where the intended test goes red and its siblings do not.
  10.7's QA round applied this to AC-33 and it is the standard here.
- **Green-because-disabled is the failure mode of this story specifically.** AC-17. An
  authorization assertion on this branch is measuring a hardcoded `true` unless the identity was
  supplied directly and the decision was mutated.

### The criteria most likely to be satisfied vacuously or cut under pressure — named

Stated so that a reviewer knows where to look first, and so that a later quiet downgrade is
visible as a change from the draft rather than as an interpretation of it.

1. **AC-13a, the six value shapes.** The weakest by some distance, and the easiest to
   half-do: the obvious implementation writes one new canary test beside 10.13's, asserts the
   plain value is absent from one surface, records "mutation: removed redaction → red", and stops.
   That satisfies the words and not the criterion. The criterion is **six shapes × 10.13's surface
   list × a named red test each**, inside 10.13's files.
2. **AC-17, the non-vacuity of every authorization test.** Green on this branch is the default
   state. The specific way this gets downgraded is that the *refusal* tests are written carefully
   with injected identities and the *permit* tests are left to ride the bypass, because they pass
   either way and nobody looks at a passing test.
3. **AC-12, the non-persistence assertions.** `doesNotContain` is the cheapest assertion in
   software and the easiest to make true by accident. Without the "prove it travelled first" rule
   these are decorative.
4. **AC-2, the envelope conformance.** Under time pressure this becomes "assert `RunJob.java`'s
   field names match the schema's property names" — which is the assertion class that let this
   divergence live through a whole wave and a QA round. The criterion is **the serialized bytes,
   validated against the document read from the file**.
5. **AC-14, the JSON-escape variant.** A one-line addition that looks like polish and is the only
   thing standing between a password containing a quote mark and the pod log.

## Split hint

**The seam is the wire, and the cut is at `POST /v1/runs`.** If this story outgrows its estimate,
the cut is:

- **(i) API-side** — the typed adapter (AC-1), envelope conformance (AC-2), the secret-use
  authorization seam and the fake vault provider (AC-4, AC-5a, AC-9), the revocation/rotation
  conditions behind the two existing codes (AC-7a, AC-8, AC-10), the compile-path re-falsification
  and the job-body non-persistence assertions (AC-11, AC-12), and AC-17.
- **(ii) Runner-side** — correspondence refusal before capacity (AC-3), the six value shapes
  through 10.13's harness (AC-13a), the JSON-escape variant (AC-14), the runner half of the wipe
  (AC-15), the position re-falsification (AC-16a).

**Three things must not be cut apart.**

1. **Never cut "values travel" from "values are correspondence-checked before launch."** Shipping
   (i) alone puts a job on the wire whose missing secret is discovered mid-step, in front of a real
   application, with a capacity slot held and a browser running — which is strictly worse than
   today, where the same job is refused at the envelope. If (i) lands alone, the runner's existing
   `400 JOB_INVALID` must remain the behaviour until (ii) lands, and that must be stated in the
   PR rather than assumed.
2. **Never cut the canary extension away from the material that makes it necessary.** This is the
   mirror of 10.13's own rule — 10.13 blocks this story precisely *"because it adds the secret
   material that (ii)'s canaries exist to chase"* — and cutting AC-13a out of the story that
   introduces real values would leave 10.13's harness chasing a planted constant forever, with
   nobody owning the substitution.
3. **Never cut the fake vault (AC-9) from the authorization seam (AC-4).** A seam with no
   implementation is an interface nobody has exercised, and the fail-closed provider selection is
   the thing that stops the fake reaching a deployed profile. They are one change.

**If it outgrows even the two-way cut**, the next thing to go is AC-2's non-reference fields —
`deadlines`, `videoKey`, `manifestKey` — carried as a named follow-up with 10.14, since those three
are the fields whose *consumers* are not yet built. The reference and resolution fields may never
be the part that is deferred: they are the story.

## Implementation Notes

- **The contract is right and the producer is wrong — so no ADR is needed and none should be
  sought.** ADR-002 §12 governs changes *to* the document. AC-2 changes the API to match a document
  that already declares exactly what §8.4 specifies. Escalating it would block a wave for nothing,
  which is the reasoning §12 applies to Class A. What **would** need an architect is the opposite
  move: widening `RunJob` to admit `testId`, `environment` or `callbackBaseUrl` because the API
  happens to send them. That is §12's third rule verbatim — *loosening is never a story's call* —
  and `callbackBaseUrl` in particular is the field the runner's `CALLBACK_SHAPED_KEYS` list was
  written to refuse.
- **Do not build a second redactor, a second wipe path, a second canary harness or a second
  bounding path.** 10.2's `createRedactor`/`safeMessage`, 10.6's `ReportBounds` and serialize-then-
  redact `Logger`, 10.13's `wipe()` and canary files are load-bearing and tested. This story routes
  new material through them and proves it. Three of this epic's silent failures came from two
  hand-maintained copies of one fact (ADR-002 §15.6, §16.1, §18.3).
- **Serialize-then-redact is correct and has one consequence nobody has paid for.** `logging.ts`
  redacts the finished JSON string precisely so a field nobody enumerated is still caught — the
  right trade. The cost is that the *bytes* in that string are JSON-escaped, so a value containing
  `"`, `\` or a newline is no longer the value the redactor is looking for. AC-14 adds the variant;
  it does **not** reverse the ordering, which would reintroduce the larger hole to close the smaller
  one.
- **Do not zero what cannot be zeroed, and do not claim to.** `Resolved` holds `char[]` and
  `close()` fills them with `\0`. The moment the maps are serialized into a JSON body, the platform
  creates `String`s that no code can erase. The decidable property is that nothing retains a
  **path** to the values after the send; the serializer's transient buffers are a named residual
  (AC-15), not a claim.
- **A fake vault that can be reached in production is worse than no vault.** AC-9's fail-closed
  selection, the refusal to start, and the startup line naming the provider are the three cheap
  controls; the expensive one — detecting it later — is the one this avoids. `ED-02`'s fallback
  authorises development identities *"confined to local/mock operation"*, and "confined" is the
  operative word.
- **Resist a CSI column on the `secrets` table.** It is the obvious way to make AC-5a's CSI check
  real against stored data, and it would be inventing an entitlement model on a table `ED-02`
  replaces — Article IV, and a migration this story does not need (A-9). The CSI/environment halves
  are decidable from the **revision and the execution**, which is where AC-5a puts them; the
  principal half is `ED-02`'s and is AC-5b.
- **The `POST /tests/{id}/execute` route gains no new refusal code without ratification.** AC-6's
  refusals ride the codes the preflight path already produces. If a new `400` code is genuinely
  needed, §14.7's pre-ruling lets a story populate `x-conflict-codes` for **`409`** only — it does
  not extend to `400` and it does not extend to any other field. Anything else is Class C.
- **Starting values, not commitments** — the §8.5 dispatch values, the §5.2 browser values,
  `POOL_SIZE=1`. §8.5 says tune against staging.
- **No CodeRabbit section in this story, and none in Epic 10.** Ruled once for the epic by @po on
  2026-09-11: `coderabbit_integration.installation_mode` is `wsl`, this repository is worked on a
  Darwin host, the CLI is absent, and `graceful_degradation.skip_if_not_installed: true` applies. A
  draft checklist expecting such a section is satisfied by that ruling.

### The questions as originally raised

   The condition is currently a silent fail-open (`orElse(List.of())` → a run with no references).
   Making it terminal is not in question; **naming it** is a product decision, and §5.1.3 declines

2. **Are `resolvedVars` scrubbed, or only `resolvedSecrets`?** The contract says `resolvedVars` are

### "Close rather than watch" — it generalises, with one addition and one caution

Not safe as an unconditional rule.

**The addition: a closure is only as closed as everything it returns.** The corollary's own failure
mode is the one I just probed — remove the mutator and the object still hands out its mutable
interior. Here it cost nothing, because the removed path also removed the fragmenting; that was luck
of mechanism, not design. So: *close, then ask what the closed surface still hands out*, and keep a
small assertion on the production object afterwards — a closure with no assertion has no way to
announce that a later refactor reopened it. That is what shipped, and it is better than closing alone.

**The caution: where closing is unavailable, watching is not second-best, it is the whole of it**, and
it must not be read as a smell. This epic has at least four: `INHERITED_ENV_KEYS`'s
registry-redirecting class, where ADR-001 §4.2 *requires* `PLAYWRIGHT_BROWSERS_PATH` so the key cannot
be removed (SEC-2); the `ED-02` bypass, whose removal is 10.18's, so a live sibling is the only
instrument until then; `x-assigned-by` and the runner-error-code disjointness, which are documented
properties with nothing to close; and **`bounds.ts`'s truncate-before-redact residual itself** — @po
ruled against restructuring it, so the *ordering* is still watched and only the *access* got closed.

**The form that generalises:** *close when the bypass is removable without moving a responsibility to
a module that should not hold it; otherwise watch, and point the watcher at the production symbol
rather than at a stand-in.* Stated that way it is safe and consistent with @po's ruling.

I looked and did not find a new shape. What I found is the sixteenth repeating: the test written to
