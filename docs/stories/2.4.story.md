## User Story

**As a** platform operator running put-checks on 2+ replicas,
**I want** ShedLock (JDBC-backed) to ensure that `@Scheduled` tasks execute on exactly one pod at a time,
**so that** the cron dispatcher doesn't fire duplicate check executions and the partition DDL scheduler doesn't race on concurrent `CREATE TABLE` / `DETACH CONCURRENTLY`.

## Implementation Notes
- **ShedLock table in V1:** The V1 migration already creates `shedlock` with the exact schema ShedLock expects. No migration needed.
- **Two-context IT:** Use `@SpringBootTest` with different `spring.application.name` or `shedlock.lockedBy` values. Both share the same datasource (Zonky embedded PG). Execute the scheduled method directly (bypass `@Scheduled` timing).
- **lockAtLeastFor:** `30s` prevents rapid re-execution if the lock holder finishes quickly. This matches the 30s poll interval of the cron dispatcher.

## Dev Notes / QA Gate Notes

### Dev Notes (2026-04-18)

- **PROXY_SCHEDULER mode** (default) used instead of PROXY_METHOD. PROXY_METHOD causes `@Scheduled` auto-trigger to hold the lock, blocking test method calls. PROXY_SCHEDULER only intercepts scheduler-triggered invocations.
- **initialDelay** added to `@Scheduled` (configurable `checks.scheduling.initial-delay-ms`, default 5s). Tests override to 300s to prevent scheduler auto-firing during test execution.
- **usingDbTime()** configured on LockProvider — uses database server time instead of JVM time for reliable multi-pod locking.
- **Tests use LockProvider API directly** to verify mutual exclusion, rather than spinning up two Spring contexts. Cleaner and more reliable.
