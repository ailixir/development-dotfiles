## User Story

**As a** put-checks frontend developer validating the walking-skeleton end-to-end,
**I want** to toggle off MSW for specific API domains (`csi`, `checks`, HTTP execution paths) via an env flag and watch the real backend serve those requests,
**so that** the M1 exit criterion "FE works against localhost:8080" is provably met, and remaining MSW handlers (studio, reports) keep working while we wait for M4/M5.

---

## Acceptance Criteria

- [ ] **AC-1:** `frontend/src/services/mocks/mockMode.ts` is updated so MSW can be disabled per-domain rather than all-or-nothing. The set of "disabled" domains is read from `VITE_DISABLE_MSW_DOMAINS` env var (comma-separated).
- [ ] **AC-2:** Handler registration uses the per-domain toggle: if `csi` is disabled, the csi-handlers are not registered with `worker.use(...)`; similarly for `checks` + `studio` + `reports` + `dashboard`. Requests to disabled domains fall through to the real network (Vite / Webpack dev-server proxies to `VITE_API_URL`).
- [ ] **AC-3:** `VITE_API_URL` defaults to `http://localhost:8080` in `.env.development`; points to the platform-nginx-proxied origin in staging/prod.
- [ ] **AC-4:** The backend + FE run together locally:
  ```
  terminal 1: cd backend && ./gradlew bootRun --args='--spring.profiles.active=local'
  terminal 2: cd frontend && VITE_DISABLE_MSW_DOMAINS=csi,checks npm run dev:standalone
  ```
  The dashboard loads CSIs + checks from real backend; Create Check POSTs to real backend; HTTP check execution returns real 202 + poll works. Studio + Reports still use MSW.
- [ ] **AC-5:** `frontend/README.md` documents the env flag + a table: "M1 cutover: `csi,checks`. M2 cutover: add `schedules`. M4 cutover: add `reports`. M5 cutover: add `studio`. Full cutover: remove flag entirely."
- [ ] **AC-6:** `put:auth:unauthorized` browser-event handler (already in `apiClient.ts` from prior MFE work) is verified to fire correctly when the real backend returns 401 (no session). On fire: the MFE dispatches the event + the shell's AuthGate redirects to Core's `/api/v1/auth/login`. Manual verification + an automated Cypress test.
- [ ] **AC-7:** Cypress E2E test `checks-walking-skeleton.cy.ts`:
  - Run against the real backend (spawned in CI with Testcontainers-PG + Flyway).
  - Log in (Cypress auth shim writes the `put_session` cookie to the test browser) — OR use the Phase-2 `X-User-*` header path with a mock gateway.
  - Navigate to Dashboard → assert CSI list loads from real backend.
  - Create an HTTP check → POST hits backend → 201 returned.
  - Trigger execution → 202 received, poll endpoint returns SUCCESS after a moment.
  - Assert remaining FE routes (Studio, Reports) still render with MSW active.
- [ ] **AC-8:** CI job runs the Cypress E2E against a provisioned real backend + Zonky, publishes results. Does NOT block merges if only this single job fails (flaky E2Es shouldn't stop shipping) but reports status visibly.
- [ ] **AC-9:** Frontend console errors / warnings: 0 during the happy-path E2E. Any new "MSW disabled but handler matched" warning fails the test.

## Implementation Notes

- **Cypress auth shim:** the cleanest approach is to POST directly to a backend test-only endpoint that issues a `put_session` cookie via a stubbed identity (a Spring profile `cypress-test` wires `FakeCoreServiceClient` from story 1.4 as a primary bean). Isolates the E2E from the real OIDC dance while still exercising the real filter chain.
- **MSW handler unregistration:** MSW's `worker.start({ onUnhandledRequest: 'bypass' })` lets unhandled requests pass through to the network — this is what enables the per-domain toggle.
- **Don't move `apiClient.ts`**: the existing client already supports `VITE_API_URL` + cookie credentials. Zero changes needed there.
