## User Story

**As a** platform operator,
**I want** a `ReportDeliveryDispatcher` that polls for due reports every 60 seconds and dispatches them for rendering and delivery,
**so that** reports are automatically delivered to recipients at their configured schedule without manual intervention.

---

## Context & Rationale

Mirrors the `CronDispatcher` pattern established in EPIC-02: a `@Scheduled` poller with `@SchedulerLock` finds due items, dispatches them asynchronously, and advances the next delivery timestamp. The key difference is that report delivery is heavier (render HTML + send SMTP), requiring a larger lock window and smaller batch size.

## Acceptance Criteria

### Dispatcher bean

- [x] **AC-1:** `ReportDeliveryDispatcher` in `scheduling/` package with `@Component` and `@ConditionalOnProperty(name = "checks.reports.delivery-enabled", havingValue = "true", matchIfMissing = true)`.
- [x] **AC-2:** `@Scheduled(fixedDelayString = "${checks.reports.poll-interval-ms:60000}", initialDelayString = "${checks.reports.initial-delay-ms:10000}")`.
- [x] **AC-3:** `@SchedulerLock(name = "reportDeliveryDispatcher", lockAtMostFor = "10m", lockAtLeastFor = "1m")`.

### Polling logic

- [x] **AC-4:** `ReportsRepository.findDueReports(Instant now, Pageable pageable)` query: `SELECT r FROM Report r WHERE r.status = 'active' AND r.deletedAt IS NULL AND r.nextDeliveryAt IS NOT NULL AND r.nextDeliveryAt <= :now ORDER BY r.nextDeliveryAt ASC`.
- [x] **AC-5:** Batch size configurable via `checks.reports.batch-size` (default: 50).
- [x] **AC-6:** For each due report: delegate to `ReportDeliveryService.deliver(report)` (story 4.4f), then advance `nextDeliveryAt` using `ReportScheduleResolver.nextDeliveryFrom()`.

### Error isolation

- [x] **AC-7:** Individual report delivery failures are logged and counted but do not block other reports in the batch. Same pattern as `CronDispatcher.dispatchSingle()`.
- [x] **AC-8:** `nextDeliveryAt` is advanced regardless of delivery success/failure (prevents infinite retry loops for permanently-failing reports).

### Observability

- [x] **AC-9:** Micrometer gauge `checks.reports.delivery.due_count` — reports due per poll tick.
- [x] **AC-10:** Micrometer counter `checks.reports.delivery.dispatches_total{outcome=success|failure}`.
- [x] **AC-11:** MDC context: `dispatcherId=report-delivery`, `reportId`, `traceId`.

### Configuration

- [x] **AC-12:** `application.yml` defaults: `checks.reports.delivery-enabled: true`, `checks.reports.poll-interval-ms: 60000`, `checks.reports.batch-size: 50`.
- [x] **AC-13:** `application-local.yml`: `checks.reports.delivery-enabled: false` (disabled for local dev).
- [x] **AC-14:** `application-worker.yml`: `checks.reports.delivery-enabled: true`.
- [x] **AC-15:** `application-api.yml`: `checks.reports.delivery-enabled: false`.

## Implementation Notes

- **60s poll interval vs 30s for checks:** Reports are heavier (render + SMTP); lower frequency reduces DB load and prevents overwhelming the SMTP relay.
- **lockAtMostFor 10m:** A batch of 50 reports could take minutes to render and send. 10m gives headroom.
- **Stub delivery service:** If implementing 4.4d before 4.4f, create a `ReportDeliveryService` interface or class with a `deliver(Report report)` method that logs `"Report delivery not yet implemented for {reportId}"`. Replace in 4.4f.
- **Drift-free advancement:** Use `ReportScheduleResolver.nextDeliveryFrom(schedule, report.getNextDeliveryAt())` — same pattern as the CronDispatcher drift fix (story 2.8).
