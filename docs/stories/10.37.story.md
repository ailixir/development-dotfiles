## Story

**As a** Studio author,
**I want** global context and stable per-step context persisted as execution-affecting revision inputs,
**so that** save/load, reorder and concurrent edits cannot detach context from its step or leave an obsolete candidate runnable.

## Acceptance Criteria

1. **FR-1 / AC-1:** `ui_tests` persists optional global context and ordered v2 steps using the 10.36 contract. Create, update and read round-trip the same context scopes and exact text values.
2. **FR-1 / AC-2:** legacy rows containing ordered string steps are adapted durably on the first successful v2 write: each original string is byte-preserved, empty context is valid, and generated step IDs remain stable on all later reads. Reads before that write remain legacy and generate no IDs.
3. **FR-4 / AC-7:** validation rejects missing, duplicate and orphan step IDs atomically. Reorder/edit retains IDs and context; insertion requires a new ID; copy requires a fresh ID; deletion removes only the deleted step and its metadata.
4. **FR-5 / AC-8:** changing global context, a step's text/context, step order, a nonsecret referenced value or selected evidence reference increments the appropriate execution-affecting revision, sets compile status `STALE` and clears the current candidate under the existing 10.4 rules. Name/description-only changes retain readiness.
5. **FR-5 / AC-9:** update requires matching source/configuration revisions and performs revision comparison, persistence and stale transition atomically. Two writes from one base revision yield one success and one `409 STALE_REVISION`; a late compile cannot restore readiness after a context edit.
6. Immutable `ui_test_revisions` snapshots store the exact global context, ordered stable-ID steps and selected evidence-reference identities used for that candidate. Existing confirmed/history rows are never rewritten.
7. CSI visibility and write authorization continue to apply through the existing Studio service/repository path. No cross-CSI context or evidence-reference identity is disclosed by create/read/update behavior.
8. The migration is forward-only, applies after V17 on databases containing legacy and v2 rows, and does not fabricate confirmed revisions or observed evidence.
9. Testcontainers and service tests cover migration from legacy rows, repeat-read ID durability, exact empty/Unicode/quoted/newline/whitespace context, add/edit/reorder/copy/delete, duplicate/orphan rejection, optimistic races, context-only invalidation and immutable revision snapshots.
10. Targeted backend tests, Spotless, Checkstyle and SpotBugs pass; `./gradlew check` is attempted and any known environment-only baseline failure is recorded without weakening the story tests.
