## User Story

**As the** put-checks platform,
**I want** a `@Scheduled` poller that identifies schedules whose `next_execution_at` has passed, dispatches their checks for async execution, and advances the next execution time,
**so that** scheduled checks run on their configured cadence without user intervention.

---

## Acceptance Criteria

- [x] **AC-1:** `CronDispatcher` bean with `@Scheduled(fixedDelay = 30000)` polls the `schedules` table for rows where `enabled = true AND next_execution_at <= NOW()`.
- [x] **AC-2:** For each due schedule: dispatch the associated check via the existing `CheckExecutorDispatcher` + async execution path (same as `POST /checks/{id}/execute` from story 1.12). Re-uses `checkExecutor` bean for async dispatch.
- [x] **AC-3:** After dispatch, compute `next_execution_at` from `cron_expression` + `timezone` using `CronExpression.next(ZonedDateTime.now(timezone))` and update the schedule row.
- [x] **AC-4:** If a check's executor throws or the dispatch fails, log the error and skip to the next schedule. Do NOT stop the entire poll cycle for one failure.
- [x] **AC-5:** Each dispatch cycle is wrapped in its own transaction per schedule (not one big tx for all due schedules). If one schedule fails to update, others are not affected.
- [x] **AC-6:** MDC enrichment: `schedulerId=cron-dispatcher`, `scheduleId`, `checkId`, `traceId` (generated per dispatch cycle).
- [x] **AC-7:** Micrometer counters: `checks_scheduled_dispatches_total{outcome=success|failure}`, gauge `checks_scheduled_due_count` (number of due schedules found per poll).
- [x] **AC-8:** Dispatcher disabled via `@ConditionalOnProperty(checks.scheduling.dispatcher-enabled)`. Set to `false` in application-local.yml (used by tests + local dev). Defaults to `true` (production).
- [x] **AC-9:** Integration test `CronDispatcherIT`: seed a schedule with `next_execution_at = NOW() - 1 minute` + enabled=true, trigger the dispatcher method manually (not via `@Scheduled`), assert: (a) execution_result row created, (b) `next_execution_at` advanced to the future.
- [x] **AC-10:** Integration test `CronDispatcherDisabledIT`: seed a schedule with `enabled = false`, trigger dispatcher, assert no execution dispatched.
- [ ] **AC-11:** JaCoCo coverage ≥ 80%.

## Implementation Notes
- **Poll interval:** 30s `fixedDelay` is a balance between latency and DB load. Configurable via property `checks.scheduling.poll-interval-ms`.
- **Batch size:** limit the query to 100 due schedules per cycle to prevent a single poll from hogging the executor. Remaining due schedules are picked up in the next cycle.
- **CronExpression:** Spring 6's `CronExpression` supports standard 6-field cron. Use `expression.next(ZonedDateTime.now(ZoneId.of(schedule.getTimezone())))` to compute next fire time.
- **Transaction isolation:** use `TransactionTemplate(REQUIRES_NEW)` per schedule, same pattern as bulk delete in story 1.14.

## Dev Notes / QA Gate Notes

### Dev Notes (2026-04-18)

- **@ConditionalOnProperty** used instead of `@Profile("!test")` per PO note N-2.3-1. Property `checks.scheduling.dispatcher-enabled` defaults to `true` (matchIfMissing), disabled in `application-local.yml`.
- **TransactionTemplate** per schedule with managed entity reload inside the tx to ensure `next_execution_at` updates are persisted (detached entities from the initial query don't auto-flush).
- **Batch size** capped at 100 schedules per poll cycle. Remaining are picked up next cycle.
- **Async dispatch** re-uses the same `checkExecutor` bean and `executeAsync` pattern from `CheckExecuteController`.
