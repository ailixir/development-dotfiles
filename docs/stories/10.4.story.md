## User Story

**As a** Studio author whose confirmed test may be recompiled, edited or executed concurrently by others,
**I want** every compiled candidate stored as an immutable revision with hashes, provenance and write-once confirmation, separate from my mutable draft,
**so that** what I approved is exactly what runs, an out-of-order or stale compile can never replace it, and history keeps the revision it actually executed.

---

## Problem Statement

Today `ui_tests` is the only Studio table: steps live as mutable JSONB on the test row, there is no compile state, no artifact identity, and `StudioService.updateTest` overwrites `csiId` (line 75), which would move historical evidence between CSIs. The review (P1-2, P1-5) showed that a user can review artifact A, a recompile can replace it with B for the same text, and the first user's confirmation then approves unseen B.

Architecture §4.2/§8.1 require: mutable `sourceRevision`/`configurationRevision` on the draft; compile states `STALE | COMPILING | AWAITING_CONFIRMATION | READY | NEEDS_REVISION`; a persisted compile request identity whose result publishes only if request and source revision still match; an immutable `ui_test_revisions` row per validated candidate; confirmation recorded once with `confirmedBy/At`; CSI registered, non-null and immutable.

Latest migration is `V11`. This story owns **`V12`**. Story 10.1's V14 adds `ui_test_executions.revision_id` referencing this table, so V12 must merge first (FOC-01).

## Acceptance Criteria

### Schema (V12)
- [ ] **AC-1:** `V12__ui_test_revisions_and_compile_state.sql` creates `ui_test_revisions`: `id UUID PK`, `test_id UUID NOT NULL REFERENCES ui_tests(id)` (no cascade delete: history survives soft delete), `csi_id VARCHAR(20) NOT NULL`, `source_revision BIGINT NOT NULL`, `configuration_revision BIGINT NOT NULL`, `source JSONB NOT NULL` (ordered `originalText`), `source_hash VARCHAR(64) NOT NULL`, `artifact JSONB NOT NULL`, `artifact_hash VARCHAR(64) NOT NULL`, `artifact_schema_version INT NOT NULL`, `configuration JSONB NOT NULL` (nonsecret), `references JSONB NOT NULL` (declared variable/secret references), `provenance JSONB NOT NULL` (model, prompt, language-policy, syntax-reference, validator, executor and runtime-compatibility versions), `created_by`, `created_at`, `confirmed_by VARCHAR(255) NULL`, `confirmed_at TIMESTAMPTZ NULL`; `UNIQUE (test_id, source_revision, configuration_revision, artifact_hash)`; index `(test_id, created_at DESC)`.
- [ ] **AC-2:** V12 adds to `ui_tests`: `source_revision BIGINT NOT NULL DEFAULT 1`, `configuration_revision BIGINT NOT NULL DEFAULT 1`, `compile_status VARCHAR(30) NOT NULL DEFAULT 'STALE'` with CHECK on the five states, `compile_request_id UUID NULL`, `compile_error JSONB NULL`, `compile_diagnostics JSONB NULL`, `current_candidate_revision_id UUID NULL REFERENCES ui_test_revisions(id)`, `confirmed_revision_id UUID NULL REFERENCES ui_test_revisions(id)`.
- [ ] **AC-3:** V12 adds `ui_tests.quarantined_at TIMESTAMPTZ NULL` and sets it to `NOW()` for rows whose `csi_id` is `NULL` or not present in `csi_systems`, logging the count. Quarantined rows are excluded from every user-facing query and from compile/confirm/execute, but are **never deleted or reassigned** (BRD §9: no authored test is lost). A CHECK `(csi_id IS NOT NULL) OR (quarantined_at IS NOT NULL)` enforces registered CSI for all non-quarantined rows; the API requires a registered `csiId` on create. Resolution of quarantined rows is an explicit later migration or admin action, not part of this story.
- [ ] **AC-4:** A trigger (or equivalent DB constraint) on `ui_test_revisions` rejects any `UPDATE` that changes a column other than `confirmed_by`/`confirmed_at`, and rejects changing `confirmed_by`/`confirmed_at` once non-null (write-once).
- [ ] **AC-5:** All legacy `ui_tests` rows end the migration with `compile_status = 'STALE'`, no candidate and no confirmed revision. No fabricated revision rows are created.

### Draft revisions and optimistic concurrency
- [ ] **AC-6:** `PUT /tests/{id}` requires `sourceRevision` and `configurationRevision` in the body; if either differs from the stored value the update is rejected with `409 STALE_REVISION` and no field changes.
- [ ] **AC-7:** A step-text change increments `source_revision`; an execution-affecting configuration change (environment, variable values/references, viewport, timeoutSeconds, browser, waitStrategy, target policy selection) increments `configuration_revision`; `name`/`description` changes increment neither.
- [ ] **AC-8:** Any increment of `source_revision` or `configuration_revision` sets `compile_status = 'STALE'` and clears `current_candidate_revision_id`; `confirmed_revision_id` is retained for history but the test is not runnable until a new candidate is confirmed (readiness enforcement is 10.8).
- [ ] **AC-9:** `csiId` is accepted on create only, must exist in `csi_systems`, and is ignored-with-`409 CSI_IMMUTABLE` on update when it differs from the stored value. `StudioService.updateTest` no longer calls `setCsiId`.

### Compile-state machine (service layer, used by 10.8/10.9)
- [ ] **AC-10:** `CompileStateService.beginCompile(testId)` persists a new `compile_request_id` and `compile_status = 'COMPILING'` together with the `source_revision` it was started for, in one transaction.
- [ ] **AC-11:** `CompileStateService.publishCandidate(testId, compileRequestId, sourceRevision, candidate)` inserts the `ui_test_revisions` row and sets `current_candidate_revision_id` + `AWAITING_CONFIRMATION` **only if** `ui_tests.compile_request_id` and `source_revision` still equal the supplied values (conditional `UPDATE ... WHERE`); otherwise the candidate is discarded and the call returns `DISCARDED_OUT_OF_ORDER`. An older compile for the same text is discarded the same way.
- [ ] **AC-12:** `CompileStateService.publishInvalid(...)` records per-step diagnostics and sets `NEEDS_REVISION` under the same conditional rule; `publishError(...)` leaves the draft saved and sets `STALE` with `compile_error`.
- [ ] **AC-13:** `CompileStateService.confirm(testId, revisionId, artifactHash, sourceRevision, configurationRevision, principal)` succeeds only when `current_candidate_revision_id = revisionId`, the revision's `artifact_hash`, `source_revision` and `configuration_revision` match, and the revision is unconfirmed; it sets `confirmed_by/at` once, `confirmed_revision_id`, and `READY`. Any mismatch returns `409 STALE_CANDIDATE`. (The HTTP endpoint and repair loop are 10.9; this story ships the transaction and its tests.)
- [ ] **AC-14:** Soft-deleting a test (`DELETE /tests/{id}`) keeps all its revisions readable through history and blocks new compile/confirm with `409 TEST_DELETED`.

### Tests
- [ ] **AC-15:** `RevisionMigrationIT` (Testcontainers): V12 applies on a DB seeded with V1–V11 data including null-CSI and unknown-CSI tests; quarantine counts match; write-once trigger rejects a second confirmation and any artifact mutation.
- [ ] **AC-16:** `OptimisticSaveIT`: two concurrent `PUT`s with the same revisions → exactly one succeeds, the other gets `409 STALE_REVISION`.
- [ ] **AC-17:** `CompileStateServiceTest`: reversed completion (request 2 publishes before request 1) leaves request 2's candidate current and discards request 1; two compiles of identical text cannot publish the older one.
- [ ] **AC-18:** `ConfigurationRevisionTest`: name/description update preserves `READY`; each execution-affecting field change flips to `STALE` and requires reconfirmation.
- [ ] **AC-19:** `CsiImmutabilityIT`: update with a different `csiId` → `409`; the test's revisions keep their original `csi_id`.
- [ ] **AC-20:** `RevisionRetentionIT`: after 10.1's V14 is present, a queued or historical execution row keeps its `revision_id` after the draft is edited and recompiled. (Runs only once 10.1b has merged; documented as the FOC-01 cross-check.)
- [ ] **AC-21:** JaCoCo ≥ 80% on modified classes; `./gradlew check` green.

## Implementation Notes

- **FOC-01:** this story must merge before 10.1b. If one owner takes both, V12 still lands first as its own migration.
- Hashes: `source_hash` over the canonical JSON of ordered `originalText`; `artifact_hash` over canonical artifact bytes (§8.1). Use one canonicalization helper shared with 10.8/10.9 and document it in the contract.
- Conditional updates are the mechanism for every transition (`UPDATE ui_tests SET ... WHERE id = ? AND compile_request_id = ? AND source_revision = ?`); check affected-row count, never read-then-write.
- Keep `compile_diagnostics` bounded (per-step message length and count) so a hostile compile output cannot bloat the row; exact limits come from §4.3 input/output limits configured in 10.8.
- The CSI quarantine hides rows from user access; it never deletes or reassigns them. Keep the quarantine predicate in one repository specification reused by every list/get path.
