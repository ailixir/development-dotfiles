## User Story

**As a** user managing check schedules,
**I want** schedule CRUD operations to use the dedicated `/api/v1/schedules` backend resource,
**so that** I can create, update, enable/disable, and delete schedules independently, with cron validation and timezone support from the real backend.

---

## Acceptance Criteria

- [ ] **AC-1:** New `schedulesApi.ts` service created in `src/services/api/` with all CRUD operations: create, list, getById, update, setEnabled, delete.
- [ ] **AC-2:** `schedulesApi.create()` calls `POST /api/v1/schedules` with body `{checkId, frequency, cronExpression, timezone, enabled}`. Returns 201 + `ScheduleDto`.
- [ ] **AC-3:** `schedulesApi.list()` calls `GET /api/v1/schedules` with optional filters: `checkId`, `enabled`, `timezone`, pagination. Response normalized via `normalizePageResponse`.
- [ ] **AC-4:** `schedulesApi.getById()` calls `GET /api/v1/schedules/{id}`. Returns `ScheduleDto`.
- [ ] **AC-5:** `schedulesApi.update()` calls `PUT /api/v1/schedules/{id}`. Returns updated `ScheduleDto`.
- [ ] **AC-6:** `schedulesApi.setEnabled()` calls `PATCH /api/v1/schedules/{id}/enabled` with body `{enabled: boolean}`. Returns updated `ScheduleDto`.
- [ ] **AC-7:** `schedulesApi.delete()` calls `DELETE /api/v1/schedules/{id}`. Returns 204.
- [ ] **AC-8:** Schedule mapper `mapScheduleDtoToCheckSchedule(dto: BackendScheduleDto): CheckSchedule` created in `src/services/api/mappers/scheduleMapper.ts`. Maps: `cronExpression`→`cron`, `frequency`, `timezone`, `enabled`, `nextExecutionAt`→computed display.
- [ ] **AC-9:** `checksApi.updateCheckSchedule()` refactored: instead of `PUT /checks/{id}/schedule`, it now calls `schedulesApi.create()` (if no schedule exists) or `schedulesApi.update()` (if schedule.id is known from the embedded check response). Seamless for callers.
- [ ] **AC-10:** `checksApi.pauseCheck()` and `checksApi.resumeCheck()` for schedule-related pause/resume refactored to call `schedulesApi.setEnabled(scheduleId, false/true)`. NOTE: the original `POST /checks/{id}/pause` and `POST /checks/{id}/resume` mock endpoints handled check-level pause, not schedule-level. If the BE has no check-level pause, these should map to schedule disable/enable. If the BE adds check-level pause in story 3.9, revisit.
- [ ] **AC-11:** `ScheduleDialog` component updated: on save, calls `schedulesApi.create()` or `schedulesApi.update()`. Cron validation errors from BE (400 response) displayed inline.
- [ ] **AC-12:** `checksSlice.ts` thunks `updateCheckSchedule`, `pauseCheck`, `resumeCheck` updated to use `schedulesApi`. State shape unchanged.
- [ ] **AC-13:** `fetchUpcomingExecutions` thunk updated: calls `schedulesApi.list({enabled: true, limit: N})` and maps to the existing upcoming executions format, OR defers to story 3.9's `/checks/upcoming` endpoint. Use schedule list as interim.
- [ ] **AC-14:** Add `schedules` to `VITE_DISABLE_MSW_DOMAINS` cutover comment.
- [ ] **AC-15:** `npm run type-check` passes.
- [ ] **AC-16:** ScheduleDialog create/edit/enable/disable verified in browser (manual verification).

## Implementation Notes

### Backend ScheduleDto shape
```json
{
  "id": "550e8400-...",
  "checkId": "550e8400-...",
  "frequency": "EVERY_5_MIN",
  "cronExpression": "*/5 * * * *",
  "timezone": "America/New_York",
  "enabled": true,
  "nextExecutionAt": "2026-04-27T15:30:00Z",
  "createdAt": "2026-04-27T...",
  "updatedAt": "2026-04-27T..."
}
```

### Schedule lookup from check
The `GET /api/v1/checks/{id}` response already embeds the schedule (per story 2.1 AC-10). When the user opens ScheduleDialog, the schedule ID is extracted from `check.schedule.id`. If null, create; if present, update.
