## 1. Recommendation

Make Code an optional advanced editor for the **supported Studio browser instructions**, backed by **native immutable Studio revisions**. An author edits a separate draft, saves it, validates the exact whole artifact without AI rewriting, reviews and explicitly confirms the resulting revision, then runs that exact identified revision. Offer **Download revision** as a faithful Studio source package. [FR-1–FR-8; DEC-1–DEC-5; architecture-proposal.md; research.json]

| Option | Benefit | Cost or limitation | Proposed decision |
|---|---|---|---|
| Native immutable revisions + editable draft | Reuses existing CSI authorization, validator, confirmation, dispatch and evidence; exact code/run provenance | Adds durable manual authoring, full concurrency guards and explicit source-mode transitions | **Recommended** |
| Mutable code override at Run | Small apparent editor/API change | Visible code can move after approval; making it safe requires validated immutable snapshots | Reject as execution authority |
| Git as execution authority | Developer branches, reviews and collaboration | Adds credentials, CSI/repository authorization, ingestion and dual-authority reconciliation; a commit alone does not pin runtime inputs | Consider later integration; ingest into native validated revisions |
| Full Playwright/TypeScript projects | Imports, custom helpers and maximum flexibility | Exceeds current allowlist and operation-only runner; needs separate isolation, dependency, credential and evidence architecture | Separate product/runtime scope |

The recommendation assumes the requested editing concerns Studio's existing bounded language [ASM-1]. A locally runnable Playwright package is an additional capability [ASM-2; OQ-1], not the initial download format. Support existing permitted sequences of awaited calls within each step; do not reduce the actual validator grammar to the Code tab's inaccurate single-call comment. No new editor library or execution service is required for this first slice. [CON-1/CON-3; research.json; ux-analysis.md]

### 1.1 PRD and implementation findings

The checked-out PRD §5.2 requires source review, exact immutable revision confirmation and reconfirmation after relevant edits. Its explicit download commitment is **video download**; it does not explicitly mandate editable source or source download. Those additions derive from the user's request. Earlier inspected PRD revisions mention Python generation and evidence downloads; the current plan retires Python export. [requirements.json: prdGap, USER-1, PRD-1–PRD-3, HISTORY-1]

Today Code shows only the independently read confirmed artifact/hash in read-only blocks. ADR-002 §30 expressly establishes that confirmed-only surface. The proposed Draft/candidate editor **explicitly supersedes that restriction for distinct views** while retaining the Confirmed view's identity guarantee. New revision inspection/export requires a deliberate public-contract amendment, including ADR-002 §21/§30; no existing code route is presumed to permit these new semantics. [CODE-1; ADR-30; CON-1; architecture-proposal.md]

The current dirty-tree compile path calls `publishAcceptedCandidate`, which stamps confirmation actor/time and READY during preparation. This is a static-code finding, not a statement about a deployed environment. It conflicts with the PRD's review of the exact generated bytes. Correcting generated approval is a prerequisite of the proposed manual-source lifecycle: **neither generated preparation nor manual validation may approve newly produced source**. [CODE-2; FR-3; architecture-proposal.md]

### 1.2 First-slice boundary

Goals: optional bounded source editing; durable draft recovery; whole-artifact validation; explicit generated/manual review and confirmation; exact run identity; authorized native source download. [FR-1–FR-8]

Separate scope: arbitrary TypeScript/projects, Python export, portable `.spec.ts` adapters, source import, Git synchronization, automatic English/code synchronization, mixed manual/generated incremental merging, historical restore/rerun selection and revision-browser product expansion. Saved checkpoints and retained revisions support preservation and the required current/candidate/last-run views; this proposal does not add a general history-management product. [CON-1/CON-2/CON-5; architecture-proposal.md; research.json; ux-analysis.md]

## 3. Execution-source architecture

All technical details in this section derive from Aria's [architecture-proposal.md](architecture-proposal.md), Dara's [data-versioning-review.md](data-versioning-review.md) and verified patterns in [research.json](research.json). They are proposed decisions, not existing API/schema guarantees. [DEC-1–DEC-5]

### 3.1 One source authority, separate version identities

| Identity | Meaning and rule |
|---|---|
| `sourceRevision` | Existing checklist order, stable step IDs and original English identity; retain its meaning |
| `configurationRevision` / `authoringContextDigest` | Existing execution/generation context, settings, referenced nonsecret values and selected evidence freshness |
| `codeDraftRevision` | New monotonic per-test counter for accepted manual saves and explicit GENERATED/MANUAL mode changes; never reset on a switch |
| `authoringMode` | GENERATED or MANUAL; selects preparation authority |
| `codeDraftHash` | Server hash of ordered saved manual step IDs/code/base/mode; null for ordinary generated authoring |
| `requestId` / `attemptId` | Captured immutable preparation event; retry identity |
| `revisionId` | Immutable validated artifact/context/provenance event, even when another event has equal code |
| `artifactHash` | SHA-256 of canonical artifact UTF-8 bytes; content integrity, not approval or a unique revision identity |
| Artifact version / execution snapshot revision | Artifact schema / SSE state counter; neither is source-version identity |

Use this full freshness tuple:

```text
F = { sourceRevision, configurationRevision, codeDraftRevision,
      authoringMode, authoringContextDigest, codeDraftHash }
```

Hashes/digests come from saved server state. Client values are expectations to compare. An abbreviated hash may supplement a visible revision ID; it must not be labeled a unique revision number. Configuration-only changes can produce different execution revisions with identical artifact bytes. [FR-5/FR-6/FR-7; DEC-2]

### 3.2 Save, prepare, confirm, execute

1. **Edit** copies a compatible retained candidate/confirmed revision belonging to the same test/CSI into a working buffer. Preserve stable step IDs/order and frozen `originalText`; edit only step code. Opening Edit or typing does not mutate server readiness. UI dirty protection blocks dispatch of unresolved local changes. [FR-1/FR-4]
2. **Save** conditionally checks F and the base/checkpoint identity, structurally binds code to the saved checklist, creates an append-only manual checkpoint and activates MANUAL authority. Keep bounded invalid syntax so it can be corrected; this is unvalidated authoring data, not an executable revision. Advance `codeDraftRevision` for an accepted actual code/mode change; ordinary identical-save retries have stable documented idempotency/no-op semantics. Retain the historical confirmed pointer. [FR-1/FR-5/FR-6; data review]
3. **Validate** captures exact manual code/hash, F, source/context, reference policy, actor, versions and deadline under the draft lock; commit before validator work. Validate the whole artifact with existing schema/AST/policy/resource rules. Invoke no LLM or automatic repair and do not rewrite saved manual code. [FR-3/FR-8; NFR-1]
4. **Publish** settles only the still-current captured attempt/F within lifecycle/deadline guards. Candidate insertion and settlement are atomic. Success creates a new immutable manual revision and AWAITING_CONFIRMATION; failure publishes bounded diagnostics for those inputs. A delayed success, failure, timeout or repair cannot replace newer work. [FR-3/FR-5/FR-6; NFR-2]
5. **Review/confirm** shows exact code/settings, changes against base and summaries of validated operations. Confirmation submits candidate `revisionId`, `artifactHash`, request identity and F; only an explicit authenticated approval writes confirmation actor/time once. [FR-3/FR-4]
6. **Execute** submits the intended current confirmed `revisionId`, `artifactHash` and F. Under the existing acceptance lock, repeat readiness/current-identity checks and snapshot that exact revision. A confirmation race cannot redirect the run to someone else's newer revision. Existing dispatcher/runner read accepted immutable source and convert validated code to typed operations. [FR-5/FR-6/FR-8]

Run on new generated/manual source may prepare and open review. An explicit **Confirm and Run** may approve the displayed candidate and then execute it, but the execution request must still carry the same identity/F. An already current compatible confirmed revision runs directly. Save/Validate/Compile/Download never approve newly prepared source. [FR-3; UX-05/06]

Readiness remains a consistent read of current saved inputs and confirmed revision, independent of `compileStatus`. Add independent mode/code counter/hash/context checks to existing ownership, source/configuration, artifact, reference-policy and compatibility checks. A saved code change blocks readiness even if status is erroneously READY. A failed optional recompilation of unchanged inputs does not revoke an otherwise current compatible confirmation. A changed candidate pointer alone does not silently replace existing accepted source. [FR-6; architecture proposal]

### 3.3 Checklist changes and regeneration

MANUAL blocks ordinary generated compile, save listeners, retries, inference and incremental entry points. Use an explicit **Generate from Steps** conditional mode transition; advance code identity, clear active manual identity and preserve saved manual checkpoints/history. Protect unsaved work with Save/Discard/Keep editing. New generated output awaits review. Late results from an earlier mode remain ineligible. [FR-4/FR-6]

Checklist/context changes stale manual source as a whole. With identical stable IDs/order/English, explicit review can revalidate preserved code under changed context. Text/structural changes require compatible generation in this first slice; no silent positional remapping, reverse translation or per-step merge. Initially exclude manual revisions from generated incremental baselines; use compatible generated baselines or full generation. [FR-4; research recommendation; architecture proposal]

### 3.4 References and provenance

Keep current artifact alignment and schema limits, including 100 steps and 2000 code characters per step, subject to stricter applicable validator/API caps. Multiple permitted awaited calls per step remain supported. Validation of syntax/reference policy does not prove equivalence with original English or the intended business assertion. [FR-3/FR-4; NFR-1; architecture proposal]

Versioned authoring's required/allowed reference policy derives from saved immutable authoring, with current derivation version; manual code cannot omit required references or introduce undeclared/disallowed ones. Legacy authoring keeps its existing token-reference rule. Context/reference-policy changes require new validation/confirmation, not a manual-source bypass. Historical `expectedIntent` is retired by ADR-SC-003 and must not become a behavioral-equality constraint forcing manual corrections to remain generated operations. [FR-8; architecture proposal]

Manual provenance records actual editor/validator actor/time, MANUAL origin, parent revision, checkpoint/attempt identity, authoring/policy derivation and validator/executor/runtime compatibility pins. Its validation fingerprint describes actual validation/policy/runtime inputs, distinct from a generated compiler fingerprint; it has no fabricated model/prompt fields. Parent model provenance is a separate historical reference, not a claim that AI generated edited source. Incompatible/revoked history remains inspectable subject to authorization but cannot execute. [FR-5/FR-8]

## 4. Proposed contracts and Code-tab behavior

The exact F fields from §3.1 apply to each expected/captured identity below. Names and routes are proposed for a coordinated contract amendment; they do not exist today. Keep existing authorization/lifecycle/refusal ordering and no-existence-oracle behavior. [architecture-proposal.md; FR-6/FR-8]

| Operation | Proposed successful behavior | Required safeguards |
|---|---|---|
| Existing authoring/Steps/context/configuration writes | Required expected F for code-capable draft; conditional existing authoring save returns current/new complete F, preserving checkpoint history | Compare caller F against current persisted draft under the common write lock; classify actual input changes using existing source/config meanings; retain manual mode/code and mark incompatible source unresolved; metadata/no-op saves do not manufacture changed freshness |
| `GET /tests/{id}/code-draft` | 200 saved mode/F/base and ordered code blocks | CSI-scoped read; detail projection only; no heavy list payload |
| `PUT /tests/{id}/code-draft` | Expected F, mode MANUAL, baseRevisionId and ordered `{stepId, code}`; conditional checkpoint/save returns new F. GENERATED is deliberate regeneration transition | Server structural assembly; bounded/credential/mapping rejection; 409 stale identity/base; preserve old saved work |
| `POST /tests/{id}/code-draft/validate` | Expected F; 202 immutable requestId/captured F; existing request-state surface exposes status, diagnostics and candidate | Correct active mode; captured full identity; accepted validation rejection is NEEDS_REVISION; unavailable validator is retryable authoring failure |
| Existing compile | Expected/captured F; generated success is AWAITING_CONFIRMATION | Reject MANUAL unless explicit switch already succeeded; no auto-approval |
| Existing confirm-compile | Existing revision/hash/source/config fields plus request identity, code/mode/context/hash expectations; 200 committed confirmed detail | Exact still-current candidate/F/policy; stale candidate 409; write-once approval |
| Existing execute | Required expected confirmed revisionId/artifactHash/F; ordinary accepted execution response unchanged | Identity/current readiness checked under acceptance lock; moved source 409; no implicit latest-revision selection |
| `GET /tests/{id}/revisions/{revisionId}` | 200 safe SourceRevisionDetail for selected retained same-test/CSI candidate/confirmed/last-run artifact/hash/identity/state, safe provenance, step mapping and validated behavior summary | Shared protected reader with ZIP; one authoritative persisted snapshot; explicit §21 amendment; no current-draft substitution/raw provenance |
| `GET /tests/{id}/revisions/{revisionId}/source-download` | 200 protected ZIP of selected immutable artifact + allowlisted manifest | Existing CSI visibility first; integrity checks; no unsaved source identity; safe server filename |

Paths above are relative to `/api/v1/studio`; authoring payload schema v2 is distinct from API contract/capability versioning. Version/capability the new confirmation/execute contract and update first-party clients/MSW together. A client lacking full expectations cannot bypass code-draft checks. Any temporary old generated-only contract exists only in an explicit code-disabled compatibility window and is removed or given equivalent server identity enforcement at full rollout. [FR-6; architecture proposal]

Execute idempotency hashes stable submitted fields: test, principal, route and expected revision/hash/F. An identical-key identical-request replay returns its original accepted execution after later edits; look up that replay before checking whether the old F is current. The same key for another revision is a conflict. Do not hash later server state into the request digest. [FR-5/FR-6; NFR-2]

### 4.1 Complete writer/outcome guard matrix

The complete freshness guarantee applies to **existing and new paths**. Public mutations use client-supplied expected F; background preparation work uses the server's immutable captured F and request identity. A worker must not fabricate request-body expectations from whatever draft exists when it finishes. The shared draft lock or equivalent conditional SQL is the final arbiter. Cancellation/abandonment below describes settlement of existing preparation work; it adds no user cancellation capability. [FR-6; NFR-2; architecture/data reviews; critique-1.json: CRIT-1]

| Existing/new path | Identity checked against current persisted state | Allowed mutation / stale outcome |
|---|---|---|
| Existing Steps/authoring/context/config saves, including legacy/v2 adapters and save listeners | Authenticated caller's expected F; current owning CSI/lifecycle; server-derived saved authoring/context identity | Atomically apply actual source/config change and return new F; preserve manual checkpoints; invalidate affected candidate/request freshness. Metadata/no-op does not revoke readiness. Stale caller gets conflict before changes |
| Manual code save / explicit mode switch | Caller expected F and base/checkpoint ownership/hash; server verifies structural checklist compatibility | Append bounded checkpoint or deliberate authority event; advance code counter for actual change; preserve history. Stale save/switch changes nothing |
| Generated/manual preparation capture, including inference/incremental/repair entry points | Caller expected F when invoked publicly; otherwise current authoritative persisted F; permitted mode; exact source/context/reference policy/runtime pins | Capture immutable requestId/F/input snapshot under draft lock before work. Generated capture refuses MANUAL; repair inherits its eligible captured parent identity |
| Successful candidate publication | Captured requestId/F/code checkpoint/hash plus current active request, lifecycle and deadline; insert bound to captured event | Candidate insertion/settlement atomically publishes AWAITING_CONFIRMATION. A stale result cannot insert/publish a runnable candidate or change newer draft state |
| Validation failure, unavailable dependency, timeout/deadline, bounded repair exhaustion | Same captured requestId/F and current active request/lifecycle; outcome-specific deadline conditions | Publish diagnostics/error for that current captured work only. Late outcome cannot clear newer candidate/request; unchanged current confirmed readiness survives optional preparation failure |
| Preparation cancellation or abandonment sweeper | Selected request's immutable requestId/F/capture identity rechecked against current active request/draft in conditional settlement; applicable cancellation/deadline/abandonment criteria | Status/time can select candidates for examination, but cannot authorize mutation alone. Old cancellation/sweep cannot clear newer manual/request/candidate or revoke unchanged confirmed readiness; stale settlement has no current-draft effect |
| Exact confirmation | Caller candidate revisionId/artifactHash/requestId/F; immutable candidate capture; current candidate/F and reference/runtime compatibility | Write first approval and change confirmed pointer atomically. Stale/cancelled/replaced preparation cannot be confirmed |
| Readiness | One consistent saved draft + confirmed revision read; compare persisted F/hash/ownership/context/reference/runtime identity | Read-only verdict independent of compileStatus; real saved input/mode/code change blocks, optional unchanged preparation outcome alone does not |
| Execution acceptance and stable replay | Authenticate owning CSI; replay exact submitted-key/digest first; for new acceptance compare caller expected confirmed revisionId/hash/F under draft lock and repeat readiness | Original accepted replay stays original; new acceptance snapshots exactly expected revision. Moved identity refuses; concurrent save cannot interleave between gate and snapshot |

### 4.2 Views and action states

Keep Steps as the starting point and add explicit **Edit source**, **Validate source**, **Confirm this exact revision**, **Generate from Steps** and **Download revision**. Page Save includes code; local code survives tab changes/background reads and joins existing dirty/navigation/unload guards. Use existing accessible MUI controls with per-step labels and diagnostics rather than requiring a rich-editor dependency. [FR-1/FR-7; NFR-3; UX-01/03/10]

Provide **Draft**, **Confirmed**, and **Last run** views where applicable. They select inspected/downloaded source, not alternative execution targets. Show source origin, state and distinct revision identity. After manual editing label English **Original checklist context** and derive **Executed behavior** from validated operations. Never update the English description through an assumed equivalence. [FR-4/FR-7]

Page Save across the existing authoring endpoint and the new code endpoint is an **ordered two-request flow**, not one cross-request transaction: capture the Save-start buffer, save changed Steps/context/config first, then use returned F to save compatible code. If either request fails, stop; do not validate or Run and do not report all work saved. Preserve unsaved code and any edits made after Save began. If English/order changes make the code mapping incompatible, keep that code for recovery, show that Steps were saved but source is unresolved, and require explicit compatible generation; do not remap it to the returned steps or discard it. A later conflict preserves both the successful first save and the remaining local work. [FR-1/FR-4/FR-6; UX-03/07/09; QA pre-review save-flow finding]

| State | Next action and Run behavior |
|---|---|
| Saved Steps, no source | Generate from Steps; Run prepares then opens review |
| Local code changed | Save/discard; protect local work; do not dispatch unresolved changes |
| Saved manual draft invalid/pending | Correct/Validate; actionable bounded diagnostics; no draft execution |
| Valid new candidate | Review/Confirm exact revision; explicit Confirm and Run may then dispatch the same identity |
| Current confirmed compatible source | Run exact revision directly; edit/download permitted |
| Source/context/config changed | Previous confirmation remains historical; explicit validation/regeneration and renewed approval |
| Optional preparation failed, unchanged confirmed inputs | Explain failed preparation while preserving existing readiness |
| Active execution, later draft changes | Last run remains pinned; future authoring does not alter accepted source |
| Conflict/denial/network error | Keep local buffer and explain recovery; no auto-retry approval against replacement source |

## 5. Exact source download

Download a retained **validated revision**, whether candidate, confirmed or selected last-run source; accurately label that state. The first slice excludes mutable/unsaved draft downloads. Selecting a historical revision for inspection/download never restores it as current or runs it. [FR-2/FR-7; CON-5]

The proposed protected ZIP contains:

| File | Required contents |
|---|---|
| `source.artifact.json` | Canonical UTF-8 artifact from the selected stored revision; code strings and originalText are preserved; SHA-256 equals its stored artifactHash |
| `manifest.json` | Export/schema/canonicalization versions; test/revision identity; artifactHash/algorithm; source/config/code identities; mode/origin/parent; allowed actor/timestamps/confirmation state; ordered stable step mapping where available; context digest and safe policy/runtime compatibility version strings; declared reference identifiers |

Recanonicalize with existing `ArtifactCanonicalizer` and reject integrity mismatch. The artifact hash covers artifact bytes, not the manifest or full ZIP. Promise canonical artifact content/code identity, not reproduction of an original HTTP or database JSON serialization. [FR-2/FR-5; data review; architecture proposal]

Use an explicit manifest allowlist. Exclude resolved variable/secret values, vault paths, ephemeral credentials, current execution-configuration values, bearer URLs, callback/storage keys, provider payloads and internal deployment settings. Existing source-safety policy must reject credential-bearing stored artifact text; silently redacting while claiming the original hash is prohibited. Derive filename from safe identifiers and use protected/no-store headers. A retention 410 is permitted only for a previously authorized tombstoned revision; otherwise preserve existing visibility/no-existence-oracle policy. [FR-8; architecture proposal]

The package is **Studio step source; runs in Studio**. It is useful for inspecting/downloading the exact revision; it is not a standalone test project or a portability guarantee. A future derived `.spec.ts` adapter needs its own version/hash and verified bindings/settings/secrets/setup contract. [FR-2; ASM-2; CON-5; research.json]

## 6. Persistence, migration and rollout

Extend existing `ui_tests` with mode/code identity and active/latest retained checkpoint pointers. Add append-only manual checkpoints with same-test/CSI ownership, base revision, ordered code/step IDs, saved-input snapshot/hash and authenticated actor/time. Retain bounded invalid or unvalidated saved manual work across mode changes; a checkpoint is not an executable revision. [FR-1/FR-4/FR-5; Dara review]

Extend existing captured preparation infrastructure with GENERATED_COMPILE/MANUAL_VALIDATION kind and full snapshot/F/manual identity. Every new candidate binds to a captured request. Store mode/code/checkpoint/manual parent and truthful provenance in immutable revisions. Keep `parentRevisionId` (edited source) distinct from incremental `baselineRevisionId`. Composite ownership foreign keys prevent cross-test/CSI parent or checkpoint links. Existing execution acceptance references remain authoritative. [FR-5/FR-8; DEC-4]

Create distinct successful revision events even when artifact hashes match across authors, policies, settings or generated/manual origins. Deduplicate identical retries of the same captured request, not independent events by content. Content-sharing can be considered separately without collapsing event/approval identity. [FR-5; NFR-2]

Future forward-only migrations must reconcile V18 captures, surviving V24 content uniqueness and the deliberately staged V19 cutover outside automatic Flyway migrations. Verify the actual applied ledger; checked-out migration files do not prove deployment. Drain incompatible publishers before changing dedup constraints; manual candidates cannot bypass V19 with null compile_request_id. Upgrade every capture/success/failure/timeout/repair/confirm/readiness/acceptance predicate, not only new routes. [FR-5/FR-6; complexity flags; data review]

Restore complete immutability protection equivalent to V18's row-wide comparison excluding only the first confirmation fields. V21/V24 enumerated triggers omit request metadata; new fields must not inherit that hole. Preserve checkpoint/request/outcome update/delete protection and revision parent/execution retention/FK rules. Mode changes, soft deletion and candidate replacement do not cascade away code evidence. No new source retention duration is invented. [FR-5; OQ-3; data review]

Proposed sequencing: formal PRD/ADR/OpenAPI amendments; explicit generated approval correction; backward-readable persistence/capture changes; coordinated drained-publisher cutover; fully guarded backend; frontend/MSW editor/review/export; integrated race/authorization/accessibility verification; enable feature. A disable switch preserves history/saved work and cannot restore auto-confirmation. [architecture proposal; complexity flags]

Historic auto-confirm records remain truthful historical facts. Before the approval-policy cutover, inventory affected current revisions and require explicit renewed review for their eligibility under the new policy; never fabricate evidence of a prior human review or rewrite historical actors. Exact operational rollout rules remain a release-owner decision before implementation rollout. [FR-3/FR-5; architecture proposal]
