# Editable Studio source: persistence and execution identity review

Status: proposal only; no schema or application changes. Reviewer: Dara, data engineering. Requirements: FR-1–FR-8 and NFR-2 in `requirements.json`.

## Recommendation

Retain the existing immutable revision and execution-reference model. Introduce a separately versioned manual code draft and explicit `GENERATED`/`MANUAL` authoring mode. Saving code does not update an existing revision. Validation captures one immutable preparation attempt, then creates an immutable candidate. The author explicitly confirms that candidate; execution accepts its exact identity under the draft lock. Deduplicate retries of the same preparation attempt, never separate authorship events merely because artifact hashes match.

Keep manual code preparation in the existing captured-attempt infrastructure, extended with a preparation kind such as `GENERATED_COMPILE` or `MANUAL_VALIDATION`. Manual validation invokes the existing bounded validator without an AI replacement step. This avoids a parallel revision trust boundary and works with the staged V19 invariant requiring a captured request for every newly inserted candidate.

## Counter options

| Option | Advantages | Costs and decision |
| --- | --- | --- |
| Extend `sourceRevision` to include checklist and manual code saves | Existing pair checks would invalidate many stale operations automatically. Fewer counters. | Changes an established checklist/context identity across classifiers, DTOs, compiler captures and incremental baselines. Mode, request and code hash checks remain necessary; no automatic safety guarantee. Viable with an explicit broad contract change, but less clear here. |
| Separate `codeDraftRevision`, retain source/configuration meanings | Clear checklist, execution configuration and code identities; manual editing does not masquerade as a changed English checklist. Explicitly detects same-checklist code changes and mode transitions. | Requires an exhaustive predicate audit and additive persistence/contract fields. Recommended because the existing authoring identity and incremental work already distinguish checklist/context from compiled output. |
| Artifact hash alone | Convenient byte-content comparison and cache key. | Cannot establish author, lineage, current editor state, confirmation or an individual validation event. Rejected as execution identity. |

`codeDraftRevision` is a monotonically increasing per-test counter for accepted code saves and explicit mode transitions. It is not reset when switching modes or restoring an older artifact. Checklist/context changes keep their existing source/configuration classifications. Any change invalidates the full runnable identity; unchanged manual text remains available for revalidation rather than regeneration. A validation retry has a separate attempt ID and need not increment the code counter. Ordinary identical-save retries use an idempotency token; an intentional new authorship action is recorded separately.

## Conceptual persistence additions

Names describe the design; final migrations and API names require implementation design review.

| Record | Proposed fields/invariants |
| --- | --- |
| Mutable `ui_tests` draft | `authoring_mode`, `code_draft_revision`, active manual-checkpoint pointer, latest retained manual-checkpoint pointer, active preparation request pointer. Checklist/configuration counters remain unchanged in meaning. Persisted manual code/hash may be read through the checkpoint rather than duplicated on this row. |
| Append-only manual authoring checkpoints | UUID, owning test/CSI, accepted code-draft counter, parent/base revision UUID, ordered stable step IDs and editable code strings, editor-snapshot hash, source/configuration counters and context digest at save, authenticated creator and timestamp. Save records bounded source text even if its AST later fails validation. A checkpoint is explicitly unvalidated authoring data, never an executable revision. |
| Immutable preparation request | Existing request ID plus preparation kind, mode, code-draft counter, manual checkpoint/code snapshot hash, parent revision, exact source/configuration and authoring/context snapshot, declared references, validation/runtime policy fingerprint, principal/time/deadline. Capture under one draft lock; commit before asynchronous work. Generated requests keep generated input; manual requests additionally carry the user source. |
| Immutable `ui_test_revisions` | Captured mode/code counter, manual parent and checkpoint identity, artifact/hash, existing source/configuration/authoring snapshots, validator/runtime provenance, actor and capture identity. New manual code has honest manual provenance; copied AI provenance is not evidence that AI created edited code. First confirmation remains the only permitted update. |
| Execution acceptance snapshot | Existing revision UUID, artifact hash and configuration/runtime snapshot; add mode, code counter and preparation/parent identity as needed for diagnostics. Runtime loads the accepted immutable revision, never a mutable checkpoint. |

Manual `parent_revision_id` denotes the revision edited. Keep it distinct from `baseline_revision_id`, whose existing meaning is incremental compile reuse eligibility. Use composite foreign keys `(parent_revision_id, test_id, csi_id)` and equivalent checkpoint ownership keys so another test/CSI revision cannot become a parent. Require an existing earlier revision for a manual parent; reject mismatched ownership before exposing its content. A server-created checkpoint supplies actor/time; clients cannot claim those fields.

The checkpoint archive preserves saved but invalid or never-validated manual work after a mode switch. Switching to generated mode advances the code counter and changes the active mode/pointer, while the last manual checkpoint and all immutable revisions remain retained. Unsaved browser text prompts the local Save/Discard flow before switching. Restoring a checkpoint creates a new checkpoint/counter event under current source/context; it does not rewrite its original record or claim that old confirmation still applies.

## Atomic transitions and freshness

All execution-affecting draft writers lock or conditionally update the same draft row. Code save compares the caller's expected source/config/code counters, mode and base/checkpoint identity against the persisted row; the context digest and code snapshot hash are independently verified. On mismatch, return the existing conflict pattern and preserve local text for reconciliation. On success, append the checkpoint, advance the code counter and clear current candidate/request/readiness state in one transaction. Keep the previous confirmed pointer as historical evidence; readiness must compare the new code counter/mode/hash, so that pointer is no longer runnable.

Preparation capture, successful publication, failed publication, timeout settlement, cancellation, confirmation and acceptance must each enforce their applicable complete identity. For publication this includes current request ID, source/config/code counters, mode, authoring/context digest and captured manual snapshot identity. Old generated success or failure must not replace manual work or clear its newer candidate. An automatically triggered generated compile must refuse while the active mode is MANUAL. Only an explicit conditional mode switch permits regeneration. Manual preparation does not modify the saved code bytes.

Readiness remains a single consistent persisted-draft/confirmed-revision read. It adds code counter/mode comparison, independently verifies the current manual snapshot/hash against the confirmed artifact and keeps all existing hash/reference/runtime checks. This protects the case where an implementation forgets to clear a request or change `compile_status`. Do not treat `compile_status = READY` as sufficient. Local unsaved edits block Run in the UI because the server cannot observe browser-only text; API execution always refers to persisted confirmed source.

Confirmation matches revision UUID, artifact hash, complete freshness tuple, captured preparation identity and current policy. It moves AWAITING_CONFIRMATION to READY and writes confirmation actor/time once. Validation success does not confirm. Execution acceptance repeats persisted readiness under the existing draft lock and stores that exact revision; a concurrent save cannot interleave between validation and snapshot creation. Existing execution idempotency replay returns the original accepted execution, not an execution of the latest code.

## Content deduplication and append-only protection

The new path allocates a revision for each successful distinct preparation event; `artifactHash` remains a canonical content-integrity value. A MANUAL event whose source happens to equal GENERATED source still has its own actor, parent, request and confirmation. Two authors producing equal content likewise retain distinct accepted checkpoint/preparation events. Retrying the same request ID returns its existing outcome/revision, after verifying identical captured input and principal. A content-addressed blob store could share bytes in the future while the revision/event records remain separate; it is unnecessary for this first slice.

Implementation must explicitly reconcile V18/V24 and staged V19 deployment states. A safe future migration replaces conflicting content uniqueness with request-event uniqueness while retaining all historical rows, hashes and confirmation values. During cutover, drain incompatible publishers as the current V19 runbook requires. The old content-reuse writer cannot remain enabled once its supporting constraint is removed. Extend the existing immutable request capture and revision insert-check trigger with mode/code/parent/checkpoint fields, and ensure the V19 require-request trigger accepts the same captured preparation model. Do not bypass it by inserting manual candidates with a null request ID.

Restore default protection of all revision fields via the V18 row-wide comparison excluding only first-confirmation fields, or provide equivalent complete enforcement proven by negative tests. Preserve immutable request/outcome/checkpoint UPDATE and DELETE protections. Revision removal is additionally constrained by parent/execution foreign keys and retention rules; the existing revision UPDATE trigger alone is not a universal deletion ban. Do not add a generic mutable `updated_at` to append-only evidence merely to satisfy a table convention.

## Retention and downloads

Revision and checkpoint retention must be explicit. The initial design retains them alongside existing revision history; no cascade from draft soft deletion, mode changes or current-candidate replacement. Parent-linked or execution-referenced revisions cannot be pruned independently. An approved future retention policy must cover attempts, checkpoints, revision DAG edges, executions and exported evidence together; no arbitrary retention duration is asserted here.

Download reads an authorized, retained immutable revision. The artifact is the same stored source representation, including its code strings, not a freshly regenerated translation. Include revision UUID, artifact hash/canonicalization meaning, schema version, mode, actor/time, parent and confirmation state in a metadata envelope/manifest; clearly separate manifest bytes from the artifact bytes covered by the hash. Canonical JSON may differ in whitespace/key order from the original transport, so promise identical artifact content and code strings, not an unattested original HTTP byte stream. Never include resolved secrets. An unconfirmed validated candidate must be labeled accordingly; historical downloads remain possible when policy revocation prevents execution, subject to authorized history-read access. Soft-deleted test history needs its own authorized lookup rather than ordinary visible-draft retrieval.

Working text export, if introduced later, must use a distinct unvalidated-draft format. This proposal's download does not silently substitute local unsaved text for the selected immutable revision. A standalone Playwright package would be a separately identified derived artifact with its own adapter/runtime contract, not a new name for the existing Studio step artifact.

## Required implementation evidence

Before rollout, prove concurrent saves reject stale counters; equal generated/manual or two-author content preserves distinct lineage; same-request replay is idempotent; delayed generated success/failure cannot overwrite manual state; checklist/config changes retain manual work but block Run; mode switch/restore retains saved invalid code; tampering any new immutable column is rejected; foreign-key ownership prevents cross-test/CSI lineage; invalid manual code creates no runnable candidate; confirmation is explicit for both modes; accepted execution survives subsequent edits; and revision download verifies its canonical hash without resolving secrets. Tests should exercise actual database constraints and publication interleavings, including both pre-cutover and fully migrated compatibility states needed for deployment.
