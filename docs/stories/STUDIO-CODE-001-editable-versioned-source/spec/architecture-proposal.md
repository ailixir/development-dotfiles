# Editable Studio source and execution versioning

Owner: Aria / architect. Status: evaluated proposal, not an accepted ADR or implementation authorization. Inputs: requirements.json, research.json/research-notes.md, ux-analysis.md and Dara's data-versioning-review.md. Repository evidence includes the existing dirty worktree; production behavior was not exercised during this analysis.

## Recommendation and requirement boundary

Use native append-only Studio source revisions. Let an authorized author edit a separate bounded source draft, validate the entire exact artifact without AI rewriting, review the resulting immutable candidate, explicitly confirm it, and execute that identified revision. Download the selected revision's exact canonical artifact plus a safe identity manifest. This extends the present product: PRD.md:99,110-113 requires exact immutable source confirmation, but neither editing nor source download is explicitly promised; source downloads originate from USER-1 (FR-1/FR-2).

The default proposal assumes editing the supported Studio step language, not executing arbitrary TypeScript projects (ASM-1). A standalone runnable Playwright package is separate future scope (ASM-2). These assumptions qualify the recommendation; they do not prevent evaluation of the alternatives.

| Option | Execution authority and tradeoff | Decision |
|---|---|---|
| Native immutable manual candidates | Reuses CSI authorization, whole-artifact validation, confirmation, revision retention, dispatch and evidence. Adds durable manual draft, attempt snapshot and provenance. | Recommended; smallest coherent extension. |
| Mutable code overrides at Run | The visible code can move between approval and execution. Making it safe requires snapshotting and validating it into an immutable revision first. | Reject as execution authority; a mutable draft is allowed before candidate creation. |
| Git repository as authority | Can support developer collaboration, but adds repository credentials/CSI access, ingestion, merge reconciliation and runtime manifests. A branch/tag cannot identify the exact reviewed bytes without resolving an object and importing it. | Later optional import/export integration; imported content must still become a native validated revision. |
| Unrestricted Playwright/TypeScript files | Imports, control flow, dependencies and arbitrary code exceed the existing AST and operation-only child protocol; requires a separate isolation, dependency, reporting and credential policy. | Separate product/runtime architecture, not a hidden editor enhancement. |

The runtime stays bounded: studio-runner/src/validator/index.ts:43-114 produces typed operations; executor/executor.ts:12-18 executes only those operations. Existing supported sequences of awaited calls per step remain supported; CodeTab.tsx:15's single-call comment does not define the actual grammar. No new editor or execution dependency is necessary for the first slice (research.json).

## Required reconciliation of current approval behavior

The active dirty compile path calls publishAcceptedCandidate (CompilePipeline.java:361-370). CompileStateService.java:281-303 stamps confirmed_by/confirmed_at and READY as part of preparation. CompilePipeline.java:147-149 explicitly treats Run as approval before the generated bytes exist. This conflicts with PRD.md:99,110 and the exact-candidate review boundary. Requiring confirmation metadata at readiness is insufficient when preparation fabricates that metadata.

Propose one policy for generated and manual source: preparation publishes AWAITING_CONFIRMATION without stamping approval; only an authenticated explicit confirmation of the displayed immutable revision/hash writes the write-once confirmation metadata. Run may prepare and open review; Confirm and Run may approve the displayed revision and then request its execution. No save, compile, validate or download action approves newly created source. Retire the auto-accept publication path for both modes. Preserve old records truthfully; do not infer historic user review or rewrite confirmation actors. Release owners must reconcile pre-cutover auto-accepted current revisions explicitly rather than grandfathering them as proven human reviews (FR-3/FR-5; UX-05/06).

This proposal explicitly supersedes ADR-002 §30's confirmed-only Code view for a distinct editable Draft surface. The Confirmed view retains independently read confirmed identity/bytes and never substitutes a candidate. New revision export/history consumers also require a deliberate contract amendment; this proposal does not silently reverse §21's earlier rejection of an unnecessary generic revision route.

## Version identities

Choose an additive codeDraftRevision, rather than expanding sourceRevision's meaning. StudioService.java:733-746 currently associates sourceRevision with stable checklist step identity/text and configurationRevision with execution context. A code-only save should not pretend the English was edited, erase its useful identity or accidentally feed compiler incremental heuristics.

| Identity | Meaning |
|---|---|
| sourceRevision | Existing checklist order, stable step identities and original English source identity. |
| configurationRevision + authoring context digest | Existing generation/execution-affecting configuration, structured context, nonsecret referenced values and selected evidence identity. |
| codeDraftRevision | Monotonic counter for persisted manual code and authoring-mode changes; not incremented per keystroke. |
| authoringMode | GENERATED or MANUAL; governs which preparation path has authority. |
| codeDraftHash | Server-computed hash of the bounded saved manual snapshot, including ordered stable step IDs/code and base revision/mode; null for ordinary generated authoring. |
| revisionId | Immutable validated artifact/context/provenance event identity. Different revision events can have identical artifactHash. |
| artifactHash | SHA-256 over canonical artifact UTF-8 bytes only; not proof of approval or globally unique execution version. |
| attemptId / requestId | Immutable captured preparation attempt; retry deduplication identity. |
| artifact version | Artifact schema version, unrelated to any revision counter. |

The freshness token F is {sourceRevision, configurationRevision, codeDraftRevision, authoringMode, authoringContextDigest, codeDraftHash}. The server computes hashes/digests; client-supplied values are expectations for comparison, not authoritative recomputation. Existing referenced-value/context digest identity must be captured from current saved authoring and compared. Persisted execution/version labels use revisionId, with an abbreviated hash as a separate content hint (FR-5/FR-6; NFR-2).

New local edits do not mutate server readiness until saved; opening Edit only creates a local buffer and does not activate persisted MANUAL authority. The frontend dirty guard prevents dispatch while local changes are unresolved. A changed manual save or explicit mode switch advances codeDraftRevision and invalidates the current candidate/authoring diagnostics under a conditional write; an idempotent retry/no-op against the same saved checkpoint does not manufacture an edit or revoke readiness. The historical confirmed pointer stays readable. Configuration-only changes can yield a new revision with identical artifactHash and still require reconfirmation.

Using sourceRevision alone would simplify existing pair-based CAS only if every authoring, hash, save, compile and readiness consumer adopted broader semantics. It does not eliminate manual-source storage, provenance or mode guards. Separate code identity is clearer and is supported by Dara's persistence review; its cost is mandatory extension of every guard, not just the new endpoint.

## Authoring and preparation lifecycle

1. **Start editing:** derive a working buffer from an authorized retained candidate/confirmed revision belonging to the same test/CSI. Preserve step IDs/order and frozen originalText. Edits change only each step's supported code. No candidate exists merely because Edit was clicked.
2. **Save:** save the bounded manual snapshot and its base revision under F, with explicit MANUAL authority. The server assembles/checks artifact structural fields against saved checklist identity. Incorrect mapping, references and credentials cannot be hidden in client-owned JSON. The mutable draft can hold invalid syntax for correction within request/resource limits; it is not runnable.
3. **Validate:** capture one immutable MANUAL_VALIDATION attempt under a draft lock, with exact code snapshot/hash, F, checklist/authoring identity, declared references, reference policy and runtime/validator pins. Do not hold a transaction across validator network work. Do not call the LLM or repair manual code. Whole-artifact validation returns typed operation summaries/diagnostics.
4. **Publish:** settle success only if attempt identity, F, lifecycle and deadline still match. Persist a new immutable revision with manual provenance and parentRevisionId, then publish AWAITING_CONFIRMATION. Settlement and candidate insertion are atomic; losing late results do not leave runnable candidates. Failure diagnostics are similarly bound; late failures cannot clear newer success.
5. **Review and confirm:** read source/settings plus validated operation summaries. Show original English as Original checklist context and user edits as manually authored behavior, never as AI-verified English equivalence. Confirmation submits revisionId, artifactHash, attemptId and F; writes approval once only when the exact current candidate and current compatibility/reference policy still match.
6. **Execute:** submit the reviewed confirmed revisionId/hash and F. Under the existing acceptance lock, require that identity to be the current compatible confirmed source; snapshot it into the execution. Later edits affect future authoring only. Dispatcher/runner consume the accepted immutable revision, never the current draft.

Readiness continues to be a predicate over the confirmed revision and current saved inputs, not compile_status (ExecutionReadinessService.java:24-49). Add mode/code counter/hash/context identity comparisons to that predicate; setting STALE alone is insufficient. A failed optional generated recompilation of unchanged input must continue to preserve existing confirmed readiness. A saved code edit must invalidate readiness even when someone sets compile_status READY (FR-3/FR-6).

## Manual authority and regeneration

All preparation entry points honor authoringMode: page Run, rerun, save listeners, inference endpoints, repair retries and incremental compilation. Ordinary generated compilation in MANUAL returns an explicit conflict requiring deliberate regeneration; it cannot overwrite a saved manual draft. Initially exclude manually authored revisions from incremental generated baselines. Generated regeneration selects a compatible generated-only baseline or compiles all steps; never use manual corrections as model-authorized provenance (FR-4/FR-5; research recommendation).

A checklist/context change makes the manual draft stale as a whole. If stable step mapping/text is unchanged, the user may explicitly review the changed context and revalidate the preserved code against the new snapshot/policy. Structural/text changes cannot be positional-remapped silently: retain manual work for copy/recovery and require explicit generation of a compatible artifact in this first slice. No code-to-English reverse translation is implied.

Generate from Steps is a conditional authority switch that advances codeDraftRevision, clears active manual code identity and captures fresh generated inputs. Preserve immutable history and the latest saved manual working checkpoint, even if invalid/unvalidated; distinguish that checkpoint from an executable revision. Protect unsaved work with Save/Discard/Keep editing before switching. The old generated attempt cannot publish after this switch, even if English/configuration counters are unchanged (FR-4/FR-6; UX-07).

## Validation and provenance compatibility

Manual source uses the same complete schema/AST/resource/credential/reference checks as generated artifacts. Keep one artifact entry per originalText with valid ordered step mapping; multiple supported awaited calls per step are permitted within existing caps. Existing artifact schema limits include 100 steps and 2000 code characters per step; use the stricter applicable schema/validator/API bound, not an invented unrestricted editor payload.

ADR-SC-003 reference policy is derived from saved authoring, not invented from manual code. VersionedIntentDeriver.java:39-79 checks immutable authoring identity/text alignment and derives policy; IntentRevisionVerifier verifies saved derivation/provenance. Manual revisions capture those same immutable authoring inputs and versioned required/allowed reference policy. Code cannot omit required references or introduce undeclared/disallowed ones. Changing required references is an explicit authoring/context operation, invalidates freshness, and requires renewed validation/confirmation. Legacy authoring retains its existing source-token reference rule; manual source does not obtain an authoring-v2 bypass (FR-8/NFR-1).

The historical expectedIntent/English-derived expectation is retired by ADR-SC-003; do not resurrect it as an equality check forcing manual locators/actions to remain generated behavior. The current required/allowed reference constraint remains authored policy, while behavior summaries are recomputed from newly validated typed operations. This permits useful locator/assertion corrections without claiming English equivalence.

Provenance records source origin MANUAL, actual editing/validation actor, base revision, attempt identity, policy/derivation version, validator, executor and runtime compatibility pins. A manual validation fingerprint identifies validation/policy/runtime inputs; it is distinct from the generated compiler fingerprint and includes no fabricated LLM model/prompt/response fields. Parent generated provenance may be referenced separately; do not label edited source as model output. Current exact-match compatibility checks apply to manual and generated candidates using truthful shared validator/syntax/runtime fields; revoked/incompatible source stays readable as history but cannot run. Runner admission revalidates the full immutable artifact and policy into typed operations again; child messages remain operation-only (FR-3/FR-5/FR-8).

Artifact hash is content identity; revision event and approval are separate. Identical code produced by two authors, or validated under two different policies/configurations, must not acquire the wrong author/provenance through content deduplication. Deduplicate retries of the same immutable attempt, not independent events with equal hashes. Consult data-versioning-review.md for forward-only migration, request binding, composite parent ownership and write-once trigger design.

## Proposed public contract surface

Names below are a concrete proposal for contract review; the new routes/fields do not exist today. Paths are relative to the existing Studio API base (/api/v1/studio); authoring-v2 identity is a payload/domain version, not an invented second route namespace. All use the centralized frontend API client and equivalent MSW handlers. Apply authentication, existing CSI visibility and lifecycle checks before returning source or distinguishable metadata. Existing no-existence-oracle refusal behavior remains authoritative; authorize the persisted owning CSI, not a submitted CSI.

| Operation | Proposed request and successful response | Important refusal |
|---|---|---|
| GET /tests/{id}/code-draft | Saved source mode, F, base revision and ordered code blocks; 200. Include additive draft metadata in detail reads, omit heavy draft/artifact projections in lists. | 401/403 under existing visibility rules. |
| PUT /tests/{id}/code-draft | expected F, mode MANUAL, baseRevisionId, ordered {stepId, code}; conditional durable save, new F, 200. mode GENERATED is explicit Generate from Steps, preserving the prior manual checkpoint. | 400 malformed/mapping/bounds/credential failure; 409 STALE_REVISION or stale base; 401/403. |
| POST /tests/{id}/code-draft/validate | expected F; 202 with requestId and captured F. Existing request-state read exposes bounded status/diagnostics/current candidate. | 409 STALE_REVISION or wrong mode; lifecycle 409; 400 unsafe input; 401/403. Accepted validation failure becomes NEEDS_REVISION, unavailable validator leaves retryable authoring. |
| Existing compile preparation | Extend expected/captured identity to F; reject MANUAL unless the deliberate authority switch already succeeded; generated success awaits review. | 409 MANUAL_SOURCE_ACTIVE / STALE_REVISION. |
| Existing confirmation | Add expected code/mode/context/hash and request identity to revisionId/artifactHash/source/configuration fields; 200 after exact approval. | 409 STALE_CANDIDATE for moved/corrupt/incompatible input; 401/403. |
| Existing execute | Require expected confirmed revisionId/artifactHash and F for new code-capable contract; normal accepted response unchanged. | 409 when identity differs or approval is no longer current; existing authorization/quota/disabled refusals remain. |
| GET /tests/{id}/revisions/{revisionId} | 200 safe SourceRevisionDetail: exact artifact/hash/identity, confirmation state, safe provenance, ordered step mapping and validated behavior summary. Provides candidate/confirmed/last-run inspection through the same protected revision reader used by export. | 401/403; authorized retention expiry follows the source-download policy. |
| GET /tests/{id}/revisions/{revisionId}/source-download | Authorized retained validated revision, 200 application/zip attachment containing source.artifact.json and manifest.json. No arbitrary filesystem or object-store paths. | 401/403; 410 only for a previously authorized revision whose retention tombstone exists, otherwise follow existing no-existence-oracle policy. |

Capability/version the changed confirmation/execute request contract and update first-party clients/mocks together; do not let an old client silently bypass F on a code-capable draft. Pre-cutover generated-only clients can use the old contract only during a deliberate compatibility window when the code feature is disabled. Final rollout removes that bypass or enforces equivalent server identity matching.

Execute idempotency digest includes only submitted stable request fields (test, principal, route, expected revision/hash/F), never later server state. An identical key/request replay returns the original accepted execution after later authoring edits; reusing the key for a different requested revision is a conflict. The server must check existing idempotent acceptance before requiring that old submitted F still be current (FR-5/FR-6; NFR-2).

## Exact authorized source download

The ZIP contains canonical UTF-8 source.artifact.json; its SHA-256 equals the selected revision's artifactHash. Recanonicalize the persisted artifact using the same ArtifactCanonicalizer rather than trusting database JSON text formatting, and refuse integrity mismatch. manifest.json identifies export schema version, testId, revisionId, artifactHash/algorithm/canonicalization version, artifact schema, source/configuration/code identities, mode/origin, parent revision, validation/confirmation actor/timestamps when present, ordered stable step mapping when available, context digest and safe policy/runtime compatibility version strings. Use an explicit allowlist, not serialization of raw provenance/configuration/dispatch snapshots.

Exclude resolved variables/secrets, vault paths, ephemeral credentials, execution configuration values, target bearer URLs, runner callback/object-store keys, provider request bodies and internal runtime deployment settings. Include only reference identifiers needed to interpret source. Artifact code/originalText remains exact; if persisted source unexpectedly contains credentials, fail through existing source safety policy instead of redacting and claiming the redacted bytes match the canonical hash. Server derives the attachment filename from safe test/revision identifiers and sends protected/no-store response headers.

This ZIP is a Studio revision source package; it does not claim standalone local execution. Candidate, confirmed and last-run revision downloads identify their actual state; a working/unsaved draft never exports under immutable revision identity. Draft export and a derived runnable .spec.ts package are outside the first slice (FR-2/FR-7/FR-8; ASM-2).

## Persistence and rollout feasibility

Detailed database design belongs to Dara; see data-versioning-review.md. Conceptually extend the existing durable captured request ledger with MANUAL_VALIDATION and mode/code snapshot/parent context so the drained-publisher V19 cutover requirement remains satisfied. The staged backend/db/cutover/V19 contract requires a captured request for new revisions; a separate manual table with null compile_request_id would fail that invariant. Preserve attempt event identity and all immutable snapshot fields in the revision trigger. Remove/replace incompatible content-unique identities prospectively; keep old revisions and confirmations untouched.

Roll out in coordinated phases: amend PRD/ADRs/OpenAPI/state expectations; repair explicit generated approval and prove it; introduce backward-readable database/attempt snapshot changes; drain old publishers and apply deliberate capture/dedup cutover; enable new guarded backend paths; update frontend/MSW editor/approval/export; enable the feature after race and authorization gates. Do not run old pair-only publishers concurrently with manual authors. A kill switch disables new editing/validation/export behavior while preserving existing readable history; it cannot restore auto-confirmation or erase saved manual work.

Critical migration reviews: inventory the actual applied Flyway ledger and staged V19, ensure no dirty unpublished migration is treated as deployed, verify every late settlement and listener honors mode/code identity, preserve retention/FK rules for active draft/parent and accepted execution, and reject any attempted rollback that re-enables obsolete writers. Historical auto-confirm records remain historical facts; current eligibility after approval-policy cutover is a deliberate product/release decision requiring explicit renewed review for affected tests.

## Verification needed before implementation completion

- Generated preparation and manual validation create unconfirmed immutable candidates; only exact explicit review writes approval; Confirm and Run cannot execute another candidate after a race.
- Two source saves have one conditional winner; stale save preserves client code; late generated/manual success, failure, timeout and repair cannot overwrite a newer mode/code/context.
- Equal artifact hashes across new attempts/authors/policy/configuration remain distinct provenance events; retry of the same captured attempt is stable; every added immutable field resists mutation.
- Code-only save blocks readiness even if compile_status is forced READY; unchanged confirmed source remains runnable after optional generated preparation failure; accepted executions remain pinned after subsequent edits.
- Full artifact and reference-policy validation rejects forbidden nodes/methods, extra/missing references, mapping mismatch and bound violations; no LLM call occurs on manual validation; runner child still refuses source text.
- Export canonical bytes match hash; manifest/state identifies the selected candidate/confirmed/run revision; CSI denial precedes bytes; secrets/configuration/runtime credentials are excluded; corrupt source cannot be exported with a false identity.
- Frontend code survives tab/background refresh, participates in save/navigation guards, protects regeneration and presents accessible diagnostics; MSW and real API share the same lifecycle/race contracts.
