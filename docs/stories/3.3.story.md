## User Story

**As a** user browsing CSI systems in the Checks module,
**I want** the CSI list and detail pages to load data from the real backend,
**so that** I see the actual CSI inventory from the database instead of hardcoded mock data.

---

## Acceptance Criteria

- [ ] **AC-1:** `csiApi.listCsis()` calls `GET /api/v1/csi` with query params mapped: FE `page` (1-based) → BE `page` (0-based), FE `limit` → BE `size`. Filters: `businessUnit`, `criticality`, `environment`, `status`, `search`. Response normalized via `normalizePageResponse`.
- [ ] **AC-2:** `csiApi.getCsiById()` calls `GET /api/v1/csi/{id}`. Response mapped: BE `CsiDto` → FE CSI type. Field mapping: `id` (string, not UUID — CSI IDs are VARCHAR(20)), `name`, `description`, `businessUnit`, `criticality`, `ownerEmail`, `environment`, `status`, `metadata` (JSONB), `createdAt`, `updatedAt`.
- [ ] **AC-3:** CSI mapper `mapCsiDtoToEntity(dto: BackendCsiDto): CSI` created in `src/services/api/mappers/csiMapper.ts`. Handles metadata extraction for fields the FE expects but BE stores in JSONB (e.g., `applications`, `tags`).
- [ ] **AC-4:** `csiSlice.ts` thunks updated to use the real API + mapper. State shape unchanged.
- [ ] **AC-5:** CSI select/autocomplete components continue to work. NOTE: `csiApi.searchCsis()` remains on MSW until story 3.6 builds the BE endpoint. The search function gracefully falls back if the endpoint returns 404.
- [ ] **AC-6:** `csiApi.getBusinessUnits()` remains on MSW until story 3.6. No changes to the function signature.
- [ ] **AC-7:** `csiApi.getCsiHealth()` remains on MSW until story 3.6. No changes.
- [ ] **AC-8:** Add `csi` to `VITE_DISABLE_MSW_DOMAINS` cutover comment in `.env.development`. NOTE: only core list/detail endpoints are wired; search/health/business-units remain mocked until 3.6.
- [ ] **AC-9:** `npm run type-check` passes.
- [ ] **AC-10:** CSI-related pages/components render correctly with real backend data (manual verification).

## Implementation Notes

### Backend CsiDto shape
```json
{
  "id": "174523",
  "name": "Trade Processing System",
  "description": "Core trading platform...",
  "businessUnit": "Markets & Securities Services",
  "criticality": "CRITICAL",
  "ownerEmail": "david.chen@citi.com",
  "environment": "PRODUCTION",
  "status": "ACTIVE",
  "metadata": { "tags": [...], "applications": [...] },
  "createdAt": "2026-04-17T...",
  "updatedAt": "2026-04-17T..."
}
```

### Partial domain disable strategy
Since `VITE_DISABLE_MSW_DOMAINS=csi` would disable ALL CSI MSW handlers (including search/health which aren't in BE yet), the migration needs a per-endpoint strategy:
- Option A: Don't disable the MSW domain yet — let all calls hit MSW, override specific endpoints in csiApi to call BE directly (set `__doNotRetry` flag or use a different axios instance).
- Option B: Keep MSW enabled for CSI domain, but have the csiApi functions for list/detail explicitly call the real backend URL.
- **Recommended: Option B** — csiApi.listCsis and getCsiById build full URLs bypassing MSW. Other functions stay as-is. When 3.6 completes, fully disable the domain.
